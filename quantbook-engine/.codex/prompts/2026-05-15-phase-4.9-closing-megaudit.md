## Areas to probe (in priority order)

### A. Cross-sub-phase invariants

These are the "only surfaces when N≥2 sub-phases meet" issues.

1. **Canonical-storage round-trip determinism (design § 4.4
   contract).** Save a workbook with R1C1 mode + DE locale and a
   formula stored canonically. Reload. Now `set_formula` again with
   text that should canonicalize to the same A1+EnUs form. Does the
   PlanCache hit, OR does the loaded workbook's separate process
   start fresh and re-bind? If start-fresh, no problem; if there's
   any shared cache state, check for staleness.

2. **`@` AST → canonical text round-trip.** Walk through:
   `parse("@Sheet1!A1")` → AST with `ImplicitIntersection(CellRef
   { sheet: Name("Sheet1"), col: 0, row: 0 })` → `print_with(.., A1,
   EnUs, None)` → `@Sheet1!A1` or `@Sheet1!A1` ? The W5-143
   printer emits `@<inner>` where inner's emission includes the
   sheet prefix. Confirm the AST round-trip test pinned at
   `printer::tests::sheet_at_cellref_round_trips_via_ast` is
   correct AND that no production code path produces the alternate
   `Sheet1!@A1` shape (it's accepted on PARSE but never emitted
   on PRINT). Verify no test pin asserts the wrong order.

3. **Op-log replay × canonical-storage interaction.** Producer
   writes `R[-1]C` in R1C1 mode at cell (1, 0). Canonical storage
   stores `A1`. Op-log emits `PutFormula { text: "A1" }`. Replay
   into a fresh workbook (still default A1 mode) re-applies the
   canonical text. Does the replay's `lex_with(A1, EnUs)` correctly
   re-bind? AND if the producer also emitted `Op::SetReferenceMode
   { R1C1 }` BEFORE the formula, does that change anything? (Per
   design canon: it shouldn't — the stored text is canonical
   regardless of mode.)

4. **Implicit intersection × range × site interaction.** The 4.9.H
   binder narrows `@A1:A10` at bind time using `site.cell`. The
   set_formula path passes `BindSite::at_cell(addr)`. But the
   PlanCache key is `(canonical_text, sheet, name_gen)` — NOT cell-
   specific. If the SAME canonical text `@A1:A10` is bound at cell
   (5, 0) → cached as `CellRef(A6)`, then bound at cell (10, 0) →
   cache HIT returns `CellRef(A6)` (WRONG — should be A11). Check
   whether this collision exists and whether the cache key needs
   to include cell coords for `@`-bearing formulas.

5. **Workbook-scope mode/locale change × stored formulas.** Per the
   W5-148 `reference_mode_change_leaves_stored_formula_text_canonical`
   test, the stored text stays canonical when the user switches
   modes. But: does the PlanCache get invalidated? If a formula
   was bound at cache miss, the plan is stored. The next time
   set_formula sees the same canonical text, it cache-hits with the
   pre-mode-change plan. That's actually fine (the plan doesn't
   depend on mode). But: confirm.

### B. R1C1 forms — parser/printer/binder triangle

6. **AxisSpec arithmetic correctness.** `R[-1]C[2]` at anchor
   (5, 5) → ExprPlan::CellRef { row: 4, col: 7 }. Anchor at (0, 0)
   with R[-1] → resolved row would be -1. The W5-140 binder uses
   i64 to detect underflow → `BindError::R1C1OutOfBounds`. Verify
   the i64 arithmetic doesn't have a sign-extension bug for
   AxisSpec::Rel(i32::MIN).

7. **Mixed-relativity range rejection coverage.** `build_range`
   checks `axis_relativity_matches(a_row, b_row)` AND
   `axis_relativity_matches(a_col, b_col)`. Per-axis. What about
   `R1C[1]:R10C[5]` — both rows absolute, both cols relative.
   Should that be accepted? My read of design § 3.1 says yes (each
   axis independently consistent). Confirm the existing parser
   tests cover this case and not just "all-or-nothing relativity."

8. **R1C1 absolute axis bound = `MAX_ROW + 1` / `MAX_COLUMN + 1`.**
   The lexer accepts `R1048576C16384` (= MAX_ROW+1, MAX_COLUMN+1)
   and emits AxisSpec::Abs(1048576) / Abs(16384). The binder maps
   `Abs(n) → n - 1` (0-indexed). `1048576 - 1 = MAX_ROW`. OK. But:
   the lexer rejects `R1048577` as `RowTooLarge`. Verify the
   bound is exactly `MAX_ROW + 1` (1048576) on the lexer side, not
   off-by-one.

### C. Locale handling — printer / loader / op-log triangle

9. **Locale `Unknown` propagation.** The W5-145 qbook v7 loader
   captures unknown locale strings to `LocaleWire::Unknown(s)` and
   surfaces `QbookError::UnknownLocale { found }`. The W5-146
   op-log replay has the parallel path: `LocaleWire::Unknown(s)` →
   `ReplayError::UnknownLocale { index, found }`. But: is there
   any production code path where an unknown locale could be
   SAVED? (The save-side `from_runtime` only emits canonical
   variants.) If yes, we have a save-side bug. If no, we're fine.

10. **Locale × number printing precision.** The W5-142 printer
    swaps `.` → locale glyph in Rust's f64 Display output. What
    about numbers in scientific notation? `1e-10` prints as
    `0.0000000001` (Rust f64 Display) — has a single `.`. In DE,
    the swap produces `0,0000000001`. Confirmed by the
    `print_with_de_locale_small_fraction` test. But what about
    `format!("{n}")` producing an actual `e` notation (very large
    or very small magnitudes)? Verify the swap doesn't accidentally
    convert `1e10` → `1,10` or similar.

11. **DE/FR symmetry.** Locale `Fr` is documented as identical to
    `De` per design § 3.2. The W5-142 tests have one FR-specific
    test but most are DE. Spot-check that FR doesn't diverge in
    any helper or table.

### D. Implicit intersection — design § 3.3 rule coverage

12. **Rule 7 (array result) — what's the current behavior?**
    W5-144 deferred this to a "known gap" — array-returning
    functions under `@` return `#CALC!` per the pre-existing
    4.7.G limit. The user-visible impact: `@TRANSPOSE(A1:A10)`
    returns `#CALC!` instead of A1 (top-left). Should this be
    a HIGH (since TRANSPOSE+@ is a documented Excel pattern) or
    MEDIUM (rare in practice)?

13. **Rule 9 (StructuredRef inner) — is_this_row patch
    correctness.** W5-144 patches `is_this_row: true` on the inner
    StructuredRef result. Confirm this doesn't break the
    `Sales[@Col]` case (which already has `is_this_row: true`
    from the parser). Specifically: parse `Sales[@Col]` → inner
    spec is `ThisRowColumn("Col")` → resolve_structured_ref
    returns `is_this_row: true`. Wrapping in `@` and re-patching
    is idempotent — but confirm the binder test covers this.

14. **Rule 8 (function inner) array-return scalar-context
    interaction.** `@SUM(A1:A10)` where A1:A10 has 10 values →
    SUM returns scalar 55 (no spill). Works. But `@TRANSPOSE(A1:A10)`
    → TRANSPOSE returns array → scalar context returns `#CALC!`.
    Documented above (rule 7). NO additional concern beyond #12.

### E. Persistence × op-log

15. **v7 persistence × op-log SetReferenceMode/SetLocale
    interaction.** Save a workbook in R1C1 + DE state. The v7
    envelope writes `reference_mode = "R1C1"`, `locale = "de"`.
    The op-log file contains `Op::SetReferenceMode { R1C1 }` and
    `Op::SetLocale { De }` from the runtime-API calls. On load,
    the envelope sets R1C1+DE. The replay then RE-applies
    SetReferenceMode + SetLocale (idempotent — no-op since the
    state already matches). OK. But: what if the envelope was
    hand-edited to A1+EnUs but the op-log still has the SetReferenceMode
    op? The replay would CHANGE the workbook to R1C1+DE after
    load. Is that intended? (Probably yes — the op-log is the
    source of truth for the post-load state.) Confirm.

16. **v6 → v7 migration path.** A user with a v6 .qbook saves
    on the new build. Save writes v7 (with reference_mode + locale
    fields omitted since default). Load that v7. Then save again.
    Diff the two v7 saves — byte-identical? The forward-compat
    assertion in the loader only fires for `schema_version < 7`
    AND v7-field-present. The new save path always emits v7 with
    fields omitted for defaults. Confirm round-trip determinism.

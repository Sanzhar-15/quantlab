### Algorithm (V3.6.0.8.1 8-step, implemented at V3.6.0.8.3)

1. Empty `last_seen_version` Buffer → return `fullRebuildRequired=true` + current VV.
2. No prior workbook cache → return `fullRebuildRequired=true`.
3. Decode caller VV via `loro::VersionVector::decode`; malformed → `fullRebuildRequired=true` (conservative — does NOT throw `bad_argument`).
4. Staleness check (caller_vv != cached_vv) → `fullRebuildRequired=true`.
5. Same-VV fast-path (current_vv == cached_vv) → empty delta with current version.
6. Enumerate ops `[cached_op_count, log.len())` via `inner.log().iter().skip(start).take(end-start)`; collect into owned Vec to release the borrow before any potential force_clear; classify via `classify_delta_op` walker.
7. If any rename op → `fullRebuildRequired=true` (V3.6.0.8.3 conservative scope).
8. Cell-only fast-path: clone cached Arc via `(*cached_arc).clone()` (forks Workbook), apply `[cached_op_count, current_op_count)` via `apply_ops_in_range`, skip repair walks (no rename ops by construction), Arc-wrap + replace cache, build JSON delta via the workbook_snapshot rendering pipeline (format::render with parsed_format_cache).

### V3.6.0.8.3 documented scope limitations

- `removedCells` always empty (V3.7+ feature).
- `sheetsChanged` always empty in cell-only path (cell ops don't change sheet metadata).
- Rename ops trigger fullRebuild fallback rather than incremental rename delta.
- Bench delta-vs-full at 100k cells deferred to V3.6.0.8.4 (i.e., THIS audit cycle — see below).

## Audit scope

Verify correctness, robustness, and discipline across the chain.  Focus on:

### 1. 3-field cache invariant ("all Some / all None")

The V3.6.0.8.2 design was 2 fields; V3.6.0.8.3 added `last_snapshot_op_count` as the 3rd.  Verify:
- `set_workbook_cache` populates all 3 atomically (no intermediate "Some-Some-None" state).
- `force_clear_workbook_cache` clears all 3 atomically.
- All 4 invalidation callsites correctly call `force_clear_workbook_cache` (not just `force_clear_snapshot_cache`).
- `force_clear_snapshot_cache` test seam clears the workbook cache too.
- No code path observes a "2 Some, 1 None" state.

### 2. Algorithm correctness

Walk the 8 steps in code:

- Step 1 (empty Buffer): `last_seen_version.is_empty()` check.  Does napi-rs `Buffer::is_empty` correctly return true for `Buffer.alloc(0)` from JS?  Verify the napi-rs 3.9.0 Buffer ↔ Vec<u8> contract.
- Step 2 (no cache): tuple match with `Some(arc), Some(vv), Some(n)` extracts; any None routes to fullRebuild.  Verify the destructure handles all 3 None-cases.
- Step 3 (decode): `loro::VersionVector::decode(bytes)` -- what does Loro do with garbage bytes?  Does it ever panic instead of returning Err?  Check the Loro 1.12.0 decode contract.
- Step 4 (staleness): `caller_vv != cached_vv` -- VersionVector equality semantics in Loro 1.12.0.  Is BTreeMap equality the correct semantic (key-set match + counter match)?  Or does Loro use a custom Eq impl?
- Step 5 (same-VV): trivial early-return.
- Step 6 (enumeration): `inner.log().iter().enumerate().skip(start).take(end-start).map(|(_idx, op_result)| op_result).collect()` -- the Vec collection is intentional to release the immutable borrow on `inner.log()` so `inner.force_clear_workbook_cache()` calls below can take `&mut`.  Verify no Op data is lost via the collect.
- Step 7 (rename detect): `classify_delta_op` matches `Op::RenameSheet | RenameTable | RenameColumn` + BatchCommit recursion.  Are there other ops that effectively rename (e.g., do tables have a separate rename path)?  Check `Op::CreateTable` vs `Op::RenameTable`.  Does `Op::MoveSheet` count as a rename for the purpose of the cell-only fast-path?  (Probably no — MoveSheet changes display order, not formula references; but verify.)
- Step 8 (cell-only apply): `(*cached_arc).clone()` makes a fresh `Workbook`.  Then `apply_ops_in_range(inner.log(), &mut next_workbook, cached_op_count, current_op_count, &registry)`.  Verify the `inner.log()` borrow on step 8 doesn't conflict with the later `inner.set_workbook_cache(...)` `&mut` borrow.
- Cache replacement: `Arc::new(next_workbook)` + `inner.set_workbook_cache(Arc::clone, current_vv)`.  Verify the prior cache's Arc is correctly dropped (no leak via dangling clones).

### 3. Cache populate in workbook_snapshot

The `workbookSnapshot` napi now:
- Takes `&mut inner.lock()`.
- Wraps workbook in `Arc` BEFORE rendering.
- Rendering reads through `Arc::deref` (claims identical cost to `&Workbook`).
- Calls `inner.set_workbook_cache(Arc::clone(&workbook), cache_vv)` AFTER rendering.

Verify:
- The Arc wrap doesn't introduce reference-count contention.
- `cache_vv` is captured BEFORE any mutation (currently captured right after `rebuild_workbook` succeeds; verify no mutation between capture + populate).
- `set_workbook_cache` pins `self.log.len()` -- this MUST match the moment of `cache_vv` capture.  Is there any way `self.log.len()` could change between `oplog_vv()` and `set_workbook_cache(_, cache_vv)`?  (Probably no — `&mut inner` is held throughout — but verify.)

### 4. Multi-peer + concurrent edits

- Two peers both call `workbookSnapshot` → both populate their local caches with their local VVs.  They mutate independently (each calls `appendPutValue` etc.).  Both call `workbookSnapshotDelta(localCachedVersion)`.  Each gets a cell-only delta of their own local changes.
- Peer A calls `merge_bytes(B's bytes)` → A's cache is invalidated (V3.6.0.8.2 closure).  A's next `workbookSnapshotDelta` returns `fullRebuildRequired=true` because the cache is empty.  Verify this matches the expected staleness recovery flow.
- Peer A merges B's bytes containing a rename op.  Verify the cache invalidation fires correctly (and Peer A's IDE is told to fullRebuild).

### 5. BatchCommit recursion

`classify_delta_op` recurses into `Op::BatchCommit { ops }`.  Verify:
- The recursion handles nested BatchCommits (V3.4.0.X HIGH-1 walker discipline).
- An empty BatchCommit (ops: vec![]) is a no-op.
- A BatchCommit containing a RenameSheet correctly propagates `has_rename = true` to the outer call.
- A BatchCommit containing PutValue + PutFormula + SetCellFormat for the same cell coord registers ONE entry in `changed_cells` (HashSet dedup).

### 6. R-V3.6-14 (cached Workbook stale after Loro retract) closure

V3.6.0.8.2 wired undo/redo to call `force_clear_workbook_cache` AT TOP (before Loro's undo).  V3.6.0.8.3 added a mocha test (`v3_6_0_8_3 D6 -- workbookSnapshotDelta invalidation by undo`).  Verify:
- The clear is genuinely BEFORE Loro's undo (the `self.undo.undo()` call comes after the `force_clear_workbook_cache` call).
- The clear fires even when Loro's undo is a no-op (empty undo stack).  Currently the V3.6.0.8.2 wiring clears unconditionally at top; verify this is correct or whether it should be conditional on `consumed=true` (defensive — extra clears are cheap; missed clears are correctness violations).

### 10. IDE consumer protocol soundness

The two-call protocol in the mocha tests:
1. First `workbookSnapshotDelta(Buffer.alloc(0))` → fullRebuildRequired=true.
2. Caller calls `workbookSnapshot()` to populate cache + read full state.
3. To capture version: the mocha test pattern probes via `workbookSnapshotDelta(Buffer.alloc(0))` AFTER the workbookSnapshot to read `version` (because there's no dedicated `currentVersion()` accessor in V3.6.0.8.3).
4. Subsequent calls pass the captured version.

Verify:
- The "probe to read version" pattern is sound or has a race window.
- A `currentVersion()` accessor would be cleaner; defer to V3.7+ if not adding now.

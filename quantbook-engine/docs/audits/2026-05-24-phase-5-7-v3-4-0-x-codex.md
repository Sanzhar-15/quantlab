## HIGH

### HIGH-1 -- `CellState` cache ignores `BatchCommit`-nested cell ops

**Files:**
- `crates/ql-collab/src/session.rs:674-707`
- `crates/ql-collab/src/session.rs:933-953`
- `crates/ql-oplog/src/op.rs:168-176`
- `crates/ql-oplog/src/replay.rs:677-684`
- `crates/ql-exec/src/workbook_runtime/cells.rs:788-809`

**Problem:** The V3.4 cache update paths match only top-level `Op::PutValue`, `Op::PutFormula`, and `Op::ClearFormula`. `Op::BatchCommit { ops }` is a production op shape, and replay recurses into it. `WorkbookRuntime::set_value` over a formula cell emits `BatchCommit { PutValue, ClearFormula }` to keep the pair atomic. `rebuild_workbook` sees that nested value; `rebuild_snapshot_cache` does not. A `.qbook` can therefore save/replay correctly but load into an IDE session whose `exportSnapshot` / `listSheets` cache omits the nested cell update.

**Reproduction:**
1. Produce an op log via `WorkbookRuntime::set_formula(0,0,0, ...)`, then `set_value(0,0,0, 99)`. The runtime emits `PutFormula` followed by `BatchCommit { PutValue, ClearFormula }` (`crates/ql-exec/src/workbook_runtime/cells.rs:1471-1495`).
2. Save through `.qbook`; `toQbook` routes through recursive `replay_into`, so the workbook state includes the value.
3. Load via `fromQbook` / `from_snapshot`; `rebuild_snapshot_cache` skips `BatchCommit`, so the cache still reflects only the top-level `PutFormula`.
4. `exportSnapshot(0)` skips formula-only cells and returns no `99` value.

**Recommended closure:** Add a small internal cache-folding helper that recurses through `BatchCommit` in both `append_op` and `rebuild_snapshot_cache`. Reuse the same helper for top-level ops to prevent drift. Add ql-collab tests for `BatchCommit { PutValue, ClearFormula }`, nested `BatchCommit`, and import/from_snapshot cache rebuild.

### HIGH-2 -- `addSheet` accepts invalid `chunkRows`, re-opening a known panic/OOM class

**Files:**
- `crates/ql-bindings-node/src/lib.rs:539-543`
- `extensions/quantlab/src/quantbook/session.ts:145-158`
- `crates/ql-exec/src/workbook_runtime/sheets.rs:71-77`
- `crates/ql-storage/src/workbook.rs:658-672`
- `crates/ql-storage/src/sheet.rs:155-170`
- `crates/ql-storage/src/column.rs:100-101`

**Problem:** The new NAPI `addSheet(name, chunkRows)` takes `chunk_rows: u32` directly and the TS wrapper forwards it without validation. This repeats the old `ToUint32` boundary class fixed for `appendPutValue`: `0`, `NaN`, `Infinity`, negative, and fractional JS inputs can be accepted or silently coerced. `WorkbookRuntime::add_sheet` explicitly rejects `chunk_rows == 0` before appending the op because a zero chunk size can later panic in `ColumnStore::with_chunk_rows`. The NAPI path bypasses that guard and appends the bad op.

**Reproduction:**
1. Call `session.addSheet("S", 0)` or `addSheet(session, "S", 0)`.
2. Append a value to sheet 0.
3. Call `toQbook`. Replay adds a sheet with `chunk_rows = 0`; the first cell write grows a column and calls `ColumnStore::with_chunk_rows(0)`, which asserts.
4. For `-1`, JS `ToUint32` can become `4294967295`, risking an enormous allocation path instead of a structured `[bad_argument]`.

**Recommended closure:** Change the NAPI signature to accept `chunk_rows: f64` and validate finite integer range `[1, u32::MAX]` before constructing `Op::AddSheet`, matching `validate_u32_index` style. Add TS wrapper validation and mocha tests for `0`, `-1`, `NaN`, `Infinity`, fractional, and valid `1000`.

### HIGH-3 -- Save As is wired to local panels whose sessions still lack `AddSheet` ops

**Files:**
- `extensions/quantlab/src/commands/quantbookCommands.ts:199-226`
- `extensions/quantlab/src/commands/quantbookCommands.ts:358-382`
- `crates/ql-bindings-node/src/lib.rs:519-525`
- `crates/ql-oplog/src/replay.rs:397-409`

**Problem:** V3.4.0.4a correctly documents the semantic gap: `rebuild_workbook` requires sheets to exist before `PutValue`. The default local `quantlab.quantbookCellGrid` command still seeds sample data by calling `appendPutValueValidated` on sheets 0, 1, and 2 without first calling `addSheet`. `quantlab.quantbookSaveAs` picks the oldest local panel and calls `exportToQbook` on that session. That default user path fails with replay invalid-sheet instead of saving.

**Reproduction:**
1. Run `Quantbook: Open Cell Grid` to open the sample local panel.
2. Run `Quantbook: Save As`.
3. The selected panel's session contains `PutValue` ops but no `AddSheet` ops, so `toQbook` calls `rebuild_workbook`, `replay_into` validates `sheet=0` against an empty workbook, and save fails.

**Recommended closure:** Seed `addSheet(session, "S0")`, `addSheet(session, "S1")`, and `addSheet(session, "S2")` before the sample `appendPutValueValidated` calls. Add a command-level mocha/unit test or direct wrapper test that mirrors the default panel seed and asserts `exportToQbook` succeeds.

## MEDIUM

### MEDIUM-1 -- `ClearFormula` on a formula-only cell leaves an empty cache key

**Files:**
- `crates/ql-collab/src/session.rs:696-704`
- `crates/ql-collab/src/session.rs:943-948`
- `crates/ql-collab/src/session.rs:817-823`
- `crates/ql-collab/src/session.rs:3042-3072`

**Problem:** `ClearFormula` uses `get_mut` + skip-if-absent, which avoids creating an entry for a never-written cell. But if the cell previously had only `PutFormula`, clearing the formula leaves `CellState { value: None, formula: None }` in the map. `list_sheets_from_cache` then reports the sheet from the empty key.

**Reproduction:** Append `PutFormula { sheet: 7, row: 0, col: 0 }`, then `ClearFormula` for the same cell. `snapshot_cells(7)` contains an empty state and `list_sheets_from_cache()` includes `7`, even though replay leaves no value/formula at that cell. The existing test covers `PutValue + PutFormula + ClearFormula`, not formula-only clear.

**Recommended closure:** After clearing `formula`, remove the key if both `value` and `formula` are `None`. Add append-path and rebuild-path tests for formula-only clear and import/from_snapshot.

### MEDIUM-2 -- Committed edits never broadcast `typing:false`

**Files:**
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:337-385`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:401-416`
- `extensions/quantlab/test/quantbook-roundtrip.test.ts:3822-3826`

**Problem:** `beginEdit` posts `presenceUpdate` with `typing:true`. `endEdit(true)` enters the commit branch, posts `putValue`, and returns before the `typing:false` block. Only cancel/blur reaches the false broadcast. The test asserts only that the HTML contains `typing:false`, not that the commit path executes it.

**Reproduction:** Start editing a cell, press Enter. Remote peers receive `typing:true`; on successful commit the host re-renders the local webview but no presence update clears typing. The peer can remain visually "typing" until another presence write or dispose-time clear.

**Recommended closure:** On successful `putValue`, update presence to the same cell with `typing:false` before `onCommit`, or add a webview success-ack path that sends `typing:false` only after the host accepts the commit. Add a dispatcher/webview test that checks the commit path ordering, not just substring presence.

### MEDIUM-3 -- `presenceUpdate` runtime validation only checks `typeof number`

**Files:**
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:217-249`
- `crates/ql-bindings-node/src/lib.rs:383-390`
- `extensions/quantlab/test/quantbook-roundtrip.test.ts:3876-3902`

**Problem:** The dispatcher validates presence numeric fields only with `typeof === 'number'`. It does not reject `NaN`, `Infinity`, negative numbers, fractional numbers, or out-of-range sheet values before crossing into NAPI's `u16` / `u32` object conversion. This is the same boundary class that V3.2.d closed for cell writes.

**Reproduction:** Dispatch `{ type: "presenceUpdate", state: { sheet: 0, row: -1, col: 0, selectionEndRow: -1, selectionEndCol: 0, typing: false } }`. It passes the dispatcher guard and relies on NAPI conversion rather than producing the promised `[bad_argument]` errorReply.

**Recommended closure:** Add a presence numeric validator mirroring `appendPutValueValidated`: `sheet` integer `[0, 65535]`; row/col/selectionEnd* integer `[0, 4294967295]`; finite only. Add malformed numeric tests for negative, fractional, `NaN`, and `Infinity`.

### LOW-2 -- UUID PeerId entropy comment overstates the random bits

**Files:**
- `extensions/quantlab/src/quantbook/session.ts:168-178`
- `docs/architecture/ide-consumer-contract.md:1051-1068`

`generateUuidPeerId` strips dashes and takes the first 16 hex chars. In a UUIDv4, those 16 chars include the fixed version nibble (`4xxx` group), so the result has about 60 random bits, not 64. The collision risk remains acceptable for V3.4, and the non-zero retry cap is still a loud broken-entropy signal, but the birthday-paradox comments should say ~2^30 sessions rather than ~2^32.

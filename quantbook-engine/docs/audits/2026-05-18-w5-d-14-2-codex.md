# W5-D-14.2 HIGH Findings

Scope: requested commit `6ba2ce6ff89`.

## Preserved opaque parts are orphaned in UpdateOriginal

Severity: HIGH

File: `crates/ql-io-xlsx/src/write/update_original.rs:108`

Description: `UpdateOriginal` copies preserved parts such as drawings, charts, comments, media, embeddings, external links, and `docProps/custom.xml`, but it writes shadow-owned `xl/workbook.xml`, worksheet XML, worksheet rels, workbook rels, and root rels instead of merging the references that make those parts reachable. As a result, preserved parts can remain in the zip and in `[Content_Types].xml` while Excel/LibreOffice no longer display or use them.

Suggested fix: Make preservation relationship-graph aware: merge the required workbook/root/worksheet relationship entries plus inline anchors (`<drawing>`, `<legacyDrawing>`, comments, externalReferences, custom-properties rels, etc.), or classify these families as dropped/unsupported until that merge exists.

## Strict UpdateOriginal writes output before returning an error

Severity: HIGH

File: `crates/ql-io-xlsx/src/write/update_original.rs:155`

Description: The final `output_path` is written before `unsupported_policy` is enforced at lines 158-169. In `Strict` mode, a workbook containing VBA/ActiveX can overwrite the requested destination with a lossy macro-stripped export and then return `Err`, which violates strict no-loss semantics and can destroy the caller's previous file.

Suggested fix: Enforce `Strict` before writing `output_path`, or write to a temp output and atomically commit only after policy checks pass.

## Shadow temp path collides between concurrent exports

Severity: HIGH

File: `crates/ql-io-xlsx/src/write/update_original.rs:456`

Description: `sibling_tmp_path` creates `AtomicU64::new(0)` inside the function, so every call in the same process returns suffix `0` for the same output stem. Concurrent exports to the same destination compute the same shadow path and can race between `export_new_workbook`, `std::fs::read`, and guard cleanup.

Suggested fix: Use `tempfile`/`create_new` in the output directory, or lift the counter to a module-level static and still open with exclusive creation.

## Table autoFilter includes the totals row

Severity: HIGH

File: `crates/ql-io-xlsx/src/write/umya_export.rs:869`

Description: `render_table_xml` writes `<autoFilter ref="{t.ref_a1}"/>` even when `t.ref_a1` includes a totals row. The table parser's own documented OOXML shape shows `table/@ref` covering the totals row while `autoFilter/@ref` excludes it; exporting the full range can make Excel repair or mis-render totals-row filtering.

Suggested fix: Compute an `auto_filter_ref` that excludes the last row when `has_totals` is true, and add an E2E test for a totals-row table.

## Custom totals functions are silently dropped on table export

Severity: HIGH

File: `crates/ql-io-xlsx/src/write/umya_export.rs:897`

Description: `totals_function_attr` returns `None` for `TotalsFunction::Custom`, so an imported `totalsRowFunction="custom"` re-exports with no totals function metadata and re-imports as `None`. If the formula is only present in the totals-row cell, the table column still loses the table-level custom totals marker.

Suggested fix: Serialize `TotalsFunction::Custom` as `totalsRowFunction="custom"` and include a `<totalsRowFormula>` child when the totals-row formula is available; otherwise report the custom totals function as unsupported/dropped.

### Target B. Click-to-edit script + DOM event handler safety -- PASS

Per-character XSS walk through `escapeHtml` (line 323-334 in cellGridHtml.ts):

- `<` -> `&lt;` ✓
- `>` -> `&gt;` ✓
- `&` -> `&amp;` ✓
- `"` -> `&quot;` ✓
- `'` -> `&#39;` ✓
- Backtick: NOT escaped. **Is this a hazard?** Backtick is NOT a special
  character in HTML attribute syntax (HTML5 spec: attribute values can be
  unquoted, single-quoted, or double-quoted; backtick has no special role).
  In **double-quoted attribute context** (all uses in renderRows()),
  unescaped backtick is benign. In **unquoted attribute context** it can
  terminate the attribute in some IE versions but this is V3.2-irrelevant
  (VS Code webviews are Chromium). PASS.
- Null byte (U+0000): NOT escaped. HTML parsers treat null byte as
  REPLACEMENT CHARACTER (U+FFFD) per HTML5 § 8.2.4. In attribute context
  this is harmless. In text-content context same. PASS.
- BOM (U+FEFF): NOT escaped. Treated as zero-width-no-break-space by the
  parser; no XSS impact. PASS.
- RTL override (U+202E): NOT escaped. Renders text RTL but cannot inject
  script. PASS.

**Data-original-text round-trip walk:**

The renderRows() at line 142 emits
`data-original-text="${escapeHtml(valueStr)}"`. If the cell value is the
literal string `<script>alert(1)</script>`, the attribute carries
`data-original-text="&lt;script&gt;alert(1)&lt;/script&gt;"`. The browser
parses the attribute value and stores the UNESCAPED string
(`<script>alert(1)</script>`) accessible via `getAttribute('data-original-
text')` (HTML5 spec: getAttribute returns the parsed unescaped form). The
cancel path then does:

```js
cell.appendChild(document.createTextNode(cell.getAttribute('data-original-text') || ''));
```

`createTextNode` creates a TEXT node whose `nodeValue` is the raw string. The
DOM tree-walker stage of HTML serialization re-escapes text node content on
render (writing `&lt;script&gt;alert(1)&lt;/script&gt;` to the screen). No
double-decode is possible because `createTextNode` does NOT parse HTML.
**PASS.** The mocha test at line 2325 in quantbook-roundtrip.test.ts pins
this: `<script>` payloads in cell text are escaped in BOTH the visible cell
AND `data-original-text`, and the mocha assertion verifies the rendered HTML
does not contain raw `<script>...`. (The cancel-restore behavior is not
unit-tested -- only the HTML-build is. See LOW-7 for the test gap.)

**errorReply selector injection walk:**

`cellGridHtml.ts:304`:

```js
var sel = '.cell-value[data-row="' + Number(msg.row) + '"][data-col="' + Number(msg.col) + '"]';
```

Adversarial cases for `msg.row`:
- `Infinity` -> `Number(Infinity)` = `Infinity` -> `String(Infinity)` = `"Infinity"`.
  Selector becomes `.cell-value[data-row="Infinity"]`. Valid CSS selector;
  matches nothing (no cell has `data-row="Infinity"`). querySelector returns
  null; the handler's `if (cell !== null)` guard at line 306 skips decoration.
  Fails closed. PASS.
- `NaN` -> `String(NaN)` = `"NaN"`. Same as Infinity. PASS.
- `"1\"][data-row=\"0"` (selector injection attempt) -> `Number(...)` =
  `NaN` -> `String(NaN)` = `"NaN"`. Coerced. PASS.
- `BigInt(1)` -> `Number(BigInt(1))` = `1`. Safe. PASS.
- `null` -> `Number(null)` = `0`. Selector becomes `[data-row="0"]`. Targets
  the (0, 0) cell. Wrong but not a security issue (only attacker who can
  inject `null` for msg.row would also send a real putValue with row=0; benign
  decorative mistargeting). PASS.

`Number()` coercion is the load-bearing sanitizer here. PASS.

**Title attribute walk:**

`cellGridHtml.ts:308`:

```js
cell.setAttribute('title', '[' + String(msg.code) + '] ' + String(msg.message));
```

`setAttribute` PARSES the value as a string per DOM spec (no HTML re-parsing).
Title attribute is plain text in tooltip rendering (no HTML interpretation).
Even if `msg.message` is `<img onerror=alert(1)>`, it shows up as that literal
string in the tooltip. PASS.

What if msg.message contains a NULL byte? Stored as-is in the attribute; browser
tooltips render it as either replacement char or just nothing. No XSS surface.
PASS.

What if msg.message contains an RTL override? Title text renders RTL. No
script execution. PASS.

**acquireVsCodeApi() collision walk:**

The script at line 211 calls `acquireVsCodeApi()` once at module load. The
docstring at the top of buildClientScript notes this is single-call-only per
VS Code's webview API contract. Two CellGridPanels share the EXTENSION HOST

**Verdict: PASS** (1 LOW finding about Number() coercion edge cases that
mis-target wrong cells but are not security issues -- see LOW-1).

### Target C. dispatchIncomingMessage envelope validation -- PASS-WITH-FINDINGS

Per-field adversarial walk:

- **rawInput = null:**
  `parseCellRawInput(null)` -> `null.trim()` -> TypeError. Caught at line 181-191
  by the try/catch. `parseQuantbookError(TypeError)` walks the TypeError's
  `.message` for the bracket prefix, finds none, walks `.cause` (TypeError has
  no cause), returns `{code: 'unknown', message: <TypeError text>, cause: ...}`.
  The errorReply then carries `code: 'unknown'`. **This is the wrong code per
  the V2.7 contract:** the dispatcher should treat malformed input as
  `bad_argument`, not `'unknown'`. See HIGH-2.

- **rawInput = undefined:** Same as null. `undefined.trim()` TypeErrors. Same
  result. HIGH-2.

- **rawInput = 42 (number):** `(42).trim()` -- but wait, Number has no `.trim`.
  TypeError: `(intermediate value).trim is not a function`. Same path as null.
  HIGH-2.

- **rawInput = "" (empty string):** parseCellRawInput throws
  `Error('[bad_argument] cell value cannot be empty')`. parseQuantbookError
  finds the bracket prefix -> returns `{code: 'bad_argument', message: '...'}`.
  errorReply gets `code: 'bad_argument'`. PASS.

- **rawInput = "NaN":** `Number('NaN')` = `NaN`, `Number.isFinite(NaN)` = false,
  throws `[bad_argument] cell value must be a finite number, got "NaN"`. PASS.

- **sheet = NaN:** First, `req.sheet !== deps.sheet` -- if `deps.sheet=0` and
  `req.sheet=NaN`, the `!==` comparison returns TRUE (NaN !== anything). Drops
  via the sheet-mismatch warning at line 174. Silent drop, no errorReply.
  Defensible (the WEBVIEW never sends NaN since the script bakes SHEET as a
  numeric literal), but a future multi-sheet panel could surface NaN. Document
  in the dispatcher comment. See LOW-2.

- **sheet = Infinity:** `Infinity !== 0` -> drops silently. Same as NaN. LOW-2.

- **sheet = -0:** `-0 === 0` is true. Passes the mismatch guard. Then proceeds
  to `appendPutValueValidated` which calls `Number.isInteger(-0)` = true,
  `-0 < 0` = false, `-0 > 0xFFFF` = false. All checks pass. The engine receives
  `sheet=-0` which is bitwise 0 in u16 cast. PASS (correct semantics).

- **row = 4294967296 (u32::MAX + 1):** Reaches appendPutValueValidated; the
  `row > 0xFFFFFFFF` guard rejects with
  `'appendPutValue: row must be an integer in [0, 4294967295], got 4294967296'`.
  This error has NO bracket prefix (it's a plain `Error()` constructor in
  session.ts:80). parseQuantbookError walks for prefix, finds none, returns
  `{code: 'unknown', ...}`. The errorReply gets `code: 'unknown'`. **Same
  HIGH-2 contract violation:** the IDE-side validator is producing `'unknown'`-
  coded errors for what is semantically `bad_argument`.

- **row = 1.5 (fractional):** Same -- `Number.isInteger(1.5)` = false, throws
  bracketless Error. errorReply code = 'unknown'. HIGH-2.

- **row = -1:** Same -- `-1 < 0` triggers throw, bracketless. HIGH-2.

- **row = BigInt(1):** `Number.isInteger(BigInt(1))` returns false (the type
  check). Throws bracketless. errorReply code = 'unknown'. HIGH-2.

- **col, value:** Same surface as row. HIGH-2 covers all of these.

**onError postMessage delivery walk (in real panel at line 243):**

```ts
onError: reply => { void this.panel.webview.postMessage(reply); }
```

`webview.postMessage` returns a Thenable<boolean>. The `void` discards it. If
the webview is HIDDEN and `retainContextWhenHidden: false` (which is the V3.2
config at line 124), the webview is destroyed when hidden -- postMessage
queues until reveal OR is lost. VS Code's docs say "messages posted to a
hidden webview will be queued and delivered when the webview is shown again",
but with `retainContextWhenHidden: false` the webview's STATE is destroyed
(including any script handler), so the queued message may be delivered to a
fresh webview that just re-rendered (i.e., a fresh document with no input
element to decorate). User-visible failure mode: user typed a value, hit
Enter, saw the input element, hid the panel, the host validation failed
async, errorReply queues; user re-shows panel, panel re-renders from the
LATEST snapshot (which doesn't have their bad value), errorReply delivers to
fresh document, the selector at line 304 fails to find a cell with
`data-row="X"][data-col="Y"]` in error state (the cell exists but isn't in
error state), gets decorated red. Confusing but recoverable.

A more concrete failure mode: user types value, hits Enter, closes panel
BEFORE the dispatcher completes. The dispatcher fires onError on a disposed
webview. The postMessage Thenable rejects (or no-ops); the void discards it.
The user sees no error -- their data was lost without notification. See
MEDIUM-1.

**Verdict: PASS-WITH-FINDINGS** (HIGH-2 on the `unknown`-instead-of-
`bad_argument` code mismatch for the dispatcher's three TypeError-prone
input paths; MEDIUM-1 on postMessage-after-dispose).

### Target D. connectOrSpawn race + relay lifecycle -- PASS

- **websocketConnect timeout:** Looking at multiWindowDemo.ts:228 +
  ql-bindings-node Transport.websocketConnect. The napi binding wraps
  `WebSocketTransport::connect_async` from ql-collab-ws. Tracing this... the
  V2.3 audit covered the websocketConnect failure modes (Codex MEDIUM-3 +
  Opus). The handshake step has a timeout via tokio-tungstenite's internal
  handling. The TCP connect step uses tokio's `TcpStream::connect` which is
  governed by the OS default TCP connect timeout (typically 60-75s on Linux,
  20s on macOS). If a relay is bound but not responding to the WS upgrade,
  the handshake times out. **There is no application-layer timeout wrapper
  in connectOrSpawn.** A pathological case where the relay binary binds the
  port but never responds to upgrade requests would hang for tens of seconds.
  V3.1.e Opus M1 closure for the SPAWN timeout (10s default) does not cover
  the websocketConnect call itself. See LOW-4 (defer to V3.x backlog;
  current threat model is local binary trust).

- **Marker spoofing:** Already addressed in the prompt's threat model
  section. The relay binary is local-only; if the local binary has been
  replaced with a malicious one that emits the readiness marker without
  serving, the websocketConnect succeeds-then-fails-on-first-send. The IDE
  sees `transport_io` / `transport_closed`; reconnect ladder runs; exhausts;
  Restart prompt fires. Recoverable. PASS (out of scope per V3.2 trust
  model; documented in connectOrSpawn comment at line 226+).

- **SIGTERM vs SIGKILL:** multiWindowDemo line 399 + cellGridPanel line 389
  both use `state.spawnedRelay.kill()` (default = SIGTERM). The relay binary
  (V3.1.a) handles SIGTERM via `tokio::signal::ctrl_c() + tokio::signal::
  unix::signal(SIGTERM)` per V3.1.e Codex LOW-2 closure (engine commit
  `97ac0b902d1`). Verified at
  `crates/ql-collab-ws/examples/relay-server.rs`. PASS.

- **Joiner race-retry timing window:** connectOrSpawn lines 252-273 implement
  the V3.1.e Opus MEDIUM-2 + Codex LOW-1 convergent closure. The spawn fails
  (typically with `[relay] binary exited before readiness`), the race-retry
  attempts `websocketConnect` once more. If the OTHER window's relay is still
  spawning, this retry MAY fail. In that case the original spawnErr is
  thrown (lines 271-272). The user sees a FATAL spawn error and must run
  the command again. Acceptable for V3.2 (the race window is sub-second on
  local dev). Documented at line 252+. PASS.

**Verdict: PASS** (LOW-4 deferred for V3.x: app-layer websocketConnect
timeout).

### Target E. Single-tab-per-sheet cache invariant -- PASS-WITH-FINDINGS

The four-case state walk (decision lock in V3.2.c.1 § C3 + comment at
cellGridPanel.ts:97-101):

1. **local-then-local:** Open local on sheet 0 -> activePanels.set(0,
   localPanel1). Open local on sheet 0 again -> attachment === undefined,
   activePanels.get(0) === localPanel1 (defined) -> reveal + render -> return
   existing. activePanels still has localPanel1. PASS (intended single-tab).

2. **local-then-collab:** Open local on sheet 0 -> activePanels.set(0,
   localPanel1). Open collab on sheet 0 -> attachment !== undefined, SKIPS the
   cache check entirely (line 102: `if (attachment === undefined)`). Creates
   collabPanel1, activePanels.set(0, collabPanel1) at line 157 OVERWRITES.
   localPanel1 is still ALIVE (visible to user) but no longer in the map.
   **HIGH-1 surfaces here:** if user runs `quantlab.quantbookCellGridRefresh`,
   only collabPanel1 is refreshed. localPanel1 silently never refreshes.
   Worse: when localPanel1 disposes (user closes it), its onDidDispose
   checks `activePanels.get(0) === instance`, which is FALSE (the map has
   collabPanel1). So no map mutation. Fine. But the orphaned-from-refresh-
   command surface is undocumented + breaks user expectation.

3. **collab-then-local:** Open collab on sheet 0 -> activePanels.set(0,
   collabPanel1) (bypass cache via attachment !== undefined). Open local on
   sheet 0 -> attachment === undefined, activePanels.get(0) === collabPanel1
   -> reveal collabPanel1 + render. **This is wrong:** the user explicitly
   ran the LOCAL command (`quantlab.quantbookCellGrid`), but the existing
   COLLAB panel is revealed instead. The local-only session that was created
   at quantbookCommands.ts:204 (with sample data) is leaked -- never attached
   to a panel. The collab panel's session is now showing instead. See HIGH-1.

4. **collab-then-collab:** Open collab on sheet 0 -> activePanels.set(0,
   collabPanel1). Open collab on sheet 0 again -> attachment !== undefined,
   SKIPS cache, creates collabPanel2. activePanels.set(0, collabPanel2)
   OVERWRITES. collabPanel1 still alive but orphaned. The user now has
   TWO collab panels for sheet 0, both polling, both with their own session
   + transport + spawned-relay-tracking. The first one is silently orphaned
   from Refresh + cache. When the user closes the orphaned panel1, its
   onDidDispose's `disposeAttachment` runs (correctly stops timers, detaches
   transport, kills its OWN spawnedRelay if present). But if BOTH panels
   spawned relays (unlikely but possible under tight race), the second one's
   relay is the live one + the first's kill() correctly only kills its own.
   The relay-ownership model is correct (each panel owns its own
   spawnedRelay or has undefined). **But the orphan-leak is real:** two live
   collab sessions both flushing on the same workbook -> two PIDs writing
   under the same peerId (BigInt(process.pid)). This violates the V3.1.b
   PeerId uniqueness assumption (one PeerId per writer). See HIGH-1 for the
   recommended closure.

**onDidDispose race:** the prompt's "reveal between check and delete"
scenario. JS is single-threaded; the onDidDispose handler runs to completion
before any reveal can be processed. `activePanels.get(sheet) === instance`
captures the current value atomically. PASS for the benign case.

**WebView slot exhaustion:** vscode.window.createWebviewPanel CANNOT silently
fail to register -- per the VS Code extension API, it either returns a panel
or throws. The createWebviewPanel call at line 110-127 is synchronous; no
slot-exhaustion failure mode exists at this layer. PASS.

**Verdict: PASS-WITH-FINDINGS** (HIGH-1 on the local-then-collab + collab-then-
local + collab-then-collab cases breaking the single-tab invariant).

### Target F. Rule 4 sweep across V3.2.a + V3.2.b + V3.2.c -- PASS

**exportSnapshot &self vs &mut self:**

`crates/ql-bindings-node/src/lib.rs:505`:

```rust
#[napi(js_name = "exportSnapshot")]
pub fn export_snapshot(&self, sheet: u16) -> Result<String> {
    let inner = self.inner.lock();
    ...
}
```

`&self` matches the V2.4 `Arc<Mutex<CoreCollabSession>>` design. The
`inner.lock()` acquires the parking_lot Mutex. The held guard is dropped at
function exit (no early-return scopes; the for-loop + sort + map + serialize
+ Ok(...) all run with the lock held).

**Re-entrant lock concern:** could exportSnapshot be called from inside
another locked method? The napi-rs binding does NOT have a way to call a
JS-facing method from inside a Rust-side method (napi methods are entry
points from JS). The only Rust-Rust call paths are:
- exportSnapshot -> inner.op_log().iter() -> ... (engine internals; does not
  call back into the napi class)
- exportSnapshot -> CellWireValue match arms -> serde_json::json! (pure
  data; no callbacks)

So re-entrancy is structurally impossible. PASS.

But: the exportSnapshot lock is held for the duration of a full op-log scan +
JSON serialization. For large op logs (V3.3 scale), this could starve OTHER
JS-initiated calls on the same session. At V3.2 scale (hundreds of cells,
~thousands of ops) the lock-hold time is sub-millisecond, fine. Document the
performance tradeoff at V3.3 entry. See V3.3 ENTRY-READINESS § "performance
ceiling".

**serde_json dep + cdylib symbol exposure:**

`crates/ql-bindings-node/Cargo.toml:85`: `serde_json = { workspace = true }`.
Added unconditionally at V3.2.a. Does it pull in symbols that production
builds don't want?

I cannot run `nm` here (no built dylib in this audit's context). But: serde_json
is a pure Rust crate; it does not declare any extern "C" symbols. Its
contribution to the cdylib is `serde_json::*` Rust symbols which are name-
mangled. The only way for an external consumer (or attacker) to invoke them
is via the napi-rs bindings (which only expose the methods marked `#[napi]`).
So no surface-widening. PASS.

Recommended closure for V3.2.d: run `nm -gU
quantlab-quantbook/quantbook-engine/target/release/libql_bindings_node.dylib |
grep -i serde` and verify only mangled Rust symbols are exposed (no extern "C"
serde_json symbols). If any unmangled symbols leak, escalate to MEDIUM.
**This audit recommends but does not require this check** (the napi-rs
toolchain has historically managed cdylib symbol exposure correctly; serde_json
is a well-behaved consumer).

**attachmentState 7-field walk (per Rule 4 analogous concern):**

The fields are `engine, transport, spawnedRelay, log, pollTimer,
reconnectInFlight, disposed`. Node.js is single-threaded; concurrent
mutations across threads are structurally impossible (no Worker pool with
shared `attachmentState`). The only concurrency surface is the JS event loop
+ async/await scheduling. Each field's mutation sites + reentry handling is
covered in Target A. PASS.

**CollabAttachment interface is `readonly`:** types.ts already pins the
fields as `readonly`. The TS compiler enforces no reassignment. The fields
themselves can mutate their interior state (e.g., the ChildProcess's
exitCode), but the BINDING is immutable. PASS.

**Verdict: PASS** (no new Rule 4 trigger; arc terminus stays at 6).

```
2. Run "Quantbook: Open Cell Grid (Collab)" -> collabPanel1 (cached @ sheet 0; localPanel1 ORPHANED from map)
3. Run "Quantbook: Open Cell Grid"        -> reveals collabPanel1 (WRONG: user asked for LOCAL)
                                               -- the local-mode session created at line 204 is leaked.
```

Or:

```
1. Run "Collab" twice
   -> collabPanel1 + collabPanel2 both alive; both ticking pollRemote on sheet 0;
      both flushing under the SAME peerId = BigInt(process.pid).
   -> Loro CRDT op log will accept both peers' ops (PeerId is the same; they
      look like a single peer to the merge layer) -- but the per-peer VV
      tracking is now ambiguous. Two writers under one peerId violates the
      V3.1.b PeerId-uniqueness contract.
```

**Why this is HIGH:**

- Case 3 (collab-then-local): the user runs the LOCAL command and gets the
  COLLAB panel revealed. Their explicit user intent is silently overridden.
  A session is leaked + GC'd (its op log + transport-less state never reach
  the user).
- Case 4 (collab-then-collab): two concurrent collab sessions writing under
  the same peerId. Loro will accept this but the per-peer VV math may produce
  surprising results (especially for delta flushes: the second session's
  flush-baseline could be wrong if the first session flushed first).
- Documentation in cellGridPanel.ts:97-101 acknowledges "collab panels DO NOT
  reuse a cached panel" but does NOT acknowledge:
  - case 3 (collab-then-local revealing the existing collab)
  - case 4 (collab-then-collab creating an orphaned tab)
  - the orphan-from-refreshAll surface (case 2 + case 4)

**Suggested closure:**

The cleanest fix is to make the cache attachment-mode-aware:

```ts
const cacheKey = `${attachment === undefined ? 'local' : 'collab'}:${sheet}`;
// (or split into two Maps: localPanels + collabPanels)
```

Then:
- local-then-local: hits cache, reveals localPanel1. (unchanged)
- local-then-collab: separate cache key -> creates collabPanel1, both panels
  in their respective cache. Refresh iterates both.
- collab-then-local: separate cache key -> creates localPanel1, both panels
  alive + cached.
- collab-then-collab: hits the collab cache, reveals collabPanel1.
  **No orphan; PeerId uniqueness preserved.**

Additionally, `quantbookCellGridCollab` should warn (or refuse) if a collab
panel is already open for this sheet in this window:

```ts
if (collabPanels.has(sheet)) {
  vscode.window.showWarningMessage('Cell Grid (Collab) is already open for this sheet.');
  collabPanels.get(sheet)!.reveal();
  return;
}
```

Land in V3.2.d closure cycle.

### HIGH-2 (Target C): dispatcher's `bad_argument` path bypasses `parseQuantbookError` prefix and surfaces `'unknown'`

**Files:**
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:177-191`
- `extensions/quantlab/src/quantbook/session.ts:76-89`

**Reproduction:**

The webview cannot send these values today (the script bakes SHEET as a

dispatcher is the trust boundary -- per V3.2.b.1 decision B1's "host parses +

unit test, a manual postMessage from devtools) should surface
`code: 'bad_argument'`. Today:

1. `dispatchIncomingMessage({type:'putValue', sheet:0, row:0, col:0, rawInput: null}, deps)`

- engine-side `appendPutValue` validators -> `code: 'bad_argument'` ✓
- IDE-side `appendPutValueValidated` validators -> `code: 'unknown'` ✗

The IDE-side validators are SUPPOSED to be defense-in-depth that fails
EARLIER with FRIENDLIER messages (per session.ts:53-67 docstring). The
"friendlier" part works (the messages are clear). The "earlier" part works.
But the CODE on the errorReply is wrong. A webview consumer doing
`switch (info.code)` to differentiate categories (e.g., color the cell
differently for bad input vs network error) would treat IDE-rejected input
as a generic "unknown error" rather than the specific "bad input" category.

**Suggested closure:**

Prefix all IDE-side validation errors in session.ts:76-87 with
`[bad_argument]`:

```ts
export function appendPutValueValidated(...): void {
    if (!Number.isInteger(sheet) || sheet < 0 || sheet > 0xFFFF) {
        throw new Error(`[bad_argument] appendPutValue: sheet must be an integer in [0, 65535], got ${sheet}`);
    }
    // ... and so on for row, col, value
}
```

Also: in cellGridLogic.ts:177-191, the dispatcher could pre-validate
`typeof req.rawInput === 'string'` before calling parseCellRawInput:

```ts
if (typeof req.rawInput !== 'string') {
    deps.onError({
        type: 'errorReply', sheet: req.sheet, row: req.row, col: req.col,
        code: 'bad_argument',
        message: `rawInput must be a string, got ${typeof req.rawInput}`,
    });
    return;
}
```

This is defensible either way (the V2.7 contract says: "bracket prefix is
the load-bearing signal"; the dispatcher could rely on parseQuantbookError
to do the discrimination), but the engine + IDE should be SYMMETRIC about
which side prepends the prefix. Picking either side and being consistent
closes the contract.

The mocha test at quantbook-roundtrip.test.ts:2418-2426 pins
`code: 'bad_argument'` for the `'hello world'` case (which is correctly
bracketed by parseCellRawInput). But there's NO test for the
null/undefined/non-string-rawInput case where it currently surfaces
`'unknown'`. The closure should add 3+ mocha tests pinning the
`'bad_argument'` code for all bracketless validation paths.

Land in V3.2.d closure cycle.

### MEDIUM-1 (Target C): postMessage to disposed/hidden webview silently loses errorReply

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:243`

The `onError` callback does `void this.panel.webview.postMessage(reply)`. If
the panel has been disposed OR is hidden with `retainContextWhenHidden: false`
(the V3.2 config), the message is silently lost:

- Disposed panel: postMessage returns a rejected Thenable or no-ops. `void`
  discards. User's typed value was rejected by validation; they see no error
  decoration; they may think it succeeded.
- Hidden panel: queued until reveal, but when revealed with
  `retainContextWhenHidden: false`, the webview re-renders from scratch (no
  cached state). The errorReply delivers to a fresh document where the cell
  is no longer in edit mode, the decoration applies to a cell that may now
  show the LATEST committed value but be marked red.

**Suggested closure:**

1. Check `this.panel.visible` + `!this.panel.disposed` (note: WebviewPanel has
   no public `disposed` property; track via local `_disposed` boolean set in
   onDidDispose) before postMessage. If not visible/alive, log + show
   showErrorMessage instead.

2. Await the postMessage Thenable + check its boolean result. The boolean is
   `true` only if delivery succeeded. If false, fall back to showErrorMessage.

Alternative: set `retainContextWhenHidden: true` for the cell-grid panel.
This keeps the webview state across hidden/show cycles. Costs: memory
(small, single inline script + ~hundreds of DOM nodes); benefits: messaging
is reliable. Recommend for V3.3 grid scale.

Defer-acceptable: localhost edits in a single window are fast (sub-ms);
hidden-panel timing windows are narrow in practice. Land in V3.x backlog as
"WebView message delivery contract" if not closed at V3.2.d.

### MEDIUM-2 (Target A): Reconnected transport leaked when panel disposed mid-await

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:332-338`

In `handleTransportClosed`:

```ts
const fresh = await reconnectWithBackoff(state.engine, state.log);
if (state.disposed) {
    return;
}
this.session.attachTransport(fresh);
```

If `panel.dispose()` is called during the 0-3.5s `reconnectWithBackoff` await
window, the function early-returns at line 334 WITHOUT closing or attaching
the `fresh` Transport wrapper. The wrapper is held by the local `fresh`
variable, which goes out of scope at the return. JS GC eventually collects
the wrapper; napi-rs finalize fires; the inner `Box<dyn Transport>` drops;
`WebSocketTransport::drop` aborts its tasks (per
`crates/ql-collab-ws/src/lib.rs:689`).

So the connection IS cleaned up -- just non-deterministically (potentially
several GC cycles later). On a long-running session that churns reconnects,
this can leak WebSocket connections + their writer/reader tokio tasks until
V8 GC reclaims them. Not a leak in the strict sense; a deterministic-cleanup
gap.

Same pattern exists at multiWindowDemo.ts:414-419.

**Suggested closure:**

Explicitly close the fresh transport in the disposed-during-reconnect path:

```ts
const fresh = await reconnectWithBackoff(state.engine, state.log);
if (state.disposed) {
    // Drop the freshly-connected transport. There's no explicit
    // close() binding; rely on Rust-side Drop. Force GC by losing
    // the reference immediately + log the drop for observability.
    state.log.appendLine('[collab] disposed during reconnect; dropping fresh transport');
    return;
}
```

Or add a `Transport.close()` binding (already on V3.x backlog per
`.plans/_active.md:196 "LoopbackTransport.close() binding"`) and call it
here.

Defer-acceptable for V3.2.d closure; promote to HIGH if reconnect churn
becomes a real measurable hazard in V3.3 testing.

### MEDIUM-3 (Target B): formatCellValue('number', NaN) produces 'NaN' string but cell still gets data-original-text='NaN'

### MEDIUM-4 (Target G / V3.3 entry): exportSnapshot lock-hold time scales linearly with op log size

**File:** `crates/ql-bindings-node/src/lib.rs:505-552`

At V3.2 scale (~thousands of ops on sheet 0), the entire op log iteration +
HashMap insertion + sort + JSON serialize runs with `self.inner.lock()` held.
On a 10K-op session, this can take low milliseconds. On a 100K-op session
(V3.3 scale with multi-sheet + accumulating edits), this can take 50-100ms +
hold the lock for that duration. Concurrent JS calls
(`session.appendPutValue`, `session.pollRemote`) block on lock acquisition.

The V3.2.c 1s pollRemote tick triggers a render which triggers an
exportSnapshot which locks for the iteration. Two windows both ticking at
1Hz, both with lots of ops, could see lock contention.

**Suggested closure:** see V3.3 ENTRY-READINESS § "exportSnapshot performance
ceiling". Either:
- Move to `rebuild_workbook` (V3.5+) which caches a parsed workbook + does
  incremental updates.
- Add an incremental cache (a HashMap kept up-to-date as ops are appended,
  exportSnapshot reads from the cache).
- Pre-compute on a background thread (would require interior mutability +
  per-peer lock granularity).

Defer to V3.3 entry decision; V3.2 ships are not blocked.

## V3.3 ENTRY READINESS analysis

### What V3.2 BUILDS that V3.3 CARRIES

1. **The vscode-free split pattern** (cellGridHtml.ts / cellGridLogic.ts /
   cellGridPanel.ts). V3.3 can grow `cellGridGrid.ts` (or rename to
   `cellGridRenderer.ts`) WITHOUT breaking the test surface. Mocha can
   continue to import + drive helpers without vscode. PASS.

2. **CSP-nonce + structured message envelope** (decision B1 PutValueRequest +
   ErrorReplyMessage). V3.3 will add `PutValueText`, `PutValueBool`,
   `SetFormula`, etc. as additional outgoing types; ErrorReply stays one-
   shape. The "unknown type logged + ignored" pattern is forward-compatible.
   PASS.

3. **parseQuantbookError + structured error code switching.** First
   production consumer of the V2.7 contract. V3.3 grid can hook
   `transport_closed` (network), `bad_argument` (input), `session_oplog`
   (CRDT internal) into distinct UI surfaces. PASS.

4. **CollabAttachment + handleTransportClosed reconnect ladder.** Lifted
   from V3.1.b multiWindowDemo verbatim. V3.3 multi-sheet inherits the
   same reconnect contract per-panel. PASS (assuming HIGH-1 is closed at
   V3.2.d).

5. **Single-tab-per-sheet (with the HIGH-1 fix applied).** V3.3 multi-sheet
   makes this multi-tab-per-window; one tab per (sheet, mode) pair.

6. **classifyPollTick** + the four-branch result. V3.3 may add a
   `'optimistic'` branch for the V3.x optimistic-render mode, or a `'stale'`
   branch for the snapshot-skew detection -- both are additive.

### What V3.2 SHIPS that V3.3 MUST REPLACE

1. **Full HTML rebuild via `webview.html = buildHtml(...)`.** Works at V3.2
   scale (hundreds of cells, 1Hz refresh); breaks at V3.3 scale (10K+ cells,
   needing virtualization + per-cell updates).

   **Path forward:**
   - Leading candidate: switch to a **client-side virtualized grid** using
     clusterize.js or a similar 1-file UMD library that doesn't pull in
     React or other heavyweight framework. The current inline script is
     ~110 lines; clusterize.js adds ~5KB. Webview CSP allows
     `'unsafe-eval'` if needed but the library doesn't require it.
   - Alternative: **react-window**. Requires React (~40KB) + a bundler step
     (webview script today is INLINE in cellGridHtml.ts -- adding a
     bundle artifact means asWebviewUri + new file in the extension). More
     work but matches the rest of the IDE's React posture.
   - NOT VIABLE: VS Code TreeView (no cell-grid affordance), DataTable
     (Theia/Eclipse Che pattern; not in VS Code).
   - The renderer must support **incremental updates** -- the merged-N-blobs
     path needs to mutate only the changed cells, not re-render. This
     requires a snapshot diff against the previous render. The
     `exportSnapshot` JSON return is already sorted by (row, col) which
     enables linear-merge diffing.

   **Decision to lock at V3.3 entry:** which virtualization library + diffing
   strategy. Mocha-friendly (pure functions) preferred.

2. **exportSnapshot full-op-log iteration.** O(N) in op count per call. At
   V3.3 scale this hits MEDIUM-4 (lock-hold time becomes user-visible).

   **Path forward:**
   - **Option A:** add a per-session `last_snapshot: HashMap<(u32, u32),
     CellWireValue>` field updated incrementally on `append_op` /
     `merge_bytes`. `exportSnapshot` reads from the cache instead of
     iterating. Requires careful invalidation on undo/redo (V3.4+).
   - **Option B:** route exportSnapshot through `rebuild_workbook`
     (V3.5+ Phase 5.3 closure). The Workbook struct already maintains a
     parsed cell map; exportSnapshot just reads from it. This is the
     "correct" architectural path but waits on the rebuild_workbook ship.
   - **Option C:** add `exportSnapshotSince(baseline_vv)` for incremental
     fetching. Reduces V8-thread blocking + matches the diff-merge
     renderer's needs.

   **Decision to lock at V3.3 entry:** Option A (incremental cache) is the
   simplest; can ship in V3.3 without waiting on rebuild_workbook (which is
   V3.5). Option B is the V3.5+ migration target. Option C is the V3.x
   polish.

3. **One panel = one sheet, sheet baked into script constant.** V3.3 needs
   either multi-sheet-per-panel (tabs) or sheet-selector UI.

   **Path forward:**
   - Recommend **one panel per (workbook, sheet)** for V3.3, with **sheet
     tabs in the panel webview** for navigation. Each tab = a different
     panel.webview.html rebuild (matches the V3.2 full-rebuild model;
     incremental updates within a single sheet still apply).
   - Alternative: **one panel = one workbook**, sheet selector inside the
     webview. Lower memory but more complex script logic.
   - **API surface needed:** `CollabSession.listSheets(): Vec<u16>` napi
     method. Today the V1 binding has no enumeration; sheets are addressed
     by u16 index but there's no list-of-known-sheets accessor.

   **Decision to lock at V3.3 entry:** one panel per (workbook, sheet) +
   add `listSheets()` napi + sheet-tab-in-webview. Multi-window-multi-sheet
   demo as the smoke for V3.3.

4. **rebuild_workbook routing.** V3.2 reads the local op log directly. V3.3
   may NOT need rebuild_workbook (it can still source from the op log + add
   the incremental cache from §2 Option A). But V3.4+ undo/redo + V3.5+
   formula evaluation REQUIRE rebuild_workbook.

   **Path forward:** keep V3.3 on direct-op-log reading; defer rebuild_workbook
   to V3.5+ (paired with Phase 5.3 production-visible closure). Architecture
   permits both -- the snapshot shape from exportSnapshot is decoupled from
   the source data.

5. **Persistence (.qbook save/load).** V3.2 has none. V3.3 needs it.

   **Path forward:**

## Engine context (what the xlsx I/O has to integrate with)

- **`Workbook`** (`crates/ql-storage/src/workbook.rs`): the in-memory
  representation. Has sheets, cells, named targets, tables, names.
- **`WorkbookRuntime`** (`crates/ql-exec/src/workbook_runtime.rs`):
  graph-based recompute + op-log + spill handling.
- **`.qbook/` persistence v7** is our native format (different from
  xlsx; bitcode-serialized).
- **Phase 4.8 tables** ship with rename / resize hooks, structured
  refs (`Sales[Qty]`).
- **Phase 4.9 locale + R1C1** ship; affects formula serialization.
- **260 fns** match Excel canon (with documented W5-58 strict-text
  divergences).

The xlsx I/O sits BETWEEN the file format and the Workbook —
bidirectional mapping.

## The three decisions

### Decision 1: Read library

| Option | Pros | Cons |
|--------|------|------|
| **calamine** | Battle-tested, fast, popular. Returns evaluated cell values + formula strings + basic structure (sheets, cells, named ranges). | Doesn't expose all OOXML XML. For features like conditional formatting / data validation / cell styles in full / table column types, you'd need to supplement with direct XML access anyway. |
| **Roll-own (zip + roxmltree)** | IronCalc's choice. Full XML access — you see every OOXML element. Total control over what's preserved. | High upfront effort (~1-2 weeks). Re-implementing well-trodden ground. Easy to miss OOXML edge cases that calamine has already solved. |
| **Hybrid (calamine + targeted XML)** | Use calamine for the 80%-common path (cells, formulas, values, sheets); roll-own for OOXML features calamine doesn't expose (CF, DV, table-column metadata, defined names with scope). | Two parsers to maintain. Risk of state drift between calamine's view and direct-XML view. |

Note: formualizer uses calamine + supplements (their backends/calamine.rs
is 1169 lines — it's NOT just a thin wrapper). IronCalc rolls its own
xlsx import in `.references/ironcalc/xlsx/src/import/`.

### Decision 2: Write library

| Option | Pros | Cons |
|--------|------|------|
| **umya-spreadsheet** | Pure rust, formulas + styles + tables + named ranges. Active maintenance. Read+write parity with formualizer's reader. | Some OOXML features unsupported; round-trip fidelity has edges. |
| **rust_xlsxwriter** | Production-grade, Microsoft-recommended porting line. Excellent for new xlsx generation. | No formula RECALC on write (the formulas you put in are kept as text). Less full-fidelity for our use case (we want our recomputed values cached in the output). |
| **Roll-own (zip + xml builder)** | Matches our reader if we go roll-own. Total control over the OOXML output. | High effort. |

### Decision 3: First batch scope (W5-D-14)

| Option | Scope | Closes | Estimate |
|--------|-------|--------|----------|
| **Minimal import** | Cells + sheets + values + formula strings. Skip styles/tables/names. Goal: open xlsx, populate Workbook, recompute via the engine. | XLSX-4-01 + 4-02 (minimal) | 3-5 days |
| **Read-only path full** | Complete read side first: cells + tables + names + styles + CF/DV. | XLSX-4-01 + 4-03 partial | 1-1.5 weeks |
| **Round-trip slice** | Tight loop: minimal import + evaluate + minimal export. | Round-trip story partial | 1 week |

## What I need from you

Think DEEPLY about what's optimal for QUANTBOOK SPECIFICALLY (not for
a generic xlsx tool). Consider:

1. **Round-trip is a primary user need**. Quantbook users will round-
   trip between xlsx and the engine. Fidelity loss compounds with
   each round-trip. Which approach minimizes lossy compression?

2. **Phase 5 is collaborative CRDT**. The xlsx I/O might be a one-way
   street most of the time (users import, work in Quantbook, share
   via Quantbook). Or it might be bidirectional and round-trip is
   critical. Argue both sides.

3. **Engine integration cost**: how much glue code is required between
   each library's data model and our `Workbook`/`WorkbookRuntime`?
   The library that's closest in shape to our internal model wins on
   integration speed.

4. **Long-term maintenance**: if we adopt calamine and it stagnates,
   what's the migration cost? Same for umya. vs. owning our own xlsx
   parser/serializer (large upfront, lower ongoing).

5. **Risk profile**: which approach is most likely to surface
   integration bugs LATE in Phase 4.11 vs EARLY? (Late surfacing
   forces phase slip.)

6. **What does formualizer ACTUALLY do** (they had to make the same
   decision)? Read `.references/formualizer/crates/formualizer-
   workbook/src/backends/calamine.rs` — is it just calamine or do
   they supplement?

7. **What does IronCalc actually do** — read `.references/ironcalc/
   xlsx/src/import/` — and what motivated their roll-own choice over
   calamine?

Use compiled probes if useful. Cross-check the libraries' actual

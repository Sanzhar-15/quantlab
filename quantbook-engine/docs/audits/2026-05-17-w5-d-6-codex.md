## MEDIUM

### MEDIUM-001

- **Subject:** COVARIANCE.S test/doc provenance does not match the current Microsoft support example
- **Where:** `crates/ql-functions/src/range_fns.rs:4157`, `crates/ql-functions/tests/coverage.rs:315`, `docs/compat/excel-matrix.md:90`
- **Detail:** The `covariance_s_microsoft_example` fixture computes valid sample covariance for `data1=[3,2,4,5,6]` and `data2=[9,7,12,15,17]`: `sum_prod=26`, divisor `n-1=4`, result `6.5`. However, the current Microsoft COVARIANCE.S support page documents `{2,4,8}` and `{5,11,12}` with result `9.666666667`; the `3/9 ... 6/17` dataset appears on the current Microsoft COVARIANCE.P page as the population-covariance example with result `5.2`. The implementation math is correct, but the test name/comment, coverage rationale, and compat matrix overstate this fixture as the Microsoft COVARIANCE.S anchor.
- **Recommendation:** Either replace/add a COVARIANCE.S fixture using Microsoft Support's current `{2,4,8}` / `{5,11,12}` example and expected `9.666666667`, or relabel the existing `6.5` fixture as a manual sample-covariance transform of the COVARIANCE.P/COVAR dataset. Update `coverage.rs` and `excel-matrix.md` to match the chosen provenance. Sources checked: Microsoft COVARIANCE.S support page (`https://support.microsoft.com/en-us/office/covariance-s-function-0a539b74-7371-42aa-a18f-1f5320314977`) and Microsoft COVARIANCE.P support page (`https://support.microsoft.com/en-us/office/covariance-p-function-6f0e1e6d-956d-4e4b-9943-cfef0bf9edfc`).
- **Severity rationale:** Medium because the compatibility evidence is falsely attributed to Microsoft COVARIANCE.S, which can mislead future audits, even though the actual covariance kernel and result are correct.

## LOW

### LOW-001

- **Subject:** Stale kernel rustdoc says `compute_covariance` requires at least two pairs
- **Where:** `crates/ql-functions/src/range_fns.rs:1419`
- **Detail:** The doc block immediately above `compute_covariance` still includes the CORREL-era precondition ``xs.len() == ys.len() >= 2``. That is contradictory for the new shared covariance kernel: `COVARIANCE.P` intentionally calls it with exactly one numeric pair and expects `0`, while `COVARIANCE.S` is the caller that enforces `n >= 2`.
- **Recommendation:** Split the CORREL formula/precondition docs from `compute_covariance`, and document the covariance kernel invariant as equal-length numeric slices with caller-specific minimum-n enforcement. A `debug_assert_eq!(xs.len(), ys.len())` would also make the shared-kernel contract explicit.
- **Severity rationale:** Low because current callers enforce the correct runtime preconditions and tests pin the single-pair population behavior; the risk is maintainability and future misuse.

### LOW-002

- **Subject:** COVARIANCE.S matrix row omits the constant-array semantic difference from CORREL
- **Where:** `docs/compat/excel-matrix.md:90`
- **Detail:** The COVARIANCE.P row documents `constant array -> cov=0 (NOT #DIV/0! like CORREL)`, but the COVARIANCE.S row does not mention the same zero-variance behavior. The unit test at `crates/ql-functions/src/range_fns.rs:4178` pins `COVARIANCE.S` constant-array output as `0`, and the W5-D-6 review criteria call out documenting this difference for both covariance variants.
- **Recommendation:** Extend the COVARIANCE.S matrix row to mention `constant array -> cov=0`, and ideally mirror the paired-array notes already present for COVARIANCE.P (`no numeric pairs -> #DIV/0!`, shape mismatch -> `#VALUE!`, non-numeric paired rows skipped).
- **Severity rationale:** Low because behavior and tests are correct; only the compatibility matrix under-documents an important edge case.

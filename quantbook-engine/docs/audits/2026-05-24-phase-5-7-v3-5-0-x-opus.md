## § B -- Cross-sub-step interaction surfaces (adversarial design audit)

### B.1 Tombstone + move + partial-invalidate interaction

#### B.1.a Tombstoned-sheet move

A user deletes sheet 3 (Op::RemoveSheet); subsequently calls moveSheet(3, 0). The napi check `if (sheet_id as usize) >= workbook.sheet_count()` -- this passes because tombstone preserves `sheet_count` (V3.5.0.3b semantic). So move proceeds.

`Workbook::move_sheet(3, 0)`: finds id=3 in `sheet_display_order`, removes it, re-inserts at clamped position 0. **Display order now `[3, 0, 1, 2, 4, ...]`.**

`workbookSnapshot`: iterates display order = `[3, 0, 1, 2, 4, ...]`; at `id=3`, `is_sheet_removed(3) == true`, skip. Snapshot returns `[0, 1, 2, 4, ...]` (sheet 3 omitted but still in display_order vec at position 0).

**Behavior is correct** but the docstring at workbook.rs:377-381 acknowledges this as "ORTHOGONAL"; the snapshot filter handles it. No bug, but the user's "move sheet 3 to position 0" intent is silently INVISIBLE in the snapshot. **The IDE may want to refuse move-on-tombstoned at the command layer** -- a defensive UX guard. NOT a bug.

#### B.1.b Move then delete then undo

Sequence: addSheet(S1), addSheet(S2), moveSheet(1, 0) [now display = `[1, 0]`], deleteSheet(1) [tombstone id=1], undo() [retracts Op::RemoveSheet].

Undo dispatch:
- `pre_undo_last_op` = `Op::RemoveSheet { id: 1 }`.
- `affected_cells_for_partial_invalidate(Op::RemoveSheet)` returns `None` (non-cell-keyed; `_ => false` catch-all in `collect_affected_cells_recursive`).
- Falls back to `rebuild_snapshot_cache()` -- correct.

Post-undo state: log = `[AddSheet S1, AddSheet S2, MoveSheet 1 -> 0]`. Re-replay rebuilds Workbook. `Workbook::default()` -> 2 AddSheet calls add ids 0, 1 to `sheets` AND append 0, 1 to `sheet_display_order`. Then MoveSheet(1, 0) -> display = `[1, 0]`. `removed_sheets` is now empty (`Workbook::default()` initialized fresh). **Sheet 1 is correctly resurrected; display order preserved.**

This is the design intent: tombstone is on the WORKBOOK STATE (rebuilt fresh per `rebuild_workbook`), not on the OPLOG. Op::RemoveSheet undone = it's no longer in the visible log = next rebuild has no tombstone. **No bug.**

But this exposes an interaction: `rebuild_workbook` is called inside `workbook_snapshot` napi (every render). Undo of RemoveSheet via full-rebuild only updates `last_snapshot` (cell cache). The next `workbook_snapshot` call rebuilds `Workbook` fresh, sees no Op::RemoveSheet, returns the un-tombstoned sheet. **Correct end-to-end.**

#### B.1.c Undo retracting SetCellFormat on tombstoned sheet

Setup: addSheet(S1), addSheet(S2), setCellFormat(sheet=1, row=0, col=0, builtin=2), deleteSheet(1), undo() [retracts deleteSheet].

After undo of deleteSheet: rebuild fresh -> SetCellFormat applies normally (sheet 1 exists). Cache walker `apply_cache_effect::SetCellFormat` writes state.format. **Correct.**

Same setup but: ..., undo() [retracts SetCellFormat, sheet 1 still tombstoned].

- pre_undo_last_op = `Op::SetCellFormat { sheet: 1, row: 0, col: 0, id: Some(_) }`.
- affected_cells_for_partial_invalidate returns `Some([(1, 0, 0)])`.
- `invalidate_cell(1, 0, 0)`: drops cell entry, walks log applying effects on (1,0,0).
- Walker finds SetCellFormat (still in log? no -- retracted), but does it? Wait -- Loro UndoManager appends an INVERSE op (not physical removal at the LoroDoc level, but the visible iteration shrinks because the inverse op resolves to the same containerized state).

Actually `pre_undo_last_op` is captured BEFORE undo. So we know the retracted op's shape. `invalidate_cell((1,0,0))` walks the POST-undo log. The retracted op is no longer visible (verified by V3.5.0.6's shrink-by-1 check + the V3.4.0.X `undo_retracts_visible_op_from_op_log_len` test). So the walker sees: AddSheet x2 + RemoveSheet(1). No SetCellFormat ops touching (1,0,0). Result: cell at (1,0,0) is removed from cache (ghost-entry-avoidance). **Correct.**

But the SetCellFormat replay handler at `replay.rs:728-757` does NOT check `is_sheet_removed`. This is a SEPARATE BUG -- see H1 below.

### B.2 Format extension + partial-invalidate interaction

#### B.2.a Format-only cell + SetCellFormat retraction

Sequence: addSheet(S1), setCellFormat(0, 0, 0, builtin=2), undo() [retracts SetCellFormat].

- pre_undo_last_op = SetCellFormat.
- affected_cells = Some([(0, 0, 0)]).
- invalidate_cell(0, 0, 0): drops entry; walks log; finds AddSheet only (no cell-keyed effects on (0,0,0)); applies no effects; local_snapshot empty; ghost-entry-avoidance leaves the entry removed.

**Correct ghost-entry handling**. Apply_cache_effect's `format: Some` -> `entry().or_default()` would CREATE an entry, but no SetCellFormat survives in the walked log so nothing fires.

#### B.2.b SetCellFormat { id: None } on never-set cell

Per cache walker: `format: None` -> `get_mut + skip-if-absent` (apply_cache_effect lines 834-841). On a never-set cell, get_mut returns None, no-op. **Correct ghost-entry avoidance.**

But the spec's wording at § 4.1.z5 line 1465 says "all three fields None triggers cache key removal". This requires entry to ALREADY EXIST. The check at apply_cache_effect line 837 reads `state.value.is_none() && state.formula.is_none() && state.format.is_none()` -- this is inside `if let Some(state) = snapshot.get_mut(&key)`, so it ONLY fires on existing entries. Correct.

If a cell had `(value=Some, formula=None, format=Some)`, then `SetCellFormat { None }` clears format -> `(value=Some, formula=None, format=None)` -> doesn't satisfy all-None -> entry preserved. Correct.

### B.3 Render migration + mid-edit-render guard interaction

**Question (audit prompt §B.3)**: should the mid-edit-render guard also block `onCommit`-triggered renders?

Answer: NO. Here's the rationale verified against code:
- `onCommit` fires from `dispatchIncomingMessage`'s `putValue` arm AFTER `appendPutValueValidated` succeeds. This happens AFTER the user has clicked Enter or otherwise committed the cell.
- At this point, `typing: false` should ALREADY have been broadcast by the webview's `endEdit(commit=true)` flow.
- The V3.4.0.X HIGH-3 closure moved the `typing:false` broadcast above the if(commit) branch -- so it ALWAYS fires before the commit's putValue.

So the sequence for local commit:
1. Webview: user presses Enter.
2. Webview `endEdit(true)`: posts `presenceUpdate { typing: false }`.
3. Dispatcher's presenceUpdate arm: calls `updatePresence(typing:false)`, then `onLocalTyping(false)`.
4. `setPresenceTyping(false)` -> `_presenceRepaintInFlight = false`.
5. Webview posts `putValue` message.
6. Dispatcher's putValue arm: calls `appendPutValueValidated`, then `onCommit()`.
7. `onCommit` -> `render()`.

By step 6, `_presenceRepaintInFlight === false`. So even if the guard checked the flag for `onCommit`-triggered renders, it would not block. **The guard's "merged tick only" scope is correct.**

The non-trivial case: REMOTE commit lands while local user is mid-editing -- handled by the merged-tick branch (which IS guarded). **Design is correct.**

### B.4 Undo dispatch peek-most-recent + MoveSheet interaction (and CRITICAL FINDING)

#### B.4.a MoveSheet undo via full-rebuild

undo of Op::MoveSheet: `affected_cells_for_partial_invalidate` returns `None` -> full rebuild. Full rebuild rebuilds `last_snapshot` from scratch via `collect_cache_effects` + `apply_cache_effect`. These ONLY mutate the cell cache; Workbook state (including `sheet_display_order`) is NOT rebuilt by `rebuild_snapshot_cache`.

But the spec says "Display-order undo via `invalidate_cell`-style approach" is V3.5.0.6 partial-invalidate work (out-of-scope at § 4.1.z5). When MoveSheet is undone:
- last_snapshot (cell cache): rebuilt from log walk -- NO ops touch cells, so it stays unchanged. Correct.
- `Workbook.sheet_display_order`: lives on the WORKBOOK, which is rebuilt fresh PER `workbook_snapshot` call via `rebuild_workbook`. Next render rebuilds the workbook; since the MoveSheet was retracted, the rebuild doesn't apply it; display_order reverts to append order.

**End-to-end correct via the Workbook-rebuild-per-snapshot pattern.** The "Display-order undo" V3.6 deferral in the spec is misleading -- undo of MoveSheet ALREADY works correctly because `workbook_snapshot` rebuilds Workbook fresh every call. The deferral is really about "partial-invalidate of display order without full Workbook rebuild" -- a performance concern, not correctness.

Recommendation: clarify the spec at line 1545.

#### B.4.b **HIGH-2: partial-invalidate picks the WRONG cell when a remote cell-keyed op trails the retracted local op in iteration order**

**File**: `crates/ql-collab/src/session.rs:2338-2408`

The undo dispatch captures `pre_undo_last_op` via `self.log.iter().last()` BEFORE undo. This is the most-recent VISIBLE op. The docstring acknowledges: "when no remote op landed AFTER that local op, the most-recent VISIBLE op equals the to-be-retracted op."

But Loro CRDT iteration order is causal+(lamport,peer-id)-tiebreaker. If a remote op `R` has lamport timestamp > local op `L`'s lamport (e.g., the remote peer saw L before producing R), then iteration order is `[..., L, R]`. After merge_bytes(R), the cache is full-rebuilt -> correct. Then user undoes L. UndoManager retracts L. Visible log = `[..., R]` (len shrunk by 1).

Pre-undo last_op (captured BEFORE undo) = R. Post-undo len = pre_len - 1 (shrink check passes). `affected_cells_for_partial_invalidate(R)` returns `Some(R's cells)` (if R is cell-keyed). Dispatch calls `invalidate_cell(R's cells)`. **But L's cells are NOT invalidated.** L's cache entry retains the value L wrote.

Concrete scenario:
```
peer A: appendOp(PutValue(0, 0, 0, 100.0))  // L
peer B (independently): appendOp(PutValue(0, 1, 1, 200.0))  // R, lamport > L's
peer A: merge_bytes(B's export)
  -> cache full-rebuilt; cells (0,0,0)=100 and (0,1,1)=200
peer A: undo()
  -> pre_undo_last_op = iter().last() = R (because R's lamport > L's, R is iterated last)
  -> shrink check passes (len went from 2 to 1)
  -> partial_cells = Some([(0,1,1)])  // R's cell, NOT L's
  -> invalidate_cell(0,1,1) -- rebuilds R's cell correctly (R still in log)
  -> cache: (0,0,0)=100  // STALE -- L was retracted but cache still says 100
           (0,1,1)=200   // correct
```

Expected post-undo state: `(0,0,0)` should be ABSENT (no surviving op writes to it); `(0,1,1)=200` (R still in log). Actual: `(0,0,0)=100`. **CORRECTNESS BUG.**

**Severity**: HIGH. Triggers whenever:
1. The session has remote ops (collab mode).
2. A remote op's lamport > most-recent-local-op's lamport.
3. User undoes the local op.

Step 2 is common: any concurrent collab where the remote peer was active after the local user appended. Step 1 is the entire collab use case.

**Mitigation**:
- Fix 1: capture pre_undo_last_op via "most recent LOCAL op" (filter by peer-id in iter()), not just `iter().last()`. Loro exposes peer-id in OpId; the OpLog::iter() shape would need extension.
- Fix 2: conservative fallback -- if `self.log.iter().count_by(|op| produced_by_this_peer) > 0_after_partial_check`, fall back to full rebuild whenever there's any remote op since the local one. Simpler but defeats partial-invalidate for any collab session with active remote peers.
- Fix 3 (cleanest, V3.6+ scope): wait for Loro UndoManager `on_pop` callback (V3.5 D2 deferral); it surfaces the retracted op shape directly.

**Recommended in-cycle closure**: ship Fix 2 (conservative fallback) NOW. It preserves correctness while leaving the architectural shape (partial-invalidate dispatch) intact for the local-only case. V3.6+ replaces with Fix 3 / per-cell op-index.

Or alternatively: add a regression test that captures this scenario + a comment in `pub fn undo()` acknowledging the known-correctness gap until Fix 3 lands; demote to KNOWN-GAP.

This is the V3.5.0.6 R-V3.5-2 risk register item ("Partial-invalidate undo correctness under causal reorder") but the risk register description doesn't enumerate this specific failure mode. Recommend in-cycle update to the risk text.

The test `local_undo_after_remote_merge_preserves_remote_ops` at session.rs:4176-4210 verifies Loro-level retract semantics but does NOT check the per-cell cache after the undo. **Test gap.**

### B.5 Mid-edit-render guard + Delete Sheet command interaction

**Scenario**: user is mid-editing in sheet 0 of window A (`_presenceRepaintInFlight = true`); user (or remote peer) deletes sheet 0 via quantbookSheetDelete; merged tick fires render; render is SKIPPED due to flag; user finishes typing; flag clears; next merged tick renders.

At render time: `workbookSnapshot()` -> `rebuild_workbook` sees `Op::RemoveSheet(0)` -> Workbook has tombstone on sheet 0. `extractSheetSnapshot(snapshot, this.sheet=0)` looks for `id=0`; the napi already filtered tombstoned sheets out of the returned snapshot at workbookSnapshot napi level. So `extractSheetSnapshot` returns `null`.

`render()` falls back to empty entries + `console.warn`. Panel shows empty cell grid. User's typed content (the PutValue that was on its way) -- what happens?

Walk:
1. User clicks cell A1 in sheet 0 -> beginEdit -> `<input>` appears.
2. presenceUpdate { typing: true, sheet: 0 } broadcasts.
3. Another peer (or local concurrent op) executes deleteSheet(0).
4. Remote merge arrives via pollRemote -> merge_bytes -> cache full-rebuilt -> classifyPollTick returns 'merged'.
5. tickPollRemote: `_presenceRepaintInFlight === true` -> SKIP render + log warning.
6. User types "999" + Enter.
7. Webview `endEdit(commit=true)`: posts presenceUpdate { typing: false } THEN posts putValue { sheet: 0, row: 0, col: 0, rawInput: "999" }.
8. Dispatcher: presenceUpdate arm -> updatePresence + onLocalTyping(false) -> `_presenceRepaintInFlight = false`.
9. Dispatcher: putValue arm -> `appendPutValueValidated(session, 0, 0, 0, parsed)`.
   - This appends `Op::PutValue { sheet: 0, row: 0, col: 0, value: 999.0 }` to the log.
   - `append_op` updates cache: `apply_cache_effect::PutValue` -> `entry().or_default().value = Some(999.0)`. The CACHE now has (0,0,0)=999.
   - But the WORKBOOK state at next rebuild has `removed_sheets={0}`. So on replay, the PutValue is silently dropped (V3.5.0.3b semantic at replay.rs:411-417).
   - **MISMATCH**: cell-cache has (0,0,0)=999, but workbook (rebuilt fresh) does NOT have this cell. **`workbook_snapshot` napi has tombstone filter that SKIPS the entire sheet 0** -- so the (0,0,0)=999 stale cache entry is invisible to the IDE renderer (because the napi only emits cells for non-tombstoned sheets).

10. onCommit -> render() -> workbookSnapshot -> sheet 0 absent -> extractSheetSnapshot null -> empty entries.

**End-result for user**: sheet 0 panel shows EMPTY. The typed "999" is silently lost from the user's perspective. The Op::PutValue is still in the log (for archaeology). The cache has stale (0,0,0)=999 that's never surfaced.

**Severity**: This is the V3.5.0.3b "silent drop on tombstoned sheet" semantic at the user level. It's intentional but USER-HOSTILE in this race scenario. The user MIGHT have lost work without realizing it.

**Mitigation options**:
- (a) The IDE could refuse putValue if `extractSheetSnapshot(snap, this.sheet) === null` at commit time (catch the tombstone race + show a warning toast).
- (b) Auto-dispose the panel when its sheet is tombstoned (the V3.5.0.4b docstring at cellGridPanel.ts:511 mentions "V3.6+ may auto-dispose").
- (c) Surface a permanent banner on the panel: "This sheet was deleted; your edits will not persist".

**Recommendation**: V3.5.1+ closes this. The V3.5 ship behavior is "graceful but lossy"; the user-visible signal (`console.warn` + empty render) is weak. Document in the R-V3.5-3 risk register entry that the V3.5.0.4b "sheet-not-found tombstone-race fallback" can silently drop user input under this race. **Severity at V3.5 ship**: ACKNOWLEDGED-LOW (rare race; user can re-open the workbook). At V3.5.1+: address via (a) or (b).

Note: the V3.5.0.4b cellGridPanel.ts docstring at line 506-511 acknowledges this race. The spec at § 4.1.z5 line 1447 also mentions it. But neither mentions the SILENT-DROP-OF-USER-INPUT consequence. Spec drift -- recommend update.

## § F -- V3.6 ENTRY READINESS PACKET (the design basis for V3.6.0.1)

This is the analogue of V3.4.0.X Opus § F V3.5 ENTRY READINESS. Each item lists: (a) recommended decision; (b) rationale; (c) effort estimate; (d) risks; (e) interaction with other V3.5 surface.

### F.1 Session-wide RegisterFormat FormatTable cache (V3.5.0.5 deferral)

**Decision recommendation**: NEW session-wide `format_table_cache: HashMap<FormatId, String>` on `CollabSession`. Cache shape mirrors `Workbook::formats` (which is `FormatTable`). Walker integration: `collect_cache_effects` handles `Op::RegisterFormat` by emitting a new `CacheEffect::RegisterFormat { id, string }`. `apply_cache_effect` inserts into the cache. WorkbookSnapshot napi extends with `formats: Vec<FormatDefJson>` field (additive; preserves V3.5 IDE consumers).

**Rationale**:
- Per-cell format passthrough (V3.5.0.5 ship) is incomplete without RegisterFormat for V3.6+ format-aware rendering (the IDE needs the format STRING to render).
- Session-wide cache matches the cache pattern V3.4.0.2 established for cell-keyed ops.
- Cross-peer convergence: concurrent RegisterFormat on the same id either resolves via Loro causal-merge (deterministic peer-id tiebreaker) OR -- if `register_at` rejects same-id-different-string -- the second registration produces a `FormatRejected` replay error. V3.6 design must decide: error or LWW-overwrite?
- Cache invalidation: a `Op::RegisterFormat` invalidates EVERY cell with that format id (in terms of format-aware rendering). The cell cache (CellState.format) is NOT invalidated -- it carries the FormatId which is stable across re-registration. So no cross-cache invalidation needed.

**Effort**: 2 sessions (1 for cache infrastructure + invariant pin; 1 for napi extension + IDE consumption infra).

**Risks**:
- Cross-peer concurrent RegisterFormat collision -- decide between error/LWW at design lock.
- Memory cost: format definitions are bounded (workbooks typically have < 100 custom formats) -- negligible.
- Schema-version: NO bump needed -- WorkbookSnapshotJson extension is additive (TS consumers that destructure `.sheets` only keep working).

**Interaction with V3.5**:
- Extends V3.5.0.5 CellState.format passthrough -- cells point at format ids; format ids resolve via the new session-wide cache.
- Extends V3.5.0.2 WorkbookSnapshotJson -- new top-level field `formats: Vec<FormatDefJson>`.

**V3.6.0.X sub-step suggestion**: V3.6.0.1 design lock + V3.6.0.2 ship + V3.6.0.3 cross-peer tests.

### F.2 Format-aware buildHtml rendering (V3.5.0.5 deferral)

**Decision recommendation**: Phase 1 -- numeric / currency / percentage / scientific format STRINGS interpreted via a deterministic engine-side Rust `format_value(value, format_string) -> String` function (already exists at `ql-storage::format::FormatTable::render_value`). IDE receives the pre-rendered string in CellSnapshotJson; no JS-side eval / template injection (CSP-safe).

**Rationale**:
- Engine-side rendering is CSP-safe; no `<script>` injection or JS eval needed.
- The format machinery already exists at `ql-storage::format::FormatTable` (used by xlsx export); reuse it for IDE rendering.
- The CellSnapshotJson schema could add `rendered: Option<String>` (the format-interpreted display string) -- additive.
- Alternative: ship raw value + format id; IDE computes the display string via a TS port of the format machinery. Avoid -- duplicates engine logic.

**Effort**: 2 sessions (1 for engine `format_value` API extraction + napi extension; 1 for IDE consumption + buildHtml integration).

**Risks**:

**Interaction with V3.5**: extends V3.5.0.5 format passthrough + V3.5.0.2 WorkbookSnapshotJson shape.

**V3.6.0.X sub-step suggestion**: V3.6.0.4 (after F.1 ships).

### F.3 Per-cell op-index for O(ops-for-this-cell) invalidate_cell (V3.5.0.6 deferral)

**Decision recommendation**: NEW `cell_op_index: HashMap<(SheetId, RowId, ColId), Vec<usize>>` on `CollabSession`. Maps cell coordinate -> list of op-log indices that emit an effect on that cell. Maintained incrementally in `append_op` per emitted CacheEffect's key. Rebuilt during `from_snapshot` + `merge_bytes` (full walk -- O(N) but only once per merge).

**Rationale**:
- Closes the V3.5.0.6 R-V3.5-2 cost story -- `invalidate_cell` would walk `cell_op_index[(s, r, c)].iter()` instead of the full log.

- BatchCommit recursion: each inner cell-keyed op contributes one index to the inner cell's vec. Tracked via the same `collect_cache_effects` walker that emits the effects.
- Invariant: every op-log mutation site (`append_op`, `merge_bytes`, `from_snapshot`, `discard_pending_ops`, `undo`, `redo`) updates `cell_op_index` in sync with `last_snapshot`. Mirrors the cache discipline.

**Interaction with V3.5**:

## What to look for

For each of the 4 functions, find:

1. **Mathematical errors.** Sign mistakes, off-by-one in period indexing, formula transcription errors against Microsoft canon and IronCalc reference. For DB in particular: the period-2 / period-life+1 / period-in-middle branches each have subtle correctness conditions — does the `accumulated` variable actually hold cumulative-through-(k-1) at the right moment?

2. **Divergences from IronCalc / Microsoft canon.** Both intentional (and documented in matrix?) and accidental.
   - DDB: we use `arg_num` for the `factor` arg; IronCalc uses `get_number_no_bools`. Documented in matrix — verify that's actually flagged correctly.
   - DB: is the 3-decimal rate-rounding identical? `round((1 - (salvage/cost)^(1/life)) * 1000) / 1000`?
   - SYD's `#NUM!` vs SLN's `#DIV/0!` for `life=0` — verify the asymmetry matches Microsoft (not just our internal choice).

3. **Missing edge cases.**
   - `cost == 0` short-circuits documented for DB; what about DDB / SYD / SLN? `compute_ddb` would compute `0 * ...` which is fine. `compute_syd` with `cost == 0`, `life > 0`: `(0 - salvage) * ... / (life * (life+1))` produces something. Is that the right Excel behavior?
   - `salvage > cost` for any of them. Microsoft docs sometimes say "Salvage must be less than or equal to Cost" — do we validate, and is that documented?
   - `life < 0` for any of them. SLN allows; SYD allows (per IronCalc); DDB has `life > 0` implicitly via `period > life` check — but `factor / life` with negative life flips the rate sign. What does Excel do?
   - NaN / Inf inputs. `arg_num` doesn't filter NaN/Inf; do we surface them via `sanitize_f64` at the end?
   - DB with `life == 0` and `period == 1`: validation lets it through (no explicit `life > 0` check); rate becomes `(salvage/cost)^(1/0) = (salvage/cost)^Inf`. What's the result? Should we reject?

4. **Validation gaps.** Arity boundaries (0, min-1, max+1). Error propagation: if `args[2]` is `Value::Error(#REF)`, does that propagate? What about `Value::Error(#REF)` in the optional 5th arg of DDB/DB — is the `match arg_num` evaluated only when `args.len() == 5`?

5. **Test gaps.**
   - DB tests assert `Value::Number(_)` for `period == life` with `db_full_year_period_equals_life_succeeds` — does it actually pin the *value* or just the fact that it's a number? Could mask a regression where the value is wrong but type is right.
   - DDB rate-clamp test: does it actually test both branches (period == 1 returns cost vs period > 1 returns 0)?
   - SYD `sum_over_periods` invariant: is the tolerance (1e-6) appropriate given floating-point accumulation across 10 periods?
   - Any fixture that hard-codes a value instead of computing it from the formula?

6. **Documentation accuracy.**
   - Each function's doc-comment vs implementation. Anything claimed in the comment that's not actually enforced in code?
   - Matrix row's description vs implementation behavior. Any divergence not flagged?
   - Coverage list entry vs what tests actually pin.

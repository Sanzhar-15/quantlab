# Codex Audit - W5-D-5 Distributions

Scope: `GAMMA` / `GAMMA.DIST` / `GAMMA.INV` / `GAMMALN` / `GAMMALN.PRECISE` / `BETA.DIST` / `BETA.INV` / `CONFIDENCE.NORM` / `CONFIDENCE.T`.

Summary: 1 HIGH, 0 MEDIUM, 2 LOW.

## HIGH

### CODEX-HIGH-1 - `GAMMA.INV` can non-terminate when scale reciprocal overflows

Where: `crates/ql-functions/src/distribution_fns.rs:1421`, `crates/ql-functions/src/distribution_fns.rs:1511`

Detail: `gamma_dist_with` converts Excel's shape-scale parameters to statrs's shape-rate form with `let rate = 1.0 / scale`, but it only relies on callers checking `scale > 0`. Finite subnormal scale values are accepted by the formula lexer/coercion path, for example `5E-324`; `1.0 / 5e-324` is `+Inf`. statrs 0.18.0 then accepts `Gamma::new(1.0, +Inf)` because it rejects NaN / `<= 0`, and only rejects the case where both shape and rate are infinite.

For `GAMMA.INV(0.5, 1, 5E-324)`, `dist.inverse_cdf(0.5)` enters statrs's bracketing loop. With `rate = +Inf`, `cdf(high)` remains `0.0` for the doubled `high` values and still returns `0.0` when `high` becomes `+Inf`, so `while self.cdf(high) < p { high *= 2.0; }` never exits. I confirmed this with a direct compiled probe of `gamma_inv(&[0.5, 1.0, 5e-324])`, which timed out after 2 seconds. The same unchecked rate overflow can also make `GAMMA.DIST` return incorrect finite values for tiny scales instead of surfacing a clean error.

This is reachable from formula input: the lexer parses finite subnormal numeric literals and only rejects NaN/Inf.

Recommendation: Guard the converted rate before constructing statrs `Gamma`. A minimal fix is to make the helper return `Result<Gamma, ErrorValue>` or to precompute in each caller:

```rust
let rate = 1.0 / beta_scale;
if !rate.is_finite() {
    return Value::Error(ErrorValue::Num);
}
```

Then construct `Gamma::new(alpha, rate)` only after the finite-rate check. Add regression tests for `GAMMA.INV(0.5, 1, 5e-324)` returning `#NUM!` without hanging, and a companion `GAMMA.DIST` tiny-scale pin.

Severity rationale: This is a workbook-triggerable non-termination in a scalar function. It can hang formula evaluation rather than returning an Excel error, so it is availability-impacting, not just a numeric parity issue. IronCalc appears to share the unchecked conversion, but this is the same class of statrs edge where the prior W5-D-4 panic fix correctly diverged from IronCalc to protect the engine.

## LOW

### CODEX-LOW-1 - `GAMMA.INV(1, ...)` effective behavior is not pinned or documented clearly

Where: `crates/ql-functions/src/distribution_fns.rs:1488`, `crates/ql-functions/src/distribution_fns.rs:1512`, `docs/compat/excel-matrix.md:124`

Detail: The function docs and matrix say `GAMMA.INV` accepts `0 <= probability <= 1` inclusive. The implementation does allow `p == 1` past the domain check, but statrs returns `max() == +Inf`; the finite guard then returns `#NUM!`. That matches IronCalc's effective implementation path, but neither unit nor e2e tests pin the upper endpoint, and the matrix wording can be read as if `p == 1` is accepted as a valid result-producing input.

Recommendation: Add unit and dispatcher tests for `GAMMA.INV(1, 1, 1) -> #NUM!`, and clarify the docs/matrix wording: domain check is inclusive, but `p == 1` maps to `#NUM!` because the inverse is non-finite.

Severity rationale: Current runtime behavior is plausibly correct for the IronCalc port, but the endpoint is easy to regress or misunderstand during future cleanup.

### CODEX-LOW-2 - Dispatcher coverage lacks a `BETA.INV` / `BETA.DIST` round-trip

Where: `crates/ql-exec/tests/distribution_fns_e2e.rs:935`

Detail: Unit tests cover the beta round-trip in `distribution_fns.rs`, and e2e tests cover individual `BETA.DIST` and `BETA.INV` dispatcher calls. The dispatcher round-trip section only pins `GAMMA.INV` composed with `GAMMA.DIST`; there is no corresponding e2e `BETA.INV(p, alpha, beta)` then `BETA.DIST(x, alpha, beta, TRUE)` check. This leaves the variadic beta pair less protected at the registry/parser/dispatcher layer than the gamma pair.

Recommendation: Add an e2e round-trip test analogous to `gamma_inv_dist_round_trip_through_dispatcher`, ideally including optional `[A, B]` bounds to exercise the transformed-domain path through both functions.

Severity rationale: This is a coverage gap, not an observed implementation bug. The unit tests already validate the math, and existing dispatcher tests prove the functions are registered and callable.

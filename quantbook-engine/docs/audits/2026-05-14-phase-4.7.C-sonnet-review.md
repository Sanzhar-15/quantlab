## 1. `lex_error_sigil` correctness

### 1.1 Clone-then-advance pattern

**PASS.** The function clones `chars` (a `Peekable<Chars<'_>>`) into `peek`, advances `peek` via the fragment-collection loop, then consumes exactly `matched_len` chars from the real `chars` iterator. `Peekable<Chars>` is `Clone`; cloning copies the underlying `Chars` iterator state independently. No aliasing is possible — `chars` and `peek` are separate owners of separate `Chars` values reading from the same underlying `&str` (which is immutable). There are no double-consume bugs: the real iterator is not advanced during fragment collection, only after a match is found.

### 1.2 Longest-first match is actually the longest match

**PASS.** The match loop (`for ev in ql_types::ErrorValue::ALL { ... }`) iterates all 15 sigils and updates `best` only when `sigil.len() > prev_len` (strictly greater). The final `best` holds the longest match. There is no early-return on first match. Additionally, a Python exhaustiveness check confirmed that **no sigil is a case-insensitive prefix of any other sigil** — so even a naive first-match would be correct. The longest-first logic is sound regardless.

### 1.3 Byte-length vs char-length

**PASS.** Every sigil character in all 15 `ErrorValue` sigils is ASCII (letters `A-Z`, digits `0-9`, `_`, `/`, `!`, `?`). The comment at `lexer.rs:267` states this correctly: "All sigil bytes are ASCII (1 char = 1 byte), so byte length and char count coincide." The fragment-collection loop accepts the same ASCII-only set, so `fragment` is always ASCII. The `for _ in 0..matched_len { chars.next(); }` loop consumes exactly the right number of Unicode scalar values (= bytes for ASCII). Safe.

One observation: the `.` character is included in the fragment-body char set (`lexer.rs:240`) but no current sigil contains a dot. This is dead code — harmless but slightly misleading. Not a bug.

### 1.4 Over-consume guard removal

**PASS.** The function collects a fragment of all sigil-body chars, finds the longest sigil that is a prefix of the fragment, then consumes exactly `matched_len` chars. The tail of the fragment beyond `matched_len` is never consumed — it was only built on the clone, not the real iterator. For example, `#REF!5`: fragment = `"#REF!5"` (6 chars, `5` included because `'0'..='9'` is in the body set), `matched_len = 5` (`#REF!`), real iterator consumes `#`, `R`, `E`, `F`, `!`; `5` remains. The `error_sigil_followed_by_digit_does_not_over_consume` test confirms this.

There is no over-consume bug in any edge case:
- Fragment longer than sigil: only `matched_len` chars consumed.
- Fragment equals sigil exactly: all chars consumed.
- Fragment shorter than any sigil: `best` is `None`, returns `InvalidErrorSigil`.

## 4. Test coverage gaps

### 4.1 Quantbook-specific sigils not per-tested

**FAIL — MEDIUM severity.**

The commit adds 10 per-sigil tests covering all 9 Excel-canonical sigils plus `#CIRC!`. The 5 Quantbook-specific sigils have **no dedicated positive lex tests**:

- `#DISCONNECTED!` (`ErrorValue::Disconnected`)
- `#BINDING!` (`ErrorValue::Binding`)
- `#TIMEOUT!` (`ErrorValue::Timeout`)
- `#PERMISSION!` (`ErrorValue::Permission`)
- `#AI_NOT_AVAILABLE_V1` (`ErrorValue::AINotAvailable`)

These variants ARE in `ErrorValue::ALL` so they would be recognized by the current code. The `case_insensitive` test covers 3 different sigils (Ref, Value, NA) but not any QB-specific ones. If a future refactor accidentally dropped a QB-specific sigil from `ALL` without updating `sigil()` (which would cause a compile error), or added a typo in `ALL`, there would be no test to catch it.

**Severity:** MEDIUM — the code is correct today; this is an under-tested area for Quantbook-specific surface. A test for at least `#DISCONNECTED!` and `#AI_NOT_AVAILABLE_V1` (the longest sigil, no `!`/`?` terminator) would close the gap.

**File/line:** `crates/ql-formula-syntax/src/lexer.rs` — add tests near line 1680.

**Suggested fix:** Add 5 minimal lex-ok tests (one per QB-specific sigil), mirroring the pattern of `error_sigil_circ_lexes`. Especially important for `#AI_NOT_AVAILABLE_V1` because it ends with a digit `1` rather than `!`/`?`, making it the structural analog of `#N/A` — a case where the "no trailing terminal punctuation" path is exercised for a long sigil.

### 4.2 `{}` empty array literal

**PASS.** `lbrace_and_rbrace_lex_to_brace_tokens` lexes `"{}"` and verifies exactly `[LBrace, RBrace]`. Empty array literal coverage at the lexer level is present. (Parser rejection of semantically empty arrays is a 4.7.D concern.)

### 4.3 Nested braces `{{1, 2}}`

**PASS (not a 4.7.C concern).** The lexer would emit `LBrace, LBrace, Number(1), Comma, Number(2), RBrace, RBrace` — two `LBrace` tokens. Per design § 3.3, nested arrays are out of scope; the parser (4.7.D) will reject this with `ParseError::Unexpected`. No lexer-level test is needed because the lexer has no concept of nesting — both `{` chars emit `LBrace` and both `}` chars emit `RBrace`. This is correct behavior; the parser enforces grammar constraints.

### 4.4 Leading whitespace before sigil (` #REF!`)

**PASS.** The main `lex` loop skips `' ' | '\t' | '\n' | '\r'` before dispatching on the next character (`lexer.rs:81-83`). Leading whitespace before `#` is consumed by the loop's whitespace-skip; the next character seen is `#`, dispatching to `lex_error_sigil`. This is correct and inherited from the existing whitespace handling. No dedicated test needed.

### 4.5 `#AI_NOT_AVAILABLE_V1` followed by content

**PASS (tested implicitly, but no dedicated test).** This sigil ends with digit `1` (not `!`/`?`), structurally parallel to `#N/A`. Fragment collection would collect `#AI_NOT_AVAILABLE_V1X` (if `X` follows), match the 20-char sigil as a prefix, and leave `X` in the real iterator. The `error_sigil_na_followed_by_letter_does_not_over_consume` test covers the analogous case for `#N/A`. No dedicated test for `#AI_NOT_AVAILABLE_V1` over-consume, which falls under the MEDIUM gap in §4.1.

## 5. Doc-vs-code drift

### 5.1 Token types match design § 3.3

**PASS.** Design § 3.3 specifies array cells as `NUMBER | STRING | BOOL | error literal`. At lex time:
- `NUMBER` → `Token::Number(f64)` — pre-existing, unmodified.
- `STRING` → `Token::String(Arc<str>)` — pre-existing, unmodified.
- `BOOL` (`TRUE`/`FALSE`) → no `Token::Boolean` exists; the parser resolves these via the `Token::Ident` path (`parser.rs:231-235`). This is documented in a comment at `parser.rs:228`. The lexer behavior is unchanged and correct; the 4.7.D parser must handle `Ident("TRUE")` / `Ident("FALSE")` inside array literals via the same resolution path.
- `error literal` → `Token::Error(ErrorValue)` — **new in this commit**. Correct.

### 5.2 `#GETTING_DATA` drift

**FAIL — MEDIUM severity.**

Design § 3.3 (`docs/architecture/2026-05-14-array-formulas-and-spills.md:95`) explicitly lists `#GETTING_DATA` as a valid error literal for array cells:

> `error literal` — `#NULL!`, `#DIV/0!`, `#VALUE!`, `#REF!`, `#NAME?`, `#NUM!`, `#N/A`, `#GETTING_DATA`, `#SPILL!`, `#CALC!` — matches IronCalc's `ArrayNode::Error` variant

However, `#GETTING_DATA` is **not** in `ErrorValue::ALL` (which has exactly 15 variants — 9 Excel-canonical, 5 QB-specific, 1 CIRC). The lexer would reject `{1, #GETTING_DATA}` with `LexError::InvalidErrorSigil("#GETTING_DATA")`. This is a direct contradiction between the design document and the implementation.

`#GETTING_DATA` is an Excel Online / async-data sigil (emitted while external data is loading). It was likely included in the design doc by reference to IronCalc's enum but never added to `ErrorValue`.

**Severity:** MEDIUM — the code is self-consistent (the lexer faithfully iterates `ErrorValue::ALL`); the bug is in the design doc claiming a sigil that doesn't exist in the type system. The 4.7.D parser and test corpus will never exercise `#GETTING_DATA` unless this is resolved either by (a) adding `ErrorValue::GettingData` or (b) striking `#GETTING_DATA` from § 3.3 with a note that it's deferred.

**File:** `docs/architecture/2026-05-14-array-formulas-and-spills.md:95`

## 6. `ErrorValue::ALL` exhaustiveness

**PASS (with LOW note).**

`ErrorValue::ALL` is a `const [ErrorValue; 15]`. The `sigil()` method uses an **exhaustive** `match self { ... }` over all variants — if a new variant is added to the enum without updating `sigil()`, Rust will fail to compile. This provides a compile-time guarantee that `sigil()` stays complete.

**The gap:** If a developer adds a new variant to `ErrorValue` AND updates `sigil()` (required by the compiler) but forgets to add the new variant to `ALL`, the lexer will silently fail to recognize the new sigil — no compile error, no test failure from the existing tests.

**Is there a runtime exhaustiveness test?** Not a direct one. `all_contains_fifteen_distinct_variants` (`error.rs:148`) only checks that `ALL` has 15 items and they're distinct — it doesn't compare against the enum variants. `from_str_roundtrips_all_variants` (`error.rs:213`) iterates `ALL` and checks round-trips, but again doesn't verify the enum is fully covered.

**How this manifests:** A new `ErrorValue::Foo` added to `sigil()` but not `ALL` would compile, pass all existing tests, and silently reject `#FOO!` as `InvalidErrorSigil` in the lexer.

**Severity:** LOW — this requires two simultaneous mistakes (add to enum, add to sigil, forget ALL). The compile-time check on `sigil()` catches the most dangerous case (variant with no sigil). The risk is low at current team size but is a maintenance hazard as ErrorValue grows.

**Suggested improvement:** Add a compile-time or test-time assertion that `ErrorValue::ALL.len()` equals the total number of enum variants. Without `strum`, this can be approximated by:
```rust
// In error.rs tests:
#[test]
fn all_is_exhaustive() {
    // If this count mismatches ALL.len(), a variant was added without updating ALL.
    // Update this count whenever a new ErrorValue variant is added.
    const EXPECTED_VARIANT_COUNT: usize = 15;
    assert_eq!(ErrorValue::ALL.len(), EXPECTED_VARIANT_COUNT,
        "ErrorValue::ALL is out of sync with the enum — update ALL when adding variants");
}
```
This is weaker than `strum::EnumIter` but cheaper to adopt. Alternatively, doc-comment `ALL` with "MUST be updated whenever a variant is added" and add `strum` as a future polish item.

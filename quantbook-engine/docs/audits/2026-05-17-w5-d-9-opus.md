# W5-D-9 Opus Audit: DEC2BIN / DEC2OCT / DEC2HEX / BIN2DEC / OCT2DEC / HEX2DEC + lexer extension
Date: 2026-05-17

## Summary

Independent post-implementation review of W5-D-9 (Phase 4.10 V1-260 closeout: base conversion). Six new scalar fns + one cross-cutting lexer change to unlock `letters-digits-letters` Excel function names.

**Math correctness:** Clean. Two's-complement encoding/decoding is exactly right for all three bases. Constants `BIN_MAX = 1024`, `BIN_HALF = 512`, `OCT_MAX = 2^30`, `OCT_HALF = 2^29`, `HEX_MAX = 2^40`, `HEX_HALF = 2^39` match IronCalc verbatim. Negative DEC2* always produces 10 digits, positive DEC2* zero-pads to `places`, places-too-small for positive returns `#NUM!`. Round-trip identities pinned in tests.

**Lexer extension:** Surgical. The new `letters + digits + letters` branch is correctly guarded (`!leading_dollar && !mid_dollar && !letters.is_empty() && next-char-is-letter`). Trailing-digit-only patterns like `LOG10`, `LOG10(2)`, `ATAN2(x,y)`, `A1048577`, and `A1:B5` are preserved by the `next-char-is-letter` peek. Full lex-of-known-callsites was traced manually — no regression.

**Gate status:** Workspace clean — `cargo fmt --all -- --check`, `cargo clippy --all-targets --all-features -- -D warnings`, `cargo test --workspace` all pass; 1679 ql-functions tests, 451 ql-formula-syntax tests, 63 region_mul2_e2e tests, 3 coverage tests, all green. Registry count bumped 243 → 249 correctly.

**Findings:** 0 HIGH, 2 MEDIUM, 4 LOW, plus several confirmed non-issues.

The implementation is correct and ready to commit. The MEDIUMs are coverage/parity gaps; the LOWs are mostly accounting/doc precision. Codex's separate audit (`2026-05-17-w5-d-9-codex.md`) converges on LOW-001 (test-count mismatch) and LOW-002 (lexer-level direct tests absent) — both reproduced here as M-1 (raised, see rationale).

## MEDIUM

### M-1 — Matrix test counts overstate actual scalar test coverage (also called LOW-001 by Codex)

- **Where:** `docs/compat/excel-matrix.md:315-320`; tests in `crates/ql-functions/src/scalar_fns.rs:7400-7782`.
- **Detail:** The matrix advertises DEC2BIN/OCT/HEX/BIN2DEC/OCT2DEC/HEX2DEC at 10/9/10/8/8/8 = 53 unit tests. Verified actual count via `grep -c '^    fn <prefix>_'`:
  - DEC2BIN: 10 (matches matrix)
  - DEC2OCT: 8 (matrix says 9 — off by 1)
  - DEC2HEX: 9 (matrix says 10 — off by 1)
  - BIN2DEC: 7 (matrix says 8 — off by 1)
  - OCT2DEC: 8 (matches matrix)
  - HEX2DEC: 8 (matches matrix)
  - **Total: 50 (not 53)**.

  The implementing-Opus prompt also claimed 53. So this discrepancy propagates from prompt → matrix → real artifact. Raising to MEDIUM because:
  - Matrix is a public-facing compatibility document; off-by-one numbers undermine its accuracy.
  - The under-counted fns (DEC2OCT, DEC2HEX, BIN2DEC) each lose 1 test of coverage that the documentation IMPLIES exists. Specifically BIN2DEC has no direct out-of-range-after-parse test (e.g. `BIN2DEC(11111111111) → #NUM!` testing the `(0..BIN_MAX).contains(&parsed)` branch). The behavior IS exercised by `bin2dec_non_binary_digit_is_num_error` (input "102") — but that's the parser-fail path, not the range-fail path. Different code path; should be covered.
- **Recommendation:** Either correct matrix counts to 10/8/9/7/8/8 = 50, OR add three tests: (a) `BIN2DEC(11111111111) → #NUM!` (pins parser-success-but-out-of-range path); (b) `DEC2OCT(64, 10) → "0000000100"` (pins places=10 boundary); (c) `DEC2HEX(-1, 10) → "FFFFFFFFFF"` (pins places ignored on negative + width=10). Adding the tests is the lower-risk option since the matrix would then become accurate AND coverage tightens.
- **Severity:** MEDIUM. Coverage gap is real (one untested codepath in BIN2DEC) and matrix is wrong as written. Pure-accounting LOW would understate.

### M-2 — Lexer-level direct unit tests for the W5-D-9 branch are absent

- **Where:** `crates/ql-formula-syntax/src/lexer.rs:619-665`. Test module at lines 1485-2050+ has NO direct test for `DEC2BIN`/`BIN2DEC`/etc.
- **Detail:** The cross-cutting lexer change is the largest regression-risk surface in W5-D-9. It is currently pinned ONLY indirectly:
  1. `e2e_base_conversion_through_dispatcher` (region_mul2_e2e.rs) shows the dispatch path works end-to-end.
  2. The existing `log10_lexes_as_cellref_with_text_for_parser` + `log10_followed_by_lparen_preserves_text_for_function_dispatch` confirm the no-trailing-letter path still emits CellRef.

  But there is no lexer-level test that:
  - Asserts `DEC2BIN` tokenizes to `Token::Ident("DEC2BIN")` (1 token).
  - Asserts `BIN2DEC` tokenizes to `Token::Ident("BIN2DEC")` (1 token).
  - Asserts the absolute-marker guards work: `$DEC2BIN` should NOT lex via the new branch (must fall through to CellRef-row-parse path and error). Similarly `DEC$2BIN`.
  - Asserts `LOG10A` (hypothetical trailing-letter on a known-function-named CellRef) now lexes as Ident, not CellRef + Ident.
  - Asserts mid-token underscore acceptance: `DEC2_BIN` lexes as a single Ident.
  - Asserts that `A1B` (formerly CellRef + Ident with a guaranteed parser-trailing-token error) now lexes as Ident("A1B") (changed behavior, intentional but unpinned).

  Without these, ANY future refactor of `lex_ident_or_ref` risks silently breaking the W5-D-9 path. The whole motivation for this branch was that "before W5-D-9, DEC2BIN was a `Trailing { count }` parser error". A test pinning that the NEW path emits `Token::Ident` is the natural regression guard.
- **Recommendation:** Add a `// W5-D-9 (lexer)` block in the lexer test module (near the existing `log10_*` tests, say around line 1530) with ~6 tests covering the cases above. This costs ~30 LOC and shores up the largest cross-cutting change in the batch.
- **Severity:** MEDIUM. Codex called this LOW; I'm raising because (a) the change is cross-cutting and affects ALL formulas (any letter-digit-letter token), (b) the only existing pins are downstream (e2e + indirect), and (c) the affected branch only has 6 lines of code yet alters tokenization for an unbounded class of strings.

## LOW

### L-1 — Documented `value_raw > 0.0` vs `value >= 0` semantic on negative-fractional inputs

- **Where:** `crates/ql-functions/src/scalar_fns.rs:3514, 3520` (our `finish_dec_conversion`) vs IronCalc `number_basis.rs:168, 207, 247` (`value_raw > 0.0`).
- **Detail:** Prompt flagged this as a potential parity drift. I traced every potentially-divergent input:
  - `value_raw ∈ (-1, 0]` (e.g., -0.5, -0.1, -0.0, +0.0): value = 0. Both IronCalc and us output the same string. IronCalc skips the places-overflow check (since `value_raw > 0.0` is false); we apply the check but it can never fire (places ≥ 1 ≥ len("0") = 1). Output is identical.
  - `value_raw > 0`: both apply the overflow check on the same `result`. Identical.
  - `value_raw ≤ -1`: both treat as negative, skip overflow check, output 10-digit two's-complement. Identical.

  **No observable divergence.** The semantic is documented differently but the output is bit-identical across all inputs. Calling this a non-issue if it were already documented; it isn't, so I'm flagging at LOW.
- **Recommendation:** Add a comment in `finish_dec_conversion` explaining "IronCalc uses `value_raw > 0.0`; we use `value >= 0` on the trunc'd i64. The two semantics diverge for `value_raw ∈ (-1, 0]` in classification, but `result = "0"` (1 char) and `places ≥ 1` guarantees identical output. Verified exhaustively in W5-D-9 audit."
- **Severity:** LOW. Output is correct; comment-clarity only.

### L-2 — Boolean inputs accepted; Microsoft & IronCalc canonically reject

- **Where:** `scalar_fns.rs` — all six fns use `coercion::to_number_strict` (DEC2*) or the Number+Text path (BIN2DEC). `to_number_strict` accepts Boolean as 1.0/0.0.
- **Detail:** Per Microsoft Support (verified via web search) and per IronCalc's `get_number_no_bools` (cast.rs:177-191), Booleans are NOT accepted by DEC2BIN/OCT/HEX or BIN2DEC. They return `#VALUE!`. Our impl returns:
  - `DEC2BIN(TRUE)` → `"1"` (we accept)
  - `DEC2BIN(FALSE)` → `"0"`
  - `BIN2DEC(TRUE)` → `1` (format("1") → from_str_radix("1", 2) = 1 → 1)
  - `HEX2DEC(TRUE)` / `OCT2DEC(TRUE)` → `#VALUE!` (these use the Text-only path, so they DO reject Boolean — consistent with canon)

  This is NOT a W5-D-9-specific bug — the entire BIT* family (W5-D-8) and 50+ other scalars in the codebase use `to_number_strict` and accept Booleans uniformly. The codebase has a long-standing policy. But the W5-D-9 doc comment says "verified vs IronCalc" — which is misleading for the Boolean axis.
- **Recommendation:** Either (a) document the Boolean-accept divergence in `scalar_fns.rs:3460` ("Microsoft canon divergence: Boolean → numeric via `to_number_strict`, NOT rejected as IronCalc does"), OR (b) introduce a project-wide `to_number_no_bools` helper for engineering-strict fns (separate, larger refactor). Option (a) is the W5-D-9-scoped fix.
- **Severity:** LOW. Codebase-wide convention; not a W5-D-9 regression. Doc-only correction needed.

### L-3 — HEX2DEC/OCT2DEC reject Number input; Excel/IronCalc accept

- **Where:** `scalar_fns.rs:3650-3654, 3683-3687`.
- **Detail:** Per Microsoft Support (verified): `HEX2DEC(10) = 16` (Excel auto-coerces Number→Text). IronCalc agrees (cast.rs:209-218 — `get_string` converts Number to text via `format!("{f}")`). Our impl:
  ```rust
  let text = match &args[0] {
      Value::Text(s) => s.clone(),
      Value::Error(e) => return Value::Error(*e),
      _ => return Value::Error(ErrorValue::Value),
  };
  ```
  REJECTS Number with `#VALUE!`. So `HEX2DEC(10)` is `#VALUE!` in our impl vs `16` in Excel/IronCalc.

  The W5-D-9 doc says `Input MUST be text (per Excel canon)`. That's **wrong** — Excel canon is "argument type is Text, but Number is auto-coerced". Same applies to OCT2DEC.

  Note BIN2DEC takes a Number (correct per canon); HEX2DEC/OCT2DEC take Text-but-coerce-from-Number. The asymmetry is intentional in Excel.

  This is a coverage-test-pinned divergence (`hex2dec_number_arg_is_value_error` and `oct2dec_number_arg_is_value_error` explicitly test our rejection behavior). So it's a deliberate decision — but the docs/comments don't acknowledge it accurately.

  Same applies to Boolean inputs to HEX2DEC/OCT2DEC: IronCalc converts to "TRUE"/"FALSE" text → parse-fail → `#NUM!`. Ours returns `#VALUE!` (Boolean is not Text → match-fall-through). Lesser concern; same flavor.

  Same applies to Blank: IronCalc treats EmptyCell as "" text → parse-fail → `#NUM!`. Ours returns `#VALUE!` (Blank is not Text → match-fall-through).
- **Recommendation:** Decide policy. Two options:
  (a) **Match canon**: change to `coercion::to_text_for_arg` (which handles Number/Bool/Blank/Text/Error uniformly). This would auto-fix Number → coerce to "10" → parse as hex/octal → 16/8 respectively. Boolean → "TRUE"/"FALSE" → parse fails → `#NUM!`. Blank → "" → parse fails → `#NUM!`. ALL three align with IronCalc/Excel. Trade-off: changes the `_number_arg_is_value_error` tests.
  (b) **Document divergence**: leave behavior, but rewrite the docstring from "per Excel canon" to "**deliberate divergence from Excel/IronCalc**: takes Text-only; Number/Boolean/Blank → `#VALUE!`. Rationale: project-wide tighter-than-Excel arg-typing for engineering fns."

  Either is defensible. (a) matches the broader user-facing canon claim and is closer to "what real workbooks do"; (b) keeps the current tests intact. Plan author's call.
- **Severity:** LOW. The divergence is pinned by tests, so it's deliberate. Doc/policy needs alignment.

### L-4 — BIN2DEC has no length-cap; relies on numeric range to reject 11+ char binary

- **Where:** `scalar_fns.rs:3627`: `if !(0..BIN_MAX).contains(&parsed) { return #NUM!; }`.
- **Detail:** BIN2DEC, per Microsoft canon, has the constraint: "Number cannot contain more than 10 characters (10 bits)". Our impl doesn't explicitly enforce length; it indirectly enforces via the range check `parsed < 1024`. For binary inputs:
  - 10-char input "1111111111" → parsed = 1023 → in range → result = -1 (sign extend). OK.
  - 11-char input "11111111111" → parsed = 2047 → not in [0, 1024) → `#NUM!`. OK by coincidence.
  - But what about "10000000000" (11-char with leading 1, then 10 zeros)? parsed = 1024 → not in [0, 1024) → `#NUM!`. OK.

  IronCalc has the same range-based-only check (line 24 in number_basis.rs). So this is parity. But neither has a dedicated length-cap test. If someone later refactors to extend the binary range, the unstated invariant could be broken. Adding the explicit test `BIN2DEC(11111111111) → #NUM!` (already mentioned in M-1) would pin this.
- **Recommendation:** Combine with M-1's BIN2DEC out-of-range test.
- **Severity:** LOW. Behavior is correct; missing pin.

## Confirmed Non-Issues

These were prompt-flagged "special concerns" — investigated and confirmed clean:

1. **Regression risk on `LOG10`, `ATAN2`, `LOG2`**: traced lexer logic. The W5-D-9 branch's `chars.peek().is_some_and(is_ascii_alphabetic)` check ALSO requires a trailing alphabetic AFTER the digits. For `LOG10` followed by EOF / `(` / `+` / `:` / etc., peek is not alphabetic, so the new branch is skipped, falling through to the established CellRef path. Verified by manual trace + existing tests `log10_lexes_as_cellref_with_text_for_parser` and `log10_followed_by_lparen_preserves_text_for_function_dispatch` still pass (451 lexer tests green).

2. **Regression risk on `$DEC2BIN`**: `leading_dollar` is `true`, so the W5-D-9 branch's guard `!leading_dollar` fails. Falls through to the row-parse path; tries to parse "2BIN" as digits, fails on 'B'. Lexer returns... actually let me re-verify. Looking at the flow: row_digits = "2", then `2BIN` continues — row_digits stops at "B" (non-digit). row_1based = 2. CellRef constructed with col=DEC, row=1. Then "BIN" is the next token (Ident). So `$DEC2BIN` → `CellRef("$DEC2") + Ident("BIN")`. Parser sees CellRef + Ident with no operator → trailing-tokens error. Same as pre-W5-D-9. Not a regression.

3. **`mid_dollar` guard correctness**: `DEC$2BIN` — letters="DEC", mid_dollar=true. W5-D-9 branch guarded out. Row parsing on "2BIN" → same as case 2. CellRef + Ident → parser error. Not a regression.

4. **Underscore in identifiers**: Excel function name canon has no underscores (per IronCalc and Microsoft canon for these six fns). The new branch accepts `_` in the trailing letter run but there's no Excel-known function name affected. The W5-D-2 `.DIGIT+LETTER` branch dropped underscore acceptance (W5-D-2.1 closure) for the SAME reason — narrowing accepted grammar to canon. The W5-D-9 trailing-letter run could be similarly narrowed (drop the `|| c == '_'`) for symmetry, but the binder/registry rejects unknown idents either way. Cosmetic-only.

5. **Cell-ref still-valid corner cases**: `A1B` was previously CellRef("A1") + Ident("B") (parser error). NOW lexes as Ident("A1B") (binder → `#NAME?`). Both rejected, different error class. No EXISTING test/code depended on the old behavior (verified via grep across all crates). No regression.

6. **10-digit two's-complement canon constants**: Verified `BIN_MAX = 1024 = 2^10`, `BIN_HALF = 512 = 2^9`, `OCT_MAX = 1073741824 = 2^30`, `OCT_HALF = 536870912 = 2^29`, `HEX_MAX = 1099511627776 = 2^40`, `HEX_HALF = 549755813888 = 2^39`. Cross-checked against IronCalc constants and the canonical Excel doc (10 digits in target base × log2(base) bits each → 2^(10·log2(base)) wrap point).

7. **Negative DEC2* encoding**: `value + radix_max` arithmetic stays well within i64 mantissa for ALL in-range negative inputs. Verified: `-HEX_HALF + HEX_MAX = -2^39 + 2^40 = 2^39 = 549_755_813_888 < i64::MAX`. Casts are exact.

8. **Positive DEC2* places behavior**: Verified `if value >= 0 && p < raw.len() as i32 { #NUM! }`. Correctly disables for negative (always 10 chars). Tested directly: `dec2bin([n(-1), n(3)]) == t("1111111111")`.

9. **BIN2DEC numeric input**: `format!("{raw}")` does NOT produce scientific notation for any reasonable input. Verified probe: `1e15` → `"1000000000000000"` (16 chars), `1e20` → `"100000000000000000000"` (21 chars). For all such inputs, either `from_str_radix` rejects on non-binary digits, or the parsed result violates the range check → `#NUM!`. No silent acceptance of invalid input.

10. **HEX2DEC / OCT2DEC text input**: `text.len() > 10` rejects byte-length not char-length. ASCII hex/octal digits are 1-byte, so practical behavior matches. Non-ASCII UTF-8 input → byte-length might be ≥ char-count; could pass length check then fail `from_str_radix` → `#NUM!`. Safe in both directions.

11. **Round-trip identities**: `bin2dec(dec2bin(x))` test loops over `[0, 1, 5, 42, 255, 511]`. Same for hex/oct round-trips. All pass. **However**, none of the round-trip tests cover NEGATIVE x. Suggest adding e.g. `for x in [-1, -42, -512]` and verifying. The negative-encoded paths are tested individually but not round-tripped. Minor coverage suggestion; not a finding because the negative encoding has its own dedicated tests.

12. **f64 → i64 cast precision near 2^39**: i64 cast of f64 values ≤ 2^53 is exact. 2^39 ≪ 2^53, so HEX_HALF / HEX_MAX boundaries are bit-exact. No cast precision concern.

13. **f64 → string formatting for BIN2DEC for values > 1e15**: see #9 — no scientific notation.

14. **`Value::Text` clone semantics**: `Value::Text(Arc<str>)`. `Arc<str>::clone` is a refcount bump; no deep copy. `s.clone()` in HEX2DEC/OCT2DEC is O(1). Confirmed via Value type definition (ql-types/src/value.rs:40).

15. **Test coverage shape**: per-fn 7-10 tests covering anchor, boundary, negative, places, out-of-range, type rejection, error-prop, arity, round-trip. Matches the documented shape. The 1-off discrepancies (M-1) are accounting; the per-fn coverage shape itself is balanced.

16. **Coverage entries match impl**: spot-checked all 6 entries in `coverage.rs`. Texts match implemented behavior. The "Strict 1-arg" claim for *2DEC matches the code's `args.len() != 1`. The "places in [1,10]" claim for DEC2* matches `parse_places_arg`'s `(1..=10).contains(&p)` check. Cross-cutting facts (Microsoft canon, divergences, IronCalc parity) accurately described.

17. **Matrix rows accurate**: row content (semantics columns) accurate. Only the test counts are off (see M-1). Status flips ❌ → ✅ correctly. Phase tags `4.10 V1-260 closeout (W5-D-9)` consistent with the W5-D-8 / Wave 3 row patterns immediately above.

18. **Count bump 243 → 249 verified**: `assert_eq!(r.len(), 249)` matches the 6 new registrations in `default_registry`. Test `default_registry_has_expected_count` passes.

19. **Argument-order divergence in DEC2BIN**: `DEC2BIN(out-of-range, invalid-places)` — IronCalc checks places first, ours checks value first. Both end up returning `#NUM!`. NO observable divergence in the error class. Verified by case-walk.

20. **Wrap-overflow risk (W5-D-8 trend)**: W5-D-8 had a wrap-overflow HIGH around `wrapping_shl`/`wrapping_shr`. W5-D-9 has NO equivalent pattern — it uses f64 → trunc → i64 → range-check → adjust → format. The adjustment math (`value + radix_max`) stays within ±2^40 = 2^41 magnitude, well within i64. No wrap-overflow surface.

21. **NaN/Inf path**: `to_number_strict` returns `#NUM!` for NaN/Inf via `sanitize_f64` (verified at ql-types/src/coercion.rs:31-37). Our DEC2* and BIN2DEC propagate this `#NUM!`. HEX2DEC/OCT2DEC don't see Number inputs at all (rejected with `#VALUE!` upstream), so NaN/Inf can only enter via Number cells, which propagate as `#NUM!` from the upstream coercion. Safe.

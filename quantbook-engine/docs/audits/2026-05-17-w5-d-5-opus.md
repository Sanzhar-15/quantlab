## LOW

### LOW-O-1 (test-coverage gap) — GAMMA.INV at `p=1.0` upper boundary not pinned

File: `crates/ql-functions/src/distribution_fns.rs:5006-5019`

Tests pin `p > 1` (`gamma_inv_p_above_one_is_num_error`) and `p < 0` (`gamma_inv_p_negative_is_num_error`), but not `p == 1.0` exactly. The domain comment at line 1508 says `0 <= p <= 1` INCLUSIVE matches IronCalc; with `p = 1`, `inverse_cdf(1.0)` returns `+Inf` for Gamma, which fails the `!x.is_finite()` guard at line 1513 and surfaces as `#NUM!`. This boundary deserves a pinned test since the canon claims `p = 1` is INCLUSIVE but the implementation deliverable for `p = 1` is `#NUM!` (not a numerical answer) — exactly the kind of corner where users expect documented inclusivity to mean "returns a value".

The matrix entry (line 124) says `0 ≤ p ≤ 1 INCLUSIVE` which is technically right at the domain-check level but misleading at the result level. Either pin a test asserting `gamma_inv(p=1, α=1, β=1) = #NUM!` or update the matrix entry to `0 ≤ p < 1 effectively (p=1 → #NUM! via Inf-guard)`. Same shape applies to GAMMA.INV at `p = 0` with `α = 0.001` (well-defined → 0) vs `p = 0` with `α >> 1` (statrs returns 0; documented inclusive lower).

### LOW-O-2 (test-coverage gap) — CONFIDENCE.NORM vs CONFIDENCE.T error-class divergence for negative-fractional size not pinned

File: `crates/ql-functions/src/distribution_fns.rs` (no tests)

For `size = -0.5`:
- CONFIDENCE.NORM: `.floor()` → -1 → `< 1` → `#NUM!`.
- CONFIDENCE.T: `.trunc()` → 0 → `< 2` → `#DIV/0!`.

This is the only input regime where the `.floor()` vs `.trunc()` divergence has user-observable consequences (positive-fractional input rounds identically). Module docstring at line 243-245 claims "the divergence is invisible for in-domain inputs" — true, but for **out-of-domain negative fractional**, error classes differ. Worth one belt-and-suspenders test pinning both fns at `size = -0.5` to lock the divergence. Currently no test catches a regression that flipped both to `.floor()` or both to `.trunc()` (the same-error-class case for positive-fractional inputs would still pass).

### LOW-O-3 (defensive guard) — BETA.INV missing `t < 0.0` rejection (asymmetric with GAMMA.INV)

File: `crates/ql-functions/src/distribution_fns.rs:1676-1680`

```rust
let t = dist.inverse_cdf(p);
if !t.is_finite() {
    return Value::Error(ErrorValue::Num);
}
Value::number(a + t * (b - a))
```

GAMMA.INV guards `!x.is_finite() || x < 0.0` (line 1513) defensively against statrs Newton-Raphson returning slightly-negative values. BETA.INV's guard at 1677 only checks finiteness, not `t < 0.0` or `t > 1.0`. For Beta(α, β) on [0, 1], inverse_cdf should mathematically return `t ∈ [0, 1]`, but Newton-Raphson can drift slightly outside on extreme inputs.

This matches IronCalc beta.rs:203 which has the same gap, so it's parity-with-source, but the asymmetry with GAMMA.INV (which DOES have the negative guard) is internally inconsistent. Low priority — no test demonstrates a real failure, and the divergence may be intentional since Beta's bounded support makes Newton-Raphson behavior more predictable than Gamma's unbounded right tail.

### LOW-O-6 (anchor-precision note) — CONFIDENCE.T anchor uses statrs-internal value, not true math

File: `crates/ql-functions/src/distribution_fns.rs:5627-5641`

The anchor `0.715_356_905_970_664_3` is statrs's Newton-Raphson output for `t(0.975, df=9) / √10`. True math gives ≈ `0.71531056`. The test comment correctly documents this divergence and the test name `_statrs_self_consistent` reflects the W5-D-3 self-consistency pattern, so this is intentional. The LOW is only a flag: if statrs ever revises its inverse_cdf algorithm (e.g., higher-order Newton or analytic improvement), this anchor will silently shift and the test will fail. There's no test currently asserting "statrs's t(0.975, df=9) ≈ 2.262" as a checkpoint — only the composite `t·σ/√n` value is pinned. A second test pinning just `students_t_with(9.0).inverse_cdf(0.975)` (or referencing the existing T.INV test for this value) would localize a future statrs algorithm change to its source. Minor — current pattern is consistent with W5-D-3.

## Confirmed Non-Issues

The following were investigated and confirmed correct or intentional:

1. **Shape-scale → shape-rate conversion for Gamma**: `rate = 1.0 / scale` matches IronCalc exactly. Pre-check `scale > 0` rules out the `Inf` rate case. Verified for α=1, β=1: gamma reduces to exp(rate=1), CDF(1) = 1 - e⁻¹, PDF(0) = 1. Both anchor-tested.

2. **Beta variadic 4-6 / 3-5 arity ranges**: BETA.DIST `if !(4..=6).contains(&args.len())` (line 1573). BETA.INV `if !(3..=5).contains(&args.len())` (line 1635). Match IronCalc exactly. Arity-too-low + arity-too-high both tested for both fns.

3. **Beta optional bounds transform**: `t = (x - a) / width`, `pdf / width` (Jacobian) at lines 1614-1622. Matches IronCalc beta.rs:96-97/114. Verified anchor: BETA.DIST(5,1,1,FALSE,0,10) = 0.1 (U(0,10) PDF = 1/10). BETA.DIST(5,1,1,TRUE,0,10) = 0.5 (CDF at midpoint).

4. **BETA.INV bound transform**: `a + t * (b - a)` (line 1680). Matches IronCalc beta.rs:212. Verified: BETA.INV(0.7,1,1,0,10) = 0 + 0.7·10 = 7.

5. **A == B rejected for BETA.DIST; B <= A rejected for BETA.INV**: BETA.DIST line 1611 uses `b == a` matching IronCalc (b < a indirectly rejected via x-bounds since x can't simultaneously be ≥a and ≤b when a > b). BETA.INV line 1672 uses `b <= a` matching IronCalc beta.rs:183 (`<=` not `<`).

6. **BETA.INV p domain strict both ends**: line 1669 `p <= 0.0 || p >= 1.0`. Matches IronCalc beta.rs:175 (`p <= 0.0 || p >= 1.0`). IronCalc has a confusing comment at beta.rs:174 ("NB: p==0 or p==1 are actually valid inputs") that does NOT match its impl; W5-D-5 follows the impl (strict). Docstring at line 1631 correctly says "STRICT both" without misleading commentary. **No discrepancy** between code, IronCalc impl, and our docs.

7. **CONFIDENCE.NORM `.floor()`**: line 1712 matches IronCalc normal.rs:216 exactly.

8. **CONFIDENCE.T `.trunc()`**: line 1749 matches IronCalc normal.rs:277 exactly. Divergence from NORM's floor is deliberate per IronCalc.

9. **CONFIDENCE.T `#DIV/0!` for size < 2**: line 1756 returns `Value::Error(ErrorValue::DivZero)`. Matches IronCalc normal.rs:293 (`Error::DIV`). First and only `#DIV/0!`-returning fn in `distribution_fns`. Documented at module level (line 246-247) and inline (line 1733-1734). Pinned by unit test `confidence_t_size_less_than_two_is_div_zero` (5644) AND e2e test `confidence_t_size_less_than_two_through_dispatcher_returns_div_zero` (904).

## Findings

### HIGH-1: PlanCache key omits cell anchor for `@<range>` formulas

**Files (at audit-scope HEAD W5-149):**
- `crates/ql-exec/src/plan_cache.rs:60-65` (`PlanCacheKey` definition)
- `crates/ql-exec/src/workbook_runtime.rs:592-596` (`set_formula` cache key)
- `crates/ql-exec/src/workbook_runtime.rs:991-996` (reader re-bind path)
- `crates/ql-exec/src/workbook_runtime.rs:3156-3162` (spill-reader path)
- `crates/ql-exec/src/workbook_runtime.rs:3304-3308` (`recompute_all` path)
- `crates/ql-exec/src/plan.rs:893-905, 974-1005, 1014-1029, 1031-1050`
  (the bind sites that bake `anchor.row`/`anchor.col` into the plan)

**Issue:** W5-144's `bind_implicit_intersection` narrows `@<range>`,
`@A:A`, `@1:1`, and `@A1:A10` AT BIND TIME using `site.cell`, producing
an `ExprPlan::CellRef { row: anchor.row, col: ..., ... }` that
hard-codes the formula cell's own row/col. The `PlanCacheKey` at the
audit scope is `(text: Arc<str>, sheet: SheetId, name_gen: u64)` —
NO cell coordinates. Canonical text for `@A:A` / `@A1:A10` etc. is
identical across cells, so the second `set_formula` with the same text
at a different cell HITS the cache and reads the FIRST call's narrowed
coord.

Concrete repro that the W5-150 commit ships as a regression test
(`plan_cache_at_range_collision_across_cells_regression`):

```rust
wb.put((0, 3, 0), Number(11.0));
wb.put((0, 5, 0), Number(99.0));
let mut rt = WorkbookRuntime::new(&mut wb, &reg);
let v1 = rt.set_formula(0, 3, 1, "@A:A").unwrap(); // row 3 → A4 = 11
let v2 = rt.set_formula(0, 5, 1, "@A:A").unwrap(); // pre-fix: 11 (WRONG)
```

The same canonical text `@A:A` produces identical cache keys, so v2 hits
the cached plan from v1 (which is hard-coded to row 3). The bound plan
is built once with `BindSite::at_cell(0,3,1)` and re-used for all cells.

Note: this collision does NOT apply to `Sales[@Col]` / `@Sales[Col]`
StructuredRef because the structured-ref path resolves via eval-time
`is_this_row` flag (eval consults `WorkbookEnv::with_formula_cell`).
Only `@<range>` and `@<bare-col-or-row>` collapse to `ExprPlan::CellRef`
at bind time. R1C1 relative refs canonicalize to a cell-specific A1
form (e.g. `R[-1]C` at (5,5) → `E5`), so their canonical text differs
across cells and the cache key naturally separates them.

**Fix:** `PlanCacheKey` needs a cell-anchor slot conditionally populated
when canonical text contains `@`. W5-150 ships this fix:
`cell_anchor: Option<(RowId, ColId)>` set to `Some((row, col))` when
`canonical_text.contains('@')`, else `None`. Non-`@` formulas (the
overwhelming majority) preserve the cell-independent cache-sharing fast
path. False positives (`@` inside string literals like `"@foo"` or in
the printed-form of `Sales[@Col]` which round-trips through
`StructuredRef.spec`'s `@[Col]` emission) trigger extra cache splits
without correctness loss.

I verified the W5-150 fix by `git show ab33dcf6841 --
crates/ql-exec/src/plan_cache.rs crates/ql-exec/src/workbook_runtime.rs`:
all 4 call sites updated, regression test landed and asserted to pass.

### MEDIUM-1: `@Sales[#Headers,Qty]` and other non-column StructuredRefs incorrectly forced into `is_this_row` narrowing

**File:** `crates/ql-exec/src/plan.rs:901-920`.

**Issue:** The W5-144 binder unconditionally sets `is_this_row: true`
on any `Expr::StructuredRef` wrapped by `@`. The design § 3.3 rule 9
specifically describes the column case: `=@Sales[Qty]` narrows the
column to the formula's row. But the patch applies to ALL StructuredRef
shapes:

- `@Sales[[#Headers], [Qty]]` resolves to a single header cell at
  `(header_row, qty_col)`. Pre-patch: `is_this_row: false` → eval
  reads the single header cell (rule 5 idempotent).
  Post-patch (W5-144): `is_this_row: true` → `narrow_structured_ref`
  checks `cell.row == header_row`. Formula in any other row → `#VALUE!`.
- `@Sales[#All]` resolves to the full 2-D footprint. Per design rule 4,
  should be `#VALUE!`. Post-patch: `is_this_row: true` narrows to
  `(cell.row, cell.row, start_col..end_col)` — a multi-col range →
  `#CALC!` (multi-cell in scalar context). Wrong error class.

The intent of the patch is "if `@` wraps a column-data ref, narrow to
formula's row". The implementation doesn't discriminate by what shape
the underlying range is.

**Fix:** Only set `is_this_row: true` if the resolved range is a single
column (`resolved.start_col == resolved.end_col`) OR the underlying
spec is `TableSpecSubtree::BareColumn(_)`. Otherwise leave
`is_this_row` at whatever `resolve_structured_ref` returned (which
already handles the special-form cases correctly).

No test exercises these non-column @-wrapped structured refs today, so
the bug is latent. Recommended: add 2 tests pinning `@Sales[#Headers]`
(returns header value at formula row OR #VALUE!) and `@Sales[#All]`
(returns #VALUE! per rule 4) per IronCalc's reference behavior.

### MEDIUM-2: `Op::SetReferenceMode` unknown wire values reject loudly only via JSON parse error, no clean `UnknownReferenceMode` variant

**File:** `crates/ql-oplog/src/op.rs:268-272`, parallel to
`crates/ql-oplog/src/op.rs:297-322` (`LocaleWire` with `Unknown(_)`).

**Issue:** `LocaleWire` has a custom Deserialize that captures unknown
strings into `Unknown(s)`, surfaced via
`ReplayError::UnknownLocale { index, found }`. `ReferenceModeWire`
uses the derive-only path with only `A1` and `R1C1` variants — an
unknown string (e.g. a future `Op::SetReferenceMode { mode: "R1C0" }`
from a forward-compat op-log file) surfaces as a `serde_json::Error`
inside `OpLogError::Deserialize`, NOT as a clean
`ReplayError::UnknownReferenceMode { index, found }`.

The asymmetry breaks the forward-compat closure pattern that
`LocaleWire` carefully implements. Future engines adding a `Mixed`
or `Personal` mode would either (a) break op-log forward-compat or
(b) need to retroactively add the `Unknown` arm.

**Fix:** Add `Unknown(String)` to `ReferenceModeWire`; custom
Deserialize captures unknown to that variant; add
`ReplayError::UnknownReferenceMode { index, found }`; replay arm
matches and surfaces. Mirror the `LocaleWire` pattern exactly.
Probably 30 lines including a 1-test pin.

This is design-doc-aligned: the design § 4.9.J commit row says
"Unknown wire values (forward-compat) → `ReplayError::UnknownReferenceMode`
per design § 4.9.J", but the code derives `Deserialize` with a
plain enum (no `#[serde(other)]` or `Unknown(_)`), so the intended
behavior isn't actually implemented.

### LOW-2: Printer `axis_spec_to_absolute_coord` permits out-of-grid resolved coords (defense-in-depth gap)

**File:** `crates/ql-formula-syntax/src/printer.rs:268-291`.

**Issue:** The function bounds-checks against `u32::MAX` (`!(0..=(u32::MAX as i64)).contains(&resolved)`)
but NOT against `MAX_ROW` / `MAX_COLUMN`. A synthetically constructed
AST `Expr::R1C1Ref { col_axis: AxisSpec::Rel(16385), ... }` at anchor
col 0 would resolve to col 16385 → emit `column_index_to_letters(16385)`
→ `"XFO"` (beyond Excel's `XFD` max). The result is a non-round-trippable
string the lexer would reject.

Production paths (`lex_with` → `parse` → `print_with`) can't reach this
since the lexer caps `Abs(n)` at `MAX_*+1` and the binder caps
`anchor+offset` at `MAX_*`. The printer's looser bound is
defense-in-depth gap only.

**Fix:** Tighten the bound to `MAX_ROW + 1` / `MAX_COLUMN + 1` (mirroring
`resolve_r1c1_axis` in `plan.rs:1083-1116`), and surface
`PrintError::R1C1AxisOutOfRange` with a more specific context message.
Plus 2 unit tests pinning the boundary. Marked LOW because no production
path constructs such an AST.

### LOW-3: No test pin for per-axis-independent R1C1 range relativity

**Files:**
- `crates/ql-formula-syntax/src/parser.rs:794-825` (build_range R1C1 arm)
- Parser tests at `crates/ql-formula-syntax/src/parser.rs:3006-3028` only
  pin the REJECTION cases (mixed-relativity row, mixed-relativity col,
  mixed both).

**Issue:** Design § 3.1 specifies that relativity is checked PER AXIS —
`R1C[1]:R10C[5]` (both rows absolute, both cols relative, NO axis
mixed within itself) MUST be accepted. The `axis_relativity_matches`
helper (parser.rs:838-843) implements this correctly. But the test
corpus only has the rejection side; there's no test that
`R1C[1]:R10C[5]` / `R[1]C1:R[5]C10` actually parse cleanly. A future
refactor that accidentally tightens to "either all-relative or
all-absolute" wouldn't fail any test.

**Fix:** Add 2 tests asserting the cross-axis pattern parses. Pure
test coverage; no production fix needed.

### LOW-4: Lexer's MalformedR1C1 fragment-string is silently truncated by `mem::take` in axis parser error paths

**Files:**
- `crates/ql-formula-syntax/src/lexer.rs:960, 964, 968`
  (`parse_r1c1_axis` error returns).

**Issue:** Each error path in `parse_r1c1_axis` does
`std::mem::take(fragment)`, which CONSUMES `fragment` — but the function
is called from `try_lex_r1c1_ref` which also accumulates into the same
`fragment` String. After the first error, `fragment` is empty for any
subsequent error message. If the row-axis parser fails, the fragment
contains the consumed row-portion characters; but if the col-axis
parser fails, the fragment contains row + `C` + the partial col body —
useful diagnostics. Calling `mem::take` is safe HERE because the
function returns immediately afterward, but the pattern is fragile
against future refactor (e.g. if `parse_r1c1_axis` ever propagated an
error AFTER taking the fragment for some other purpose).

Cosmetic; doesn't affect correctness in v1.

**Fix:** Use `fragment.clone()` instead of `mem::take(fragment)` —
costs one allocation per error path (cold), gains future-refactor
safety.

  that the production path (`set_formula` → canonicalize via `print_with(..,
  A1, EnUs, Some(site))?` → bind) always lowers R1C1 → A1 BEFORE the
  bound plan reaches calcgraph fingerprint/stripe registration. The
  `unreachable!()` panics are correctly unreachable in production.

- **Sheet-prefix + `@` interaction (W5-143):** `Sheet1!@A1` and
  `@Sheet1!A1` parse to identical ASTs (`apply_sheet_to_term` at
  `parser.rs:983-986` recurses INTO `ImplicitIntersection`). Printer
  emits canonical `@Sheet1!A1`. Round-trip test pinned at
  `printer.rs:2011-2020`.

- **Mixed-relativity R1C1 range rejection (W5-139):** per-axis check
  at `parser.rs:805-810` correctly rejects axis-internal mixed
  relativity while accepting cross-axis differences. Test corpus
  pins the rejection cases (parser.rs:3006-3028). LOW-3 above notes
  the missing acceptance-pin coverage.

- **AxisSpec::Rel(i32::MIN/MAX) arithmetic safety
  (`plan.rs:1083-1116`):** the i64 sum can never overflow given
  `anchor: u32 ≤ MAX_ROW` (~1M) and `offset: i32` (~2B); the
  bounds check catches negative/overflow correctly. Matches the
  self-audit's LOW-3 finding.

- **Two-phase qbook load + forward-compat field rejection
  (W5-145):** `SchemaVersionProbe` works as designed.
  `ForwardCompatFieldOnOldVersion` correctly fires when a v6 file
  carries v7 fields (`qbook_format.rs:1645-1658`).

- **Locale `Unknown` propagation (W5-145 + W5-146):** load path
  surfaces `QbookError::UnknownLocale`; op-log replay path surfaces
  `ReplayError::UnknownLocale`. Save-side `from_runtime` never produces
  `Unknown`. (See MEDIUM-2 for the missing parallel
  `ReferenceModeWire::Unknown`.)

- **Locale × scientific-notation printing:** Rust's `f64` Display
  uses scientific notation only for very large / very small
  magnitudes, in which case there's no `.` to swap. Within the
  decimal-emitting magnitudes, the swap is correct. Test
  `print_with_de_locale_small_fraction` at `printer.rs:1960-1964`
  pins one end; `print_with_de_locale_scientific_integer` pins the
  integer-valued large case. LOW-2 in the self-audit notes the
  missing scientific-with-fractional-mantissa test pin.

- **Op-log SetReferenceMode + SetLocale replay (W5-146):** verified
  at `replay.rs:551-564` and tested at `replay.rs:1763-1809`.
  Idempotent — `set_reference_mode` / `set_locale` early-return
  when value matches (workbook_runtime.rs:1741-1751, 1763-1774),
  so the log stays compact.

- **Canonical text invariance under mode/locale change (W5-148):**
  `reference_mode_change_leaves_stored_formula_text_canonical` and
  `locale_change_leaves_stored_formula_text_canonical` pin the
  design § 4.4 contract. Mode/locale changes do NOT trigger
  formula re-canonicalization or cache invalidation — and they
  don't NEED to, since the canonical text is mode/locale-invariant.

- **30-cell coverage matrix (W5-149):** every (mode × locale ×
  @-presence) triple asserts the design § 4.4 canon (canonical text
  is mode/locale-invariant, `@` preserved verbatim). 30 cells = 2 modes ×
  3 locales × 5 @-presence classes. Sanity tests pin the axis counts
  so a future cell-add trips the axis test until the doc is updated.

## Verdict

**SHIP-READY** (post-W5-150 fix).

The HIGH-1 finding (PlanCache × `@<range>` cell collision) is a real
ship blocker at the audit scope HEAD `72f39a84446`, but the W5-150
commit (currently at the working-tree HEAD `ab33dcf6841`) shipped the
fix + regression test. I verified the fix touches all 4 cache-key
construction sites and the regression test asserts the previously-broken
case.

MEDIUM-1 (non-column @-wrapped StructuredRef forced into `is_this_row`)
is a latent correctness gap that no current test exercises. Recommended
to fix before declaring Phase 4.9 fully shipped, but it's NOT a ship
blocker because no test breaks and the existing `Sales[@Col]` pattern
(the primary user-visible path) works correctly.

MEDIUM-2 (`ReferenceModeWire::Unknown` missing) is a design-doc-promise
gap — the design § 4.9.J table promises forward-compat parity with
`LocaleWire`, but the code doesn't deliver it. Not a ship blocker for
v1 (the wire enum is only 2 variants, unlikely to expand), but the
design-doc divergence should be reconciled — either implement the
`Unknown` variant or update the design row.

The 4 LOW findings are polish items for follow-up commits.

End-state assessment: the R1C1 + locales + `@` implicit-intersection
trifecta is complete across the full stack (lex/parse/bind/eval/print/
persist/op-log/canonical-storage). Test coverage is broad — 169+ new
tests including the 30-cell coverage matrix and 12 round-trip property
tests. The cache-collision bug found by the self-audit + this audit
was the only HIGH and is fixed.

**SHIP-READY**

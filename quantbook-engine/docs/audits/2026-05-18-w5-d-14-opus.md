# W5-D-14 XLSX Round-Trip Spine — Adversarial Opus Audit

Branch: `feat/quantbook-engine`
Head at audit: `13b64488dc0` (W5-D-14e — umya exporter, NewWorkbook mode)
Auditor: separate Opus session (per `quantbook_engine_audit_discipline.md`)
Date: 2026-05-18

## Verdict

The W5-D-14e commit message claims **"Phase 4.11 round-trip spine: CLOSED"** and the
file header doc claims **"Cells + formula text + cached values round-trip"**.

**That claim is false.** Compile-probe evidence:

1. **Every formula is silently dropped on export.** `umya::Cell::set_value_*`
   internally calls `remove_formula()`. The exporter calls `set_formula` then
   immediately `apply_value_to_cell` (which calls `set_value_number/_bool/_string`),
   which wipes the formula it just set. Round-trip of `example.xlsx` shows
   `formulas_before=36, formulas_after=0`.
2. **The `date1904` workbook property is silently lost on export.** The exporter
   never writes a `<workbookPr date1904="1"/>` element. A Quantbook workbook
   created with `Workbook::set_date_system(Excel1904)` round-trips as `Excel1900`.
3. **Tables are silently dropped on export.** Round-trip of `example.xlsx` shows
   `tables_before=1, tables_after=0`. Exporter writes no `xl/tables/*.xml`,
   no sheet rels, no table xml.
4. **All `Value::Error(_)` values become `Value::Text("#…")` on round-trip.**
   The exporter writes the sigil as a string via `set_value_string`. On reimport,
   calamine returns `Data::String("#DIV/0!")` (not `Data::Error`), so the engine
   gets `Value::Text`. This is asymmetric and indistinguishable from a
   user-typed `'#DIV/0!` literal.
5. **A real-world fixture imports break hard.** `libreoffice_888_example.xlsx`
   uses `<numFmt numFmtId="164" formatCode="General"/>` (LibreOffice's idiom);
   our `register_at` rejects this with `StringCollision`. Hard failure for a
   common Excel-source workbook.
6. **Sheet → table rels-resolution is wrong for non-trivial workbooks.**
   `tables_import.rs:50` uses `xl/worksheets/_rels/sheet{N+1}.xml.rels` where
   `N` is calamine's sheet-INDEX. The OOXML file-NUMBER mapping is governed
   by `r:id` in `xl/workbook.xml`. For `example.xlsx`, the one table parses
   successfully but gets attached to the wrong `sheet_id` (4 / "shared")
   instead of the intended sheet (5 / "Table"). The Codex architecture
   review flagged this as a follow-up gap; it's already biting on a public
   IronCalc fixture.

In total: round-trip preserves SHEET COUNT, single-cell VALUES (other than
errors), and that's roughly it. Tables, formulas, names, date1904, custom
styles, chartsheets, theme — all silently destroyed. The only existing
round-trip test (`round_trip_ironcalc_basic_text_preserves_sheet_count`)
asserts sheet count and nothing else, so the regressions are invisible.

The arc shipped is the **scaffolding** + the **IMPORT side** of a round trip
spine. The **EXPORT side** is non-functional beyond cell values. The commit's
"round-trip spine: CLOSED" framing reverses the truth: spine is open on the
write side; the OOXML scanner work in W5-D-14b/c/d is solid as an import
foundation but currently dead-end because the export half discards it.

## HIGH findings

### H-1 — Exporter clobbers every formula it writes (umya API misuse)

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:86-104`

**Detail:** The export loop, for each formula cell:
```rust
cell.set_formula(formula_text.as_str());
if formula_cache == FormulaCachePolicy::WriteRecomputed {
    apply_value_to_cell(cell, val);
}
```
`apply_value_to_cell` calls `set_value_number` / `set_value_bool` / `set_value_string`.
Per umya 2.2.0 source (`structs/cell_value.rs:93-126`), each of those internal
setters calls `self.remove_formula()` AFTER updating the raw value:
```rust
pub fn set_value_number<T>(&mut self, value: T) -> &mut Self
where T: Into<f64>,
{
    self.raw_value = CellRawValue::Numeric(value.into());
    self.remove_formula();          //  <-- wipes the formula
    self
}
```

The default `formula_cache` is `WriteRecomputed`, so this is the hot path. Even
when `FormulaCachePolicy::SkipCache` is selected, the `(None, val)` branch only
fires when the formula map miss happens — irrelevant here.

**Compile-probe evidence:**
- Probe `probe_formula_export_inspects_sheet_xml`: emitted sheet XML for a
  Quantbook workbook with one formula cell `C1 := A1+B1` (cached `=3`) was
  literally `<c r="C1"><v>3</v></c>` — NO `<f>` element.
- Probe `probe_round_trip_with_ironcalc_export`: round-tripping `example.xlsx`
  drops formulas from 36 to 0. Sample formula `NA()` parsed on import is gone
  after export.
- Probe `probe_two_layer_round_trip_with_one_formula`: a one-formula workbook
  loses the formula after layer 1.

**Recommendation:**
1. Reorder the calls — write the cached value FIRST via `set_value_*`, then
   call `set_formula(formula_text)`. (`set_formula` does NOT clear the value
   per umya source `cell_value.rs:160`.)
2. OR use umya's `set_formula_result_default(value_string)` AFTER `set_formula`
   — that path is specifically designed for formula+result and does not
   clobber. `set_formula_result_default` accepts a string; the caller must
   convert numeric/bool to the OOXML-canonical string form (e.g.
   `format!("{}", n)` for numbers, `"TRUE"/"FALSE"` for bools).
3. Add a round-trip test that asserts formula text + cached value preservation
   for ALL value variants (Number / Boolean / Text / Error / Blank). The
   existing `export_workbook_with_values_round_trips_via_calamine` test only
   covers value-only cells, which is why this regression shipped.
4. Add a fixture-level test: import `example.xlsx`, export, reimport, assert
   `formula_count() == 36`. (Current round-trip smoke test asserts only sheet
   count.)

**Severity rationale:** This is the headline broken claim. The whole point of
W5-D-14e ("round-trip spine") was to round-trip formulas. The test surface
designed to catch this gap is shallow enough to miss it. Real users would
discover this immediately: any saved-then-reopened workbook turns formulas
into stale values. The fix is one line, but the gap is HIGH because the docs
+ commit message claim the feature works.

### H-2 — `date1904` workbook property silently dropped on export

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:25-30` (the exporter
constructs `umya_spreadsheet::new_file_empty_worksheet()` which initializes
a default workbook with no `date1904`). Quantbook's `Workbook::date_system()`
is never read.

**Detail:** The exporter has zero awareness of the workbook's `date_system`.
The output xlsx always uses the default 1900 epoch. A user opening a 1904
workbook in Quantbook, saving, reopening, will see their date serials shift
by 1462 days because Excel/calamine will interpret 1900-epoch serials.

**Compile-probe evidence:** Probe `probe_export_then_inspect_for_date1904_attribute`:
exported a workbook with `set_date_system(Excel1904)`. Inspected
`xl/workbook.xml`. The element `<workbookPr filterPrivacy="1"/>` was present —
no `date1904="1"` attribute anywhere.
```
PROBE: original date_system=Excel1904; reimport=Excel1900
```

**Recommendation:**
1. After `new_file_empty_worksheet()`, set the date1904 property on the umya
   spreadsheet. umya exposes this via `set_workbook_calculation` / similar;
   verify the exact API (check `umya_spreadsheet::structs::WorkbookProperties::set_date1904`).
2. Add a round-trip test that round-trips both 1900 and 1904 workbooks and
   asserts `date_system()` survives. Today this gap is only catchable via the
   compile-probe above.
3. If umya 2.2.0 lacks a `date1904` setter, document the gap loudly in the
   exporter and surface a `dropped_features` entry / warning in
   `XlsxExportReport`.

**Severity rationale:** Silent semantic corruption of every date value in a
1904 workbook. The W5-D-14b commit explicitly added `date1904` parsing for
this exact reason; the export side missed the loop-closure. The bug stays
hidden because tests only use 1900 fixtures and the round-trip test asserts
sheet count.

### H-3 — Tables completely dropped on export

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:25-117` — no code path
reads `workbook.tables()` or emits `xl/tables/*.xml`, no sheet rels, no
`tableParts` references in sheet XML.

**Detail:** The W5-D-14c commit says (XLSX-4-03): "tables ✅, formats ✅,
names parsed (NameTable wiring W5-D-15)". Tables are claimed to be part of
the closed acceptance. But the exporter does nothing with them. Structured
references like `Sales[Qty]` evaluated against an imported table would round-
trip the FORMULA TEXT (modulo H-1) but the TABLE METADATA needed to bind
the formula is gone — on reimport the engine would either bind to no table
(name lookup fails → `#NAME?`) or, worse, to a different table that happens
to exist.

**Compile-probe evidence:** Probe `probe_round_trip_drops_tables_silently`:
```
PROBE: example.xlsx imported 1 table(s)
PROBE: reimport sees 0 table(s)
```
The export "succeeded" with no warnings, no `dropped_features` entry.

**Recommendation:**
1. Add table-write to the exporter. The structure to mirror is what the import
   side parses: emit `xl/tables/table{N}.xml` per `TableMetadata`, plus
   the worksheet rels and the worksheet `<tableParts>` ref. umya may have
   a Table API (`umya_spreadsheet::structs::Table`) — check.
2. UNTIL implemented, the exporter MUST loudly flag drop. Either:
   - emit an `UnsupportedFeature { feature: ... }` for every table in the workbook
     into `XlsxExportReport.dropped_features`, OR
   - call out the gap in the export report's `warnings`, OR
   - return `XlsxError::Engine` if `workbook.tables().len() > 0` and we'd be
     silently destroying user data on save.
3. Add a round-trip test that exports a workbook with a table and asserts
   `tables().len()` round-trips.

**Severity rationale:** XLSX-4-03 (the acceptance criterion the commit
explicitly claims to close on tables) is FALSE. A user-visible table — the
most-load-bearing Phase 4.8 feature — silently vanishes on save. No warning,
no error.

### H-4 — Custom number formats dropped on export

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs` (no code path emits
`xl/styles.xml/<numFmts>` from `workbook.formats()`).

**Detail:** Same shape as H-3. The W5-D-14d import side parses `<numFmt>`
entries and registers them with `FormatTable::register_at` (replay-determinism
preserved). The export side never reads `workbook.formats()`. umya generates
a default `xl/styles.xml` with built-in formats only.

**Compile-probe evidence:** Probe `probe_round_trip_drops_custom_format_silently`:
```
PROBE: customfmt 164 after round-trip = None
```
Workbook registered `FormatId(164)="yyyy-mm-dd"` pre-export. Post-roundtrip
reimport sees `None` for `FormatId(164)`.

**Recommendation:**
1. Wire `workbook.formats().iter()` into umya's stylesheet API. umya tracks
   number formats via `StyleSheet::add_number_format` (verify exact API).
2. Test: export a workbook with a registered custom format; reimport; assert
   `formats().lookup(FormatId(164)) == Some("yyyy-mm-dd")`.
3. Note: per-cell `<c s="N">` application is admittedly W5-D-14 follow-up
   (commit doc), so even if the formats round-trip, cells don't display
   them. Still, the format-table contents themselves must survive.

**Severity rationale:** XLSX-4-03 claims "formats ✅". This is also false on
the export side. Without per-cell wiring this is partially academic, but
the format-table registration is the foundation per-cell wiring will build
on; losing it across save defeats the W5-D-14d work.

### H-5 — All Excel error values become text on round-trip

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:124-144` (sets value
via `set_value_string(e.sigil())`).

**Detail:** OOXML represents cell errors via `<c r="A1" t="e"><v>#DIV/0!</v></c>`.
Calamine's `Data::Error(CellErrorType::*)` variant maps to that. The current
exporter writes the sigil string as a regular string cell (`t="str"` or
`t="s"`), not as an error cell. On reimport, calamine sees a String and we
produce `Value::Text("#DIV/0!")`, indistinguishable from a user-typed
`'#DIV/0!`.

**Compile-probe evidence:** Probe `probe_round_trip_error_value_becomes_text`:
```
PROBE: Value::Error(DivZero) round-trips as Text("#DIV/0!")
ASYMMETRY DETECTED: Value::Error(DivZero) → exported as text → calamine reads back as Value::Text("#DIV/0!")
```
Probe `probe_error_all_variants_round_trip`: all 7 ErrorValue variants
(DivZero, NA, Name, Null, Num, Ref, Value) round-trip as `Text(...)`.

**Recommendation:** Use umya's `set_error(sigil)` API
(`umya-spreadsheet/src/structs/cell.rs:216`) instead of `set_value_string`.
Note `set_error` is implemented identically to `set_value_string_crate` (per
`cell_value.rs:187`), so umya may NOT actually emit `t="e"` either — needs
verification.

Even if umya doesn't emit `t="e"`, the BUG STATEMENT applies: the import
mapping is asymmetric with the export mapping. Either:
1. Make the export emit OOXML `t="e"` cells (verify umya support), OR
2. Document the loss explicitly in the export report's `dropped_features`
   (every Error cell triggers a dropped-feature entry), OR
3. Stop offering `Value::Error` round-trip in the public API contract.

**Severity rationale:** Errors are first-class engine values. Silent
text-conversion makes formulas downstream of an error cell produce a
different result on reopen (`ISERROR` returns false on a text). Asymmetric
round-trip with NO indication in the report violates the "never silently
claim fidelity" architecture principle.

### H-6 — Real-world fixture (`libreoffice_888_example.xlsx`) fails to import

**Where:** `crates/ql-io-xlsx/src/read/styles_import.rs:36-58` — uses
`FormatTable::register_at`, which rejects `StringCollision`.

**Detail:** LibreOffice emits this in `xl/styles.xml`:
```xml
<numFmts count="3">
  <numFmt numFmtId="164" formatCode="General"/>
  <numFmt numFmtId="165" formatCode="[$$-409]0.00"/>
  <numFmt numFmtId="166" formatCode="0.00"/>
</numFmts>
```
Note `numFmtId="164" formatCode="General"` — a "custom" format with the same
format-code string ("General") as built-in `FormatId(0)`. Our
`FormatTable::register_at(FormatId(164), "General")` fails with
`StringCollision { string: "General", existing_id: FormatId(0), attempted_id: FormatId(164) }`.
`register_custom_formats` translates that to `XlsxError::MalformedOoxml`.

The result: a real LibreOffice-exported xlsx — which is what users in the
broader OOXML ecosystem commonly produce — cannot be imported at all.

**Compile-probe evidence:** Probe `probe_unsupported_strict_mode_libreoffice`:
```
PROBE: libreoffice fixture import error = MalformedOoxml { part: "xl/styles.xml",
  message: "numFmt registration failed for id 164: StringCollision { string: \"General\",
  existing_id: FormatId(0), attempted_id: FormatId(164) }" }
```

**Recommendation:** OOXML doesn't forbid redundant custom format entries that
duplicate a built-in. Three options:
1. **Skip silently** when the new id is custom (≥164) AND its format-code
   string already exists at a built-in id. Record the mapping `id→builtin_id`
   somewhere so per-cell `<c s="N">` resolution still works (per-cell wiring
   is admittedly W5-D-14 follow-up).
2. **Allow ALIAS registration** in `FormatTable` (a new API that maps a
   second id to the same string as an existing id). More invasive but cleaner.
3. **Surface a warning** in the report instead of erroring. Still loses the
   id ↔ string association needed for round-trip, but at least the import
   doesn't fail.

Whichever path is chosen, this fixture (or an equivalent LibreOffice-source
xlsx) MUST be added to the test corpus so the regression can't recur.

**Severity rationale:** Real-world LibreOffice xlsx files don't import at all.
LibreOffice represents 10%+ of the OOXML ecosystem. The fixture is right
there in the IronCalc test corpus and was never run against the import path.

### H-7 — Sheet-rels resolution heuristic is wrong for non-trivial workbooks

**Where:** `crates/ql-io-xlsx/src/read/tables_import.rs:41-58`

**Detail:** The code assumes `sheet{idx+1}.xml.rels` is the rels file for
sheet at calamine index `idx`. But the OOXML file-number is governed by
`r:id` references in `xl/workbook.xml`, NOT by workbook-order index. Excel
freely reorders sheet xml file names when sheets are inserted, deleted, or
reordered.

The codebase doc-comment at `tables_import.rs:43-49` admits the gap:
> For files with non-standard layouts (gaps in sheet numbers, user-renamed
> paths) we'd need to follow the workbook rels; W5-D-14c uses the 1:1
> ordering which covers the standard case. Tracked as a W5-D-14 follow-up
> if a fixture exposes it.

**A fixture exposes it: `example.xlsx`.**

**Compile-probe evidence:** Probe `probe_sheet_rels_path_offset_for_example_xlsx`:
```
PROBE: sheet 0 = "Sheet1"          ← actual file: sheet1.xml? or different?
PROBE: sheet 1 = "Chart1"
PROBE: sheet 2 = "Second"
PROBE: sheet 3 = "Sheet4"
PROBE: sheet 4 = "shared"
PROBE: sheet 5 = "Table"
...
PROBE: table "TABLE1" attached to sheet_id=4   ← attached to "shared"!
```

The `xl/workbook.xml/<sheets>` shows:
```
<sheet name="Sheet1"          sheetId="1"  r:id="rId1"/>
<sheet name="Chart1"          sheetId="6"  r:id="rId2"/>
<sheet name="Second"          sheetId="3"  r:id="rId3"/>
<sheet name="Sheet4"          sheetId="8"  r:id="rId4"/>
<sheet name="shared"          sheetId="9"  r:id="rId5"/>
<sheet name="Table"           sheetId="7"  r:id="rId6"/>
<sheet name="Sheet2"          sheetId="2"  r:id="rId7"/>
<sheet name="Created fourth"  sheetId="4"  r:id="rId8"/>
<sheet name="Frozen"          sheetId="10" r:id="rId9"/>
<sheet name="Split"           sheetId="11" r:id="rId10"/>
<sheet name="Hidden"          sheetId="5"  state="hidden" r:id="rId11"/>
```

The actual sheet files are numbered `sheet1.xml..sheet10.xml`. There's only
ONE TABLE in example.xlsx (`xl/tables/table1.xml`), and that table belongs
to the "Table" sheet (workbook position 5). Our code looks at `sheet5.xml.rels`
when processing calamine index 4 ("shared"). Whichever sheet that
corresponds to is NOT "Table" — and the table gets attached to the wrong
sheet_id.

Result: `wb.tables().lookup("TABLE1")` returns metadata with
`meta.sheet = 4` (= "shared"). On any formula like `TABLE1[Col]`, the
binder resolves to the wrong sheet's cells.

**Recommendation:**
1. Parse `xl/_rels/workbook.xml.rels` to build the `r:id → part-path` map.
2. Cross-reference with `xl/workbook.xml/<sheets>` (already parsed in
   `workbook_xml.rs`) to map workbook-position-index → sheet-xml path →
   sheet-rels path.
3. Replace the `sheet{N+1}.xml.rels` heuristic in `tables_import.rs:50`
   with the proper rels-following resolution.
4. Add a round-trip test using `example.xlsx` (or a synthetic equivalent
   with shuffled sheet numbers) that asserts the table attaches to the
   right sheet.

**Severity rationale:** This bug strikes the FIRST real-world fixture used
to validate the import. Tables silently bind to the wrong sheet — data
corruption invisible until a user evaluates a structured ref. This is the
biggest single-bug failure-mode in the whole arc, because the metadata
LOOKS imported (count is right) but the linkage is broken.

### H-8 — Strict-mode UnsupportedFeature check fires AFTER potentially-failing styles import

**Where:** `crates/ql-io-xlsx/src/lib.rs:159-193`

**Detail:** Order of operations in `import_xlsx_bytes`:
```
1. package handle
2. parse_workbook_xml (date1904 + names)
3. scan_unsupported_features (populates inventory)
4. build_workbook_from_grid (cells + formulas via calamine)
5. set_date_system
6. import_tables (errors propagate)
7. parse_styles_xml + register_custom_formats (errors propagate)
8. IF UnsupportedPolicy::Strict AND inventory non-empty → error    ← only NOW
9. recompute
```

The strict-mode unsupported-feature check at step 8 happens AFTER steps 6
and 7, both of which can return errors. In particular, the
LibreOffice-style `StringCollision` (H-6) is a hard `MalformedOoxml` failure
that pre-empts the strict-mode signal.

A user who intends "import everything strictly, error on first
unsupported feature" gets the WRONG error class for libreoffice xlsx —
they see "MalformedOoxml" when they should see "UnsupportedFeature" (or
the LibreOffice case should be successful and only the actual unsupported
features should trip strict mode).

**Recommendation:**
- Move the strict-mode check earlier (immediately after scan_unsupported_features).
- Or split the strict-mode semantics: feature-inventory strict vs structural
  strict.

**Severity rationale:** Diagnoseability + UX. Not a data-loss bug but
materially affects the user's understanding of import failures.

### H-9 — `XlsxExportReport.dropped_features` is never populated by the exporter

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs` (entire file).

**Detail:** The export report has `dropped_features: Vec<UnsupportedFeature>`
and `warnings: Vec<XlsxWarning>` fields, but the exporter never pushes to
either. So when the exporter drops tables (H-3), custom formats (H-4),
named ranges (`workbook.names()` is also never read), date1904 (H-2), error
types (H-5), the report says clean. The "never silently claim fidelity"
architecture principle is violated at the export boundary.

**Compile-probe evidence:** Probe `probe_export_workbook_no_inventory_visibility`:
```
PROBE: export report dropped_features = []
PROBE: export report warnings = []
```
(For a workbook with a table that gets dropped silently.)

Same for the names probe (`probe_export_drops_named_ranges_silently`):
the exporter dropped the registered name with NO `dropped_features` entry.

**Recommendation:** Whenever export drops something it doesn't know how to
write, push an `UnsupportedFeature` to `dropped_features` (or an
`XlsxWarning` to `warnings`). At minimum the exporter today should emit:
- one per `workbook.tables().iter()` table
- one per `workbook.names().iter()` defined-name
- one per registered custom format (numFmtId ≥ 164)
- one per `Value::Error` cell encountered
- one if `workbook.date_system() == Excel1904` (until that round-trips)

That makes the loss explicit — the caller can choose to abort or proceed
informedly.

**Severity rationale:** Per the architecture review quoted in the code:
"the key assertion isn't that every OOXML feature is implemented in batch
one. The key assertion is that Quantbook never silently claims fidelity it
does not have." Today the export side silently claims fidelity for tables,
names, date1904, formats, errors. This is a direct architecture-principle
violation.

### H-10 — Inventory misses critical OOXML parts (theme, chart, calcChain, sharedStrings, chartsheets, vmlDrawings)

**Where:** `crates/ql-io-xlsx/src/read/feature_inventory.rs:36-44`

**Detail:** The patterns list:
```
xl/comments, xl/drawings/, xl/media/, xl/externalLinks/,
xl/pivotTables/, xl/pivotCache/, xl/vbaProject.bin
```
Plus worksheet-XML substring detection for CF, DV, hyperlinks, mergeCells,
sheetProtection.

Missing parts (verified by inspecting `example.xlsx` and `custom_theme_colors.xlsx`):
- `xl/theme/theme1.xml` (theme — colors / fonts hierarchy)
- `xl/charts/chart*.xml` + `xl/charts/style*.xml` + `xl/charts/colors*.xml` (embedded charts)
- `xl/chartsheets/sheet*.xml` (CHART SHEETS — a whole sheet that is a chart, not data)
- `xl/calcChain.xml` (calc dependency chain; not load-bearing for round-trip but worth knowing)
- `xl/sharedStrings.xml` (shared strings — usually present, regenerated by exporter)
- `xl/drawings/vmlDrawing*.vml` (VML drawings — legacy comment shapes)

In particular: example.xlsx has a sheet named "Chart1" that is actually a
**chartsheet** (`xl/chartsheets/sheet1.xml`). Calamine returns it as a regular
sheet name. Our import then creates an empty worksheet for it.

**Compile-probe evidence:**
- `probe_chartsheet_is_treated_as_regular_sheet`: "Chart1" imports as a sheet
  with `bounds = 0x0`. No feature-inventory flag.
- `probe_inventory_misses_chartsheets_chart_parts`: example.xlsx has
  `xl/charts/chart*.xml`, `xl/chartsheets/sheet1.xml`. Inventory reports
  `{PivotTables: 5, Comments: 2, Drawings: 6, ConditionalFormatting: 1,
  MergedCells: 1}`. Charts/chartsheets aren't there.
- `probe_inventory_misses_theme_part`: `custom_theme_colors.xlsx` inventory
  is `{Drawings: 2}`. Theme + chart + calcChain all missed.

**Recommendation:**
1. Add `UnsupportedFeatureKind` variants: `Theme`, `Charts`, `ChartSheets`,
   `VmlDrawings`. (Skip `CalcChain` and `SharedStrings` since they're
   regenerated by the exporter — not user-data-bearing.)
2. Add detection patterns: `xl/theme/`, `xl/charts/`, `xl/chartsheets/`, and
   `.vml` extension scan or explicit check.
3. For chartsheets specifically: the chartsheet xml IS the sheet (not a
   regular worksheet). The current import creates a phantom empty worksheet
   for these via calamine; that's incorrect semantics. At minimum the
   inventory must flag them so the user knows a sheet was effectively lost.

**Severity rationale:** Two of the IronCalc test fixtures (example.xlsx,
custom_theme_colors.xlsx) contain features the inventory doesn't detect. A
Strict-mode user importing these gets either silent feature loss or an
incorrect "clean" inventory followed by data corruption.

## MEDIUM findings

### M-1 — `iter_formulas` is HashMap-ordered, making exports non-deterministic

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:39-41`; underlying
`crates/ql-storage/src/workbook.rs:885` (`iter_formulas` doc says "Iteration
order is HashMap-arbitrary").

**Detail:** The exporter builds a `HashMap<(u16, u32, u32), String>` from
`workbook.iter_formulas()` then iterates sheet-by-sheet, row-by-row. The
formula_map insertion happens in HashMap order, but the lookup is keyed by
exact `(sheet, row, col)` — so the ORDER of insertion doesn't actually
affect correctness here. False alarm.

**HOWEVER** — there's a real determinism concern for the WHOLE export:
re-exporting the same workbook should produce byte-identical output (a
common requirement for diff-friendly version control or hash-based dedup).
Two factors break this:
- `iter_formulas` iteration order leaks into UMYA via the per-sheet write
  loop ONLY if the same (sheet, row, col) appears twice (it doesn't), so
  no effect.
- BUT umya's internal HashMaps for cell storage, styles, etc., DO produce
  HashMap-order output, so non-determinism is downstream of our code.

**Compile-probe evidence:** Probe `probe_iter_formulas_is_hashmap_ordered`
shows 4 inserts come out in arbitrary order. For now, harmless via the
keyed-lookup pattern; documenting the smell.

**Recommendation:** If future work needs byte-identical exports, sort formulas
by `(sheet, row, col)` before iterating; OR rely on the per-sheet inner
loop's deterministic row-major order (which is what the current code does)
and treat the formula_map ordering as an internal detail. The current code
is correct but worth defensive sorting if export determinism becomes a
contract.

**Severity rationale:** Not a bug today; flagged because the comment in
`umya_export.rs:36-41` doesn't mention determinism, and the `iter_formulas`
storage doc says it's HashMap-arbitrary. The smell is worth noting because
the deterministic-export requirement may surface in the qbook round-trip
path.

### M-2 — Inconsistent formula-text canonicalization: import strips `=`, direct put_formula doesn't

**Where:**
- Import path: `crates/ql-io-xlsx/src/read/calamine_grid.rs:128-130`
  (`s.strip_prefix('=').unwrap_or(s)`).
- Direct API: `crates/ql-storage/src/workbook.rs:830-853` (`put_formula`
  doc says "formula body WITHOUT the leading `=`" but the API doesn't
  enforce it — accepts whatever string the caller passes).

**Detail:** The convention in storage is "without leading `=`". Calamine
import strips `=` defensively. But the direct API `wb.put_formula(s, 0, 0, "=A1")`
stores `"=A1"` verbatim. So formulas stored by the import path are
canonical, but formulas stored by direct callers (tests, future op-log
replay, internal pipelines) may not be.

Effect on round-trip: if a non-canonical formula gets stored, then exported
via `iter_formulas`, the OOXML output gets `<f>=A1</f>` instead of `<f>A1</f>`.
Whether that breaks downstream consumers depends on their parser
forgiveness; safe consumers (Excel, calamine) tolerate both. But it's a
latent canonicalization bug.

**Compile-probe evidence:** Probe `probe_iter_formulas_arc_str_strip_eq`:
`put_formula(s, 0, 0, "=A1")` stores `"=A1"` with the leading equals.

**Recommendation:**
1. Either: `Workbook::put_formula` strips a leading `=` (enforces invariant).
2. Or: the EXPORTER strips it before writing.
3. Document the storage canon clearly and add a debug-assert in
   `put_formula` rejecting strings starting with `=`.

**Severity rationale:** Currently no demonstrated user-visible bug (since
H-1 destroys formulas before this matters), but a real-world issue once
H-1 is fixed and formulas survive export. Cleanup MEDIUM.

### M-3 — `convert.rs` uses `catch_unwind` when fallible API is available

**Where:** `crates/ql-io-xlsx/src/read/convert.rs:38-50`

**Detail:** The code wraps `wb.add_sheet(sheet_name)` in `catch_unwind` to
turn a panic into `XlsxError::MalformedOoxml`. But `Workbook` already exposes
`try_add_sheet_with_chunk_rows` (`workbook.rs:612`) which returns
`Result<SheetId, SheetNameError>` cleanly. `catch_unwind` adds latent risk
(double-panic, requires AssertUnwindSafe, breaks unwind invariants in
upstream crates), and is unnecessary here.

The CLAUDE.md "No Fallbacks" rule also pushes against `catch_unwind` since
it's effectively a `rescue nil` — broad enough to catch unrelated panics
from inside `add_sheet`'s implementation (e.g. allocator failure) and
misreport them as malformed OOXML.

**Recommendation:** Replace with:
```rust
let sheet_id = wb
    .try_add_sheet_with_chunk_rows(sheet_name, ql_storage::column::chunk_rows_from_env())
    .map_err(|e| XlsxError::MalformedOoxml {
        part: format!("workbook sheet[{sheet_idx}]"),
        message: format!("sheet name {sheet_name:?} rejected: {e:?}"),
    })?;
```

**Severity rationale:** Code smell + correctness risk (catches panics it
shouldn't) + violates the no-fallbacks rule. Easy fix.

### M-4 — `unwrap_or_default()` patterns silently mask malformed OOXML

**Where:** Multiple files.

**Detail:** Pattern audit — flag where `unwrap_or_*` could mask real
malformation:

| File:Line | Pattern | Risk |
|---|---|---|
| `tables_xml.rs:106` | `header_row_count = val.parse::<u32>().unwrap_or(1)` | LOAD-BEARING: silently defaults to 1 if attribute is malformed |
| `tables_xml.rs:108` | `totals_row_count = val.parse::<u32>().unwrap_or(0)` | LOAD-BEARING: silently defaults to 0 |
| `tables_xml.rs:98` | `id = val.parse::<u32>().unwrap_or(0)` | minor (id is mostly internal) |
| `tables_xml.rs:120` | `col_id = val.parse::<u32>().unwrap_or(0)` | LOAD-BEARING: column IDs are stable identifiers (rename-survival); silently colliding to 0 breaks invariants |
| `styles_xml.rs:180` | `num_fmt_id = val.parse::<u32>().unwrap_or(0)` | LOAD-BEARING: silently maps malformed numFmtId to General (FormatId 0) |
| `workbook_xml.rs:159-161` | `if let Ok(n) = ...parse::<u32>() { ... }` | OK — only sets local_sheet_id on parse success; defaults to None |
| `workbook_xml.rs:227-232` | `sheetId = ...parse::<u32>().map_err(...)` | OK — properly surfaces error |

`numFmtId="bad"` silently becomes General (0). Per CLAUDE.md "No Fallbacks":

**Recommendation:** For each load-bearing parse:
1. Switch to `.map_err(|_| XlsxError::MalformedOoxml { part, message })`.
2. Keep existing behavior under a feature flag (`#[cfg(feature = "permissive-malformed-ooxml")]`)

**Severity rationale:** No demonstrated real-world bug from these defaults
in the current fixture corpus, but the CLAUDE.md "no fallbacks" rule
explicitly targets exactly this anti-pattern. The bug surfaces silently
when a malformed workbook hits the engine — and we can't see it because
we have no failing test for it.

### M-6 — Export iterates every cell within bounds, including blanks

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs:78-109`

**Detail:** The export loop does `for row in 0..bounds.row_extent { for col in 0..bounds.col_extent { ... } }`.
For a sparse sheet — e.g. cell A1 and cell Z1000 — `bounds = 1000 x 26 =
26_000 cells` get touched even though only 2 cells have data.

This is acknowledged in the code comment at `umya_export.rs:76`:
> This is O(rows * cols) and inefficient for large sparse sheets; W5-D-14e
> follow-up: switch to column-wise iteration via ColumnStore.

Compile-probe measured:
- 100x100 sparse sheet (2 cells): export iterates 10_000 cells. <5ms.
- 5000x100 sparse sheet (2 cells): export iterates 500_000 cells. ~16ms.
- MAX_ROWxMAX_COLUMN sparse sheet (1 cell at boundary): export iterates
  ~17 billion cells (1048576 x 16384). Probe took 290+ seconds. Effectively
  a DoS vector if a user happens to have a cell near the bottom-right.

**Recommendation:** Two fixes, in priority order:
1. **Sparse iteration**: walk `Sheet::column(c).user_overlay/computed_overlay`
   entries directly instead of read(r, c) for every (r, c). `Sheet::read`
   already short-circuits on empty columns, but the outer loop still does
   the work. The MAX boundary probe (290s) is the smoking gun.
2. **Pre-flight bound**: if `bounds.row_extent * bounds.col_extent` exceeds
   some threshold (say 10M), use sparse iteration. Keep dense iteration as
   the simple path for typical sheets.

**Severity rationale:** Performance — not a correctness bug. Significant
because a benign user action (writing at `ZZ1048576`) can stall the engine
for 5 minutes. MEDIUM because the gap is documented in the code but not
guarded.

### M-8 — `import_xlsx_path` reads entire file into memory before parsing

**Where:** `crates/ql-io-xlsx/src/lib.rs:102` (`std::fs::read(path.as_ref())?`).

**Detail:** `import_xlsx_bytes` requires bytes already; `import_xlsx_path`
slurps the whole file. Then `CalamineGrid::from_bytes` and
`XlsxPackage::from_bytes` clone the bytes again (one `Vec<u8>` to each).
Plus `XlsxPreservation::original_bytes` clones a third time if preservation
is requested.

For a 100 MB xlsx, that's ~400 MB peak memory. Not catastrophic but a
real-world surprise.

**Recommendation:** Use `Arc<[u8]>` shared across `CalamineGrid` +
`XlsxPackage` + `XlsxPreservation`, or have callers opt into preservation
via a separate path that doesn't clone again.

**Severity rationale:** Memory pressure on large workbooks. Won't bite on
typical sheets but worth noting.

## Cross-cutting observations

### O-1 — "Round-trip spine: CLOSED" is the wrong frame for what shipped

W5-D-14a–e shipped a solid IMPORT side and a SCAFFOLDING export side. The
import side:
- Calamine cell grid is correct (modulo H-5's data_to_value asymmetry).
- date1904 + scoped name parse is correct.
- Feature inventory is structurally sound (modulo H-10 coverage gaps).
- Tables parse correctly (modulo H-7 rels-resolution).
- Styles parse correctly (modulo H-6 LibreOffice collision).
- The `recompute_loaded_workbook` bridge into the engine works.

The export side:
- Cell values (Number, Boolean, Text, Blank) round-trip.
- That's it.

Suggested re-framing of W5-D-14e in MASTER-PLAN: "round-trip spine half-
closed; import side complete, export side carries only value-cell scaffolding;
formulas, tables, names, date1904, custom formats deferred to follow-up
batches." Adjust XLSX-4-01 through XLSX-4-04 accordingly — none are
actually closed.

### O-2 — Tests + assertions need to mirror claimed acceptance criteria

The audit-discipline pattern (memory: `quantbook_engine_audit_discipline.md`)
calls for parallel Codex + separate-Opus audits per batch. The shipping
W5-D-14 series did not undergo this in advance, per the user's framing.
The shallow assertions in the existing integration tests are the immediate
cause of H-1 through H-5 shipping undetected: any test that says
"round-trip preserves sheet count" but not "preserves formulas, values,
tables" gives the wrong reassurance.

The recommended audit-discipline fix going forward: every claimed-closed
acceptance criterion needs at least one test that would FAIL if the
acceptance broke. The current code has 0 such tests for XLSX-4-03 and
weak ones for XLSX-4-01.

### O-3 — IronCalc's import is meaningfully bigger because it solves problems we haven't

Cross-referencing the IronCalc `xlsx/src/import/` (cited in the prompt at
~2800 lines): IronCalc parses theme, colors, shared strings, comments, and
re-parses defined-name formulas against the loaded sheet list. Quantbook's
hybrid approach (calamine + targeted scanner) is architecturally cleaner,
but the SCOPE delta is real: anything IronCalc parses that we don't is a
silent feature loss on our import.

The Codex architecture review (cited in lib.rs:19-23) framed the hybrid
choice well. The ongoing risk is that "calamine handles the common path"
becomes a license to skip OOXML pieces we should be aware of. Inventory
coverage (H-10) is the most-load-bearing missing piece — once we know
something exists, we can decide whether to handle it; until then it's
just dropped.

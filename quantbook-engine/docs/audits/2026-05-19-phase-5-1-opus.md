# Opus design audit — Phase 5.1

## Severity-tagged findings

### H-1 — Format ID Collision: wire format must be locked in 5.1

`docs/architecture/crdt-data-model.md:442-447` (open question 5).
The current wire format uses `u32` (`crates/ql-oplog/src/op.rs:121`
and `formats.rs:51`). Switching to UUID is a schema-breaking change.

**Recommendation:** Decide in 5.1 whether format-ids stay `u32`
(with deterministic on-wire allocation like Lamport counters) or
switch to UUID. Do not lock 5.2's wire format before this is
resolved.

### H-2 — RenameSheet asymmetric merge → user-visible bug

`docs/architecture/crdt-data-model.md:281`. If peer A does
RenameSheet(S→X) and peer B concurrently writes `=S!A1`, then
after merge on peer A's side, B's formula is broken. Peer B can
still edit successfully under the old name locally until they
pull the merge.

**Recommendation:** Acceptable for V1, but explicitly document
that users will see #NAME? on some peers until next session
restart. Consider producer-side RenameSheet rewrite-pass at
replay time to catch B's concurrent edits.

### H-3 — AddSheet name collision LWW + reject is undesirable UX

`docs/architecture/crdt-data-model.md:280`. Spreadsheet users
expect Google Sheets behavior: both sheets created with names
S and S(2). Silently rejecting the second AddSheet is worse
than Google's auto-rename.

**Recommendation:** Either implement S(2) auto-rename in 5.2
(not 5.3), or explicitly call out in Phase 5.2 acceptance
criteria that this is a known V1 limitation.

### M-1 — LWW Lamport semantics not formally verified

`docs/architecture/crdt-data-model.md:99-100` claims "Loro's
LoroList::push operations merge by Lamport timestamp" and "this
is last-writer-wins on Lamport timestamps." The design does
not cite Loro's merge proof or version-vector causality
semantics.

**Recommendation:** Verify Loro's source for the merge rule
before publishing the design. If causal-only (not LWW),
concurrent `PutValue{A1, 5}` and `PutValue{A1, 7}` could
produce either value non-deterministically on different peers.

> **Status note from consolidated doc:** Codex V1 verified this
> claim is wrong. Loro uses Fugue/origin-based ordering with
> peer-id tiebreaker, NOT Lamport timestamps. The SEMANTIC LWW
> outcome at the engine level still holds because replay
> applies both ops in deterministic causal order; whichever is
> later in causal order wins. Design doc wording corrected in
> closure commit.

### M-2 — Spill invariant claim under-tested in CRDT context

`docs/architecture/crdt-data-model.md:247-250` states spill-
anchor / spill-target ordering depends on set_formula-before-
set_value-at-target ordering. Op-log preserves this — but the
code path (`cells.rs:624-710`) shows the blocking check
(`write_spill`) runs AFTER the set_formula op is already
logged.

**Recommendation:** Add a probe test in 5.2 that logs concurrent
set_formula + set_value on a spill target across two simulated
peers, exports/imports, and verifies the spill anchor survives
the merge.

### M-3 — Effort estimate assumes Tier D2 closure

5.1 says 5.2 is "1-2 weeks" and depends on "Tier D2 closes
before 5.2." `docs/phase5/entry-plan.md:49-54` lists D2 as
"ql-oplog → ql-io reverse dependency cleanup" with no
committed effort or date.

**Recommendation:** Confirm D2 is in-flight before 5.2 starts.
If not, add 3-5 days to the 5.2 estimate.

### M-4 — ql-collab scope under-specified for transport

The design lists `ql-collab` modules as `session, transport,
presence, undo` with "Total Phase 5.2 crate LOC estimate:
~1,500-2,500 LOC." But `Transport` is a trait with no concrete
impl (WebSocket deferred to 5.5). 1,500-2,500 LOC for a trait
+ three modules on an empty crate seems low.

**Recommendation:** Break down the 5.2 LOC estimate by module
(session: X, presence: Y, transport trait: Z, undo: W) with
concrete function signatures in the next iteration.

### M-5 — Open Question 3 (BatchCommit atomicity) not addressed

`docs/architecture/crdt-data-model.md:423-424` asks whether
inner ops are STILL contiguous in the merged log. The design
defers verification to 5.2 ("Verify this with Loro docs + a
probe test") but provides no reference.

**Recommendation:** Add to 5.1 audit checkpoint a hand-traced
example or cite a Loro spec guaranteeing per-peer op
contiguity survives merges.

> **Status note:** Codex V2 verified this is correct. BatchCommit
> is a single LoroList entry (one JSON blob, one push); concurrent
> peer's op can land before or after, never inside.

### L-1 — ShallowSnapshot compaction policy deferred without guard

`docs/architecture/crdt-data-model.md:165-175` acknowledges
100k cells × 10 peers × 1k edits = 10M list entries, mitigated
by "Phase 5.5's offline-sync work uses ExportMode::ShallowSnapshot."
No 5.2 acceptance criterion guards against unbounded op-log
growth.

**Recommendation:** Add a Phase 5.2 test that exercises 100k
cells × 10 ops per cell (1M ops total) and measures export
size with/without ShallowSnapshot, setting a baseline.

### L-2 — Presence container persistence model unclear

`docs/architecture/crdt-data-model.md:228-226` states presence
is "ephemeral and unordered" and ".qbook may or may not
persist it." But the container shape lists `LoroMap "presence"`
as persistent at line 208. If it's a LoroMap in the LoroDoc,
it WILL persist via `ExportMode::Snapshot` unless explicitly
excluded.

**Recommendation:** Clarify: does `.qbook/oplog.bin` save
presence? If no, the export logic must use a filter to exclude
`"presence"` from snapshots.

## OK confirmations

- **OK-1**: Cycle detection in `recompute_all` (recompute.rs:109-128)
  correctly builds an ephemeral CalcgraphSession, runs Tarjan SCC,
  pre-writes `#CIRC!` BEFORE the HashMap-order loop. Matches design.
- **OK-2**: Replay's idempotence on format registration verified
  at `formats.rs:45-46` — re-registering the same string at the
  same id is a no-op. Design claim sound.
- **OK-3**: BatchCommit nesting is explicitly permitted by schema
  and handled recursively in replay. Design claim correct.
- **OK-4**: Option A's preservation of Phase 4 invariants is
  well-supported. Same storage / calcgraph code paths regardless
  of producer or replay source. No special CRDT merge path
  needed for invariant preservation.

## Verdict

Design is sound for Phase 5 V1, but THREE HIGH-severity items
need 5.1 closure or explicit 5.2 acceptance-criteria
guardrails: format-id wire-format lock, RenameSheet user-
experience documentation, and AddSheet name-collision auto-
rename scheduling. The spill invariant and BatchCommit
atomicity claims are reasonable but MUST be verified with
probe tests in 5.2 before merging collaborative peer edits
into production.

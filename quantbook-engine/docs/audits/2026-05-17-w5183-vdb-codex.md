# W5-183 VDB Codex Audit

Scope: commit `f81965a0a9c` on `feat/quantbook-engine`.

I rechecked the six Microsoft examples and compared the implementation against LibreOffice/OpenFormula's VDB algorithm shape. The core iteration, 0-based range overlap, full-period book depletion, and locked SLN switch are consistent with the independent reference for normal inputs. The findings below are validation and coverage gaps.

## HIGH

No HIGH findings in the core VDB period math. The Microsoft fixtures recompute to:

- `VDB(2400,300,3650,0,1)` = `1.315068493...`
- `VDB(2400,300,120,0,1)` = `40`
- `VDB(2400,300,10,0,1)` = `480`
- `VDB(2400,300,120,6,18)` = `396.306053...`
- `VDB(2400,300,120,6,18,1.5)` = `311.808936...`
- `VDB(2400,300,10,0,0.875,1.5)` = `315`

### HIGH-1: `salvage > cost` returns `0` instead of `#NUM!`

- Path: `crates/ql-functions/src/financial_fns.rs:830`
- Snippet:

```rust
if cost < 0.0
    || salvage < 0.0
    || life <= 0.0
    || start_period < 0.0
    || end_period < start_period
    || end_period > life
    || factor <= 0.0
```

The validation never rejects `salvage > cost`. For `VDB(100,200,10,0,1)`, the kernel computes `book - salvage = -100`, clamps the DDB amount to `0`, computes a negative SLN amount, never switches, and returns `0`. `VDB(0,1,10,0,1)` also returns `0` because the `cost == 0` short-circuit runs after this incomplete validation.

OpenFormula's VDB constraints require `Salvage < Cost`, and LibreOffice's VDB wrapper rejects `fSalvage > fCost` before calculation. This should be `#NUM!`, not silent zero depreciation.

Proposed fix: add `|| salvage > cost` before the short-circuits and add tests for both `VDB(100,200,10,0,1)` and `VDB(0,1,10,0,1)`. Keep `salvage == cost` returning `0` only if that is the intended Excel-compatibility relaxation.

## MEDIUM

### MEDIUM-1: the DoS guard still allows a multi-billion-iteration endpoint

- Path: `crates/ql-functions/src/financial_fns.rs:837`
- Snippet:

```rust
|| life > i32::MAX as f64
|| end_period > i32::MAX as f64
```

- Path: `crates/ql-functions/src/financial_fns.rs:855`
- Snippet:

```rust
let end_ceil = end_period.ceil() as i32;

for period in 0..end_ceil {
```

The guard rejects values above `i32::MAX`, but it still accepts `life = end_period = 2_147_483_647.0`, then attempts roughly 2.1 billion loop iterations. It also accepts values just below the max whose `ceil()` reaches `i32::MAX`. That defeats the stated DoS purpose even though the cast itself no longer overflows.

Proposed fix: validate `end_period.ceil()` before the cast and use a practical maximum iteration cap, not `i32::MAX`. At minimum reject `end_period.ceil() >= i32::MAX as f64`; better, define a documented financial iteration limit and test that boundary directly.

### MEDIUM-2: crossover/fractional behavior is verified by examples but not pinned at the risky boundaries

- Path: `crates/ql-functions/src/financial_fns.rs:2676`
- Snippet:

```rust
fn vdb_no_switch_diverges_from_default_partial_range() {
    ...
    assert!(
        switched >= no_switch,
        "switched ({switched}) should be ≥ no_switch ({no_switch})"
    );
}
```

The implementation matches the independent reference for crossover and fractional ranges, but the tests only assert an inequality for the switch-sensitive range. They do not pin the actual crossover outputs or the fractional overlap cases called out in the audit prompt.

Proposed fix: add exact-value tests:

- `VDB(1000,100,10,5,7)` = `117.9648`
- `VDB(1000,100,10,5,10)` = `227.68`
- `VDB(1000,100,10,5,10,2,TRUE)` = `220.3058176`
- `VDB(1000,100,10,0.5,1.5)` = `180`
- `VDB(1000,100,10,2.3,4.7)` = `249.344`

That would pin the full-period book depletion, no-switch divergence, non-integer `end_period.ceil()` behavior, and partial first/last period overlap math outside the Microsoft fixtures.

## LOW

### LOW-1: no-switch full-life test comment states a false invariant

- Path: `crates/ql-functions/src/financial_fns.rs:2654`
- Snippet:

```rust
// Both should equal cost - salvage = 2100 over the full life
// (DDB salvage cap ensures full depreciation either way).
```

This is true for the chosen `2400/300/10/factor=2` fixture because the DDB schedule happens to hit the salvage floor by the last period. It is not a general VDB invariant when `no_switch=TRUE`; for example `VDB(1000,100,10,0,10,2,TRUE)` is `892.6258176`, not `900`.

Proposed fix: rewrite the comment to say this specific fixture reaches salvage under no-switch, or change the test to assert a known no-switch value where default and no-switch differ.

### LOW-2: matrix test count and `arg_type` wording are inaccurate

- Path: `docs/compat/excel-matrix.md:265`
- Snippet:

```markdown
| VDB | ✅ | 19 | ... **Engine convention**: `no_switch` uses `arg_type` (Boolean-strict); ...
```

There are 21 `vdb_*` unit tests in `financial_fns.rs`, not 19, and the e2e adds another dispatch test. Also, `arg_type` is not Boolean-strict; it uses numeric coercion and treats any non-zero numeric value as `TRUE`, blank as `FALSE`, and errors as propagated. That behavior may be fine, but the matrix wording should not call it Boolean-strict.

Proposed fix: update the count and reword to "`no_switch` uses the TVM-style logical coercion helper (`0`/blank false, non-zero true, errors propagate)."

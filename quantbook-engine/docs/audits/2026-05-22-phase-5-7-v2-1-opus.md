# Phase 5.7 V2.1 — Opus adversarial audit lane

## Scope

V2.1 introduces the FIRST cross-FFI Transport surface (LoopbackPair + 5 new
CollabSession methods on the napi class + 1 new Rust-side
`attach_transport_boxed` sibling). The V1 closure ran 3 audit cycles + an
Opus-B V2-readiness analysis that pre-cleared the design path; V2.1 follows
Option A (opaque Transport class + factory pattern). This lane asks "what
could still go wrong?" with focus on memory/lifetime, consumption-semantics
edge cases, error mapping fidelity, test gaps, async-V2.3 forward-compat,
and Rule 4 application.

## Verdict

**PASS-WITH-FINDINGS.** V2.1 is shippable. The Rust-side sibling-method
shape is sound, the Send compile-assert for the napi `Transport` is
correct, and the napi class's single-use `take_inner()` discipline catches
the obvious double-attach hazard. Two HIGH findings should be FIXED
IN-CYCLE: a behavioral-spec mocha test asserts a tautology and ships a
docstring that contradicts the actual engine semantics (mistake LOAD-BEARING
for V2.2 design); a stale inner-fn comment block in
`CollabSession::attach_transport<T>` falsely claims the function body
performs the VV-reset (which now happens only inside the delegated
`attach_transport_boxed`). Four MEDIUMs flag (a) a missing `#[must_use]` on
the new sibling, (b) an under-asserted Sync surface for `LoopbackPair`, (c)
an error-discrimination gap in the binding (CollabSessionError variants
collapse to Display strings — the IDE cannot programmatically distinguish
Closed-vs-Io), and (d) the LoopbackPair design boxing+unwrap is fragile for
future composition. Five LOWs + four OBS captured for completeness.

The "Rule 4 sweep" returned ONE finding: the binding's `!Sync` claim for
`CollabSession` is documented but never compile-proved (the commented-out
probe pattern is preserved from V1 — V1 audit accepted this). For
`Transport` and `LoopbackPair` no `!Sync` claim is made, so Rule 4 doesn't
trigger.

## HIGH

### HIGH-1: The mocha test "detach drops in-flight bytes on the loopback queue" pins a WRONG behavioral spec — the docstring is incorrect AND the assertion is a tautology that catches no regression

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:591-617`.

**Specific issue**: this test claims to verify "detaching session A's
transport drops the bytes it just sent. Peer B's poll then returns 0 (the
bytes went into the Loopback queue which was tied to the now-dropped
transport end on A's side)" — this mental model is FALSE. Verifying
against `crates/ql-collab/src/transport.rs:380-394`:

```rust
pub fn pair() -> (Self, Self) {
    let a_to_b = Arc::new(Mutex::new(VecDeque::new()));
    let b_to_a = Arc::new(Mutex::new(VecDeque::new()));
    let a = Self {
        inbox: b_to_a.clone(),
        outbox: a_to_b.clone(),
        closed: AtomicBool::new(false),
    };
    let b = Self {
        inbox: a_to_b,            // ← THIS Arc was a.outbox
        outbox: b_to_a,            // ← THIS Arc was a.inbox
        closed: AtomicBool::new(false),
    };
    (a, b)
}
```

The shared queues live in `Arc<Mutex<VecDeque<Vec<u8>>>>`. When endpoint A
sends, bytes are pushed into `a_to_b` — which is also `b.inbox`. When
endpoint A is dropped (via `sessionA.detachTransport()`), A's two Arc
clones decrement, but B's Arc on the same queue keeps the `VecDeque` alive
with the bytes. **B's `pollRemote` would return 1, not 0, and the merged
op would commit to session B's log.**

The test asserts `merged >= 0`. Since `merged` is `number` (u32), this
assertion is TAUTOLOGICALLY TRUE — every possible non-negative integer
satisfies it. The test catches no regression: an engine refactor that
flipped the Arc-sharing pattern (e.g., re-engineered queues to live in
endpoint A's storage exclusively) would silently pass.

This is doubly bad because the test's docstring TEACHES the wrong mental
model to future readers who copy-paste from it. The note at lines 597-599
("NOTE: this pins current Loopback semantics. If the engine later
guarantees in-flight delivery (e.g., via a sticky queue), this test should
be updated to reflect that.") rationalizes the wrong-headed test by
implying the current semantics already DON'T guarantee delivery — but they
DO (per the Arc sharing).

Mocha would surface this hazard the moment a real assertion was added.
Test 27 (this one) is the only one in the V2.1 suite that's effectively
dead code.

**Closure recommendation**: **FIX NOW** — replace with two distinct tests:
1. `'detach does NOT drop bytes already queued for peer (Arc-shared queue contract)'`:

   ```ts
   sessionA.appendPutValue(0, 0, 0, 1);
   sessionA.flushToTransport();
   sessionA.detachTransport();
   // B's inbox queue still has A's bytes — Arc-shared semantics
   const merged = sessionB.pollRemote();
   assert.strictEqual(merged, 1, 'B drained the 1 queued blob after A detached');
   assert.strictEqual(sessionB.opCount(), 1, 'B has the op even though A detached');
   ```

2. `'detach IS load-bearing for V2 V3 step 1 baseline-reset (re-attach delivers all ops)'`:
   – exists already as test "reattach a different transport resets VV baseline"
   – call out the distinction clearly.

**Why HIGH**: this test is a baseline mocha+behavior test for the Transport
binding and pins V2.1's two-peer semantics. A misleading-name test +
tautological assertion + wrong-mental-model docstring violates the
"test-as-spec" discipline that V1 + V2-V3-V4 cycles relied on (every
audit-closure mocha test pins ONE specific contract). V2.2's auto-flush
work will write similar tests; this one's pattern is contagious.

### HIGH-2: Stale "Phase 5.5 V2 V3 step 1" comment block inside `CollabSession::attach_transport<T>` falsely claims the function body resets `last_flushed_vv` — but the body now only delegates to `attach_transport_boxed`

**Repo**: engine.
**File:line**: `crates/ql-collab/src/session.rs:715-726`.

**Specific issue**: the V2.1 refactor changed `attach_transport<T>` from
"do the reset + replace" to "delegate to `attach_transport_boxed`". But
the 6-line block-comment from the V2 V3 step 1 era was left in place
attached to the function body, NOT migrated into `attach_transport_boxed`:

```rust
pub fn attach_transport<T: Transport + Send + 'static>(
    &mut self,
    transport: T,
) -> Option<Box<dyn Transport + Send>> {
    // **Phase 5.5 V2 V3 step 1 (2026-05-21):** reset `last_flushed_vv`
    // to `None`. A new transport-peer hasn't seen ANY of this
    // session's ops, so the next `flush_delta_to_transport` must
    // send from the empty VV (= all ops). If we kept the stale
    // VV from a prior transport, the new peer would miss ops
    // 0..stale_vv and end up with a corrupt view.
    self.attach_transport_boxed(Box::new(transport))
}
```

The comment is about a step the body NO LONGER performs (the reset now
happens inside `attach_transport_boxed` at line 745). A reader of the
generic entry point sees a comment that doesn't match the code; if they
modify `attach_transport<T>` to e.g. add a wrap step, they may delete the
comment thinking it's stale (it IS, but the V2 V3 step 1 invariant is
still load-bearing — they just need to read `attach_transport_boxed`'s
comment, not this one).

The mirror comment IS in `attach_transport_boxed` at lines 743-744 ("//
Mirror attach_transport<T>'s contract: reset the VV baseline so the next
flush sends from empty.") — also misleading because there's nothing TO
mirror anymore; `attach_transport<T>` doesn't do the reset itself.

This is a Rule 4 doc-drift hazard in the same shape as the V1 HIGH-1 that
Opus-B caught in the megaudit ("`PeerId::new` rejects" docstring claim
that was actually false — the rejection was at a sibling layer). The V2.1
analog is the inverse: a comment claims this function does X, when
actually a SIBLING method does X.

**Closure recommendation**: **FIX NOW** (doc-only) — replace the comment
in `attach_transport<T>` with:

```rust
pub fn attach_transport<T: Transport + Send + 'static>(
    &mut self,
    transport: T,
) -> Option<Box<dyn Transport + Send>> {
    // Delegate to the boxed sibling. The V2 V3 step 1 baseline-reset
    // invariant (last_flushed_vv = None) lives in attach_transport_boxed.
    self.attach_transport_boxed(Box::new(transport))
}
```

And update the comment in `attach_transport_boxed` from "Mirror
attach_transport<T>'s contract" to be the authoritative statement (drop
the "Mirror" framing — this IS the contract now):

```rust
pub fn attach_transport_boxed(
    &mut self,
    transport: Box<dyn Transport + Send>,
) -> Option<Box<dyn Transport + Send>> {
    // V2 V3 step 1 contract: every attach resets the VV baseline so
    // the next flush sends from empty (new transport-peer hasn't seen
    // any ops from this session).
    self.last_flushed_vv = None;
    self.transport.replace(transport)
}
```

**Why HIGH**: per the engine's own audit-discipline Rule 4 + the V1
megaudit's HIGH-1 closure pattern, comments that claim engine behavior
must verify against the actual source. This is a small but exact pattern
match for the kind of doc-drift Rule 4 was added to catch.

## MEDIUM

### MEDIUM-1: `CollabSession::attach_transport_boxed` lacks `#[must_use]` — the returned `Box<dyn Transport + Send>` carries WebSocketTransport background tasks but the new entry point silently invites callers to drop it

**Repo**: engine.
**File:line**: `crates/ql-collab/src/session.rs:739-747` (no `#[must_use]`)
vs `crates/ql-collab/src/session.rs:760-767` (`detach_transport` HAS
`#[must_use = "drop the returned transport to release its background
tasks; holding it past detach keeps the old TCP socket alive"]`).

**Specific issue**: `detach_transport` was annotated `#[must_use]` in the
V2 V3 step 5 megaudit (per its docstring at lines 753-759, "Opus-A M3,
2026-05-21"). The reason: the returned `Box<dyn Transport + Send>` owns
WebSocketTransport's reader+writer tasks; dropping it eagerly is required
or the old TCP socket leaks.

`attach_transport_boxed` returns the PRIOR transport in the same shape —
`Option<Box<dyn Transport + Send>>` — with the SAME drop-eagerly semantics.
But it has no `#[must_use]`. Rust-side callers of the boxed sibling can
silently drop the returned `Option` (e.g., `session.attach_transport_boxed(box1);`
without a `let _ =` or `let _prior =`) — the borrow-check accepts it, and
for WebSocketTransport this means the prior connection's TCP socket and
tasks leak until the GC catches up.

This is a Rust-side regression. The napi binding's V2.1 caller does `let
_prior = self.inner.attach_transport_boxed(boxed);` (line 439) so the
binding is safe, but the engine API surface is now asymmetric:
`detach_transport` makes you handle the prior, `attach_transport_boxed`
silently drops it.

Note: the original `attach_transport<T>` ALSO lacks `#[must_use]` — V1
megaudit Opus-B LOW-3 (line 287-298) flagged the asymmetry but recommended
"V2 BACKLOG ITEM." V2.1 had a chance to close the asymmetry by adding
`#[must_use]` to BOTH `attach_transport<T>` and `attach_transport_boxed`,
but only the boxed sibling was added without the annotation — making the
gap wider.

**Closure recommendation**: add `#[must_use = "drop the returned prior
transport to release its background tasks; holding it past attach keeps
the old TCP socket alive"]` to BOTH `attach_transport<T>` and
`attach_transport_boxed`. The V1 LOW-3 recommendation can be closed in V2.1
since both methods share the same boxed return shape now.

### MEDIUM-2: `LoopbackPair` napi struct has no Send/Sync compile-assertions — Rule 4 pattern says "negative claims need positive proof" but the converse-quality gap here is that LoopbackPair has no positive claim at all

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:595-643` (no
`_ASSERT_LOOPBACK_PAIR_*` const fn).

**Specific issue**: V2.1 added `_ASSERT_BINDING_TRANSPORT_SEND` (lines
667-670) which compile-proves `Transport: Send`. Good. But `LoopbackPair`
got no equivalent. The wrapper holds `a: Option<LoopbackTransport>, b:
Option<LoopbackTransport>` — and `LoopbackTransport: Send + Sync` is
compile-asserted in `crates/ql-collab/src/transport.rs:457-460`
(`_ASSERT_LOOPBACK_TRANSPORT_SEND_SYNC`). By composition,
`Option<LoopbackTransport>: Send + Sync`, and `LoopbackPair: Send + Sync`.
This is the "right" answer but it's not pinned.

If a future refactor makes LoopbackTransport `!Sync` (e.g., adds a
`RefCell` field for some debug hook), `LoopbackPair: !Sync` would
silently flow through. napi-rs's class-instance discipline relies on
JS single-threadedness, so the loss of Sync wouldn't break V2.1 — but
it WOULD break a future V2.3+ use case if e.g. `Transport.websocketConnect`
ever wanted to return a `Transport` that's `Sync` for shared-reference
patterns across N-API worker threads.

Audit-discipline Rule 4 explicitly says "negative trait claims need
positive proof OR per-field walk." For LoopbackPair there's no claim
either way today. This isn't a Rule 4 VIOLATION — it's a quality gap that
applying Rule 4 mechanically would close.

**Closure recommendation**: add a const-fn compile assertion mirroring
`_ASSERT_BINDING_TRANSPORT_SEND`:

```rust
const _ASSERT_BINDING_LOOPBACK_PAIR_SEND: fn() = || {
    fn assert_send<T: Send>() {}
    assert_send::<LoopbackPair>();
};
```

Or write a docstring-walk explaining the field composition. The const-fn
version is cheaper and self-maintaining.

### MEDIUM-3: napi binding's error mapping via `format!("{e}")` collapses `CollabSessionError`/`TransportError` variants into Display strings — IDE callers cannot programmatically distinguish `TransportError::Closed` from `TransportError::Io(msg)` from `CollabSessionError::OpLog(_)`

**Repo**: engine + IDE.
**File:line**: `crates/ql-bindings-node/src/lib.rs:478-482`
(`flushToTransport`), `crates/ql-bindings-node/src/lib.rs:501-507`
(`pollRemote`).

**Specific issue**: every Result-returning napi method in V2.1 uses
`map_err(|e| Error::from_reason(format!("{e}")))`. The Display impl on
`CollabSessionError::Transport(TransportError::Closed)` produces "transport
error: transport closed" (concatenation via `#[error("transport error:
{0}")]` and `#[error("transport closed")]`). For `Io(msg)` it's "transport
error: transport I/O error: msg". The IDE-side can only `.message`-match
substrings to discriminate.

For V2.1 + Loopback there's no observable distinction in practice (Loopback
never returns Io errors absent mutex poisoning, which is itself
unreachable in single-threaded V8). But the V1 megaudit Opus-B MEDIUM-1
already flagged that V2.3 WebSocketTransport WILL hit `Closed` vs `Io`
distinctions — the IDE's reconnect handshake needs to know "peer reset"
vs "auth rejected" vs "capacity exceeded" (the V2 V3 step 5 megaudit's
`Transport::last_error()` lift was the closure for this exact concern).

`transport_last_error()` is the engine-side answer (returns
`Option<String>` containing the underlying impl-specific message). But:
1. V2.1 doesn't bind `transport_last_error()` (V2.2 ships it per plan).
2. Even with it bound, IDE callers would still need to substring-match on
   the Display message to distinguish error categories — `Display` is a
   lossy projection of the enum discriminant.

This is V1 territory propagated forward, not a V2.1 regression. But V2.1
is the FIRST step where the surface becomes large enough that an IDE
consumer might write reconnect logic on top — at which point the lossy
mapping starts to bite.

**Closure recommendation**: V2.1 ship can stay (V1 baseline). V2.2 should
either:
- (a) Bind `transport_last_error()` AND add a `kind()` accessor to
  TransportError that returns a stable string discriminant
  (`'closed' | 'io'`), OR
- (b) Switch the IDE binding to throw a structured error subclass
  (`TransportClosedError extends Error` etc.) so JS can `instanceof`-check.

Option (b) is napi-rs-supported via `#[napi(constructor)]` on a custom
Error struct + throwing it via `napi::Error::with_code(code, msg)` where
`code` becomes the JS Error's `.code` field. Cheap and unblocks IDE
reconnect logic at the error level rather than the substring level.

**Why MEDIUM not HIGH**: V2.1 doesn't introduce the hazard, just inherits.
Should be CLOSED IN-CYCLE for V2.2 because V2.2 binds
`transport_last_error` and `transportLastError`-using IDE code will be
written then. Pinning a substring-match contract in V2.2 mocha is a
debt the team will regret.

### MEDIUM-4: `loopbackTransportPair()` TS helper at `session.ts:130-134` calls `takeA()` then `takeB()` sequentially with no try/finally — if `takeB()` ever throws (it can't in V2.1, but could in V2.3+ if construction fails), the `tA` Transport instance leaks

**Repo**: IDE.
**File:line**: `extensions/quantlab/src/quantbook/session.ts:130-134`.

```ts
export function loopbackTransportPair(): [TransportInstance, TransportInstance] {
    const engine = loadQuantbookEngine();
    const pair = new engine.LoopbackPair();
    return [pair.takeA(), pair.takeB()];
}
```

In V2.1 neither takeA nor takeB can fail on a fresh pair (the `Some`
fields are populated by `new()`). So this code is safe TODAY. But:
1. The helper signature returns a 2-tuple ALWAYS — there's no error path.
2. A future change that makes either taker fallible (e.g., V2.3 might add
   `LoopbackPair.takeAWithBackpressure(maxQueue)` that errors if max is
   invalid) would make this helper leak the `tA` Transport if `tB` throws.
3. Even today, if a future napi-rs version starts throwing on
   `napi_unwrap` failures for class instances (defense against undefined-
   behavior cases — a possible 4.x change), this becomes a real concern.

A `try/finally` doesn't help here because `tA` is the throwaway — the
helper has no way to "undo" the take. The right fix is to let JS's GC
clean up the orphaned `Transport` wrapper (which it will), AND to make
the helper signature acknowledge fallibility.

**Closure recommendation**: V2.1 ship can stay. Document the
single-takeable invariant in the helper's JSDoc as a "if either take
throws, the pair is unusable; discard and construct a fresh pair." Don't
introduce try/finally machinery for a hypothetical V2.3 scenario.

**Why MEDIUM not LOW**: this is the "Don't Be Lazy" + "no fallbacks" angle
— the helper as written silently swallows the case where `takeB` fails
mid-call. It's not a bug today, but it's a pattern that V2.3+ should be
explicitly hardened against. Marking MEDIUM so V2.2's audit picks it up
as a known footgun candidate.

## LOW

### LOW-1: napi `attachTransport` validates input type via `napi_instanceof` ONLY if `#[napi(strict)]` is set — V2.1 doesn't set strict, so a JS caller passing a wrong-type class instance falls through to `napi_unwrap` on the raw wrapped pointer

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:429-441`
(`attach_transport`) + `napi-derive-backend-5.0.4/src/codegen/fn.rs:446-465`
(strict-gated `#type_check`).

**Specific issue**: napi-rs's codegen for `&mut Transport` parameters
generates `from_napi_mut_ref` which calls `napi_unwrap(env, napi_val, ...)`
directly — no type check unless `#[napi(strict)]` was set on the method.
V2.1 doesn't set strict. So JS calling
`session.attachTransport(someOtherNapiClassInstance)` where
`someOtherNapiClassInstance` is a `#[napi]` class with a different wrapped
pointer type would:
1. `napi_unwrap` returns Ok with the raw pointer of the wrong type.
2. The Rust code casts the pointer to `&mut Transport`.
3. `transport.take_inner()` reads the field-offset of `Transport::inner`
   into memory belonging to a DIFFERENT type — UB.

This is a napi-rs ecosystem hazard, NOT V2.1-introduced. V1 has the same
issue with `mergeBytes(notUint8Array)` — though for Uint8Array, napi-rs
has a `value_type()` Object check that catches blatant primitives.

For class-to-class confusion (`CollabSession` passed as `Transport`), the
hazard depends on whether the two wrapper types' first field reads
overlap. For V2.1's `Transport { inner: Option<Box<dyn ...>> }` vs
`CollabSession { inner: CoreCollabSession }`, both first fields are
`inner` but of different types — confusion would corrupt memory.

**Closure recommendation**: V2 BACKLOG ITEM. Adding `#[napi(strict)]` to
every method in V2.2+ is the right call (per "Don't Be Lazy" + "no
fallbacks"). The cost is one `napi_instanceof` call per param per method
invocation — sub-microsecond, way under the engine's own call overhead.

**Why LOW not MEDIUM**: V1 already has this hazard for every method; V2.1
doesn't make it worse. Quality bar for V2.2 to systematically apply
`strict`.

`Err(CollabSessionError::Transport(TransportError::Closed))` → JS Error

the napi layer. V2.2's `transportLastError` binding will want this.

**Closure recommendation**: V2 BACKLOG ITEM. V2.2 should either bind
`Transport.close()` (extension on the napi wrapper) OR add a

## OBSERVATIONS

### OBS-1: napi-rs's `from_napi_mut_ref` returns `&'static mut T` from the raw `napi_unwrap` pointer with no runtime borrow check — V2.1 doesn't introduce re-entry vectors, but a future async addition could

**Repo**: napi-rs ecosystem.
**File:line**: `napi-derive-backend-5.0.4/src/codegen/struct.rs:131-146`.

The N-API model assumes JS single-threadedness for the borrow check.
V2.1's surface is fully synchronous so this assumption holds. V2.3's
`Transport.websocketConnect(url)` async will use `#[napi(async)]` /
`AsyncTask`; when the resulting Promise resolves, it's back on the V8
thread — no re-entry. **But**: if a future binding exposes a JS-callable
callback (e.g., a "transport status changed" hook), and that callback
fires from a tokio task → cross-thread Reference::ThreadsafeFunction →
back to JS → JS calls `session.flushToTransport()` while another
`session.*` is mid-call on the stack, napi-rs's `&'static mut` from
`napi_unwrap` would produce two aliased mutable references to the SAME
CollabSession instance. UB.

This is hypothetical for V2.1 but is the load-bearing reason the
binding's `CollabSession: Send + !Sync` claim is correct AND the IDE's
"never expose JS callbacks back into Rust" discipline matters.

OBS only because V2.1 doesn't introduce this hazard.

### OBS-2: `LoopbackTransport: Send + Sync` per
`_ASSERT_LOOPBACK_TRANSPORT_SEND_SYNC` — and the wrapper's
`Box<dyn CoreTransport + Send>` is `?Sync`, so `Transport: Send + ?Sync`
— the `!Sync` claim isn't made in the docstring but isn't needed either

The compile assert at lib.rs:667-670 only asserts Send. No Sync claim is
made for the napi `Transport` wrapper. Per Rule 4 ("negative claims need
positive proof"), this is fine because the absence of a `!Sync` claim
means no negative claim is being made. Good Rule 4 hygiene.

A FUTURE contributor adding "`Transport` is `Send + !Sync`" to the
docstring would trigger Rule 4 — and the per-field walk would show that
the trait object `dyn CoreTransport + Send` is `?Sync` (no bound), so
`Box<dyn ... + Send>: ?Sync`, so `Option<Box<...>>: ?Sync`. The wrapper
`Transport { inner: Option<Box<...>> }: ?Sync`. So `!Sync` is the
expected result — but `?Sync` would also be correct (it's the
auto-derived bound). Pinning `!Sync` would require either
`PhantomData<*const ()>` or `static_assertions::assert_not_impl_all` (the
latter has the "AmbiguousIfImpl" gotcha per audit-discipline memory).

OBS only: V2.1 didn't claim, so V2.1 doesn't owe proof.

### OBS-3: The "drop prior on attach" behavior in napi `attachTransport` is the right default for V2.1 (Loopback has no background tasks) and forward-compatible with V2.3+ (WebSocketTransport's `Drop` calls `JoinHandle::abort()` which is non-blocking)

The napi `attachTransport` body does `let _prior =
self.inner.attach_transport_boxed(boxed);` — the `_prior` is dropped at
end of function. For WebSocketTransport's `Drop` impl
(`crates/ql-collab-ws/src/lib.rs:609-637`), this calls `closed.store(true)`,
`progress.1.notify_all()`, and `writer_task.abort()` / `reader_task.abort()`
on the JoinHandles. None of these block.

The IDE's JS thread blocks for the duration of the `napi_call_function`
that triggered `attachTransport` plus the time to drop the prior box.
Drop itself is microseconds — abort signals a flag and returns. **The
async task reaping happens in the background on the tokio runtime worker
thread**, not on the V8 thread.

So V2.3 forward-compat for "drop prior" is FINE. The MEDIUM-1 about
`#[must_use]` is about the Rust-side engine API, not the napi binding's
behavior.

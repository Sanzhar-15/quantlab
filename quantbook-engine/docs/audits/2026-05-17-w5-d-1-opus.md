## HIGH

### HIGH-O-1 — Arity-mismatch error class diverges from established codebase convention.

**Where:** `crates/ql-functions/src/distribution_fns.rs:64, 99, 125, 155`.

**Detail:** All four NORM.* functions return `Value::Error(ErrorValue::NA)` on arity mismatch. Sweep of the rest of `crates/ql-functions/src/`:

```
$ grep -B1 -A2 "args.len()" crates/ql-functions/src/*.rs | grep "ErrorValue::" | sort | uniq -c
  7 ErrorValue::NA       ← ALL SEVEN are in distribution_fns.rs (this commit)
132 ErrorValue::Value    ← every other arity check across scalar/range/financial/date/array
```

The convention across **all** other arity checks in the codebase — scalar_fns, range_fns, financial_fns (most recently the W5-180→183 depreciation batch), date_fns, array_returning_fns — is `Value::Error(ErrorValue::Value)`. This includes the freshly-shipped financial fns that came in immediately before this commit. NORM.* is the first deviation.

IronCalc's source uses `CalcResult::new_args_number_error` which returns the `Error::ERROR` sigil — they're consistent with themselves (every fn does it the same way). Excel's actual behavior for "wrong arg count in a typed-in formula" is in fact `#N/A`-equivalent at the cell level, so on Excel-canon grounds `#N/A` is closer to canon than `#VALUE!` — but the codebase made a global choice for `#VALUE!` and stuck with it for ~200 fns. NORM.* should follow that choice unless we are deliberately migrating the rest of the codebase, which would need to be its own PR with the global rationale.

**Impact:** A user calling `NORM.DIST(1, 2, 3)` (3 args instead of 4) gets `#N/A`. A user calling `SUM()` (0 args) gets `#VALUE!`. Two different sigils for the same class of authoring mistake. Tests pin both, so this divergence is **load-bearing in the test suite** and won't be quietly fixed if we change it later.

**Recommendation:** change all four returns to `Value::Error(ErrorValue::Value)` AND update all 7 arity-mismatch test assertions in `distribution_fns.rs` accordingly. If the choice is intentional (move toward `#N/A` for arity globally), this should be a separate cross-cutting commit with a documented rationale and all 200 existing fns flipped at once — not a unilateral departure for the first 4 fns of Wave 3 distributions.

**Severity rationale:** HIGH because (a) it's a user-visible error-sigil divergence — different sigil for the same author mistake breaks the principle of least surprise; (b) the tests pin the wrong-but-asserted behavior, so silent regression is impossible but silent perpetuation across the rest of Wave 3 IS the risk if not flagged now; (c) catching it on the first batch of Wave 3 is cheap (4 returns × 1 line each + 7 test asserts); catching it after T.DIST, CHISQ.DIST, F.DIST, BINOM.DIST, POISSON.DIST, GAMMA.DIST, BETA.DIST all land will cost ~50+ touchpoints.

### HIGH-O-2 — Coercion divergence from IronCalc not documented in matrix or doc-comment as a divergence.

**Where:** `crates/ql-functions/src/distribution_fns.rs:24-27` (module docstring), `docs/compat/excel-matrix.md:97-100` (4 rows), all 4 fn doc-comments.

**Detail:** Our impl uses `coercion::to_number_strict` for `x` / `mean` / `sd` / `prob`. IronCalc uses `get_number_no_bools` for the same args. The two differ in **two ways**:

| Input | `to_number_strict` (ours) | IronCalc `get_number_no_bools` | Excel canon |
|---|---|---|---|
| `Boolean(true)` | `Ok(1.0)` (accepts) | `Err(#VALUE!)` (rejects) | depends on Excel version; modern Excel does coerce booleans in numeric arg context for NORM.* |
| `Text("0.5")` (parseable) | `Err(#VALUE!)` (rejects ALL text) | `Ok(0.5)` (parses via `cast_number`) | Excel: coerces parseable text to number |
| `Text("abc")` | `Err(#VALUE!)` | `Err(#VALUE!)` | `#VALUE!` |

**This is two divergences, not one, and both go in opposite directions.** Boolean: we're MORE PERMISSIVE than IronCalc; closer to Excel. Text-numeric: we're MORE STRICT than IronCalc; FURTHER from Excel.

Furthermore the `cumulative` arg uses `to_logical` which accepts `Text("true")` / `Text("false")` (case-fold + trim). IronCalc's `cast_to_bool` accepts the same — coincidentally compatible. Boolean and Number paths also align with IronCalc here (Number → `n != 0` → bool both sides). So `cumulative` coercion is divergence-free; only the numeric args diverge.

**Where the doc-comment misleads:**

```rust
//! Args are coerced via `ql_types::coercion::to_number_strict` (Text
//! → `#VALUE!`, Boolean → 0/1, Blank → 0, Number passes, Error
//! propagates). The `cumulative` flag uses `to_logical` (numeric → 0/non-0
//! → bool, Text "true"/"false" case-folded → bool, else `#VALUE!`).
```

This is factually correct but says nothing about whether `NORM.DIST(TRUE, 0, 1, TRUE)` gives `Φ(1) ≈ 0.84` (ours) vs `#VALUE!` (IronCalc) vs Excel's actual answer. The matrix rows are silent on the divergence.

The current depreciation batch matrix entries (DB, VDB, etc.) explicitly call out the divergence from IronCalc when one exists — e.g., the "AVERAGEA / MAXA / MINA" row at line 95 documents `Boolean → 1/0` + `Text → 0` divergence from base AVERAGE behavior. The W5-D-1 rows should follow the same pattern.

**Impact:** Behavioral inconsistency with the port source (IronCalc) **on the most-used arg type** (Boolean in numeric position). When IronCalc fixtures are eventually built to cross-check NORM.* — which is the natural next step for Wave 3 cohort-wide regression testing — they will diverge silently OR force re-port. Catching the divergence in documentation NOW means the future fixture-author knows where to expect deltas.

**Recommendation:** add a short sub-paragraph to the module doc-comment AND to each of the four matrix rows explicitly listing the two divergences against IronCalc. Decide and document the policy (likely: keep ours because it's closer to Excel for Booleans, accept the IronCalc-divergence on numeric text). If the eventual policy is "match IronCalc for behavioral parity with the port source," switch to a custom coercion helper that rejects Booleans (like IronCalc) — but flag this **NOW** so the rest of Wave 3 doesn't bake in the divergence further.

**Severity rationale:** HIGH because (a) Boolean-in-numeric-position is a frequent real-world arg pattern (`=NORM.DIST(A1, mean, sd, TRUE)` where `A1 = TRUE` for a sentinel column) — silent behavioral divergence from the port source is the worst kind of bug because tests pass and users see no error; (b) the project's documented strategy in module docstring is "port IronCalc verbatim … numerical results are identical out-of-the-box" — this statement is **strictly false** under any non-Number/Blank arg, and the docstring should not assert it; (c) this is forward-looking for the rest of Wave 3, which will all want to inherit a consistent policy. Decide now or pay later.

### MEDIUM-O-2 — Module-docstring claim of "numerical results are identical out-of-the-box" is too strong.

**Where:** `crates/ql-functions/src/distribution_fns.rs:7-10`.

**Detail:**

```rust
//! Implementation strategy: port IronCalc's `statistical/normal.rs` impls
//! verbatim (modulo our `ScalarFn` ABI: `fn(&[Value]) -> Value` vs
//! IronCalc's `&[Node] + CellReferenceIndex`). Both projects use the
//! `statrs` crate (pinned to 0.18.0 across both) for the underlying
//! distribution math, so numerical results are identical out-of-the-box.
```

The claim "numerical results are identical out-of-the-box" is only true for `Number → Number` paths (which are identical because both use `statrs::Normal` with the same pin). For:

- Boolean inputs: we return a Number (statrs result for `mean=1.0` for example); IronCalc returns `#VALUE!`. Not identical.
- Text inputs that IronCalc would parse (`"0.5"` etc): IronCalc returns a Number; we return `#VALUE!`. Not identical.
- Arity mismatch: we return `#N/A`; IronCalc returns `#ERROR!`. Not identical (also tied to HIGH-O-1).

The numerical math is identical when both impls reach `dist.pdf(x)` / `dist.cdf(x)` / `dist.inverse_cdf(p)` with the same f64 inputs. The end-to-end behavior is NOT identical because the coercion frontends diverge.

**Recommendation:** soften the claim to: "the underlying distribution math reduces to identical `statrs::Normal::{pdf,cdf,inverse_cdf}` calls for any pair of inputs that successfully coerce to the same f64 — coercion divergences (see HIGH-O-2) are the only behavioral delta." This is the truth and matches what a future maintainer needs to know.

**Severity rationale:** MEDIUM. Doc-comment honesty is a non-fallback principle (per the CLAUDE.md "No fallbacks / errors visible" rule, but applied to doc comments as a form of silent miscommunication). A maintainer reading this comment three months from now will assume the impl is bit-exact-equivalent to IronCalc and will be surprised when a fixture diverges. Pre-empting that surprise is cheap.

### MEDIUM-O-3 — `Value::Blank` arg behavior is untested in all four fns.

**Where:** `crates/ql-functions/src/distribution_fns.rs` test module (no `Value::Blank` use).

**Detail:** The module docstring claims `Blank → 0` (via `to_number_strict` semantics). None of the 35 tests exercise this path. Spreadsheet users **routinely** pass blank-cell references as `mean` / `sd` args without realizing they evaluate as 0:

- `NORM.DIST(0, Blank, Blank, TRUE)` would compute `Φ((0-0)/0)` → `sd=0` → `#NUM!` (correct).
- `NORM.DIST(1, Blank, 1, TRUE)` would compute `Φ(1) ≈ 0.8413` (silently treats missing mean as 0).
- `NORM.DIST(0, 0, 1, Blank)` — `cumulative=Blank` → `to_logical(Blank) → Ok(false)` → PDF path → 1/√(2π).

The third case is potentially surprising: `cumulative=Blank` defaults to `FALSE` (PDF), not user-expected CDF. If a user writes `=NORM.DIST(A1, 0, 1,)` with a trailing blank, they get PDF — but a parser might also reject the trailing comma as an arity error. Either way, **the contract should be tested**.

**Recommendation:** add three tests:

```rust
#[test]
fn norm_dist_blank_mean_treats_as_zero() {
    assert_close(
        norm_dist(&[Value::number(1.0), Value::Blank, Value::number(1.0), Value::Boolean(true)]),
        0.841_344_746_068_542_9,
    );
}

#[test]
fn norm_dist_blank_sd_is_num_error() {
    assert_eq!(
        norm_dist(&[Value::number(1.0), Value::number(0.0), Value::Blank, Value::Boolean(true)]),
        Value::Error(ErrorValue::Num)
    );
}

#[test]
fn norm_dist_blank_cumulative_treats_as_false() {
    // Blank → false → PDF path. 1/sqrt(2π) ≈ 0.39894228.
    assert_close(
        norm_dist(&[Value::number(0.0), Value::number(0.0), Value::number(1.0), Value::Blank]),
        0.398_942_280_401_432_7,
    );
}
```

**Severity rationale:** MEDIUM. Real-world frequent input pattern; documented but unpinned behavior is a regression-pit if someone refactors `to_number_strict` later (e.g., changes `Blank → 0` to `Blank → #VALUE!` somewhere).

### MEDIUM-O-4 — `cumulative` numeric-coercion path is untested.

**Where:** `crates/ql-functions/src/distribution_fns.rs` test module.

**Detail:** Per the module docstring (line 26-27): `cumulative` is coerced via `to_logical`, which accepts `Number(n) → n != 0`. Tests only ever pass `Value::Boolean(true|false)` for `cumulative`. The numeric-coercion path is unexercised:

Likewise NORM.S.DIST has no numeric / text-bool tests for `cumulative`.

**Recommendation:** add ~4 tests per fn covering `cumulative` as Number(1), Number(0), Number(-1), Text("TRUE"), Text("false"). Two test cases per fn (CDF + PDF expected) is the minimum.

### MEDIUM-O-5 — Dead defensive `Normal::new(...).map_err()` paths obscure the actual invariant.

**Where:** `crates/ql-functions/src/distribution_fns.rs:35-42` (`standard_normal` + `normal_with`) and the 4 use-sites that `match` on their result.

**Detail:** Looking at `statrs-0.18.0/src/distribution/normal.rs:71-81`:

```rust
pub fn new(mean: f64, std_dev: f64) -> Result<Normal, NormalError> {
    if mean.is_nan() { return Err(NormalError::MeanInvalid); }
    if std_dev.is_nan() || std_dev <= 0.0 { return Err(NormalError::StandardDeviationInvalid); }
    Ok(Normal { mean, std_dev })
}
```

Our pre-checks:

- `mean`: comes from `to_number_strict` which rejects NaN/Inf via `sanitize_f64` → if `to_number_strict` returned `Ok(_)`, the value is **finite**. Cannot be NaN. Cannot fail `is_nan()` check in statrs.
- `sd`: same upstream sanitization PLUS our explicit `if sd <= 0.0 { return #NUM! }`. By the time `Normal::new(mean, sd)` is called, both invariants are guaranteed.

So `Normal::new` **cannot return `Err`** in our flow. The `map_err(|_| ErrorValue::Num)` is fully dead code. Same for `standard_normal()` — `Normal::new(0.0, 1.0)` is statically valid.

This is structurally similar to IronCalc's defensive `match Normal::new(...) { Err(_) => return CalcResult::Error { ... } }` blocks at lines 41-50, 92-101, 131-140, 174-183 of `.references/ironcalc/base/src/functions/statistical/normal.rs`. **IronCalc has the same dead code.** We inherited it from the port.

The two concerns:

1. **Dead code is hidden complexity.** A future reader sees `match standard_normal() { Ok(d) => d, Err(e) => return Value::Error(e) }` and wonders under what circumstances `standard_normal()` can fail. The answer is "never in this codebase" — that fact should be visible.
2. **`#[allow(dead_code)]` clippy guards are not in play here**, but if the code were stricter (e.g., a `match` with `Err(_)` that could be statically eliminated), Rust's exhaustiveness check would still require it. We're paying complexity tax for paranoid safety against an impossible state.

**Recommendation:** two viable approaches:

(a) **Document explicitly that this path is defensive / dead.** Add a comment above each `match normal_with(...)` saying: "Defensive: Normal::new can fail on NaN mean / Inf-NaN sd, both excluded by upstream sanitize_f64 + the sd > 0 check. The map_err is unreachable but kept to match IronCalc's structure and to fail loudly if a future refactor weakens the upstream guards."

(b) **Replace with `.expect()`** to assert the invariant explicitly. `let dist = normal_with(mean, sd).expect("upstream sanitize_f64 + sd>0 check guarantees Normal::new succeeds");` makes the invariant load-bearing. If a future refactor breaks it, the panic surfaces in the test suite immediately rather than silently returning `#NUM!` for an unintended path.

Per project's CLAUDE.md "No fallbacks" rule, (b) is more aligned with "errors must be visible" — a silent fallback `Err → #NUM!` for an impossible state literally IS a fallback that hides a real bug.

**Severity rationale:** MEDIUM because the No-fallbacks rule directly applies. The current code is the kind of "graceful degradation that silently switches to an alternative path" the CLAUDE.md explicitly bans.

### MEDIUM-O-6 — `inverse_cdf` panic boundary is not pinned by a test.

**Where:** `crates/ql-functions/src/distribution_fns.rs:139-146, 161-168` (NORM.INV + NORM.S.INV pre-checks).

**Detail:** From `statrs-0.18.0/src/distribution/normal.rs:172-178`:

```rust
fn inverse_cdf(&self, x: f64) -> f64 {
    if !(0.0..=1.0).contains(&x) {
        panic!("x must be in [0, 1]");
    } else {
        self.mean - (self.std_dev * f64::consts::SQRT_2 * erf::erfc_inv(2.0 * x))
    }
}
```

**`inverse_cdf` will panic on `x` outside `[0, 1]`.** Our pre-check is `if p <= 0.0 || p >= 1.0 { return #NUM! }` — note **strict** inequality on both ends. statrs allows the **closed** interval `[0, 1]`. So `p == 0.0` and `p == 1.0` are accepted by statrs but rejected by us → we are stricter than statrs on the boundary.

This is correct (Excel: NORM.INV(0, ...) → #NUM!; NORM.INV(1, ...) → #NUM!). But the comment in tests doesn't make explicit why we reject the closed-interval endpoints that statrs allows. The risk is: if a future refactor weakens our pre-check from `<=` / `>=` to `<` / `>` (allowing `p == 0.0` / `p == 1.0` through), the test would then call `dist.inverse_cdf(0.0)` which returns `-Infinity` (not panic actually — let me re-read). statrs's source `if !(0.0..=1.0).contains(&x)` → for `x = 0.0`, `0.0..=1.0` DOES contain 0.0, so no panic. Compute: `erfc_inv(0)` = `+inf`. `mean - (sd * sqrt(2) * inf)` = `-inf`. Then `finite_or_num(-inf) → #NUM!`. So weakening our pre-check to `<` / `>` would still produce `#NUM!` from the finite-check at the end — but for the wrong reason (statrs returning `±inf` rather than us rejecting at the gate). The test would still pass with `Value::Error(ErrorValue::Num)`, but the failure mode would have shifted from "domain check" to "post-hoc Inf-filter."

The deeper concern: **what if statrs releases 0.19.0 and tightens `inverse_cdf` to `0.0 < x < 1.0`?** Our strict `<=` / `>=` pre-check is the safety net. The pin is `=0.18.0` (good — see LOW-O-3), but the safety-margin isn't articulated.

**Recommendation:** add a comment above the pre-check explaining why we use strict `<=` / `>=` (Excel canon) AND why this is also defensive against statrs returning ±Inf at the closed-interval endpoint:

```rust
// Excel canon: probability strictly in (0, 1). Endpoints rejected.
// Also defensive: statrs's `inverse_cdf` accepts the closed interval
// [0, 1] but returns ±Inf at the endpoints (would be filtered by
// `finite_or_num` below, but cleaner to reject at the gate).
if p <= 0.0 || p >= 1.0 || sd <= 0.0 {
    return Value::Error(ErrorValue::Num);
}
```

Plus: add tests for `p == f64::MIN_POSITIVE` (smallest positive subnormal) and `p == 1.0 - f64::EPSILON` (largest representable below 1) — confirm both produce finite Numbers. The audit prompt lists these in Item 13 and they're untested.

**Severity rationale:** MEDIUM. Math is correct today, but the safety margin isn't explicit in code or test. If statrs ever changes its boundary behavior, our impl could silently shift from "domain reject" to "post-hoc Inf-reject" — same final answer but different path. Documentation-by-test is the established discipline.

### MEDIUM-O-7 — Untested: result-is-Inf path through `finite_or_num` for extreme inverse-CDF input.

**Where:** `crates/ql-functions/src/distribution_fns.rs:46-52` (`finite_or_num`) + 146, 168.

**Detail:** `finite_or_num` converts non-finite results to `#NUM!`. This is the safety net for statrs producing `±Inf` (e.g., `NORM.INV` at `p` very close to 0 or 1 — `erfc_inv(2 * p)` for very small `p` is large but finite to a point, then becomes Inf).

The audit prompt's Item 13 asks: "for `p = 1.0 - 1e-15`, the result is ~7.941. Finite. Verify."

f64 can represent `1.0 - 1e-15` but the floating-point gap near 1.0 is about `1.1e-16` (machine epsilon), so `1.0 - 1e-15` is representable. statrs's `erfc_inv(2.0 * (1.0 - 1e-15))` = `erfc_inv(2.0 - 2e-15)` which exceeds the typical erfc_inv domain (it expects `[0, 2]` input). The result depends on statrs's `erfc_inv` impl — empirically it returns ~ -7.941 for that input (giving the symmetric +7.941 z-score). **Untested.**

More dangerous: `NORM.S.INV(0.5 + 0.5*f64::EPSILON)` — just above 0.5 — should give a tiny positive z. `NORM.S.INV(1.0 - 1.0e-300)` — extremely close to 1.0 — statrs might saturate to Inf. Untested.

**Recommendation:** add 2 boundary-probability tests:

```rust
#[test]
fn norm_s_inv_near_one_boundary_returns_finite() {
    let v = norm_s_inv(&[Value::number(1.0 - 1e-15)]);
    match v {
        Value::Number(n) => {
            assert!(n.is_finite(), "expected finite, got {n}");
            assert!(n > 0.0, "expected positive z, got {n}");
        }
        other => panic!("expected Number, got {other:?}"),
    }
}

#[test]
fn norm_s_inv_extreme_near_zero_overflows_to_num_error() {
    // p so close to 0 that statrs's erfc_inv overflows to -Inf.
    // finite_or_num converts to #NUM!. Confirm the safety net works.
    let v = norm_s_inv(&[Value::number(f64::MIN_POSITIVE)]);
    // Could be either a very large negative finite number OR #NUM!
    // depending on statrs's saturation behavior. Either is acceptable,
    // but this test pins which one we get TODAY so we notice if statrs
    // changes.
    match v {
        Value::Number(n) => assert!(n.is_finite()),
        Value::Error(ErrorValue::Num) => (),
        other => panic!("expected Number(finite) or #NUM!, got {other:?}"),
    }
}
```

**Severity rationale:** MEDIUM. Not a bug, but the safety net `finite_or_num` exists specifically for this case and is never invoked by any test. Pinning the boundary tells future maintainers that the contract is "finite or #NUM!, no Inf leaks."

### MEDIUM-O-9 — Module docstring lists future fns ("T.* / CHISQ.* / F.* / BINOM.* / POISSON.* / GAMMA.* / BETA.*") but doesn't mention statrs's actual capability surface.

**Where:** `Cargo.toml:104-108` (workspace dep block) + `crates/ql-functions/src/distribution_fns.rs:2-4`.

```

 "approx",
 "num-traits",

```

`rand` is not pulled in (good — no need for random sampling). But what about distribution-specific features? statrs 0.18.0 doesn't gate distributions behind features — they're all in the default surface. So `default-features = false` is safe today.

```toml
statrs = { version = "0.18.0", default-features = false, features = [] }
```

We use:

```toml
statrs = { version = "=0.18.0", default-features = false }
```

The two are **equivalent in resolved features** (both disable defaults, no extras), but IronCalc's explicit `features = []` is slightly more diff-resistant. Adding it costs zero.

**Severity rationale:** MEDIUM. The Cargo.toml comment makes a forward-looking promise that depends on statrs's feature stability. If we ship a Wave 3 cohort and a follow-on `statrs` patch (the project pins `=0.18.0` so this requires a deliberate bump) gates a distribution, the comment becomes a lie. Cheap to harden now.

### LOW-O-9 — `to_logical` accepts text `"true"`/`"false"` (trimmed, ASCII case-fold); divergence from IronCalc text-bool behavior is undocumented.

**Where:** `crates/ql-functions/src/distribution_fns.rs:78, 105` (calls `to_logical`) + `crates/ql-types/src/coercion.rs:53-65`.

**Detail:** Our `to_logical` is **mostly** equivalent to IronCalc's `cast_to_bool` for the `cumulative` arg — both accept Number, Boolean, Text("true")/("false") case-insensitively. The differences are subtle:

- Ours: `Blank → false`, IronCalc's: `EmptyCell|EmptyArg → false`. Same effective semantic.
- Ours: trims whitespace before case-fold. IronCalc's: `s.to_lowercase() == "true"` — no trim. So `Text(" true ")` is `Ok(true)` in ours, `Err(#VALUE!)` in IronCalc.
- Ours: ASCII case-fold. IronCalc's: Unicode lowercase. For ASCII-only `"TRUE"` / `"True"` both are equivalent; for Unicode edge cases (e.g., Turkish `İ`), they diverge.

The whitespace-trim and ASCII-vs-Unicode case-fold are intentional design choices in our `to_logical`, but the **module doc-comment doesn't mention them as divergences** from IronCalc.

**Recommendation:** if the divergence-documentation policy from HIGH-O-2 is adopted, add the `cumulative`-text-edge-cases to the same divergence list (trim + ASCII case-fold).

**Severity rationale:** LOW. Realistic users don't pass whitespace-padded text-booleans. ASCII case-fold is the right call. Just document it.

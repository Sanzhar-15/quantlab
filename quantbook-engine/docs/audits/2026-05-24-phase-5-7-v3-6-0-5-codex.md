# Phase 5.7 V3.6.0.5 D4 Codex Audit

Audit date: 2026-05-24  
Scope: format-aware buildHtml rendering via `CellSnapshotJson.rendered`, `WorkbookSnapshotJson.dateSystem`, and IDE `buildHtml` consumption  
Engine target: shipped D4 surface at `5b3017c70d2`  
IDE target: shipped D4 surface at `d7cb01557d4`

## Verdict

FAIL

D4's basic formatted-rendering happy path works, and the IDE escaping path is sound. However, the date-system contract is not actually preserved for collab sessions loaded from `.qbook`: `workbookSnapshot().dateSystem` is effectively `Excel1900` unless a future op-log metadata op exists. That makes Excel1904 date-rendered cells display with the wrong epoch and can resave a loaded Excel1904 workbook as Excel1900.

I confirmed one HIGH correctness bug, two MEDIUM issues, and three LOW issues.

## Summary

- Engine-side percent rendering works in the core pipeline: `RegisterFormat("0.00%") + SetCellFormat + PutValue(0.5)` renders `"50.00%"`.
- `workbookSnapshot` builds its render `EvalContext` from the rebuilt workbook at `crates/ql-bindings-node/src/lib.rs:1653`, but `fromQbook` discards the loaded `Workbook` and keeps only the op log at `crates/ql-bindings-node/src/lib.rs:1897`.
- `CellWireValue::Pending` is converted to `Value::Blank` at `crates/ql-oplog/src/wire.rs:111`; D4 then routes it through numeric/date formats and can display `"0.00"` instead of the IDE's previous `"(pending)"`.
- Server and client HTML paths both escape the final rendered/fallback string before `innerHTML`: server at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:229` and `:257`, client at `:622` and `:631`.
- The current mocha tests pin shape only, not a rendered-present value.

## HIGH findings

1. HIGH-1: `dateSystem` is effectively constant under op-log replay / `fromQbook`, so Excel1904 date rendering is wrong.

   Scope: `.qbook` load, `workbookSnapshot().dateSystem`, date-format rendering, save-back metadata.

   Evidence:

   - `.qbook` loading preserves the envelope date system in the loaded `Workbook` at `crates/ql-io/src/qbook_format.rs:1659` through `crates/ql-io/src/qbook_format.rs:1664`; ql-io already has an Excel1904 round-trip test at `crates/ql-io/src/qbook_format.rs:3062`.
   - The binding's `fromQbook` immediately discards that loaded workbook: `let (_workbook, oplog) = ...` at `crates/ql-bindings-node/src/lib.rs:1897`.
   - It reconstructs the session solely from `oplog.export_bytes()` via `CoreCollabSession::from_snapshot` at `crates/ql-bindings-node/src/lib.rs:1908` through `crates/ql-bindings-node/src/lib.rs:1912`.
   - The op enum has workbook-scope `SetReferenceMode` and `SetLocale`, but no `SetDateSystem`, at `crates/ql-oplog/src/op.rs:397` through `crates/ql-oplog/src/op.rs:413`.
   - `workbookSnapshot` reads the date system from the rebuilt op-log workbook at `crates/ql-bindings-node/src/lib.rs:1653` and returns it at `crates/ql-bindings-node/src/lib.rs:1834`.
   - `toQbook` also saves the rebuilt op-log workbook at `crates/ql-bindings-node/src/lib.rs:1575` through `crates/ql-bindings-node/src/lib.rs:1585`, so the same metadata loss can persist back to disk.

   Empirical confirmation:

   - A temporary core-pipeline probe saved a `.qbook` whose loaded workbook had `DateSystem::Excel1904`, then replayed only the loaded op log, matching `fromQbook`'s implementation. The replayed workbook reported `Excel1900`, and a serial `1.0` with `yyyy-mm-dd` rendered as `"1900-01-01"` instead of the Excel1904 date.

   Impact:

   Excel1904 workbooks render date-formatted cells roughly four years off. `Workbook::set_date_system` documents a 1462-day shift at `crates/ql-storage/src/workbook.rs:402` through `crates/ql-storage/src/workbook.rs:406`, so this is not cosmetic. It also means the new `WorkbookSnapshotJson.dateSystem` field gives consumers a false sense that date epoch is faithfully propagated.

   Suggested closure:

   Add an op-log representation for workbook date system, e.g. `Op::SetDateSystem { system: DateSystemWire }`, replay it into `Workbook::set_date_system`, and have `fromQbook` seed that op when the loaded workbook carries non-default metadata not already represented in the log. Add a regression that loads/saves an Excel1904 `.qbook` with a date-formatted serial and asserts both `dateSystem === "Excel1904"` and the rendered string match Excel1904.

## MEDIUM findings

1. MEDIUM-1: Pending cells with a format render as formatted blank/zero instead of staying pending.

   Scope: formula-pending values, `CellSnapshotJson.rendered`, IDE display semantics.

   Evidence:

   - D4 renders whenever `state.format` and `state.value` are both present at `crates/ql-bindings-node/src/lib.rs:1747` through `crates/ql-bindings-node/src/lib.rs:1765`; there is no `CellWireValue::Pending` filter.
   - `CellWireValue::Pending` decodes to `Value::Blank` at `crates/ql-oplog/src/wire.rs:111` through `crates/ql-oplog/src/wire.rs:125`.
   - The formatter treats `Value::Blank` as `0.0` for number sections at `crates/ql-functions/src/format/render.rs:202` through `crates/ql-functions/src/format/render.rs:207` and date sections at `crates/ql-functions/src/format/render.rs:520` through `crates/ql-functions/src/format/render.rs:525`.
   - The IDE fallback would display pending explicitly at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:278`, but D4 prefers `rendered` at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:229`.

   Empirical confirmation:

   - A temporary core-pipeline probe appended `SetCellFormat(Builtin(2) = "0.00")` and `PutValue(Pending)`. The D4-equivalent render path returned `Some("0.00")`.

   Impact:

   A not-yet-computed formula can look like a real numeric zero. That is worse than falling back because it fabricates a computed-looking value while the cell value kind remains pending.

   Suggested closure:

   Treat `CellWireValue::Pending` like "no evaluated value" in the D4 pipeline: return `rendered = None` before `to_value()`. Add a regression with `Pending + "0.00"` asserting `rendered` is absent and IDE fallback remains `"(pending)"`.

2. MEDIUM-2: The shipped tests do not exercise the actual rendered-present integration path.

   Scope: ql-bindings-node coverage, IDE mocha coverage, D4 regression risk.

   Evidence:

   - The D4 mocha tests explicitly document that they only pin shape because no `appendSetCellFormat` / `appendRegisterFormat` napi methods exist at `extensions/quantlab/test/quantbook-roundtrip.test.ts:5701` through `extensions/quantlab/test/quantbook-roundtrip.test.ts:5712`.
   - The existing ql-bindings-node unit tests cover only version, core session round-trip, and transport plumbing at `crates/ql-bindings-node/src/lib.rs:2983` through `crates/ql-bindings-node/src/lib.rs:3070`.
   - A direct Rust unit probe calling the napi `workbook_snapshot()` method failed to link outside a Node host with unresolved `_napi_delete_reference` / `_napi_reference_unref`, matching the crate's own comment about napi wrapper testing limits at `crates/ql-bindings-node/src/lib.rs:3025` through `crates/ql-bindings-node/src/lib.rs:3036`.

   Impact:

   The core feature shipped without a compiled regression asserting `rendered === "50.00%"`. The two correctness bugs above were not catchable by shape-only tests.

   Suggested closure:

   Factor the snapshot construction into a non-napi helper, e.g. `build_workbook_snapshot_json(inner: &CoreCollabSession) -> Result<WorkbookSnapshotJson, CollabSessionError>`, and have the napi method only map errors. Then add Rust tests for percent, date, pending, malformed format fallback, and HTML-sensitive rendered strings. Separately, add `appendRegisterFormat` and `appendSetCellFormat` napi methods when the IDE write-path is ready so mocha can pin end-to-end behavior.

## LOW findings

1. LOW-1: `EvalContext.locale` is hardcoded to EN-US despite workbook locale being op-log replayable.

   Scope: localized workbooks, future locale-aware format rendering.

   Evidence:

   - `workbookSnapshot` sets `locale: ql_types::Locale::EnUs` at `crates/ql-bindings-node/src/lib.rs:1654` through `crates/ql-bindings-node/src/lib.rs:1657`.
   - `Workbook` exposes `locale()` and `set_locale()` at `crates/ql-storage/src/workbook.rs:436` through `crates/ql-storage/src/workbook.rs:450`.
   - `Op::SetLocale` replays into `workbook.set_locale(loc)` at `crates/ql-oplog/src/replay.rs:858` through `crates/ql-oplog/src/replay.rs:866`.
   - V3.6 documents locale-aware format rendering as out of scope at `.plans/_active.md:318`, so this is a known limitation rather than a surprise crash.

   Impact:

   Non-EN workbooks cannot get locale-correct formatted display through D4. Current `format::render` still hardcodes English month/weekday names, so the immediate blast radius is limited; the binding should not bake in the wrong source once renderer locale support lands.

   Suggested closure:

   Change the D4 EvalContext to `locale: workbook.locale()` and add a regression using `Op::SetLocale`. If the renderer remains EN-only, document the renderer limitation there rather than forcing EN-US at the napi boundary.

2. LOW-2: D4 parses and clones the format string per formatted cell per snapshot call.

   Scope: `workbookSnapshot` performance under formatted large sheets / multi-panel polling.

   Evidence:

   - The render pipeline clones `fmt_str.to_string()` and calls `ql_functions::format::parse(&fmt_string)` for each cell at `crates/ql-bindings-node/src/lib.rs:1754` through `crates/ql-bindings-node/src/lib.rs:1761`.
   - The field doc acknowledges per-cell parse cost at `crates/ql-bindings-node/src/lib.rs:587` through `crates/ql-bindings-node/src/lib.rs:589`.
   - The IDE panel calls `workbookSnapshot()` on every render at `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:682` through `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:684`, with the per-render cost caveat at `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:667` through `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:673`.

   Impact:

   Correctness is unaffected, but a workbook with many formatted cells and several open panels pays repeated parse cost on every poll/render. The current implementation is acceptable for V3.6 scale, but it should be profiled before calling D4 performance closed.

   Suggested closure:

   Cache parsed `FormatString` by `FormatId` for the duration of one `workbookSnapshot()` call at minimum. If profiling shows repeated calls dominate, promote that cache onto `CollabSession` and invalidate it on `RegisterFormat`.

3. LOW-3: D4 docs/contract drift remain after ship.

   Scope: consumer docs and source comments.

   Evidence:

   - TS JSDoc references `WorkbookSnapshotJson.date_system` even though the JS field is `dateSystem` at `extensions/quantlab/src/quantbook/types.ts:123` through `extensions/quantlab/src/quantbook/types.ts:126`.
   - `ide-consumer-contract.md` still says format-aware rendering is deferred at `docs/architecture/ide-consumer-contract.md:1468`, marks R-V3.5-4 as merely documented at `docs/architecture/ide-consumer-contract.md:1542`, and lists format-aware rendering as out of scope at `docs/architecture/ide-consumer-contract.md:1550`.
   - The older `workbookSnapshot` docstring still says the rebuilt workbook is discarded after sheet metadata extraction at `crates/ql-bindings-node/src/lib.rs:1598` through `crates/ql-bindings-node/src/lib.rs:1605`, which is stale now that formulas, formats, rendered strings, and date system use the rebuilt workbook.
   - `.plans/_active.md` still mentions a likely `DateSystemJson` enum in the D4 decision body at `.plans/_active.md:169`, while the implementation shipped a string field.

   Impact:

   Consumers reading the docs see the wrong shape name and may think R-V3.5-4 is still open/closed in the wrong place. This is not runtime-breaking, but it undermines the exact contract D4 added.

   Suggested closure:

   Add a V3.6.0.5 D4 subsection to `ide-consumer-contract.md`, mark R-V3.5-4 CLOSED with the pending audit caveats, fix `date_system` to `dateSystem`, and update the binding docstrings to describe the rebuilt workbook as the source for sheet metadata, repaired formulas, formats, rendering, and date system.

## INFO findings

1. INFO-1: CSP escaping is correct for rendered strings.

   Evidence:

   - Server path chooses `e.rendered ?? formatCellValue(e.value)` at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:229` and escapes it in both the attribute and cell body at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:253` through `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:257`.
   - Client path mirrors the same choice at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:622` and uses `htmlEscape` before `innerHTML` at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:631` through `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:635`.
   - The JSON data block also guards `</script>` termination at `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:126` through `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:129`.

2. INFO-2: Silent fallback for unregistered format ids and unknown error sigils is mostly unreachable on well-formed visible cells.

   Evidence:

   - Replay rejects unregistered `SetCellFormat` ids at `crates/ql-oplog/src/replay.rs:747` through `crates/ql-oplog/src/replay.rs:755`.
   - Replay decodes `PutValue` through `CellWireValue::to_value()` and returns `ReplayError::ValueDecode` on unknown error sigils at `crates/ql-oplog/src/replay.rs:418` through `crates/ql-oplog/src/replay.rs:420`.
   - `workbookSnapshot` calls `rebuild_workbook` before rendering at `crates/ql-bindings-node/src/lib.rs:1641` through `crates/ql-bindings-node/src/lib.rs:1644`.

   Note:

   The silent branches in the D4 render code are still questionable as invariant masking if the cache and rebuilt workbook diverge, but normal malformed-op paths fail before rendering.

3. INFO-3: `NowProvider::System` is currently not a practical nondeterminism source for format rendering.

   Evidence:

   - The D4 comment says format strings can reference NOW/TODAY at `crates/ql-bindings-node/src/lib.rs:1649` through `crates/ql-bindings-node/src/lib.rs:1652`.
   - Current `format::render` date sections convert the cell value serial via `serial_to_ymd(serial, ctx.date_system)` at `crates/ql-functions/src/format/render.rs:545` through `crates/ql-functions/src/format/render.rs:549`; it does not call volatile functions.

   Note:

   Tests for volatile functions still need `NowProvider::Test`, but D4 format rendering itself did not show clock nondeterminism in this code path.

4. INFO-4: Rule 4 remains satisfied.

   Evidence:

   - `CellSnapshotJson.rendered: Option<String>` at `crates/ql-bindings-node/src/lib.rs:590` and `WorkbookSnapshotJson.date_system: String` at `crates/ql-bindings-node/src/lib.rs:704` are additive fields on existing napi objects.
   - Both are Send + Sync by primitive/String composition; no new top-level Arc terminus is introduced.

## Coverage gaps identified

- No engine-side permanent regression for `RegisterFormat + SetCellFormat + PutValue -> rendered == "50.00%"`.
- No permanent regression for `dateSystem == "Excel1904"` or Excel1904 date rendering.
- No pending-value regression ensuring `CellWireValue::Pending` does not produce formatted zero/date output.
- No rendered-present mocha test because the IDE napi lacks `appendRegisterFormat` / `appendSetCellFormat`.
- No rendered re-render tests for value change, format change, or format clear.
- No malformed-format test proving fallback is intentional and visible to diagnostics.
- No coverage for boolean + numeric/date formats.
- No HTML-sensitive rendered-string test at the IDE boundary.
- No profiling or microbench for post-D4 `workbookSnapshot` parse/render cost.

## 1. Parser cell-grammar correctness

### 1a. Unary `-` followed by non-Number (e.g. `-TRUE` or `-#REF!`)

**PASS.**

`parse_array_cell` consumes `Token::Op(Operator::Minus)` then immediately calls `self.advance()`. If the next token is anything other than `Token::Number`, the `Some(other)` arm fires:

```rust
// parser.rs:535-537
Some(other) => Err(ParseError::InvalidArrayCellToken {
    got: format!("Op(Minus) followed by {other:?}"),
}),
```

`-TRUE` would arrive as `Op(Minus)` then `Ident("TRUE")` — correctly rejected with `InvalidArrayCellToken`. `-#REF!` arrives as `Op(Minus)` then `Error(Ref)` — same arm, also rejected. Both cases are correct per design § 3.3 (only unary-signed-NUMBER is allowed).

### 1b. Plus path symmetry (`+5`)

**PASS.**

The `Token::Op(Operator::Plus)` arm is exactly symmetric to `Minus`. `+TRUE` → `InvalidArrayCellToken { got: "Op(Plus) followed by Ident(\"TRUE\")" }`. `+5` → `Expr::Number(5.0)`. Correct.

### 1c. TRUE/FALSE in mixed case (`tRuE`, `False`)

**PASS.**

The `Token::Ident(name)` arm calls `name.to_ascii_uppercase()` and tests `== "TRUE"` / `== "FALSE"`:

```rust
// parser.rs:552-563
Token::Ident(name) => {
    let upper = name.to_ascii_uppercase();
    if upper == "TRUE" { Ok(Expr::Bool(true)) }
    else if upper == "FALSE" { Ok(Expr::Bool(false)) }
    else { Err(ParseError::InvalidArrayCellToken { ... }) }
}
```

`tRuE` → `to_ascii_uppercase()` → `"TRUE"` → `Expr::Bool(true)`. `False` → `"FALSE"` → `Expr::Bool(false)`. The parser test `parse_array_literal_false_lowercase_bool` covers `{true, false}` but not mixed-case. The logic is provably correct by inspection, but test coverage of mixed-case (e.g. `{tRuE}`) is absent.

### 1d. String literals with embedded quotes (`"a""b"`) in array cells

**PASS.**

`parse_array_cell` has a `Token::String(s) => Ok(Expr::String(s))` arm. The string token is produced by the lexer's `lex_string` function which unescapes `""` to `"` before the parser sees it. The round-trip direction (print) uses `print_string_literal` which re-escapes `"` to `""`. Both directions handle this correctly and this is covered by the existing string-literal test infrastructure. No array-specific issue here.

### 1e. `{}` (empty literal) → `EmptyArrayLiteral`

**PASS.**

`parse_array_literal` peeks for `Token::RBrace` as the very first check:

```rust
// parser.rs:466-469
if matches!(self.peek(), Some(Token::RBrace)) {
    self.advance();
    return Err(ParseError::EmptyArrayLiteral);
}
```

The `parse_array_literal_empty_rejects` test covers this. Error is `EmptyArrayLiteral`, not `UnexpectedEnd` or `InvalidArrayCellToken`. Correct.

### 1f. `{1, 2, }` (trailing comma)

**PASS (behavior), MEDIUM (no test, error message is opaque).**

After consuming `1` and `2`, the `while let Some(Token::Comma)` loop fires on the trailing `,`, advances past it, then calls `parse_array_cell()`. Inside `parse_array_cell`, `advance()` returns `Some(Token::RBrace)`, which hits the fallthrough arm:

```rust
// parser.rs:564-567
other => Err(ParseError::InvalidArrayCellToken {
    got: format!("{other:?}"),
}),
```

Result: `InvalidArrayCellToken { got: "RBrace" }`. This is a rejection (correct), but the error message is opaque — a user reading `"invalid array-cell token in array literal: RBrace"` won't understand they left a trailing comma. Not a correctness bug, but an ergonomics gap. No test exists for this case.

**Severity: LOW** — error message quality, not correctness.

### 1g. `{1;}` (trailing semicolon)

**PASS (behavior), LOW (no test, same opaque error).**

After parsing row `[1]`, the match arm `Some(Token::Semicolon) => continue` fires. On the next loop iteration, `parse_array_cell()` is called immediately; `advance()` returns `Some(Token::RBrace)` → `InvalidArrayCellToken { got: "RBrace" }`. Rejection is correct. Same opaque error quality issue as 1f.

## 2. Arity-check correctness

### 2a. `expected`/`found`/`row` field semantics

**PASS.**

From the parser code at `parser.rs:486-491`:

```rust
Some(expected) if expected != row_arity => {
    return Err(ParseError::ArrayRowArityMismatch {
        expected,
        found: row_arity,
        row: rows.len() as u32,  // length BEFORE push
    });
}
```

- `expected` = row 0's length (set on first iteration as `expected_arity = Some(row_arity)`).
- `found` = the offending row's length.
- `row` = `rows.len()` at the point of mismatch, which is the number of rows already pushed (i.e., the 0-based index of the offending row). Correct: row 0 is already in `rows`, so `rows.len() == 1` when the mismatch is detected on row 1.

The test `parse_array_literal_arity_mismatch_rejects` for `{1, 2; 3}` asserts `expected=2, found=1, row=1`. This is correct.

### 2b. First-row-empty edge

**PASS.**

The empty-literal guard (`if matches!(self.peek(), Some(Token::RBrace))`) fires before the loop begins. The loop's first iteration always calls `parse_array_cell()` unconditionally, so if the parser enters the loop, row 0 gets at least one cell (or `parse_array_cell` returns an error). The `expected_arity = Some(row_arity)` path is always taken on the first iteration; the `ArrayRowArityMismatch` path cannot fire for row 0. Confirmed correct.

### 2c. Third-row mismatch `{1; 2, 3}` → expected=1, found=2, row=1

**PASS (logic), MEDIUM (not tested).**

Tracing: Row 0 = `[1]`, `expected_arity = Some(1)`. Row 1: `2` parsed, Comma seen, `3` parsed → `row_arity = 2`. Arity check: `expected=1 != found=2` → `ArrayRowArityMismatch { expected: 1, found: 2, row: rows.len() as u32 = 1 }`. Correct.

Not tested. The existing test only covers `{1, 2; 3}` (second row shorter, first row longer). The symmetric case (`{1; 2, 3}`) — second row longer — is not covered.

**Finding M1** (MEDIUM): Test gap for arity-mismatch row=1 where second row is LONGER than first.

## 3. Printer round-trip property

### 3a. Round-trip test coverage for arrays

**PASS.**

`print_array_round_trip_through_parse_print_parse` tests the property `parse(print(parse(s))) == parse(s)` for `{1, 2; 3, 4}`. The property holds because the printer emits canonical whitespace (`", "` / `"; "`) which the lexer accepts identically on re-parse, and cell printing uses the same sub-functions as formula printing.

### 3b. String cells with embedded separator chars (`{1, "a, b"}`)

**PASS.**

`print_string_literal` wraps the string in `"..."` and escapes only `"` characters (as `""`). It does not need to escape `,` or `;` because those characters inside a quoted string are tokenized as part of the string literal by the lexer, not as separators. The printer correctly writes `"a, b"` and the lexer correctly re-reads it as a single string token. No test for this specific case exists, but the mechanism is sound and covered by the pre-existing string-literal escape tests.

### 3c. Unary-signed number in array: parser folds, printer emits `-5`

**PASS.**

The parser folds the sign: `{-5}` → `Expr::Number(-5.0)`. The printer calls `print_number(-5.0, out)`. Since `-5.0.fract() == 0.0` and `(-5.0).abs() == 5 < 1e16`, it formats as `format!("{}", -5i64)` = `"-5"`. The round-trip test `print_array_literal_mixed_cells` covers `{1, TRUE, "hi", #N/A, -5}` and asserts the printed form is identical to the input. Correct.

### 3d. Error literal case-canonicalization (`#ref!` → `#REF!`)

**PASS.**

`print_error_literal_canonicalizes_case` tests exactly this: lex `#ref!`, parse, print, assert `"#REF!"`. The printer emits `ev.sigil()` which is the canonical uppercase form. Correct.

## 5. Fingerprint stability

### 5a. Tag byte 11 is the next free tag

**PASS.**

From `fingerprint.rs`:
- 0 = Number
- 1 = String
- 2 = Bool
- 3 = CellRef
- 4 = RangeRef
- 5 = Binary
- 6 = Unary
- 7 = Function
- 8 = Array
- 9 = Spill
- 10 = NameRef
- 11 = Error (new)

Tag 11 is the next free tag. Correct.

### 5b. Fingerprint hashes sigil string, not discriminant

**PASS.**

`ev.sigil().hash(h)` hashes the sigil string (e.g. `"#REF!"`, `"#N/A"`). Adding a new `ErrorValue` variant later would not shift the fingerprint of any existing error value, provided the new variant is not interleaved among existing sigils. This is a sound design choice — it gives sigil-value stability rather than discriminant-value stability, which is harder to guarantee across codebase evolution.

## 6. Bundling decision (4.7.D + 4.7.E in one commit)

**PASS.**

The bundling rationale is sound. The pre-existing printer had:

```rust
Expr::Array(_) | Expr::Spill(_) => unreachable!("...")
```

The moment `parse_array_literal` starts producing `Expr::Array(...)` in any parser test, the printer `unreachable!()` becomes reachable. Since the parser tests call the printer via round-trip helpers (`round_trip` in printer tests; `parse_ok`/`parse_err` in parser tests), the build would fail with a panic. Bundling is the only option that maintains green gates at each committed state. The commit message documents this rationale clearly.

## Findings Detail

### M1 — MEDIUM: `{1; 2, 3}` (second row longer) arity mismatch not tested

**File:** `crates/ql-formula-syntax/src/parser.rs`, test module
**Severity:** MEDIUM
**Justification:** The `ArrayRowArityMismatch` error has two distinct directions of mismatch — second row shorter (`{1, 2; 3}`) and second row longer (`{1; 2, 3}`). Only the first is tested. Both produce the same error type but the field values differ (expected=1, found=2, row=1 vs expected=2, found=1, row=1). Any bug that inverts `expected` and `found` in the code would not be caught by the current tests.

**Suggested fix:** Add to the parser test module:
```rust
#[test]
fn parse_array_literal_arity_mismatch_row_longer_rejects() {
    let err = parse_err("{1; 2, 3}");
    match err {
        ParseError::ArrayRowArityMismatch { expected, found, row } => {
            assert_eq!(expected, 1);
            assert_eq!(found, 2);
            assert_eq!(row, 1);
        }
        other => panic!("expected ArrayRowArityMismatch, got {other:?}"),
    }
}
```

### M2 — MEDIUM: `Expr::Error` has no golden fingerprint entry

**File:** `crates/ql-calcgraph/src/fingerprint.rs`, `golden_fingerprints_locked` test
**Severity:** MEDIUM
**Justification:** The golden fingerprint test is the early-warning system for algorithm drift (per the module's own comments). All pre-existing `Expr` variants have golden entries. `Expr::Error` was added in this commit but no golden entry was added. Any future change that perturbs the error-fingerprint (algorithm rotation, sigil string change, etc.) will not be caught.

**Suggested fix:** Add one entry to the `goldens` array in `golden_fingerprints_locked`:
```rust
(
    "Error(Ref)",
    Expr::Error(ql_types::ErrorValue::Ref),
    0x<actual_value>,  // compute by running with 0 first
),
```
Run the test once with value `0` to obtain the actual fingerprint, then lock it.

### M3 — MEDIUM: No 3+ row array test

**File:** `crates/ql-formula-syntax/src/parser.rs`, test module
**Severity:** MEDIUM
**Justification:** Tests cover 1×3 (one row), 3×1 (three single-cell rows), and 2×2 (two rows). A 3×2 test `{1, 2; 3, 4; 5, 6}` would exercise the row-iteration loop for a case where the arity check fires twice (once for row 1, once for row 2 — both matching row 0, so no mismatch). This is the minimal case to rule out an off-by-one in `expected_arity` accumulation across 3+ rows.

**Suggested fix:**
```rust
#[test]
fn parse_array_literal_3x2() {
    let expr = parse_ok("{1, 2; 3, 4; 5, 6}");
    match expr {
        Expr::Array(rows) => {
            assert_eq!(rows.len(), 3);
            assert_eq!(rows[0].len(), 2);
            assert_eq!(rows[1].len(), 2);
            assert_eq!(rows[2].len(), 2);
            assert_eq!(rows[2][1], Expr::Number(6.0));
        }
        other => panic!("expected Array, got {other:?}"),
    }
}
```

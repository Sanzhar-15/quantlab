## What to look for

### Correctness

1. **Excel canon domain**: `[0, 2^48 - 1]` integer for all 5 fns.
   `2^48 - 1 = 281_474_976_710_655`. Verify `BIT_MAX` matches.
2. **Integer check via `n.trunc() == n`**: rejects fractional inputs.
   Note: IronCalc uses the same check on the FIRST arg only of
   shift fns (silently truncates shift). We follow IronCalc.
3. **`|shift| <= 53`** for BITLSHIFT/BITRSHIFT (Excel canon — beyond
   53 the i64 / f64 boundary becomes lossy).
4. **Negative shift inverts direction** (Excel canon, matches
   IronCalc): `BITLSHIFT(x, -s) = BITRSHIFT(x, s)`.
5. **Result overflow guard**: `result.abs() > BIT_MAX` → `#NUM!`.
   Matches IronCalc. Note: my impl uses `wrapping_shl`/`wrapping_shr`
   for the i64 operation to avoid Rust's panic-on-shift-overflow;
   the result is then checked against BIT_MAX. Verify this can't
   produce a wrong value for valid inputs (s in `[0, 53]`).
6. **i64 cast safety**: after the `<= BIT_MAX` pre-check (2^48-1
   well within i64 range 2^63-1), `as i64` is safe.

### IronCalc parity

7. Line-by-line: arg count, get_number, trunc/non-negative/max-value
   checks, i64 cast, bitwise op, result-bound check.
8. `wrapping_shl` vs IronCalc's `<<` on i64: IronCalc uses
   `number << shift` which would PANIC in debug mode for shifts
   that overflow. Our `wrapping_shl` defends against this. Verify
   no observable behavior difference for in-domain inputs.

### Coverage

11. Round-trip: `BITLSHIFT` ∘ `BITRSHIFT` round-trip pinned.
12. Algebraic identity: `a ^ b = (a | b) - (a & b)` pinned for
    bit-disjoint values (well-known property).

### Risk concerns specific to W5-D-8

- **`as i64` cast safety after BIT_MAX check**: BIT_MAX (2^48-1)
  fits comfortably in i64 (max 2^63-1). Verify no path can reach
  the cast with an out-of-range value.
- **`wrapping_shr` vs Rust's `>>` panic-on-overshift**: my impl
  uses wrapping_shr; IronCalc uses `>>`. For shifts in `[0, 53]`
  and `[0, 63]` on i64, behavior is identical. Verify.
- **Result-bound check after BITLSHIFT/BITRSHIFT**: `result.abs()
  > BIT_MAX` catches overflow. But `wrapping_shl` could produce
  a wrapped (negative) value before the abs check — verify the
  abs check handles wrapped values correctly.

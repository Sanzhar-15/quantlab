## 2. Aggregate-context expansion correctness

### 2a. `has_range_or_array_arg` rename exhaustiveness

**PASS.**

The old predicate `has_range_arg` (pre-W5-100) detected only `ExprPlan::AggregateNameRef`. The new name `has_range_or_array_arg` (scalar.rs line 238) now checks:

```rust
matches!(a, ExprPlan::AggregateNameRef { .. } | ExprPlan::Array(_))
```

There is only ONE call site for this predicate (line 241: `if has_range_or_array_arg && crate::plan::is_aggregate_function(name)`). No other copies of the old name exist. Rename is exhaustive.

### 2b. Single-AggregateNameRef fast path vs ExprPlan::Array

**PASS — correct exclusion.**

The fast path (lines 209–230) pattern-matches:
```rust
let single_range_arg = match args.as_slice() {
    [ExprPlan::AggregateNameRef { range, .. }] => Some(*range),
    _ => None,
};
```

`ExprPlan::Array` does NOT match this pattern (it matches `_` → `None`). So `SUM({1,2,3})` with a single Array arg skips the fast path and falls into the `has_range_or_array_arg` expansion path below.

The argument for why this is correct: array literals have no cache key (they have no range provenance). Caching by content would be a no-op since the array is stateless and always evaluates identically. The current design explicitly notes "array-literal args are pure values without provenance, so caching them is a no-op" (scalar.rs line 247). The exclusion is intentional and correct.

### 2c. Row-major iteration order

**PASS.**

The expansion loop (scalar.rs lines 263–269):
```rust
for row in rows {
    for cell in row {
        flat.push(eval_scalar_with_cache(cell, env, registry, cache));
    }
}
```

`ExprPlan::Array(Vec<Vec<ExprPlan>>)` is `Vec<rows>` where each `rows` is `Vec<cells-in-that-row>`. The outer loop advances rows; the inner loop advances columns within each row. This is row-major (row 0 col 0, row 0 col 1, ..., row 1 col 0, ...). This matches the existing `env.read_range` flat shape per the comment at line 262. The 2D test (`array_literal_sum_2d_array_row_major`) verifies `{1,2;3,4}` → `10`.

### 2d. Per-cell eval covering all four W5-99 literal kinds

**PASS.**

The W5-99 binder restricts array cells to `Number / Bool / String / Error`. All four are handled in `eval_scalar_with_cache`:

- `ExprPlan::Number(n)` → `Value::number(*n)` (line 136)
- `ExprPlan::Bool(b)` → `Value::Boolean(*b)` (line 137)
- `ExprPlan::String(s)` → `Value::Text(s.clone())` (line 138)
- `ExprPlan::Error(ev)` → `Value::Error(*ev)` (line 295)

Each cell call returns a concrete `Value`. SUM/MIN/MAX/AVERAGE receive those values in the flat `Vec<Value>` and handle errors via `coerce_numeric` → `NumericArg::Error(e) → return Value::Error(e)`.

## 3. Non-aggregate function behavior

**PASS.**

Path for `=ABS({-1, -2})`:

1. `lookup_range_aware("ABS")` → `None` (ABS is not range-aware).
2. `lookup_context_aware("ABS")` → `None` (ABS is not context-aware).
3. `registry.lookup("ABS")` → `Some(f)`.
4. `single_range_arg` check: args is `[ExprPlan::Array(...)]`, not `[AggregateNameRef]` → `None`.
5. `is_aggregate_function("ABS")` → `false`.
6. `has_range_or_array_arg` is `true` (array arg), but `is_aggregate_function` is `false` → condition fails.
7. Falls to the `else` branch: `evaluated: Vec<Value>` via `eval_scalar_with_cache(&ExprPlan::Array(...))`.
8. `eval_scalar_with_cache` dispatches `ExprPlan::Array(_)` → `Value::Error(ErrorValue::Calc)` (line 300).
9. ABS receives `[Value::Error(Calc)]` → propagates per error-arg rule.

Test `array_literal_in_non_aggregate_function_still_calc_error` pins this (scalar.rs line 1405). The test asserts `Value::Error(ErrorValue::Calc)`. **PASS.**

## 5. Range-aware and context-aware path coverage

### 5a. Range-aware path (SUMIF, VLOOKUP, etc.) with array args

**PASS as v1 decision — LOW future flag.**

In the `lookup_range_aware` arm (lines 159–179), non-`AggregateNameRef` args fall into:
```rust
other => {
    fn_args.push(FnArg::Scalar(eval_scalar_with_cache(other, env, registry, cache)));
}
```

`ExprPlan::Array` matches `other` → `eval_scalar_with_cache` on it → `Value::Error(ErrorValue::Calc)` → `FnArg::Scalar(#CALC!)`. The range-aware function (e.g., SUMIF) receives a `#CALC!` scalar as its criteria-range — effectively a no-match criteria → result is `0` or an error depending on SUMIF's error-propagation logic.

This is acceptable for v1. Design § 6.3 only specifies aggregate-context (scalar SUM/AVERAGE/COUNT) behavior. `SUMIF(array, criteria)` accepting an array-as-range is Phase 4.9+ work. Flagged LOW below.

### 5b. Context-aware path

**PASS as v1 decision.** Context-aware functions (DATE, NOW, WEEKDAY) are not aggregates and don't consume range inputs. `Array` → `#CALC!` via the scalar arm is correct for v1.

## 6. Coverage gaps

### 6a. PRODUCT via array — tested implicitly?

**MIXED — LOW.**

`PRODUCT` is in `is_aggregate_function` (plan.rs line 282) and in the scalar registry (scalar_fns.rs line 153). The aggregate-context expansion code handles it correctly — `PRODUCT({1,2,3})` would expand to `flat=[1,2,3]` and call `product(&[1,2,3])` → `6.0`. But there is NO explicit test in this commit for `PRODUCT({...})`. The existing `product_basic` test in `scalar_fns.rs` tests `product(&[Value::Number(2.0), Value::Number(3.0)])` directly, not through array expansion.

`product()` uses the same `coerce_numeric` pattern as `sum()`/`max()`/`min()` — structurally the expansion is identical. The gap is test coverage only, not a correctness bug. Severity: LOW.

### 6b. Empty array

**PASS.** Empty array literals are rejected at parse time (`ArrayRowArityMismatch`) and binder time. The `is_degenerate()` path in `into_scalar_for_test` handles it, but no real formula can reach an empty `ExprPlan::Array` in the eval path. Correctly skipped.

### 6c. SUM({1,2}, A1) — mixed array + cell-ref

**PASS.** The `array_literal_sum_mixed_with_scalar_arg` test covers `SUM({1,2}, 3, 4)` → 10. The mixed path uses `has_range_or_array_arg=true` (at least one array arg), so it enters the aggregate expansion branch where `other => flat.push(eval_scalar_with_cache(other, ...))`. Cell-refs (`ExprPlan::CellRef`) are handled by the `other` arm and evaluated as scalars normally. The test pattern covers this path implicitly.

### 6d. SUM(SUMIF(...), {1,2,3}) — nested aggregate calls

**PASS as design.** `SUM(SUMIF(...), {1,2,3})`: the inner `SUMIF(...)` is a `Function` ExprPlan, which is handled by the `other` arm in the aggregate expansion loop → `eval_scalar_with_cache(ExprPlan::Function{SUMIF,...})` → routes to `lookup_range_aware` → produces a scalar `Value`. Outer `SUM` sees `[scalar_from_SUMIF, ...array_cells...]`. The array expansion fires because `has_range_or_array_arg=true`. The result is correct. NOT explicitly tested, but the code path is structurally identical to `SUM({1,2}, 3, 4)` with the scalar arg being a nested function call instead of a literal. Coverage gap is LOW.

### 6e. COUNTA({1, "", #N/A})

**PASS on semantics, MEDIUM on test coverage.**

`COUNTA` is in `is_aggregate_function` (plan.rs line 279) and the aggregate expansion fires. `counta()` counts all non-blank values: `c = args.iter().filter(|v| !matches!(v, Value::Blank)).count()`. Three values: `Number(1)`, `Text("")`, `Error(NA)` — none are `Blank` → count = 3. (Note: `""` is a `Text("")`, which is NOT `Blank` in the Quantbook type system. Blank is a distinct variant.)

**However:** the claim in the audit prompt `=COUNTA({1, "", #N/A})` — the `""` is a Text string literal, not blank. So result is 3, not 2. This may surprise users expecting Excel behavior where `""` in a range is sometimes treated as blank by COUNTA (it's NOT — Excel's COUNTA also counts `""` as non-blank). So the behavior is correct per Excel canon.

There is no explicit `COUNTA({...})` test in this commit. The `counta_counts_non_blank` test in `scalar_fns.rs` tests COUNTA directly (not via array expansion). Severity: LOW (missing test, not a bug).

## 7. Doc + test consistency

### 7a. SUM({1,#N/A,3}) → #N/A trace

**PASS.**

Commit message claim: `SUM({1, #N/A, 3})` → `#N/A`. Trace:

1. Aggregate expansion fires: `flat = [Number(1), Error(NA), Number(3)]`.
2. `sum(&flat)` iterates:
   - `coerce_numeric(Number(1))` → `NumericArg::Number(1.0)` → `total = 1.0`.
   - `coerce_numeric(Error(NA))` → `NumericArg::Error(NA)` → `return Value::Error(NA)`. **Short-circuits here.**
   - `Number(3)` is never evaluated.
3. Result: `Value::Error(ErrorValue::NA)`.

SUM short-circuits on first error, left-to-right, as confirmed by `scalar_fns.rs` line 70: `NumericArg::Error(e) => return Value::Error(e)`. The renamed test pins this.

### 7b. MAX({-5,-3,-1}) → -1

**PASS.**

`max()` iterates: `-5`, `-3`, `-1` via `coerce_numeric` (all `NumericArg::Number`). It tracks `current = Some(c.max(n))`. Result: `max(-5, -3) = -3`, then `max(-3, -1) = -1`. Returns `Value::Number(-1.0)`.

The test `array_literal_max_without_error_short_circuit` (scalar.rs line 1461) asserts `Value::Number(-1.0)`. Correct — `-1` is the LEAST negative (largest) of the set. No confusion with absolute values.

**Finding:** Design doc § 11 table lists `4.7.G (W5-101)`, but the actual commit is tagged `W5-100`. The numbering drifted by one because W5-98 bundled sub-phases 4.7.D + 4.7.E, causing W5-99 to land 4.7.F (design had it at W5-100) and W5-100 to land 4.7.G (design had it at W5-101).

- Same doc line 201: `"(W5-101 / Phase 4.7.G migration target)"`.

The sub-phase CONTENT (evaluator + EvalResult) is correct and complete. The drift is doc-only. Severity: LOW.

**Suggested fix:** Update the § 11 table row and the two inline mentions in the design doc to say `4.7.G (W5-100)`. Future sub-phases should be renumbered accordingly (4.7.H → W5-101, etc.).

### 8b. `lookup_any` dispatch migration not performed — MEDIUM

**Finding:** Design doc § 6.2 states: "Caller-side dispatch in `ql-exec::eval` (W5-101 / Phase 4.7.G migration target): ... `match registry.lookup_any(name) {...}`". The implication is that Phase 4.7.G should migrate `eval_scalar_with_cache`'s three-branch dispatch (`lookup_range_aware` → `lookup_context_aware` → `lookup`) to the unified `lookup_any` + match-on-tier approach.

The commit did NOT perform this migration. `lookup_any` remains unused outside of `ql-functions`' own tests. The aggregate-context array expansion was grafted onto the existing three-branch dispatch, adding a 4th tier of logic inside the `lookup` arm without collapsing the outer branches.

**Is this a correctness problem?** No — the current dispatch still routes correctly. The three-branch structure is equivalent to a `lookup_any` + match in observable behavior.

**Is it a design-conformance problem?** Yes — the design doc explicitly designated this commit as the migration point. Deferring it means Phase 4.7.J (`set_formula` adoption) will need to integrate with the un-unified dispatch, potentially deepening the nesting further.

**Severity: MEDIUM.** Not a shipping blocker for W5-100 itself, but the longer the migration is deferred, the harder it becomes (each sub-phase that adds to the current dispatch structure increases the refactor surface). Should be done before or at 4.7.J.

`scalar.rs:151-301` is the entire dispatch block that would be collapsed. No correctness risk in the refactor — it is a pure structural change.

### 8c. SUMPRODUCT({1,2},{3,4}) silently wrong via range-aware path — LOW

**Finding:** `SUMPRODUCT` appears in `is_aggregate_function` (to allow binder's `AggregateNameRef` context) but is registered as `range_aware` in the function registry. The dispatch order in `eval_scalar_with_cache` checks `lookup_range_aware` first. So `SUMPRODUCT({1,2},{3,4})` would:

1. `lookup_range_aware("SUMPRODUCT")` → `Some(f)`.
2. Both array args → `other` arm → `eval_scalar_with_cache(ExprPlan::Array(...))` → `#CALC!`.
3. `FnArg::Scalar(#CALC!)` passed to SUMPRODUCT.
4. SUMPRODUCT sees scalar error args → propagates `#CALC!`.

The aggregate expansion path (which would correctly expand arrays) is never reached because `lookup_range_aware` fires first. This is a v1 limitation consistent with § 5a above, but the distinction from SUM is subtle: SUM is scalar-registered (aggregate expansion fires); SUMPRODUCT is range-aware-registered (expansion does NOT fire). Users might expect SUMPRODUCT to accept array literals the same way SUM does.

**Severity: LOW** — design § 6.3 only specifies SUM/AVERAGE/COUNT class, not SUMPRODUCT. But should be flagged as a known gap in the future polish list.

# W5-D-14 Phase 4.11 audit — self (integration pass)

**Date:** 2026-05-18
**Auditor:** Implementing Opus 4.7 (this conversation's primary agent).
**Scope:** Whole-W5-D-14 audit complementing parallel Codex + separate-Opus audits.
**HEAD:** `13b64488dc0` on `feat/quantbook-engine`.

## Summary

**5 HIGH severity round-trip gaps found.** The W5-D-14e commit message
claim "Phase 4.11 round-trip spine: CLOSED" is materially FALSE for
5 out of 10 features that should round-trip per the acceptance
criteria. Per-batch audits caught nothing wrong because each batch's
tests verified the IMPORT side; the export side was added last
without symmetric tests.

## Methodology

Built a self-audit probe (`crates/ql-io-xlsx/tests/zzz_self_audit_
probe.rs`, deleted post-audit) that constructs a Quantbook workbook
with EVERY claimed-supported feature, exports via `ExportMode::
NewWorkbook`, re-imports, and compares.

## HIGH

### HIGH-1 — `Error(_)` round-trips as `Text(_)` (asymmetric export/import mapping)

**Subject:** Export serializes `Value::Error(e)` as `set_value_string(e.sigil())`, which writes the `#DIV/0!` literal as plain text. On re-import, calamine sees a string and produces `Value::Text("#DIV/0!")`, NOT `Value::Error(DivZero)`. Round-trip is lossy.

**Where:**
- Export: `crates/ql-io-xlsx/src/write/umya_export.rs:138` (`set_value_string(e.sigil())`)
- Re-import: `crates/ql-io-xlsx/src/read/calamine_grid.rs::data_to_value` — Data::String → Value::Text

**Detail:** OOXML represents cell errors with `<c t="e"><v>#DIV/0!</v></c>` (the `t="e"` attribute is the discriminant). umya's `set_value_string` does NOT set `t="e"`, so the cell is written as a regular text cell. Calamine reads it back as `Data::String("#DIV/0!")`.

**Recommendation:** Use a different umya API — `Cell::get_cell_value_mut().set_value_and_data_type(...)` with `CellValue::set_error(...)` or equivalent. Verify the round-trip restores `ErrorValue` correctly.

**Severity rationale:** HIGH. Errors are a fundamental cell value type; lossy round-trip means evaluating an imported sheet, exporting it, and re-importing produces SEMANTICALLY DIFFERENT values for any cell that evaluates to an error. The acceptance criterion XLSX-4-02 (formulas recalc through graph) is degraded since re-imported error cells now have a different type.

### HIGH-2 — `date_system` 1904 silently resets to 1900 on export

**Subject:** The exporter uses `umya_spreadsheet::new_file_empty_worksheet()` which constructs a fresh workbook with default 1900 system. The Quantbook workbook's date_system is never propagated to umya before write.

**Where:**
- Export: `crates/ql-io-xlsx/src/write/umya_export.rs:31` — no `set_date1904` call.

**Detail:** umya's `Spreadsheet` has a `Workbook` substruct with workbook-level properties including `date1904`. The exporter doesn't access this — every exported file claims 1900 regardless of the Quantbook source. **Every date serial in the original workbook is now misinterpreted by 1462 days** if the workbook was 1904.

**Recommendation:** Add `if workbook.date_system() == DateSystem::Excel1904 { spreadsheet.workbook_mut().set_date1904(true); }` (or equivalent umya API) before write.

**Severity rationale:** HIGH. The W5-D-14b commit explicitly added `set_date_system` on import. Not propagating it on export is a one-line miss with a 4-year-difference impact on date serials. Phase 4.11 acceptance XLSX-4-03 requires "date systems survive" implicitly via "formats survive".

### HIGH-3 — Tables are NOT exported (lost on round-trip)

**Subject:** `umya_export.rs` writes cells + formulas only. Quantbook's `TableTable` entries are never written to `xl/tables/*.xml`. Re-import finds no tables.

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs` — no `tables_mut().add_table(...)` or equivalent umya calls.

**Detail:** Quantbook's `TableTable` carries `name`, `display_name`, `sheet`, `top_row`, `top_col`, `rows`, `cols`, `has_header`, `has_totals`, `columns` per table. None of this is serialized. After round-trip, structured references like `=Sales[Qty]` fail to bind because `SALES` doesn't exist in the re-imported workbook.

**Recommendation:** Iterate `workbook.tables().iter()` (if available; see `TableTable::iter()`) and call umya's table-add API for each. umya supports `Worksheet::tables_mut()` / `add_table(Table)`. Verify the round-trip restores `TableMetadata` semantically equivalent to the original.

**Severity rationale:** HIGH. Tables are first-class Phase 4.8 territory. The W5-D-14c commit message states "Closes Phase 4.11 acceptance XLSX-4-03 (tables-side)" — that claim covers IMPORT only. Round-trip is what the user cares about; export tables = lost data on user's first save.

### HIGH-4 — Named ranges are NOT exported (lost on round-trip)

**Subject:** Workbook-scoped + sheet-scoped names are parsed on import (W5-D-14b) but not written on export. Re-import finds no names.

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs` — no `defined_names_mut().add_defined_name(...)` or equivalent umya calls.

**Detail:** Quantbook's `NameTable` carries `(name → NamedTarget)` mappings — `Cell`, `Range`, `Constant`, `Formula` variants. None of these are serialized. After round-trip, `=MyName` formulas fail to bind.

Note: W5-D-14b commit message accurately notes "scoped names PARSED but not yet registered with the engine NameTable (W5-D-15)". So the import side is also incomplete — names are read but not wired. The compound effect is that names are silently lost on BOTH sides.

**Recommendation:** Iterate `workbook.names().iter()` and call umya's defined-names API for each workbook-scoped entry. For sheet-scoped: iterate each sheet's `scoped_names()`. Set `localSheetId` on the umya defined-name to match.

**Severity rationale:** HIGH. Same compound impact as HIGH-3. Names are a Quantbook first-class concept and a Phase 4.11 acceptance criterion explicitly.

### HIGH-5 — Custom format codes are NOT exported (lost on round-trip)

**Subject:** `xl/styles.xml/<numFmts>` custom format codes (numFmtId ≥ 164) are parsed on import (W5-D-14d) but not written on export. Re-import finds id 164 unregistered.

**Where:** `crates/ql-io-xlsx/src/write/umya_export.rs` — no `formats_mut().set_number_format(...)` or equivalent.

**Detail:** Quantbook's `FormatTable` carries the workbook's custom format codes at their original numFmtIds. The export should:
1. Iterate `workbook.formats().iter()` for entries with `id.0 >= 164`.
2. Write each as a `<numFmt numFmtId="N" formatCode="..."/>` in the exported styles.xml.

Without this, even if per-cell style application were wired (it isn't), the format codes the cells reference would not exist in the exported file.

**Recommendation:** Add a styles-write step to the exporter. umya exposes a styles-add API on the workbook level.

**Severity rationale:** HIGH. W5-D-14d commit message claims "the workbook's FormatTable correctly carries the user's custom format strings, so when per-cell wiring lands it can just FormatId(N) directly without re-allocating ids." This is true for the in-memory state but FALSE for round-trip — the codes are lost on export.

## MEDIUM

### MEDIUM-1 — `unwrap_or_default()` patterns swallow malformed OOXML in parsing

**Subject:** OOXML parsers use `attr.unescape_value().unwrap_or_default()` for required attributes, silently converting parse failures to empty strings.

**Where:** 9 sites in `workbook_xml.rs`, 6 in `tables_xml.rs`, 3 each in `rels.rs` + `styles_xml.rs`. Total 21 sites.

**Detail:** Per CLAUDE.md no-fallbacks rule, malformed OOXML should surface errors loudly. Example: `attr.unescape_value().unwrap_or_default().to_string()` for the `name` attribute of `<sheet>` returns `""` on UTF-8 decode failure, which then passes the `if name.is_empty()` malformed-check — but only because we happen to check `is_empty()`. Sites without such follow-up checks silently corrupt.

**Recommendation:** Replace each `unwrap_or_default()` with `.map_err(|e| XlsxError::XmlParse {...})?` propagation. Add tests for malformed-UTF-8-attribute fixtures.

**Severity rationale:** MEDIUM. Not currently a known correctness bug (the sites that matter happen to have follow-up validation), but a load-bearing pattern across 21 sites is a forward-defense gap.

### MEDIUM-2 — `tables_import.rs` 1:1 sheet-index-to-filename heuristic is brittle

**Subject:** `tables_import.rs:51` assumes the rels file is at `xl/worksheets/_rels/sheet{N+1}.xml.rels` where N is the calamine sheet index. Per OOXML spec, sheet → file mapping requires workbook-rels resolution; non-Excel-generated files may have gaps.

**Where:** `crates/ql-io-xlsx/src/read/tables_import.rs:51`.

**Detail:** Documented in the source as a v1 limitation ("for files with non-standard layouts ... we'd need to follow the workbook rels"). But Phase 4.11 W5-D-14c claims tables round-trip "where supported" without quantifying what "supported" means. Real workbooks generated by LibreOffice / Google Sheets / pandas / openpyxl may not match the 1:1 mapping.

**Recommendation:** Build a sheet-name → sheet-part-path map via workbook rels (`xl/_rels/workbook.xml.rels`) instead of hard-coding the convention. Add a fixture with a non-standard layout to pin the gap.

**Severity rationale:** MEDIUM. Affects real-world fixtures from non-Excel sources. Documented but not tested.

### MEDIUM-3 — Bounds check warnings on import never produce a Failure

**Subject:** `convert.rs` warns when a cell's row/col exceeds `MAX_ROW`/`MAX_COLUMN` but Quantbook's MAX values match Excel exactly (1048575 / 16383). The warnings are effectively dead code.

**Where:** `crates/ql-io-xlsx/src/read/convert.rs:62-83`.

**Detail:** Since `MAX_ROW = 1_048_575` matches Excel and calamine inherits Excel's limits, no real xlsx file can produce a cell beyond Quantbook's bounds. The bounds-check code path is unreachable in practice.

**Recommendation:** Either (a) remove the bounds-check (the storage layer's panic on `put_at` is sufficient defense for the impossible case), or (b) keep the check but acknowledge in a comment that it's defense-in-depth for hand-constructed malformed xlsx.

**Severity rationale:** MEDIUM. Dead-code-looking pattern in a load-bearing trust boundary.

### MEDIUM-4 — `data_to_value` collapses 3 calamine variants to lossy mappings

**Subject:** `DateTimeIso` and `DurationIso` become `Value::Text(_)` — the ISO string is preserved but the type information is lost. Round-trip from `xl/styles.xml`-cached date display reverts to the raw serial.

**Where:** `crates/ql-io-xlsx/src/read/calamine_grid.rs:170-175`.

**Detail:** The W5-D-14a comment acknowledges this: "ISO-8601 string forms — preserve as text for now; W5-D-14b adds a parsing pass to convert these to serial-date numbers using the workbook's date system." But W5-D-14b did NOT add this parsing pass. The deferral is documented in the comment but never implemented.

**Recommendation:** Add a date-string parsing pass in `data_to_value` using `chrono` (already a transitive dep via umya). Or accept the lossy behavior and update the W5-D-14a comment to clarify it's a permanent v1 divergence.

**Severity rationale:** MEDIUM. The original commit acknowledged the gap as a TODO; the TODO was never resolved.

### MEDIUM-5 — Round-trip smoke test only asserts sheet count

**Subject:** `tests/calamine_smoke.rs::round_trip_ironcalc_basic_text_preserves_sheet_count` is the ONLY round-trip smoke test for W5-D-14. It asserts `sheet_count` preservation only, not cell values, not metadata, not anything else.

**Where:** `crates/ql-io-xlsx/tests/calamine_smoke.rs` (the new test added in W5-D-14e).

**Detail:** A test named "preserves" that asserts only sheet count is a documentation lie. A future refactor that drops all cell values on export would PASS this test. Per the W5-D-13.1 audit-discipline Rule 3 ("lex+parse+bind+eval coverage"), round-trip tests must assert SEMANTIC equivalence end-to-end.

**Recommendation:** Add a comprehensive round-trip test that asserts:
1. Sheet count preserved.
2. Each cell's value preserved (including type — Number/Text/Bool/Error).
3. Each formula's text preserved.
4. Tables registered count preserved (= 0 today per HIGH-3 — pin the gap).
5. Names registered count preserved (= 0 today per HIGH-4 — pin the gap).
6. Date system preserved (= broken per HIGH-2 — pin the gap).
7. Custom format codes preserved (= broken per HIGH-5 — pin the gap).

When HIGH-2/3/4/5 are fixed, the test updates accordingly.

**Severity rationale:** MEDIUM. Process / test-quality gap. The shallow test PROVES that the per-batch audits were not catching round-trip issues — they only spot-checked what each batch wrote.

## LOW

### LOW-1 — `feature_inventory.rs` uses string-`contains` for in-sheet XML triggers

**Subject:** `<conditionalFormatting`, `<dataValidations`, etc. are detected via `content.contains("<conditionalFormatting")` on the worksheet XML string. False positives possible if a sheet's cell text contains the trigger string (e.g., a SUM cell with text `"this <conditionalFormatting>"`).

**Where:** `crates/ql-io-xlsx/src/read/feature_inventory.rs:69-83`.

**Recommendation:** Use proper XML element-name matching via quick-xml events. The per-event scan is similar cost to string-contains on small worksheets but is correct.

**Severity rationale:** LOW. False positive only matters if a user's cell content happens to contain XML-element-name strings. Cosmetic in practice.

### LOW-2 — `lib.rs` does double zip-decode (XlsxPackage + CalamineGrid)

**Subject:** Both `XlsxPackage::from_bytes(bytes.to_vec())` and `CalamineGrid::from_bytes(bytes.to_vec())` clone the entire byte buffer and re-open the zip. On a 100MB workbook this is 200MB of memory.

**Where:** `crates/ql-io-xlsx/src/lib.rs:122,137`.

**Recommendation:** Share the zip handle. Either (a) `XlsxPackage::open_archive()` returns a `ZipArchive` that calamine wraps, or (b) factor the zip-reading code so calamine and the OOXML scanner reuse one parse. Performance follow-up.

**Severity rationale:** LOW. Correctness OK; memory pressure for large workbooks. Not a v1 blocker.

### LOW-3 — Phase 4.11 plan claims XLSX-4-03 partial closure includes names

**Subject:** The W5-D-14b commit message says "scoped names PARSED but not yet registered with the engine NameTable (W5-D-15)". The Phase 4.11 plan says scope names contribute to acceptance XLSX-4-03. They don't — they're parsed and dropped on the floor.

**Where:** `crates/ql-io-xlsx/src/lib.rs` import_xlsx_bytes — `workbook_props.defined_names` is computed but NEVER consumed.

**Recommendation:** Either wire the NameTable registration (W5-D-15 scope) or remove the "names parsed" claim from W5-D-14b acceptance progress.

**Severity rationale:** LOW. Doc/claim hygiene; not a code bug. Becomes a HIGH if a user reports "I imported with named ranges and they were silently dropped."

## Audit-discipline lesson

**The per-batch audits missed HIGH-1 through HIGH-5 because they audited each commit in isolation.** Each commit's tests verified the side it shipped:
- W5-D-14a: import cells ✓ (tested)
- W5-D-14b: import dates ✓ (tested via fixture)
- W5-D-14c: import tables ✓ (tested via fixture)
- W5-D-14d: import format codes ✓ (tested)
- W5-D-14e: export cells ✓ (round-trip values)

**No commit's tests verified ROUND-TRIP of metadata.** The acceptance criteria say "X survives round-trip" which is a CROSS-COMMIT contract — and per-commit audits don't check cross-commit contracts.

**Forward lesson** (for the audit-discipline rule, Rule 3 extension): When a batch ships the WRITE side of a round-trip, the batch's audit MUST include a round-trip test that exercises EVERY feature the read side claimed to support. Otherwise the round-trip claim is structurally untestable in the per-batch shape.

This mirrors the W5-D-13.1 megaudit pattern where the Phase 4.10 V1-260 megaudit caught cross-batch issues the per-batch audits missed. W5-D-14 is the second instance of the same audit-discipline blind spot in three months.

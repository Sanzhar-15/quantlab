## 1. Binder Lowering Correctness

### 1.1 Four allowed cell kinds

**PASS.**

The binder's inner match on `cell` (plan.rs lines ~450-467) maps:
- `Expr::Number(n)` → `ExprPlan::Number(*n)`
- `Expr::Bool(b)` → `ExprPlan::Bool(*b)`
- `Expr::String(s)` → `ExprPlan::String(s.clone())`
- `Expr::Error(ev)` → `ExprPlan::Error(*ev)`

All four allowed kinds per design §3.3 are lowered correctly and produce the parallel `ExprPlan` variants. The `Arc::clone` on String is correct since `ExprPlan::String` holds `Arc<str>`. The `*ev` copy for ErrorValue is correct since `ErrorValue` derives `Copy`.

### 1.2 Disallowed kinds — rejection set exhaustiveness

**PASS.**

The `other =>` arm catches everything not matched above and returns `BindError::ArrayCellNotLiteral { ... got: variant_kind(other) }`. The disallowed kinds that reach this arm are: `CellRef`, `RangeRef`, `Binary`, `Unary`, `Function`, `Array` (nested), `Spill`, `NameRef`. All eight are rejected.

Two tests cover representative cases: `CellRef` at (row=0, col=1) and nested `Array`. The remaining six disallowed kinds are untested but the `other =>` catch-all is sound — any new `Expr` variant would also reach it rather than silently pass.

**However:** `NameRef` and `Function` as array-cell kinds have NO dedicated tests. See §7.2.

### 1.3 `variant_kind` helper — exhaustiveness

**PASS with LOW observation.**

The function explicitly matches all 12 `Expr` variants:
`Number`, `Bool`, `String`, `Error`, `CellRef`, `RangeRef`, `Binary`, `Unary`, `Function`, `Array`, `Spill`, `NameRef`.

These correspond exactly to the 12 variants in `crates/ql-formula-syntax/src/ast.rs` (`Expr` enum). The match is exhaustive as a Rust pattern match. If a 13th `Expr` variant were added in a future phase, the compiler would error on `variant_kind` — good. **No gap here.**

LOW note: `variant_kind` is only invoked on the error path (inside `ArrayCellNotLiteral`). This means the compiler's exhaustiveness check fires at the `variant_kind` definition, not at the call site — a future developer adding `Expr::SomethingNew` will get a compile error in `variant_kind`, not in `bind_with_context`. This is acceptable and consistent.

## 3. Eval-Site Behavior

### 3.1 Parity between `eval_scalar` and `eval_scalar_with_cache`

**PASS.**

Both functions have the identical new arms (scalar.rs):

```
ExprPlan::Error(ev) => Value::Error(*ev),
ExprPlan::Array(_) => Value::Error(ErrorValue::Calc),
```

They are in the same order relative to the other arms (both come after `AggregateNameRef`). The eval tests cover both entry points:
- `eval_scalar_expr_plan_error_returns_value_error` → `eval_scalar`
- `eval_scalar_with_cache_expr_plan_error_returns_value_error` → `eval_scalar_with_cache`
- `eval_scalar_expr_plan_array_in_scalar_context_returns_calc_error` → `eval_scalar`
- `eval_scalar_with_cache_expr_plan_array_returns_calc_error` → `eval_scalar_with_cache`

No drift between the two functions. Good pattern symmetry with the pre-existing `AggregateNameRef` arms in both.

### 3.2 `#CALC!` interim correctness and spill interception site

**PASS** on interim correctness, with MEDIUM doc note on the interception site.

The design §6.3 says: "cell-boundary context → spill; sub-expression scalar context → `#CALC!`." Phase 4.7.J will implement the spill path. For now, **every** `ExprPlan::Array` evaluation through the scalar evaluator produces `#CALC!` — including the cell-boundary case.

Tracing the interception point in `WorkbookRuntime::set_formula` (workbook_runtime.rs lines ~517-535):

```
let value = eval_scalar_with_cache(plan.as_ref(), &env, registry, cache);
// ... then:
workbook.put_computed_at(sheet, row, col, value.clone());
```

The interim `#CALC!` lands in the computed overlay. This is **correct interim behavior**: the spill path (Phase 4.7.J) will need to intercept `plan.as_ref()` **before** calling `eval_scalar_with_cache`, by pattern-matching `Arc<ExprPlan>` against `ExprPlan::Array`. The path is clear and documented in the scalar.rs comments.

**What if Phase 4.7.J incorrectly calls `eval_scalar_*` first?** It would get `#CALC!` at the cell and never reach the spill write path. This is a correctness gap in Phase 4.7.J's implementation, not in Phase 4.7.F's. Phase 4.7.F's `#CALC!` fallback is explicit and documented. No issue with this commit.

Note: `eval_scalar_with_registry` (the legacy entry point, used by `WorkbookTransaction::commit`) delegates to `eval_scalar_with_cache` with `NoAggregateCache`. The `ExprPlan::Array` arm will also fire there, producing `#CALC!`. This is correct.

## 4. Defense-in-Depth Coverage

### 4.1 Binder rejection set vs parser rejection set

**PASS.**

Parser `parse_array_cell` (parser.rs lines ~523-568) allows: `Token::Number`, `Token::String`, `Token::Error`, `Token::Op(Minus/Plus) + Token::Number` (folded to `Expr::Number`), `Token::Ident("TRUE"/"FALSE")` → `Expr::Bool`. Everything else → `ParseError::InvalidArrayCellToken`.

Binder allows: `Expr::Number`, `Expr::Bool`, `Expr::String`, `Expr::Error`. Everything else → `BindError::ArrayCellNotLiteral`.

The sets are consistent. There is no kind that the parser allows but the binder rejects (which would be a false negative) or vice versa.

### 4.2 Parser folds unary-signed numbers

**PASS — key safety property confirmed.**

Parser `parse_array_cell` for `Token::Op(Minus)` advances and folds the next `Token::Number(n)` directly to `Expr::Number(-n)`. It does NOT emit `Expr::Unary { op: Minus, operand: Expr::Number(n) }`. Therefore the binder will never see `Expr::Unary` inside an array cell from real parsed input. The binder's rejection of `Expr::Unary` via the `other =>` arm is defense-in-depth for directly-constructed ASTs only.

This means the design intent (§5: "no `Unary` — the lexer folds signs into literals") is correctly implemented at the parser level.

## 5. Empty-Array Path

**FAIL.** LOW severity.

### Finding L-1: `Expr::Array(vec![])` uses the wrong error variant

The binder handles zero-row arrays (plan.rs ~line 412-418):

```rust
if rows.is_empty() {
    return Err(BindError::UnsupportedVariant(
        "Expr::Array with zero rows is not constructible from source; \
         direct AST construction with an empty Vec is rejected",
    ));
}
```

The parser uses `ParseError::EmptyArrayLiteral` — a **dedicated** variant with its own `#[error("empty array literal '{{}}' is not allowed")]`. The binder uses the generic `BindError::UnsupportedVariant`.

**Why it matters:** Design §5 explicitly states "No `BindError::UnsupportedVariant` for `Expr::Array` itself — it's now supported." The zero-row case is a degenerate form of `Expr::Array`, not an "unsupported variant." A consumer pattern-matching on `BindError` to distinguish "array not yet supported" from "your array construction was malformed" cannot distinguish these two cases today.

**Suggested fix:** Add `BindError::EmptyArrayLiteral` mirroring `ParseError::EmptyArrayLiteral`:

```rust
// In BindError enum:
/// `Expr::Array` with zero rows — not constructible from source
/// (`ParseError::EmptyArrayLiteral` fires first); rejected here as
/// defense in depth against direct AST construction.
#[error("array literal with zero rows is not valid")]
EmptyArrayLiteral,
```

And replace the `UnsupportedVariant` return in the binder with `BindError::EmptyArrayLiteral`.

The existing test `bind_array_literal_zero_rows_rejects` checks `matches!(err, BindError::UnsupportedVariant(_))` — it would need updating to `BindError::EmptyArrayLiteral`.

**Severity: LOW** — no observable runtime regression (the parser prevents this path in production), but it is an API inconsistency that breaks the parallel-with-parser design intent and could mislead an IDE consumer.

## 7. Test Coverage Gaps

### 7.1 Error literal: only two ErrorValue variants tested

**MIXED.** LOW severity.

`bind_error_literal_lowers_to_expr_plan_error` tests `ErrorValue::Ref`. The eval tests test `ErrorValue::Ref`, `ErrorValue::NA`, `ErrorValue::DivZero`. The lowering is mechanical (`*ev` copy), so the other 12 ErrorValue variants are de facto covered by transitivity. No test gap for correctness, but a broader parametric test would improve confidence.

### 7.2 Missing rejection tests: `NameRef` and `Function` as array cell kinds

**FAIL.** MEDIUM severity. **Finding M-1.**

The commit's 8 binder tests cover: `CellRef` rejection and `Array` (nested) rejection as `ArrayCellNotLiteral`. Missing:

- `Expr::NameRef("SomeRange")` inside array cell — not tested. Would produce `got = "NameRef"`.
- `Expr::Function { name: "SUM", args: vec![] }` inside array cell — not tested. Would produce `got = "Function"`.
- `Expr::Unary { op: Minus, operand: Expr::Number(5.0) }` inside array cell — not tested. Parser folds this to `Expr::Number(-5.0)` so it can't arise from parsing; but direct AST construction is the exact scenario defense-in-depth targets. Would produce `got = "Unary"`.
- `Expr::Binary { ... }` inside array cell — not tested.
- `Expr::RangeRef(...)` inside array cell — not tested.
- `Expr::Spill(...)` inside array cell — not tested.

The `other =>` arm is correct and covers all these cases. But the audit task calls for "every variant should have at least one trigger test" for the rejection path. At minimum, `NameRef` and `Function` (the most likely direct-AST construction candidates) should have tests.

**Severity: MEDIUM** — the binder code is correct; the gap is test coverage for the defense-in-depth claim. A future refactor that accidentally narrows `other =>` would not be caught.

**Suggested fix (minimal):** Add two tests:

```rust
#[test]
fn bind_array_literal_rejects_name_ref_cell() {
    let expr = Expr::Array(vec![vec![Expr::NameRef(Arc::from("SomeRange"))]]);
    let err = bind(&expr, 0).unwrap_err();
    match err {
        BindError::ArrayCellNotLiteral { got, .. } => assert_eq!(got, "NameRef"),
        other => panic!("expected ArrayCellNotLiteral, got {other:?}"),
    }
}

#[test]
fn bind_array_literal_rejects_function_cell() {
    let expr = Expr::Array(vec![vec![
        Expr::Function { name: Arc::from("SUM"), args: vec![] }
    ]]);
    let err = bind(&expr, 0).unwrap_err();
    match err {
        BindError::ArrayCellNotLiteral { got, .. } => assert_eq!(got, "Function"),
        other => panic!("expected ArrayCellNotLiteral, got {other:?}"),
    }
}
```

### 7.3 Error literal inside aggregate-arg context: `SUM({1, #N/A, 3})`

**MIXED.** MEDIUM severity. **Finding M-2.**

The commit tests binary propagation (`1 + #N/A → #N/A`). It does NOT test what happens when an array literal containing an error cell (`{1, #N/A, 3}`) appears as an argument to a function. In the current evaluator, `SUM({1, #N/A, 3})` would bind the outer array to `ExprPlan::Array(...)` as a Function argument, and `eval_scalar_with_cache` would evaluate the `ExprPlan::Array` arm on the **outer** Function arg, producing `#CALC!` — and then pass `#CALC!` as a `Value` to `SUM`. `SUM` would then propagate the `#CALC!` error.

This is internally consistent (the outer `ExprPlan::Array` is in a scalar argument position, so `#CALC!` per §6.3), but it is not what Excel does: `=SUM({1, #N/A, 3})` should produce `#N/A` via error propagation, not `#CALC!`. The correct path for this is the "aggregate-arg context" described in design §6.3 — which is deferred to Phase 4.7.G.

**The point:** there's no test that documents the **current** (wrong but deliberate) behavior of `SUM({1, #N/A, 3})`. A future developer implementing Phase 4.7.G needs to know that fixing this behavior is intentional, not a regression. The interim `#CALC!` result should be captured in a `// TODO(Phase 4.7.G)` test.

**Suggested fix:** Add an eval-site test pinning the interim behavior:

```rust
#[test]
fn sum_with_array_literal_arg_produces_calc_in_phase_4_7_f_interim() {
    // TODO(Phase 4.7.G): once array-in-aggregate-context is wired,
    // SUM({1, #N/A, 3}) should yield #N/A (error propagation).
    // For now, ExprPlan::Array in scalar arg position → #CALC! per §6.3.
    let env = crate::env::MapEnv::new();
    let registry = ql_functions::default_registry();
    let cache = NoAggregateCache;
    let plan = ExprPlan::Function {
        name: Arc::from("SUM"),
        args: vec![ExprPlan::Array(vec![vec![
            ExprPlan::Number(1.0),
            ExprPlan::Error(ErrorValue::NA),
            ExprPlan::Number(3.0),
        ]])],
    };
    // Interim: Array arg is evaluated in scalar context → #CALC!
    // The SUM evaluator receives #CALC! and propagates it.
    let v = eval_scalar_with_cache(&plan, &env, &registry, &cache);
    assert_eq!(v, Value::Error(ErrorValue::Calc));
}
```

**Severity: MEDIUM** — no current correctness bug, but missing a test that documents deliberate interim behavior and would catch a Phase 4.7.G regression.

### 7.4 Cross-eval-path: eval-site tests bypass binder

**PASS** (this is expected and correct, not a gap).

The eval-site tests construct `ExprPlan::Array(...)` directly without going through the binder. The binder tests construct `Expr::Array(...)` and go through `bind()`. These are orthogonal coverage axes. The eval-site tests exercise the evaluator's `ExprPlan::Array → #CALC!` path; the binder tests exercise the binder's arity+cell-kind validation. Together they cover both layers. No issue.

### 7.5 Evaluator latent assumption about array shape

**PASS.**

`eval_scalar` and `eval_scalar_with_cache` handle `ExprPlan::Array(_)` with a single arm that ignores the content entirely and returns `#CALC!`. They do not read `rows[0].len()` or `rows.len()` or perform any arithmetic on the array's shape. There is no latent assumption about uniform arity that could fail post-binder-bypass.

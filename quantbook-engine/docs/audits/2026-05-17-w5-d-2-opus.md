## MEDIUM

### MEDIUM-O-1

Subject: Cross-cutting lexer change ships with zero new lexer-level unit tests
Where: `crates/ql-formula-syntax/src/lexer.rs:536-583` (digit-leading dotted-segment branch) and the tests module at `lexer.rs:1765-1875`
Detail: W5-D-2 introduces a new lexer code path (the `if next_is_digit` branch starting at line 552) and a new error condition (the `saw_letter` check at line 569 — pure-digit segments rejected). The implementing commit adds *zero* `#[test]` functions in `lexer::tests` to pin this new behavior. The only happy-path coverage is the e2e tests in `distribution_fns_e2e.rs` (e.g. `t_dist_case_insensitive_lookup_works` which exercises `t.dist.2t`/`t.dist.rt`). A future refactor of `lex_ident_or_ref` could regress the digit-leading branch and the only failures would surface as "T.DIST.2T (unknown function)"-style errors in the e2e suite, not in lexer tests where regressions belong.

Missing lexer tests that should exist:
1. `T.DIST.2T` lexes to single `Token::Ident("T.DIST.2T")`.
2. `T.INV.2T` lexes to single `Token::Ident("T.INV.2T")`.
3. `T.DIST.RT` lexes correctly (covered by existing all-letter branch but should pin alongside).
4. `T.DIST.2` (digit-only suffix) → `Err(UnexpectedChar('.'))` — pins the new `saw_letter` check.
5. `A.B.2C` (multi-dot with digit-leading final segment) lexes correctly — pins forward compat for `CHISQ.DIST.RT`-style.
6. Lowercase `t.dist.2t` lexes to single `Ident("t.dist.2t")` (case preserved at lex time).
7. `T.DIST.2T$` and `T.DIST.2T1` still rejected by post-loop guard.

Note: the existing `orphan_dot_in_ident_position_errors` test at line 1822 still passes (verified by running `cargo test -p ql-formula-syntax orphan_dot`) because `VAR.1` lexes through the new digit-leading branch, reads `1`, exits with `saw_letter=false`, and returns `UnexpectedChar('.')`. The pre-W5-D-2 error char (`'.'`) is coincidentally the same as the new error char, which is why the test still passes — but the *reason* the error fires has changed (now it's `saw_letter` check instead of the lookahead reject). This is fragile coincidence-coverage, not principled regression coverage.
Recommendation: Add a dedicated `#[test] fn dotted_ident_w5d2_digit_leading_segments()` block in `lexer::tests` with the cases above. Particularly important: pin the `T.DIST.2T` and `T.DIST.2` (no-letter rejection) cases, since those exercise the two new branches end-to-end.
Severity rationale: MEDIUM. A cross-cutting lexer change without local pin-tests is a regression surface — the engine's lexer module has 441 unit tests for precisely this reason. The fact that the existing trailing-digit test still passes only by coincidence (new branch happens to return the same error char as the old branch) increases the risk: a future maintainer could easily break the digit-leading path without it surfacing in the lexer module. Not HIGH because correctness is verified end-to-end via e2e tests and the implementation itself is correct.

### MEDIUM-O-2

Subject: Module docstring "Excel canon" section is stale for T.* additions
Where: `crates/ql-functions/src/distribution_fns.rs:18-28`
Detail: The module-level docstring includes an "Excel canon (verified against Microsoft docs + LibreOffice 7.6)" section listing the 4 NORM.* functions with their arity + domain spec. W5-D-2 added 5 T.* functions but did NOT extend this section. A reader scanning the module-level docstring sees the title "W5-D-2 (this commit): T.DIST / T.DIST.2T / T.DIST.RT / T.INV / T.INV.2T" at line 5-6 but no canon spec for them — they have to drill into each fn's individual docstring.

The W5-D-1.1 closure for HIGH-O-2 (per the docstring at line 41-61) explicitly added an "IronCalc divergences" table at module level — establishing the pattern that *module-level canon docs are first-class*. W5-D-2 didn't follow this pattern.
Recommendation: Extend the "Excel canon" section to include the 5 T.* signatures:
- `T.DIST(x, deg_freedom, cumulative)` — 3 args. `cumulative=TRUE` → left-tailed CDF, `FALSE` → PDF. `df >= 1` (truncated to integer) else `#NUM!`.
- `T.DIST.2T(x, deg_freedom)` — 2 args. Two-tailed `P(|T| >= x)`. `x >= 0` AND `df >= 1` else `#NUM!`. Result clamped to `[0, 1]`.
- `T.DIST.RT(x, deg_freedom)` — 2 args. Right-tailed `P(T >= x)`. Negative `x` ALLOWED. `df >= 1` else `#NUM!`.
- `T.INV(probability, deg_freedom)` — 2 args. Left-tailed inverse CDF. `0 < p < 1` strict; `df >= 1`. Else `#NUM!`.
- `T.INV.2T(probability, deg_freedom)` — 2 args. Two-tailed inverse, returns `|x|`. `0 < p <= 1` (upper-inclusive); `df >= 1`. Else `#NUM!`.

Also: the "Implementation strategy" section at line 10-11 says "Numerical kernel reuses `statrs::distribution::Normal` (pinned to 0.18.0 in workspace deps — matches IronCalc's pin)." This is now inaccurate — for T.* the kernel uses `statrs::distribution::StudentsT`. Extend to mention both.
Severity rationale: MEDIUM. Module docstring is the first thing a new contributor reads when touching `distribution_fns`. Stale canon + stale kernel doc is more than a typo — it's a documentation regression that masks the W5-D-2 surface area. Easy to fix.

### MEDIUM-O-3

Subject: Module-level "Arg coercion" section silently inherits W5-D-2 behavior without saying so
Where: `crates/ql-functions/src/distribution_fns.rs:30-39`
Detail: The "Arg coercion" section says numeric args are coerced via `to_number_strict`, the `cumulative` flag via `to_logical`, and arity → `#VALUE!`. This was written for W5-D-1 NORM.* fns; it happens to also apply verbatim to W5-D-2 T.* fns. But:
1. The section doesn't mention the `df.trunc()` rule that applies to all 5 T.* fns. This is a new behavior specific to T.* (NORM.* doesn't truncate any arg).
2. The IronCalc divergence table at line 41-57 mentions `Boolean(true)` and `Text("0.5")` divergences but doesn't mention the additional T.*-specific divergences (e.g., the `result < 0.0` defensive reject in T.DIST.RT, the `clamp(0.0, 1.0)` in T.DIST.2T, the `.abs()` in T.INV.2T).

These behaviors are documented in each fn's docstring, but the module-level section misses the cross-cutting pattern.
Recommendation: Add a brief paragraph after the existing "Arg coercion" section like:
"**W5-D-2 (T.* fns)** additionally truncate `deg_freedom` to an integer via `.trunc()` before the `df >= 1` pre-check. Per IronCalc canon, T.DIST.2T clamps results to `[0, 1]` (defensive against fp overshoot near tails), T.DIST.RT rejects negative results (1-cdf can drift negative for extreme x), and T.INV.2T returns `.abs()` of the inverse CDF result."
Severity rationale: MEDIUM. The doc gap is real but not safety-critical — fn-level docs cover it. Flagged MEDIUM (not LOW) because the module docstring is the *organizing layer* of the file and the W5-D-1.1 closure of HIGH-O-2 set the precedent that cross-cutting policy lives at module level.

### LOW-O-2

Subject: `T.DIST.RT` does not use `finite_or_num` while other T.* fns do
Where: `crates/ql-functions/src/distribution_fns.rs:316-322`
Detail: T.DIST, T.DIST.2T, T.INV, T.INV.2T all route their kernel result through `finite_or_num(...)`. T.DIST.RT instead has an inline `if !result.is_finite() || result < 0.0` check + manual `Value::number(result)` return. This is because `finite_or_num` only checks `.is_finite()` — it doesn't check the `result < 0.0` defensive condition that T.DIST.RT (matching IronCalc) needs.

The inconsistency is justified — `finite_or_num` is a 2-line helper and adding a `result < 0.0` check to it would change behavior for all callers — but it creates stylistic drift between sister fns.
Recommendation: One of:
(a) Add an inline comment at line 316-319 explicitly noting "Cannot use `finite_or_num` here — needs the additional `result < 0.0` defensive check per IronCalc canon."
(b) Add a sibling helper `finite_nonneg_or_num(r)` for T.DIST.RT to keep the routing uniform.
(a) is cheaper and adequate.
Severity rationale: LOW. Code reads cleanly today; this is a maintainability hint, not a correctness issue.

### LOW-O-3

Subject: T.DIST.2T silently clamps catastrophic-error inputs via `.clamp(0.0, 1.0)`
Where: `crates/ql-functions/src/distribution_fns.rs:286-289`
Detail: The line `let result = (2.0 * upper_tail).clamp(0.0, 1.0);` is documented as defensive against fp overshoot near tails. But it also silently masks arbitrarily large errors: if statrs's `cdf` somehow returned 2.0 (catastrophic), `1.0 - 2.0 = -1.0`, `2 * -1.0 = -2.0`, `clamp(0, 1) = 0.0` — and we silently return `Value::number(0.0)` with no signal that something went wrong. Strict reading of the CLAUDE.md No-Fallbacks rule would flag this as a fallback.

In practice, statrs::ContinuousCDF::cdf is well-tested and won't return values outside [0, 1] except by tiny fp epsilons. IronCalc takes the same approach. Excel takes the same approach (silent clamp). The behavior is justified and matches canon.
Recommendation: No code change. Add a one-line comment at line 287 (next to the `.clamp(0.0, 1.0)`) explicitly acknowledging this: "Per IronCalc + Excel canon: silently clamp rather than `#NUM!` on near-boundary overshoot. statrs's cdf is well-bounded; this never fires in practice but is defensive."
Severity rationale: LOW. The principle question (strict No-Fallbacks application) is real, but the practical risk is zero (statrs is reliable) and aligning to IronCalc/Excel is the right call. Comment-only suggestion.

### LOW-O-4

Subject: T.INV.2T's `.abs()` is dead defense given the strict `p <= 1` domain check
Where: `crates/ql-functions/src/distribution_fns.rs:376`
Detail: `t_inv_2t` computes `target_cdf = 1.0 - p / 2.0` and then `dist.inverse_cdf(target_cdf).abs()`. For valid p in `(0, 1]`, `target_cdf` is in `[0.5, 1)`, so `inverse_cdf(target_cdf)` is always `>= 0` (Student's t is symmetric around 0; cdf(0) = 0.5; inverse_cdf of anything `>= 0.5` is `>= 0`). The `.abs()` is therefore never actually flipping a sign in the valid domain.

It matches IronCalc line-for-line, which has the same dead defense. Per W5-D-1.1 IronCalc-parity principle, leaving it is correct.
Recommendation: No code change. Optional: add a comment "`.abs()` is defensive — given the domain check `p <= 1.0`, target_cdf is `>= 0.5` so inverse_cdf is always `>= 0`. Matches IronCalc convention."
Severity rationale: LOW. Pure documentation suggestion.

### LOW-O-6

Subject: T.DIST.2T's "clamp at zero in far tail" test doesn't actually verify the clamp triggers
Where: `crates/ql-functions/src/distribution_fns.rs:987-997`
Detail: The test `t_dist_2t_clamped_at_zero_in_far_tail` asserts only `(0.0..=1.0).contains(&n)` for `T.DIST.2T(50, 2)`. For df=2 and x=50, `1 - cdf(50)` is small but well-defined (~1.96e-4) — `2 * that = 3.92e-4`, comfortably inside [0, 1]. The clamp doesn't actually fire here. The test pins "result is in [0, 1]" but doesn't pin "clamp is the reason."

For the clamp to actually fire (i.e., raw result outside [0, 1]) you'd need an input where `2 * (1 - cdf(x))` returns a numerically negative or > 1 value from statrs. This requires extreme df values or specific x boundaries — not easy to reproduce as a portable anchor.
Recommendation: Either rename the test to `t_dist_2t_far_tail_in_unit_range` to match what it actually verifies, OR add a comment explaining the test pins the invariant rather than the clamp-firing condition. Or find an input where the raw 2*(1-cdf) does measurably exceed 1.0 (likely none portable).
Severity rationale: LOW. The test is not wrong (the invariant is real) but the name promises more than the body delivers.

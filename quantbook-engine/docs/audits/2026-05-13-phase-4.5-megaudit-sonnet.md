# Phase 4.5 mega-audit — Sonnet verdict (W5-68 → W5-75)

**Branch:** `feat/quantbook-engine`
**HEAD:** `36470b7859d` (W5-75 V2 wave 4/6)
**Auditor:** Sonnet (running in parallel with Codex)
**Date:** 2026-05-13

## One-paragraph verdict

Phase 4.5 ships a 22-function date library on top of a clean three-tier
registry architecture. The 1900-leap-year-bug centralization in
`ql-types::date` is honest and self-consistent; the `ContextAwareFn` tier
+ `WorkbookEnv::eval_context()` plumbing is wired through both the
formula evaluator and the transaction commit path. **But Phase 4.5
ships with three real correctness issues that the test suite doesn't
catch.** First and most serious (HIGH-S3): `WEEKDAY` return types
12-16 are systematically OFF BY ONE — the `anchor = n - 11` formula
at `date_fns.rs:510` should be `anchor = n - 10`. Empirically
verified: `WEEKDAY(2024-01-02, 12)` (where 2024-01-02 is Tuesday and
RT=12 says Tuesday=1) returns 2 instead of 1. EVERY return type from
12 through 16 is wrong; the corresponding tests (lines 1696-1746) DO
NOT cover any RT in [12, 16]. This is a user-facing math bug that
would silently misclassify days in any workbook using non-default
weekday anchors. Second (HIGH-S1): `YEARFRAC(s, e, 0)` and
`DAYS360(s, e, FALSE)/360` are INTERNALLY INCONSISTENT — YEARFRAC
basis 0 falls through to European 30/360 while DAYS360 (default
method) implements the US NASD day-31 adjustment, so the same date
pair yields different fractional-year answers (concrete demo:
2024-01-31 → 2024-05-15 gives 104/360 vs 105/360, a 1-day-out-of-360
disagreement). DAYS360 already has the right algorithm; YEARFRAC just
needs to share it. Third (HIGH-S2): `edate_ctx`'s code comment at
lines 597-600 promises EDATE-into-Feb-1900 returns the phantom serial
60, but the implementation goes through system-agnostic
`days_in_month(1900, 2) = 28` and returns serial 59. This is a
code-doc mismatch — the comment overclaims behavior the code doesn't
deliver. (Whether real Excel returns 59 or 60 in this edge case is
debatable; the bug is internal-consistency.) Also notable: WEEKDAY's
RT-12-to-16 untested branch and the YEARFRAC basis-1 cross-year
approximation (365.25 hardcode, rustdoc overclaims "average-year-
length method") together signal the test gating wasn't tight. The
W5-69 dispatch wiring (range → context → scalar) is solid, the
cross-table disjointness invariant is correctly panicked at
registration, the schema v3 migration is mechanical, the
`set_date_system`-cache lifetime is OK because the setter is pre-load,
and the 7 dispatching tests in scalar.rs cover the ContextAwareFn
tier end-to-end. **Recommend W5-76 closure block on HIGH-S3 (WEEKDAY)
and HIGH-S1 (YEARFRAC/DAYS360). HIGH-S2 (EDATE doc mismatch) can be
closed by fixing the comment OR the behavior.**

## NEW HIGH (correctness / false confidence)

### HIGH-S1 — YEARFRAC basis 0 ≠ DAYS360 default (internal inconsistency)

**File:** `crates/ql-functions/src/date_fns.rs:741-812` (yearfrac_ctx)
and `crates/ql-functions/src/date_fns.rs:935-987` (days360_ctx).

The Phase 4.5 design doc § 5.1 (V1 wave) lists YEARFRAC basis 0 as
"US (NASD) 30/360" and DAYS360 default method as US NASD. Both
functions should produce the same fractional-year answer for the same
date pair when YEARFRAC's basis is 0 and DAYS360's method is FALSE
(default). They do NOT.

`yearfrac_ctx` basis-0 branch falls through to the European 30/360
algorithm (lines 801-807, the `0 | 4` match arm), which applies NO
day-31 → 30 adjustment beyond the raw subtraction. `days360_ctx`
default-method branch (lines 974-984) DOES apply the day-31
adjustments per the US NASD convention (sd=31→30 always; ed=31→30
when post-adjusted sd=30).

**Empirical demonstration** (verified by manual algebra,
re-derivable from the source):

  Start = 2024-01-31, End = 2024-05-15 (Excel1900):
  - YEARFRAC(s, e, 0) → European 30/360 → 360*0 + 30*(5-1) + (15-31)
    = 104. Fraction = 104/360 = 0.28888...
  - DAYS360(s, e, FALSE) → US NASD → sd=31→30, ed=15. Days = 360*0
    + 30*4 + (15-30) = 105. Fraction = 105/360 = 0.29166...
  - Disagreement: 1/360 day on the fractional-year scale.

This is filed as GAP-F-11 ("YEARFRAC basis 0 uses European 30/360 in
V1"), but GAP-F-11 only documents the YEARFRAC↔Excel divergence — it
does NOT mention that DAYS360 ALREADY implements the correct US NASD
math, making the V1 internal inconsistency self-inflicted rather than
an Excel-canon shortfall.

**Why this matters:** users writing `=YEARFRAC(A, B, 0)` and `=DAYS360(A, B) / 360`
in adjacent cells expecting agreement get divergent answers. Financial
spreadsheets routinely use both. The fix is mechanical: route
YEARFRAC basis 0 through the same US-NASD adjustments that
`days360_ctx` already implements — `~30 LOC of share-the-helper` work,
not a 50-LOC reimplementation.

**Required test:** add a pinning test that calls `yearfrac_ctx(start,
end, 0)` and `days360_ctx(start, end) / 360.0` for a date pair where
day-31 adjustment matters, asserting equality. This test does NOT
exist today.

### HIGH-S2 — EDATE phantom-edge: code comment promises behavior the code doesn't deliver

**File:** `crates/ql-functions/src/date_fns.rs:571-605` (edate_ctx).

Code comment at lines 597-600 promises:

> **W5-68 § 3.2 / serial-60 contract:** in Excel1900, if EDATE
> lands on (1900, 2, 29) (e.g., EDATE(1900-03-29, -1)), return the
> phantom serial 60. Otherwise route through ymd_to_serial which
> handles the phantom on its own.

The behavior does NOT match the comment. Walking through `edate_ctx(serial_of_1900_03_29, -1)`
(serial 89):

1. `(y, m, d) = (1900, 3, 29)` via `serial_to_ymd`.
2. `add_months(1900, 3, -1) = (1900, 2)`.
3. `max_day = days_in_month(1900, 2)` — returns **28** (real Gregorian;
   `days_in_month` is system-agnostic — see `date.rs:80-93`).
4. `clamped_d = d.min(max_day) = 29.min(28) = 28`.
5. `ymd_to_serial(1900, 2, 28, Excel1900) = 59`.

EDATE returns 59 (1900-02-28). The comment says it should return 60
(phantom 1900-02-29). This is a code-doc mismatch even if real Excel
itself returns 59 (which is plausible — Excel's documented EDATE
behavior clamps to the real month length, and the 1900-bug applies
inconsistently across functions per Microsoft's KB).

For an Excel-canon-faithful EDATE, the function should consult an
Excel-bug-aware day count for Feb 1900. Either:
- Special-case `(norm_y, norm_m) == (1900, 2)` in `edate_ctx` to
  use max_day = 29 (like `eomonth_ctx` lines 551-553 do explicitly).
- OR add a `days_in_month_excel(year, month, system)` helper that
  returns 29 for Feb 1900 in Excel1900.

**Severity:** the divergence only affects dates that land EDATE in
Feb 1900 — vanishingly rare in real-world workbooks, but the comment
explicitly advertises behavior the code doesn't implement, which is
worse than silent divergence. A user reading the source to understand
EDATE will form a wrong mental model.

**No test pins this.** `tests_wave2::edate_*` covers normal months
and clamp-shorter-month for 2024 / 2023, but NEVER touches the
1900-Feb phantom. (Compare `eomonth_feb_1900_returns_phantom_60` at
line 1775 which DOES pin the analogous EOMONTH behavior — the
asymmetry is suspicious.)

## NEW MEDIUM (overstatement, scope, missed test)

### MEDIUM-S1 — YEARFRAC basis 1 uses 365.25 for cross-year spans

**File:** `crates/ql-functions/src/date_fns.rs:787-800`.

Function-level rustdoc lines 727-734 says:

> `1` Actual/actual — uses real day count; denominator handles
> leap-year span via the average-year-length method.

The implementation does NOT use the average-year-length method; for
`ly != hy` it divides by the hardcoded constant `365.25`. The inline
comment on lines 791-793 admits this is an "approximation," but the
public doc-comment still claims "uses ... average-year-length method"
— which is misleading.

Real Excel basis-1 algorithm (per OpenOffice / IronCalc reference,
roughly):
- If year is the same: actual_days / year_len (this matches Quantbook).
- Else: actual_days / (sum of year_lengths_in_span / number_of_years).
  For 2024-01-01 to 2025-12-31 (730 days, 366-day + 365-day years):
  730 / ((366 + 365) / 2) = 730 / 365.5 ≈ 1.9973.
- Quantbook returns 730 / 365.25 ≈ 1.9986.

Divergence is small (~0.07%) but the rustdoc overclaims. Either fix
the algorithm OR fix the doc-comment to say "V1 approximation —
365.25 divisor; full Excel basis-1 algorithm deferred to Phase 4.10."

GAP-F-XX should be filed. No test pins this divergence.

### MEDIUM-S2 — EXPLICITLY_DEFERRED waiver bloat

**File:** `crates/ql-functions/tests/coverage.rs:194-223`.

22 new date entries added in W5-72/73/74/75, all with boilerplate
reasons like `"W5-72; covered by date_fns::tests"`. The W5-62 Codex
mega-audit specifically flagged this exact pattern ("EXPLICITLY_DEFERRED
is becoming a waiver list, not a coverage gate"). Phase 4.5 made it
materially worse.

The substantive concern: per-function-overrides matrix tests use
disciplined canon-vs-divergence tags (`*_canon_*`, `*_v1_divergence_*`).
Module-level tests like `tests_wave3::yearfrac_basis_3_actual_365` do
not. So a V1 divergence in a date function (e.g. the GAP-F-11 YEARFRAC
basis-0 fall-through) is pinned by exactly ONE test
(`yearfrac_default_basis_is_zero` which only verifies arg-arity
equivalence with `basis=0`), not by a `*_v1_divergence_basis_0_uses_european_30_360`
test that would fail loudly when GAP-F-11 is fixed without a test
update.

**Recommendation:** when GAP-F-11 closes (Phase 4.10), the waiver
should not silently roll into the matrix tests. Add a single
`yearfrac_basis_0_v1_divergence_uses_european_30_360` test that pins
the CURRENT (divergent) behavior with a comment "remove this test
when GAP-F-11 closes." Same pattern for GAP-F-09, GAP-F-10.

### MEDIUM-S3 — NETWORKDAYS / WORKDAY perf — O(n) loop, no fast path

**File:** `crates/ql-functions/src/date_fns.rs:676-684` (networkdays_ctx)
and `crates/ql-functions/src/date_fns.rs:704-722` (workday_ctx).

Both functions iterate one serial day at a time. For
`NETWORKDAYS(serial_jan_1_1900, serial_dec_31_9999)` that's ~2.95M
iterations per call. For `WORKDAY(start, 10_000_000)` that's 10M+
iterations. There's a closed-form solution for weekday counting
(integer division by 7 + boundary corrections) that would be O(1).

This is V1-acceptable for typical workbooks (small ranges), but at
the 4.7 array-formula expansion, range-applied NETWORKDAYS could
become a perf hazard. File as `PERF-F-01` or similar; not blocking V1.

### MEDIUM-S4 — WASM target NOW/TODAY behavior unverified

**File:** `crates/ql-types/src/eval_context.rs:92-110`, where
`NowProvider::System` calls `std::time::SystemTime::now()`.

The Phase 4.5 design doc § 3.2.1 explicitly says "on wasm32 SystemTime
panics — Phase 6.3 bindings will inject Test variant." But TODAY,
nothing in the code prevents the panic in WASM builds. There is no
`#[cfg(target_arch = "wasm32")]` conditional. There is no compile-fail
test ensuring the WASM build refuses to use `System`. A user who
builds the engine for wasm32 and calls NOW() at runtime gets a
service-killing panic.

The scaffolding contract in the doc-comment on lines 60-66 says
"callers must guard `System` behind a target check OR set `Test`
explicitly" — but the runtime makes no such guard. This is a
documented gap (GAP-T-01-adjacent), and the deferred WASM bindings
work (Phase 6.3) will need to address it; but it's worth pinning as a
known compile-time hazard. Suggest a `cfg_if!` block that swaps
`NowProvider::System` for a build-time error on `wasm32`, or at minimum
a runtime panic with a clearer message ("WASM target: call
`NowProvider::Test` from the JS callback instead").

### MEDIUM-S5 — `volatile::now` and `volatile::today` are dead code, not deprecated

**File:** `crates/ql-functions/src/volatile.rs:199-220`.

Registry no longer routes `NOW` / `TODAY` to these — they're shadowed
by `now_ctx` / `today_ctx` (registry.rs:349-350). The legacy fns are
not re-exported in `lib.rs`. They have no callers. Their doc-comments
say "Legacy scalar path retained for backwards compat" — but no
`#[deprecated]` attribute, no caller-guard. They're just orphan code.

Either:
- Mark `#[deprecated(note = "use volatile::now_ctx via the registry")]`.
- OR delete them and remove the dead-code comment hazard.

The "legacy compat" claim is weak — these are crate-internal `pub`
functions with no documented external dependency.

### MEDIUM-S6 — TIMEVALUE accepts no-space AM/PM suffix but rejects no-space prefix

**File:** `crates/ql-functions/src/date_fns.rs:362-419` (parse_time_text).

Code accepts `"12:00PM"` (no space, via `strip_suffix("PM")`) AND
`"12:00 PM"` (with space). But the parse silently coerces `"12 AM"` to
parse "12" as a single-element split and fail (`if mm > 59` early
check). No test pins `"12:00pm"` (lowercase) — the implementation

test for `"12:00 P.M."` (with periods) or `"12:00am"` (no space,
lowercase) — these are real-world variants Excel may accept.

Excel actually rejects most of these too — V1 scope is fine. But the
test coverage matrix is lopsided.

## Per-concern verdict

### A: 1900 leap-year bug correctness — CLEAN with one edge-case bug

`ql-types::date.rs` correctly handles serial 60 = phantom Feb 29 1900
in both directions (`serial_to_ymd` lines 193-195; `ymd_to_serial`
lines 237-240). Excel1904 with serial 0 returns the real epoch
correctly (line 522-525). Mid-implementation correction is consistent
in YEAR/MONTH/DAY (all route through `serial_to_ymd`); DATEVALUE works
via `ymd_to_serial`; EOMONTH explicitly special-cases Feb 1900
(lines 551-553).

**BUT** EDATE does NOT — see HIGH-S2 above. Code comment promises
phantom-60 return; implementation returns 59 due to system-agnostic
`days_in_month`. Asymmetry with EOMONTH is suspicious and the
acceptance is broken.

### B: EvalContext threading completeness — CLEAN

Dispatch order (range → context → scalar) verified in
`scalar.rs:146-181`. Cross-table disjointness panicked at registration
(`registry.rs:60-152`). `MapEnv` uses the trait default → Excel1900;
`WorkbookEnv` overrides correctly per env.rs:217-219. Transaction
path uses `WorkbookEnv::new(workbook)` (transaction.rs:376), so
formula-bearing-cell commits do see the workbook's date_system.

**One subtle observation:** `WorkbookEnv::new` reads `date_system`
once and caches it in `eval_ctx` (env.rs:94-97). If a workbook calls
`set_date_system` mid-session, an already-constructed WorkbookEnv
would carry stale ctx. But WorkbookEnv is short-lived (new'd per
transaction commit), and `set_date_system` is only public for tests
+ pre-load. Not a real risk today, but if Phase 4.6+ wires
`set_date_system` to a mid-session mutation (xlsx import path?),
this caching becomes a hazard.

## MEDIUM

### MEDIUM-1 -- PID-only PeerId is vulnerable to restart/reuse collision

**File:line:** `extensions/quantlab/src/quantbook/multiWindowDemo.ts:258`, `extensions/quantlab/src/quantbook/multiWindowDemo.ts:268`, `crates/ql-collab/src/session.rs:397`

The IDE derives `peerId` solely from `process.pid`, then constructs the session with that value. Core docs explicitly warn that concurrent sessions must use distinct peer ids and that duplicate ids corrupt the document via conflicting OpIDs. Two simultaneously-live VS Code windows will not share an OS PID, but PID reuse after a window/process restart is possible while another peer still retains the old peer's CRDT history.

**Concrete reproduction:** Run window A with PID `P` and window B. Let A append and B merge the op. Close A. Later start another window whose OS PID is reused as `P` while B still runs, then run the multi-window demo. The new session starts fresh but emits ops under the same `PeerId(P)` as A. B now receives ops from two logical sessions with the same peer id and overlapping Loro counters.

**Suggested closure:** Generate a per-demo-invocation random non-zero u64 peer id instead of using PID as identity. Reject `0` and `u64::MAX` before calling `new engine.CollabSession(...)`. Keep PID only as diagnostic text and, if needed, derive the demo row from a separate collision-handled display slot. This also sidesteps the 16-bit row collision from `pid & 0xffff` (`multiWindowDemo.ts:278`).

## LOW

### LOW-1 -- Simultaneous `connectOrSpawn` losers fail instead of retrying the winner's relay

**File:line:** `extensions/quantlab/src/quantbook/multiWindowDemo.ts:192`, `extensions/quantlab/src/quantbook/multiWindowDemo.ts:207`, `crates/ql-collab-ws/examples/relay-server.rs:60`

The symmetric design is connect-first, spawn-on-failure. If two windows start at the same time and both initial connects fail, both spawn. One relay binds; the second process exits before readiness due address-in-use. `spawnRelayBinary` rejects, and the losing window surfaces a fatal command error instead of trying one final connect to the relay that the winning window just started.

**Concrete reproduction:** Ensure no relay is running on 7117. Trigger `quantlab.quantbookDemoMultiWindow` in two VS Code windows at the same time. Both calls can pass the initial failed connect. One spawn binds and prints readiness; the other spawn fails bind before readiness. The second command reports a multi-window demo error even though the relay is now available.

**Suggested closure:** In `connectOrSpawn`, wrap `spawnRelayBinary(...)` in a catch that logs the spawn failure, then retries `engine.Transport.websocketConnect(RELAY_URL)` once before surfacing the error. That converts the address-in-use race into the same join-existing-relay path used by later windows.

### LOW-2 -- Relay shutdown is process termination, not explicit graceful task shutdown

**File:line:** `crates/ql-collab-ws/examples/relay-server.rs:71`, `extensions/quantlab/src/quantbook/multiWindowDemo.ts:318`

The relay main loop is an infinite accept loop with spawned per-connection tasks. There is no `tokio::signal` handling or cancellation path. IDE dispose calls `spawnedRelay.kill()`; Node's default signal is SIGTERM. SIGKILL cannot be graceful by definition, and SIGTERM/SIGINT currently rely on OS process termination to close sockets rather than a Tokio runtime shutdown path that lets tasks exit intentionally.

**Concrete reproduction:** Start the relay with connected clients, then send SIGTERM/SIGINT to the relay process. The process exits and sockets are reclaimed by the OS, but there is no code path that stops accepting, signals connection tasks, or awaits their completion.

**Suggested closure:** Either document the current demo contract as "process termination; OS reclaims sockets" or add a graceful shutdown path: `tokio::select!` the accept loop against `tokio::signal::ctrl_c()` (and Unix terminate where supported), track connection tasks in a `JoinSet`, close/cancel them, and then return from `main`.

### LOW-3 -- Connection id wrap can theoretically collide with a still-live connection

**File:line:** `crates/ql-collab-ws/examples/relay-server.rs:69`, `crates/ql-collab-ws/examples/relay-server.rs:79`, `crates/ql-collab-ws/examples/relay-server.rs:134`

`AtomicUsize::fetch_add` wraps on overflow. That avoids a panic, but if a connection with id `0` were still live when the counter wrapped back to `0`, the sender-side self-filter would treat frames between those two distinct connections as self frames and drop them.

**Concrete reproduction:** In a focused relay test, seed the counter near `usize::MAX`, keep the first wrapped-id connection alive, then accept enough clients to reuse the same `conn_id`. Frames between the two same-id clients will match `sender_id == conn_id` and be filtered at `relay-server.rs:134`.

**Suggested closure:** For V3.1 demo scale, documenting this as practically unreachable is acceptable. For hardening, use a random non-zero 128-bit/UUID-style connection token or maintain an active-id set that refuses reuse while a prior connection with the same id is still alive.

### LOW-4 -- `exitCode === null` is not a complete "child still alive" predicate

**File:line:** `extensions/quantlab/src/quantbook/multiWindowDemo.ts:315`

The dispose path checks `spawnedRelay.exitCode === null` before `kill()`. In Node, a process that exited due signal has `exitCode === null` and `signalCode` set. The idempotent `isDisposed` guard prevents repeated dispose calls inside the same demo instance, but if the child was externally signaled before dispose, this predicate still attempts to kill an already-dead child.

**Concrete reproduction:** Start the demo in the relay-owning window. Externally send SIGTERM to the relay child. When the demo later disposes, `exitCode` can still be `null` because the exit was signal-based, so the code logs and calls `kill()` on an already-exited child.

**Suggested closure:** Replace the predicate with a liveness helper such as `spawnedRelay.exitCode === null && spawnedRelay.signalCode === null`, optionally also checking `!spawnedRelay.killed` for cleaner logging.

### LOW-5 -- Reconnect-mid-flight remains untested

**File:line:** `extensions/quantlab/test/quantbook-roundtrip.test.ts:1851`, `.plans/_active.md:94`

The V3.1 mocha test proves the relay round trip, but it does not kill the relay after sessions are attached and assert that the IDE reconnect path behaves correctly. The active plan explicitly marks this as deferred.

**Concrete reproduction:** Remove the relay process after `sessA` and `sessB` attach in the current test shape. There is no existing test assertion for `transportLastError()` population, reconnect retry timing, disposed-mid-reconnect behavior, or successful restart after relay respawn.

**Suggested closure:** Add the deferred V3.1.d follow-up test: spawn the relay, attach two sessions, kill the relay mid-flight, assert the transport reports closed/error state, respawn on the same test port, then verify reconnect and resumed A <-> B propagation. Keep using a non-default test port.

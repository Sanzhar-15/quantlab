## Concern 1 — API coherence: naming conventions

**Verdict: MIXED — LOW**

The four new read accessors are internally consistent and match existing Workbook patterns:
- `spill_anchors()` matches `formats()` / `names()` (plural-noun accessor returning a table ref)
- `spill_anchor_at(sheet, row, col)` matches `formula_at(sheet, row, col)` exactly
- `spill_target_anchor(sheet, row, col)` is a compound with no close analog but is unambiguous

One naming inconsistency with existing mutators: `register_spill` uses the verb "register" where the rest of the Workbook API uses "put" (`put_formula`, `put_at`, `put_computed_at`). Conversely, "clear" is already used for the complementary operation so `clear_spill_at` fits. The verb mismatch is minor because "register" signals multi-step setup (the map-only nature + lack of overlay writes) while "put" implies writing through to storage. The distinction is defensible and the docstring makes it explicit. File as LOW polish.

**Citation:** `workbook.rs:581` (`register_spill`) vs `workbook.rs:726` (`put_formula`).

**Suggested fix (LOW, deferred):** Consider renaming `register_spill` → `put_spill` for consistency with the put/clear verb pair across the API. Or document the deliberate verb choice ("register = map-only, no overlay") in the method doc — the current doc does say "Map-only" but doesn't frame it as a naming rationale.

## Concern 2 — API coherence: coordinate-arg style (TUPLE vs separate args)

**Verdict: FAIL — MEDIUM**

This is the most concrete API inconsistency in the commit. The **mutating** spill methods take the anchor as a single `(SheetId, RowId, ColId)` tuple:

```rust
pub fn register_spill(&mut self, anchor: (SheetId, RowId, ColId), shape: SpillShape) -> ...
pub fn clear_spill_at(&mut self, anchor: (SheetId, RowId, ColId)) -> ...
```

Every other coordinate-taking method in `Workbook` uses **separate** `(sheet, row, col)` arguments:

```rust
pub fn put_at(&mut self, sheet: SheetId, row: RowId, col: ColId, value: Value)
pub fn put_computed_at(&mut self, sheet: SheetId, row: RowId, col: ColId, value: Value)
pub fn clear_computed_at(&mut self, sheet: SheetId, row: RowId, col: ColId)
pub fn clear_user_at(&mut self, sheet: SheetId, row: RowId, col: ColId)
pub fn clear_formula(&mut self, sheet: SheetId, row: RowId, col: ColId)
pub fn formula_at(&self, sheet: SheetId, row: RowId, col: ColId) -> ...
```

Even the new **read** accessors added in this same commit use separate args:

```rust
pub fn spill_anchor_at(&self, sheet: SheetId, row: RowId, col: ColId) -> ...
pub fn spill_target_anchor(&self, sheet: SheetId, row: RowId, col: ColId) -> ...
```

So within the four new spill methods, the reads use separate args and the writes use tuples. This is an internal inconsistency within the Phase 4.7.H surface itself.

The tuple style is inherited from `SpillAnchorTable::register(anchor, shape)` where the tuple is motivated by carrying the anchor as a conceptual unit. That's fine for the storage-layer type, but the Workbook facade should normalize to the existing API style.

**Impact:** The Runtime author (Phase 4.7.J) will call both `spill_anchor_at(s, r, c)` (separate) and `register_spill((s, r, c), shape)` (tuple) at the same site — ugly and likely to cause confusion about which functions take tuples vs flat args.

**Citation:** `workbook.rs:555–574` (reads, separate) vs `workbook.rs:581–586`, `workbook.rs:599–617` (writes, tuple).

**Suggested fix:** Change `register_spill` and `clear_spill_at` signatures to use flat args:

```rust
pub fn register_spill(&mut self, sheet: SheetId, row: RowId, col: ColId, shape: SpillShape) -> Result<(), SpillBlockError>
pub fn clear_spill_at(&mut self, sheet: SheetId, row: RowId, col: ColId) -> Result<(), SpillNotFoundError>
```

This requires updating the 6 workbook integration tests that currently pass tuples (e.g. `wb.register_spill((0, 0, 0), shape)` → `wb.register_spill(0, 0, 0, shape)`). The `SpillAnchorTable` layer may keep its tuple style unchanged since it explicitly handles the anchor as a unit in its two-map design.

## Concern 3 — `Default` derive on `Workbook`

**Verdict: PASS**

`SpillAnchorTable` derives `Default` at `spill.rs:139`. `HashMap::<K,V>::default()` produces an empty map for both `anchors` and `targets`, so `Workbook::default()` (and `Workbook::new()` which calls it) produce a workbook with an empty spill table. No regression possible.

## Concern 4 — `Clone` derive on `Workbook`

**Verdict: PASS**

The existing Clone doc at `workbook.rs:232–248` notes that Clone is "shallow with respect to Arrow chunk buffers" (Arc refcount bump for chunk data). `SpillAnchorTable` uses plain `HashMap`, not `Arc`-wrapped data. `HashMap<K,V>: Clone` produces a **deep copy** of all entries when all key and value types implement `Clone` — and they do:

- Keys: `(SheetId, RowId, ColId)` = `(u16, u32, u32)`, all `Copy + Clone`
- `anchors` values: `SpillShape { rows: u32, cols: u32 }`, derives `Clone`
- `targets` values: `(SheetId, RowId, ColId)`, `Copy + Clone`

After cloning a `Workbook`, modifying the clone's spill table does not affect the original. The Clone behavior is correct and arguably better than the Arrow chunk case (fully independent rather than Arc-shared). The existing Clone doc's "shallow" qualifier is scoped to chunk buffers and does not misrepresent the new field.

## Concern 5 — Test coverage: storage layer

**Verdict: MIXED — MEDIUM (missing boundary test) + LOW (no large-rectangle stress)**

**What is tested:** `cell_count`, `register`/`unregister`/`anchor_at`/`target_anchor` for 1x1, 5x1, 2x3, 2x2, 3x1, 3x3 rectangles, atomicity, degenerate-shape rejection, re-register after unregister, two disjoint spills, cross-sheet independence, `iter_anchors`. All 15 test functions pass.

**Gap 1 — boundary cell test (MEDIUM):** No test places an anchor near `MAX_ROW` / `MAX_COLUMN`. The design is explicit that bounds checking is the **runtime's** responsibility (§ 8.1 step b), but there is no test to document what the storage layer actually does when asked to register a spill that extends beyond the Excel grid. Concretely:

```
anchor = (sheet=0, row=MAX_ROW, col=0), shape=(2, 1)
```

The register loop computes `MAX_ROW + 1` as `u32` — no overflow (MAX_ROW = 1_048_575, u32::MAX = 4_294_967_295) — but it inserts a target entry for a logically out-of-bounds row. The storage layer silently accepts this. This is intentional per design, but a test documenting the behavior (even just asserting the registration succeeds and a target at `MAX_ROW+1` exists in the map) would lock in the "storage is bounds-agnostic" contract so a future reviewer doesn't add accidental defensive clamping.

**Citation:** `spill.rs:207–228` (register loop, no bounds check).

**Gap 2 — large rectangle (LOW):** No test with a 100×100 or MAX-row rectangle. The loops are O(rows×cols); for realistic SEQUENCE(1048575) a 1M-entry `targets` map is non-trivial. No functional bug, but a performance/stress note. Not a closure-blocker.

## Concern 6 — Test coverage: workbook layer

**Verdict: MIXED — LOW (anchor-cell clearing implicit, not explicit)**

**What is tested:**
- `register_spill` round-trip (table contents after register) ✓
- `clear_spill_at` clears computed overlays at every target ✓ — **this test implicitly covers the anchor cell**: the 1×3 spill at `(0,0,0)` writes computed at `(0,0,0)` (the anchor itself), `(0,0,1)`, `(0,0,2)` and asserts all three read `Blank` after `clear_spill_at`. The anchor overlay IS verified.
- `register_spill` rejects collision ✓
- `clear_spill_at` unknown anchor errors ✓
- `clear_spill_at` preserves user overlays outside rectangle ✓
- `spill_anchors` accessor returns table ✓

**Gap — anchor-cell clearing not called out by name (LOW):** The existing test at `workbook.rs:1349` covers anchor-cell clearing implicitly (cell (0,0,0) is both the anchor and the first cell cleared). However, the "anchor is its own target" invariant is the most subtle correctness property in the design. A dedicated test named `clear_spill_at_clears_anchor_cells_own_computed_overlay` — using a 2D spill where the anchor is visually distinct from the other targets — would serve as explicit documentation that the anchor cell is cleared like any other target.

**Persistence round-trip (OUT OF SCOPE FOR THIS PHASE):** `register_spill` then save+load round-trip is deferred to Phase 4.7.L per design § 7.3. The current `spill_anchors` field has no `Serialize`/`Deserialize` derive and the `qbook_format.rs` save loop makes no reference to it — the existing save path is unaffected. No regression.

## Concern 7 — Re-eval invariant (design § 8.3) and clear_spill_at idiom

**Verdict: PASS — with LOW note**

The documented idiom is consistent. Design § 8.1 step 2 says explicitly: "If `workbook.spill_anchor_at(s, r, c).is_some()`, call `workbook.clear_spill_at(...)`." The `clear_spill_at` docstring (`workbook.rs:597–598`) repeats the same instruction: "Callers that want a no-op-on-miss behavior should pre-check `spill_anchor_at(...).is_some()`."

Both sources prescribe the same pre-check idiom. The runtime author (Phase 4.7.J) has unambiguous guidance.

**LOW note:** an idempotent `clear_spill_if_present` convenience would reduce the chance of the runtime author omitting the pre-check. Currently the design relies on documentation. This is acceptable for a storage-layer API where pre-checking is cheap (one HashMap lookup) and the error type is named `SpillNotFoundError` (not `SpillError`), which somewhat signals "this shouldn't happen unexpectedly." File as LOW / ergonomic polish.

## Concern 8 — Concurrent invariant violations

**Verdict: PASS**

**Field visibility:** `Workbook::spill_anchors` (field) has no visibility keyword at `workbook.rs:274` — Rust default is private to the containing module (`workbook`). External crates cannot access the field directly.

**`&mut` accessor:** `spill_anchors()` at `workbook.rs:548` returns `&SpillAnchorTable` (immutable). There is no `spill_anchors_mut()` method. All mutations must go through `Workbook::register_spill` or `Workbook::clear_spill_at`. An external crate cannot obtain `&mut SpillAnchorTable` from a `Workbook`.

**Double-clear scenario:** If a caller calls `Workbook::clear_computed_at(s, r, c)` on a cell that is a spill target, then later calls `clear_spill_at`, the inner loop calls `sheet.clear_computed(arow+dr, acol+dc)` on an already-cleared cell. `clear_computed` on a cell with no computed overlay is a no-op in the `ColumnStore`/`SparseOverlay` layer — BTreeMap remove on a missing key returns `None` silently. Idempotent, no issue.

**Invariant violations by external code:** The `SpillAnchorTable` type is `pub` in `ql-storage`, and its `register`/`unregister` methods are also `pub`. External crates can construct a standalone `SpillAnchorTable` and call `unregister()` on it. This is irrelevant to the `Workbook`'s internal table (no `&mut SpillAnchorTable` escape path). The test at `spill.rs:353` accesses `t.targets.len()` directly — this is valid because the test lives in `mod tests` within `spill.rs`, which has access to the private fields of its parent module. Standard Rust pattern.

## What is needed for W5-101 closure

**Blocking (MEDIUM):**

1. **MEDIUM — Coordinate-arg style inconsistency:** `register_spill` and `clear_spill_at` take `anchor: (SheetId, RowId, ColId)` tuple while all other Workbook coordinate methods use separate `(sheet, row, col)` args. Fix before Phase 4.7.J uses these methods to avoid locking in the inconsistent calling convention across the runtime codebase.
   - Files: `workbook.rs:581–586`, `workbook.rs:599–617` + 6 integration tests.

2. **MEDIUM — Missing boundary-cell storage test:** Add a test that documents the storage layer's behavior for an anchor near `MAX_ROW` / `MAX_COLUMN` (registration succeeds, target at `MAX_ROW+1` exists in map). This locks in the "storage is bounds-agnostic; runtime is responsible for bounds" contract so Phase 4.7.J knows exactly where the enforcement must go.
   - File: `spill.rs` (new test in `mod tests`).

**Non-blocking (LOW / deferred):**

3. **LOW — Explicit anchor-cell overlay clearing test:** Add a test specifically named and scoped to verify the anchor cell's computed overlay is cleared by `clear_spill_at`. The invariant is already covered implicitly by the existing test, but an explicit test documents the "anchor is its own target" property.

4. **LOW — Idempotent `clear_spill_if_present` helper:** Add a thin Workbook method that pre-checks `spill_anchor_at().is_some()` and calls `clear_spill_at` only if present. Reduces the chance of a Phase 4.7.J author omitting the pre-check. Can be introduced at the start of 4.7.J rather than requiring a 4.7.H re-commit.

5. **LOW — `register_spill` verb alignment:** Consider renaming to `put_spill` to match the `put_formula` / `clear_formula` pair. Low priority; the "map-only, no overlay" distinction the doc describes is a good reason to keep a different verb if the team prefers it.

All PASS items (Default, Clone, design § 7 match, encapsulation, re-eval idiom doc) are solid. The two MEDIUM items are API-surface issues that will compound at Phase 4.7.J if not resolved beforehand.

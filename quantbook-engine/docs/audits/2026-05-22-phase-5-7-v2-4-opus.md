# Phase 5.7 V2.4 — Opus adversarial audit lane (Arc<Mutex> refactor + spawn_blocking)

## Scope

V2.4 closes V2.3's two convergent HIGH findings (Codex FAIL + Opus
PASS-WITH-FINDINGS HIGH-1 + HIGH-2) via Option (a) — refactor the napi
`CollabSession` wrapper to `Arc<parking_lot::Mutex<CoreCollabSession>>`.

Key V2.4 changes:
- Struct field `inner: CoreCollabSession` → `inner: Arc<Mutex<CoreCollabSession>>`.
- ALL `#[napi]` methods on `CollabSession` changed `&mut self` → `&self`.
- Sync methods acquire `self.inner.lock()` internally.
- `flushPendingToTransport` REINTRODUCED as `pub async fn(&self)` with
  `Arc::clone` + `tokio::task::spawn_blocking` + `inner.lock()` inside.
- The `unsafe` marker is GONE (napi-rs only requires `unsafe` on
  `&mut self` async).
- Send + Sync compile-asserts updated: both Send AND Sync asserted.
- New direct deps: `parking_lot = "=0.12.5"` + `tokio = { workspace = true }`.

This lane checks: did V2.4 ACTUALLY close V2.3's HIGH-1 (Rust UB) and
HIGH-2 (tokio starvation)? Did the Arc<Mutex> refactor introduce NEW
hazards (lock-held-across-panic state corruption, V8-thread blocking
on mutex contention, blocking-thread budget exhaustion)? Are the new
mocha tests vacuous or load-bearing? Rule 4 sweep for new claims.
No-fallback discipline.

## Verdict

**PASS-WITH-FINDINGS.** V2.4's two structural changes (`&mut self` →
`&self` everywhere + `spawn_blocking` for the async method) ACTUALLY
close V2.3's HIGH-1 and HIGH-2. Verified by reading
`napi-derive-backend-5.0.4/src/codegen/fn.rs:278-284` (the `FnSelf::Ref`
arm produces `let this: &#parent = Box::leak(Box::from_raw(this_ptr))`
— shared reference, not `&mut`). Multiple shared `&` aliases to the
same instance are sound by Rust's rules; mutation goes through the
Mutex's interior mutability. The `spawn_blocking` path runs on tokio's
blocking pool (default budget 512, separate from the worker pool;
verified via `tokio-1.50.0/src/runtime/builder.rs:288` —
`max_blocking_threads: 512`), so Condvar waits no longer occupy a
worker thread.

The Send + Sync claim verifies cleanly: `lock_api-0.4.14/src/mutex.rs:144`
shows `unsafe impl<R: RawMutex + Sync, T: ?Sized + Send> Sync for
Mutex<R, T>`. `CoreCollabSession: Send` (verified by the engine-side
compile assert at `ql-collab/src/session.rs:87-90`). Therefore
`Mutex<CoreCollabSession>: Send + Sync` and `Arc<Mutex<...>>: Send + Sync`.
The V2.4 binding-side `_ASSERT_BINDING_COLLAB_SESSION_SEND` at lib.rs:1058-1064
asserts both via `assert_send::<CollabSession>()` and
`assert_sync::<CollabSession>()` — Rule 4 positive proof in place.

**But**: V2.4 introduces TWO new hazards that V2.3's UB closure
implicitly traded off:

1. **HIGH-1**: V8 thread can be BLOCKED waiting on the mutex while
   `spawn_blocking` holds it during a Condvar wait. Specifically:
   when JS calls a sync method (e.g., `session.opCount()`) while a
   `flushPendingToTransport()` Promise is in-flight (its
   spawn_blocking task is mid-`flush_pending` Condvar wait holding
   the mutex), the sync method's `self.inner.lock()` blocks the V8
   thread for the duration of the Condvar wait. WebSocketTransport's
   Condvar wait can be up to 30+ seconds (or longer on a slow peer);
   the V8 event loop is frozen for that time. **This is a real IDE
   UX hazard** that the V2.4 docstring acknowledges in passing
   ("blocks until the lock is available") but doesn't surface as a
   V8-thread-freeze concern. The IDE will see UI hangs.

2. **HIGH-2 (Rule 4)**: the V2.4 module-level docstring at lib.rs:70-91
   still claims `Send + !Sync` for `CollabSession` — citing
   `Reference<T>: !Send when T: !Sync` as the cross-Worker isolation
   guarantee. **This claim is now stale**. The V2.4 struct docstring
   (line 239-243) AND the compile asserts (line 1058-1064) both
   correctly say `Send + Sync`. The module-level docstring contradicts
   the struct-level + compile-time truth. A maintainer reading the
   module header forms a wrong mental model; the safety argument from
   V1+V2.1+V2.2+V2.3 ("CollabSession: !Sync blocks cross-Worker
   sharing") is no longer load-bearing — V2.4 IS Sync, so a future
   worker_threads usage WOULD work concurrently (subject to the
   napi-rs Reference<T> single-thread-drop discipline). This is a
   Rule 4 anti-pattern at the META level: V2.4 updated the
   compile-time claim but not the documented rationale.

Rule 4 sweep beyond HIGH-2: V2.4 doesn't introduce any new !Send/!Sync
claims. The V1+V2.1+V2.2 `CoreCollabSession: !Sync` engine-side claim
is still correct (its `Option<Box<dyn Transport + Send>>` field is
`?Sync`), and that drives why the binding wraps in Mutex — Mutex<T>
becomes Sync regardless of T: Sync.

The 5 new V2.4 mocha tests pass but only ONE actually exercises the
mutex semantics meaningfully (the "interleaved sync during pending
async" test). The "concurrent JS callers serialize via Arc<Mutex>"
test is essentially vacuous on LoopbackTransport (whose `flush_pending`
is the trait-default `Ok(())` no-op — verified via
`ql-collab/src/transport.rs:238-240`). Both spawn_blocking tasks
complete in microseconds; there's no observable serialization to
demonstrate. The test pins the COMPILES + RUNS contract, not the
SERIALIZES contract. See MEDIUM-1.

## HIGH

### HIGH-1: V8 thread blocks on `self.inner.lock()` when a sync method is called while `flushPendingToTransport`'s spawn_blocking task is mid-Condvar-wait holding the mutex — IDE UI freezes for the Condvar wait duration (up to 30+ seconds on slow WebSocket peers)

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:794-804` (V2.4
async method) + ALL sync `#[napi]` methods on CollabSession (every
`self.inner.lock()` call site, e.g., line 333, 344, 386, 404, 423,
431, 438, 480, 499, 506, 523, 558, 603, 634, 661, 712, 733) +
`crates/ql-collab-ws/src/lib.rs:733-760` (`flush_pending`'s Condvar
wait loop, 100ms `wait_timeout` ticks).

**Specific issue**:

V2.4's `flushPendingToTransport`:

```rust
pub async fn flush_pending_to_transport(&self) -> Result<()> {
    let inner = Arc::clone(&self.inner);
    tokio::task::spawn_blocking(move || {
        let mut guard = inner.lock();   // <-- acquires Mutex
        guard.flush_pending_to_transport()  // <-- Condvar wait
    })
    .await
    .map_err(...)
}
```

The spawn_blocking task:
1. Acquires `inner.lock()` on a blocking-pool thread.
2. Calls `guard.flush_pending_to_transport()` which dispatches to
   `WebSocketTransport::flush_pending()` (when WS is attached).
3. WebSocketTransport's flush_pending enters a `cv.wait_timeout(counter,
   Duration::from_millis(100))` loop, blocking the calling thread until
   `progress.counter >= queued_count` OR `self.closed == true`.
4. **The MutexGuard is held for the ENTIRE Condvar wait** — there's no
   intermediate release in the spawn_blocking closure.

Meanwhile, on the V8 thread, JS code calls any sync method:

```ts
const p = session.flushPendingToTransport();  // spawn_blocking starts
const n = session.opCount();                  // V8 thread blocks here
await p;
```

`session.opCount()` runs on the V8 thread (napi sync method) and
executes:

```rust
pub fn op_count(&self) -> u32 {
    let inner = self.inner.lock();  // <-- V8 THREAD BLOCKS HERE
    u32::try_from(inner.op_count()).unwrap_or(u32::MAX)
}
```

`inner.lock()` blocks until the spawn_blocking task releases. Since
the spawn_blocking task is in `cv.wait_timeout(100ms)`, the V8 thread
sleeps for the full Condvar duration (could be seconds to minutes if
the WS peer is slow / unresponsive).

**The V8 thread IS the JS event loop.** When it blocks on a mutex,
the entire Electron renderer process's main event loop stalls — no
mouse / keyboard / animation frames process. The IDE looks frozen.

This is a regression from V1+V2.1+V2.2+V2.3's UX:
- V1-V2.2: no async methods → no concurrent access → no contention.
- V2.3: async method existed but had UB (V2.3 HIGH-1+HIGH-2). Sync
  methods would also race-UB but in practice "appeared" fast because
  there's no mutex blocking them.
- V2.4: closed the UB but introduced explicit blocking via mutex. The
  V8 thread CAN block for arbitrary duration.

**The V2.4 docstring acknowledges this but doesn't flag the V8-thread
implication.** Lines 784-788 say:

> Inside the blocking task, `inner.lock()` acquires the mutex.
> If a concurrent JS call holds the lock (e.g., another
> mid-flight method), this call blocks until the lock is
> available. No deadlock because mutex order is consistent
> (all session methods acquire the SAME mutex).

The framing is "the spawn_blocking task blocks waiting for JS" — but
the REVERSE is the IDE-killing case: "JS blocks waiting for the
spawn_blocking task." That reversed direction is missing from the
docstring entirely. The TS-side JSDoc (per types.ts pattern) similarly
won't warn IDE callers.

**Concrete IDE scenario**:

```ts
// User opens a new cell, the IDE adds an op
session.appendPutValue(0, 0, 0, 1);
// IDE auto-flushes on append:
session.flushDeltaToTransport(); // returns immediately (queued)
const p = session.flushPendingToTransport(); // spawn_blocking starts

// User types in another cell:
session.appendPutValue(0, 0, 1, 2); // <-- V8 blocks until WS writer drains
// User sees: cursor frozen, no typing echo. Could be 30s+ if WS slow.

await p;
session.appendPutValue(0, 0, 1, 2); // now unblocks
```

**Closure recommendation**: **FIX NOW**, before V2.7 megaudit. Two
options:

**Option A (recommended — engine-side refactor)**: split the engine's
`flush_pending_to_transport` into two halves:
1. A `&mut self` call that captures the current target (queued_count
   snapshot) and the transport's Condvar handle (Arc<(Mutex, Condvar)>).
2. A free-function or `&self` (Arc handle) that performs the Condvar
   wait WITHOUT the CollabSession mutex held.

Binding becomes:

```rust
pub async fn flush_pending_to_transport(&self) -> Result<()> {
    // Take a transport handle clone while we briefly hold the lock.
    let handle_opt = {
        let mut guard = self.inner.lock();
        guard.flush_pending_handle()  // returns Option<Arc<TransportProgress>>
    }; // lock released here
    let Some(handle) = handle_opt else { return Ok(()) };
    tokio::task::spawn_blocking(move || {
        // Condvar wait WITHOUT the CollabSession mutex held.
        handle.wait_for_drain()
    })
    .await
    .map_err(...)
    .and_then(|r| r.map_err(...))
}
```

This is the V2.3 audit's HIGH-1 Option B path resurrected. The
engine-side refactor cost is moderate (extract progress handle from
WebSocketTransport, add `flush_pending_handle()` to the Transport
trait or split into a helper). But it ELIMINATES the V8-block hazard.

**Option B (cheaper — release the mutex within the spawn_blocking
body)**: change the binding to release+re-acquire the mutex around
the Condvar wait:

```rust
tokio::task::spawn_blocking(move || -> Result<(), _> {
    // Take a transport handle reference under the lock.
    // (Requires the engine to expose a non-&mut-self way to peek
    // at the transport — see Option A for the path.)
    ...
})
```

If the engine refactor in Option A is too large for this cycle,
Option B without engine support is impossible (the Condvar handle is
behind the Mutex). Option A IS the right fix.

**Option C (cheapest, mitigation only)**: add `try_lock` paths to the
"hot" sync methods that callers might invoke during a pending flush
— `opCount`, `pendingOpCount`, `hasTransport`, `hasPendingFlush`,
`peerId` — and return a "busy" sentinel (or throw a JS Error) instead
of blocking the V8 thread. This is observable to JS but at least
keeps the event loop responsive.

```rust
pub fn op_count(&self) -> Result<u32> {
    let inner = self.inner.try_lock().ok_or_else(|| {
        Error::from_reason("session is busy (flushPending in progress); retry after await".to_string())
    })?;
    Ok(u32::try_from(inner.op_count()).unwrap_or(u32::MAX))
}
```

Trade-off: changes the JS API (now throws or returns a different
type). Breaking. Probably not the V2.4 path.

**Minimum (if no code fix)**: document the V8-block hazard PROMINENTLY
in the V2.4 docstring + TS JSDoc + V2 backlog entry, and add a mocha
test that demonstrates the hazard (assert a sync method called during
a pending flushPending blocks for measurable time > 100ms on a
Condvar-blocked transport). This converts a hidden hazard into a
documented one.

**Why HIGH**: this is a USER-VISIBLE UI freeze in normal IDE usage.
The V2.3 audit's HIGH-1 Option (a) closure plan said "engine refactor
to `Arc<parking_lot::Mutex<CoreCollabSession>>`" — V2.4 implemented
exactly that. But the hidden cost — sync method serialization
through the SAME mutex that the async holding — wasn't analyzed at
plan time. V2.4 ships with the UB closed but the IDE UX regressed.

**Likely opus-only**: Codex protocol lane reads source for runtime
behavior but may not trace the IDE UX implication. The protocol lane
verifies "no UB" + "spawn_blocking on blocking pool" — both true.
The "V8 thread blocks on mutex" is the consequential side effect
of correctness.

## MEDIUM

### MEDIUM-1: `concurrent JS callers serialize via Arc<Mutex>` mocha test is essentially vacuous — both flushPending calls on LoopbackTransport complete in microseconds (LoopbackTransport::flush_pending is the trait-default `Ok(())` no-op); the test doesn't observe mutex serialization

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:1211-1225`.

**Specific issue**:

```ts
test('flushPendingToTransport: concurrent JS callers serialize via Arc<Mutex> (V2.4 soundness contract)', async function () {
    this.timeout(10000);
    const session = createSession(1n);
    const [tA, _tB] = loopbackTransportPair();
    session.attachTransport(tA);

    const p1 = session.flushPendingToTransport();
    const p2 = session.flushPendingToTransport();
    await Promise.all([p1, p2]);
});
```

LoopbackTransport's `flush_pending` is the Transport-trait default
(verified at `ql-collab/src/transport.rs:238-240`):

```rust
fn flush_pending(&mut self) -> Result<(), TransportError> {
    Ok(())
}
```

So when `session.flushPendingToTransport()` is called on a session
with Loopback attached, the spawn_blocking body:
1. Locks the mutex (microseconds).
2. Calls `inner.flush_pending_to_transport()` → calls Loopback's
   no-op → returns `Ok(())` immediately.
3. Releases the mutex.

Total runtime: microseconds per call. Both spawn_blocking tasks
complete BEFORE there's any observable contention.

**The test PASSES regardless of**:
- Whether the mutex actually serializes correctly.
- Whether spawn_blocking actually runs on the blocking pool.
- Whether the `Arc::clone` is sound.
- Whether the V2.4 refactor closed V2.3's UB.

The test only verifies:
- The async fn body compiles and returns a Promise.
- The Promise resolves without throwing.
- Two concurrent calls don't deadlock (which would require a
  re-entrant lock acquisition).

A no-op binding that ignored the mutex entirely would ALSO pass this
test. The test doesn't observe any V2.4-specific behavior.

**Why this matters**: the test's docstring asserts "Two concurrent
flushPending calls must SERIALIZE on the internal mutex — no UB, no
deadlock, both resolve." The "no UB" part is structural (compile-time
soundness via `&self` codegen — already covered by the V2.4 design).
The "no deadlock" part is the only runtime contract this test
actually checks. The "serialize on the internal mutex" claim isn't
observable through this test.

**Closure recommendation**: V2 BACKLOG ITEM. Strengthen the test by
either:

**(a)** Switch to a transport that has a meaningful flush_pending
delay. The only V2.4 transport that does is WebSocketTransport, which
requires a relay. Approximately:

```ts
test('flushPendingToTransport: concurrent JS callers serialize via Arc<Mutex> (WebSocket, observable)', async function () {
    this.timeout(15000);
    const relay = await spawnWsRelay();
    try {
        const engine = loadQuantbookEngine();
        const tA = await engine.Transport.websocketConnect(relay.url);
        const session = createSession(1n);
        session.attachTransport(tA);

        // Append ops so flush_pending has work to do.
        for (let i = 0; i < 10; i++) {
            session.appendPutValue(0, 0, i, i + 1);
        }
        session.flushDeltaToTransport();

        // Concurrent calls must serialize without deadlock.
        const p1 = session.flushPendingToTransport();
        const p2 = session.flushPendingToTransport();
        const p3 = session.flushPendingToTransport();
        const start = Date.now();
        await Promise.all([p1, p2, p3]);
        const elapsed = Date.now() - start;
        // The first call may take many ms; the next two should be
        // very fast (writer already drained). Assert elapsed < 1000
        // — if mutex deadlock occurred, this would timeout at 15s.
        assert.ok(elapsed < 1000, `concurrent flushPending elapsed ${elapsed}ms`);

        session.detachTransport();
    } finally {
        await relay.close();
    }
});
```

**(b)** Add a SIBLING test that uses a `MockTransport` with an
artificial delay in `flush_pending`, exercises 3+ concurrent calls,
and asserts the elapsed time approximates `3 * delay` (proving
serialization) rather than `delay` (which would indicate parallelism,
i.e., a missing mutex). But this requires a test-only Transport impl
or wiring the LoopbackTransport with a configurable delay.

**Why MEDIUM**: V2.4's structural soundness is verified via napi-rs
source reading + compile-asserts; the test is icing. But the test
COULD catch a future regression (e.g., V2.5+ moves to a different
synchronization primitive that doesn't actually serialize) — and
without a meaningful delay, it can't.

### MEDIUM-2: `interleaved sync method during pending async is safe` mocha test relies on Loopback's instant flushPending — `session.opCount()` likely runs AFTER the spawn_blocking task has already completed, so the test doesn't actually exercise the mutex-contention path; the V8-block hazard (HIGH-1) is therefore unpinned by the test suite

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:1227-1243`.

**Specific issue**:

```ts
test('flushPendingToTransport: interleaved sync method during pending async is safe (V2.4 soundness)', async function () {
    this.timeout(10000);
    const session = createSession(1n);
    const [tA, _tB] = loopbackTransportPair();
    session.attachTransport(tA);

    const p = session.flushPendingToTransport();
    // Concurrent sync call on the same session. Acquires the
    // mutex; safe.
    const count = session.opCount();
    assert.strictEqual(count, 0, 'opCount visible mid-pending-async');
    assert.ok(session.hasTransport(), 'hasTransport visible mid-pending-async');
    await p;
});
```

Sequence on the V8 thread:
1. `session.flushPendingToTransport()` is called. This synchronously:
   - Calls the napi async-fn entry-point.
   - napi-rs spawns the future onto its tokio runtime.
   - The future body `Arc::clone(&self.inner); tokio::task::spawn_blocking(...)`
     runs once and yields a Pending state (spawn_blocking submits to
     the blocking pool, returns a JoinHandle::await pending).
   - JsDeferred is created. Promise object is returned to JS.
2. `session.opCount()` is called synchronously on the V8 thread.
   - This runs IMMEDIATELY without yielding to the event loop.

Between steps 1 and 2, the spawn_blocking task has been submitted to
the blocking pool but the V8 thread hasn't yielded yet. The blocking
pool's thread:
- Has to be picked from the idle pool.
- Has to start executing the closure.
- Calls `inner.lock()` — microseconds.
- Calls `flush_pending_to_transport()` on Loopback — Ok(()) instantly.
- Releases the mutex.

This entire sequence takes microseconds. On a fast machine, the
spawn_blocking task may complete BEFORE the V8 thread reaches step 2.
On a slow machine or under contention, the V8 thread MAY reach step
2 before spawn_blocking completes; in that case, `opCount()` would
contend on the mutex (microsecond wait) and proceed.

**The test ALWAYS passes** because:
- Even if spawn_blocking finished first: opCount sees the released
  mutex, runs through cleanly, returns 0.
- Even if opCount tried first: it briefly contends on the mutex
  (microsecond wait — Loopback's flush_pending is instant), then
  succeeds.

**What the test does NOT verify** (the V2.4 HIGH-1 hazard):
- Sync method called while spawn_blocking is doing a LONG Condvar
  wait. The Loopback transport never does this.

**Concrete missing test** (the one that WOULD pin HIGH-1):

### MEDIUM-4: V2.4 spawn_blocking budget — tokio's blocking pool default is 512 threads, but napi-rs's tokio runtime is a process-wide singleton; this budget is SHARED across all CollabSession instances AND any future spawn_blocking sites. **Repo**: engine (and napi-rs external).
**File:line**: `crates/ql-bindings-node/src/lib.rs:780-783` (claim) +
`napi-3.9.0/src/tokio_runtime.rs:31-34` (runtime creation, no
max_blocking_threads override) + `tokio-1.50.0/src/runtime/builder.rs:288`
(default 512).

**Specific issue**:

V2.4 docstring claims:

> `tokio::task::spawn_blocking`, which runs on a dedicated
> blocking thread (NOT a tokio worker). The Condvar wait
> doesn't occupy the napi-rs runtime's worker pool — closes
> V2.3 HIGH-2 (runtime starvation).

This is TRUE in the small. But "dedicated blocking thread" implies
"infinitely available." Tokio's blocking pool is sized to

napi-rs runtime at `napi-3.9.0/src/tokio_runtime.rs:31-34` uses
defaults — NO override).

**Hazard scenarios**:
1. **Many concurrent flushPending calls**: 600 sessions each calling
   `flushPendingToTransport` concurrently. The first 512 occupy the
   blocking pool; the 513th queues. The blocking pool tasks may be
   in Condvar waits, so they don't release for many seconds. Calls

2. **Other spawn_blocking sites in the engine or its deps**: Loro's

   pool with our flushPending calls, they contend.
3. **Cumulative leakage**: a spawn_blocking task in an infinite loop

   holds 1 of the 512 slots. The system slowly degrades over
   process lifetime.

already busy." For an IDE running for hours with N sessions, the
budget could become a real constraint.

- (a) Document the 512 budget explicitly in the V2.4 docstring +

- (b) Switch the napi-rs runtime to a customized one (via

**Why MEDIUM**: the V2.4 docstring framing implies infinite
blocking-thread availability. The 512 budget is enough for most IDE
scenarios but not all. V2.5+ may legitimately exhaust it (e.g.,
multi-workspace + multi-session + Loro internal compactions). Add
the documentation now; the deeper fix tracks HIGH-1.

### MEDIUM-5: V2.4 has no `catch_unwind` protection — `inner.lock()` returns a `parking_lot::MutexGuard` that releases on drop (including panic-drop), but `CoreCollabSession` is NOT documented as panic-safe; a panic mid-mutation leaves the Mutex unpoisoned (parking_lot semantics) and the next caller acquires a possibly half-corrupt session

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs` (all sync methods +
the async method) + `crates/ql-collab/src/session.rs` (no panic-safety
docs).

**Specific issue**:

`parking_lot::Mutex` does NOT poison on panic (unlike `std::sync::Mutex`).
This is documented behavior (see `parking_lot-0.12.5/src/raw_mutex.rs:259-260`).
The semantics:

1. Thread A acquires the lock, starts mutating `CoreCollabSession`.
2. Thread A's closure panics partway through (e.g., a Loro internal
   `unreachable!()` or assert).
3. parking_lot's MutexGuard drops, releasing the lock.
4. **The CoreCollabSession is left in a half-mutated state.**
5. Thread B acquires the lock and reads/mutates the corrupt state.

V2.4 has no `catch_unwind` at any layer:
- napi-rs's V1+V2+V2.4 binding has explicitly DECLINED `catch_unwind`
  (V1 audit closure: "pre-validate inputs rather than catch_unwind").
- The spawn_blocking closure isn't wrapped in `catch_unwind`.
- The engine's `flush_pending_to_transport` isn't documented as
  panic-safe (verified: no RefUnwindSafe / catch_unwind / panic
  contract docs in the engine).

If a panic occurs:
- The spawn_blocking task's panic propagates to the JoinHandle. The
  binding correctly maps `JoinError` to a JS error
  ("flushPendingToTransport task: {e}").
- BUT the mutex is released, and the session is potentially corrupt.
- The next mutator call on the same session sees the corrupt state
  and may panic again, OR commit a corrupt op log (worse — the
  corruption persists across saves).

**Codex's V2.3 audit FAIL was about UB.** V2.4 closes the UB but
INTRODUCES a soft-state-corruption hazard via panic-with-half-mutation.
The hazard severity depends on how reachable panics are inside Loro's
internals. The V1 megaudit Opus-B M2 backlog tracked "engine-level
assert_*! is NOT a safe boundary for FFI"; V2.4 strengthens this
because the panic is now CAUGHT (by spawn_blocking's JoinHandle) but
not REASONED ABOUT.

**Closure recommendation**: V2 BACKLOG ITEM. Three layers:

1. **Engine-side**: document `CoreCollabSession`'s panic-safety
   contract. Loro itself uses `RefCell` internally — if the panic
   came from a borrow conflict, the state could be partially
   committed to LoroDoc. Explicitly state: "On panic mid-mutation,
   subsequent calls on this session may observe an inconsistent
   state; the session should be discarded and reconstructed from
   a snapshot."
2. **Binding-side**: wrap the spawn_blocking closure (and ideally
   sync methods too) in `std::panic::catch_unwind` to convert
   panics into JS errors that explicitly signal "session is now
   poisoned, reconstruct from snapshot." This makes the soft-corruption
   hazard EXPLICIT to JS callers.
3. **Test-side**: add a mocha test that:
   - Triggers a known engine panic (e.g., via a future debug-only
     `__panic_for_test` method on CollabSession).
   - Asserts the subsequent call on the same session throws with a
     specific "session is poisoned" message.
   - Asserts that creating a new session from the last-known-good
     snapshot recovers.

Pre-V2.4, the panic-corruption hazard existed but was MASKED by the
fact that subsequent calls would themselves operate on `&mut
CoreCollabSession` and (if the panic happened during `&mut`) Rust's
exclusive-access rules would have surfaced any aliasing issues at
compile-time-or-near-it. V2.4's interior mutability via Mutex<>
means the corruption is INVISIBLE to the type system; only runtime
behavior can catch it.

**Why MEDIUM**: the hazard is real but not yet exploited (V2.4
mocha tests don't trigger panics). Closing requires engine-side docs
+ a panic-safety contract. Not blocking V2.4 ship; tracking for V2.5+.

### MEDIUM-7: Performance — `parking_lot::Mutex` doesn't have a read/write distinction; pure-read methods (`opCount`, `pendingOpCount`, `hasPendingFlush`, `peerId`, `transportLastError`, `hasTransport`, `autoFlushPolicy`) all acquire the full mutex even though they only read. For high-frequency polling (IDE status bar polling opCount per frame), this serializes against any concurrent mutator. RwLock or atomic snapshots would be faster

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:402-440` (multiple
read-only methods) + others (V2.1+V2.2 methods).

**Specific issue**:

V2.4's pure-read methods all do:

```rust
pub fn op_count(&self) -> u32 {
    let inner = self.inner.lock();  // <-- exclusive lock
    u32::try_from(inner.op_count()).unwrap_or(u32::MAX)
}
```

Even though `inner.op_count()` is a pure read of an internal counter,
the mutex acquisition is EXCLUSIVE. Concurrent calls to `opCount`
from multiple threads would serialize through the mutex (though
napi-rs's class instance is V8-thread-only in practice, so this
serialization is invisible most of the time).

The HIGH-1 hazard interacts here: if `flushPendingToTransport` holds
the mutex during a Condvar wait, EVERY pure-read sync method blocks
the V8 thread. An IDE status bar polling `session.opCount()` every
frame would block during a flush.

**Closure recommendation**: V2 BACKLOG ITEM. Two paths:

**(a) RwLock**: switch `Arc<Mutex<T>>` to `Arc<RwLock<T>>`. Read-only
methods take `read()`, mutator methods take `write()`. parking_lot's
RwLock is fair and reader-prioritized; multiple `opCount` calls can
proceed concurrently. Downsides: the engine's API doesn't distinguish
&self from &mut self consistently (everything takes &mut self
currently), so the binding would have to know which methods are
read-only — fine but error-prone.

**(b) Atomic snapshots**: for the hottest read fields (op_count,
peer_id, has_transport), maintain atomic mirrors in the binding's
CollabSession wrapper. e.g.:

```rust
pub struct CollabSession {
    inner: Arc<Mutex<CoreCollabSession>>,
    op_count_atomic: Arc<AtomicU64>,
}
```

Each mutator method takes the mutex, mutates, AND updates the atomic.
Pure reads return from the atomic without locking. Downsides: more
state to keep in sync; race window between atomic update and lock
release is benign for monotonic counters but tricky for non-monotonic
state.

Probably (a) is the right path — RwLock is a small change.

**Why MEDIUM**: doesn't break anything today; performance hazard
that compounds with HIGH-1. If HIGH-1 closes via engine refactor
(Condvar handle extraction), this MEDIUM becomes moot. If HIGH-1
closes via the cheaper Option C (try_lock), this MEDIUM still
applies.

**Specific observation**:

The pattern:

```rust
let inner = Arc::clone(&self.inner);

    let mut guard = inner.lock();
```

is the canonical "share a Mutex across a spawned task" idiom. Both
`Arc::clone` and `Mutex::lock` are uncontended-fast (atomic-CAS for
the Arc refcount increment + atomic-CAS for the lock acquisition).
The closure captures `inner` (the Arc, not the wrapper struct), so
the spawn_blocking task is independent of the napi class instance's
lifetime — `Arc`'s ref-counting keeps the inner alive as long as
either the wrapper OR the spawned task holds a reference.

No performance OBS to flag here; the idiom is clean.

### OBS-2: The V2.4 `flushPendingToTransport` body has TWO error mapping sites — JoinError (spawn_blocking task panic) → JS error, then inner Result → JS error. The order is correct (`?` propagation handles the JoinError first), but a future maintainer could accidentally swap them. Pattern is brittle

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:800-803`.

**Specific observation**:

```rust
.await
.map_err(|e| Error::from_reason(format!("flushPendingToTransport task: {e}")))?
.map_err(|e| Error::from_reason(format!("{e}")))
```

The `?` after the first `map_err` propagates the JoinError → JS
error. The second `map_err` converts the inner `Result<(), CollabSessionError>`'s
error variant to a JS error. The chain works.

A future maintainer adding intermediate logic between these two
`map_err`s could break the contract (e.g., logging the JoinError but
not the inner). This isn't a current hazard, just a noted brittleness.

A tidier idiom:

```rust
let join_result = tokio::task::spawn_blocking(move || {
    let mut guard = inner.lock();
    guard.flush_pending_to_transport()
}).await;

match join_result {
    Ok(Ok(())) => Ok(()),
    Ok(Err(engine_err)) => Err(Error::from_reason(format!("{engine_err}"))),
    Err(join_err) => Err(Error::from_reason(format!("flushPendingToTransport task: {join_err}"))),
}
```

More verbose but clearer intent. Trade-off; not a fix.

### OBS-3: V2.4's `parking_lot::Mutex` choice is correct over `std::sync::Mutex` for this case — std::sync::Mutex's poison flag would surface a `PoisonError` on lock() after a panic, requiring the binding to handle PoisonError. parking_lot's no-poison choice trades off panic-safety visibility for ergonomics. The MEDIUM-5 hazard (silent corruption on panic) is the cost of that trade

**Repo**: engine.

**Specific observation**:

This is a design choice with trade-offs:

- **std::sync::Mutex**: PoisonError lets the next caller SEE that a
  panic occurred. The binding could map PoisonError to a JS error
  "session is poisoned, reconstruct from snapshot."
- **parking_lot::Mutex**: no poison flag. Next caller is unaware of
  the prior panic. Silent corruption (per MEDIUM-5) is the cost.

V2.4 went with parking_lot. The Cargo.toml comment justifies this
("no poison flag, no syscall on uncontended path") but doesn't
acknowledge the trade-off cost (corruption visibility).

For the spawn_blocking task specifically, the JoinError IS the panic
signal — so panics aren't silent at the FFI layer. The corruption
risk applies to the NEXT call after a panic, not the panicked call
itself.

Not a fix; just noted as a forward-design consideration.

### OBS-4: V2.4's `Send + Sync` enables future workflows that V1-V2.3 couldn't — e.g., multiple napi `ThreadsafeFunction`s could share a CollabSession reference. Whether the IDE will use this is a V3+ question, but the trait bound is now available

**Repo**: engine.

**Specific observation**:

Pre-V2.4 (`CollabSession: Send + !Sync`):
- A single napi `Reference<CollabSession>` couldn't be cloned across
  threads (Reference<T>: !Send when T: !Sync).
- Each napi callback ran on the V8 thread; CollabSession was
  V8-thread-local in practice.

Post-V2.4 (`CollabSession: Send + Sync`):
- A `Reference<CollabSession>` could be cloned across threads
  (Reference<T>: Send when T: Sync). Subject to napi-rs's
  Reference<T>: !Send constraint (which is itself separate from
  the inner T's bounds — Reference<T> always !Send for
  drop-thread-locality reasons).
- The underlying CollabSession is now thread-safely shareable at
  the Rust level.

The V2.4 module-level docstring's "Reference<T> !Send blocks
cross-Worker" argument STILL holds for IDE-facing scenarios — but
the SAME mechanism would allow a future "background sync worker"
pattern where the engine itself spawns tokio tasks that share a
CollabSession via Arc<Mutex>. V2.4 enables that pattern; V1-V2.3
didn't.

Not a hazard; an unlock for future features.

## Rule 4 sweep result

**Two new POSITIVE behavior claims in V2.4**:

1. **CollabSession: Send + Sync** (struct doc + compile-assert at
   lib.rs:1058-1064). VERIFIED via:

     T: ?Sized + Send> Sync for Mutex<R, T>`.
   - `ql-collab/src/session.rs:87`: `CoreCollabSession: Send`
     compile-assert.
   - parking_lot::RawMutex: Sync (always — atomic-CAS internals).
   - Therefore Mutex<CoreCollabSession>: Sync. Composition with Arc
     yields Send + Sync.
   - Rule 4 positive proof: compile-asserts present at line 1058-1064.

2. **napi-rs `&self` codegen produces `&'static CollabSession`**
   (claim at lib.rs:775-777). VERIFIED via:
   - `napi-derive-backend-5.0.4/src/codegen/fn.rs:278-284`: the
     `FnSelf::Ref` arm generates `let this: &#parent = Box::leak(Box::from_raw(this_ptr));`
   - This produces a SHARED `&'static CollabSession`, not `&'static mut`.
   - Multiple aliasing reads of the same instance are sound by
     Rust's rules.
   - Rule 4 positive proof: source citation should be ADDED to the
     docstring (MEDIUM-3). The claim is true but uncited.

**One ANTI-PATTERN carried**: the module-level docstring at lib.rs:70-91
still asserts `Send + !Sync` — directly contradicting compile-asserts
at line 1058-1064 (see HIGH-2 above). This is the V2.3 audit's

don't match compile-time truth.

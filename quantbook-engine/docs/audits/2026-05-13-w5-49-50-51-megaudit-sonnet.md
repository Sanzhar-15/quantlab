# Sonnet mega-audit — W5-49/50/51

## Verdict (one paragraph)

W5-50 is the most important commit and its core correctness logic is sound: the Graph revocation APIs (`clear_outgoing`, `clear_range_deps_for_formula`), the StripeIndex reverse index, and the Tarjan supplemental adjacency all implement the W5-49 decision faithfully. The H3/H4/H1 scenario tests are genuine and pass. However, there is one confirmed HIGH bug: `on_clear_formula` calls `remove_formula_deps` but NOT `graph.clear_outgoing` or `graph.clear_range_deps_for_formula`, leaving stale graph edges and stripe entries behind whenever a formula cell is cleared (rather than rebound). This is the same class of staleness that W5-50 was specifically built to fix — and it was missed for the clear path. W5-51 (trig batch) is correct but has a doc-title error in the `atan2` rustdoc (says `ATAN2(y, x)` in the signature line but the implementation and tests use the correct `(x, y)` Excel order). W5-49 is a decision doc and its claims about Codex effort estimates are honest. No false cycles, no determinism breaks, and no test-count fraud were found, though per-file counts in commit messages have minor off-by-one errors that net to zero.

## W5-50 (graph correctness fix — the main audit target)

### HIGH

**BUG: `on_clear_formula` does not revoke graph edges or stripe entries.**

File: `quantbook-engine/crates/ql-exec/src/calcgraph_session.rs`, lines 721-731.

```rust
pub fn on_clear_formula(&mut self, sheet: SheetId, row: RowId, col: ColId) {
    self.hook_counts.clear_formula = self.hook_counts.clear_formula.saturating_add(1);
    if let Some(node) = self.cell_index.get(&(sheet, row, col)).copied() {
        self.remove_formula_deps(node);   // ← session-side only
        self.dirty.remove(&node);
    }
    self.mark_dirty_from_cell_write(sheet, row, col);
}
```

`remove_formula_deps`'s own docstring at line 533 says: "Does NOT touch the `Graph`'s stripe state or edges — those are revoked separately by the caller via `Graph::clear_outgoing` + `Graph::clear_range_deps_for_formula` (W5-50)." The caller here is `on_clear_formula`, and it does neither. The result: clearing a formula that previously depended on A1 leaves a stale outgoing edge from the cleared formula's NodeId pointing to A1, and any range deps remain in the stripe index. Concrete failure:

```
1. set_formula(B1, "=A1")   → outgoing[B1] = [A1], incoming[A1] = [B1]
2. set_formula(A1, "=B1")   → outgoing[A1] = [B1], Tarjan: A1↔B1 cycle → #CIRC!
3. clear_formula(B1)        → session-side: remove_formula_deps(B1), dirty.remove(B1)
                            → BUT outgoing[B1] still = [A1], incoming[A1] still = [B1]
4. (later edit that makes both A1 and B1 dirty)
   schedule_dirty()         → Tarjan sees stale B1→A1 + real A1→B1 → false #CIRC! again
```

This is the exact H3 class of failure that W5-50 was designed to eliminate, reproduced on the clear path. The fix requires adding two lines inside the `if let Some(node)` block:

```rust
self.graph.clear_outgoing(node);
self.graph.clear_range_deps_for_formula(node);
```

No test covers the clear path for graph-level staleness — the existing test `clear_formula_evicts_self_and_dirties_downstream` (line 1883) only checks the session-side dirty set, not graph edges or stripe state.

### MEDIUM

**build_range_supplemental produces duplicate G entries when F has multiple ranges that both contain G.**

File: `calcgraph_session.rs`, lines 1002-1012.

The inner loop over `ranges` iterates per range; for each range it iterates the full `dirty_addrs` list. If F has `SUM(A:A) + SUM(A:A)` (same range twice — possible after a re-bind if the dedup in `extract_and_register_deps` missed it) or more practically `SUM(A1:A10)` and `SUM(A1:A5)` (two ranges that both contain the same G at A3), G will be pushed twice into `supplemental[F]`. Tarjan re-traverses the back-edge on the second hit but handles it correctly (the `indices.contains_key` check prevents re-visiting). However, the Vec grows unnecessarily, and the topo test `supplemental_does_not_duplicate_existing_real_edge` only covers real-edge + supplemental-edge deduplication, not supplemental + supplemental. This is a latent inefficiency but not a correctness bug today. It will worsen as Phase 4.3 V2 adds multi-range functions.

**`remove_formula_deps` docstring is misleading about caller responsibilities.**

The docstring says "those are revoked separately by the caller via `Graph::clear_outgoing` + `Graph::clear_range_deps_for_formula` (W5-50)." This is true for `extract_and_register_deps` but false for `on_clear_formula`, making the gap invisible from the doc. The docstring implies a contract that only one of two callers honors.

### LOW

- W5-50 commit message says "+4 unit tests" for `edges.rs` but the actual count is +5 (the functions `clear_outgoing_returns_prior_targets_and_empties`, `clear_outgoing_on_node_with_no_edges_is_empty`, `clear_outgoing_oob_panics`, `remove_back_pointer_removes_all_matching_entries`, `remove_back_pointer_preserves_others` = 5 new tests). Similarly "+7 unit tests" for `graph.rs` but the actual count is +8 (the 8 functions listed at lines 729-929). The total "+35" delta is correct; the per-file breakdown in the commit message is off by 1 in two files that cancel out.

- The revision counter bumps for both `clear_outgoing` and `clear_range_deps_for_formula` even when no-op (empty edges / no range deps). Since these are called on every `extract_and_register_deps`, the revision counter advances 2 extra ticks per formula bind regardless of whether any state changed. This is harmless today but could confuse cache-validity checks that use `graph.revision()` as a cheapness proxy if they see spurious bumps.

### Test gaps

- **Missing: graph-edge staleness after `on_clear_formula`.** No test confirms that `graph.outgoing(cleared_formula)` is empty after clear, nor that `incoming` on the former deps no longer includes the cleared formula's node.
- **Missing: stripe staleness after `on_clear_formula`.** No test confirms that `dependents_for_cell` no longer returns the cleared formula as a dependent after clear.
- **Missing: supplemental duplicate-G scenario.** No test for a formula F with two ranges that overlap, both containing G, verifying that `supplemental[F]` either deduplicates G or that Tarjan handles the duplicate correctly.
- **Missing: VEQ (value-equality short-circuit) interaction with supplemental.** Codex's watch list (decision doc, "Implementation watch list") explicitly named "VEQ behavior for range-dep formulas (Phase 3.8 short-circuit + supplemental edges must compose)." No test in W5-50 covers this. If VEQ short-circuits a formula that appears in the supplemental adjacency, the supplemental edge is correctly NOT followed (non-dirty target), so this is safe today — but the interaction is untested.
- **Missing: `schedule_dirty` called with an already-empty dirty set.** The `schedule_dirty_with_empty_dirty_is_empty_schedule` test exists — good — but there is no test that schedule_dirty also clears `self.dirty` (it uses `drain()`, so it does), which could trip up callers that check `dirty_formulas()` after scheduling.

## W5-51 (trig batch)

### HIGH
None. The implementations are correct.

### MEDIUM

**Rustdoc title for `atan2` says `ATAN2(y, x)` — the wrong arg order.**

File: `quantbook-engine/crates/ql-functions/src/scalar_fns.rs`, line 819:

```rust
/// `ATAN2(y, x)` — two-argument arc tangent. Returns radians in
```

The implementation correctly uses `args[0]` as `x` and `args[1]` as `y` (Excel order: `ATAN2(x_num, y_num)`), and the actual call is `y.atan2(x)`. The doc title inverts the argument labels, which is confusing to anyone reading the signature. The function body, the inline comment at line 843, and the test `atan2_basic_quadrants` are all correct. This is a documentation-only error but could mislead a future maintainer.

### LOW

- The ATAN2 doc says "Excel argument order is `ATAN2(x, y)` historically — but the W3C / OOXML standard and modern Excel use `ATAN2(x_num, y_num)`." This framing implies there was a historical inversion, but Excel has always used `ATAN2(x_num, y_num)`. The "historically" qualifier is misleading. Minor.
- ATAN2 arity error returns `ErrorValue::Value` for wrong arg count. Excel returns `#VALUE!` for this case — correct. But 0 args and 3+ args both return `#VALUE!` — Excel returns `#VALUE!` for 0 args and some versions error differently for 3+ args. The behavior is acceptable.
- Blank coerces to 0.0 in the ATAN2 implementation (`NumericArg::Skip => 0.0`). This means `ATAN2(0, 0)` where both args are blank returns `#DIV/0!` — which matches the explicit zero-zero check. But `ATAN2(blank, 1)` returns `ATAN2(0, 1) = π/2`, not an error. Excel behavior here varies by version; this may be acceptable but is untested.

### Test gaps

- **Missing: trig with infinity input.** `SIN(f64::INFINITY)` → NaN → `sanitize_f64` → `#NUM!`. No test for infinity input to any trig function.
- **Missing: negative zero input.** `TAN(-0.0)` — behavior is well-defined (returns -0.0) but untested. 
- **Missing: ATAN2 with one blank arg.** `ATAN2(blank, 1)` is not tested.
- **Missing: ASIN/ACOS with NaN input.** The domain check `!(-1.0..=1.0).contains(&n)` correctly rejects NaN (NaN is not contained in any range), returning `#NUM!`. This is the right behavior but it is not explicitly tested.
- The commit claims the compat coverage script "unchanged at 40%." The matrix update flips one row to ✅ but adds no new rows to the 217-row matrix. Coverage is correctly unchanged. No concern.

## Cross-cutting concerns

### CONCERN-1 (function-signature scope discovery)

The W5-51 commit honestly declares the gap: "batch ordering revised to lead with the scalar-only work that fits the existing `ScalarFn = fn(&[Value]) -> Value` contract." The W5-49 decision doc's stop-condition list says "Phase 4.3 V2 actually requires FormulaRegion for function SEMANTICS (not just perf)" but this is framed around FormulaRegion (Option B), not the simpler `ScalarFn` arity problem. The actual blocker for SUMIF is not FormulaRegion — it's that the function dispatch contract cannot distinguish "this argument is a range reference" from "this argument is a scalar." This is a narrower infrastructure problem than FormulaRegion, and the W5-49 doc does not mention it.

This is (a) a legitimate scope discovery and (b) a real doc gap. Defensible as (a) because W5-49 was about graph correctness, not function-call infrastructure. Not fully defensible as (b) because the implementation outline explicitly says "Phase 4.3 V2 (SUMIF/COUNTIF/lookup family) is gated on GAP-G-01 + GAP-G-03 shipping" without noting any function-infra prerequisite. A reader of the decision doc would expect V2 to start immediately after W5-50, and it cannot. The W5-49 doc should have noted that range-aware functions also need a function signature extension.

Codex's review listed this as a stop condition using the FormulaRegion framing but implicitly assumed `fn(&[Value]) -> Value` could somehow carry range metadata without modification. That's a Codex miss too.

### CONCERN-2 (determinism of build_range_supplemental)

The brief's analysis is correct. `dirty_vec` is sorted before `build_range_supplemental` runs (line 952-953: `dirty_vec.sort()`). `dirty_addrs` is built from `dirty_vec` in sorted order. The inner `for &(g, ...) in &dirty_addrs` iterates in sorted order. So `supplemental[F]` ends up with G's in sorted-by-NodeId order. Tarjan looks up by key (not by HashMap iteration order), so HashMap randomization is irrelevant. Determinism holds end-to-end. No bug found.

One subtle note: if F has multiple ranges (e.g., `SUM(A:A) + SUM(A:A)`), the outer loop over `ranges` iterates them in the order stored in `formula_to_range_deps`. That order is the insertion order from `register_range_dependency`, which is the AST walk order from `walk_plan_for_deps`. This is deterministic for the same plan. Confirmed.

### CONCERN-3 (self-edge in supplemental)

The self-edge behavior is correct and intentional. `A1 = SUM(A1:A10)` where A1 is at row 0, col 0: `range_contains_rowcol(A1:A10, 0, 0)` returns true (row 0 is in `start_row..=end_row`, col 0 is `start_col..=end_col`). So `supplemental[A1] = [A1]` (self-loop). Tarjan's self-loop detection at line 254-266 correctly checks `supp_self_loop` via the supplemental map. The test `supplemental_self_loop_is_cycled` (topo.rs line 567) and `self_range_cycle_via_supplemental` (calcgraph_session.rs line 2313) confirm this. No bug.

Excel would also treat `=SUM(A1:A10)` at cell A1 as a circular reference. Behavior is correct.

### CONCERN-4 (cross-sheet range deps)

The `build_range_supplemental` code resolves the range sheet with `Graph::range_ref_sheet(range).unwrap_or(fs)` (F's sheet) and then checks `gs == resolved_sheet`. For intra-sheet ranges (where `sheet: None` resolves to F's sheet), only G's on F's sheet are included. For explicitly cross-sheet ranges (where `sheet: Some(other)` is set), only G's on that other sheet would be included. This is structurally correct.

However, as noted in the brief: Phase 3.3 sets `range.sheet = Some(_)` always during binding, so the `unwrap_or(fs)` fallback is currently unreachable. The future cross-sheet case (Phase 4.6) will work correctly if the binder sets `sheet: Some(target_sheet)` for cross-sheet refs. The one risk: if a future binder sets `sheet: None` for cross-sheet refs and relies on context, the supplemental builder would incorrectly scope G's to F's sheet. This is a latent risk, not a current bug.

### CONCERN-5 (W5-51 trig edge cases not covered)

The brief's analysis is accurate:
- `TAN(FRAC_PI_2)`: test asserts `v > 1e10`. Actual value is `f64::tan(std::f64::consts::FRAC_PI_2)` = approximately `1.633e16`. The threshold `1e10` is loose but correct.
- `SIN(INFINITY)` → NaN → `#NUM!`: untested (confirmed missing, see Test gaps above).
- Negative zero: untested.
- NaN through ASIN domain check: `!(-1.0..=1.0).contains(&NaN)` = true → returns `#NUM!` before calling `f64::asin`. Correct, untested.
- ATAN2 blank arg: untested.

### CONCERN-6 (perf of clear paths on first-bind)

Confirmed cheap. On first-time bind of a formula node:
- `edges.clear_outgoing(formula_node)`: `std::mem::take(&mut self.outgoing[idx])` on an empty `Vec<NodeId>` → returns empty vec → zero iterations over drained list → zero back-pointer removals. One revision bump.
- `stripes.clear_for_formula(formula_node)`: `formula_to_stripe_keys.remove(&formula_node)` → HashMap remove of absent key → O(1) no-op. Zero stripe iterations.

No perf concern for initial load path. The revision counter bumps twice per formula bind (once per clear call), which is the only overhead.

### CONCERN-7 (cargo audit re-run)

The W5-51 commit claims "cargo audit ✓ (1 pre-existing allowed warning)." W5-51 added no new dependencies (only `scalar_fns.rs`, `registry.rs`, and `excel-matrix.md` were changed). The cargo audit status is plausible as unchanged from W5-50. Cannot independently verify in this sandbox (no `cargo` in PATH), but there is no reason to doubt the claim given no Cargo.toml change.

## Recommended follow-up (W5-52 fix scope)

### HIGH issues that MUST be fixed

1. **`on_clear_formula` must call `graph.clear_outgoing(node)` and `graph.clear_range_deps_for_formula(node)`.** Add both calls after `remove_formula_deps(node)` at line 724 in `calcgraph_session.rs`. Add a regression test: set a formula with a range dep and a cell dep, clear it, then verify `graph.outgoing(node).is_empty()` and `graph.dependents_for_cell(...)` no longer returns the cleared node.

### MEDIUM issues worth fixing

2. **Deduplicate G in `build_range_supplemental`.** Add a `HashSet<NodeId>` per F inside the supplemental builder (or a post-pass `dedup` on each Vec) to prevent the same G from being pushed multiple times when F has overlapping ranges. Or, at minimum, add a test documenting the current behavior.

3. **Fix the `atan2` rustdoc title.** Change `` `ATAN2(y, x)` `` to `` `ATAN2(x_num, y_num)` `` to match Excel's argument label convention and the implementation.

4. **Document the `ScalarFn` signature gap in the W5-49 decision doc (or add a new GAP entry).** The Phase 4.3 V2 prerequisite notes in MASTER-PLAN.md should call out that SUMIF/COUNTIF/VLOOKUP also need a function-dispatch extension, not just the GAP-G-01/G-03 graph fixes.

### LOW issues to defer or document

5. **`remove_formula_deps` docstring**: clarify that the contract "revoked separately by the caller" applies to `extract_and_register_deps` only, and that `on_clear_formula` must also honor it. (This is now fixed by item #1, but the docstring should be updated to avoid future confusion.)

6. **Revision counter spurious bumps on first-bind**: document this is expected, or add a "no edges, no revision bump" fast-path in `clear_outgoing` if benchmarks show measurable impact.

7. **Missing trig edge-case tests** (infinity input, NaN input to ASIN/ACOS, ATAN2 blank arg): defer to Wave 2 trig batch (SINH/COSH/TANH) or a separate test-coverage pass.

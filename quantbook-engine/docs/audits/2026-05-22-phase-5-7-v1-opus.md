# Phase 5.7 V1 audit -- Opus adversarial lane

Cross-repo audit of the FIRST IDE binding to the quantbook engine via napi-rs.
Engine commit `677ee03ee8b` (new `crates/ql-bindings-node/` crate) + IDE commit
`1a7fc8bbe3f` (loader + types + session wrapper + demo command + 10 mocha tests).

Codex lane runs the protocol/correctness audit separately. This lane focuses on:
- Adversarial / careless / malicious-caller paths through the FFI surface
- Edge cases where docstrings overstate what's verified
- Future-IDE-engineer footguns where assumptions don't hold
- napi-rs threading + panic-safety claims (Rule 4 sweep)
- CLAUDE.md no-fallback rule scan

## Methodology

1. Read both repos' Phase 5.7 V1 diffs in full.
2. Walked the napi-rs 3.9.0 + napi-derive-backend 5.0.4 source to verify:
   - Catch-unwind opt-in/opt-out semantics (`napi-derive-backend/src/codegen/fn.rs:217`)
   - JS Number to Rust u16/u32 conversion path (`napi-3.9.0/src/bindgen_runtime/js_values/number.rs:46-58`)
   - BigInt to u64 path (`napi-3.9.0/src/bindgen_runtime/js_values/bigint.rs:95-101`)
   - Uint8Array `as_ref` to raw pointer (`napi-3.9.0/src/bindgen_runtime/js_values/arraybuffer.rs:653-661`)
   - Class instance Send/Sync constraints (`napi-3.9.0/src/bindgen_runtime/callback_info.rs:90-126`)
   - Reference<T> Send/Sync constraints (`napi-3.9.0/src/bindgen_runtime/js_values/value_ref.rs:33-42`)
3. Engine Rule-4 sweep: grep on `ql-collab/src/session.rs` + `ql-oplog/src/log.rs`
   + `ql-oplog/src/op.rs` + `ql-oplog/src/wire.rs` for all `panic!`, `unreachable!`,
   `unimplemented!`, `todo!`, `assert!`, `assert_eq!`, `assert_ne!`, `debug_assert*`,
   `.unwrap()`, `.expect(` in **non-test** code, then traced reachability from the
   nine FFI entry points.
4. Concrete adversarial input table — what happens when a careless or malicious
   JS caller passes each edge value to each FFI method.

## Summary

**Verdict: PASS-WITH-FINDINGS.** The V1 ship is sound at the substrate level — the
one panic path the smoke test caught (PeerId(0) → `assert_ne!` → Node abort) is
correctly closed by the FFI pre-validator. No additional engine-side panic paths
reachable from the V1 FFI surface were found (the other two `assert_ne!`s in
`OpLog::set_peer_id` and `CollabSession::from_snapshot` are also for `peer_id==0`,
guarded by the same FFI helper). However, the audit found:

- **Three HIGH findings**: (1) cache-poisoning bug in `loadQuantbookEngine` when
  the loaded module fails the smoke-check, (2) JS Number `-1` silently coerces to
  `u32::MAX` for row/col args via ECMAScript ToUint32 + `try_into::<u32>()`
  succeeding, (3) lib.rs module doc claims `#[napi]` wraps each entry point in
  `catch_unwind` — confirmed FALSE per napi-derive-backend 5.0.4 codegen (it's
  opt-in via `#[napi(catch_unwind)]`, which the binding does NOT use).
- **Eight MEDIUM findings**: Send/Sync docstring inaccuracy on the napi
  threading model, loader walk-up sibling collision risk, SharedArrayBuffer
  data-race exposure, NaN/Infinity passthrough on f64 value, u32::MAX silent
  clamp on op-count overflow, IDE-test coupling to engine error-vs-Ok semantics,
  silent CI-pass risk if engine binary isn't built, 6-hop fallback can land on
  wrong directory.
- **Six LOW findings + seven OBS** detailed below.

All findings have closure recommendations. Most should land in-cycle as a
follow-up commit pair (engine + IDE).

## HIGH-1: loader.ts cache-poisoning bug

**Severity**: HIGH
**Repo**: IDE
**Citation**: `extensions/quantlab/src/quantbook/loader.ts:140-180`

The `loadQuantbookEngine()` function assigns `cachedModule = fakeModule.exports as
...` on **line 169** BEFORE the smoke-check on lines 172-178 validates the
exports surface. If the smoke-check throws, `cachedModule` is left pointing at
the bad module object. The very next call to `loadQuantbookEngine()` short-
circuits via lines 141-143 (`if (cachedModule !== undefined) return cachedModule;`)
and returns the POISONED module. The consumer code (e.g., `createSession`) then
hits `new engine.CollabSession(...)` where `CollabSession` is undefined → cryptic
`TypeError: engine.CollabSession is not a constructor` at the call site, instead
of the actionable "missing expected exports" diagnostic the loader was supposed
to surface.

This is a precise instance of the "value || default that masks ... state"
pattern CLAUDE.md's no-fallback rule warns about — except here the masking is on
the SECOND call, not the first. The first call's diagnostic is correct; the
cache-poisoning makes the failure mode regression-prone for repeated calls.

**Closure recommendation (in-cycle, IDE side)**:

```ts
const loaded = fakeModule.exports as unknown as QuantbookNativeModule;
if (typeof loaded.version !== 'function' || typeof loaded.CollabSession !== 'function') {
    throw new Error(
        `Quantbook engine at ${enginePath} loaded but is missing expected exports. ` +
        `Got: ${JSON.stringify(Object.keys(loaded))}. ` +
        `Expected at least: version(), CollabSession constructor.`,
    );
}
cachedModule = loaded;
return cachedModule;
```

Move the assignment to AFTER the smoke check passes. Add a regression test:
inject a partial module (mock `dlopen` to leave `exports` empty), verify the
SECOND call also throws (not just the first).

## HIGH-2: JS Number -1 silently becomes u32::MAX for row/col

**Severity**: HIGH
**Repo**: engine (binding side); IDE if validation lives there
**Citation**: `crates/ql-bindings-node/src/lib.rs:152` (`appendPutValue` signature
`row: u32, col: u32`); via napi-rs 3.9.0
`src/bindgen_runtime/js_values/number.rs:46-58`

Walked the napi-rs 3.9.0 `FromNapiValue` impl for u32:
1. `napi_get_value_uint32(env, val, &mut ret)` — per Node-API spec, applies
   ECMAScript `ToUint32` algorithm. `ToUint32(-1) → 0xFFFFFFFF`.
2. `ret.try_into::<u32>()` — `ret: u32`, so `try_into::<u32>` always succeeds.
3. The Rust `appendPutValue` receives `row = 4294967295` (u32::MAX).

So when a JS caller passes `appendPutValue(0, -1, 0, 42)`, the engine
**silently writes to row u32::MAX** without any error. The same applies to
JS Number `4294967296` (one past u32::MAX) — `ToUint32(4294967296) = 0` →
`appendPutValue` receives row=0. Silent wrap.

Other silent-coercion cases through the same path:
- `appendPutValue(0, 2.5, 0, 42)` → row = 2 (silent floor toward zero)
- `appendPutValue(0, NaN, 0, 42)` → row = 0 (ToUint32(NaN) = 0)
- `appendPutValue(0, Infinity, 0, 42)` → row = 0 (ToUint32(Infinity) = 0)
- `appendPutValue(-1, 0, 0, 42)` (sheet u16) — different path: u16 uses
  `napi_get_value_uint32` then `try_into::<u16>()` which FAILS for `0xFFFFFFFF`,
  so this case correctly throws "Failed to convert u32 to u16". Asymmetric:
  u16 is safe, u32 (row/col) is unsafe.

This is a HIGH because a careless IDE engineer wiring a cell-grid UI in V2/V3
could pass a column index from a UI control that allows negative values (e.g.,
keyboard navigation that goes off-grid). The op silently lands at
`row = u32::MAX` corrupting the workbook state with no error visible to the IDE
or user.

**Closure recommendation (in-cycle, engine binding side)**:

Add explicit non-negative + finite validation in `append_put_value`:

```rust
#[napi(js_name = "appendPutValue")]
pub fn append_put_value(&mut self, sheet: u16, row: u32, col: u32, value: f64) -> Result<()> {
    // u32 args silently accept JS Number -1 via ECMAScript ToUint32 → u32::MAX.
    // ... but they were already through ToUint32 by the time we see them.
    // Push validation to the TS wrapper layer where we can see the JS value.
    ...
}
```

Better: surface the validation at the TS-wrapper layer (`session.ts`) since
that's where JS-side semantic checks belong:

```ts
export function appendPutValue(s: CollabSessionInstance, sheet: number, row: number, col: number, value: number): void {
    if (!Number.isInteger(sheet) || sheet < 0 || sheet > 0xFFFF) {
        throw new Error(`appendPutValue: sheet must be an integer in [0, 65535], got ${sheet}`);
    }
    if (!Number.isInteger(row) || row < 0 || row > 0xFFFFFFFF) {
        throw new Error(`appendPutValue: row must be an integer in [0, 4294967295], got ${row}`);
    }
    if (!Number.isInteger(col) || col < 0 || col > 0xFFFFFFFF) {
        throw new Error(`appendPutValue: col must be an integer in [0, 4294967295], got ${col}`);
    }
    if (!Number.isFinite(value)) {
        throw new Error(`appendPutValue: value must be finite, got ${value}`);
    }
    s.appendPutValue(sheet, row, col, value);
}
```

(Note: the TS-side `Number.MAX_SAFE_INTEGER` is 2^53-1 = 9007199254740991, well
above u32::MAX, so passing a JS Number near u32::MAX is representable.)

Add adversarial tests:
```ts
test('appendPutValue rejects negative row', () => {
    const s = createSession(1n);
    assert.throws(() => s.appendPutValue(0, -1, 0, 42), /row must be/);
});
test('appendPutValue rejects fractional col', () => {
    const s = createSession(1n);
    assert.throws(() => s.appendPutValue(0, 0, 2.5, 42), /col must be/);
});
test('appendPutValue rejects NaN value', () => {
    const s = createSession(1n);
    assert.throws(() => s.appendPutValue(0, 0, 0, NaN), /finite/);
});
test('appendPutValue rejects Infinity value', () => {
    const s = createSession(1n);
    assert.throws(() => s.appendPutValue(0, 0, 0, Infinity), /finite/);
});
```

## HIGH-3: lib.rs module docstring falsely claims napi-rs wraps entry points in catch_unwind

**Severity**: HIGH (documentation drift; convergent with smoke-finding context)
**Repo**: engine
**Citation**: `crates/ql-bindings-node/src/lib.rs:14-17`

Module doc claims:
> "panic safety: napi-rs wraps each `#[napi]` entry point in a `catch_unwind`
> and surfaces panics as JS exceptions (no Node process crash)."

Walked napi-derive-backend-5.0.4 `src/codegen/fn.rs:217-240`:

```rust
let function_call = if self.catch_unwind {
    quote! {
        {
            std::panic::catch_unwind(|| { #function_call })
                .map_err(|e| { ... })
                .and_then(|r| r)
        }
    }
} else {
    quote! { #function_call }
};
```

The `catch_unwind` wrap is **conditional on `self.catch_unwind`**, which is set
only when `#[napi(catch_unwind)]` opt-in is present (parser at
`src/parser/mod.rs:892`). The Phase 5.7 V1 binding uses bare `#[napi]`,
`#[napi(constructor)]`, `#[napi(factory)]`, and `#[napi(js_name = "...")]` —
**NONE** include `catch_unwind`. So Rust panics during these calls **propagate
across the FFI boundary undefined** → "failed to initiate panic, error 5,
aborting" → Node process aborts.

The commit message correctly identifies this empirically ("napi-rs 3.x's
default panic handler did NOT reliably catch this into a JS exception during
the smoke test"). The lib.rs module-doc was not updated to match.

This matters because future maintainers reading the docstring will believe the
"panic safety" claim and may relax the FFI pre-validator (e.g., remove the
`peer_u64 == 0` check believing the engine's panic will be caught). The
docstring needs to be corrected so the audit trail is preserved.

**Closure recommendation (in-cycle, engine side)**:

Replace lines 14-17 with a correction matching the V1 finding:

```rust
//!   - panic safety: napi-rs 3.x does NOT wrap entry points in `catch_unwind`
//!     by default. The `#[napi(catch_unwind)]` opt-in attribute would enable
//!     it but is NOT used by this binding (we want panics to be CALLER bugs,
//!     not silently swallowed). Each `#[napi]` method must pre-validate any
//!     input that could trigger an engine-side `assert_*!`, `panic!`, `unwrap`,
//!     or `expect`. The V1 smoke test caught PeerId(0) →
//!     `CollabSession::new`'s `assert_ne!(peer_u64, 0)` → Node process abort
//!     ("failed to initiate panic, error 5"). The current FFI surface uses
//!     `peer_id_from_bigint` to pre-validate. V2 sweep TBD.
```

Add to V2 backlog: "engine-side `assert_*!`/`unwrap`/`expect` sweep with each
new method exposed via napi" — the test `merge_bytes_with_empty_slice_does_not_panic`
already pins one such contract; extend the discipline to every FFI-reachable
engine method.

## MEDIUM-1: Send/Sync docstring claim about napi internal locking is inaccurate

**Severity**: MEDIUM (documentation drift; Rule 4 trigger)
**Repo**: engine
**Citation**: `crates/ql-bindings-node/src/lib.rs:43-49`

Docstring claims:
> "`CollabSession` is `Send + !Sync` (verified per V2 V4 V1 step 3 + audit-
> discipline Rule 4 in the engine's audit memory). napi-rs's generated class
> wraps each instance in a per-JS-object slot accessed under napi's internal
> locking; we don't need `Sync` for the binding to work — JS code can hold the
> object across an `await` but cannot call methods concurrently (napi enforces
> this)."

Verified by reading `napi-3.9.0/src/bindgen_runtime/callback_info.rs:90-126`
(`_construct<T: ObjectFinalize + 'static>`) — there is **no `Send`/`Sync` bound
on T**; the instance is stored as `Box::into_raw(obj)` in a `napi_wrap`'d
container. The class instance doesn't take a lock.

The actual safety story is:
1. JS event loop is single-threaded. `&mut self` napi methods are called
   serially per JS context (Worker / main thread / etc.).
2. `Reference<T>` is explicitly **not Send** (per docstring at
   `value_ref.rs:32`: "It's not `Send` because of the `drop` of the `Reference`
   must be called in the same thread as the `Reference` is created."). This
   COMPILE-TIME prevents the class reference escaping to a different worker.
3. `Reference<T>: Sync` only when `T: Sync`. For our `CollabSession`
   (`!Sync` per V2 V4 V1 step 3), the JS-side reference is also `!Sync`, so
   it can't be shared even within the same thread group.

So the SAFETY conclusion ("no concurrent &mut self call possible") is correct,
but the JUSTIFICATION ("napi's internal locking") is wrong. The justification
is JS event-loop single-threadedness + Rust's compile-time `Send`/`Sync` on
`Reference<T>`.

**Closure recommendation (in-cycle, engine side)**:

Replace lines 43-49 with:

```rust
//! ## Send + Sync
//!
//! `CollabSession` is `Send + !Sync` (verified per V2 V4 V1 step 3 +
//! audit-discipline Rule 4). napi-rs's generated class instance lives in a
//! `Box<CollabSession>` stored in JS object slot via `napi_wrap` (see
//! `napi-3.9.0/src/bindgen_runtime/callback_info.rs:90-126`). napi-rs does NOT
//! lock the instance. Safety against concurrent `&mut self` rests on:
//!   1. JS event loop is single-threaded per Worker / main thread.
//!   2. `napi::Reference<T>` is NOT Send (intentional, per the napi-rs docs:
//!      "drop must run on the same thread as creation"). This compile-time
//!      prevents passing the class reference to a different Worker thread.
//!   3. `napi::Reference<T>: Sync` only when `T: Sync`. `CollabSession: !Sync`
//!      blocks even read-only cross-thread sharing.
//!
//! Conclusion: `Send + !Sync` is the correct bound; the IDE cannot use this
//! class concurrently from multiple Workers even if it wanted to.
```

## MEDIUM-2: Loader walk-up returns the wrong IDE root in worktree layouts

**Severity**: MEDIUM
**Repo**: IDE
**Citation**: `extensions/quantlab/src/quantbook/loader.ts:78-107`

`findIdeRepoRoot` walks UP looking for the first `package.json` with
`name: "code-oss-dev"`. Verified that **the engine worktree
(`quantlab-quantbook/`) has the SAME `code-oss-dev` package.json** (it's a git
worktree of the IDE repo on a different branch) — including
`quantlab-quantbook/extensions/quantlab/` with the same source tree.

Failure modes:
1. If a user is running the extension built FROM the engine worktree (e.g.,
   they `cd quantlab-quantbook/extensions/quantlab && npm run compile && code .`),
   the walk-up resolves to `quantlab-quantbook/` itself. Then
   `path.resolve(ideRepoRoot, '..', 'quantlab-quantbook', ...)` resolves to
   `quantlab/quantlab-quantbook/` — coincidentally correct ONLY in the canonical
   sibling layout.
2. If the engine worktree lives at a non-canonical path (e.g.,
   `/tmp/engine-checkout/`), the resolved engine path is
   `/tmp/quantlab-quantbook/quantbook-engine/target/release/...` — wrong
   directory; load fails (file doesn't exist); user gets a confusing error.

The 6-hop fallback for `ideRepoRoot === undefined` (lines 60-69) is even more
fragile — it assumes a specific `__dirname` depth that varies between compiled
(`out/src/quantbook`) and uncompiled (`src/quantbook`) trees.

**Closure recommendation (in-cycle, IDE side)**:

Option A (safer): require `QUANTBOOK_ENGINE_PATH` env var as the primary,
documented mechanism. Default discovery should be a developer-convenience
fallback with a LOUD warning when it fires.

Option B (V2 publish pipeline path): ship the .dylib bundled inside the
extension's `node_modules/@quantlab/engine-bindings/` so the loader uses
`require.resolve('@quantlab/engine-bindings/native.node')`. Eliminates the
walk-up entirely.

For V1, recommend at minimum:
- Add a 5-second console.warn when the loader uses the default discovery path
  (not env var) to make CI silent-discovery visible.
- Document in `loader.ts` that the worktree-layout assumption is the
  CONVENTION, not enforced — and that the user should set
  `QUANTBOOK_ENGINE_PATH` for any non-canonical layout.

## MEDIUM-3: SharedArrayBuffer data race in mergeBytes / fromSnapshot

**Severity**: MEDIUM (V2-V3 scope; flag now)
**Repo**: engine
**Citation**: `crates/ql-bindings-node/src/lib.rs:140-145, 180-186`

`mergeBytes(bytes: Uint8Array)` and `fromSnapshot(peer_id, bytes: Uint8Array)`
both call `bytes.as_ref()` which returns a `&[u8]` pointing into the JS-owned
ArrayBuffer (verified via `napi-3.9.0/src/bindgen_runtime/js_values/arraybuffer.rs:653-661`:
`slice::from_raw_parts(self.data, self.length)`).

If the underlying ArrayBuffer is a `SharedArrayBuffer` (shared between the main
thread and a Web Worker), the Worker thread can mutate the bytes WHILE Loro's
deserialization is reading them. This is a true data race at the Rust level:
the engine reads via `&[u8]` slice while a different OS thread writes via the
SAB's shared memory.

Failure modes:
- Best case: Loro deserialization errors out mid-stream with a malformed-data
  error → JS Error surfaces. No crash.
- Worst case: deserialization produces a corrupted LoroDoc internal state (the
  CRDT invariants may not be preserved if the bytes change mid-deserialize).
  Subsequent operations may panic or return wrong results.

V1 IDE doesn't expose SharedArrayBuffer paths (the demo creates plain
`Uint8Array`s via `exportBytes()`), but a future IDE engineer wiring a Web
Worker for off-main-thread sync COULD trigger this.

**Closure recommendation (V2-deferred)**:

V2 should clone the bytes before passing into Loro:
```rust
pub fn merge_bytes(&mut self, bytes: Uint8Array) -> Result<u32> {
    // Defensive copy to ensure the data Loro deserializes doesn't change
    // mid-flight (SharedArrayBuffer-backed Uint8Arrays from Workers).
    let owned: Vec<u8> = bytes.as_ref().to_vec();
    let count = self.inner.merge_bytes(&owned)...?;
    Ok(u32::try_from(count).unwrap_or(u32::MAX))
}
```

Trade-off: extra allocation per call. For V1 round-trip workloads (snapshots
are typically small), this is negligible. For V2 streaming deltas, may want
to validate the SAB-vs-AB distinction at the napi layer and only clone on
SAB-backed buffers (requires `napi_get_arraybuffer_info`).

For V1 in-cycle: add a docstring note that the binding assumes
non-SharedArrayBuffer inputs.

## MEDIUM-4: NaN/Infinity passthrough on appendPutValue value parameter

**Severity**: MEDIUM
**Repo**: engine
**Citation**: `crates/ql-bindings-node/src/lib.rs:152-163`; `crates/ql-oplog/src/op.rs:45-51`

`appendPutValue(sheet, row, col, value: f64)` accepts any f64, including `NaN`
and `Infinity`. The engine wraps it as `CellWireValue::Number(value)` and
stores it in Loro. There is no guard at the FFI boundary or at the engine
boundary for non-finite values.

Failure modes:
- `NaN`: stored as-is. On replay, `Value::Number(NaN)` flows through the
  workbook. Formula evaluation that operates on this cell may propagate NaN
  silently (`NaN + 1 = NaN`, `NaN == NaN` is false in IEEE 754). This is
  spreadsheet-app-standard behavior, but the IDE has no way to distinguish a
  user-entered NaN from a computed-NaN.
- `Infinity` / `-Infinity`: similar passthrough. Loro stores f64 without
  validation; serialization preserves them through snapshot/merge.

Excel rejects non-finite values: writing `=1/0` produces `#DIV/0!`, not
`Infinity`. The engine's wire format COULD distinguish these via a special
`CellWireValue::Error(...)` variant, but currently doesn't filter.

**Closure recommendation (in-cycle, engine binding side)**:

Add finite-value guard at the FFI boundary:

```rust
#[napi(js_name = "appendPutValue")]
pub fn append_put_value(&mut self, sheet: u16, row: u32, col: u32, value: f64) -> Result<()> {
    if !value.is_finite() {
        return Err(Error::from_reason(format!(
            "appendPutValue value must be finite, got {value}"
        )));
    }
    let op = Op::PutValue { sheet, row, col, value: CellWireValue::Number(value) };
    ...
}
```

Or push to the IDE TS wrapper (paired with HIGH-2 closure).

Pin the contract with a test:
```ts
test('appendPutValue rejects NaN', () => {
    const s = createSession(1n);
    assert.throws(() => s.appendPutValue(0, 0, 0, NaN), /finite/);
});
```

## MEDIUM-5: u32::MAX silent clamp on op-count overflow

**Severity**: MEDIUM
**Repo**: engine
**Citation**: `crates/ql-bindings-node/src/lib.rs:185, 195, 209`

Three methods clamp via `u32::try_from(usize_count).unwrap_or(u32::MAX)`:
- `merge_bytes()` returns `u32`
- `op_count()` returns `u32`
- `pending_op_count()` returns `u32`

The docstrings say "returns merged count" / "Local op log length" / "count of
ops added since the last flush" — but DON'T disclose the u32::MAX silent
clamp on overflow. A future caller building a "session is corrupt if op_count
matches u32::MAX" guard would never realize that's actually the clamp value.

Practically unreachable in V1 — 4 billion ops would consume terabytes of Loro
storage — but the silent clamp violates "verify before claiming" (CLAUDE.md).

**Closure recommendation (in-cycle, engine side)**:

Either:
- (A) Change return type to `BigInt` (matches the V1 `peerId() -> BigInt`
  precedent for u64-domain values; `usize` may be u64 on 64-bit hosts).
- (B) Document the clamp in the docstring AND surface a separate `Result`
  variant when the clamp would fire:

```rust
#[napi(js_name = "opCount")]
pub fn op_count(&self) -> Result<u32> {
    let raw = self.inner.op_count();
    u32::try_from(raw).map_err(|_| Error::from_reason(format!(
        "op_count {raw} exceeds u32::MAX; use opCountBigInt for unbounded sessions"
    )))
}
```

Option (A) is simpler and matches the BigInt usage pattern. For V1,
documenting the clamp in the docstring is sufficient:

```rust
/// **Returns**: `u32::MAX` if the actual count exceeds u32. V2 will switch
/// to BigInt return type for unbounded sessions.
```

## MEDIUM-6: IDE test couples to engine's Loro 1.12 empty-merge error semantics

**Severity**: MEDIUM
**Repo**: IDE (test)
**Citation**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:151-156`

The test asserts:
```ts
test('mergeBytes of empty array is rejected (engine error surfaces)', () => {
    const s = createSession(1n);
    assert.throws(() => s.mergeBytes(new Uint8Array(0)));
});
```

But the engine's `merge_bytes_with_empty_slice_does_not_panic` test
(`crates/ql-oplog/src/log.rs:730-780`) explicitly DOESN'T pin Ok-vs-Err:

> "The strict pinned invariants are: (1) does not panic, (2) log.len() remains
> pre_len, (3) Err variant (if any) is OpLogError::Loro (the documented
> passthrough variant), not some other variant. Treating Ok and Err as equally
> valid is a deliberate trade-off — strict Err pinning would catch intentional
> Loro behavior shifts as test failures."

The IDE test pins **Err** specifically. If Loro 1.13 upgrades to "accept empty
as Ok no-op" (which the engine test documents as acceptable), the IDE test
fails. The IDE test is **over-strict relative to the engine contract**.

**Closure recommendation (in-cycle, IDE side)**:

Either:
- (A) Loosen the test to match the engine contract: assert that mergeBytes
  either throws OR returns 0:
  ```ts
  test('mergeBytes of empty array: throws OR returns 0', () => {
      const s = createSession(1n);
      let result: number | 'threw' = 'threw';
      try { result = s.mergeBytes(new Uint8Array(0)); } catch {}

  });
  ```
- (B) Add a comment in the IDE test explaining the coupling and reference the
  engine's K7 contract so a future maintainer knows this test is the pinned
  CURRENT behavior, not the contract.

function shouldSkip(): { skip: boolean; reason?: string } {

## LOW-2: `try/catch` in loader.ts swallows JSON parse errors during walk-up

**Repo**: IDE
**Citation**: `extensions/quantlab/src/quantbook/loader.ts:89-98`

} catch (err) {

## OBS-1: napi8 feature targets Node 12; VS Code Electron uses Node 20+

`napi = { version = "=3.9.0", default-features = false, features = ["napi8"] }`
(workspace Cargo.toml:79). `napi8` is the Node 12+ ABI baseline. VS Code's
Electron version is well past Node 12 (Electron 30+ = Node 20+). Using `napi8`
is safe but forfeits access to napi9+ features (e.g., `node_api_create_buffer`,
better error-handling APIs). Pin is intentional per workspace comment;
consider bumping to `napi9` or higher in V2 if any napi9 feature becomes
useful.

## OBS-3: Demo command uses hardcoded peer IDs `1n`, `2n`

Engine documentation warns against pinned peer IDs ("Prefer per-process-random
peer ids over user-/device-pinned ids" — session.rs:365). The demo uses
`createSession(1n)` and `sessionFromSnapshot(2n, ...)` every invocation. For
the demo's single-process scope this is fine, but the IDE engineer wiring V2
should NOT copy this pattern. Add a `// DEMO ONLY` comment.

## OBS-4: process.dlopen `as unknown as NodeJS.Module` cast can be eliminated

Per Node.js docs (verified via WebFetch), `process.dlopen()` accepts a plain
object `{ exports: {} }`; the `NodeJS.Module` type signature is the only
reason for the cast. Two cleaner alternatives:
1. (Preferred) Symlink/copy the `.dylib` to `.node` at load time and
   `require()` it — eliminates the cast AND integrates with Node's module
   cache.
2. (Cosmetic) Use a TS type assertion that's narrower:
   `process.dlopen(fakeModule as Pick<NodeJS.Module, 'exports'>, enginePath);`
   (untested but should satisfy the dlopen signature).

V2 publish pipeline (per existing comment in loader.ts) will switch to
`.node` + `require()`. For V1, the comment ackowledging the cast is
sufficient.

## OBS-5: `process.dlopen` has no `dlclose`; engine cdylib stays loaded for extension-host lifetime

No way to unload the cdylib in Node.js without restarting the process. If a
user upgrades the engine binary during extension development, they must
restart the extension host (Cmd+R reload doesn't re-dlopen). Document this in
loader.ts or in the V2 publish-pipeline scope.

## OBS-6: f32 not supported by napi-rs as parameter type

The number.rs impl only generates `FromNapiValue` for u8/i8/u16/i16/u32/i32/i64/f64
— NOT f32. If a future engine method needs an `f32` parameter, it must be
written as f64 at the FFI boundary. Trivial constraint but worth noting.

## OBS-7: Tests in suiteSetup bump timeout to 60s for dlopen cold load

This is correct discipline for the cold-load case, but masks a perf concern:
3.5MB cdylib + Loro symbol resolution taking 10-30s suggests the release
binary may be incidentally large (debug symbols? non-stripped?). Verify
`strip` is run in the workspace release profile (`debug = "line-tables-only"`
is set — should be small symbols; sanity-check with `du -h` of the .dylib).

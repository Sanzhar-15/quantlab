# Self-audit: W5-D-15 (Phase 4.11 XLSX-4-03 per-cell format APPLICATION)

Commit `4f5226a9876` on `feat/quantbook-engine`.

Closes the final Phase 4.11 round-trip gap: per-cell `(row, col) →
FormatId`. Three new E2E tests covering custom-code + built-in +
dedup round-trips. 83 ql-io-xlsx tests + 4114 workspace tests passing.

Self-audit is the third leg of the parallel Codex + separate-Opus +
self discipline. Both other audits running in parallel.

## HIGH findings

### H-1: Blank-cell format overlays are silently lost on export

- File: `crates/ql-io-xlsx/src/write/umya_export.rs` (export walk:
  ~line 130-200 + post-process: ~line 460-475).
- What's wrong: the export walk skips `(None, Value::Blank)` cells —
  no `<c r="...">` is emitted by umya for them. The SetStyle
  post-process needle `<c r="C5"` then has nothing to match against,
  and the format overlay entry is silently dropped from the output.
- Why it matters: a user formats column A as `yyyy-mm-dd` and leaves
  the column empty for future data entry. The format is real
  application state but doesn't survive export → re-import. On any
  practical workbook with empty-cell-style preallocation (very
  common in finance / data-entry templates), formats silently
  disappear.
- Suggested fix: in the per-sheet walk, BEFORE pushing SetStyle
  fixes, ensure every cell with an overlay entry has an actual
  `<c r="...">` in the worksheet xml. Two paths:
  - (a) Write a Blank-but-styled cell to umya as a value-bearing
    cell (set_value_string("") or similar). umya would emit a
    `<c r="..." t="..."><v></v></c>` placeholder.
  - (b) During post-process, for each (row, col) overlay entry
    whose ref isn't found in the worksheet xml, INSERT a fresh
    `<c r="..." s="N"/>` element into `<sheetData>` (sorted by
    row/col).
  
  (b) is more surgical and avoids polluting cell values. Requires
  parsing `<row r="N">` boundaries.

### H-2: `applyNumberFormat` default semantics may be inverted vs OOXML spec

- File: `crates/ql-io-xlsx/src/read/styles_xml.rs:175` (parser
  default: `false`) + `lib.rs` per-cell wiring (skips when
  apply_number_format is false).
- What's wrong: ECMA-376 / OOXML schema says `applyNumberFormat`
  in `<cellXfs><xf>` defaults to `true` when the attribute is
  absent (i.e., the numFmtId in this cellXf IS applied to cells
  referencing it). The current parser defaults to `false`, and the
  per-cell wiring skips cellXfs with `apply_number_format == false`.
  Net effect: cells whose source file omits `applyNumberFormat="1"`
  (very common — many real-world tools like LibreOffice / openpyxl
  / xlsxwriter omit the attr) silently lose their formats on import.
- Why it matters: a real workbook with date cells generated by
  LibreOffice would round-trip with the dates UNFORMATTED. The
  format codes are interned in the FormatTable (W5-D-14d works), but
  no cell ever references them — defeating the entire XLSX-4-03
  closure for that file.
- Suggested fix: empirically check what Excel / LibreOffice /
  openpyxl emit (probe via fixture inspection). If the spec is the
  authoritative truth, flip the default to `true`. ALSO: add a
  fixture-driven E2E test using a non-Quantbook-generated file
  (e.g., a hand-built minimal xlsx with formatted cells but
  applyNumberFormat omitted).

### H-3: cellxfs_roster order is HashMap-iteration nondeterministic — byte-unstable round-trip

- File: `crates/ql-io-xlsx/src/write/umya_export.rs` (~line 200-225
  in the per-sheet walk).
- What's wrong: `sheet.format_overlay().iter()` returns entries in
  HashMap iteration order. The first FormatId encountered gets
  `xf_index=1`, the second `xf_index=2`, etc. Two runs of the same
  export can produce `<cellXfs>` with the same set of entries but in
  DIFFERENT order, yielding different `s="N"` per cell.
- Why it matters: byte-non-deterministic xlsx output breaks:
  (a) Replay / .qbook persistence determinism contracts; (b) CRDT
  state diffing if Phase 5 ever relies on byte identity; (c) golden
  tests comparing xlsx bytes; (d) caching layers keyed on output
  digest. Round-trip is semantically correct (FormatId mapping
  survives) but the bytes differ.
- Suggested fix: sort `cellxfs_roster` by `FormatId` before
  assigning xf indices, OR collect into a `BTreeMap<FormatId,
  Vec<(RowId, ColId, SheetId)>>` during the per-sheet walk. The
  latter is cleaner (one pass, sorted-by-construction).

## MEDIUM findings

### M-1: `cellXfs` case-2 (no existing block) insertion position is wrong

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:inject_cell_xfs_into_styles_xml`
  Case-2 branch (`text.rfind("</styleSheet>")` → insert before).
- What's wrong: OOXML CT_Stylesheet child-element order is
  `numFmts? fonts fills borders cellStyleXfs? cellXfs? cellStyles?
  dxfs? tableStyles? colors? extLst?`. Inserting `<cellXfs>` just
  before `</styleSheet>` lands it AFTER any `<cellStyles>`,
  `<dxfs>`, `<tableStyles>`, etc. — a schema violation.
- Why it matters: latent — umya 2.2.0 always emits a `<cellXfs>`
  block, so case-2 never fires today. A future refactor (e.g.,
  using a different writer that omits cellXfs) would silently
  produce invalid xlsx.
- Suggested fix: when no cellXfs exists, insert AFTER
  `</cellStyleXfs>` if present, else after `</borders>`. The
  cleanest version uses the same `</tag>`-or-`/>` pattern as the
  numFmts/definedNames injection sites to find the prior sibling
  and insert immediately after.

### M-2: Out-of-bounds xf index on import silently skips with no warning

- File: `crates/ql-io-xlsx/src/lib.rs` (~line 184 — `let Some(xf) =
  style_index.cell_xfs.get(xf_idx as usize) else { continue; };`).
- What's wrong: a corrupted or hand-edited xlsx with `<c s="99">`
  where `cellXfs` only has 5 entries silently drops the format
  reference. No warning, no report entry.
- Why it matters: corruption goes invisible. The Phase 4.11 spirit
  ("corruption + unsupported features surface visible errors")
  applies.
- Suggested fix: surface as `XlsxWarning` in
  `report.warnings` with `{location, message}` set to the cell's
  address and the offending xf index. Strict mode could escalate
  to an error.

### M-3: Per-cell style application doesn't fire for `UpdateOriginal` mode separately — the shadow carries it through, but no test covers this

- File: tests gap.
- What's wrong: the W5-D-15 commit message claims "Per-cell style
  application for `UpdateOriginal` mode: the shadow export already
  carries the overlay through, so this works for free". True, but
  no test asserts this — a future change to UpdateOriginal that
  diverges from NewWorkbook (e.g., to preserve more original parts)
  could regress without notice.
- Suggested fix: add an E2E test:
  `w5_d_15_round_trip_per_cell_format_via_update_original` that
  imports a fixture with `preserve_package=true`, applies a format
  to a cell, and exports via `UpdateOriginal`. Assert the round-
  trip overlay matches.

### M-4: cellxfs replacement clobbers umya's potentially non-default cellXfs entries

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:inject_cell_xfs_into_styles_xml`.
- What's wrong: we replace the ENTIRE `<cellXfs>` block. If umya
  emits multiple xfs (e.g., for cells with text type — `t="s"` —
  umya might assign them an xf with `fontId="1"` or similar),
  those get clobbered. Cells umya wrote with `s="2"` would now
  reference an out-of-bounds xf (our roster only has 0..N where N
  = cellxfs_roster.len()).
- Why it matters: latent — verify empirically what umya emits.
  This audit has time to probe.
- Suggested fix: instead of replacing, APPEND our custom xfs at the
  end of umya's existing cellXfs. Then our `xf_index` should be
  computed as `len(existing_cellxfs) + roster.len()`. More complex
  but safer.

### M-5: Format overlay on a sheet other than sheet 0 — no test

- File: tests gap.
- What's wrong: all 3 new E2E tests use sheet 0. Multi-sheet
  format overlays could fail if the post-process zip walk
  mis-attributes fixes to sheet xml paths.
- Suggested fix: add a multi-sheet variant of the round-trip test.

## LOW findings

### L-1: `parse_a1_cell` accepts arbitrary letter counts; col overflow at very long refs

- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs:80-103`.
- `col = col * 26 + ...` overflows u32 for ~12+ letter refs (very
  unrealistic — Excel caps at XFD = 16384 = 3 letters). No crash
  (release-mode wraps), but defensive caller would clamp.
- Severity: LOW — Excel domain rejects.

### L-2: `apply_number_format` parsing accepts `"true"`/`"1"` but not `"True"`/`"TRUE"`

- File: `crates/ql-io-xlsx/src/read/styles_xml.rs:182`.
- Uses `val.eq_ignore_ascii_case("true")` → covers True/TRUE.
- Actually re-checking: the code IS case-insensitive. False alarm.

### L-3: cellxfs_roster sorting by FormatId would make audit-trail clearer

- Cosmetic — see H-3 for the real fix.

### L-4: No assertion that round-trip preserves the COUNT of overlay entries

- The 3 new E2E tests check specific cells, not the total count.
  A bug where one cell of three gets dropped wouldn't be caught
  unless that cell happens to be the one asserted.
- Add `assert_eq!(imported.format_overlay().len(), 2)` etc.

### L-5: parse_cell_styles_xml runs per-sheet but reads the whole worksheet xml

- For huge sheets (millions of cells) this loads the entire xml
  into memory. quick-xml supports streaming `Reader::from_reader`;
  we use `from_str`. LOW — Phase 4.11 doesn't claim huge-sheet
  support yet.

### L-6: applyNumberFormat="0" import-side skip — no test

- We skip it correctly in lib.rs, but no fixture exercises this
  path. Same as M-3 (test gap).

### L-7: SetStyle needle doesn't anchor on byte AFTER the closing `"`

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:apply_cell_fixes_to_sheet_xml`
  SetStyle branch.
- Needle `<c r="C5"` would also match `<c r="C5"></c>` and inject
  `s="N"` correctly. No actual collision in real-world OOXML, but
  the needle could be tightened to require a space or `>` after the
  closing `"`.

## What looked right

- The import-side skip on `s="0"` matches the storage layer's
  General-is-implicit convention; `format_overlay.get()` returns
  None for cells with FormatId::GENERAL semantics.
- `format_to_xf_index` dedup map ensures cells with the same
  FormatId share one cellXf slot — verified by
  `w5_d_15_round_trip_dedup_shared_format_id`.
- SetStyle ordering (push AFTER cell-walk fixes) prevents
  RemoveStrType / OverrideErrorSigil needles from being disrupted
  by an inserted `s="..."` attribute.
- `build_sheet_part_paths` mirrors `build_sheet_rels_paths` and
  uses the same workbook.xml.rels resolution — no new sheet-index
  heuristic introduced.
- xf slot 0 is reserved as the bare default
  (`<xf numFmtId="0" .../>` with no apply flags), matching umya's
  emission convention.
- `inject_cell_xfs_into_styles_xml` uses the `</tag>` first /
  defensive `/>` second pattern from the M-1 closure of W5-D-14.2.3.
- The Cow-based sheet-name parse from W5-D-14.2.3 isn't touched by
  this commit; format-overlay paths are independent.

question).

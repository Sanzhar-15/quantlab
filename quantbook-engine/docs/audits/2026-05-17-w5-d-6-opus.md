### MEDIUM-O-1 (test-coverage gap) — Missing `e2e_covariance_registered` registry-lookup smoke test in `region_mul2_e2e.rs`

File: `crates/ql-exec/tests/region_mul2_e2e.rs` — no W5-D-6 test added.

Every other Wave 3 paired-array fn has a parallel registry-lookup smoke test in `region_mul2_e2e.rs`:

- `e2e_correl_registered` (W5-177, line 542)
- `e2e_slope_intercept_registered` (W5-178, line 528)
- `e2e_pearson_rsq_steyx_registered` (W5-179, line 515)

Each asserts `lookup_range_aware("NAME").is_some()` for both uppercase and lowercase. The rationale (per the W5-177 comment at line 543): "range-arg construction can't go through the lightweight `bind(&ast, 0)` test helper without named-range / table-ref scaffolding. Smoke-check via registry dispatch."

W5-D-6 follows the same pattern (RangeAwareFn, range-only args, no scalar promotion) but does not add the parallel `e2e_covariance_p_s_registered` test. The unit-level `default_registry_has_expected_count` test confirms the count went 234 → 236, but does not confirm the names are reachable via `lookup_range_aware` (which goes through `to_ascii_uppercase` normalization — a separate code path).

**Risk**: low (the registry has a consistent insert-or-panic guard and case-insensitive lookup is well-trodden), but the established convention is to add the smoke test for every new paired-array fn. Skipping it is a coverage-shape regression vs the W5-177/178/179 baseline.

**Recommendation**: add the missing test:

```rust
#[test]
fn e2e_covariance_p_s_registered() {
    // W5-D-6: COVARIANCE.P + COVARIANCE.S are RangeAwareFns;
    // registry-lookup smoke check per the W5-177/178/179 pattern.
    let registry = default_registry();
    assert!(registry.lookup_range_aware("COVARIANCE.P").is_some());
    assert!(registry.lookup_range_aware("covariance.p").is_some());
    assert!(registry.lookup_range_aware("COVARIANCE.S").is_some());
    assert!(registry.lookup_range_aware("covariance.s").is_some());
}
```

This also exercises the dot in the function name — the only Wave 3 paired-array fns with a dot in the canonical name, so case-insensitive lookup of `covariance.p` is a meaningfully novel code path that no other test currently covers (CORREL/PEARSON/RSQ/STEYX/SLOPE/INTERCEPT all have all-letter names).

## LOW

### LOW-O-1 (coverage-shape) — Booleans and Blanks not explicitly tested for skip-pair behavior

File: `crates/ql-functions/src/range_fns.rs:4083-4090` (covariance_p) and 4180-4187 (covariance_s)

The skip-non-numeric tests use `Value::Text` only:

```rust
let x = r(vec![n(1.0), n(2.0), n(3.0), t("ignored")]);
let y = r(vec![t("dropped"), n(4.0), n(6.0), n(99.0)]);
```

CORREL's coverage has three distinct tests for this category:

- `correl_skips_pairs_with_nonnumeric_either_side` (Text)
- `correl_skips_pairs_with_blanks` (`Value::Blank`)
- `correl_skips_booleans` (`Value::Boolean`)

STEYX uses Boolean (`steyx_skips_non_numeric_pairs`, line 4031). The covariance kernel reuses the same `collect_xy_pairs` helper, so semantically these are inherited — but explicit per-type coverage would close a coverage-shape gap and pin the Boolean-not-coerced-to-1/0 canon (the **non-default** behavior that diverges from SUM).

Not blocking — the inherited helper has full coverage in CORREL — but a 1-2 line additional test would round out the suite.

### LOW-O-2 (semantic divergence — inherited, not new) — Count-mismatch with same-shape arrays diverges from IronCalc

File: `crates/ql-functions/src/range_fns.rs:1493-1530` (`collect_xy_pairs`)

IronCalc's COVARIANCE.* (lines 73-91 of `covariance.rs`) does **two** counts:

1. Per-array `is_some()` count.
2. If `count1 != count2` (same shape, different numeric positions) → `Error::NA`.

Our `collect_xy_pairs` only does post-pairing filter (drop pair when either side is non-numeric). For the fixture `x=[1,2,t], y=[t,3,t]` (same shape, counts 2 vs 1):

- IronCalc returns `#N/A`.
- We return a computed covariance over `xs=[2], ys=[3]` (one numeric pair). For cov_p that yields 0; for cov_s that yields `#DIV/0!`.

This divergence is **inherited from the W5-179 `collect_xy_pairs` helper** and is consistent with CORREL/PEARSON/RSQ/STEYX/SLOPE/INTERCEPT — it is engine-wide convention, not a W5-D-6 regression. However, the matrix doc rows for COVARIANCE.P/.S only call out the `#VALUE!` vs `#N/A` shape-mismatch divergence; they don't surface this subtler count-mismatch divergence (and neither does the CORREL row).

Not blocking — staying consistent with the rest of the paired-array family is the right call — but worth flagging as a doc-completeness item that could be added to the family-wide divergence note in `excel-matrix.md` (one-time edit covering all 8 paired-array fns).

### LOW-O-3 (test-shape) — Asymmetric arity coverage between cov_p and cov_s

File: `crates/ql-functions/src/range_fns.rs:4131-4137` (`covariance_p_arity_violations`) vs 4198-4205 (`covariance_s_arity_violations`)

`covariance_p_arity_violations` only asserts:

- `&[]` → Value
- `&[s, s]` (2 scalar args) → Value

`covariance_s_arity_violations` asserts:

- `&[]` → Value
- `&[s]` (1 scalar arg) → Value
- `&[s, s]` (2 scalar args) → Value

The 1-arg case is tested for cov_s but not cov_p. Neither tests the 3+-arg case (would also return `#VALUE!` because `args.len() != 2`). The kernel branches are identical (`if args.len() != 2 { return Value::Error(ErrorValue::Value); }`), so semantically it's covered transitively, but the per-fn test shape is asymmetric.

Not blocking; cheap to fix (add the 1-arg case to cov_p).

### LOW-O-4 (terminology) — Coverage entry for cov_p says "Bessel-correction-free divisor"

File: `crates/ql-functions/tests/coverage.rs:313`

```
"W5-D-6; unit tests pin closed-form covariance on y=2x (cov=2.5) and y=-2x (cov=-2.5) + Bessel-correction-free divisor + constant-array → cov=0 ..."
```

"Bessel-correction-free divisor" is informally correct (the population formula uses `n`, no `n-1` correction) but reads awkwardly. The standard phrasing is "population divisor n" or "uncorrected divisor n". Minor wordsmithing — not blocking.

### LOW-O-5 (numerical algorithm) — Two-pass naive formulation is reference-parity but not numerically optimal

File: `crates/ql-functions/src/range_fns.rs:1426-1449` (`compute_covariance`)

The kernel uses the textbook two-pass algorithm (compute means in pass 1, then sum (x-mean_x)·(y-mean_y) in pass 2). This is **better than** the single-pass `Σxy - n·x̄·ȳ` formulation (which CORREL uses, with documented justification for staying parity with IronCalc), but for very large n with large mean / small variance, Welford's online algorithm or Kahan-compensated summation would be more accurate.

IronCalc uses the same two-pass approach, so this is parity-by-design and not a defect. Worth noting only because future ULP-sensitive callers may want to swap in a higher-precision kernel; the `compute_covariance` interface is well-suited for that future refactor.

Not blocking.

## Confirmed Non-Issues

1. **`is_finite()` guard in `compute_covariance` is redundant with `sanitize_f64`** — but matches CORREL's defense-in-depth pattern. No issue.
2. **No `COVAR` legacy alias** — Excel `COVAR` (without dot) is the deprecated pre-2010 name for `COVARIANCE.P`. Skipping it aligns with the modern-name-only convention used for `RANK.EQ` / `MODE.SNGL` (which DO have aliases) — except those are registered as registry aliases. The decision to NOT alias `COVAR` is internally consistent with the engine's approach (modern names only for the new Wave 3 batch); IronCalc registers `COVAR` as alias of `COVARIANCE.P` (`covariance.rs:fn_covariance_p` is invoked by both names per `fn_dispatcher.rs`, not visible in the file alone). If we later decide to add `COVAR` for compat, it's a one-line addition. **Flag for awareness, not a defect.**
3. **`xs.is_empty()` vs `xs.len() < 1`** — semantically equivalent; clippy would warn against `< 1`. Choice is idiomatic.
4. **`divisor_offset: f64` parameter type** — could be `usize` since only values 0 and 1 are used. Using `f64` avoids an `as f64` cast inside the kernel and lets callers pass `0.0` / `1.0` directly. Defensible choice.
5. **`Result<f64, ErrorValue>` return type from `compute_covariance`** — only error path returned is `ErrorValue::Num` from the `is_finite` guard. The `Result` shape matches `compute_correl` for API symmetry within the file. No issue.
6. **CORREL's `correl_skips_pairs_with_blanks` test** — our cov_p/cov_s suites don't cover `Value::Blank` explicitly. Captured under LOW-O-1; coverage is inherited from CORREL via `collect_xy_pairs`.
7. **Constant-on-one-side returns 0** — matches IronCalc (no special-case for zero variance). Diverges from CORREL which returns `#DIV/0!`. Matrix doc explicitly calls this out ("Constant array → cov=0 (NOT #DIV/0! like CORREL)"). Verified semantic-correct vs Excel canon (constant array on one side has zero covariance with anything; CORREL's `#DIV/0!` arises from the normalization denominator, which COVARIANCE doesn't have).

## MEDIUM

### MEDIUM-001

- **Subject:** Left-shift overflow can wrap back into an accepted numeric result
- **Where:** `crates/ql-functions/src/scalar_fns.rs:3366`, `crates/ql-functions/src/scalar_fns.rs:3403`
- **Detail:** `BITLSHIFT` and the negative-shift branch of `BITRSHIFT` compute the `i64` left shift with `wrapping_shl` before checking `result_f.abs() > BIT_MAX`. For in-domain inputs this can discard high bits and produce a small or negative wrapped value that passes the post-check. Examples: `BITLSHIFT(281474976710655, 16)` mathematically exceeds `2^48-1` and should return `#NUM!`, but `281474976710655i64.wrapping_shl(16)` is `-65536`, whose absolute value is below `BIT_MAX`; `BITLSHIFT(140737488355328, 17)` wraps to `0`. The same failure mode applies to `BITRSHIFT(number, -shift)` because that path also uses `wrapping_shl`.
- **Recommendation:** Guard the mathematical left shift before performing it, for example by using `u128`/`i128` (`(n as u128) << shift`) and comparing to `BIT_MAX as u128`, or by checking `n_i > (BIT_MAX as i64) >> shift` before `n_i << shift`. Keep right shifts as-is. Add regressions for wrap-back cases such as `BITLSHIFT(BIT_MAX, 16)`, `BITLSHIFT(2^47, 17)`, and `BITRSHIFT(BIT_MAX, -16)`.
- **Severity rationale:** Medium because valid Excel-domain inputs can return a wrong numeric value instead of the required `#NUM!`. The bug is limited to overflow-edge left shifts and does not affect registration or right-shift-only paths.

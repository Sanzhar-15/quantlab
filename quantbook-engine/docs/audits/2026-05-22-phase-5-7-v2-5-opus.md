Per-field walk of the lifetime story:

1. The `{ ... }` block creates a fresh scope for the `inner` binding. `parking_lot::MutexGuard<'_, CoreCollabSession>` is dropped at the closing brace, releasing the parking_lot mutex unconditionally (verified against the V2.4 dep pin `parking_lot = "=0.12.5"` — the standard `MutexGuard::drop` is the only exit path).
2. The return value of the block is `flush_pending_handle()`'s return — `Option<Box<dyn FlushAck + Send>>`. Walked at `crates/ql-collab/src/session.rs:884-886`: `self.transport.as_ref().and_then(|t| t.ack_handle())`. For `WebSocketTransport`, `ack_handle()` at `crates/ql-collab-ws/src/lib.rs:778-784` constructs `WebSocketProgressAckHandle { target, progress: Arc::clone(...), closed: Arc::clone(...) }`. No reference to `self`, no reference to anything inside the guard.
3. The bound `handle_opt` is moved (no borrow checker complaint possible) — the `let Some(handle) = handle_opt else { ... };` at line 837 consumes it.
4. `spawn_blocking(move || handle.wait_for_drain())` moves `handle` into the task. The handle carries Arc clones of progress state owned by the transport (and still owned by the session). No alias of the dropped guard exists at this point.

No subtle aliasing. The handle's Arc clones share state with the transport but the session mutex doesn't guard those Arcs — the writer task in `WebSocketTransport` already operates on the same Arcs concurrently with sync `send()`/`try_recv()` calls (`crates/ql-collab-ws/src/lib.rs:417,474,605`).

## Findings detail

### MEDIUM-1: `FlushAck: !Sync` claim in trait docstring contradicts implementor reality (Rule 4 drift)

**Repo**: engine.

**File:line**: `crates/ql-collab/src/transport.rs:320-325` (claim); `crates/ql-collab-ws/src/lib.rs:801-807` (`WebSocketProgressAckHandle` fields); `crates/ql-collab/src/transport.rs:725-730` (`BlockingAckHandle` fields).

**Claim**:

> **Send + !Sync** is sufficient: the handle is moved into one blocking task and never shared. `Sync` is not required by any V2.5 caller — adding it would defensively allow handle-cloning patterns, but the current single-use pattern is preferable (matches `Box`-not-`Arc` ownership and avoids mistaken concurrent waits on the same captured target).

**Source-walked reality**:

- `WebSocketProgressAckHandle { target: u64, progress: Arc<(Mutex<u64>, Condvar)>, closed: Arc<AtomicBool> }`. `Mutex<u64>: Send + Sync`, `Condvar: Send + Sync`, tuple of Send+Sync is Send+Sync, `Arc<T: Send + Sync>: Send + Sync`, `AtomicBool: Send + Sync`, `u64: Send + Sync`. Therefore `WebSocketProgressAckHandle: Send + Sync`.
- `BlockingAckHandle { block_ms: u64, release: Arc<(Mutex<bool>, Condvar)>, blocked: Arc<(Mutex<bool>, Condvar)> }` — identical analysis. Also `Send + Sync`.

The docstring asserts a negative trait property (`!Sync`) that is materially false. The Rule 4 lesson from V2 V4 V1 step 3 (`crates/ql-collab-ws/src/lib.rs:263-272`, V2 V3 step 4 docstring falsely claimed `WebSocketTransport: !Sync`) is the same pattern.

**Reproduction**:

```rust
const _ASSERT_FLUSHACK_IMPLS_ARE_SYNC: fn() = || {
    fn assert_sync<T: Sync>() {}
    assert_sync::<ql_collab_ws::WebSocketProgressAckHandle>();
    assert_sync::<ql_collab::BlockingAckHandle>();
};
```

— compiles cleanly. Pre-V2.5 audits would have caught this had Rule 4 been applied to the new trait at the same depth as the V2.4 Send+Sync work on `CollabSession`.

**Severity rationale**: MEDIUM (not HIGH). The trait's `Send` bound is correct + load-bearing for spawn_blocking. The `!Sync` is descriptive misleadingness, not a soundness hazard. If a future implementor IS `!Sync` (e.g., contains a `Cell`), the trait still allows it because the trait declares no `Sync` requirement. The harm is documentation drift that erodes audit trust — same loss-of-trust class the V2 V4 V1 step 3 fix tried to permanently end.

**Recommended closure (Option A — preferred)**: rewrite the docstring to match shipped reality. Suggested text:

> **Send is required; Sync is not.** The shipped `WebSocketProgressAckHandle` and `BlockingAckHandle` implementors happen to be `Send + Sync` (every field is Sync), but the trait requires only `Send` so that a future implementor wrapping a `!Sync` field (e.g., `Cell` for an internal cache) remains a valid `FlushAck`.

**Recommended closure (Option B)**: add a positive compile-assert `WebSocketProgressAckHandle: Sync` + `BlockingAckHandle: Sync` next to the existing `Send` asserts, pinning the actual bound for both shipped types. Pair with the docstring rewrite from Option A.

Either closure satisfies Rule 4. The V2 V4 V1 step 3 precedent took Option B.

### LOW-1: V2.5 contract-test threshold may be tight on slow CI (Codex risk flagged at plan time)

**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:1253-1257`.

```ts
assert.ok(
  elapsed < 500,
  `V2.5 contract: opCount during pending flushPending took ${elapsed}ms; expected < blockMs/2 = 500. `,
);
```

Local dev passes at ~50ms (per commit message). On slow CI (cold tokio runtime startup, contended scheduler), the napi-rs sync method's roundtrip could plausibly approach 500ms even with the V2.5 fix in place. Under V2.4 it would be ~1000ms, so the ratio is still discriminative, but the margin shrinks.

**Recommended closure**: raise the threshold to 800ms with a comment noting "blockMs=1000 - 200ms scheduler-jitter headroom = 800ms". The discrimination signal (V2.4 ~1000ms vs V2.5 ~50ms) remains intact. Or alternatively, bump `blockMs` to 2000ms and keep threshold at 500ms — wider absolute gap. Either is defensive.

### LOW-2: BlockingTransportFixture ships in every production cdylib (Codex Q4 trade-off resurfacing)

**File:line**: `crates/ql-bindings-node/Cargo.toml:51` (`ql-collab = { path = "../ql-collab", features = ["test-fixtures"] }`); `crates/ql-bindings-node/src/lib.rs:1117` (`#[napi]` without cfg gate).

The V2.6 plan ratified shipping the fixture in production builds (commit message lines 47-50) with the rationale "harden test-fixture exposure for production cdylib builds" deferred to V2 product hardening backlog. The Codex plan review treated this as L: the worst a malicious IDE extension can do via `new BlockingTransportFixture(0).takeTransport()` + `attachTransport(t)` + `flushPendingToTransport()` is block its own session's flush — no CRDT corruption, no escalation.

This Opus lane concurs: the DoS surface is bounded to per-session self-harm. The fixture cannot be used to attack other sessions (no shared state) or the IDE process beyond consuming one blocking-pool thread and one session's flush operation. The threat model is "untrusted code already running in the extension host" which already has many other DoS vectors.

**Recommended closure**: explicitly add an item to `docs/PHASE-5-7-V2-BACKLOG.md` (or wherever the V2 backlog lives) tracking the production-cdylib hardening — make the deferral visible rather than only documented in the commit message + a code comment. Suggested item: "Gate `BlockingTransportFixture` napi class behind a feature on `ql-bindings-node` itself (mirror the engine's `test-fixtures` gate); production cdylib builds disable the feature."

## Risks 5-9 from Codex plan review — post-implementation status

All 5 risks were graded LOW at plan time. Post-implementation verification:

- **Risk 5 (detach mid-wait):** LOW preserved. `WebSocketTransport::Drop` at `crates/ql-collab-ws/src/lib.rs:609-637` sets `closed = true; progress.1.notify_all()` BEFORE aborting tasks (lines 633-636). `WebSocketProgressAckHandle::wait_for_drain` at line 822 checks `self.closed.load(Ordering::Relaxed)` inside the wait loop on every wake. Worst-case latency to observe Closed: 100ms (the `wait_timeout` tick at line 827). Acceptable.

- **Risk 6 (Box overhead):** LOW preserved. One `Box::new(WebSocketProgressAckHandle { ... })` allocation per `flushPendingToTransport` call. Dominated by the spawn_blocking submission cost (~microseconds). Negligible.

- **Risk 7 (Arc cloning soundness after transport drop):** LOW preserved. The handle's `Arc<...>` clones extend the lifetime of the progress + closed state beyond the transport's lifetime. Per the V2 V3 step 5 megaudit closure (`TaskExitGuard` at lines 114-148 + `Drop` at 609-637), the writer task's Arc clones are aborted but the closed flag is set first. The handle observes `closed = true` and returns `Err(Closed)`. No UAF (Arc keeps state alive); no stale-progress read (closed-flag check on every iteration).

- **Risk 8 (existing tests):** LOW preserved per the commit message's `cargo test -p ql-collab --release --features test-fixtures --lib: 71/71`. Default-impl extension to the trait is non-breaking; verified by source-walk that `pub trait Transport {` at `crates/ql-collab/src/transport.rs:128` retains no supertrait. The workspace-gate count claim (4461) is unverified by this audit lane — left to Codex's protocol lane.

- **Risk 9 (`Send` vs `Send + Sync` for `FlushAck`):** UPGRADED TO MEDIUM-1 (see above). Codex's L rating was "Send is sufficient, Sync would be defensive overkill" — that judgment stands for the trait bound, but the *docstring* claims `!Sync` which the implementors contradict. The Rule 4 drift is what changes the severity, not the trait bound itself.

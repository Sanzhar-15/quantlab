## What to audit

### A. Layering (Codex original HIGH-3 + W5-133 revision)

W5-133 split the types across crates: `ReferenceMode` and
`Locale` (extended with `De`, `Fr`) in `ql-types::eval_context`;
`LocaleData` and `locale_data()` in `ql-formula-syntax::locale`.
`ql-storage::Workbook` holds instances.

Verify:
- No new dep-graph edges. `ql-storage → ql-types` (existing).
  `ql-formula-syntax → ql-types` (existing). Workbook can hold
  `ReferenceMode` / `Locale` without depending on `ql-formula-syntax`.
- `locale_data()` is the only entry point for separator lookup.
  Nothing else hardcodes `,` or `.` as locale-specific glyphs.

### B. Locale extension correctness (W5-133)

Existing `Locale` enum had `EnUs` only with a pre-existing
W5-68 docstring scaffolding for Phase 4.9. W5-133 extended with
`De`, `Fr`. Verify:
- `Locale::default()` still returns `EnUs` — no breaking change.
- `EvalContext::default()` and `DEFAULT_EVAL_CONTEXT` still produce
  EnUs locale.
- No call site silently changes meaning when new variants appear
  (exhaustiveness check should catch this at compile time).

### C. lex_with shim + parity (W5-134)

`lex(input)` delegates to `lex_with(input, A1, EnUs)`. Verify
the delegation is byte-identical for all existing EN test inputs.
The `lex_and_lex_with_a1_enus_match_on_representative_inputs`
test pins this for 13 representative inputs. Is the coverage
broad enough?

### D. Decimal separator semantics (W5-135)

`lex_number(chars, decimal_sep)` translates the locale's decimal
glyph to canonical `.` in the accumulated `raw` string before
calling `f64::from_str`. Verify:
- Edge case: `.` alone in DE. `lex_number` body: peek `.`, not
  digit, not decimal_sep (DE's is `,`), not exponent, break.
  raw = "". Parse "" as f64 → err → `InvalidNumber("")`. Is
  that the right error? Or should we surface `UnexpectedChar('.')`
  earlier?
- Edge case: `2e3` in DE — `2` digit consumed, `e3` exponent
  consumed. Works because `e`/`E` are locale-independent.
- Edge case: `.` followed by another `.` in DE — first `.` hits
  array-row pre-dispatch (4.9.B.3), emits `Semicolon`. Second `.`
  same. So `..` in DE → `Semicolon, Semicolon`. Is that the right
  outcome? It's a weird input but should fail-loud or be
  consistently mapped.

### E. Separator pre-dispatch (W5-136)

The pre-dispatch maps both `arg_separator` AND `array_col_separator`
to `Token::Comma` — EN's `,` plays double role and emits Comma
either way. DE has DISTINCT glyphs for each role (`;` arg vs `\\`
array col) but both still emit Comma.

Verify:
- The parser context (`(...)` vs `{...}`) does the
  disambiguation downstream. Parser still works correctly for both
  locales (no parser change shipped yet — confirm DE arrays would
  parse correctly when 4.9.C lands).
- Pre-dispatch fires BEFORE the main match — no shadowing by
  literal arms (which were deleted in W5-136). Walk through every
  locale × every separator glyph to confirm.
- The "intersection_operator removed from LocaleData" decision
  from Sonnet H-5 is still respected — `@` isn't in `LocaleData`
  at all, can't be locale-configured.

    62	
    63	1. **Scalar / single value** → pass through unchanged. `@5` = `5`. `@SUM(A1:A10)` = `SUM(A1:A10)`.

    66	   - Else → `#VALUE!`.

    68	   - If formula col IS within range col span → pick that col's cell in that row.
    69	   - Else → `#VALUE!`.

## § A Summary + Verdict

**Verdict: FAIL.**  V3.6.0.5 D4 ships clean engine plumbing for format-aware rendering but the EvalContext construction silently drops two workbook-level inputs the rendering layer depends on -- `workbook.date_system()` is preserved BUT every replay path drops it before the napi sees it (no `Op::SetDateSystem`; `fromQbook` discards the loaded `Workbook`), and `workbook.locale()` is OVERRIDDEN to `EnUs` even when `Op::SetLocale` updated it via replay.  Additionally, the IDE edit-flow regression introduced by D4 (pre-rendered strings populate `data-original-text` which feeds the `<input>` on click-to-edit + the `Escape`-cancel restore path) breaks user editing for any format that introduces non-parseable characters (`$1,234.56`, `50.00%`, `0042` with leading zeros) -- `parseCellRawInput` does `Number(trimmed)` which produces NaN for currency/percent/grouped strings and errors out on Enter.  The Pending-with-format render (`Value::Blank` -> `0.00`) is a third UX regression -- pre-D4 pending cells displayed `"(pending)"`.

The happy path (Custom format + PutValue + workbook fresh: registered Custom percent format -> "50.00%") works correctly.  Probed via `opus_d4_probe_happy_path_percent_format`.  CSP-safe path is correctly maintained by IDE (escapeHtml on both rendered + value-default paths, server-side AND in the injected client script).

The findings are concentrated in five areas: (1) **Op::SetDateSystem does not exist**; the workbook's `date_system` is set by the `.qbook` loader (`set_date_system`) but op-log replay never touches it, so the napi reads the default `Excel1900` regardless.  `fromQbook` then double-faults by discarding the loaded `Workbook` and constructing the session via `export_bytes -> from_snapshot`, so even the loader-side `set_date_system` is lost.  An Excel1904 workbook renders date format strings against Excel1900 (off by 1462 days).  Probed.  (2) **`Locale::EnUs` hardcoded** in the EvalContext while `workbook.locale()` is `EnUs` | `De` | `Fr` -- today the format render layer doesn't consult locale (month names hardcoded English in `render.rs:660-690`), so this is a DEFERRED-feature concern, but the V3.6.0.5 D4 docstring explicitly says "locale-aware deferred to V3.6.1+" implying it WILL matter and the hardcoding silently suppresses workbook locale once render.rs grows locale-conditionals.  Probed.  (3) **IDE `data-original-text` is the engine-pre-rendered string** -- a formatted cell's edit-mode `<input>` populates with the rendered display string, not the raw value; `parseCellRawInput` then NaN's on `$1,234.56` / `50.00%` / `0042`.  Pre-D4 the cell displayed the raw value and Enter committed correctly; post-D4 every format that introduces non-parseable characters breaks the edit path.  Probed by inspection (no compiled test for the mocha-level dispatcher in this audit lane).  (4) **`Pending` value + format -> `"0.00"`**: `CellWireValue::Pending.to_value()` returns `Value::Blank`; `route_section` treats Blank as `0.0`; a Number-format section renders `"0.00"`.  Pre-D4 the IDE explicitly mapped `pending` -> `"(pending)"` via `formatCellValue`; post-D4 the pre-rendered string takes precedence via `??` so a pending+formatted cell displays as `"0.00"`.  Probed.  (5) **No engine-side `FormatString` cache**: `format::parse` runs per-cell-per-snapshot.  For a workbook with 100k formatted cells, that's 100k `parse` invocations per `workbook_snapshot()` call.  The field docstring acknowledges this ("V3.7+ may cache parsed FormatString keyed by format id on CollabSession") but doesn't gate on profiling.

Findings: 3 HIGH, 3 MEDIUM, 4 LOW, 3 INFO.  No cross-peer convergence bug.  No data-loss bug.  All three HIGHs are semantically-visible behavior regressions, two of which are inherent to V3.6.0.5 D4's design (date_system propagation; pre-rendered string injection into edit-mode input).  These need in-cycle closure OR explicit reasoned defer with a backlog item.

## § B HIGH findings

### B.1 -- HIGH-1: `workbook.date_system()` is ALWAYS `Excel1900` at napi `workbook_snapshot` time; Excel1904 workbooks silently render dates 1462 days off

**Scope**: `crates/ql-bindings-node/src/lib.rs:1653-1658` (`workbook_snapshot` EvalContext construction) + `crates/ql-bindings-node/src/lib.rs:1895-1916` (`from_qbook` constructor) + `crates/ql-oplog/src/op.rs` (no `Op::SetDateSystem` variant) + `crates/ql-oplog/src/replay.rs:740-770` (no `set_date_system` call during replay).

The pipeline:
1. `workbook_snapshot` calls `inner.rebuild_workbook(&registry)` (engine line 1642).
2. `rebuild_workbook` (`crates/ql-collab/src/session.rs:2279`) does `let mut workbook = Workbook::new()` (fresh, default `DateSystem::Excel1900`), then `replay_into(&self.log, &mut workbook, registry)`.
3. `replay_into` (in `crates/ql-oplog/src/replay.rs`) walks every `Op` variant.  **No variant calls `workbook.set_date_system(_)`**.  `Op::SetLocale` exists at line 861; `Op::SetDateSystem` does not exist anywhere in the codebase (grep -- empty).
4. So `workbook.date_system()` (engine line 1653) returns `Excel1900` for every session, regardless of the underlying `.qbook` file's `date_system` envelope field.

The `from_qbook` constructor compounds this:
```rust
pub fn from_qbook(path: String, peer_id_override: BigInt) -> Result<Self> {
    let pid = peer_id_from_bigint(&peer_id_override)?;
    let (_workbook, oplog) = load_workbook_with_oplog(...)?;  // <-- workbook DISCARDED
    let bytes = oplog.export_bytes()?;
    let session = CoreCollabSession::from_snapshot(pid, &bytes)?;
    Ok(Self { inner: ... })
}
```

The loaded `Workbook` is bound to `_workbook` (discarded).  So even though `load_workbook_with_oplog` reads `workbook.toml` and produces a `Workbook` with the right `date_system`, the session is built from `oplog` alone, replay yields a fresh `Workbook::default()`, and `date_system()` reverts to `Excel1900`.

The `WorkbookSnapshotJson.dateSystem` field then surfaces `"Excel1900"` even when the file said `Excel1904`.  The `eval_ctx.date_system` used by `format::render` for date format strings (e.g., `"yyyy-mm-dd"`) is also `Excel1900` -- so a cell with serial `1` (which is `1904-01-02` in Excel1904 but `1900-01-01` in Excel1900) renders as `"1900-01-01"`.  The 1462-day off-by-one is silent.

**Reproducibility**: Probed via `opus_d4_probe_date_system_never_excel1904_via_oplog_replay` (inline, removed post-audit).  Confirmed that after a series of every-possible-Op replay, `workbook.date_system()` stays `Excel1900`.  Independently the `from_qbook` discard is verifiable from the source (line 1897: `let (_workbook, oplog) = ...`).

**Severity HIGH** because: (a) silent semantic divergence on a documented contract (`WorkbookSnapshotJson.dateSystem` docstring at engine lines 683-700 promises round-trip from the workbook's date system); (b) date-rendered cells are wrong by ~4 years for legacy macOS Excel files; (c) the IDE has no way to detect the bug (the napi reports `"Excel1900"` even when the underlying file is Excel1904); (d) the V3.6.0.5 D4 docstring explicitly cites Phase 4.6 D-1 as the source of `workbook.date_system()` -- the implication is the workbook is authoritative, but the implementation defangs it.

**Suggested closure** (in-cycle):

Option (a) -- preferred: add `Op::SetDateSystem { date_system: DateSystemWire }` variant to the op log, emit it in `from_qbook` BEFORE handing the session to the caller (or persist it via the .qbook loader's first append), and update `replay.rs` to call `workbook.set_date_system(_)`.  This mirrors the W5-146 `Op::SetLocale` + `LocaleWire` pattern exactly.  Requires:
- New `DateSystemWire` enum in `ql-oplog/src/op.rs` mirroring `LocaleWire` (`Excel1900` | `Excel1904` | `Unknown(String)` for forward compat).
- `Op::SetDateSystem { date_system: DateSystemWire }` variant in `Op` enum.
- Replay handler in `crates/ql-oplog/src/replay.rs` that calls `workbook.set_date_system(_)`.
- `from_qbook` emits a prefix `Op::SetDateSystem { date_system: loaded.date_system().into() }` BEFORE the rest of the log when the loaded workbook's date_system differs from the default.  Or: a fresh CollabSession::from_qbook variant that constructs the workbook directly and skips the export/import round-trip (more invasive).
- `WorkbookRuntime::set_date_system` (if any) appends `Op::SetDateSystem` to the log (mirror `set_locale` at config.rs:61).
- `CacheEffect::SetDateSystem` if the cache needs to track this (probably not; the napi reads workbook.date_system() directly).

Option (b) -- defer: explicitly mark `WorkbookSnapshotJson.dateSystem` as "currently always `Excel1900`" in the docstring + add a runtime warning / loud error if a non-default `date_system` is detected at load time.  Closes the silent divergence without the wire-format work.  Acceptable IF date_system support is genuinely V3.7+ scope; today's V3.6.0.5 D4 promise of "round-trips through V3.6+ format-aware rendering" is misleading without one of these.

Plus a regression test:
```rust
#[test]

    // Construct a workbook with Excel1904 via the loader; export via
    // save_workbook_with_oplog; load via fromQbook; verify napi
    // workbook_snapshot.date_system == "Excel1904".
    let mut wb = Workbook::new();
    wb.set_date_system(DateSystem::Excel1904);
    save_workbook_with_oplog(&wb, /* empty oplog */, "test", &dir)?;
    let session = CollabSession::from_qbook(dir.to_string(), BigInt::from(0_u64))?;

```

### B.2 -- HIGH-2: `data-original-text` populated with engine-rendered string breaks click-to-edit + Escape-cancel for formatted cells

**Scope**: `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:217-260` (`renderRows`) + `cellGrid/cellGridHtml.ts:402-410` (`beginEdit` client) + `cellGrid/cellGridLogic.ts:163-178` (`parseCellRawInput`).

V3.6.0.5 D4 changes `renderRows` line 229: `const valueStr = e.rendered ?? formatCellValue(e.value);`.  The `valueStr` then feeds two HTML attributes (line 254):
```ts
data-original-text="${escapeHtml(valueStr)}" data-original-kind="${escapeHtml(e.value.kind)}"
```

The webview client script (line 405) reads:
```js
var originalText = cell.getAttribute('data-original-text') || '';
// ...
var input = document.createElement('input');
input.value = originalText;  // <-- pre-rendered string fed into the input
```

On Enter, the input's value is posted as `rawInput`:
```js
vscode.postMessage({
  type: 'putValue',
  sheet: SHEET, row: ..., col: ...,
  rawInput: raw  // <-- the pre-rendered string verbatim
});
```

`parseCellRawInput` (cellGridLogic.ts:163) does:
```ts
const n = Number(trimmed);
if (!Number.isFinite(n)) {
  throw new Error(`[bad_argument] cell value must be a finite number, got "${trimmed}"`);
}
```

For three common formats, this regresses:
- Currency `[$$-409]#,##0.00`: cell value `1234.56` renders as `"$1,234.56"`.  `Number("$1,234.56")` -> `NaN` -> error.
- Percent `0.00%`: cell value `0.5` renders as `"50.00%"`.  `Number("50.00%")` -> `NaN` -> error.
- Leading-zero `00000`: cell value `42` renders as `"00042"`.  `Number("00042")` -> `42` (works, but loses leading-zero context on re-save).
- Thousands `#,##0`: cell value `1234` renders as `"1,234"`.  `Number("1,234")` -> `NaN` -> error.
- Date `yyyy-mm-dd`: cell value `1` renders as `"1900-01-01"`.  `Number("1900-01-01")` -> `NaN` -> error (date cells become uneditable in numeric mode).

The Escape-cancel path (line 394) restores `data-original-text` via `appendChild(document.createTextNode(cell.getAttribute('data-original-text')))` -- which is the SAME pre-rendered string.  No data loss on cancel, but the cell never restores to the un-edited rendered form (which was the same string anyway).

The presence-cell selector (line 471) uses `[data-row="..."][data-col="..."]` -- unaffected by the original-text change.

**Reproducibility**: Verified by inspection.  The `parseCellRawInput` -> `Number(trimmed)` -> `Number.isFinite` chain is unambiguous.  The pre-rendered string -> `data-original-text` -> input value chain is unambiguous.

A mocha test (not in this audit) could pin via:
- Construct a fixture cell with a custom percent format.  Confirm `valueStr` from `renderRows` is `"50.00%"` (would need to mock `cell.rendered`).
- Simulate beginEdit on the cell.  Read input.value via webview-equivalent (would need a JSDOM-style harness).
- POST a `putValue` with rawInput = `"50.00%"`.  Confirm the dispatcher fires `errorReply`.

The cleanest demonstration is the parseCellRawInput unit test: `assert.throws(() => parseCellRawInput("50.00%"))` is sufficient to prove the chain breaks.

**Severity HIGH** because: (a) every formatted-cell edit on production paths is broken for the most common Excel format families (currency, percent, thousands, date); (b) the regression is silent at the napi level (engine doesn't know the IDE consumer is feeding the rendered string into an input); (c) the failure mode is user-visible (every Enter on a formatted cell errors), which makes it loud once a user hits it but not detectable in unit tests today; (d) pre-D4 behavior was correct.

**Suggested closure** (in-cycle, IDE-only):

Option (a) -- preferred: emit BOTH `data-original-text` (the rendered display string) AND `data-raw-value` (the value-default representation) from `renderRows`.  `beginEdit` reads `data-raw-value` (or `data-original-text` if `data-raw-value` is absent for backward compat); `data-original-text` is still used for Escape-cancel restore.

```ts
// renderRows
const displayStr = e.rendered ?? formatCellValue(e.value);
const rawValueStr = formatCellValue(e.value);  // unconditionally raw
const dataAttrs = editable
  ? ` data-row="${rowSafe}" data-col="${colSafe}" `
    + `data-original-text="${escapeHtml(displayStr)}" `
    + `data-raw-value="${escapeHtml(rawValueStr)}" `
    + `data-original-kind="${escapeHtml(e.value.kind)}"`
  : '';

// beginEdit (client):
var rawValue = cell.getAttribute('data-raw-value') || cell.getAttribute('data-original-text') || '';
input.value = rawValue;
```

Option (b): defer pre-rendering entirely until the IDE has a separate "formula bar" surface that displays the raw value while the cell shows the rendered display.  This is the Excel model.  Bigger refactor.

Option (c): make `parseCellRawInput` strip currency / percent / thousands tokens before `Number()`.  Less clean; doesn't help dates or leading-zero formats.

I recommend (a) as the in-cycle fix.  Plus add a TS test:
```ts
test('rawValue attribute preserves un-rendered value for editing', () => {
  // Build a fixture with cell.rendered = "$1,234.56", value = number(1234.56).
  // Render to HTML.  Parse the HTML.  Confirm data-raw-value = "1234.56".
});
```

### B.3 -- HIGH-3: `CellWireValue::Pending` + number format renders as `"0.00"` (UX regression: pre-D4 IDE explicitly showed `"(pending)"`)

**Scope**: `crates/ql-oplog/src/wire.rs:113-126` (`to_value`) + `crates/ql-functions/src/format/render.rs:33-41` (`render`) + `crates/ql-functions/src/format/render.rs:47-78` (`route_section` + `routing_index_for_number`) + `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:268-281` (`formatCellValue`).

`CellWireValue::Pending.to_value()` returns `Ok(Value::Blank)`.  `format::render(&Value::Blank, ...)` then routes through `routing_index_for_number(0.0, n_sections)` (line 59) -- Blank is treated as 0.0 for section routing AND for digit rendering.  A 1-section Number format like `"0.00"` produces `"0.00"`.

Pre-V3.6.0.5 D4, the IDE's `formatCellValue` (line 278-280) explicitly mapped `pending` -> `"(pending)"`.  Post-D4, if a pending cell has a format, the engine pre-renders it as `"0.00"` (or similar) and the IDE's `??` fallback never fires.  The cell appears as a literal zero.

Users now can't distinguish "formula hasn't evaluated yet" from "formula evaluates to zero".

**Reproducibility**: Probed via `opus_d4_probe_pending_value_with_number_format_renders_zero` (inline, removed post-audit).  Confirmed `rendered = Some("0.00")` for cell with `CellWireValue::Pending` + Builtin format id 2 ("0.00").

**Severity HIGH** because: (a) silently changes the visible cell state; (b) breaks the IDE's explicit pre-D4 pending semantic; (c) the engine renderer's Blank-as-zero behavior is correct in isolation (it's Excel's behavior for cells with no value but a number format) but the IDE has a different semantic for `Pending` specifically (formula-not-yet-evaluated, not "blank").

**Suggested closure** (in-cycle):

Option (a) -- preferred: at the napi layer, SHORT-CIRCUIT pre-rendering when `state.value` is `CellWireValue::Pending` (or any value where `is_pending()` returns true).  Specifically:
```rust
let rendered: Option<String> = match (state.format.as_ref(), state.value.as_ref()) {
    (Some(fmt_id), Some(wire_value)) if !wire_value.is_pending() => {
        // ... existing pipeline ...
    }
    _ => None,  // pending cells fall back to IDE's "(pending)" display
};
```

This preserves the V3.2.a `formatCellValue('pending')` -> `"(pending)"` semantic.  Add a regression test:
```rust
#[test]
fn v3_6_0_5_d4_pending_value_does_not_pre_render() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(Op::AddSheet { name: "S".into(), chunk_rows: 100 }).unwrap();
    s.append_op(set_cell_format_builtin(0, 0, 0, 2)).unwrap();
    s.append_op(Op::PutValue {
        sheet: 0, row: 0, col: 0,
        value: CellWireValue::Pending,
    }).unwrap();
    // Per V3.6.0.5 D4 audit-of-D4 HIGH-3 closure: pending cells
    // skip pre-render so the IDE shows "(pending)" via fallback.
    // [Build snapshot via the same pipeline as the napi layer]
    assert_eq!(rendered, None);
}
```

Option (b): update the IDE renderer to detect rendered-as-zero-for-pending and override.  Brittle (engine could render differently for non-Number formats); rejected.

### C.1 -- MED-1: `Locale::EnUs` hardcoded in EvalContext silently overrides `workbook.locale()` (De / Fr)

**Scope**: `crates/ql-bindings-node/src/lib.rs:1654-1658`.

```rust
let eval_ctx = ql_types::EvalContext {
    date_system: workbook_date_system,
    locale: ql_types::Locale::EnUs,  // <-- HARDCODED, ignores workbook.locale()
    now_provider: ql_types::NowProvider::System,

```

`workbook.locale()` (`crates/ql-storage/src/workbook.rs:440-442`) exists and can be `EnUs | De | Fr`.  It is updated via `Op::SetLocale` at replay (`crates/ql-oplog/src/replay.rs:861-863`).  The napi layer silently drops it.

**Today's impact**: `format::render` does NOT consult `ctx.locale` (verified: month names hardcoded English at `render.rs:660-689`; digit / decimal separator hardcoded American).  So the hardcoding is INERT for rendering at V3.6.0.5.

**Forward impact** (per the V3.6.0.5 D4 docstring "locale-aware deferred to V3.6.1+"): once `render.rs` grows locale conditionals (likely V3.6.1 per the docstring), this hardcoding silently regresses non-EN-US workbooks to EN-US rendering.  The bug WILL surface and is invisible until then.

**Reproducibility**: Probed via `opus_d4_probe_locale_is_hardcoded_enus_ignoring_workbook_locale` (inline, removed post-audit).  Probe constructs a session with `Op::SetLocale { locale: De }`, calls the rendering pipeline, asserts `used_locale == EnUs` while `workbook.locale() == De`.  Confirmed.

**Severity MED** because: (a) no behavior regression TODAY (render.rs ignores locale); (b) silent forward-compatibility hazard that lands the moment render.rs grows locale-conditionals; (c) the V3.6.0.5 D4 docstring acknowledges locale-aware deferred, implying the hardcoding is a placeholder -- but a placeholder of `EnUs` silently suppresses the workbook's value rather than failing loudly.

**Suggested closure** (in-cycle):

Option (a) -- preferred: thread `workbook.locale()` through immediately, even if render.rs doesn't use it.  The cost is zero (one struct field assignment).  Diff:
```rust
let eval_ctx = ql_types::EvalContext {
    date_system: workbook_date_system,
    locale: workbook.locale(),  // pass through; render.rs ignores until V3.6.1+
    now_provider: ql_types::NowProvider::System,
};
```

This avoids silent regression at V3.6.1+ ship without waiting for that change.  No new tests required (V3.6.1+ tests will pin the locale-aware path; today's path is unchanged).

Option (b): explicit panic / loud-error if `workbook.locale() != EnUs` at V3.6.0.5 D4 since the napi can't honor non-EN.  Conservative; loud-failure-not-silent.  Probably overkill; option (a) is cleaner.

### C.2 -- MED-2: `format::parse` runs per-cell-per-snapshot (no engine-side cache); 100k formatted cells = 100k parse calls per `workbook_snapshot`

**Scope**: `crates/ql-bindings-node/src/lib.rs:1758-1761` (per-cell pipeline) + `crates/ql-functions/src/format/parser.rs` (parse is recursive descent over tokens; non-trivial).

The current pipeline (engine line 1747-1768) for each cell:
```rust
let rendered: Option<String> = match (state.format.as_ref(), state.value.as_ref()) {
    (Some(fmt_id), Some(wire_value)) => {
        wire_value.to_value().ok()
            .and_then(|value| {
                workbook.formats().lookup(*fmt_id)
                    .map(|fmt_str| (value, fmt_str.to_string()))
            })
            .and_then(|(value, fmt_string)| {
                ql_functions::format::parse(&fmt_string).ok().map(|fmt| (value, fmt))
            })
            .map(|(value, fmt)| {
                ql_functions::format::render(&value, &fmt, &eval_ctx)
            })
    }
    _ => None,
};
```

Per-cell `format::parse(&fmt_string)` is called.  For a workbook with N formatted cells:
- N `lookup` calls (HashMap lookup -- cheap).
- N `to_string` calls (heap alloc for the format string).
- N `parse` calls (tokenize + split_sections + build_section, each recursive descent).

`parse` is non-trivial: `parser.rs` is 899 LOC.  For Excel files with many cells sharing the same format (the COMMON case), this is highly wasteful -- the same format string is parsed N times.

**Reproducibility**: Inspection.  No probe.  Profile-able via a microbench (deferred to V3.6.0.7 D6 spike).

**Severity MED** because: (a) the V3.6.0.5 D4 field docstring acknowledges the per-call cost ("V3.7+ may cache parsed FormatString keyed by format id on CollabSession") so this is a KNOWN limitation; (b) for small workbooks the cost is invisible; (c) for large workbooks at high `workbook_snapshot` cadence the cost compounds linearly; (d) V3.6.0.7 D6 is the right spike to measure but D4 ships without any deferral gate.

**Suggested closure** (DEFER unless profiling justifies; explicit V3.6.0.7 D6 spike scope):

Option (a) -- V3.6.0.7 D6 spike: measure `workbook_snapshot` cost for 100-cell, 1000-cell, 10000-cell workbooks with mixed formats.  If `parse` is >10% of the total cost, add a per-format-id parse cache (LRU or eager) keyed on `FormatId`.

Option (b) -- in-cycle hot-fix: build a `HashMap<FormatId, FormatString>` once at the top of `workbook_snapshot`, populate it on first-seen-format, reuse for subsequent cells.  ~10 LOC diff, no API surface change.

```rust
let mut parsed_formats: HashMap<ql_storage::FormatId, ql_functions::format::FormatString> =
    HashMap::new();
// In the per-cell map:
let rendered = ... .and_then(|(value, fmt_id_ref)| {
    let fmt_id = *fmt_id_ref;
    // Cache hit / miss + populate.
    let parsed = parsed_formats.entry(fmt_id).or_insert_with(|| {
        ql_functions::format::parse(workbook.formats().lookup(fmt_id).unwrap()).unwrap()
    });
    Some(ql_functions::format::render(&value, parsed, &eval_ctx))
});
```

In-cycle option (b) closes the per-snapshot redundancy without touching the engine state.  Recommended.

### C.3 -- MED-3: ide-consumer-contract.md doc drift -- R-V3.5-4 still listed as "DOCUMENTED" / "V3.6+ scope" + multiple "DEFERRED to V3.6.0.5 D4" mentions stale

**Scope**: `docs/architecture/ide-consumer-contract.md` lines 1341, 1468, 1485, 1542.

## § D LOW findings

### D.1 -- LOW-1: 5-point silent-fallback pipeline returns `None` on EACH failure point with no telemetry / log

**Scope**: `crates/ql-bindings-node/src/lib.rs:1747-1768`.

The pipeline collapses 5 distinct failure modes into a single `Option::None`:
1. `state.value.to_value()` Err -> `unknown error sigil` (e.g., wire format saw an unrecognized canonical error string).
2. `workbook.formats().lookup(*fmt_id)` None -> format id not in workbook (replay catches this upstream; this branch should be unreachable in production -- but the silent fallback hides that promise).
3. `ql_functions::format::parse(&fmt_string)` Err -> malformed format string (V2 token, etc.).
4. The final `.map(|(value, fmt)| ql_functions::format::render(&value, &fmt, &eval_ctx))` cannot fail (render returns String unconditionally).
5. Plus the implicit "no format or no value" branch which returns None as the legitimate display fallback.

The CALLER (IDE) can't distinguish "no format" (legitimate) from "format parse error" (engine bug; format string is corrupted) from "format id missing" (engine corruption; replay should have caught this).  All three look identical.

**Severity LOW** because: (a) the silent fallback is correct semantically (IDE always gets a renderable display string via value-default); (b) for invariant-protected paths (lookup miss, replay-validated), this is defense in depth; (c) for format::parse Err on legacy V2 tokens, this is the right behavior.

But: V3.7+ telemetry would want to surface "X cells had format parse errors" to help users / developers find legacy V2 tokens that need migration.  The current pipeline gives up too much.

**Suggested closure** (DEFER to V3.7+ telemetry; comment-only in-cycle):

Add a docstring note acknowledging the collapse:
```rust
// V3.6.0.5 D4 silent-fallback: each .ok() / .and_then(None) point
// returns None to the IDE.  The IDE can't distinguish:
// - state.value.to_value() Err (engine wire-decode corruption)
// - workbook.formats().lookup() None (replay validator failed)
// - format::parse() Err (V2 token; legitimate)
// V3.7+ should consider surfacing these via a side-channel (e.g.,
// WorkbookSnapshotJson.render_errors: Vec<RenderErrorJson>).
let rendered: Option<String> = ...;
```

Or: introduce a `RenderResult { ok: Option<String>, error: Option<&'static str> }` shape that lets the caller see WHY rendering failed.  Heavier change; defer to V3.7+.

### D.2 -- LOW-2: `format_pairs` collection allocates per-cell `String` from `&str` despite `Arc<str>` availability in `format_table_cache`

**Scope**: `crates/ql-bindings-node/src/lib.rs:1756` (`.map(|fmt_str| (value, fmt_str.to_string()))`).

The pipeline does `workbook.formats().lookup(*fmt_id).map(|fmt_str| (value, fmt_str.to_string()))`.  `lookup` returns `Option<&str>`; we then heap-allocate a `String` per cell just to feed `format::parse(&fmt_string)`.  The `&str` lives as long as the `workbook` borrow (which the closure captures), so we don't NEED the heap allocation:

```rust
.and_then(|value| {
    workbook.formats().lookup(*fmt_id).map(|fmt_str| (value, fmt_str))
    // fmt_str is &str, NOT String
})
.and_then(|(value, fmt_str)| {
    ql_functions::format::parse(fmt_str).ok().map(|fmt| (value, fmt))
})
```

This requires no API change (format::parse takes `&str`).  Saves N allocations per snapshot (where N is the formatted-cell count).

**Severity LOW** because: (a) allocations are cheap; (b) bounded by N (not quadratic); (c) the V3.6.0.5 D4 docstring already flags the per-cell cost concern.

**Suggested closure** (in-cycle):

Drop the `.to_string()` call.  ~1 LOC diff:
```rust
- .map(|fmt_str| (value, fmt_str.to_string()))
+ .map(|fmt_str| (value, fmt_str))
```
... and update subsequent closures to accept `&str` instead of `String`.

### D.3 -- LOW-3: `dateSystem` String discriminator chosen over typed wrapper struct; future expansion (e.g., Excel1582?) requires breaking shape change

**Scope**: `crates/ql-bindings-node/src/lib.rs:1829-1837` + `crates/ql-bindings-node/src/lib.rs:683-700` (docstring).

The V3.6.0.5 D4 ship choses `dateSystem: String` over `dateSystem: DateSystemJson` (a tagged struct).  Per the docstring:
> String type chosen over wrapper struct for simplicity.

This MIRRORS the V3.6.0.4 D3 `FormatIdJson` / `CellValueJson` `kind: String` pattern.  BUT: those types have RICHER content (Custom { peer, counter } vs Builtin { id }).  `DateSystem` is a flat enum with 2 variants today.

Concern: if a third variant lands (e.g., a hypothetical `Excel1582` for Julian-calendar-compatible workbooks, or a `CustomEpoch { unix_seconds: i64 }`), the napi layer extends the String set BUT the TS interface union type breaks for any consumer typing `dateSystem === 'Excel1900' | 'Excel1904'`.

A typed wrapper struct `DateSystemJson { kind: 'Excel1900' | 'Excel1904' }` would let `Excel1582` land as a new `kind` value without breaking the field type.  Today's String approach commits to a flat-string namespace.

**Severity LOW** because: (a) `ql_types::DateSystem` has 2 variants today + a hypothetical 3rd is V4.x scope; (b) the TS union-type pin in `types.ts:255` is the right pin for V3.6.0.5; (c) the cost of switching later is bounded (rename one field type).

**Suggested closure** (DEFER; V4.x consider).

### D.4 -- LOW-4: `extractSheetSnapshot` field-set bookkeeping is brittle for future `CellSnapshotJson` additive fields

**Scope**: `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:781-789`.

```ts
const entry: { row: number; col: number; value: QuantbookCellValue; rendered?: string } = {
    row: cell.row,
    col: cell.col,
    value: typed,
};
if (cell.rendered !== undefined) {
    entry.rendered = cell.rendered;
}
entries.push(entry);
```

The conditional include of `rendered` is needed because V3.5.0.4b shape-stability tests assert exact key sets via `deepStrictEqual`.  Adding a `rendered: undefined` to every entry would break those tests.

The pattern works for one optional field; for N optional fields it grows linearly in conditionals + the entry-construction shape gets harder to maintain.  Each future additive field (e.g., V3.6.0.6 D5's formula passthrough) needs the same conditional + a coordinated test update.

**Severity LOW** because: (a) the current 1-field pattern is fine; (b) the test update is a small constant cost per new field; (c) ts strict-mode catches missing required fields at compile time.

**Suggested closure** (DEFER; V3.7+ refactor when 3+ optional fields exist):

Introduce a builder helper:
```ts
function buildEntry(cell: CellSnapshotJson, value: QuantbookCellValue) {
    const e: { row: number; col: number; value: QuantbookCellValue; rendered?: string; /* etc */ } = {
        row: cell.row, col: cell.col, value
    };
    if (cell.rendered !== undefined) e.rendered = cell.rendered;
    return e;
}
```

OR: update the V3.5.0.4b shape-stability tests to ignore optional-undefined fields (`deepStrictEqual` doesn't have this mode, but a custom assert helper could).

V3.6.0.6 D5 will introduce formula editing through the napi.  Formulas have the SAME edit-flow concern as formatted values: the user types `=SUM(A1:B10)`, the cell displays `42`, but `data-original-text` would carry `42` post-D5 too.  Pre-D4 the formula text was lost; post-D5 it should land in the cell so beginEdit shows the formula source, not the value.

Recommend HIGH-2 closure (option (a) `data-raw-value` attribute pattern) extends naturally to D5: `data-raw-value` for values, `data-raw-formula` for formulas, beginEdit chooses based on cell shape.

### G.3 -- V3.6.0.7 D6 profiling spike scope should include format::parse cost (per C.2 MED-2)

The V3.6.0.7 D6 spike will measure incremental-snapshot-delta perf.  Add `format::parse` cost as a sub-measurement:
- 1k cells, 10 unique formats, full snapshot: time.
- 1k cells, 1 unique format, full snapshot: time.
- Difference proves the per-cell-parse vs per-format-cache delta.

If the delta is >10ms / 1k cells, ship the C.2 MED-2 option (b) per-snapshot cache.

### G.4 -- V3.6.1+ locale-aware rendering needs to thread `workbook.locale()` through

Once render.rs grows locale-conditionals (e.g., German month names "Januar" / "März" vs English "January" / "March"), MED-1 becomes a HIGH.  The in-cycle MED-1 closure (option (a)) prevents this from regressing silently.

### G.5 -- V3.7+ stable-FormatId migration would let format_table_cache + cell_op_index unify into a single index

The current shape has:
- `format_table_cache: HashMap<FormatId, Arc<str>>` (V3.6.0.3 D2).

## LOW

### CODEX-LOW-1

Subject: Digit-leading dotted identifier lexer path has no direct lexer tests

Where: `crates/ql-formula-syntax/src/lexer.rs:522`; `crates/ql-formula-syntax/src/lexer.rs:1765`; `crates/ql-exec/tests/distribution_fns_e2e.rs:185`

Detail: W5-D-2 extends `lex_ident_or_ref` to accept segments like `.2T`, but
the lexer test block still only pins the older letter-leading dotted path
(`VAR.S`, `STDEV.P`, `A.B.C`) and rejection cases such as `VAR.1` /
`VAR.S1`. The new path is exercised indirectly through ql-exec e2e formulas
like `T.DIST.2T(1, 1)` and `T.INV.2T(0.05, 30)`, but there is no unit-level
coverage for `T.DIST.2T`, `T.INV.2T`, lowercase `.2t`, pure-digit rejection
(`T.DIST.2`), orphan-dot rejection (`T.DIST.`), or the deliberately accepted
unknown-name shape (`T.DIST.2T1`).

Recommendation: Add lexer unit tests for the digit-leading segment branch:
happy paths for `T.DIST.2T` / `T.INV.2T`, rejection for `T.DIST.` and
`T.DIST.2`, and an explicit acceptance-or-rejection decision for
`T.DIST.2T1`. Add a parser/printer round-trip for at least one digit-leading
dotted function name if printer stability matters.

Severity rationale: Low because shipped formulas work through dispatcher e2e
coverage and unknown names still fail at bind time. It is still a regression
gap in a cross-cutting lexer rule.

### CODEX-LOW-2

Subject: Digit-leading dotted segment accepts underscore despite the stated alphanumeric contract

Where: `crates/ql-formula-syntax/src/lexer.rs:562`

Detail: The W5-D-2 lexer comment and audit contract say a digit-leading dotted
segment accepts alphanumeric continuation and must contain at least one letter.
The implementation accepts underscore as well:
`else if c.is_ascii_digit() || c == '_'`. That means inputs such as
`T.DIST.2_T` lex as one identifier instead of rejecting at the unexpected
underscore. The binder will reject the name if it is used as an unknown
function, so this does not break the five registered T.* functions, but it
broadens the accepted identifier grammar beyond the stated Excel-canon shape.

Recommendation: Remove `|| c == '_'` from the digit-leading branch unless this
broader grammar is intentional. If intentional, update the comment and add a
test documenting the accepted underscore shape.

Severity rationale: Low because it is a lexical over-acceptance with downstream
unknown-name rejection, not a math or dispatch bug. It matters because this
lexer path is shared by future F.*, CHISQ.*, and other dotted statistical names.

### CODEX-LOW-3

Subject: Distribution module docs still describe only the Normal backend

Where: `crates/ql-functions/src/distribution_fns.rs:10`; `crates/ql-functions/src/distribution_fns.rs:32`

Detail: The module header now lists W5-D-2, but the implementation-strategy text
still says the numerical kernel reuses `statrs::distribution::Normal` and talks
about "f64 triples (mean, sd, x/prob)". That is stale for the new T.* functions,
which use `StudentsT::new(0.0, 1.0, df)` and have `df` as a required numeric
argument. The coercion paragraph also names numeric args as `x`, `mean`, `sd`,
and `prob`, omitting `deg_freedom`.

Recommendation: Update the docstring to say the module uses `Normal` for
NORM.* and `StudentsT` for T.*, and describe numeric args as including
`deg_freedom` / `df`. Replace the normal-only "triples" phrasing with
function-specific tuples.

Severity rationale: Low because the code is correct. The stale docstring is in
the file future distribution ports will copy from, so inaccurate backend and
coercion wording can seed later audit noise or implementation mistakes.

## Confirmed Non-Issues

- `StudentsT::new(location, scale, freedom)` is the correct statrs 0.18.0 API,
  and local statrs source confirms it rejects NaN params, `scale <= 0`, and
  `freedom <= 0`.
- `T.DIST`, `T.DIST.2T`, `T.DIST.RT`, `T.INV`, and `T.INV.2T` match the local
  IronCalc formulas: `cdf(x)`, `pdf(x)`, `2 * (1 - cdf(x))` clamped to `[0,1]`,
  `1 - cdf(x)` with the negative-result guard, `inverse_cdf(p)`, and
  `inverse_cdf(1 - p/2).abs()`.
- Domain checks match IronCalc: `df.trunc()`, `df >= 1`; `T.DIST.2T` rejects
  `x < 0`; `T.DIST.RT` allows negative x; `T.INV` rejects both probability
  endpoints; `T.INV.2T` accepts `p == 1`.
- Non-finite statrs outputs route to `#NUM!`: four functions use
  `finite_or_num`, and `T.DIST.RT` uses the equivalent manual
  `!result.is_finite() || result < 0.0` guard required by the IronCalc
  negative-result check.
- Arity mismatches return `#VALUE!` for all five functions, matching the
  codebase convention and the dispatcher e2e assertions.
- The requested anchors are pinned and correct: df=1 Cauchy PDF/CDF values,
  `T.DIST.2T(1,1)=0.5`, `T.DIST.RT(-1,1)=0.75`,
  `T.INV(0.975,10) ~= 2.228138851938055`, and
  `T.INV.2T(0.05,30) ~= 2.042272456301236`.
- Registry count is bumped to 209, and the count test passes.
- Coverage deferral entries for the five new T.* functions match the unit-test
  coverage shape.
- Matrix test counts match the actual 45 new ql-functions tests: `T.DIST` 10,
  `T.DIST.2T` 8, `T.DIST.RT` 8, `T.INV` 9, `T.INV.2T` 10.
- `A1.2B` does not enter the dotted-identifier branch. The lexer commits to
  `A1` as a cell reference, then lexes `.2` as a number and `B` as the next
  token; the parser rejects the adjacent tokens later.
- CHISQ.*, F.*, and related distribution families remain unregistered and are
  correctly out of W5-D-2 scope.

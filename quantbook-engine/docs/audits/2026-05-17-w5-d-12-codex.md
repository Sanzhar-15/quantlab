## HIGH

### HIGH-001 — SUBTOTAL is registered but not admitted to aggregate/range binding

**Where:** `crates/ql-functions/src/registry.rs:843`; `crates/ql-exec/src/plan.rs:421`

**Detail:** `SUBTOTAL` is registered as a `RangeAwareFn`, but `is_aggregate_function()` does not include `"SUBTOTAL"`. The binder uses that matcher to decide whether function arguments bind under `BindContext::AggregateArg`; otherwise they bind as `Scalar` and range names are rejected. In the current shape, `=SUBTOTAL(9, Sales)` where `Sales` is a named range will bind the `Sales` argument in scalar context and surface `NamedRangeInScalarContext` instead of producing `FnArg::Range`. Literal range refs are also not available on this path in v1. The new e2e only proves case-insensitive registry lookup, not runtime formula dispatch with a range argument.

**Recommendation:** Add `"SUBTOTAL"` to `is_aggregate_function()`, extend the `is_aggregate_function_lists_only_registered_aggregates` invariant to include it, and add a runtime e2e such as `SUBTOTAL(9, Sales)` over a named range returning the same value as `SUM(Sales)`.

**Severity rationale:** This blocks the primary user-facing SUBTOTAL range workflow despite the function being marked supported and registered. Direct unit tests call `range_fns::subtotal()` manually, so the failure is not caught by the current gates.

### LOW-002 — Coverage note assigns the STDEV.P anchor to STDEV.S

**Where:** `crates/ql-functions/tests/coverage.rs:435`

**Detail:** The coverage entry says `STDEV.S of {2,4,4,4,5,5,7,9} = 2.0`. The unit test correctly expects `STDEV.S = sqrt(32/7) ≈ 2.138089935299395`; `2.0` is the `STDEV.P` value for that sample.

**Recommendation:** Change the example to the sample standard deviation value, or refer to `STDEV.P` for the `2.0` anchor.

**Severity rationale:** Documentation-only drift, but it can mislead future audits of the function_num 7/8 dispatch table.

# W5-D-4 Opus Audit: BINOM.* / NEGBINOM.* / POISSON.* / EXPON.* / LOGNORM.*

Date: 2026-05-17
Scope: uncommitted W5-D-4 distribution-function batch on `feat/quantbook-engine`
(diff covers `crates/ql-functions/src/distribution_fns.rs`,
`crates/ql-functions/src/registry.rs`, `crates/ql-functions/tests/coverage.rs`,
`crates/ql-exec/tests/distribution_fns_e2e.rs`, `docs/compat/excel-matrix.md`).

## Summary

One HIGH panic-shape finding: `BINOM.INV` does **not** short-circuit the
`trials == 0` degenerate-binomial case, mirroring the documented `p == 0`
short-circuit. `BINOM.INV(0, p, alpha)` (with `p > 0`) is a valid Excel
domain (`trials >= 0`, `0 <= p < 1`, `0 < alpha < 1`), but it reaches
`statrs::distribution::Binomial::inverse_cdf(alpha)` over a distribution
whose CDF is identically `1.0`. The default `DiscreteCDF::inverse_cdf`
unwraps the `None` returned by `integral_bisection_search` and panics.
I reproduced this directly against statrs 0.18.0 outside the workspace
(`Binomial::new(0.5, 0).inverse_cdf(0.5)` panics with
`called Option::unwrap() on a None value`). The Codex audit found the
same issue (CODEX-HIGH-1); I confirm independently.

Two MEDIUM findings: (1) the `to_u64_index` upper-bound guard is loose
in f64-arithmetic (`u64::MAX as f64` rounds up to `2^64`, so the f64
value `2^64.0` passes the guard and saturates to `u64::MAX`); (2) the
module's "IronCalc divergences" section does not mention the
intentional `BINOM.INV` panic-avoidance divergence for `p == 0`
(and, after fixing HIGH-O-1, the same divergence for `trials == 0`).

Several LOW findings around doc/test-count drift in the matrix and
coverage entries, and one LOW around an `pmf(10)` anchor advertised in
the coverage entry but not actually present in the unit tests. None of
these affect runtime behavior.

The rest of the batch (BINOM.DIST, BINOM.DIST.RANGE, NEGBINOM.DIST,
POISSON.DIST, EXPON.DIST, LOGNORM.DIST, LOGNORM.INV) is independently
verified against:

- IronCalc references (`binom.rs`, `poisson.rs`, `exponential.rs`,
  `log_normal.rs`) — domain checks and statrs call ordering match.
- statrs 0.18.0 source (`Binomial::new(p, n)`,
  `NegativeBinomial::new(r, p)`, `Poisson::new(lambda)`,
  `LogNormal::new(location, scale)`, default `DiscreteCDF::inverse_cdf`).
- Closed-form anchor math for every claimed anchor value
  (`pmf(0;10,0.5)=1/1024`, `pmf(5;10,0.5)=252/1024`,
  `[4,6]=672/1024`, `CDF(5;10,0.5)=638/1024`, `BINOM.INV(...,0.5)=5`,
  `BINOM.INV(...,0.001)=1`, `NEGBINOM(0,1,0.5)=0.5`,
  `NEGBINOM(1,1,0.5)=0.25`, `POISSON(0,1)=e^{-1}`, `POISSON(1,1,T)=2e^{-1}`,
  `EXPON(1,1,T)=1-e^{-1}`, `LOGNORM(1,0,1,T)=Φ(0)=0.5`,
  `LOGNORM(1,0,1,F)=1/√(2π)`, `LOGNORM.INV(0.5,μ,σ)=exp(μ)`).
- All 4 ship gates per prompt assertion (assumed clean; not re-run).

## HIGH

### HIGH-O-1

Subject: `BINOM.INV` still panics for the zero-trials degenerate distribution

Where: `crates/ql-functions/src/distribution_fns.rs:1037-1057`

Detail: The pre-check accepts `trials == 0` (only `trials < 0.0` is
rejected, matching IronCalc's `binom.rs:205`). The `p == 0.0` branch is
short-circuited inline (l. 1052-1054), but `trials == 0` produces an
identically degenerate binomial for any `p`: `Binomial::pmf(0) = 1`,
`Binomial::cdf(k) = 1` for every `k >= 0` (statrs 0.18.0
`binomial.rs:146-153`, `binomial.rs:301-319`). Default
`DiscreteCDF::inverse_cdf` (statrs `mod.rs:204-221`) calls
`integral_bisection_search` over `[0, 2]` with `cdf` ≡ `1.0`; the search
returns `None` because `alpha ∈ (0, 1)` is not contained in
`[f(lb), f(ub)] = [1.0, 1.0]`, and statrs unwraps that `None`.

Reproduced externally against statrs 0.18.0:
```rust
let d = Binomial::new(0.5, 0).unwrap();
d.cdf(0);            // = 1.0
d.inverse_cdf(0.5);  // panics: called Option::unwrap() on a None value
```

Same panic shape that the in-file comment explicitly documents for
`p == 0.0` (l. 1044-1051), just reached via a second degenerate axis
that the impl missed. The current unit test
`binom_inv_negative_trials_is_num_error` only exercises `trials < 0`;
no `trials == 0` test exists, and no e2e dispatcher test for it either.
IronCalc's `binom.rs:182-237` has the same gap and would panic the same
way (this is an IronCalc bug we'd be inheriting).

Recommendation: Add a `if n == 0 { return Value::number(0.0); }`
short-circuit immediately after the `to_u64_index(trials)` conversion
(before any statrs call). Add at least one unit regression
(`binom_inv_trials_zero_returns_zero`) and at least one dispatcher
regression. Update the in-file comment to cover both
panic-avoidance branches, and add the matching note to the module's
"IronCalc divergences" section (see LOW-O-2 below).

Severity rationale: HIGH because a domain-valid user formula
(`BINOM.INV(0, 0.5, 0.5)` is well-formed Excel input) panics the engine
process. Discrete-distribution panic risks were called out as the
specific new concern for W5-D-4; this is one of two known
degenerate-CDF axes for `Binomial`, and only one is guarded.

## MEDIUM

### MEDIUM-O-1

Subject: `to_u64_index` upper-bound check is one tick too loose

Where: `crates/ql-functions/src/distribution_fns.rs:244-250`

Detail: `u64::MAX = 2^64 - 1 = 18_446_744_073_709_551_615`, but
`u64::MAX as f64 = 18_446_744_073_709_551_616.0 = 2^64` (f64 cannot
represent `2^64 - 1` exactly; it rounds up). Therefore the guard
`v > u64::MAX as f64` is equivalent to `v > 2^64`, not `v > u64::MAX`.
The f64 value `2^64.0` itself passes the guard, and `v as u64` in
modern Rust saturates to `u64::MAX` for any finite f64 above
`u64::MAX`. Result: feeding `Value::Number(2.0f64.powi(64))` as
`trials`, `number_s`, `number_s2`, `number_f`, or POISSON's `x` will
silently coerce to `u64::MAX` instead of `#NUM!`. The
public-facing contract in the docstring is "exceeds `u64::MAX` →
`#NUM!`", which the impl doesn't honor at the boundary. Codex flagged
the same issue (CODEX-MEDIUM-1); I concur on severity.

Recommendation: Switch to a strict lower bound on the f64-cast space:
`v >= u64::MAX as f64` (i.e., reject any finite f64 at or above
`2^64`), and add a comment noting the f64 precision quirk. Add at
least one boundary test (`to_u64_index(u64::MAX as f64) is None` /
`to_u64_index((u64::MAX as f64) - some_ulp)` boundary cases).

Severity rationale: MEDIUM. The issue is only reachable at extreme
inputs (no real spreadsheet uses `trials = 1.8e19`), and the cast is
memory-safe, but the impl drifts from the documented contract for
every W5-D-4 discrete function. Documentation drift on a numerical
boundary is the recurring class of MEDIUM finding from W5-D-2 and
W5-D-3; same shape here.

### MEDIUM-O-2

Subject: Module's "IronCalc divergences" section does not document the `BINOM.INV` panic-avoidance divergence

Where: `crates/ql-functions/src/distribution_fns.rs:212-232`

Detail: The W5-D-4 surface intentionally diverges from IronCalc's
`binom.rs` in one user-observable way: `BINOM.INV` short-circuits
`p == 0.0` to return `0.0` instead of (as IronCalc would, given the
same statrs pin) panicking through the default
`DiscreteCDF::inverse_cdf`. The inline comment at
`distribution_fns.rs:1044-1051` documents the panic shape and the
mathematical justification ("smallest k with CDF(k) >= alpha is 0
since CDF(0) = 1"), but the module-level "IronCalc divergences"
section (l. 212-232) lists only coercion and error-class
divergences. This same section was extended for W5-D-3 to call out
F.INV.RT's lower-strict and F.*'s missing `df` ceiling — same
documentation pattern is missing here.

Recommendation: Add a W5-D-4 bullet to the divergences section, e.g.:
"**BINOM.INV degenerate-distribution panic avoidance**: IronCalc's
`binom.rs` reaches statrs's default
`DiscreteCDF::inverse_cdf`, which panics
(`integral_bisection_search → None → .unwrap()`) for any binomial whose
CDF is constant (currently `p == 0`; see HIGH-O-1 for the matching
`trials == 0` axis). We short-circuit these cases inline and return
the only valid mathematical answer (`k = 0`). Microsoft canon is silent
on this corner; we follow the math." This frames it
symmetrically with the F.INV.RT + F.* ceiling divergences from
W5-D-3.1. Codex flagged the same gap (CODEX-LOW-3); I rate one
notch higher (MEDIUM) because it's a panic-vs-value divergence,
not a numeric or domain divergence.

Severity rationale: MEDIUM. The impl is correct, but the divergence
is more material than the W5-D-3 LOW divergences already
documented in the same section (this one is a panic-vs-value
contract; those were `p == 0` strict vs inclusive). Doc drift on
intentional divergences was the recurring W5-D-2/W5-D-3 MEDIUM class.

### LOW-O-3

Subject: `BINOM.DIST.RANGE` `cdf(upper) - cdf(lower - 1)` may produce small negative fp drift, which `finite_or_num` accepts

Where: `crates/ql-functions/src/distribution_fns.rs:1006-1011`

Detail: `binom_dist_range` returns `dist.cdf(upper) - dist.cdf(lower - 1)`
when `lower > 0`. Both calls go through statrs's `beta_reg` (regularized
incomplete beta), which can introduce floating-point rounding. For
mathematically-equal CDFs (e.g., `lower == upper + 1`, which would have
been rejected by the `number_s > number_s2` check, but tail-edge cases
like `lower == upper` for `p` near 1 can produce subtraction-of-near-
equals), the difference can drift slightly negative. `finite_or_num`
accepts any finite value including tiny negatives, so a result like
`-1.4e-17` would surface as a `Value::Number`. CHISQ.DIST.RT and
F.DIST.RT both use an explicit `result < 0.0 → #NUM!` defense for
exactly this scenario (`distribution_fns.rs:665, 815`); BINOM.DIST.RANGE
does not. IronCalc's `binom.rs:171` only checks `is_nan || is_infinite`
(matches the impl), so we're consistent with IronCalc, just inconsistent
with our own W5-D-3 right-tailed pattern.

Recommendation: Either follow the IronCalc pattern (current code,
documented) or follow our own W5-D-3 pattern (`if !prob.is_finite() ||
prob < 0.0 { return ... #NUM! }`). Both are defensible; documenting the
choice is the smaller change. No tests pin this corner.

Severity rationale: LOW. The fp drift would only matter for extreme
inputs (p near 0 or 1, narrow ranges), and even then is in the noise
floor. Largely an internal-consistency observation.

### LOW-O-4

Subject: `BINOM.DIST(n=0)` and similar degenerate non-panicking corners are untested

Where: `crates/ql-functions/src/distribution_fns.rs:917-950` (and analogous
fns); test gap

Detail: `BINOM.DIST(0, 0, p, TRUE/FALSE)`, `BINOM.DIST.RANGE(0, p, 0, 0)`,
and `NEGBINOM.DIST(0, 1, p_in_open_unit, ...)` are domain-valid corners
that do **not** panic (statrs handles them fine), but they're untested.
Given HIGH-O-1, surfacing these explicit tests as panic-regression armor
would be valuable; the discrete-distribution surface is the first one in
the codebase to have a documented degenerate-distribution panic class,
and explicit pinning prevents future statrs version-bump regressions
silently re-introducing panics.

Recommendation: Add one test per fn pinning the `n=0` (or analogous
degenerate) corner with a closed-form expected value, gated by the
post-HIGH-O-1 fix. Optional but increases panic-regression resilience.

Severity rationale: LOW. Coverage-gap finding; no current behavior bug.

### LOW-O-5

Subject: BINOM.DIST.RANGE `lower == 0` short-circuit comment slightly inaccurate

Where: `crates/ql-functions/src/distribution_fns.rs:1006-1010`

Detail: The inline comment says the `lower == 0` branch "avoids `cdf(0 - 1)`
underflow on u64". Strictly speaking, `0u64 - 1u64` in debug build would
panic on underflow, but in release it wraps to `u64::MAX`. Calling
`dist.cdf(u64::MAX)` doesn't panic — it just returns `1.0` per statrs
`binomial.rs:147-148` (`if x >= self.n { 1.0 }`). The subtraction
`cdf(upper) - 1.0` would then drift negative. So the issue avoided isn't
strictly "underflow" (no UB, no panic in either profile) but "spurious
negative result via wrap". The IronCalc port comment is silent on this.

Recommendation: Clarify the comment, e.g. "avoids `0u64 - 1u64` which
would panic in debug and wrap to `u64::MAX` in release, producing a
negative-looking probability via `cdf(upper) - 1.0`".

Severity rationale: LOW. The behavior is correct (the short-circuit
does the right thing); only the explanation is slightly imprecise.

## Confirmed Non-Issues

- Helper `to_u64_index` rejects NaN explicitly; this is defensive (NaN
  is also rejected upstream by `to_number_strict` → `sanitize_f64`).
- All BINOM/NEGBINOM/POISSON call sites pre-truncate via `.trunc()`
  before passing to `to_u64_index` (verified at all 5 entry points).
- `NegativeBinomial::new` argument order is `(r, p)` — verified
  against statrs 0.18.0 `negative_binomial.rs:88`. Impl passes
  `(number_s, p)` correctly. `number_s` is "successes" (= `r`), not
  "failures"; that role is `number_f` and is the observation
  point, not a parameter.
- `LogNormal::new(mean, sd)` is `(location, scale)` — verified
  against statrs 0.18.0 `log_normal.rs:71`. Impl maps correctly.
- `Poisson::new(0.0)` is rejected by statrs (`poisson.rs:63-69`);
  the inline `lambda == 0.0` special-case handles all 3 sub-cases
  correctly (PMF at 0 = 1, PMF at k>0 = 0, CDF for any k ≥ 0 = 1)
  and matches IronCalc `poisson.rs:55-69` exactly. Clippy
  simplification to `if cumulative || k == 0 { 1.0 } else { 0.0 }`
  yields the same truth table as the explicit
  if/else-if/else form.
- `BINOM.DIST.RANGE` arity range is `(3..=4).contains(&args.len())`
  (inclusive both ends); 3-arg form defaults `number_s2 = number_s`.
  Verified.
- `BINOM.DIST.RANGE` `lower == 0` branch returns `dist.cdf(upper)` —
  correct because `cdf(upper) - 0 = cdf(upper)` when interpreted as
  `P(0 <= X <= upper)`.
- `BINOM.INV` pre-check `0.0..1.0` is half-open (lower-inclusive,
  upper-strict) matching Microsoft canon. `alpha` pre-check
  `alpha <= 0.0 || alpha >= 1.0` is strict both ends, matching
  Microsoft. Inverse-CDF call site is correctly downstream of the
  `p == 0.0` short-circuit (when n=0 issue is fixed per HIGH-O-1,
  same will apply there).
- `EXPON.DIST` is closed-form (no statrs Continuous kernel); domain
  checks (`x >= 0`, `lambda > 0` strict) match IronCalc
  `exponential.rs:28`. PDF / CDF formulas match exactly.
- `LOGNORM.DIST` pre-check `x <= 0.0 || sd <= 0.0` is strict on x
  (log-normal undefined at 0) and matches IronCalc
  `log_normal.rs:36`. Mean can be negative — pinned by
  `lognorm_dist_negative_mean_accepted`.
- `LOGNORM.INV` pre-check `p <= 0.0 || p >= 1.0 || sd <= 0.0` is
  strict both ends; matches IronCalc `log_normal.rs:93` exactly.
- 24 e2e dispatcher tests cover all 8 new fns. The arity-mismatch
  test (`w5_d_4_arity_mismatch_through_dispatcher_returns_value`)
  covers all 8 names. The `binom_poisson_case_insensitive_lookup_works`
  test covers case-insensitivity. The
  `lognorm_inv_dist_round_trip_through_dispatcher` test covers the
  continuous round-trip end-to-end.
- Lexer untouched — all W5-D-4 names use letter-only segments
  separated by `.` (BINOM.DIST.RANGE has three segments, all
  valid).
- Registry test count bump 217 → 225 is consistent with 8 new
  registrations.
- `EXPLICITLY_DEFERRED` has entries for all 8 new fns
  (verified). The 8-fn matrix replacement in
  `docs/compat/excel-matrix.md` correctly drops the prior 4-fn
  grouped placeholder.
- The W5-D-4 module-docstring extension (l. 110-141 and l. 182-193)
  correctly enumerates the 8 new fns' Excel canon and notes the
  u64 conversion + λ=0 special case for POISSON.
- All anchor values claimed in tests are closed-form verifiable:
  pmf via binomial coefficients C(10,k) for k in {0..10};
  cdf via the same sums; NegBinom anchors via
  `C(k+r-1, k)·p^r·(1-p)^k`; Poisson via `e^{-λ}·λ^k/k!`;
  exponential via `1 - e^{-λx}` / `λ·e^{-λx}`; log-normal via
  `Φ((ln(x)-μ)/σ)` and `Φ⁻¹(p) ↦ exp(μ + σ·Φ⁻¹(p))`.
- No code outside the 5 scope files is touched in the W5-D-4 diff
  (verified via `git diff --stat`).

# W5-D-3 Opus Audit: CHISQ.* + F.* (chi-squared + Fisher-Snedecor F)

Date: 2026-05-17
Scope: uncommitted W5-D-3 distribution-function batch on `feat/quantbook-engine`
Auditor: separate-Opus instance (independent of implementer)

## Summary

Solid implementation. The 8 functions are line-by-line ports of IronCalc's
`chisq.rs` and `fisher.rs` reference sources, including the deliberate
asymmetries (CHISQ.DIST.RT uses `dist.sf(x)`; F.DIST.RT uses
`1.0 - dist.cdf(x)`; F.INV.RT alone has lower-strict `0 < p ≤ 1` domain
while CHISQ.INV / CHISQ.INV.RT / F.INV are inclusive `[0, 1]`). All `.expect()`
chains hold under inspection of statrs 0.18.0 source — `ChiSquared::new`
delegates to `Gamma::new(df/2, 0.5)` which only rejects NaN / `≤ 0` /
both-infinite-shape-and-rate (latter impossible since rate is the literal `0.5`),
and `FisherSnedecor::new` rejects only non-finite or `≤ 0` per-arg (both
ruled out by `sanitize_f64` + the `df ≥ 1` pre-check). The four right-tail /
inverse fns each carry the explicit `!result.is_finite() || result < 0.0`
guard, while the two PDF/CDF fns route through `finite_or_num` (correct
helper-vs-inline split — chi-squared / F cannot produce negative cdf/pdf,
only fp `+Inf`).

Gates verified by audit re-run: 158 unit tests pass; 58 e2e dispatcher
tests pass; `cargo clippy -p ql-functions -p ql-exec --all-targets -- -D warnings`
clean.

No HIGH findings. Three MEDIUM (two doc drift, one weak replacement test).
Six LOW (mostly docstring imprecision and test-coverage gaps for boundary
behaviors that are observably `#NUM!` despite "inclusive" domain claims).

## MEDIUM

### MEDIUM-O-1

Subject: `docs/compat/excel-matrix.md` F.DIST row drifted from reality
Where: `quantbook-engine/docs/compat/excel-matrix.md:110`
Detail: The matrix row claims `| F.DIST | ✅ | 11 |` but
`distribution_fns.rs` has only 9 unit tests in the `// ===== F.DIST =====`
section (counted by grep of `^    #\[test\]` between the section header
and the next `// ===== F.DIST.RT =====` boundary — confirmed independently
by reading the file). Additionally, the description text on the same row
references `df1=2 closed-form pdf(0)=1`, but that test was deliberately
**removed** during W5-D-3 (per the implementing-Opus spec note: statrs
returns 0.0 not 1.0 at this corner case due to its 0/0 limit handling).
The replacement test is `f_dist_pdf_at_one_equal_dfs_returns_positive`
which pins a different anchor (positive-finite at x=1 for F(10,10)).
Recommendation:
1. Change the count from `11` to `9`.
2. Replace the docstring fragment `df1=2 closed-form pdf(0)=1` with
   something accurate, e.g. `F(10,10) PDF at x=1 positive-finite regression
   pin` or — better, see MEDIUM-O-3 — pin the true closed-form value
   `630/1024 ≈ 0.6152` and reference that.
Severity rationale: MEDIUM rather than LOW because the matrix is the
authoritative compat-coverage document that downstream tooling and audit
trail rely on. False count + reference to a non-existent test undermines
the matrix's trust value. Same drift type was flagged MEDIUM in W5-D-2.

### MEDIUM-O-2

Subject: `coverage.rs` mirror of the same drift, plus a misleading
"p=0 ACCEPTED" claim for CHISQ.INV.RT
Where: `crates/ql-functions/tests/coverage.rs:780`, `:771-773`
Detail: Two separate drift items in `EXPLICITLY_DEFERRED`:
1. Line 780 (`F.DIST` coverage entry) repeats the matrix's stale claim:
   `df1=2 closed-form pdf(0)=1` — same problem as MEDIUM-O-1.
2. Lines 771-773 (`CHISQ.INV.RT` coverage entry) say
   `p=0 ACCEPTED (inclusive domain)`. The domain check
   `!(0.0..=1.0).contains(&p)` at distribution_fns.rs:628 does include
   p=0, **but** the observable behavior is `#NUM!`:
   `inverse_cdf(1.0 - 0.0) = inverse_cdf(1.0) = +Inf` → caught by the
   `!x.is_finite()` guard on line 633 → returns `Value::Error(ErrorValue::Num)`.
   A reader of the coverage description would reasonably believe
   `CHISQ.INV.RT(0, df)` produces a valid number; it does not. The
   CHISQ.INV coverage entry (lines 761-766) has the same word "p=0 ACCEPTED"
   but is more accurate (CHISQ.INV(0, df) really does return 0). The
   asymmetry between CHISQ.INV's truly-accepted lower bound and
   CHISQ.INV.RT's domain-accepted-but-observably-#NUM! lower bound is
   undocumented.
Recommendation:
1. Fix line 780's `pdf(0)=1` reference (same as MEDIUM-O-1).
2. Reword line 772-773 to e.g. `p=0 domain-accepted but produces #NUM!
   (inverse_cdf(1.0) overflows; observable behavior diverges from
   CHISQ.INV(0,df)=0)`, OR add an explicit test
   `chisq_inv_rt_at_zero_returns_num_error` pinning the actual behavior
   so future readers can grep for the boundary.
Severity rationale: MEDIUM because the misleading wording could
camouflage a future regression — if statrs's `inverse_cdf` semantics
change (e.g., starting to return MAX_VALUE instead of +Inf), the
observable behavior at p=0 would change silently. A pinned test or
accurate docstring would surface that.

### MEDIUM-O-3

Subject: `f_dist_pdf_at_one_equal_dfs_returns_positive` is a weak
regression pin; closed-form value is available
Where: `crates/ql-functions/src/distribution_fns.rs:2139-2158`
Detail: The replacement test pins only `n > 0.0 && n.is_finite()` —
genuinely true for any sensible F-pdf at the peak. The closed-form
F-distribution pdf at x=1 for F(10, 10) is:

`f(1; 10, 10) = 1/B(5,5) · (10/10)^5 · 1^4 · (1 + 10·1/10)^(-10) = 630/1024 ≈ 0.615234375`

(derivation: `B(5,5) = Γ(5)·Γ(5)/Γ(10) = 24·24/362880 = 1/630`, so
`1/B = 630`; the rest is `1 · 1 · 2^-10 = 1/1024`). statrs returns
this value to ≥10 sig figs. The current test would pass even if statrs's
F-pdf returned `1e-300` or `1e+300` — both are positive and finite.
A regression silently downgrading numerical accuracy would not be caught.
Recommendation: Replace with `assert_close(result, 630.0 / 1024.0)` —
this is a true closed-form anchor in the same family as the
`chisq_dist_pdf_at_zero_df_two_libreoffice_anchor` test that pins the
exact value `0.5` (= exponential(1/2) pdf at 0). The implementer's
docstring (line 2143) notes "Pins regression rather than a specific
canonical value" — but a canonical value exists for this exact case.
Severity rationale: MEDIUM because this test was created to *replace*
a test that pinned a wrong claim — leaving in a weaker replacement
misses the opportunity to actually verify F-pdf math. The W5-D-1/W5-D-2
batches all included closed-form anchors per fn (NORM.DIST(0,0,1,FALSE)
= 1/√(2π), T.DIST(0,1,TRUE) = 0.5 etc.); F.DIST is the only fn without
one and could easily have one.

## LOW

### LOW-O-1

Subject: distribution_fns.rs CHISQ.INV docstring references `finite_or_num`
but impl uses inline check
Where: `crates/ql-functions/src/distribution_fns.rs:582-585` (CHISQ.INV
doc-comment) and `:602-606` (impl)
Detail: The doc-comment says:
> `CHISQ.INV(1, df)` would be infinity and is rejected via `finite_or_num`.

But the implementation at lines 602-605 uses an inline check:
```rust
let x = dist.inverse_cdf(p);
if !x.is_finite() || x < 0.0 {
    return Value::Error(ErrorValue::Num);
}
Value::number(x)
```
not the `finite_or_num` helper (which doesn't have the `< 0.0` guard,
hence the inline pattern — same as W5-D-2.1 LOW-O-2 closure for T.DIST.RT).
The behavior is correct; the docstring just names the wrong helper.
Recommendation: Replace `via `finite_or_num`` with `via the inline finite-
and-non-negative check (which adds the `< 0.0` guard the shared
`finite_or_num` helper doesn't have, per the W5-D-2.1 LOW-O-2 closure
pattern)`.
Severity rationale: LOW — readers tracing through the helper-vs-inline
split via docstring grep would land in the wrong place. No behavioral
impact.

### LOW-O-2

Subject: F.INV docstring omits that p=1 produces #NUM! despite "INCLUSIVE"
domain claim
Where: `crates/ql-functions/src/distribution_fns.rs:723-728` (F.INV
doc-comment)
Detail: The F.INV doc says:
> `0 <= probability <= 1` INCLUSIVE (like CHISQ.INV; differs from T.INV's
strict). `df1 >= 1`, `df2 >= 1`. Else `#NUM!`.

The CHISQ.INV doc (lines 582-585) at least notes the p=1 edge:
> `CHISQ.INV(1, df)` would be infinity and is rejected via `finite_or_num`.

But F.INV has the analogous behavior (`inverse_cdf(1.0)` = +Inf for any
df1, df2 → caught by the inline finite check → returns #NUM!) and the
docstring is silent on it. Same observation applies to CHISQ.INV.RT
(p=0 boundary → see MEDIUM-O-2), and to F.INV.RT (which lower-strict-rejects
p=0 in domain).
Recommendation: Append to F.INV docstring: `F.INV(1, df1, df2) would be
+Inf and is rejected via the inline finite check (matches CHISQ.INV(1,
df) behavior).`
Severity rationale: LOW — same documentation-vs-observable-behavior gap
as LOW-O-1 / MEDIUM-O-2 but in a different fn's doc-comment. No code
impact.

### LOW-O-3

Subject: No tests for CHISQ.INV(1, df), CHISQ.INV.RT(0, df), F.INV(1,
df1, df2) — domain-accepted "inclusive" boundaries that observably
produce #NUM!
Where: `crates/ql-functions/src/distribution_fns.rs` (test mod, lines
1912-2105 for CHISQ.INV.*; 2375-2491 for F.INV)
Detail: Three boundary-behavior tests missing:
- `chisq_inv_at_one_returns_num_error` — pins CHISQ.INV(1.0, df) = #NUM!
  (because `inverse_cdf(1.0)` for ChiSquared → +Inf → finite check fails).
- `chisq_inv_rt_at_zero_returns_num_error` — pins CHISQ.INV.RT(0.0, df)
  = #NUM! (because `inverse_cdf(1.0 - 0.0)` = +Inf).
- `f_inv_at_one_returns_num_error` — pins F.INV(1.0, df1, df2) = #NUM!.

The "inclusive domain" advertised in the matrix + module docstring is
incompletely tested — only the lower endpoint (where inverse_cdf returns
a finite value) is verified. A statrs regression that started returning
`f64::MAX` instead of +Inf for `inverse_cdf(1.0)` would change the
observable behavior at these boundaries without triggering any test.
Recommendation: Add the three tests. Pattern from existing
`chisq_inv_at_zero_returns_zero` (line 1914-1919) — same structure but
asserting `#NUM!`.
Severity rationale: LOW because (a) the cdf-round-trip tests indirectly
exercise interior p-values, (b) statrs's `inverse_cdf` is well-tested
upstream, but (c) without explicit pins, the "inclusive domain" claim
is unverifiable from the test suite alone.

### LOW-O-4

Subject: Error propagation tests cover arg 0 only; args 1-3 paths
untested for all 8 fns
Where: `crates/ql-functions/src/distribution_fns.rs` test mod
(`*_error_arg_propagates` tests across all 8 fns; lines 1791-1801,
1891-1897, 1989-1995, 2086-2092, 2232-2243, 2345-2355, 2463-2473,
2575-2585)
Detail: Every `error_arg_propagates` test passes a `Value::Error(...)`
in **argument position 0** only. The impls coerce args via a uniform
`match coercion::to_number_strict(&args[i]) { Err(e) => return ... }`
pattern, so a regression that broke propagation on arg[1] or arg[2]
or (for F.DIST/CHISQ.DIST) the `cumulative` arg at the last position
would not be caught. Distinguishable errors (`#REF!` / `#DIV/0!`) are
used to verify the original error class survives — good — but only on
arg 0.

This is a **consistent gap from W5-D-1 / W5-D-2** (same pattern there).
Not introduced in W5-D-3; not unique to W5-D-3 either. Flagging here for
visibility on the cumulative coverage debt across the Wave 3 batches.
Recommendation: Either accept the gap (uniform coercion pattern makes
arg-0 a reasonable proxy) and add a single cross-cutting test in the
e2e file that passes `#REF!` in a non-zero position for one fn per
arity-class (e.g., NORM.DIST(0, #REF!, 1, TRUE) for 4-arg, T.INV(0.5,
#REF!) for 2-arg, F.DIST(0, 5, #REF!, TRUE) for 4-arg with the error
deepest); OR backfill per-fn tests covering each arg position.
Severity rationale: LOW because (a) the coercion impl is uniform and
trivially correct on inspection, (b) the gap is consistent with the
prior W5-D-1/W5-D-2 batches' choices. Listing for trend visibility,
not as a per-batch regression.

### LOW-O-5

Subject: F.DIST + F.DIST.RT "LibreOffice anchor" tests pin statrs's own
F.INV(0.95, 5, 10) output as input — circular self-pin, not an external
cross-check
Where: `crates/ql-functions/src/distribution_fns.rs:2160-2180`
(`f_dist_libreoffice_anchor_5_10_at_3_3258`) and `:2282-2297`
(`f_dist_rt_libreoffice_anchor_5_10_at_3_3258`)
Detail: Both tests use input `3.325_834_530_413_004_6`, which is
statrs's `FisherSnedecor::new(5, 10).unwrap().inverse_cdf(0.95)`.
By construction, `cdf(inverse_cdf(p)) ≈ p` to ≥12 digits — so the test
asserts statrs's internal self-consistency, not its agreement with
the F-distribution's true math. The true CDF value at the true 95th
percentile (per R / LibreOffice: `3.325835018413022`) is what
"LibreOffice anchor" implies. statrs diverges from true math by ~5e-7
(documented in the test comment and module docstring).

This is principled IronCalc-parity behavior (both projects pin statrs
0.18.0 and will move in lock-step), but the test name "LibreOffice
anchor" misrepresents what is being verified. The `f_inv_libreoffice_
anchor_95_pct_5_10` test (line 2396) has the same issue but is the
*source* of the statrs-divergence note — its naming is less misleading
because F.INV is the path where the divergence manifests.
Recommendation: Either rename to `f_dist_statrs_self_consistency_5_10_
at_95th_percentile` and `f_dist_rt_statrs_self_consistency_...` (truthful
about what is verified), OR add a second test per fn with `tolerance=1e-6`
that pins the *true* F-distribution percentile `3.325835018413022` and
asserts CDF ≈ 0.95 to that looser bound — this catches a coordinated
statrs+IronCalc bug that the self-pin test would miss.
Severity rationale: LOW — naming-precision issue; the test does pin
**something** valuable (statrs's per-version self-consistency). The
coordinated-bug coverage gap is theoretical but not far-fetched (a
statrs major-version bump that breaks both `inverse_cdf` and `cdf` in
matching ways would slip through).

### LOW-O-6

Subject: `chisq_dist_df_above_max_is_num_error` uses literal `1e11`
instead of `MAX_CHISQ_DEGREES_OF_FREEDOM + 1.0`
Where: `crates/ql-functions/src/distribution_fns.rs:1766-1777`
Detail: The test asserts that `df = 1e11` returns `#NUM!`. The ceiling
constant `MAX_CHISQ_DEGREES_OF_FREEDOM = 1e10` is defined on line 164,
publicly visible to the test module (private to the file but in scope).
The test uses a literal `1.0e11` instead of referencing the constant.
If `MAX_CHISQ_DEGREES_OF_FREEDOM` were ever lowered (e.g., to 1e9 to
match a future IronCalc change), the test would still pass at 1e11 —
it would no longer be pinning the **boundary** of the ceiling, just a
value 100× above it.
Recommendation: Use `MAX_CHISQ_DEGREES_OF_FREEDOM + 1.0` (or `MAX_CHISQ_
DEGREES_OF_FREEDOM * 1.0001`) so the test pins the boundary. Optionally
add a sister test asserting that `df = MAX_CHISQ_DEGREES_OF_FREEDOM`
(exactly 1e10) is **accepted** (returns a number, not `#NUM!`) — this
pins the inclusive upper bound from both sides.
Severity rationale: LOW — the brittleness only surfaces if the constant
changes, and the surrounding test framework (`assert_eq!`) would catch
a 10× regression in practice. Nice-to-have hygiene, not load-bearing.

## Confirmed Non-Issues

- **IronCalc parity**: All 8 fns line-by-line match the IronCalc
  references (`.references/ironcalc/base/src/functions/statistical/
  chisq.rs:10-258`, `fisher.rs:69-298`). Arg count, coercion order,
  `.trunc()` placement, domain checks, CDF/PDF/sf/`1-cdf` selection,
  negative-result guards all align. The two deliberate asymmetries
  (CHISQ.DIST.RT uses `sf` for numerical stability; F.DIST.RT uses
  `1 - cdf` per IronCalc choice; F.INV.RT alone is lower-strict) are
  faithfully reproduced. The only divergence is the coercion frontend
  (`to_number_strict` vs `get_number_no_bools`), already documented in
  the module docstring (lines 130-150) per the W5-D-1.1 HIGH-O-2 closure.

- **`MAX_CHISQ_DEGREES_OF_FREEDOM` ceiling**: Applied to all 4 CHISQ.*
  fns via the shared `(1.0..=MAX_CHISQ_DEGREES_OF_FREEDOM).contains(&df)`
  check (lines 539, 566, 598, 628). Constant value `1e10` matches
  IronCalc's `MAX_DEGREES_OF_FREEDOM` in `chisq.rs:8`. F.* fns correctly
  do NOT apply this ceiling (df1/df2 only checked `>= 1.0`), matching
  IronCalc canon — `FisherSnedecor::new` only rejects non-finite / ≤ 0.

- **`.expect()` chains**: I traced through statrs 0.18.0 source
  (`~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/statrs-0.18.0/
  src/distribution/`):
  - `ChiSquared::new(df)` delegates to `Gamma::new(df/2, 0.5)`.
    `Gamma::new` errors only on NaN/non-positive shape, NaN/non-positive
    rate, or both-infinite-shape-rate. Our pre-check (`df in [1, 1e10]`
    + `to_number_strict` rejecting NaN/Inf via `sanitize_f64`) excludes
    NaN, non-positive, and infinite df. Rate is the literal `0.5` so
    the both-infinite case is impossible. `.expect()` is principled.
  - `FisherSnedecor::new(df1, df2)` errors on `!freedom.is_finite() ||
    freedom <= 0.0` per arg. Our pre-check (`df1 >= 1.0 && df2 >= 1.0`)
    combined with `sanitize_f64` (rejects NaN AND infinity numerically)
    ensures both args are finite and ≥ 1. `.expect()` is principled.

- **Negative-result guards on all right-tail / inverse fns**: Verified
  6 fns have the `!result.is_finite() || result < 0.0` inline guard:
  `chisq_dist_rt` (line 571), `chisq_inv` (603), `chisq_inv_rt` (633),
  `f_dist_rt` (717), `f_inv` (750), `f_inv_rt` (784). CHISQ.DIST and
  F.DIST correctly route through `finite_or_num` (line 543, 687) since
  the cdf/pdf cannot be negative — only infinite or NaN. The helper-

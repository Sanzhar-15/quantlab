Analytical stress result: a 10k single-op undo/redo cycle should not deadlock based on the lock graph above. I did not run a 10k stress after finding the deterministic grouped-undo correctness failure below; the risk is correctness under metadata merge, not a race/deadlock in the simple cycle.

## Operation Classifier

`affected_cells_for_partial_invalidate()` returns cells for:

- `PutValue`
- `PutFormula`
- `ClearFormula`
- `SetCellFormat`
- all-cell-keyed `BatchCommit`, with sorted/deduped cells

It returns `None` for all other variants through the wildcard at `crates/ql-collab/src/session.rs:1475`.

Current non-cell-keyed variants in `crates/ql-oplog/src/op.rs` include `SetName`, `AddSheet`, `RenameSheet`, `RemoveSheet`, `MoveSheet`, `RegisterFormat`, table ops, `SetReferenceMode`, and `SetLocale`. Falling back to full rebuild for these is correct. If a future variant emits cell-keyed effects and is not added to the classifier, it will silently fall back to full rebuild if it is a top-level op, but a mixed `BatchCommit` will also fall back to full rebuild. That is inefficient but correct.

## Codec

`encode_cells_to_loro_value()` and `decode_cells_from_loro_value()` are structurally sound:

- Empty cells encode as `LoroValue::List(empty)` and decode as `Some(Vec::new())`.
- `u16`/`u32` to `i64` casts are lossless.
- Decode requires an outer list and inner 3-element lists of I64, rejecting malformed shapes and out-of-range/negative values.
- LoroValue list storage is `LoroListValue(Arc<Vec<LoroValue>>)` and `LoroValue` is documented as cheap to clone at `loro-common-1.12.0/src/value.rs:10`.

The decoder intentionally does not accept maps or future tagged shapes. That is conservative and safe because callers fall back to full rebuild on `None`.

## Critical Finding

### Grouped undo and merge-interval undo lose metadata

Loro discards new metadata when it merges a pushed item into an existing undo stack item:

```rust
if can_merge {
    if let Some(last_span) = last.0.back_mut() {
        if last_span.span.end == span.start {
            last_span.span.end = span.end;
            return;
        }
    }
}
```

Source: `loro-internal-1.12.0/src/undo.rs:389`.

`record_checkpoint()` enables this path for explicit undo groups and merge-interval auto grouping at `loro-internal-1.12.0/src/undo.rs:549`.

D1 stages per-append cells in `append_op()`. During a grouped push, the first append's meta survives, but the second and later append metas are dropped when Loro extends the first span. Then `undo()` reads `top_undo_meta()` and invalidates only the first append's cells even though Loro retracts the whole merged span.

I verified this with a temporary probe added and then removed from `session.rs`:

```rust
#[test]
fn codex_tmp_grouped_undo_cache_probe() {
    let mut s = CollabSession::new(PeerId::new(1)).unwrap();
    s.start_undo_group().unwrap();
    for col in 0..5 {
        s.append_op(put_value(0, 0, col, col as f64)).unwrap();
    }
    s.end_undo_group();

    assert_eq!(s.snapshot_cells(0).len(), 5);
    assert!(s.undo().unwrap());
    assert_eq!(s.op_log().iter().count(), 0);
    assert_eq!(s.snapshot_cells(0).len(), 0);
}
```

Failure:

```text
assertion `left == right` failed
left: 4
right: 0
```

So the visible Loro log retracted all 5 grouped ops, but the cache retained 4 stale cells.

This also applies to `set_undo_merge_interval(...)` when consecutive appends merge by interval, because the same Loro `push_with_merge(..., can_merge: true, ...)` path is used.

Recommended fix: before V3.6.0.2 ships, make merged undo items force full rebuild or carry union metadata. Conservative in-cycle fix:

- Track explicit group state in `CollabSession`.
- Track whether merge interval is enabled.
- In `append_op()`, stage `Vec::new()` whenever an append can merge into an existing undo item. That makes the surviving meta empty and causes `undo()` / `redo()` to use full rebuild.
- Add regressions asserting grouped undo and merge-interval undo cache equals forced full rebuild.

Optimized future fix: expose Loro's internal `set_top_undo_meta()` / `set_top_redo_meta()` through the public `loro::UndoManager` and union cell lists when spans merge.

## .qbook Persistence

UndoManager stack metadata does not persist through `.qbook` save/load:

- Save uses `OpLog::export_bytes()` which is `LoroDoc::export(ExportMode::Snapshot)` at `crates/ql-oplog/src/log.rs:322`.
- Load reconstructs an `OpLog` via `LoroDoc::import(bytes)` at `crates/ql-oplog/src/log.rs:414`.
- `CollabSession::from_snapshot()` then constructs a fresh UndoManager at `crates/ql-collab/src/session.rs:782`.
- The existing `reborn_session_has_empty_undo_stack` test confirms imported ops are not undoable by the reborn peer at `crates/ql-collab/src/session.rs:4891`.

This is correct: UndoManager state is in-memory and local-only. An imported session has an empty undo stack, so `undo()` is a no-op unless the new session appends local ops after load.

## Rule 4 Walk

The new field's documented Send + Sync walk is correct:

- `Arc<T>` is Send + Sync when `T: Send + Sync`.
- `Mutex<T>` is Send + Sync when `T: Send`.
- `Option<T>` and `Vec<T>` compose Send + Sync over their inner type.
- `(u16, u32, u32)` is Copy + Send + Sync.

No new negative-trait trigger is introduced by the D1 field.

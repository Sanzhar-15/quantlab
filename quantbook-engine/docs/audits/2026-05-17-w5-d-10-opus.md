W5-D-10 is **clean and ready to commit**. All 4 functions are mathematically correct, match IronCalc semantics exactly (`erf(y) - erf(x)` for the 2-arg form, strict 1-arg for the three other shapes), use the appropriate statrs API (separate `erf` / `erfc` — not naive `1 - erf(x)`), route through `finite_or_num` defense-in-depth, and propagate errors per the engine's documented coercion divergence (`to_number_strict` accepts Booleans, IronCalc rejects them — same as every other Wave 3 distribution).

The single fact worth flagging is **not** a bug: statrs erf accuracy is ~10-11 significant figures, not the ~13 implied by the module docstring. The literal anchors pinned in the tests are correct Abramowitz-Stegun values (e.g. `0.842_700_792_949_714_9` for ERF(1)), but statrs actually returns `0.8427007929427149` — diverging in the **11th digit**. Both numbers agree to within the `1e-9` tolerance `assert_close` uses, so the tests pass; the test pins are aspirational A&S values and accidentally over-claim statrs precision. Acceptable, but worth noting.

### LOW-2 — 2-arg ERF: no test pins error-propagation from args[1]

`erf_error_arg_propagates` only covers error in `args[0]` (1-arg path). The 2-arg branch reads `args[1]` only after coercing `args[0]`, but if `args[0]` is fine and `args[1]` is an error (`#REF!`, `#DIV/0!`, …), the impl correctly propagates — but no test pins this. With Excel's first-error-wins semantics, the more interesting pin is `ERF(#DIV/0!, #REF!)` returning `#DIV/0!` (args[0] wins). Neither shape is currently pinned.

Mitigation: the 1-arg path is covered, and the 2-arg coercion uses the identical `to_number_strict` helper, so the underlying behavior is exercised. But adding one targeted test would close the gap explicitly.

File: `crates/ql-functions/src/distribution_fns.rs`, ERF tests block.

All four anchor / identity / limit pins are correct:

- `ERF(0) = 0`: identity ✓
- `ERF(1) ≈ 0.842700792949714869...` (A&S table): pinned via 16-digit literal; statrs gives `0.8427007929427149`, diff ~7e-12, within `1e-9` ✓
- `ERF(2) ≈ 0.995322265018952735...` (A&S): pinned via 16-digit literal; statrs gives `0.9953222650191473`, diff ~2e-11, within `1e-9` ✓
- `ERFC(0) = 1`: identity ✓
- `ERF(-x) = -ERF(x)` (odd): pinned at x=1.5 ✓
- `ERF(x) + ERFC(x) = 1` (complement): pinned at 7 x-values ∈ [-2, 3] ✓
- `ERF(5) → 1`: statrs returns `0.9999999999984625`, diff `1.537e-12`, well within `1e-10` test bound ✓
- `ERFC(-5) → 2`: statrs returns `1.9999999999984625`, same diff, within `1e-10` ✓
- `ERFC(5) → 0`: statrs returns `1.537e-12`, within `1e-10` ✓
- 2-arg `ERF(0, 1) = ERF(1)` reduction: pinned via the literal-anchor identity ✓
- 2-arg anti-symmetry `ERF(0, 1.5) = -ERF(1.5, 0)`: pinned ✓

I independently verified all numerical statrs outputs by compiling a separate scratch crate against `statrs = "0.18"` (see auditor run log above the file). Values match to all digits printed; no rounding surprises.

### CNI-2 — IronCalc parity

Line-by-line comparison with `.references/ironcalc/base/src/functions/engineering/bessel.rs:127-177`:

- `fn_erf`: 1-2 args check, get_number_no_bools(args[0]) → x, if 2 args get_number_no_bools(args[1]) → y, return `erf(y) - erf(x)` else `erf(x)`. **Our impl matches: `args[0]` is "lower", `args[1]` is "upper", return `erf(upper) - erf(lower)` = `erf(y) - erf(x)`.** Argument-order semantics verified.
- `fn_erfprecise`: 1 arg strict, `erf(x)`. **Match.**
- `fn_erfc`: 1 arg strict, `erfc(x)`. **Match.**
- `fn_erfcprecise`: 1 arg strict, `erfc(x)`. **Match.**

Coercion divergence is the engine-wide one (`to_number_strict` accepts Boolean as 0/1; IronCalc's `get_number_no_bools` rejects). Already documented for every prior distribution function. Not new for W5-D-10.

### CNI-3 — `.PRECISE` strictness

`ERF.PRECISE` strictly 1-arg: pinned by `erf_precise_rejects_2_args` (returns `#VALUE!` for `ERF.PRECISE(0, 1)`). Microsoft canon confirmed via support.microsoft.com (ERF.PRECISE takes only `x`; for both-limit form use ERF).

`ERFC.PRECISE` strictly 1-arg by construction (delegates to `erfc_excel` which already enforces 1-arg). Pinned indirectly via `erfc_precise_arity_mismatch_returns_value` (0-arg case) + `erfc_arity_mismatch_returns_value` (2-arg returns `#VALUE!`).

### CNI-4 — statrs API: separate `erfc`, not `1 - erf`

`statrs-0.18.0/src/function/erf.rs:40-50`: `erfc(x)` calls `erf_impl(x, true)` — the boolean second parameter switches to a separate rational approximation tailored for the tail (no naive subtraction). The module docstring's "no naive `1 - erf(x)` cancellation at large positive x" claim is accurate. Test `erfc_large_positive_approaches_zero` (x=5) confirms `ERFC(5) ≈ 1.54e-12`, which would have catastrophic cancellation under `1.0 - erf(5)` since `erf(5)` round-trip-loses ~16 digits of mantissa near 1.0.

### CNI-5 — `finite_or_num` routing

All four functions route through `finite_or_num`. erf range is `[-1, 1]` and erfc range is `[0, 2]` over the full f64 input domain (statrs handles ±∞ and NaN explicitly per `erf.rs:9-20` and `40-50`), so the guard is genuinely defense-in-depth — it would only trigger if statrs ever returned NaN (e.g. NaN input → NaN output, which `finite_or_num` correctly converts to `#NUM!`). Consistent with the rest of `distribution_fns.rs`.

### CNI-6 — No domain pre-check needed

erf and erfc are defined on all of ℝ; no `x ≤ 0` or similar pre-checks needed. The impls correctly omit pre-checks (vs. GAMMALN which needs `x > 0`, or BETA which needs bounds-checking). Clean.

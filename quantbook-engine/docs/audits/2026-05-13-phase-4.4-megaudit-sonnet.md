**Auditor:** Claude (Sonnet/Opus 4.7, 1M context)

## One-paragraph verdict

The W5-64 helper migration is **largely sound** at the code level — the four
promoted helpers (`to_text_for_arg`, `to_int_arg`, `to_number_strict_skip_blank`,
`format_number_for_arg`) have correct bodies, the cross-module `coerce_numeric`
shim is total, all call sites compile and pass, and the NaN/Inf policy is
implemented uniformly (`coercion.rs:80`, `:96`, `:123`). The W5-65 matrix tests
genuinely pin the 9×5 type-pair grid and most of the §3.3 precedence rules at
the E2E layer. **However**, the arc oversells its own coverage in two ways
that an unwary maintainer could miss: (1) the W5-66 compat doc lists rows for
HLOOKUP, INDEX, CHOOSE, AND/OR/NOT, AVERAGEIF, MIN/MAX, and ROUNDUP/ROUNDDOWN
with **no enforcing test**, despite cite-test-by-name being the doc's structural
promise; (2) the W5-65 commit message claim that "matrix tests are themselves
the audit substrate now — any real divergence shows up as a test failure" is
**overstated** because the EXPLICITLY_DEFERRED list in `coverage.rs` is broad
enough (89 of 108 functions) to drain that test's intent. The W5-64 commit also
describes its `to_text_for_arg` body as "byte-for-byte identical" to the deleted
helpers — actually it's a deliberate forward-compatible behavior change for
raw `Value::Number(NaN/±Inf)` inputs (per Codex MEDIUM 1). The arc itself is
solid (no correctness bugs found); the issues are accuracy of the surrounding
claims and one genuine coverage gap on HLOOKUP.

## NEW MEDIUM (overstatement, scope gap, missing test)

### MEDIUM-S1: HLOOKUP has **zero** test coverage and the doc lies about it

- `crates/ql-functions/tests/per_function_overrides.rs:279` is a section
  header "VLOOKUP / HLOOKUP — distinct error returns per failure mode", but
  every test below it calls VLOOKUP. No `hlookup` test exists anywhere in the
  workspace.
- `crates/ql-functions/tests/coverage.rs:194-197` deferral reason for HLOOKUP
  reads `"mirrors VLOOKUP; covered by per_function_overrides"`. That's false:
  no test in `per_function_overrides.rs` calls HLOOKUP. The two functions are
  separate function bodies (`range_fns.rs:600` vs `:656`); a regression in
  HLOOKUP's col_index-bounds or not-found path would NOT be caught by VLOOKUP
  tests.
- `docs/compat/error-matrix.md:121` row for HLOOKUP says "(via VLOOKUP
  coverage; tests transitively)". This is the same lie surfaced for the user.

This is a real coverage gap surfaced as a doc/coverage-list claim of
coverage. **Fix:** add at least three `hlookup_*` tests mirroring the VLOOKUP
ones, OR change the deferral reason to be honest ("deferred — mirrors VLOOKUP
in implementation, not tested in V1") and update the doc accordingly.

### MEDIUM-S2: "byte-for-byte identical" claim in `to_text_for_arg` docstring is misleading

- `crates/ql-types/src/coercion.rs:109` docstring on `to_text_for_arg`:
  `"Replaces the private 'coerce_text' helper that lived in
  'ql-functions::scalar_fns' and 'value_to_concat_text' in 'range_fns'.
  Behavior is byte-for-byte identical to those two paths."`
- This is **wrong** for the NaN/Inf input case. The OLD `coerce_text`
  (verified at `git show 756875ad08e^:crates/ql-functions/src/scalar_fns.rs:1349`)
  unconditionally ran `format_number_for_text` on the f64 — for `Number(NaN)`
  that produced `"NaN"`. The NEW `to_text_for_arg` returns `Err(#NUM!)` for
  the same input. Same divergence for `Inf`. This is the intended W5-64
  Codex-MEDIUM-1 policy change.
- The commit body acknowledges the change ("NaN/Inf POLICY (Codex MEDIUM 1)").
  The in-line comment at `crates/ql-functions/src/scalar_fns.rs:1337-1341`
  also acknowledges it as a behavior change ("gets the new NaN/Inf policy
  'for free'"). But the public-API docstring users will read says "byte-for-
  byte identical." Two contradictory framings.
- **Fix:** rewrite the docstring on `to_text_for_arg` to say "byte-for-byte
  identical to the deleted helpers for the four finite-input variants;
  Number(NaN/±Inf) is the deliberate forward-compatible change per W5-64
  Codex MEDIUM 1 NaN/Inf policy." Same fix for the analogous comment in
  the W5-64 commit message line "byte-for-byte duplicates" (which is true
  of the OLD vs OLD comparison but misleading next to the new behavior).

### MEDIUM-S3: W5-65 commit overclaims the matrix-as-substrate guarantee

- The W5-65 commit body says: *"matrix tests are themselves the audit
  substrate now — any real divergence shows up as a test failure, not a
  doc-drift audit finding"*.
- That's overstated. Counter-example list:
  - `docs/compat/error-matrix.md:113` AND/OR/NOT row — Tag `🟢 (assumed)`,
    Test column empty. No test pins the claim. The literal hedge "(assumed)"
    confesses to the audit substrate gap.
  - `:122` INDEX row — Test column `—`. No test pins the override.
  - `:123` CHOOSE row — Test column `—`. No test pins "out-of-bounds → #VALUE!"
    or "Range arg → #VALUE!" (both real overrides in `range_fns.rs:735-748`).
  - `:142` AVERAGEIF row — Test column `—`.
  - `:86` MIN/MAX row — Test column `—ish` ("deferred to 4.4.C completion").
  - `:162` ROUNDUP/ROUNDDOWN row claims binary-float divergence
    (`ROUNDUP(0.1+0.2,1) = 0.4 not 0.3`); no test pins this; could regress
    silently to a 15-digit-display rounding implementation without anyone
    noticing.
- The matrix IS a substantial advance over no-matrix. But "any real
  divergence shows up as a test failure" is false today; the matrix needs
  doc-coverage automation or a tighter EXPLICITLY_DEFERRED list to make
  the claim true.
- **Fix:** rephrase the audit-substrate claim; add a test that walks
  `docs/compat/error-matrix.md` and asserts every Test-column citation
  resolves to a real test name in the W5-65 files (catches the HLOOKUP
  "transitively" lie); OR shrink EXPLICITLY_DEFERRED to mean what it says.

### MEDIUM-S4: EXPLICITLY_DEFERRED is a dumping ground that drains coverage.rs's intent

- `crates/ql-functions/tests/coverage.rs:56-211` has 89 EXPLICITLY_DEFERRED
  entries vs 19 EXPECTED_COVERED. That's 82% of registered functions marked
  "no matrix coverage required."
- Many deferral reasons are vague placeholders: `"default; deferred"` (8
  occurrences for ABS, ROUND, INT, TRUNC, SIGN, ODD, EVEN, etc.) — i.e., "I
  haven't gotten to it" rebranded as "no matrix coverage required."
- The test `every_registered_function_has_a_coverage_decision` PASSES today
  because EXPLICITLY_DEFERRED is permissive enough to absorb every name. It
  doesn't enforce a coverage threshold. The original Codex MEDIUM 4 intent
  was "new fns can't slip in without coverage"; landing a new fn with
  `("NEW_FN", "deferred")` will still pass.
- **Fix:** either (a) tighten the EXPLICITLY_DEFERRED reasons to require a
  named phase/gap reference (`"deferred → Phase 4.4.D"` not `"default;
  deferred"`), or (b) add a second guardrail that asserts EXPLICITLY_DEFERRED
  stays under a ratio (say 50% of registered) so future drift is visible.

### MEDIUM-S5: ROUNDUP/ROUNDDOWN binary-float divergence is doc-claimed without test

- `docs/compat/error-matrix.md:162` says ROUNDUP/ROUNDDOWN: "Binary-float,
  NOT 15-digit display rounding (`ROUNDUP(0.1+0.2, 1) = 0.4` not `0.3`)" —
  tagged 🟡 V1-divergence.
- No test in the W5-65 files pins this. If someone "fixes" ROUNDUP to use
  display rounding (a reasonable user request), the doc would silently
  become wrong and the matrix-test for ROUNDUP doesn't exist.
- This is the canonical example MEDIUM-S3 / MEDIUM-S4 protect against; called
  out separately because the row is explicitly tagged 🟡 and a V1 divergence
  is the *exact* thing the test-substrate is supposed to lock down.
- **Fix:** add a `roundup_0_1_plus_0_2_binary_float_v1_divergence` test.

### MEDIUM-S6: W5-63 ran no gates ("N/A for doc-only commit") but W5-66 did

- Compare:
  - `git log --format='%B' a2c53a6f0da` → "7 GATES — fmt / clippy / tests
    / build-flags / cargo-lock / multiversion / cargo audit — **N/A** for
    doc-only commit; verified tests pass."
  - `git log --format='%B' 2bba2e8ada9` → "7 GATES — all green: fmt | clippy
    -D warnings | cargo test --workspace (1412 passed, 0 failed) | ... ".
- The §7 acceptance-criteria checklist in the design doc (`2026-05-13-coercion-
  matrix.md:217-224`) says "All 7 gates green at every commit in the phase".
  W5-63 was that doc-only commit; gates were N/A'd, not run. W5-66 was also
  doc-only and ran them. Inconsistent application of the protocol.
- Low harm in practice (a markdown-only commit can't break clippy in
  principle), but the W5-63 commit message did not meet the acceptance
  criterion as the design doc itself wrote it.
- **Fix:** either run gates on every commit (including doc-only) or update
  the acceptance criterion to allow "N/A doc-only" formally.

### MEDIUM-S7: ql-types/lib.rs re-exports omit the four new helpers

- `crates/ql-types/src/lib.rs:21-24` re-exports the original 6 coercion
  helpers (`sanitize_f64`, `to_logical`, `to_number_{strict,lenient}`,
  `to_text_for_{display,formula}`) at the top level.
- The four W5-64 additions (`to_text_for_arg`, `to_int_arg`,
  `to_number_strict_skip_blank`, `format_number_for_arg`) are NOT in the
  re-export list. The module doc-comment at lines 6-7 still says coercion
  has only the original 6. Callers in `ql-functions` use the longer
  `coercion::to_text_for_arg` path. Functional, but inconsistent surface.
- The W5-65 doc `crates/ql-types/tests/coercion_matrix.rs:35-37` also goes
  via the `coercion::` path, so no consumer is forced through the top-level
  re-export. Still, the re-export inconsistency means callers don't have one
  obvious place to learn the coercion vocabulary.
- **Fix:** add the four helpers to the lib.rs `pub use` block and update the
  module doc-comment.

## NEW LOW (doc nits, naming, style)

### LOW-S1: `coerce_text` / `coerce_int_arg` shadow aliases live mid-file

- `crates/ql-functions/src/scalar_fns.rs:1342` `use ql_types::coercion::
  to_text_for_arg as coerce_text;` is on line 1342, **inside** the body of
  the file (between LEN's docstring and `pub fn len`'s body). Similarly
  line 1478 for `to_int_arg as coerce_int_arg`. Readers scanning top-of-file
  imports won't see them; readers grepping for `coerce_text` find the alias
  not the central API. Diff-friendly, but stylistically odd.
- **Fix:** move both `use ... as ...` statements to the top of `scalar_fns.rs`
  with the other imports.

### LOW-S2: Test count of "46" in compat doc vs "89 total" claim is slightly inflated

- `docs/compat/error-matrix.md:12-15` says "Type-pair matrix: 46 tests";
  per-fn overrides: 25 tests; error precedence: 15 tests; coverage: 3 tests.
  Total 89. The W5-65 commit body says "89 new tests across 3 crates". The
  46 includes one cross-cutting test that isn't a matrix cell (`cross_cutting_
  error_short_circuits_in_all_coercion_contexts`), so the strict 9×5=45 cell
  count is the real per-cell figure. Reasonable, but the doc could
  distinguish "matrix cells" (45) from "tests in the matrix file" (46).

### LOW-S3: `EXPLICITLY_DEFERRED` reason claims "in matrix" are ambiguous

- E.g. `crates/ql-functions/tests/coverage.rs:127` MROUND: "W5-60 nonzero-
  multiple-zero fix in matrix". Which matrix? excel-matrix? error-matrix?
  Both? Reader has to grep both files.
- **Fix:** cite the doc by path (`docs/compat/error-matrix.md §3.7`) or by
  test name.

### LOW-S4: `Tag` system collapses two concepts in §3.8

- The error-matrix doc has 🟢 canon / 🟡 divergence / ⚪ deferred. The AI row
  uses 🟡 for "V1 sentinel" — but "not implemented yet" is closer to ⚪. The
  doc's own §3.2 uses ⚪ for TYPE/NA/ERROR.TYPE in this sense. Inconsistent.
- **Fix:** make AI row ⚪ (or define when to use 🟡 vs ⚪ at the top).

### LOW-S5: `count_skips_text_and_blanks_canon` is mis-named

- `crates/ql-functions/tests/per_function_overrides.rs:62-74` tests a case
  with `[Number, Text, Blank, Number, Bool(true)]` and expects 2 (since only
  Number variants count). The name says "text_and_blanks" but the input also
  has a Boolean — and Boolean is also skipped by Quantbook's COUNT.
- This is also a latent Excel divergence: Excel COUNTs a direct-arg Boolean
  as 1 (only range-cell Boolean is skipped). Quantbook skips Boolean
  uniformly. The matrix doc does NOT call out this divergence.
- **Fix:** rename the test, and either pin/document the Boolean divergence
  separately or accept Quantbook's behavior as canon (with rationale).

## Per-concern verdict (A-K)

### A: W5-64 helper migration — silent behavior drift

**Verdict: MEDIUM-S2 finding.** Three of the four helpers are byte-for-byte
identical (`to_int_arg`, `to_number_strict_skip_blank` shim path, the
finite-Number paths of `to_text_for_arg`). The fourth case (NaN/Inf Number in
`to_text_for_arg`) is a deliberate forward-compatible change per Codex
MEDIUM 1; the commit body acknowledges it; the public docstring at
`coercion.rs:109` does NOT. The cross-module `coerce_numeric` shim
(`range_aware_fns.rs:54-60`) is total (3 input variants → 3 output variants);
no behavior introduced beyond the central API; verified by inspection. The
deleted `value_to_concat_text` body (verified at `git show 756875ad08e^:
crates/ql-functions/src/range_fns.rs:1431-1446`) is byte-for-byte the
finite-number path of `to_text_for_arg`. `format_number_for_arg` has no
out-of-module callers yet beyond the test file. **No correctness bug.**

### B: NaN/Inf policy implementation (W5-64)

**Verdict: clean implementation; tests cover the policy.** The check
`n.is_nan() || n.is_infinite()` runs BEFORE the format call in all three
paths: `to_text_for_display` (`coercion.rs:80`), `to_text_for_formula`
(`:96`), `to_text_for_arg` (`:123`). Tests exercising the branch:
`display_text_raw_nan_renders_as_num_sigil` (`:870`), the
`_w5_64_policy_*` set in `coercion_matrix.rs:135-196`. `Value::Number(0.0)`
and `-0.0` are both finite (`is_nan() || is_infinite()` returns false on
0.0); tests `display_text_finite_numbers_unchanged` (`:884`) and
`case_number_finite_display_canon_invariant_rendering` (`:95-99`) pin this.
No false-positive risk.

### C: Matrix-as-tests completeness (W5-65)

**Verdict: matrix cells fully covered; per-fn overrides have real gaps.**

1. The 9×5 type-pair matrix is fully covered: 5 contexts × 9 inputs = 45
   cells, all asserted in `coercion_matrix.rs` (46 tests, one being
   cross-cutting). No cell omitted as "obvious."

2. §3.3 error precedence — all 8 doc rows + 2 control rows tested.
   `precedence_lone_text_coercion_failure_is_value_error_canon` IS a
   genuine row, not just a control: it pins that `"abc" + 5` → `#VALUE!`
   (not `#REF!`, not other-error), differentiating it from
   `precedence_error_wins_over_text_coercion_failure_canon` where one side
   is an Error.

3. §3.4 per-function override matrix — **multiple gaps** (the
   MEDIUM-S1/S3/S5 findings): HLOOKUP, INDEX, CHOOSE, AND/OR/NOT,
   AVERAGEIF, MIN/MAX-empty, ROUNDUP/ROUNDDOWN-binary-float, COUNTIF/
   COUNTIFS, and SUMIF anchoring all live in the doc but have no
   override test. Some are covered by older tests in module-internal
   files, but the W5-65 matrix-as-substrate test file does not pin them.

4. Coverage tests:
   - `every_registered_function_has_a_coverage_decision` PASSES; 19
     covered + 89 deferred = 108 = registered count. MEDIUM-S4 critique
     stands: EXPLICITLY_DEFERRED is too permissive to be a meaningful
     guardrail.
   - `no_stale_coverage_entries_for_unregistered_functions` correctly
     catches renames (verified by inspection of the iteration loop at
     `coverage.rs:251-259`).
   - `coverage_lists_are_disjoint` is a sound invariant.

5. Test-name conventions are largely consistent. All `_canon_` tests
   really do pin canon behavior; all `_v1_divergence_` tests pin
   divergences; `_w5_*_policy_` for W5-64 NaN/Inf. One naming concern:
   `count_skips_text_and_blanks_canon` (LOW-S5).

### D: Compat doc accuracy (W5-66)

**Verdict: doc is mostly right but uneven; HLOOKUP-transitively claim is wrong.**

1. Aggregates row tags (🟢 canon for SUM / AVERAGE / COUNT / COUNTA) match
   Excel-canon and code. COUNT-vs-COUNTA error-counting divergence
   correctly captured.

2. Most Test-name cites resolve. Cross-checked HLOOKUP, INDEX, CHOOSE
   rows: cited as "—" or "transitively" — see MEDIUM-S1.

3. §3.7 has 🟡 tags on UTF-8 char-count / UPPER-LOWER unicode / ROUNDUP
   binary-float / CONCATENATE 32K-cap (all genuine V1 divergences). No
   row I could find marked 🟢 that should be 🟡 — except possibly
   AND/OR/NOT (line 113, tagged "🟢 (assumed)" — that's already a hedge).

4. AI row tag 🟡 vs ⚪ inconsistency — LOW-S4.

5. "Test wins" rule is not automation-backed (CONCERN-D5 valid). If a
   user edited the doc to claim a new behavior with no test, nothing
   breaks. A doc-test cross-reference check would close this loop (see

### E: Cross-doc drift (W5-66)

**Verdict: no major drift.** Architecture doc §3.4 and error-matrix §3.3 are

### F: Codex MEDIUM 4 (coverage spans both registries)

**Verdict: implemented; could fail more loudly.**

1. `registry.rs:131` `names_all()` chains `fns.keys().chain(range_aware_fns
   .keys())`. Both tables enumerated.

2. The disjoint-tables invariant (`register_range_aware` panics on
   cross-table collision) makes the chained iterator de-dup-free without
   needing a HashSet.

3. The test FAILS with a clear message if a function is missing from both
   lists (`coverage.rs:233-239` panic message names every missing fn). I
   did not empirically simulate this by removing an entry; verified by
   reading the code.

4. No way for a range-aware fn to slip past `names_all()` short of an
   internal API bug.

### G: Public API surface

**Verdict: clean enough, but lib.rs re-export is incomplete (MEDIUM-S7).**

1. `to_text_for_arg`, `to_int_arg`, `to_number_strict_skip_blank`,
   `format_number_for_arg` all `pub` in `coercion.rs` (lines 118, 141, 162,
   189). Compiles for all callers.

2. `ql-types/src/lib.rs:21-24` re-exports only the original 6 helpers.
   See MEDIUM-S7. No working caller is broken by this; just inconsistent
   surface.

3. `range_aware_fns::coerce_numeric` is `pub` so callers in `range_fns.rs`
   and `scalar_fns.rs` can `use` it. `pub(crate)` would also work since
   no external crate calls it, but `pub` is fine and keeps options open
   for a future `ql-bench` or test.

### H: Performance regression risk

**Verdict: probably none; not benched.**

1. Workspace builds with `lto = "thin"` (Cargo.toml profile.release).
   Cross-crate inlining should usually happen, making the `coerce_numeric`
   shim → `to_number_strict_skip_blank` → `to_number_strict` chain inlined
   to one match.

2. None of the hot functions have `#[inline]` annotations, including
   `sanitize_f64`. Thin LTO usually catches these; full LTO or
   `codegen-units=1` (already set) helps further.

3. No bench results in the audit window. If a maintainer wants to be
   confident, run `cargo bench` over SUM/AVERAGE over a 1M-cell range
   before vs after `756875ad08e`. Audit lacks the data to either flag or
   clear this as a perf regression.

### I: Test-name uniqueness across crates

**Verdict: no collisions found.** Cross-crate dedup check via grep over
all four W5-65 test files (`uniq -d`) returned zero entries. Names are
distinctive enough that the `cargo test` filtering and CI log readers can
follow them.

### J: Future-context fitness

**Verdict: the migration does not block future contexts.** The central
`to_number_strict_skip_blank(v: &Value)` takes scalar input. Array context
(Phase 4.7) would iterate cells through this; no blocker. Cross-sheet
(Phase 4.6) flattens to Value before coercion; no blocker. Python/AI
(Phase 6) and CRDT replay (Phase 5) — same `Value`-level boundary; no
blocker. §8 of the design doc enumerates these explicitly; the
implementation doesn't constrain them.

### K: Audit-protocol compliance

**Verdict: violations acknowledged, gates uneven (MEDIUM-S6).**

1. Gates ran on W5-64 + W5-65 (real-code commits) — verified by commit
   bodies. Gates were N/A'd on W5-63 (doc-only), ran on W5-66 (also
   doc-only). Inconsistent — see MEDIUM-S6.

2. The W5-65 "matrix tests are the audit substrate" claim is overstated —
   see MEDIUM-S3.

3. Cycle count W5-49 → W5-66 = 18 cycles, well past the ≤2 budget. User
   explicit-override per-cycle is noted in the brief; not my call to
   re-litigate, but the mega-audit pattern is doing the work of catching

# separate-Opus audit: W5-D-15 (Phase 4.11 XLSX-4-03 per-cell format APPLICATION)

Commit: `4f5226a9876` on `feat/quantbook-engine`.
Scope: per-cell `(row, col) → FormatId` round-trip closure.
Audited files: `cell_styles_xml.rs` (NEW), `sheet_parts.rs`, `read/mod.rs`,
`lib.rs`, `write/umya_export.rs`, `tests/calamine_smoke.rs`.

This is the separate-Opus half of the parallel-audit discipline; Codex
is running its own pass independently. Findings below are based on
(a) reading the committed source at `4f5226a9876`, (b) empirical probe
binaries that ran against the working tree (which already has the
W5-D-15.1 self-audit H-2/H-3 patches partially applied — flagged where
relevant), and (c) tracing of code paths that cannot be exercised
without surgery to the trust boundary.

The user's self-audit (`docs/audits/2026-05-18-w5-d-15-self.md`)
identifies H-1 (blank-cell loss), H-2 (`applyNumberFormat` default), and
H-3 (HashMap nondeterminism). This audit was performed without reading
that file until after independent findings were enumerated — overlap is
noted. Items unique to this audit: H-4 (multi-sheet misalignment),
H-5 (formula-blank cache loses overlay), several MEDIUM/LOW items.

## HIGH findings

### H-1: Blank-cell format overlays are silently lost on export
(Independent finding, also self-audit H-1.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:117-120` (the
  `continue` guard on empty bounds) + `:193-194` (`(None, Value::Blank)`
  skipped) + `:480-483` (SetStyle needle never matches missing cell).
- What's wrong: any `(row, col)` with a format overlay entry but no
  value/formula is silently dropped on export. Three manifestations
  confirmed empirically:
  1. Sheet bounds = (0,0) — entire W5-D-15 overlay walk SKIPPED by the
     `continue` at line 117-120. The `sheet_fixes.push(fixes)` at line
     ~252 is also skipped, which interacts with H-4.
  2. Blank cell with bounds > 0 (e.g., overlay at (5,5), value at
     (0,0) → bounds (1,1)): the W5-D-15 walk runs and schedules a
     SetStyle fix, but umya never emits `<c r="F6">` because the cell
     has no value. The SetStyle needle `<c r="F6"` doesn't match
     anything. Format silently lost.
  3. Formula cell with `Value::Blank` cached value (e.g.,
     `put_formula(s, 0, 0, "1+1")` with no `put_at`): `cache_written`
     is `false`, `set_formula` is called but umya elides the cell from
     output (empirically: `<sheetData/>` is emitted as
     self-closing). Format lost (and the formula itself doesn't
     survive, but that's a pre-existing umya behavior).
- Why it matters: data-entry templates and finance models commonly
  pre-format empty columns (e.g., "format column A as currency for
  future entries"). This is REAL application state. After the W5-D-15
  ship, users believe per-cell format application round-trips; on this
  common case it silently doesn't.
- Suggested fix:
  - Phase-1 (minimal): write a `Value::Text("")` placeholder via
    `apply_value_to_cell` whenever the cell has an overlay entry but
    no formula/value. umya will then emit `<c r="..." t="str"><v></v></c>`
    and SetStyle can inject `s="N"`. Re-import would see a blank
    text cell with the format. Not ideal (introduces a phantom text
    type) but closes the gap immediately.
  - Phase-2 (correct): post-process inject blank `<c r="..." s="N"/>`
    elements into `<sheetData>` for overlay entries whose ref isn't
    already in the worksheet xml. Requires `<row>` boundary handling
    to land each cell inside the correct row (and creating missing
    `<row>` elements if needed). Coordinate with the dimension
    `<dimension ref="...">` element so the union bounds remain
    correct.
- Empirical: probe scenarios 2 (`(5,5)` overlay only), 10 (formula
  with Blank cache), and 11 (pure overlay with bounds=0) all confirmed
  zero overlay entries after round-trip.

### H-2: `applyNumberFormat` default flipped from OOXML spec; real-world files silently lose formats
(Independent finding, also self-audit H-2.)

- File: `crates/ql-io-xlsx/src/read/styles_xml.rs:175` (committed
  default: `let mut apply_number_format = false;`).
- What's wrong: ECMA-376 / OOXML schema (CT_Xf) states the default for
  `applyNumberFormat` is `true` when the attribute is absent. The
  committed parser uses `false` as the default. The W5-D-15 wiring at
  `lib.rs:202-205` then skips populating the overlay when
  `apply_number_format == false`. Net effect: any `<xf>` in
  `<cellXfs>` that omits `applyNumberFormat="1"` (very common in
  LibreOffice, openpyxl, xlsxwriter, hand-built files) silently loses
  its format on import.
- Why it matters: real-world xlsx fixtures from non-Microsoft tools
  routinely omit the attr. Date cells, currency cells, scientific
  notation — all generated by LibreOffice without the attr — round-trip
  with `format_overlay().len() == 0`. Phase 4.11 acceptance
  XLSX-4-03 claims "formats survive round-trip where supported" but
  the support boundary excludes the most common real-world emitter.
- Working tree note: the unstaged change to `styles_xml.rs:183` flips
  this to `true` per a W5-D-15.1 closure. The committed code has the
  bug. Existing unit test
  `parse_cell_xfs_only_not_cell_style_xfs:279` would
  *fail* under the fix (it asserts `!apply_number_format` for an `<xf>`
  with no `applyNumberFormat` attr) — the test was written assuming
  the wrong default and pins it. The fix must update the test as well.
- Suggested fix: default `apply_number_format = true`. Update the
  test fixture to use an `<xf>` with explicit `applyNumberFormat="0"`
  when the intent is "format not applied". Add an E2E fixture exercising
  a LibreOffice-style minimal xlsx (attr omitted) to assert the
  default-true behavior.
- Empirical: probe scenario 5 (hand-built fixture, attr omitted)
  with the working-tree fix applied: overlay correctly populated.
  Against committed code, would return `None` (verified by code
  inspection — `xf.apply_number_format` is `false`, the wiring at
  `lib.rs:202` `continue`s).

### H-3: cellXfs roster + per-cell s="N" values are HashMap-iteration nondeterministic
(Independent finding, also self-audit H-3.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:224` (committed:
  `for ((row, col), fid) in sheet_view.format_overlay().iter()` —
  unsorted).
- What's wrong: `CellFormatOverlay::iter` returns
  `self.entries.iter()` where `entries: HashMap<(RowId, ColId),
  FormatId>`. Rust's `HashMap` uses randomized `RandomState`; the
  same set of entries yields different iteration orders across
  processes. The W5-D-15 code mints `xf_index = roster.len() + 1` for
  the FIRST occurrence of each FormatId — so the (FormatId →
  xf_index) mapping varies run-to-run. Each cell's emitted `s="N"`
  varies. The styles.xml `<cellXfs>` order varies. The output xlsx
  bytes vary.
- Why it matters: the deliverable's semantic correctness IS preserved
  on re-import (the FormatId mapping survives via numFmtId), but:
  (a) byte-deterministic xlsx output is required by replay /
  `.qbook` persistence equivalence checks at the engine layer
  (Phase 5 / CRDT history specifically — per engine plan); (b) any
  golden-bytes test against the output digest would be flaky; (c)
  diff-based tooling (e.g., user-facing "what changed" between two
  exports of the same workbook) would show every cell's `s="..."`
  flipping; (d) caching keyed on output digest (CDNs, proxies,
  signed-artifact verification) would miss.
- Working tree note: a partial fix is unstaged in `umya_export.rs:232-236`
  (`overlay_entries.sort_by` / `sort_by_key`). The committed code
  doesn't have it. ALSO: cross-sheet roster non-determinism is NOT
  addressed by the per-sheet sort — see H-4.
- Suggested fix: at the workbook-roster level, switch from
  `HashMap<FormatId, u32>` + `Vec<FormatId>` to a `BTreeMap<FormatId,
  u32>` (or post-walk sort the roster by FormatId before assigning
  final xf indices). The per-sheet sort partially fixes intra-sheet
  ordering but doesn't fix the case where two sheets contribute
  formats in different orders.
- Empirical: my probe was unable to demonstrate this because (a) the
  working tree has the partial fix already, and (b) within a single
  process the same RandomState seed can give the same iteration order
  for HashMaps with the same insertion pattern. To verify the bug
  empirically against the committed code, run `cargo test` 5+ times
  in fresh processes and diff the output bytes.

### H-4: Multi-sheet workbooks with an empty earlier sheet drop per-cell formats on later sheets
(NEW — not in self-audit; only obliquely hinted at by self-audit M-5.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:117-120` + `:252`.
- What's wrong: when a sheet has `bounds.row_extent == 0 ||
  bounds.col_extent == 0`, the `continue` at line 120 SKIPS the
  `sheet_fixes.push(fixes)` at line 252. So `sheet_fixes` ends up
  with fewer entries than `workbook.sheet_count()`. The post-process
  `apply_cell_fixes_to_sheet_xml` lookup at line 379
  (`sheet_fixes.get(sheet_idx)` where `sheet_idx` is from
  `sheet_index_from_path("xl/worksheets/sheetN.xml")` ≡ N-1, i.e.,
  workbook order) becomes MISALIGNED with the actual sheet. Sheet 2's
  fixes get applied to sheet1.xml (or to no sheet at all if the index
  is past the end of the truncated Vec).
- Concrete manifestation: workbook with sheet 0 empty and sheet 1
  populated + format overlay on (0,0). Sheet 0 hits `continue` (no
  push). Sheet 1 fully walked, fixes pushed → `sheet_fixes = [fixes_for_sheet_1]`.
  Post-process for `sheet1.xml`: `sheet_idx = 0`, `sheet_fixes.get(0)`
  returns sheet 1's fixes. These reference cell A1; sheet1.xml is umya's
  sheet 0 xml — which is also empty (no `<c r="A1">`). Needle no-op.
  Post-process for `sheet2.xml`: `sheet_idx = 1`, `sheet_fixes.get(1)`
  is None. NO fixes applied. Format LOST.
- Why it matters: hidden + empty leading sheets are common in
  enterprise templates (cover-page sheets, branding sheets,
  placeholder sheets for future content). For these, every format
  application on subsequent sheets disappears.
- Empirical: probe scenario 3 (`First` empty, `Second` populated with
  `intern("0.00%")` overlay at (0,0)) confirmed: `sheet2.xml` was
  emitted as `<c r="A1"><v>0.25</v></c>` — NO `s` attribute.
- Suggested fix: the WIP unstaged change adds `if has_cells_to_walk { ... }`
  to gate the cell walk and runs `sheet_fixes.push(fixes)`
  unconditionally. That's the correct shape, but the WIP code as of
  this audit timestamp has an UNCLOSED BRACE and doesn't compile. The
  fix must:
  - Keep cell-walk loops inside `if has_cells_to_walk { ... }`.
  - Run the overlay walk + `sheet_fixes.push(fixes)` outside the guard
    (so every sheet gets exactly one entry in `sheet_fixes`, in
    workbook order).
  - Verify with a multi-sheet round-trip test where sheet 0 is empty
    and sheet 1 has overlay.

### H-5: Formula-only cells with Blank cached values produce no `<c>` tag, dropping both formula AND overlay
(NEW.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:146-164` (the
  `(Some(formula_text), Value::Blank)` arm of the cell-walk match).
- What's wrong: when a formula cell has `Value::Blank` cached value
  (e.g., a freshly-imported formula whose recompute didn't fire, or
  one that legitimately evaluates to a blank), `cache_written = false`,
  so only `cell.set_formula(...)` is called on umya's Cell. umya 2.2.0
  appears to elide such cells from output entirely (empirically:
  `<sheetData/>` is self-closing). Two losses:
  1. The formula text is dropped (pre-existing umya/W5-D-14e
     behavior). Pre-W5-D-15 problem; not a W5-D-15 regression but
     SHOULD be on Codex's radar for Phase 4.11 separately.
  2. NEW with W5-D-15: any overlay entry on this cell is also
     dropped because the SetStyle needle has no `<c r="...">` to
     match. The W5-D-15 commit message claims "formats round-trip"
     but doesn't carve out this exception.
- Suggested fix: in the `Some(formula_text), Value::Blank` arm, also
  call `cell.set_value_string("")` (or equivalent placeholder) so
  umya emits the cell tag. Verify it doesn't double-write the
  formula's `<f>` element.

## MEDIUM findings

### M-1: Replacement `<cellXfs>` strips `xfId="0"` reference that points to a non-existent `<cellStyleXfs>`
(NEW — schema cleanliness concern.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:639` (slot 0:
  `<xf numFmtId="0" fontId="0" fillId="0" borderId="0" xfId="0"/>`).
- What's wrong: umya 2.2.0 does NOT emit a `<cellStyleXfs>` element
  in `xl/styles.xml` (empirically verified — see probe scenario 2
  styles.xml: no `<cellStyleXfs>` between `<borders>` and `<cellXfs>`).
  Our replacement preserves `xfId="0"` (matching umya's convention),
  but `xfId="0"` references a non-existent `<cellStyleXfs>` slot 0.
  Per ECMA-376 §18.8.10, `xfId` "is the zero-based index of a cell
  style XF record (CT_Xf) in `cellStyleXfs`". With no `<cellStyleXfs>`,
  this is a dangling reference. Excel tolerates it; LibreOffice may
  warn or auto-fix.
- Severity: MEDIUM — empirically umya-generated files DO open in
  Excel, and umya's own output uses `xfId="0"` without
  `<cellStyleXfs>`. So we're matching umya's convention, not creating
  a NEW violation. But the convention is technically
  schema-non-conformant. Most reliable fix: emit an empty
  `<cellStyleXfs count="1"><xf numFmtId="0" .../></cellStyleXfs>` block
  alongside the cellXfs injection so `xfId="0"` resolves.
- Suggested fix: extend `inject_cell_xfs_into_styles_xml` to also
  inject a minimal `<cellStyleXfs>` if absent. Or omit `xfId` (it's
  optional). The latter is simpler.

### M-2: Out-of-bounds xf index on import silently dropped without warning
(Independent finding, also self-audit M-2.)

- File: `crates/ql-io-xlsx/src/lib.rs:199-201` (the
  `let Some(xf) = style_index.cell_xfs.get(xf_idx as usize) else { continue; };`).
- What's wrong: a hand-edited or corrupted xlsx with `<c s="99">` but
  only 5 cellXfs entries silently skips the cell. No warning, no
  report entry. Phase 4.11 acceptance XLSX-4-04 says corruption
  surfaces visible errors; this is corruption that's silent.
- Suggested fix: append a `report.warnings.push(XlsxWarning { ... })`
  with the location (sheet name + cell ref) and the offending
  xf index. Strict mode could elevate to error.

### M-3: cellxfs replacement may clobber non-default cellXfs umya emits in non-trivial workbooks
(Independent finding, related to self-audit M-4.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:649-662` (the
  full-block replacement).
- What's wrong: empirically umya emits 2 cellXfs entries for the
  blank-cell test (probe scenario 2), with slot 1 carrying
  `fillId="1"` (gray125). For a NewWorkbook export with no overlay,
  these slot 1 styles aren't referenced by any cell anyway (umya
  doesn't write `s` attrs on the cells it generates, verified
  empirically). So in practice no harm — but the M-4 self-audit
  hypothesis "what if umya emits more cellXfs that get clobbered" is
  testable. Currently no probe scenario empirically clobbered a
  meaningful slot, but ANY scenario where umya emits a cell with
  `s="1"` AND we replace cellXfs entirely would silently swap that
  cell's intended style to whatever WE put at slot 1 (a custom
  format). The probe only ran value-bearing scenarios that umya
  emitted without `s="..."`.
- Severity: MEDIUM — latent. If umya 2.3+ or a different code path
  starts emitting cells with `s="..."`, we'd silently corrupt them.
- Suggested fix: instead of replacing the entire `<cellXfs>` block,
  APPEND our custom xfs at the end. Compute final xf_index as
  `existing_count + roster.len()`. Parse the existing cellXfs count
  from the umya-generated styles.xml to know `existing_count`.
- Cross-check: an `inject_cell_xfs_into_styles_xml` test of the
  replacement-vs-append distinction is missing from the test suite.

### M-4: HashMap-iteration nondeterminism affects roster ORDER across multiple sheets even with intra-sheet sort
(NEW — refinement of H-3.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:97-99` +
  per-sheet overlay walks.
- What's wrong: even with the unstaged self-audit H-3 fix (per-sheet
  `overlay_entries.sort_by_key(...)`), the WORKBOOK-LEVEL `cellxfs_roster`
  Vec accumulates FormatIds in the order they're FIRST seen across
  sheets. Sheet processing IS sequential (deterministic), but within
  each sheet the sort is `(FormatId, row, col)`. So intra-sheet
  determinism is fine, but if sheet 0 has FormatId 165, sheet 1 has
  FormatId 164, the roster ends up `[165, 164]` (because 165 is seen
  first on sheet 0). Two RUNS of the same exporter will produce the
  same roster (sheet processing order is stable), so this is
  deterministic — but it diverges from what a `BTreeMap<FormatId,
  u32>` would produce (`[164, 165]`).
- Severity: MEDIUM — not a correctness bug, just a roster-order
  consistency one. The H-3 sort by (FormatId, row, col) inside a
  sheet won't change the FIRST-INSERTION order in `cellxfs_roster`
  across sheets unless the WHOLE-WORKBOOK iteration is also sorted.
- Suggested fix: lift the roster construction to a workbook-level
  BTreeMap<FormatId, u32>. Or, post-pass, sort `cellxfs_roster` by
  FormatId and rewrite all `xf_index` assignments accordingly. The
  BTreeMap form is cleaner — one source of truth.

### M-6: No bounds-check on (row, col) when populating the overlay from import
(NEW.)

- File: `crates/ql-io-xlsx/src/lib.rs:210-211`
  (`sheet.format_overlay_mut().set(row, col, fmt_id)`).
- What's wrong: `parse_a1_cell` in `cell_styles_xml.rs` accepts
  arbitrary letter counts. A malformed `<c r="ZZZZ1">` with no
  bounds-check could place an overlay entry at `(0, ~16384*26 + ...)`,
  way past Quantbook's MAX_COLUMN (16,383 = XFD). The other import
  paths (`convert::build_workbook_from_grid:60-82`) bounds-check
  against `MAX_ROW`/`MAX_COLUMN` and emit warnings. The W5-D-15
  per-cell-style wiring does NOT.
- Severity: MEDIUM — consistency / corruption-surface concern.
  Doesn't crash (just stores an out-of-bounds entry in the HashMap
  that would never be read by a sane consumer), but breaks the
  Phase 4.11 acceptance "corruption surfaces visibly".
- Suggested fix: at lib.rs:210, check `row <= MAX_ROW && col <=
  MAX_COLUMN`. If out of range, emit `XlsxWarning` and `continue`.
  Match the cell-loading bounds-check pattern from `convert.rs:60-82`.

### M-7: Slot 0 missing `applyNumberFormat="0"` — schema ambiguity if H-2 fix changes default
(NEW — interacts with H-2 fix.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:639`
  (`<xf numFmtId="0" fontId="0" fillId="0" borderId="0" xfId="0"/>`).
- What's wrong: the W5-D-15 default slot 0 has no
  `applyNumberFormat` attribute. With H-2 fixed (default = true),
  this xf will be interpreted as "applyNumberFormat=true, format=0
  (General)" on re-import. The W5-D-15 import wiring at
  `lib.rs:206-208` has a special case for `xf.num_fmt_id == 0`
  (General → no overlay entry). So this works correctly. BUT: the
  combination (`apply_number_format=true` + `num_fmt_id=0`) is
  semantically redundant; some tools may interpret it as "explicitly
  set General format". Not breaking, but worth tracking.
- Suggested fix: explicitly emit `applyNumberFormat="0"` on slot 0.
  Or leave a comment in the source explaining the General-skip
  short-circuit so future maintainers don't get confused.

### M-9: `inject_cell_xfs_into_styles_xml` case-2 inserts at wrong schema position
(Independent finding, self-audit M-1.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:675-683`.
- What's wrong: case-2 (no existing `<cellXfs>`) inserts before
  `</styleSheet>`, which lands AFTER `<cellStyles>`, `<dxfs>`,
  `<tableStyles>`, `<colors>`, `<extLst>`. OOXML schema requires
  `<cellXfs>` BEFORE all those (per CT_Stylesheet child order).
- Severity: MEDIUM (latent) — umya 2.2.0 always emits a
  `<cellXfs>`, so case-2 never fires today. Future writer change
  would silently produce invalid xlsx.
- Suggested fix: insert after `</cellStyleXfs>` (if present),
  else after `</borders>`, else after `</fills>`, else after
  `</fonts>` — first-available anchor in the correct schema sequence.

## LOW findings

### L-1: `parse_a1_cell` accepts arbitrarily long letter sequences; u32 overflow not bounded
(Independent finding, self-audit L-1.)

- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs:91-97`.
- `col = col * 26 + ...` wraps silently on overflow (release mode);
  panics in debug. Excel column limit is XFD (16,384 columns =
  3 letters), so realistic input never overflows. But a hand-edited
  malicious xlsx could craft 12+-letter refs to cause panic in tests
  or wrap to a smaller index that COLLIDES with a legitimate cell.
- Suggested fix: `checked_mul` + `checked_add`; on overflow return
  `None`. Or cap letter count at 3 (Excel max) and reject longer.

### L-2: `cell_styles_xml::extracts_styled_cells` test doesn't anchor the order check
- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs:111-128`.
- The test does `assert!(out.contains(&(0, 0, 3)))`. The output Vec
  ordering is XML stream order, but the test doesn't anchor it. If
  someone changes the parser to return in a different order, the
  test still passes. Asserting order matters for `format_overlay.set`
  semantics (latest write wins — see L-4).
- Suggested fix: `assert_eq!(out, vec![(0, 0, 3), (0, 3, 5)]);`.

### L-3: Repeated `<c r="A1" s="...">` in worksheet xml — last write wins via overlay.set, but parser yields all
- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs` (the loop
  doesn't dedupe).
- If a corrupted xlsx has two `<c r="A1">` entries with different
  `s` attrs, the parser emits both. The W5-D-15 wiring at lib.rs
  applies `set` for each → the last-emitted one wins (overlay
  HashMap semantics). Stream-order dependent. Probably acceptable —
  duplicate cell refs are malformed OOXML and Excel's behavior is
  unspecified — but worth a `XlsxWarning` on detection.

### L-4: No test asserts the round-trip preserves `format_overlay().len()`
(Independent finding, self-audit L-4.)

- The three new E2E tests check specific (row, col) cells with
  `overlay.get(...) == Some(FormatId(N))`. A bug that ALSO populates
  extra phantom entries would pass these tests. Add:
  `assert_eq!(imported_overlay.len(), expected_count);`.

### L-5: `parse_cell_styles_xml` loads the whole worksheet xml into memory
(Independent finding, self-audit L-5.)

- For huge sheets (millions of cells), `package.read_part_string` +
  `Reader::from_str` is non-streaming. LOW — Phase 4.11 doesn't claim
  huge-sheet support yet.

### L-6: `apply_number_format` parser is case-insensitive for "true"/"TRUE" but only handles "1" for the number form
- File: `crates/ql-io-xlsx/src/read/styles_xml.rs:191`.
- `val == "1" || val.eq_ignore_ascii_case("true")`. Doesn't accept
  `"01"`, leading whitespace, etc. XML spec for xs:boolean accepts
  `0|1|true|false`. Practically fine; LOW. (Self-audit L-2 noted
  but corrected itself — same conclusion.)

### L-7: SetStyle needle could be tightened with an anchor on the byte AFTER closing `"`
(Independent finding, self-audit L-7.)

- File: `crates/ql-io-xlsx/src/write/umya_export.rs:480-483`.
- The needle `<c r="C5"` doesn't anchor on the byte after the
  closing `"`. In practice no collision is possible (cell refs are
  unique within a sheet, and the closing `"` ensures it isn't a
  prefix of a longer ref like `A11"`). But tightening to
  `<c r="C5" ` OR `<c r="C5">` OR `<c r="C5"/>` would make the
  intent explicit. The current form is correct but brittle to
  future emitter changes.

### L-8: `cell_styles_xml.rs:46` swallows attribute escape errors silently
- `attr.unescape_value().unwrap_or_default()` — if the attr value
  has malformed XML entities (e.g., `r="A&garbage;1"`), the
  unescape fails silently and falls back to empty string. The cell
  ref then parses as malformed → skipped. No warning.
- Suggested fix: log a warning. Phase 4.11 acceptance XLSX-4-04
  applies.

### L-9: `parse_a1_cell` rejects refs with absolute markers (`$A$1`)
- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs:80-103`.
- `parse_a1_cell` requires the ref to start with letters and only
  contain digits afterward. `$A$1` would fail (the `$` is not
  alphabetic). Cells in worksheet xml NEVER use `$` markers in the
  `r` attribute (those are only for formula content), so this is
  fine in practice. Worth a comment though.

### L-10: `cell_styles_xml::parses_a1_cell_basic` test misses single-letter beyond Z
- File: `crates/ql-io-xlsx/src/read/cell_styles_xml.rs:138-141`.
- Tests A1, Z9, AA10. Misses AZ, BA (transitions). Minor coverage
  gap.

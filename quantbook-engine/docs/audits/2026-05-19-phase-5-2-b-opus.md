## MEDIUM findings

**MED-1 — `OpLog::set_peer_id` docstring lies about idempotence** (`crates/ql-oplog/src/log.rs:135-136`).
The docstring claims `Idempotent — calling it twice with the same id is a no-op.` Reading Loro 1.12.0 internals (`loro-internal-1.12.0/src/loro.rs:183-218`), Loro does not special-case "same id":
- It always stores the value to `doc_state.peer` (line 192/214).
- It always emits a `peer_id_change_subs` notification (line 199/216).
- In auto-commit mode with an in-flight txn (line 194), it forces an implicit-barrier commit. In non-auto-commit, an in-flight txn produces `LoroError::TransactionError`.

Fix: rewrite the doc to "Setting the same id is safe but not strictly a no-op — Loro re-stores the atom and emits a peer-id-change notification each call. Avoid calling repeatedly in hot paths." OR add an actual no-op short-circuit (`if self.doc.peer_id() == peer { return Ok(()) }`) and write a test that exercises double-set with same id.

**MED-2 — `set_peer_id_after_import_works` does not assert what the docstring promises** (`crates/ql-oplog/src/log.rs:336-346` and `crates/ql-collab/src/session.rs:265-276`).
Both tests assert only that the *log's current* peer id equals the newly assigned id. The `OpLog::set_peer_id` docstring (`log.rs:145-147`) and the `CollabSession::from_snapshot` docstring (`session.rs:96-98`) both promise *imported ops retain their original peer ids*. Neither test verifies that claim — both origin sessions have ZERO appended ops, so there are no imported ops to attribute. The regression guard is therefore weaker than advertised.

**MED-3 — `PeerID::MAX` (`u64::MAX`) rejection is undocumented and untested at the OpLog/CollabSession boundary** (`crates/ql-oplog/src/log.rs:148`, `crates/ql-collab/src/session.rs:84`).
Loro 1.12.0 rejects `peer == PeerID::MAX` with `LoroError::InvalidPeerID` (`loro-internal-1.12.0/src/loro.rs:184-186`).

**MED-4 — Duplicate-peer-id pitfall completely unguarded** (per audit task §3).
The docstring escalates this to "MUST" but ships no enforcement. Cheapest fix: process-global `OnceLock<HashSet<PeerId>>` debug-assert in `CollabSession::new`/`from_snapshot` (gated on `debug_assertions`).

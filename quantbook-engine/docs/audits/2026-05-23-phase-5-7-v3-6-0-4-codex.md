# Phase 5.7 V3.6.0.4 D3 Codex Audit

Audit date: 2026-05-23  
Scope: per-cell + per-sheet op-log indices, `CacheBuckets`, `OpLog::get`, `rebuild_op_indices_only`, and index-driven `invalidate_cell`  
Engine target: shipped D3 surface at `119df9b3826`, audited on current `feat/quantbook-engine` worktree at `84cb5c9d169`

## Verdict

PASS-WITH-FINDINGS

No HIGH correctness failure was confirmed on the normal append / merge / from_snapshot / discard / undo / redo paths. The core index-driven invalidation design is mostly sound for current production callers, and the existing ql-collab and ql-oplog test suites pass.

I did confirm two MEDIUM issues:

- `poll_remote_with_limit` leaves snapshot/index caches stale if an earlier blob merged successfully and a later blob errors before the post-loop rebuild.
- `rebuild_op_indices_only` does not match `rebuild_snapshot_cache` under tombstoned-sheet histories because it duplicates only the raw index-push logic and skips the tombstone filter in `apply_cache_effect`.

## Summary

- `OpLog::get(index)` mirrors one `iter()` step and handles empty, boundary, and malformed JSON cases correctly at `crates/ql-oplog/src/log.rs:180`.
- `CacheBuckets` construction uses split borrows of disjoint fields at `crates/ql-collab/src/session.rs:1191`, `crates/ql-collab/src/session.rs:1828`, and `crates/ql-collab/src/session.rs:2032`.
- Normal `merge_bytes`, `from_snapshot`, `discard_pending_ops`, and successful `poll_remote_with_limit` rebuild indices via `rebuild_snapshot_cache` at `crates/ql-collab/src/session.rs:1078`, `crates/ql-collab/src/session.rs:1482`, `crates/ql-collab/src/session.rs:2823`, and `crates/ql-collab/src/session.rs:3165`.
- Undo/redo refresh positional indices before partial invalidation at `crates/ql-collab/src/session.rs:3318` and `crates/ql-collab/src/session.rs:3395`.
- Current `invalidate_cell` correctness survives extra tombstoned no-op indices, but the public index accessors can diverge from full-rebuild index contents.

## MEDIUM findings

1. MEDIUM-1: `poll_remote_with_limit` can commit remote ops but skip cache/index rebuild on a later blob error.

   Scope: transport polling, snapshot cache freshness, `cell_op_index` / `sheet_op_index` sync invariant.

   Evidence:

   - The drain loop merges each received blob directly into `self.log` at `crates/ql-collab/src/session.rs:3131` through `crates/ql-collab/src/session.rs:3135`.
   - A later `self.log.merge_bytes(&bytes)?` error returns immediately, before the `if merged > 0 { self.rebuild_snapshot_cache()?; ... }` block at `crates/ql-collab/src/session.rs:3155` through `crates/ql-collab/src/session.rs:3169`.
   - The method doc already acknowledges this partial state for auto-flush at `crates/ql-collab/src/session.rs:3098` through `crates/ql-collab/src/session.rs:3108`, but it only discusses `last_flushed_vv`; it does not repair `last_snapshot`, `removed_sheets`, `format_table_cache`, `cell_op_index`, or `sheet_op_index`.
   - `snapshot_cells` reads the potentially stale `last_snapshot` cache at `crates/ql-collab/src/session.rs:1722` through `crates/ql-collab/src/session.rs:1729`.
   - A compiled probe queued one valid remote snapshot followed by invalid bytes. `poll_remote_with_limit(2)` returned `Err`, `op_count()` was `1`, `snapshot_cells(0)` was empty, and `CollabSession::from_snapshot` over the same exported bytes saw the committed remote cell.

   Impact:

   After a malformed blob or transport error that occurs after one or more successful blob merges, the session's op log has advanced but the public caches and D3 indices remain at the pre-poll state. A caller that surfaces the error and keeps the session alive can read stale cells until a later successful rebuild path happens to run.

   Suggested closure:

   Track the first drain error, break to a common post-loop section, and if `merged > 0` run `rebuild_snapshot_cache()` before returning the original error. Preserve the existing "skip auto-flush on error" behavior unless product semantics explicitly choose otherwise. Add a regression test with a valid blob followed by invalid bytes and assert both `op_count()` and `snapshot_cells()` reflect the committed first blob.

2. MEDIUM-2: `rebuild_op_indices_only` diverges from full rebuild under tombstones.

   Scope: undo/redo partial path, public `cell_op_index_iter`, future delta consumers.

   Evidence:

   - The full rebuild path calls `apply_cache_effect` at `crates/ql-collab/src/session.rs:1828` through `crates/ql-collab/src/session.rs:1837`.
   - `apply_cache_effect` returns before index maintenance when a cell-keyed effect targets an already tombstoned sheet at `crates/ql-collab/src/session.rs:1323` through `crates/ql-collab/src/session.rs:1334`; the actual index push happens later at `crates/ql-collab/src/session.rs:1346` through `crates/ql-collab/src/session.rs:1364`.
   - `rebuild_op_indices_only` scans effects and pushes cell/sheet indices directly at `crates/ql-collab/src/session.rs:1888` through `crates/ql-collab/src/session.rs:1916`, with no local tombstone tracker and no call to `apply_cache_effect`.
   - The index accessors are public at `crates/ql-collab/src/session.rs:1623` and `crates/ql-collab/src/session.rs:1638`.
   - A compiled probe built `AddSheet, PutValue(A1), RemoveSheet, PutValue(A1 no-op), PutValue(A2 no-op)`, then undid the final no-op to force `rebuild_op_indices_only`. The partial undo path reported `cell_op_index[(0,0,0)] == [1, 3]`; a fresh `from_snapshot` full rebuild over the exact same visible log reported `[1]`.

   Impact:

   Current `invalidate_cell` still computes the right cell value because the extra post-tombstone index replays through a local tombstone and gets dropped. The contract still breaks: index contents differ by mutation path, and future users of `cell_op_index_iter` for deltas or diagnostics will observe spurious post-tombstone cell changes after undo/redo until a full rebuild happens.

   Suggested closure:

   Make `rebuild_op_indices_only` reuse `apply_cache_effect` with throwaway `snapshot`, `tombstones`, and `format_cache` buckets, or factor the tombstone-aware index-maintenance logic into one shared helper. Add a regression where a post-tombstone cell op survives in the log and verify `rebuild_op_indices_only` matches `from_snapshot` / `rebuild_snapshot_cache`.

## LOW findings

1. LOW-1: The `OpLog::get` O(1) performance claim is not supported by Loro 1.12.0 source.

   Scope: D3 performance contract.

   Evidence:

   - `OpLog::get` documents `LoroList::get(index)` as O(1) at `crates/ql-oplog/src/log.rs:161`.
   - `invalidate_cell` repeats the O(1) random-access claim at `crates/ql-collab/src/session.rs:1943`.
   - Loro 1.12.0's public `LoroList::get` delegates to the handler at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/loro-1.12.0/src/lib.rs:1822`; the attached list state uses `self.list.query::<LengthFinder>(&index)` over a `generic_btree::BTree` at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/loro-internal-1.12.0/src/state/list_state.rs:317`.

   Impact:

   D3 still improves from O(N) full-log scans to indexed access, but the honest bound is likely O(indices-for-cell * log N), not pure O(indices-for-cell).

   Suggested closure:

   Relax comments and plan text to "indexed lookup" or "avoids full-log scan" unless Loro upstream explicitly documents O(1). Keep the user-facing performance claim qualitative.

2. LOW-2: `invalidate_cell` mutates `last_snapshot` before fallible indexed lookups.

   Scope: invariant-violation/error path.

   Evidence:

   - `invalidate_cell` removes the target cache entry up front at `crates/ql-collab/src/session.rs:1970`.
   - It can then return `Err` for `OpLog::get` deserialization/schema failures or out-of-range indices at `crates/ql-collab/src/session.rs:2021` through `crates/ql-collab/src/session.rs:2028`.

   Impact:

   If the supposedly unreachable stale-index path does fire, the method returns an error after already deleting the cached cell. That makes a bad invariant violation leave a worse cache state for any caller that keeps using the session.

   Suggested closure:

   Fetch and collect all ops first, or build the replacement state without touching `last_snapshot` and only remove/replace the target after all fallible lookups succeed. Alternatively, on `None`, fall back to `rebuild_snapshot_cache()` instead of returning after a partial mutation.

3. LOW-3: `invalidate_cell` still populates throwaway index maps.

   Scope: per-cell invalidation overhead.

   Evidence:

   - The method allocates `local_cell_op_index` and `local_sheet_op_index` at `crates/ql-collab/src/session.rs:2009` and `crates/ql-collab/src/session.rs:2010`.
   - It passes those maps into `apply_cache_effect` at `crates/ql-collab/src/session.rs:2032` through `crates/ql-collab/src/session.rs:2038`, so index-maintenance code still runs for the local throwaway buckets at `crates/ql-collab/src/session.rs:2057`.

   Impact:

   Correct but wasteful. The cost is small for current K, but it is now in the hot path D3 was meant to shrink.

   Suggested closure:

   Split "apply state" from "maintain indices", or add an index-maintenance mode to `CacheBuckets` so per-cell replay can opt out.

4. LOW-4: Hot cells and tombstoned sheets can retain large index vectors.

   Scope: memory growth.

   Evidence:

   - Every separate cell-keyed op appends a `usize` to the cell's vector at `crates/ql-collab/src/session.rs:1355` through `crates/ql-collab/src/session.rs:1358`.
   - RemoveSheet drops snapshot entries at `crates/ql-collab/src/session.rs:1424` through `crates/ql-collab/src/session.rs:1426`, but it does not remove per-cell index vectors for cells on the removed sheet.

   Impact:

   A hot cell with 10k visible ops carries roughly 80KB of index integers, plus `Vec` overhead. Removed sheets keep their historical per-cell index vectors until a future log compaction/rebuild policy drops the underlying history.

   Suggested closure:

   Document this as bounded-by-visible-op-history. If memory profiles badly, consider per-cell compact summaries or clearing tombstoned-sheet cell vectors once stable op IDs / restore semantics are designed.

## INFO findings

1. INFO-1: Normal mutation-site index sync is present.

   Evidence:

   - `from_snapshot` rebuilds at `crates/ql-collab/src/session.rs:1078`.
   - `merge_bytes` rebuilds at `crates/ql-collab/src/session.rs:1482`.
   - `discard_pending_ops` rebuilds after replacing the log at `crates/ql-collab/src/session.rs:2823`.
   - Successful `poll_remote_with_limit` rebuilds once after the drain batch at `crates/ql-collab/src/session.rs:3155` through `crates/ql-collab/src/session.rs:3165`.
   - Undo/redo partial paths call `rebuild_op_indices_only` before invalidating cells at `crates/ql-collab/src/session.rs:3318` and `crates/ql-collab/src/session.rs:3395`.

2. INFO-2: `CacheBuckets` lifetime and aliasing look sound.

   Evidence:

   - All three construction sites pass disjoint fields/local maps: `append_op` at `crates/ql-collab/src/session.rs:1191`, full rebuild at `crates/ql-collab/src/session.rs:1828`, and `invalidate_cell` at `crates/ql-collab/src/session.rs:2032`.
   - No `CacheBuckets` escapes its function scope.

3. INFO-3: `OpLog::get` edge behavior matches its shape contract.

   Evidence:

   - Empty log and just-after-end return `None`.
   - Just-before-end returns `Some(Ok(Op::...))`.
   - A Loro list containing malformed JSON returns `Some(Err(OpLogError::Deserialize { index, .. }))`.

4. INFO-4: Out-of-range index errors are not reachable on the confirmed normal paths.

   Evidence:

   - The shipped undo regression at `crates/ql-collab/src/session.rs:4805` through `crates/ql-collab/src/session.rs:4855` covers the original visible-list compaction failure.
   - My additional probes covered normal `poll_remote_with_limit` and `discard_pending_ops` rebuilds.

   Note:

   MEDIUM-1 is a separate partial-error path where caches become stale because rebuild is skipped; it did not produce an out-of-range index in the probe.

5. INFO-5: The long-term stable-op-ID migration is non-trivial.

   Evidence:

   - `OpLog::append` stores only JSON strings in the `"ops"` LoroList at `crates/ql-oplog/src/log.rs:99` through `crates/ql-oplog/src/log.rs:103`.
   - `OpLog::get` indexes the visible list position, not a Loro element ID, at `crates/ql-oplog/src/log.rs:180`.

   Note:

   Moving `cell_op_index` to stable op IDs likely requires capturing Loro element IDs at insert/rebuild time and adding an ID lookup API, or changing the op wire shape to carry stable IDs. The current JSON-only op payload does not provide that by itself.

## Coverage gaps identified

- No regression for `poll_remote_with_limit` where a valid blob is followed by malformed bytes or transport `Io`; this should pin MEDIUM-1.
- No regression that `rebuild_op_indices_only` exactly matches `rebuild_snapshot_cache` for tombstoned-sheet histories; current D3 undo test only covers simple same-cell append/undo.
- No direct test for `merge_bytes` importing a syntactically valid Loro document with malformed op JSON and returning after `rebuild_snapshot_cache` fails.
- No test that `invalidate_cell` leaves `last_snapshot` unchanged when `OpLog::get` fails.
- No microbench asserting the actual indexed lookup complexity; current tests prove index cardinality, not `LoroList::get` cost.
- No `.qbook` round-trip assertion specifically checking the two new index accessors after `from_snapshot`.

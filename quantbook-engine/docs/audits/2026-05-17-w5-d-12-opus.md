# W5-D-12 (Phase 4.10 V1-260 sealer — SUBTOTAL) — Opus audit
**Branch:** `feat/quantbook-engine` (working tree, uncommitted on top of `88075d8da82`)
**Auditor:** Opus 4.7
**Date:** 2026-05-17
**Scope:** SUBTOTAL added as range-aware conditional aggregate; 1 fn, ~28 unit tests, 4 e2e tests, registry bump 259 → 260, coverage entry, matrix update.

## Summary

Three FINDINGS at **HIGH** severity, three at **MEDIUM**, three at **LOW**.

The single most serious finding: **`HIGH-001` — three of the four newly-added e2e tests are FAILING in the working tree** (`e2e_subtotal_sum_range_dispatch`, `e2e_subtotal_average_range_dispatch`, `e2e_subtotal_109_equivalent_to_sum_range`). They were labelled "W5-D-12.1 Codex HIGH-001 closure" in their comments, but the underlying closure is **incomplete** — adding `"SUBTOTAL"` to `is_aggregate_function` is necessary but NOT sufficient. Literal `Expr::RangeRef` is rejected by the binder unconditionally outside `BindContext::ReferenceArg`, including in `BindContext::AggregateArg`. The author was aware of this limitation (workbook_runtime.rs line 11875 explicitly notes `"Literal SUM(A1:A3) over a Range needs aggregate-arg binding which v1 routes via named ranges only"`), yet committed tests that exercise exactly the unsupported path. As a result `cargo test --workspace` fails — this is not a fly-by issue.

Beyond the test breakage, the implementation itself (the unit-level `subtotal` fn) is solid. Dispatch table matches IronCalc 1:1, NaN guard is present and probe-verified, +Inf / -Inf are panic-safe via Rust's saturating cast, all 11 textbook anchors are reproduced exactly via the compiled probe, and the v1 divergences (no hidden-row metadata, no nested-skip) are documented in the module block. The HIGH-002 / HIGH-003 / MEDIUM findings concern coverage / matrix completeness and inherited-semantics divergences from IronCalc canon that are not flagged in the user-visible docs.

## HIGH

### HIGH-001 — Three e2e tests FAIL in the working tree (broken Codex HIGH-001 "closure")

- **Subject:** `e2e_subtotal_sum_range_dispatch`, `e2e_subtotal_average_range_dispatch`, `e2e_subtotal_109_equivalent_to_sum_range`.
- **Where:** `crates/ql-exec/tests/region_mul2_e2e.rs` lines 779-832 (the three tests after `e2e_subtotal_registered`). These are present in the working tree's `git diff` and labelled `"W5-D-12.1 (Codex HIGH-001 closure)"` in their comments. The audit prompt only mentioned `e2e_subtotal_registered`, but the diff contains four e2e tests; the prompt undersells the surface area.
- **Detail:**
  - All three tests call `eval_source_with_registry("SUBTOTAL(9, A1:A3)", …)` or equivalent, where `A1:A3` is a literal `Expr::RangeRef`.
  - `cargo test --workspace`:
    ```
    test e2e_subtotal_sum_range_dispatch ... FAILED
    test e2e_subtotal_average_range_dispatch ... FAILED
    test e2e_subtotal_109_equivalent_to_sum_range ... FAILED
    ```
  - Each panics with:
    ```
    bind: UnsupportedVariant("literal RangeRef in non-Function context is unsupported in v1; use a named range (Phase 2B.4 AggregateNameRef) or wrap in an aggregate function. (Updated W5-108 / Phase 4.7.O; original Phase 0 W4-1 message referenced \"no function dispatch yet\" which has been in place since Phase 2A. W5-RT-1 added literal RangeRef support inside reference-aware fn arg lists only.)")
    ```
  - I verified independently via a compiled probe in `/tmp/probe-subtotal-in` that this is NOT specific to SUBTOTAL — `SUM(A1:A3)` also fails the bind path the same way (only `SUM(A1, A2, A3)` works). `is_aggregate_function` returning true is enough to flip arg context to `BindContext::AggregateArg`, but `crates/ql-exec/src/plan.rs` line 706-731 rejects `Expr::RangeRef` unless the context is `BindContext::ReferenceArg`:
    ```rust
    Expr::RangeRef(rr) => {
        if ctx == BindContext::ReferenceArg {
            let range = resolve_range_ref_to_range(rr, owning_sheet, sheets)?;
            Ok(ExprPlan::RangeRef { range })
        } else {
            Err(BindError::UnsupportedVariant("literal RangeRef in non-Function context …"))
        }
    }
    ```
  - The author SAW this constraint — see `workbook_runtime.rs:11875`:
    > "Literal `SUM(A1:A3)` over a Range needs aggregate-arg binding which v1 routes via named ranges only"
    — and the `plan.rs` BindContext::AggregateArg doc-comment at line 380-383 explicitly defers AggregateArg-side `RangeRef` enabling as a "separate follow-up."
  - Yet `range_fns.rs::subtotal` block comment and the coverage entry both claim the Codex HIGH-001 closure is shipped, and a substantial coverage-entry paragraph references it. The reference is **misleading** — the closure is shipped only at the `is_aggregate_function` admission level, not at the literal-RangeRef lifting level.
  - **The matrix entry marks SUBTOTAL as ✅ shipped.** With the current state of the binder, the most common Excel usage (`=SUBTOTAL(9, A1:A100)`) cannot be authored against the engine. Only `SUBTOTAL(9, A1, A2, A3)` (individual cell args, like the working `SUM` e2e test) and named-range args (`SUBTOTAL(9, SalesRange)` — UNTESTED) can possibly work. **The matrix tick over-represents what's shipped.**
- **Recommendation:**
  1. **Revert the three failing e2e tests** (`e2e_subtotal_sum_range_dispatch`, `e2e_subtotal_average_range_dispatch`, `e2e_subtotal_109_equivalent_to_sum_range`) OR convert them to use `SUBTOTAL(9, A1, A2, A3)` (cell args, not a range) so they pin a path that actually works through `bind`. The single `e2e_subtotal_registered` smoke check is sufficient at the registry-tier level and matches every other range-aware fn in the file.
  2. **Add ONE positive e2e test** using a named range — pattern: register a `NameTarget::Range` via `WorkbookRuntime`, then `set_formula("SUBTOTAL(9, MyRange)")`. This is the ONLY end-to-end path that's actually supposed to work today. Without such a test, there's NO end-to-end coverage for SUBTOTAL.
  3. **Soften the HIGH-001 closure language** in the W5-D-12 module comment and the coverage entry. Replace "Codex HIGH-001 closure" claims with a note that admission to `is_aggregate_function` is in place but AggregateArg-side literal `Expr::RangeRef` lifting is deferred (consistent with the existing `RT-V1` documented gap at `plan.rs:380-383`).
  4. **Soften the matrix entry** — mark as 🟡 / partial, or include a divergence note that literal range args do NOT bind in v1 (named-range workaround required), to match the equivalent reality already noted for SUM and the other aggregates.
- **Severity rationale:** Test failures in a committed change set are the highest signal of incompleteness. The implementation work itself is correct; the framing of "the closure is shipped" is what's broken. A user who reads the matrix and tries `SUBTOTAL(9, A1:A3)` will hit a hard #UNIMPL-equivalent — the most common form of the function does not work, and the docs imply it does.

### HIGH-002 — Coverage entry overclaims & misframes the "Codex HIGH-001 closure"

- **Subject:** `EXPLICITLY_DEFERRED` entry for SUBTOTAL.
- **Where:** `crates/ql-functions/tests/coverage.rs` lines 431-435 (the new SUBTOTAL entry).
- **Detail:** The entry asserts `**W5-D-12.1 (Codex HIGH-001 closure):** admitted to `is_aggregate_function` so range args bind as `AggregateNameRef`; invariant test in `workbook_runtime.rs::is_aggregate_function_lists_only_registered_aggregates` extended to include SUBTOTAL.` — which describes a real, applied change. But the framing implies the literal-range-arg path is also fixed, when in reality it remains broken (see HIGH-001). The matrix entry has the same overclaim with the assertion `**CLOSES Phase 4.10 V1-260 at 260 registered fns**` and `Range-aware`. The label of "closure" is too strong.
- **Recommendation:** Replace the "Codex HIGH-001 closure" framing with: "named-range path enabled via `is_aggregate_function`; literal range-arg lifting (`SUBTOTAL(9, A1:A3)`) is deferred along with the `SUM(A1:A3)` lifting per the documented `plan.rs::AggregateArg` follow-up." Also adjust the coverage entry to call out the v1 divergence from IronCalc canon on:
  - **Text in data → #VALUE! (engine) vs skip (IronCalc/Excel)** — currently the coverage entry says "Inherits text-handling from underlying aggregate (W5-58 strict; engine-wide convention)" but does not mark this as an Excel divergence.
  - **Boolean in data → coerced to 1/0 (engine) vs skip (IronCalc/Excel)** — not mentioned at all in the coverage entry.
  - **Blank scalar data → skip (engine) vs 0.0 (IronCalc subtotal_get_values line 184: `EmptyCell | EmptyArg => result.push(0.0)`)** — engine-IronCalc divergence not noted. Compiled probe: `SUBTOTAL(6 PRODUCT, blank, 5)` returns `Number(5.0)` in engine, would return `Number(0.0)` in IronCalc (because blank pushes 0.0 into PRODUCT, which then multiplies by 5.0 = 0).
  - **PRODUCT of empty range → 0 (engine, via `scalar_fns::product` `total.unwrap_or(0.0)`) vs 1 (IronCalc, multiplicative identity)** — divergence not noted. This is a real correctness divergence. IronCalc's choice is mathematically defensible; engine's choice matches the standalone PRODUCT convention which is itself Excel-canon-divergent.
- **Severity rationale:** Coverage doc is the contract for what V1 ships. Misleading framing here downstream causes integrators to write SUBTOTAL formulas that fail, and audits in subsequent waves will rest on incorrect baselines.

### HIGH-003 — No end-to-end coverage for SUBTOTAL via the only supported path (named ranges)

- **Subject:** Test coverage hole.
- **Where:** `crates/ql-exec/tests/region_mul2_e2e.rs` and `crates/ql-exec/src/workbook_runtime.rs` test modules.
- **Detail:** Of the four e2e tests added, the three positive-path ones FAIL (see HIGH-001), and the fourth (`e2e_subtotal_registered`) is a registry-lookup smoke test only — it confirms the symbol is in the table but doesn't exercise the binder or the dispatch. **There is zero end-to-end evidence that SUBTOTAL actually works for ANY input from the engine boundary.** The closest analogy is the named-range AggregateNameRef path (which IS supposed to work per the binder docs), but no test pins it. Most other range-aware fns (`MIRR`, `TEXTJOIN`, `NPV`, `IRR`, `PERCENTILE`, `QUARTILE`) follow the same registry-only smoke-test pattern — but those each have unit-test coverage that maps directly to a working binder path (cell-args). SUBTOTAL's cell-args path (`SUBTOTAL(9, A1, A2, A3)`) is the only one that works through `bind`, and it is NOT tested e2e.
- **Recommendation:** Add at least ONE positive e2e test that goes through the binder. Two options:
  1. **Cell-args form**: `SUBTOTAL(9, A1, A2, A3)` with values set → expected sum. This pins the dispatch-after-bind path identical to the existing `e2e_sum_function` pattern.
  2. **Named-range form** (preferred but more setup): register a named range pointing to `A1:A3` via `WorkbookRuntime.workbook.names_mut().add_range(...)`, then `SUBTOTAL(9, MyRange)`. This pins the path that actual users will hit when they import an Excel workbook with `SUBTOTAL(9, A:A)` or similar.
- **Severity rationale:** Without an end-to-end test, the implementation could silently regress at the binder/dispatch level (e.g., a registration typo, an `is_aggregate_function` change that drops SUBTOTAL) and the unit tests would still pass. Other fns get away with this because their unit tests + the existing aggregate fns in the file collectively cover the binder path. SUBTOTAL is the first range-aware fn where the unit tests use `FnArg::Range` directly — a path that bypasses the binder entirely.

## MEDIUM

### MEDIUM-001 — IronCalc divergence on Boolean function_num is undocumented but pinned

- **Subject:** `subtotal_boolean_function_num_coerces`.
- **Where:** `crates/ql-functions/src/range_fns.rs` lines 5657-5668. Module comment lines 1956 (the `i64::from(*b)` branch).
- **Detail:** The engine coerces `Boolean(true)` → 1 → AVERAGE and `Boolean(false)` → 0 → #VALUE!. This matches IronCalc (`cast.rs::cast_to_number` lines 155-161: `CalcResult::Boolean(f) => if f { Ok(1.0) } else { Ok(0.0) }`). But **Excel's own canon rejects Boolean function_num: `=SUBTOTAL(TRUE, A1:A4)` returns #VALUE! in Excel.** The engine matches IronCalc here, not Excel. This is fine, but **the coverage entry does not flag this as an Excel divergence**, while it's pinned by a test that locks in the IronCalc-equivalent behavior. A future Excel-canon enforcement pass would need to break this test.
- **Recommendation:** Add a one-line note to the coverage entry: "Boolean function_num coerces (TRUE → 1, FALSE → 0) matching IronCalc; Excel canon rejects Boolean function_num — minor divergence, pinned by test."
- **Severity rationale:** Documented divergence is preferable to undocumented behavior; the test pins a real choice between two reference implementations.

### MEDIUM-002 — Lenient text function_num NOT pinned (IronCalc accepts text "9" → 9.0 → SUM)

- **Subject:** `subtotal_function_num_text_is_value_error`.
- **Where:** `crates/ql-functions/src/range_fns.rs` lines 5605-5612.
- **Detail:** The test uses Text("nine") (unparseable) and pins #VALUE!. It does NOT test Text("9") (parseable text). IronCalc's `cast_to_number` line 147-154 calls `cast_number(&s)` which attempts to parse — `"9"` → `9.0` → SUM dispatch. The engine rejects ALL Text via `to_number_strict` (line 34 of `coercion.rs`: `Value::Text(_) => Err(ErrorValue::Value)`). This is a **real divergence** and the test under-pins it.
- **Recommendation:** Either (a) add a test pinning `SUBTOTAL(Text("9"), …) → #VALUE!` (engine's strict choice) or (b) implement the lenient parse to match IronCalc. The engine has shipped strict text-rejection in many siblings (e.g. T family, RAND, etc.), so option (a) is consistent. Either way, the divergence should be noted in coverage.
- **Severity rationale:** Test-coverage gap on a behavior that diverges from the cited reference.

### MEDIUM-003 — Inherited-semantics gap: scalar_fns::counta vs IronCalc subtotal_counta on Errors

- **Subject:** Behavior of `SUBTOTAL(3, [#VALUE!, 1, 2])`.
- **Where:** Dispatch routes `3` to `scalar_fns::counta`; IronCalc subtotal_counta lines 432-435.
- **Detail:** Both engine `scalar_fns::counta` and IronCalc `subtotal_counta` count errors (engine: `!matches!(v, Value::Blank).count()` includes Error; IronCalc: `String | Number | Boolean | Error => counta += 1`). Behavior matches. **However**, this is NOT pinned by any SUBTOTAL test — the `subtotal_counta_function_num_3` test only covers `[1, "skip", 2, blank, 3]` (no error). A future refactor of `scalar_fns::counta` to skip errors would silently break compatibility with IronCalc + Excel canon (Excel COUNTA does count errors) and the engine-wide aggregate convention. Probe-verified: `SUBTOTAL(3, [1, #DIV/0!, 3]) = ?`. **Not tested** in the new SUBTOTAL block (probe-confirmed = 3.0 — passes through to counta which counts the error).
- **Recommendation:** Add one test pinning COUNTA's error-counting behavior under SUBTOTAL dispatch: `SUBTOTAL(3, [1, #DIV/0!, 3]) → 3.0`. Similarly for COUNT (1.0 — error skipped, not propagated) and AVG/SUM (error propagated): there are partial pins via `subtotal_error_in_data_propagates_via_dispatched_kernel` (only the SUM path is tested), but the divergent behavior of different routes under the SAME error condition is not enumerated.
- **Severity rationale:** The dispatch table is the entire point of SUBTOTAL — tests should cover the matrix of (fn_num × data semantics) more fully. The probe I ran confirms the current behavior IS correct, but tests don't pin it.

### LOW-002 — NaN-guard comment overclaims "panic-safety"

- **Subject:** Block comment at `range_fns.rs:1929-1933` and test comment at lines 5589-5602.
- **Where:** SUBTOTAL module block (`crates/ql-functions/src/range_fns.rs`) + `subtotal_function_num_nan_is_num_error` test.
- **Detail:** Both comments frame the `is_nan()` guard as "panic-safety". But Rust ≥1.45's saturating-cast semantics make `NaN.trunc() as i64 = 0` — fully panic-safe without the guard. The guard's actual purpose is **error-code consistency**: emit `#NUM!` (the engine's NaN-from-explicit-NaN convention) rather than letting NaN fall to the `_` arm and surface as `#VALUE!`. The test comment partially acknowledges this on line 5594-5597 but the framing as "panic-safety" persists in the module block and the in-fn comment. This is a minor doc-overclaim; the guard is correct, just not for the stated reason.
- **Recommendation:** Re-frame the guard's purpose as "explicit error-code propagation for NaN function_num — without this guard NaN falls to the `_` arm and surfaces as `#VALUE!` rather than the engine's NaN-input `#NUM!` convention."
- **Severity rationale:** Documentation accuracy; behavior is correct.

## What works

- Unit-level `subtotal(args: &[FnArg])` is correct, panic-safe, and matches IronCalc dispatch shape exactly.
- Boolean / Blank / Error / NaN / ±Inf function_num all rejected without panic; error codes match documented choices.
- Textbook STDEV/VAR anchors reproduce exactly.
- Module block clearly documents the two v1 divergences (no hidden-row metadata; no nested-skip).
- IronCalc cross-reference is precise (file + line range cited).
- 28 unit tests all green; 1796 ql-functions tests all green.
- The `is_aggregate_function` admission + invariant test extension are correctly applied (the partial closure does work for the named-range path, even if literal `A1:A3` is not yet lifted).

## What fails

- **3 of 4 newly-committed e2e tests FAIL in the working tree** — they cannot have been run by the author before "closure" was claimed (see HIGH-001).
- Matrix marks SUBTOTAL ✅ shipped, but the most common Excel usage (literal range arg `A1:A100`) does not bind, with no documentation acknowledging this gap.

## Recommended fix sequence

1. **First**: Revert OR rewrite the 3 failing e2e tests to use a path that actually binds (cell-args list, OR named-range setup via WorkbookRuntime). Re-run `cargo test --workspace` to a clean green.
2. **Next**: Soften the "Codex HIGH-001 closure" framing in the module block + coverage entry + matrix entry. Add the deferred-AggregateArg-RangeRef-lifting follow-up note.
3. **Then**: Add the divergence notes for blank-scalar-as-data, Boolean-in-data, text-in-data, and PRODUCT-empty-→-0 to the coverage entry.
4. **Finally**: Fix the test-count in the matrix (25 → final).

Once the above are addressed I'd recommend a second Codex pass to verify the closure is now actually shipped — the original Codex HIGH-001 callout that admitted SUBTOTAL to `is_aggregate_function` is the right direction, but the closure as committed isn't fully wired to the binder.

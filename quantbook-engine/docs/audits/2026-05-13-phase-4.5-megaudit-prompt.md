## Specific concerns to challenge

### CONCERN-A: 1900 leap-year bug correctness (W5-70 ql-types::date)

The serial-60 contract is pinned by tests, but verify the implementation:

1. **`serial_to_ymd(60.0, Excel1900)`** returns `(1900, 2, 29)` — phantom day. Test `serial_60_is_phantom_feb_29_1900_in_excel1900`.
2. **`serial_to_ymd(60.0, Excel1904)`** returns `(1904, 3, 1)` — real date.
3. **`ymd_to_serial(1900, 2, 29, Excel1900)`** returns `60.0`.
4. **`ymd_to_serial(1900, 3, 1, Excel1900)`** returns `61.0` — phantom-skip boundary.
5. **`serial_to_ymd(0.0, Excel1900)`** returns `#NUM!` — the "1/0/1900" oddity per W5-68 § 3.3 + Codex LOW 1.
6. **`serial_to_ymd(0.0, Excel1904)`** returns `(1904, 1, 1)` — legitimate epoch (W5-70 correction to the design doc).

The mid-implementation correction (1904 serial 0 = real epoch, not universal `#NUM!`) — is this consistent across all date functions? Specifically:
- `YEAR(0)` in 1904-system: should return 1904 (via `serial_to_ymd`). Verify.
- `DATEVALUE("1904-01-01")` in 1904-system: should produce serial 0, not #NUM!.
- `EOMONTH(0, 0)` in 1904-system: should return last of Jan 1904.

### CONCERN-B: EvalContext threading completeness (W5-69)

The `ContextAwareFn` tier was introduced with `CellEnv::eval_context()` default impl returning `&DEFAULT_EVAL_CONTEXT`. `WorkbookEnv` overrides this. Verify:

1. **Dispatch order**: `eval_scalar_with_cache` checks range_aware FIRST, context_aware SECOND, scalar LAST. If a name lands in two tables by mistake, which wins? (Registry should panic at registration, but verify the runtime fallback.)
2. **Test envs**: `MapEnv` and any benchmark env — do they use the default context? When a test calls `=DATE(2024,1,1)` against MapEnv, does it correctly route through context_aware and get Excel1900 semantics?
3. **WorkbookEnv lifetime**: `WorkbookEnv::eval_ctx` is cached at construction. If the workbook's `date_system` changes mid-session (via `set_date_system`), the cached env is stale. Is this a real risk, or is `set_date_system` only ever called pre-load?
4. **Transaction path**: `crates/ql-exec/src/transaction.rs` calls `eval_scalar_with_registry` (line 377 per earlier grep). Does that path correctly use a workbook-backed env, or could it use MapEnv-equivalent and miss the date_system?

### CONCERN-C: Schema migration correctness (W5-71)

v2 envelopes without `date_system` field load as Excel1900 (default-on-missing). Verify:

1. **Round-trip integrity**: a workbook saved with Excel1904 reads back as Excel1904. Test `date_system_excel1904_round_trips` covers this.
2. **Replay determinism**: existing op logs from v2 binaries don't carry `Op::SetWorkbookDateSystem` (the design § 7.3 proposed it but W5-71 didn't ship it). Does this break replay if a workbook's date_system changes between saves? (Likely not — `date_system` is workbook-static, not op-log-tracked. But verify.)
3. **`future_schema_version_rejected` test was bumped from v3 to v4** when v3 became current. Is the test still valid as a forward-compat guard?

### CONCERN-D: NOW/TODAY upgrade semantics (W5-71)

Pre-W5-71: `now()` returned `(secs / 86400) + 25569` — flat UTC offset.
Post-W5-71: `now_ctx()` reads `ctx.now_provider`, applies UTC offset, converts via `unix_days_to_ymd` + `ymd_to_serial`.

1. **`set_test_now_secs` override**: still works, per `now_ctx_test_override_via_thread_local_takes_precedence`. But what about the BEHAVIOR change — if a test set `unix_secs = 0` expecting `25569.0`, does both the old and new path return 25569? (Yes, because Excel1900 with offset 0 gives the same serial via either path. But verify edge case: 1904-system test setting `unix_secs = 0` would expect 24107, not 25569.)
2. **GAP-T-01 timezone offset**: the V1 `NowProvider::System` returns offset 0 (placeholder until `iana_time_zone` lands). So in production, NOW() currently returns UTC-equivalent serial — same as pre-W5-71. This is a regression-neutral state. Confirm.
3. **WASM target**: `SystemTime::now()` panics on `wasm32-unknown-unknown`. The W5-69 design said WASM needs a host callback. Has W5-71 ensured the panic path is unreachable in WASM builds? (Probably not — no conditional compilation has been added yet.)
4. **Legacy `volatile::now` / `volatile::today` still in source**: dead code as far as formula dispatch goes (they're not in the registry). Does anything else call them? (gh grep for `volatile::now\|volatile::today` excluding tests.)

### CONCERN-E: DATE cascade correctness (W5-72)

DATE uses serial-arithmetic cascade (not unix-days) so the Excel1900 phantom is correctly handled. Verify:

1. **DATE(1900, 1, 60) = 60**: Jan 1 + 59 days lands on phantom Feb 29.
2. **DATE(1900, 2, 29) = 60**: direct phantom.
3. **DATE(1900, 3, 1) = 61**: skips phantom.
4. **DATE(2024, 13, 1) = DATE(2025, 1, 1)**: month overflow.
5. **DATE(2024, 0, 5) = DATE(2023, 12, 5)**: month underflow.
6. **DATE(2024, -1, 5) = DATE(2023, 11, 5)**: negative month.
7. **DATE(50, 1, 1) = DATE(1950, 1, 1)**: 2-digit year.
8. **DATE(1899, 1, 1) = DATE(3799, 1, 1)** (year 1899 + 1900) — valid serial. (W5-72 originally tested this as #NUM!; corrected.)

Edge: what about `DATE(1900, 1, 0)`? Per Excel canon, day 0 cascades to Dec 31 of previous year — so DATE(1900, 1, 0) = DATE(1899, 12, 31) which is out of range → #NUM!.

### CONCERN-F: Weekday algorithm bug-awareness (W5-73 WEEKDAY)

WEEKDAY uses the direct serial formula `(serial - 1) % 7` for Excel1900 (serial 1 = Sunday). Verify:

1. **WEEKDAY(1, 1) = 1 (Sunday)** in Excel1900. Pinned by `weekday_default_return_type_1_serial_1_is_sunday`.
2. **WEEKDAY(60, 1)** — the phantom. Per the algorithm: `(60 - 1) % 7 = 59 % 7 = 3 → Sunday+3 = Wednesday = 4`. Is this what Excel returns? (Microsoft canon may say Wednesday OR Tuesday depending on source — verify empirically.)
3. **WEEKDAY(0, 1, Excel1904)** — the 1904 epoch (1904-01-01). Per algorithm: `(0 + 5) % 7 + 1 = 6 → Friday`. Real Gregorian: 1904-01-01 was Friday. ✓
4. **WEEKDAY return_type 11-17**: the anchor-shift math. `n=12 anchor = 1 (Tue)`; verify with concrete examples.

### CONCERN-G: Date text parsing scope (W5-73 DATEVALUE)

V1 en-US scope. Accepts ISO `YYYY-MM-DD` and US slash `M/D/YYYY`. Rejects everything else. Verify:

1. **Locale parsing**: a German-localized xlsx might have dates like `15.01.2024` (dots). V1 rejects. Phase 4.9 will handle. Documented?
2. **2-digit year split**: 00-29 → 2000s, 30-99 → 1900s. Excel canon's specific cut-off is 30 (Excel says "0-29 are 21st century, 30-99 are 20th century"). Verify.
3. **Month-name parsing**: `DATEVALUE("January 15, 2024")` — Excel accepts this. V1 doesn't. Documented divergence?
4. **Phantom edge**: `DATEVALUE("1900-02-29")` in Excel1900 returns 60. Pinned.
5. **Leading/trailing whitespace**: the parser trims. What about leading/trailing `,` or other punctuation? (V1 likely rejects.)

### CONCERN-I: YEARFRAC accuracy (W5-74 + W5-75 DAYS360)

YEARFRAC basis 0 falls through to basis 4 (European 30/360). GAP-F-11 documents this. But DAYS360 (W5-75) ALSO implements US NASD (basis 0 equivalent) WITH the day-31 adjustment. Are these inconsistent?

1. **Verify DAYS360 implements proper US NASD** (modulo the Feb-29 special-case which is the bigger hole in the algorithm).
2. **YEARFRAC basis 0 calls European 30/360** — DOES THIS MATCH WHAT DAYS360 (FALSE method) RETURNS? It probably does NOT — DAYS360 has the day-31 → 30 adjustment, YEARFRAC basis 0 doesn't. So `YEARFRAC(s, e, 0)` and `DAYS360(s, e) / 360` differ on dates where the day-31 adjustment matters.

This is an internal-inconsistency bug. Suspicious — verify.

### CONCERN-J: Test fixture realism (across all date fn waves)

2. **WEEKNUM(2024-01-01, 1) = 1**: pinned. Verify real-world dates land in the expected weeks.

4. **NETWORKDAYS sanity**: 2024-01-01 (Mon) to 2024-01-05 (Fri) — pinned as 5 working days. Manually verify by walking the dates.

## What to look for — classes of problems

### Correctness

1. **Per-fn impl vs design § 5.6 pseudo-code:** verify each impl matches the design pseudo-code's semantics exactly. ROW with 0 args → calling cell + 1 (or `#REF!`); ROW with Range arg → `start_row + 1`; ROW with Array arg → `#VALUE!` (NOT array-spill — that's deferred); arity > 1 → `#N/A`.
2. **1-indexed vs 0-indexed conversion:** `RowId` / `ColId` are `u32` 0-indexed. Each impl adds `+ 1.0` when producing Excel-output. Verify ALL arithmetic sites.
3. **`u32` subtraction overflow:** ROWS computes `end_row - start_row + 1`. If a hand-constructed `Range` had `end_row < start_row` (binder normalizes via `Range::new`'s min/max, but still), the subtraction would underflow. Verify the binder's `Range::new` normalization is bulletproof; consider whether the impl should defensively saturate.
4. **Microsoft canon divergences:**
   - `ROW(SUM(A1:A3))` — Microsoft canon: in legacy Excel, `SUM` does not return a reference; ROW would `#VALUE!`. Our `materialize_ref_arg_eager` evaluates SUM eagerly, producing `Scalar(value)` → `#VALUE!` from the per-fn Scalar arm. ✓
   - `ROW(IF(TRUE, A1, B1))` — Excel: IF can return a reference; ROW would return 1. v1: no reference-returning fns → `Scalar(value)` → `#VALUE!`. Documented divergence.
   - `ROW({1,2,3})` — Excel-365: spills `{1;1;1}` (each cell's row from the array's row context). v1: `#VALUE!`. Documented?
   - `ROW(A1:A5)` at cell boundary — Excel-365: spills `{1;2;3;4;5}`. v1: `#CALC!` per HIGH-E. Documented.
5. **Error class choices:** non-reference args → `#VALUE!`; multi-arg → `#N/A`; missing arg for ROWS/COLUMNS → `#N/A`; `#REF!` arg → propagates. Verify against IronCalc.
6. **`MAX_ROW` / `MAX_COLUMN` math:** `ROWS(A:A) = MAX_ROW + 1 = 1_048_576`. `COLUMNS(1:1) = MAX_COLUMN + 1 = 16_384`. Verify the math sites give the right answers.

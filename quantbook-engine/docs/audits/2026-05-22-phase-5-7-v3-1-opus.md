## Section 1 — Per-target walks

### A. `crates/ql-collab-ws/examples/relay-server.rs` (V3.1.a)

**Walk (line by line through `main` + `handle_connection`):**

1. **Port resolution (lines 54–57)** — `env::var("QL_RELAY_PORT").ok().and_then(|s| s.parse().ok()).unwrap_or(DEFAULT_PORT)`. If the env var is set but garbage (e.g., `QL_RELAY_PORT=abc`), `.parse().ok()` returns `None` and the default `7117` silently takes over. **Borderline against the global no-fallback rule**: a malformed env var is silently masked. Acceptable for a demo binary (the next line will fail visibly if 7117 is taken), but flagged as LOW since the V3.2 cell-grid relay/server will likely promote this binary into a more visible code path.

2. **bind (lines 59–61)** — `TcpListener::bind(addr).await?` propagates `Err` upward; `main` returns `Err(Box<dyn Error>)`. Tokio prints to stderr and exits non-zero — IDE's `spawnRelayBinary` catches via the `exit` event. **OK.**

3. **stdout readiness marker (lines 63–65)** — `println!("[ql-collab-ws relay] listening on ws://{bound}")`. The format string concatenates `bound`'s `Debug` impl (i.e., includes the port). The IDE side reads `[ql-collab-ws relay] listening on` as a prefix-match, so the format is stable. **OK.**

4. **broadcast channel construction (line 68)** — `broadcast::channel::<(usize, Vec<u8>)>(BROADCAST_BUFFER)`. The `_initial_rx` is dropped immediately; this is FINE for `tokio::sync::broadcast` because the channel keeps the `Sender` alive and new subscribers via `.subscribe()` get fresh receivers. The lagged-frame contract is captured in the docstring. **OK.** Capacity is 256 **frames** (tuples), not bytes — verified by the channel signature `<(usize, Vec<u8>)>`. The audit prompt's "256 frames not bytes" cross-check **passes**.

5. **AtomicUsize counter (lines 69, 79)** — `next_conn_id.fetch_add(1, Ordering::Relaxed)` returns the prior value then increments. Wrap behavior on `usize::MAX + 1`: on 64-bit targets this is 2^64 - 1 wraps, ≈ unreachable in any realistic relay lifetime. On 32-bit targets (`usize == u32`), 4.3 billion connections wraps to 0; a wraparound collides the next conn_id with conn_id 0 (still alive in the broadcast filter). Since conn_id 0's per-conn task may still be subscribed, the wrap would break the self-filter for whichever client matches. **In practice unreachable for a demo binary.** Flagged as LOW for completeness (no 32-bit target is currently supported, but the dev-path includes Windows which historically had 32-bit builds).

6. **accept loop error path (lines 71–78)** — `match listener.accept().await { Err(e) => { eprintln!(...); continue; } }`. This is a fallback that masks the underlying error and keeps the loop running. Per the global no-fallback rule the LOG-then-continue pattern is exactly the kind of silent-degradation we forbid. **However, in this context** the surface is a stateless localhost relay; `accept()` errors are typically transient (`EMFILE` if the OS runs out of fds — relay survives by waiting for clients to disconnect; or `ECONNABORTED` — irrelevant). Stopping the loop on every accept error would crash the demo entirely. The pattern is contextually defensible but worth a docstring callout. Flagged as **LOW (advisory)**.

7. **`handle_connection` (lines 96–157):**
   - `ws = accept_async(stream).await?` — propagates the handshake error up to the spawn task's `Err` arm at line 85. The error is logged but the per-conn task exits cleanly. **OK.**
   - `(mut ws_sink, mut ws_stream) = ws.split()` — `StreamExt::split` returns two halves; the underlying `tokio_tungstenite::WebSocketStream` is wrapped in a futures `BiLock`. Both halves are `Send + Sync`. **OK.**
   - `let read_tx = broadcast_tx.clone()` — `broadcast::Sender` is `Clone + Send + Sync`. **OK.**
   - **Read half (lines 108–127):** The `while let Some(msg)` loop reads `ws_stream.next().await`. On `Ok(Message::Binary(b))`: `let _ = read_tx.send((conn_id, bytes))`. **Ignoring the send result is intentional and correct** — `broadcast::Sender::send` returns `Err(SendError)` ONLY when ALL receivers have been dropped, which happens transiently between connections; the docstring explicitly addresses this. **OK.**
   - **Hypothetical panic case (audit prompt):** What if `ws_stream.next().await` panics (e.g., tokio runtime OOM during a `Vec` allocation in the underlying reader)? The `async move` block is awaited inside a `tokio::select!`; per the Tokio docs, a panic in one branch is propagated out of `select!` to the surrounding task. The surrounding task is `tokio::spawn(async move { match handle_connection(...).await { ... } })` at line 82-87. A panic inside `handle_connection`'s read future would unwind through `select!` → `handle_connection` → the `tokio::spawn`'d task. tokio's default `JoinHandle` discards panics unless `.await`-ed; the spawn at line 82 does NOT `.await` the join handle, so the panic is silently absorbed. **The OTHER per-conn tasks are independent `tokio::spawn`s and keep running**; the broadcast channel's `Sender` is alive in `main`'s scope. The panicked client's per-conn task is dead, its read half stops, the write half's `recv` will eventually error or be dropped by `select!` on the other branch. **Verdict: panic isolation works.** Flagged as no-finding; documented for V3.2's confidence.
   - **Write half (lines 131–147):** `broadcast_rx.recv().await` returns `Lagged(n)` if the client lags; the loop `continue`s and the next `recv()` gets the freshest frame. Per the docstring, accepted because CRDT is idempotent on re-merge. **OK.**
   - `ws_sink.send(Message::Binary(bytes.into())).await.is_err() { break }` — if the sink errors (peer closed unexpectedly), the write half exits. `tokio::select!` then drops the read half. **OK.**
   - `select! { _ = read => {}, _ = write => {}, }` — whichever finishes first wins; the OTHER branch is dropped (cancelled). **`tokio::select!` cancel safety**: `ws_stream.next()` is cancel-safe (futures-util's `Next` is by-reference and re-pollable). `broadcast::Receiver::recv()` is cancel-safe. **OK.** No partial-state hazards from cancellation.

8. **Task lifecycle on SIGTERM (audit prompt):** the binary's `main` doesn't install signal handlers; SIGTERM kills the tokio runtime, which aborts all spawned tasks. tokio's `JoinHandle::abort()` on per-conn tasks drops the futures, which in turn drops the `WebSocketStream` (closing the underlying `TcpStream`'s file descriptor). **No fd leak under normal SIGTERM**. The accept loop is exited because the runtime is gone. **OK.** This is a demo binary — production would want a graceful-shutdown signal handler that drains pending broadcasts before exit. Flagged in Section 3 as a V3.2-deferral note.

9. **`Result<(), Box<dyn std::error::Error + Send + Sync>>` (line 100)** — `Send + Sync` on the error type means handler errors can cross thread boundaries; consistent with `tokio::spawn`'s `+ Send` bound. **OK.**

**Verdict:** PASS. No HIGH, 0 MEDIUM, 2 LOW (env-var silent-default + accept-loop log-then-continue). Demo-scope quality is appropriate.

6. **Three-client fan-out (lines 152–190):** A sends `from-A`, B sends `from-B`, C reads. The `seen.sort()` + `expected.sort()` correctly avoids order-dependency. **OK.**

**Verdict:** PASS-WITH-FINDINGS. 0 HIGH, 0 MEDIUM, 1 LOW (50ms readiness window may be tight on extreme CI). Twin drift surface is documented in the test file's header — acceptable.

### C. `extensions/quantlab/src/quantbook/multiWindowDemo.ts` (V3.1.b + V3.1.c)

This is the largest single piece of new code; walked in detail.

#### C.1 `spawnRelayBinary` (lines 83–176)

1. **`childProcess.spawn` env (line 89)** — `env: { ...process.env, QL_RELAY_PORT: String(RELAY_PORT) }`. Forwards the parent's env to the relay (so cargo finds the workspace if the binary is `cargo run`'d). **OK.**

2. **`stdio: ['ignore', 'pipe', 'pipe']`** — stdin closed, stdout + stderr piped. Listeners attached below. **OK.**

3. **`child.once('error', onSpawnError)` + `child.once('exit', onExit)` (lines 121–122)** — BOTH listeners can fire. Audit prompt asks: what if both fire (binary crashes during spawn)?
   - **Node's child_process semantics:** `'error'` fires for spawn failure (binary not found, EACCES, etc.); `'exit'` fires when the child process terminates. If `'error'` fires, `'exit'` usually does NOT (the child never ran). However, edge cases like ENOENT-on-spawn-followed-by-stale-exit-of-zombie are possible.
   - **Both onSpawnError and onExit guard `if (resolved) return; resolved = true;`** — the second-firing handler short-circuits. **No double-resolve risk.** **OK.**

4. **`setTimeout(() => { ... }, 5000)` (lines 163–174)** — the audit prompt asks if this is cleared on success. Answer: **NO** — the timer is NOT cleared. **However**, when it fires post-success, `if (!resolved)` is false (resolved was set to `true` on the readiness marker) and the timer's callback is a no-op. **The timer holds a Node event-loop refcount for up to 5s after success**, which is a minor non-leak — the timer fires once and is discarded. Flagged as **LOW (cosmetic; cleanup hygiene)**. Best practice would be to capture the `setTimeout` return value and call `clearTimeout` in the success branch.

5. **Cold-start time (audit prompt):** the relay binary is a small release-mode tokio binary. Local measurement: <100ms to bind on a warm system. **Cold antivirus scan or first-spawn-after-build** could exceed 5s on Windows with Defender real-time scanning enabled. **Flagged as MEDIUM** — the 5s timeout is borderline for Windows. macOS/Linux are fine. Recommend bumping to 10s OR making the timeout configurable via env var.

6. **`stdout.on('data', ...)` line-buffered scan (lines 133–147):** `buffer += chunk; const lines = buffer.split('\n'); buffer = lines.pop() ?? ''`. This handles partial lines correctly (last incomplete line stays in `buffer`). The `readyMarker` is matched via `startsWith`. **OK.**

7. **`stderr.on('data', ...)` (lines 149–158):** logs every stderr line to the output channel. Unbounded — if the relay spams stderr (e.g., dropped frames during disconnect storms), the output channel buffer grows. VS Code's `OutputChannel` does NOT cap line count internally; very-long-running demos could OOM the renderer process. **Flagged as LOW** for demo scope; **promoted to MEDIUM if V3.2 cell-grid promotes this to a production code path.** Reasonable mitigation: rate-limit stderr forwarding or cap at first 1000 lines.

8. **Stdout pipe is null path (lines 126–130):** if `child.stdout === null` (theoretically possible if stdio config is wrong), the promise rejects. Defensive. **OK.**

#### C.2 `connectOrSpawn` (lines 185–211)

1. **Race condition: both windows attempt to spawn (audit prompt):**
   - Window A and Window B both call `connectOrSpawn` concurrently. Both first try `engine.Transport.websocketConnect(RELAY_URL)` (line 194). If NO relay is up, both connects fail with `websocket_connect_failed`. Both then call `resolveRelayBinaryPath()` + `spawnRelayBinary(...)`.
   - **The OS's TCP `bind(127.0.0.1:7117)` is mutex'd by the kernel** — exactly ONE of the two relay processes will bind successfully. The OTHER will fail with `EADDRINUSE`. That failing process exits with non-zero; its `spawnRelayBinary` rejects with `[relay] binary exited before readiness ...` because the `'exit'` handler fires before the readiness marker.
   - **B's `spawnRelayBinary` promise rejects.** B's outer `connectOrSpawn` does NOT catch this rejection; it propagates up to `runMultiWindowDemo`'s caller (the command handler in `quantbookCommands.ts`), which catches and shows `FATAL multi-window demo error: ...`.
   - **This is a real UX bug.** The user sees an error in window B that says "the relay binary exited before readiness" when actually A's binary started fine and the user just needs B to try `connectOrSpawn` once more.
   - **Flagged as MEDIUM** — race-condition UX hazard. Mitigation: catch the spawn failure in `connectOrSpawn`'s second branch and re-try the initial `Transport.websocketConnect(RELAY_URL)` (now A's relay is up). The current code does not.

2. **`spawnedRelay.exitCode === null` check in `dispose` (line 315):** the audit prompt asks: what if the relay crashed BETWEEN connect and dispose? Then `exitCode !== null` and dispose skips the kill (intentional — process is already dead). The `child.kill()` would be a no-op anyway since it sends SIGTERM to a non-existent PID; the OS returns ESRCH. The check is correct optimization. **OK.**

#### C.3 `reconnectWithBackoff` (lines 223–245)

1. **Backoff multiplier:** `backoff *= 2` doubles each attempt. Attempts at 500ms / 1000ms / 2000ms. **Total wait before exhaustion = 500 + 1000 + 2000 = 3500ms** = 3.5s. Audit prompt asks to document this as the max time before the user sees the Restart Demo prompt. Confirmed in the documentation at `docs/architecture/ide-consumer-contract.md § 4.1.y`. **OK.**

2. **`await new Promise(r => setTimeout(r, backoff))` (line 230)** — not cancellable. If `dispose()` runs DURING this sleep, the sleep continues to completion, then the `Transport.websocketConnect` runs, then `if (isDisposed) return` (in `handleTransportClosed`) catches the late return. **The orphaned Transport (returned by `websocketConnect`) is dropped on the floor** — see C.4 §3 below for the napi Transport Drop semantics.

3. **Error throw on exhaustion** — `throw new Error('[reconnect] gave up after ${MAX_RECONNECT_TRIES} ...')`. The throw is caught in `handleTransportClosed`'s `catch (err) { ... }` (line 342). **OK.**

#### C.4 `runMultiWindowDemo` (lines 254–407)

1. **PeerId = BigInt(process.pid) (line 259):** The audit prompt asks what happens if `process.pid === 0`. On Linux/macOS/Windows, `process.pid` is the OS-assigned PID; **PID 0 is reserved (Linux: idle task; macOS: kernel; Windows: System Idle Process)**, no user-space process has PID 0. Node.js's `process.pid` for a user-space VS Code render process returns a positive integer. **Defensively unreachable.** **However**, the napi binding's `peer_id_from_bigint` helper at `crates/ql-bindings-node/src/lib.rs:227` explicitly rejects PeerId 0 with `bad_argument` (NOT an `assert_ne!` abort — the V1 audit closure already fixed that). So even if `process.pid` were 0 hypothetically, the JS-side `new engine.CollabSession(0n)` would throw a clean `bad_argument` error. **PASS — assert path is unreachable AND the napi layer is hardened.**

2. **Row = pid & 0xffff (line 278) collision rate:** PIDs are sequential on Linux up to `/proc/sys/kernel/pid_max` (default 4194304 = 2^22). Two windows with PIDs `0x10001` (65537) and `0x00001` (1) collide on `row = 1`. On a system with PID rollover, this is realistic over a long demo session. Two-window collision probability is roughly 1/65536 if PIDs are uniformly random over the low 16 bits — small but not vanishing. macOS has lower PID limits (historically up to ~99999) so the low-16-bits coverage is better there.
   - **Impact of collision:** both windows write to (sheet=0, row=N, col=0). Loro's CRDT merges last-writer-wins per (peer, lamport) — both windows' edits commit, neither is lost. The visual signal is degraded (the user sees one cell flicker instead of two distinct cells) but data integrity is preserved. **OK for a demo.**
   - **Flagged as LOW** — collision-induced visual confusion. V3.2 cell-grid should use a deterministic-from-peerId row mapping (e.g., row = peerId.toString().slice(0, 8) hashed) or pre-allocate non-overlapping rows.

3. **`handleTransportClosed` disposed-mid-reconnect guard (lines 324–363):** the audit prompt asks about the `await reconnectWithBackoff` → `if (isDisposed) return` flow.
   - The `await reconnectWithBackoff(...)` resolves to a `fresh` Transport. If `dispose()` was called DURING the await, the subsequent `if (isDisposed) return` (line 336–339) skips `session.attachTransport(fresh)`. **The `fresh` Transport variable goes out of scope** at the end of the `try` block.
   - **napi Transport Drop semantics:** the napi-rs `Transport` wrapper holds a `Box<dyn Transport>` containing either a `LoopbackTransport` (zero-cost) or a `WebSocketTransport`. `WebSocketTransport::drop` (per `crates/ql-collab-ws/src/lib.rs` Drop impl) calls `notify_all` and the writer/reader tokio tasks observe the shutdown signal via `tokio::sync::Notify`. The underlying `TcpStream` is closed when its `WebSocketStream` is dropped. **No leak**, but the cleanup is **asynchronous** — the tokio tasks may not have fully exited by the time the JS-side `fresh` is GC'd. For a demo this is fine; for V3.2 this is worth a per-field walk if grid teardown becomes performance-sensitive.
   - **OK** for V3.1.

4. **Timer-tick guards (lines 366, 383):** `if (reconnectInFlight || isDisposed) { return; }`. The early-return prevents any session method call during reconnect OR after dispose. **Order matters**: the check is short-circuit (JavaScript `||`), so if `reconnectInFlight === true`, `isDisposed` is not evaluated — but both being true is harmless. **OK.**

5. **`reconnectInFlight` is set to `true` BEFORE the await (line 328) but reset in `finally` (line 361):** Concurrent timer ticks during reconnect get blocked by the guard. **No re-entrancy.** **OK.**

6. **Restart Demo command re-invoke (line 358):** `void vscode.commands.executeCommand('quantlab.quantbookDemoMultiWindow')` triggers the registered command. The fresh invocation creates a NEW disposable. **The OLD disposable** (already disposed in the exhaustion branch at line 349) is still in `context.subscriptions` array — VS Code calls `dispose()` again on extension deactivation, which short-circuits via `isDisposed` guard. **No double-cleanup.** **OK.**

7. **Spawned relay `'exit'` listener (lines 400–404):** logs but does not trigger reconnect. **If the relay crashes mid-session**, the session's transport will see `transport_closed` on the next operation, which DOES trigger `handleTransportClosed`, which will fail all 3 reconnects (port still closed because relay is dead), which prompts Restart Demo. **The chain works, but is slow (3.5s + user click)**. V3.2 could add a faster-path "relay died, restart immediately" via this listener. Flagged as **LOW (UX latency)**.

**Verdict:** PASS-WITH-FINDINGS. 0 HIGH, 2 MEDIUM (cold-spawn timeout for Windows; both-windows-race-spawn UX), several LOWs documented above.

**MEDIUM-1 — `spawnRelayBinary` 5s timeout is borderline for Windows cold-spawn under Defender real-time scanning.** *(Target C.1 §5.)*

The relay binary takes <100ms to bind under normal conditions. Windows Defender real-time scanning on the first spawn after a fresh `cargo build` can introduce multi-second latency. - Make the timeout configurable via env var `QUANTBOOK_RELAY_SPAWN_TIMEOUT_MS`.
- Detect Windows platform and adjust automatically.

**MEDIUM-2 — `connectOrSpawn` race: when both windows attempt to spawn concurrently, one fails with EADDRINUSE and the user sees a confusing FATAL error.** *(Target C.2 §1.)*

Two VS Code windows invoking the demo concurrently both fail the initial `Transport.websocketConnect` (no relay up), both call `spawnRelayBinary`. The OS gives the bind to one process; the other exits with non-zero. The losing window surfaces `[relay] binary exited before readiness (code=1, ...)` to the user, instead of recovering by re-trying the initial connect (which would succeed against the winning window's relay).

**Remediation:** in `connectOrSpawn`'s `spawnRelayBinary` rejection handler, catch the `binary exited before readiness` error specifically and re-try `engine.Transport.websocketConnect(RELAY_URL)` once. If THAT also fails, surface the original error.

```ts
try {
    const spawnedRelay = await spawnRelayBinary(log, binaryPath);
    const transport = await engine.Transport.websocketConnect(RELAY_URL);
    return { transport, spawnedRelay };
} catch (spawnErr) {
    // Race: another window may have won the bind. Retry the connect.
    try {
        const transport = await engine.Transport.websocketConnect(RELAY_URL);
        log.appendLine(`[connect] joined relay spawned by another window`);
        return { transport, spawnedRelay: undefined };
    } catch {
        // Fall through to the original spawn error.
        throw spawnErr;
    }
}
```

Severity: MEDIUM because the demo's marketing claim is "open two windows and they sync"; if the user follows the OutputChannel instruction literally (open window 2 quickly), this race is real.

## Section 3 — V3.2 ENTRY READINESS

V3.2 = cell-grid UI. The next V3 sub-step lifts the demo patterns into a real grid widget. This section captures what carries forward, what does NOT scale, and what risks need to be tracked.

### 3.1 Patterns from V3.1 that carry forward

1. **PeerId = `BigInt(process.pid)`** — solid. Each render process has a unique PID; V3.2 grid widget can keep this. **CARRY.**

2. **Symmetric try-connect-first orchestration** (each window tries to join, spawns if needed) — works for the multi-window demo where relay lifecycle is transient. **PARTIAL CARRY.** V3.2 production grid likely wants a persistent shared service (LaunchAgent / systemd unit / Docker service), in which case "try-connect-first" stays but spawn-on-failure becomes "show 'service unavailable' diagnostic + offer to start" rather than spawning a child process.

3. **`reconnectWithBackoff` (500/1000/2000ms × 3)** — pattern is solid; the magic numbers are tuned for localhost demo. V3.2 grid widget will:
   - Want longer/configurable backoff for WAN (V3.x backlog item per `docs/architecture/ide-consumer-contract.md` § 4.1.y "drift hazards").
   - Want JITTER to avoid thundering-herd on multi-window reconnect against a real server.
   - Want indefinite retry on user request ("Keep trying" button).
   - **CARRY the PATTERN, NOT the constants.** Extract `MAX_RECONNECT_TRIES` + `INITIAL_RECONNECT_BACKOFF_MS` into a config object passed from the V3.2 grid widget.

4. **`parseQuantbookError` + switch-on-code error handling** — V2.7+V2.8+V2.9 closures make this rock-solid. V3.2 grid will catch errors at every grid mutation; the union code pattern scales. **CARRY.**

5. **Dispose-from-handler safety** (V3.1.c idempotent `dispose` guarded by `isDisposed`) — pattern is essential for any long-lived resource with both auto-cleanup AND user-driven teardown paths. V3.2 grid widget's unmount handler will inherit this idiom. **CARRY.**

6. **`vscode.window.showWarningMessage(msg, 'Restart Demo')` UX** — fine for demo; V3.2 grid will probably use inline toast notifications (less modal). **PATTERN CARRIES; UI primitive changes.**

7. **`Transport::ack_handle` trait + V2.5 BlockingTransport pattern** — V3.2 grid contention testing will use BlockingTransportFixture. Pattern carries unchanged. **CARRY.**

### 3.2 Patterns from V3.1 that do NOT scale to a real grid

1. **Periodic 2s append (`APPEND_INTERVAL_MS = 2000`)** — fine for demo "show that something happens"; production grid needs event-driven append (one PutValue per cell-edit keystroke or commit). **DO NOT CARRY** the timer-driven model. V3.2 fires PutValue ops on `onDidChangeTextEditorSelection` + `onDidChangeTextDocument` boundaries.

2. **1s `pollRemote` polling** — works for a low-frequency demo. Production should:
   - Use the `Transport::ack_handle` from V2.5 / V2.6 to await inbound frames event-driven rather than poll.
   - Fall back to polling only if the transport doesn't support push (LoopbackTransport — but grids use WebSocketTransport).
   - **DO NOT CARRY** the 1s polling; V3.2 grid uses notification-driven receive.

3. **Row = pid & 0xffff collision-prone mapping (LOW-7)** — visual confusion in production grid is unacceptable. V3.2 must use a deterministic, collision-free per-peer presence indicator (not row-based, but cursor-color-based per `PresenceState` work). **DO NOT CARRY.**

4. **Spawn the relay binary as a child process of the IDE** — works for demo, fails for production:
   - The relay dies when the IDE quits → all clients disconnect → state loss on next IDE launch.
   - Two IDE invocations can race the spawn (MEDIUM-2 above).
   - Production grid wants a persistent service.
   - **DO NOT CARRY** the spawn-from-IDE model. V3.2 backlog: ship the relay as a separate service (or use a remote relay).

5. **Shared OutputChannel for diagnostic logging** — debug-only. Production grid logs to a dedicated channel or VS Code's `LogLevel`-aware logger. **DO NOT CARRY** as a primary observability surface.

6. **Hardcoded port `7117`** — port-collision risk in production. V3.2 backlog: discover the port via configuration / env / DNS-SD. **DO NOT CARRY.**

### 3.3 V3.2 risks (mapped from V2.8 Lane C R1–R5 + new V3.2-specific concerns)

#### R1 — BlockingTransportFixture cfg-gating path is clear for V3.2 contention tests

**Status (per V2.8 closure):** `BlockingTransportFixture` is `#[cfg(feature = "test-fixtures")]`-gated in `ql-bindings-node`. Production cdylib does NOT carry it (verified via `strings`). Mocha contract tests rebuild with `--features test-fixtures`.

**V3.2 implication:** cell-grid contention testing (multi-window concurrent edits hitting the same cell range) needs `BlockingTransportFixture` to deterministically simulate latency. The Cargo feature workflow already exists. **V3.2 inherits a working path.** **PASS.**

**Action item for V3.2:** the IDE-side mocha test runner should set up `cargo build -p ql-bindings-node --release --features test-fixtures` as a precondition in the V3.2 test fixture; the production-build path (`cargo build -p ql-bindings-node --release`) remains the demo / production binary. Add a top-of-file note in V3.2 grid contention tests explicitly stating this.

#### R2 — `parseQuantbookError` consumer pattern + reconnect UX scales but needs inline error surface

**Status:** V2.7 introduced `Error.code`, V2.8 walks `Error.cause` chain, V2.9 enforces TS compile-time drift via `Record<Exclude<>>`. The switch/case is robust. V3.1.c contracts the reconnect UX via `showWarningMessage`.

**V3.2 implication:** Grid widget catches errors at every mutation. The switch/case scales BUT `vscode.window.showWarningMessage` is too modal for inline grid feedback. V3.2 needs:
- Inline error toast at the cell that triggered the error.
- Status bar indicator for transport state ("Connected" / "Reconnecting…" / "Disconnected").
- Per-cell error decorations for typed validation errors (e.g., `bad_argument`).

**Risk level:** MEDIUM. Pattern carries; UX layer needs design work.

#### R3 — Send + Sync claim drift as V3.2 adds new binding classes

**Status:** V3.1 added 0 new napi classes. V2.7+V2.8 megaudit per-field walks: 0 new triggers. Rule 4 arc terminus is 6.

**V3.2 implication:** V3.2 will likely add:
- `CellRange` (start_row, end_row, start_col, end_col) — likely Copy + Send + Sync (POD).
- `CellEdit` (range + new value) — Send + Sync (likely Clone, not Copy).
- `GridView` (snapshot of session's cell data at a point in time) — needs careful walking; if it holds an `Arc<Workbook>`, it's Send + Sync via the Arc, but the napi wrapper is a different beast.
- `PresenceState` and `UndoGroupGuard` (V3.2/V3.3 — `PresenceState` may have non-trivial Sync requirements due to per-peer cursor state, and `UndoGroupGuard` is RAII-translated which historically tripped V2.3 audit).

**Risk level:** HIGH if not actively audited. Every new napi class needs:
- Positive `assert_impl_all!(MyClass: Send, Sync)` proof OR explicit per-field walk (Rule 4).
- A docstring section explaining the Send/Sync rationale.

**Action item for V3.2:** parallel Codex+Opus Rule 4 review for EACH new binding class added in V3.2 (treat each as its own ship-with-audit; do not bundle 3+ classes into one audit cycle).

#### R4 — Drop order under V3.2 grid widget lifecycle

**Status:** V3.1 added no engine-side state. V2.4 made `CollabSession: Sync` via `Arc<Mutex<CollabSessionInner>>` refactor. Drop order is documented at `ide-consumer-contract.md`.

**V3.2 implication:** the grid widget owns:
- A `CollabSession` (one per workbook).
- A `Transport` (attached via `attachTransport`).
- Per-cell DOM bindings (TypeScript-side; V3.2 uses a virtualized grid).
- Inbound polling cadence OR push-notification subscription handle.

Cleanup on grid-unmount:
1. Cancel any polling timer.
2. `session.detachTransport()` — synchronous, returns the prior Box; Rust-side drops the transport. WebSocketTransport's writer/reader tasks are notified via `notify_all` and exit asynchronously.
3. `session` itself goes out of scope (JS GC); the napi-rs `CollabSession` wrapper's Drop fires when the GC eventually runs.

**Hazard:** if the grid widget is unmounted but the user opens a new grid against the same workbook within ~100ms, the OLD session's transport tasks may not have fully exited, AND the OLD session may still be GC'd (delayed). Two sessions briefly co-exist; for the same workbook, this is harmless because they each have their own Loro doc state. **No data hazard but resource-overlap during unmount/remount.**

**Risk level:** LOW. Modal grid → grid transitions are slow enough to let cleanup complete. **Action item:** per-field walk on each new binding class added; explicit Drop order doc per V3.2 ship.

#### R5 — V3.1.c reconnect contract (now in ide-consumer-contract.md § 4.1.y) — V3.2 grid must hook this for live reconnect UX

**Status:** The reconnect-with-backoff pattern is documented + tested in V3.1.

**V3.2 implication:** the grid widget MUST:
- Subscribe to `transport_closed` / `transport_io` errors at every mutation.
- Surface "Reconnecting…" in the status bar.
- Disable optimistic edits (or queue them locally; CRDT replays on reconnect) during the reconnect window.
- Surface "Disconnected" + "Reconnect" button when backoff exhausts.

**Risk level:** MEDIUM. V3.1's pattern carries but V3.2 needs UI design work to bind to it. The IDE consumer contract is the single source of truth for the protocol; V3.2 grid is the first production consumer.

**Action item:** V3.2 entry plan should reference `ide-consumer-contract.md § 4.1.y` explicitly and call out which methods/events feed the grid's status-bar indicator.

#### R6 (NEW for V3.2) — Connection-pool semantics

**Description:** V3.1's `connectOrSpawn` creates one Transport per session per window. V3.2 grid may want to multiplex many workbooks over one Transport (one WebSocket per IDE instance, many sessions per WebSocket). This requires session multiplexing in the relay protocol — currently the relay is a stateless broadcast (every frame to every peer).

**Risk level:** HIGH for V3.2's production fit; MEDIUM for V3.2 demo.

**Action item:** V3.2 entry plan must decide between (a) one Transport per session (current model; scales as session count) or (b) multiplexed Transport with session_id frames (more efficient but requires relay protocol change). Decision belongs in the V3.2 entry plan, NOT this audit; flagged here for surfacing.

#### R7 (NEW for V3.2) — Server-side state management

**Description:** V3.1 relay is stateless. V3.2 grid widget likely needs:
- "What workbooks are open?" (presence-list across windows).
- "Who else is editing this cell right now?" (per-cell presence).
- "Replay missed ops since I disconnected" (history catch-up beyond Loro's local op log).

A stateless relay cannot answer these. V3.2 needs either:
- Server-side state (relay grows into a real server) — adds significant scope.
- Client-side state propagation (each peer broadcasts presence; new peers wait for next presence beacon) — simpler, eventually-consistent.

**Risk level:** HIGH for V3.2 production scope; the relay binary in its current V3.1 form does NOT support either model out of the box.

**Action item:** V3.2 entry plan must scope the presence/history features. Treating them as "V3.3 deferred" is acceptable; treating them as "in V3.2 scope" requires server-side work that V3.1 has not enabled.

### 3.4 Net V3.2 readiness verdict

**Engine side:** V3.1.a relay binary is appropriate for V3.2 grid demos and contention tests. Production deployment requires (a) port discovery, (b) server-side state for presence/history, and (c) lifecycle separation from the IDE process. None of these are V3.1 obligations; all are V3.2/V3.3 work.

**IDE side:** V3.1.b + V3.1.c patterns are GOOD foundations for V3.2. The MEDIUM findings above (cold-spawn timeout, connect race) are V3.2 inheritance hazards if they're not addressed before grid work begins. The LOWs are demo-scope acceptable.

**Rule 4 discipline:** V3.1 added 0 new negative-trait claims. V3.2 will add binding classes and needs strict per-class Rule 4 reviews. The arc terminus of 6 is intact; the convention propagates.

**Recommendation:** V3.2 may proceed AFTER:
1. MEDIUM-1 closure (Windows cold-spawn timeout). Required only if V3.2 includes Windows CI from day 1.
2. MEDIUM-2 closure (connect race recovery). Required because V3.2 grid widget demos depend on the multi-window narrative.
3. V3.2 entry plan explicitly addresses R6 (multiplex vs per-session Transport) and R7 (server-side state vs client beacon).

All other findings can be deferred into the V3.2 entry plan as backlog.

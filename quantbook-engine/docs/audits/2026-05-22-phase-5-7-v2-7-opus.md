# Phase 5.7 V2.7 — Opus adversarial audit lane

## One-sentence strongest concern

The `KNOWN_QUANTBOOK_ERROR_CODES` set at `extensions/quantlab/src/quantbook/session.ts:181-193` includes `'unknown'` as a recognised code, which produces an asymmetric `parseQuantbookError` contract: a literal engine-emitted `"[unknown] foo"` would strip the prefix and return `{code:'unknown', message:'foo'}`, while `"[future_new_kind] foo"` returns `{code:'unknown', message:'[future_new_kind] foo'}` (prefix preserved) — both paths claim the same code but produce divergent messages. Today no engine variant returns `"unknown"`, so this is latent rather than active, but the set membership is the only place in the IDE binding that conflates "successfully parsed sentinel" with "fell back to sentinel."

### MEDIUM-1 — `'unknown'` membership in `KNOWN_QUANTBOOK_ERROR_CODES` creates a contract asymmetry

- **File:line**: `extensions/quantlab/src/quantbook/session.ts:181-193` (set definition); `:241-247` (the two branches that diverge).
- **Reproduction**: build a test `const err = new Error('[unknown] foo'); const info = parseQuantbookError(err);`. Today's code: `KNOWN_QUANTBOOK_ERROR_CODES.has('unknown') === true`, so the set-membership branch fires (`session.ts:241`), returning `{code:'unknown', message:'foo'}`. Now `const err2 = new Error('[future_new_kind] foo')`: set membership is `false`, falls through to `session.ts:247`, returns `{code:'unknown', message:'[future_new_kind] foo'}`. Two inputs, two different messages, same `code` — the message field is no longer a deterministic function of the code.
- **Why this matters**: the engine never returns `"unknown"` today (walked all three `kind()` impls — `transport.rs:138-143`, `lib.rs:252-259`, `session.rs:173-181` — none emit `"unknown"`). So the asymmetry is dormant. But the documented `QuantbookErrorInfo` contract (`types.ts:529-548`) does not warn callers that `code === 'unknown'` corresponds to *two distinct branches* with different `message` semantics. A downstream caller building a reconnect-log line via `${info.code}: ${info.message}` would emit `"unknown: foo"` for one branch and `"unknown: [future_new_kind] foo"` for the other — same code, different shapes.
- **Recommended closure**: remove `'unknown'` from `KNOWN_QUANTBOOK_ERROR_CODES`. The sentinel is exclusively IDE-internal; including it in the engine-kind-validation set is a category error. After removal, `parseQuantbookError` always reaches the `:247` fallback for unknown bracketed prefixes — and `isQuantbookErrorCode('unknown')` would then return `false`, which is also more truthful (`'unknown'` is not an engine code; it's a sentinel for the absence of one). The mocha test at line 1540 (`assert.ok(isQuantbookErrorCode('unknown'))`) would need to be inverted.

### MEDIUM-2 — binding-layer validation errors lack `[code]` prefix, silently falling to `'unknown'`

- **File:line**: `crates/ql-bindings-node/src/lib.rs:168, 173, 178, 183` (validate_u32_index); `:230, 235, 240, 245` (peer_id_from_bigint); `:411` (appendPutValue value non-finite); `:559, 1128, 1139` (consumed-Transport / consumed-LoopbackPair); `:915, 1329, 1330` (spawn_blocking JoinError); `:927, 957` (parse_auto_flush_policy + auto_flush_policy_to_string); `:1238, 1272` (assumed: BlockingTransportFixture).
- **Reproduction**: `try { new engine.CollabSession(0n); } catch(e) { console.log(parseQuantbookError(e)); }` — yields `{code:'unknown', message:'peerId must be non-zero (PeerId(0) is LEGACY_PEER, ...)'}`. The user-facing error is well-formed, but IDE consumers cannot programmatically distinguish "peer-id invalid" from "value non-finite" from "transport-already-consumed" without substring-matching the same kind of fragile prose V2.7 was designed to replace.
- **Why this matters**: the V2.7 plan rationale (`crates/ql-bindings-node/src/lib.rs:254-310`) says: "every engine error type's variant discriminant is lost on the napi boundary." V2.7 closes that for the three engine error enums — but the BINDING-layer validation errors (input validation, single-use enforcement, JoinError mapping) are equally lossy and were left untouched. From the IDE caller's perspective, all of these now look like one undifferentiated `code: 'unknown'` bucket. The MEDIUM-3 carryforward from V2.1/V2.2/V2.3 is closed for engine errors but **re-opened** at the binding boundary the moment V2.7 made `parseQuantbookError` the supposed-canonical discrimination path.
- **Recommended closure**: add a `binding_*` family of stable codes (e.g. `binding_validation`, `binding_consumed`, `binding_task_panic`) plus a helper `binding_error(kind, msg)` that emits the `[<kind>] <msg>` prefix. Extend the IDE union + set. Then sweep the ~14 raw `Error::from_reason(...)` sites to use the helper. Alternative: scope V2.7 as "engine errors only" and document in `types.ts:485-499` that binding-layer errors will continue surfacing as `'unknown'` until V2.8 — at least the contract would be explicit.

### MEDIUM-3 — `CollabSessionError::Transport(_)` kind passthrough breaks the documented session-prefix convention

- **File:line**: `crates/ql-collab/src/session.rs:178` (the `Transport(inner) => inner.kind()` line).
- **Reproduction trace per audit prompt**: engine `flush_delta_to_transport` returns `Err(CollabSessionError::Transport(TransportError::Closed))`. `collab_session_error_to_napi` (`lib.rs:294-296`) computes `format!("[{}] {e}", e.kind())`. `e.kind()` matches `Transport(inner)` → returns `inner.kind() = "transport_closed"`. `{e}` Displays via thiserror as `"transport error: transport closed"` (the outer `#[error("transport error: {0}")]` at `session.rs:144` interpolates the inner Display `"transport closed"` from `transport.rs:118`). **Final message**: `"[transport_closed] transport error: transport closed"`. Trace VERIFIED.
- **Why this is still a finding**: the result is contractually surprising. The other 4 `CollabSessionError` variants return `session_*` prefixes (`session_oplog`, `session_presence`, `session_undo`, `session_replay` — `session.rs:175-179`). Only `Transport(_)` skips the `session_` namespace and emits a `transport_*` code instead. The session.rs:166-172 docstring documents this as intentional ("for `Transport(inner)`, returns the inner `TransportError`'s kind"), and the types.ts:511-513 union also documents it. **But**: IDE consumers reading `code === 'transport_closed'` cannot tell whether the error originated from (a) `Transport.flushPending` directly (a `TransportError`) or (b) a `CollabSession` method that wrapped it (a `CollabSessionError::Transport(TransportError::Closed)`). The two have different recovery semantics — case (b) means the session's `OpLog` may have been mutated before the transport failed (mutate-then-flush ordering, `session.rs:283-291` docstring), while case (a) is pure transport.
- **Recommended closure**: split the passthrough — return e.g. `"session_transport_closed"` and `"session_transport_io"` so the inner discriminant is preserved AND the wrapping origin is recoverable. Update the IDE union (add 2 codes) + set. Alternative: keep the passthrough but document the loss explicitly in `QuantbookErrorInfo.code` JSDoc — currently the `code` field doc (`types.ts:531-535`) does not warn that one code value can come from two different engine call paths.

### LOW-1 — regex `[a-z][a-z_]*` rejects digit-bearing codes pre-emptively, even if future engine ships one

- **File:line**: `extensions/quantlab/src/quantbook/session.ts:201` (the `QUANTBOOK_ERROR_PREFIX_RE`).
- **Reproduction**: hypothetical future engine ships `WebSocketError::ProtocolV2Mismatch` → `kind() = "protocol_v2_mismatch"`. Engine emits `"[protocol_v2_mismatch] ..."`. Regex charclass `[a-z][a-z_]*` rejects the `2` digit, so the match fails entirely — falls to `unknown`, full prefix preserved as the message. Functional but slightly noisy.
- **Why low**: the engine's documented convention (kind docstrings at `transport.rs:122-137`, `lib.rs:241-260`, `session.rs:162-182`) implicitly uses snake_case alphabetics. No current code violates this. The risk is purely on a future engine variant naming choice.
- **Recommended closure**: relax to `[a-z][a-z0-9_]*` to match Rust identifier conventions. Cost: zero — none of today's codes contain digits. Benefit: future-proof.

### LOW-2 — kind() docstrings say "SemVer-stable" without an actual SemVer test

- **File:line**: `crates/ql-collab/src/transport.rs:123-137`; `crates/ql-collab-ws/src/lib.rs:243-260`; `crates/ql-collab/src/session.rs:163-172`.

Mocha test `transport_error_kind_io` (`transport.rs:1109`) updates its expected string and passes. Nothing fails — but every shipping IDE that has `if (info.code === 'transport_io')` silently stops matching.

### LOW-3 — `record_runtime_error` (`ql-collab-ws/src/lib.rs:175-190`) writes `WebSocketError::RuntimeError` which then receives kind `"websocket_runtime_error"` for every panic-side-channel error

- **File:line**: `crates/ql-collab-ws/src/lib.rs:155-167` (TaskExitGuard::drop calls record_runtime_error); `:182-188` (the actual error stashed); `:252-259` (kind() maps RuntimeError → "websocket_runtime_error").
- **Reproduction**: writer task panics. `TaskExitGuard::drop` calls `record_runtime_error(slot, "ql-collab-ws writer task panicked")`. Slot now holds `WebSocketError::RuntimeError("ql-collab-ws writer task panicked")`. Future consumer of `WebSocketTransport::last_error` sees the RuntimeError → maps to kind `"websocket_runtime_error"`. **The kind is correct, but a code intended to convey "peer reset" / "capacity exceeded" / etc. is now overloaded with the panic-detection signal.**
- **Why low**: the underlying behavior is fine; the *granularity* of the kind is what's coarse. IDE callers branching on `'websocket_runtime_error'` cannot distinguish a soft "peer reset" from a hard "writer task panicked." Display strings differ, but per the V2.7 rationale, IDE consumers shouldn't substring-match Display.
- **Recommended closure**: add a `WebSocketError::TaskPanic(String)` variant + kind `"websocket_task_panic"` for the panic side-channel, leaving `RuntimeError(String)` for legitimate runtime errors (peer reset, etc.). Update the IDE union + set. Cost: ~6 LOC engine + ~3 LOC IDE.

### LOW-4 — `parseQuantbookError(err: unknown)` lacks JSDoc warning about empty-message + non-string inputs

- **File:line**: `extensions/quantlab/src/quantbook/session.ts:227-248` (the impl); `:202-225` (the JSDoc).
- **Reproduction**: `parseQuantbookError(new Error(''))` — Regex test on empty string fails (no `^\[`), falls to `unknown` branch, returns `{code:'unknown', message:''}`. Behaviorally correct. `parseQuantbookError({toString: () => '[transport_closed] foo'})` — not an Error instance, falls to the non-Error branch (`:228`), returns `{code:'unknown', message:'[object Object]'}` (String() on the plain object).
- **Why low**: the second case is the more interesting one. A custom throwable that has a structured message but isn't an `Error` subclass loses its discrimination. JSDoc says "the value is not an Error instance" → falls to unknown, but doesn't warn that the `String(err)` conversion happens via JS's `Object.prototype.toString` defaults, which often produce `[object Object]`.
- **Recommended closure**: JSDoc note + (optional) probe the throwable's `message` property before falling back to `String(err)`: e.g. `typeof (err as any)?.message === 'string'` → use that for the regex test. This catches the `Error`-subclass-from-different-realm case (e.g. errors thrown from a vm context or web worker, where `instanceof Error` is false but `.message` is the right discriminant).

## Regex robustness verdict: VERIFIED with one LOW (LOW-1)

The regex `/^\[([a-z][a-z_]*)\]\s*(.*)$/s`:

- **Anchored at start** (`^`) so embedded `[` `]` in Display body cannot capture-mismatch. E.g., `"[transport_io] socket [refused]"` → group 1 = `"transport_io"`, group 2 = `"socket [refused]"`. VERIFIED.
- **`s` flag** makes `.` match newlines — multi-line Display strings parsed correctly.
- **`[a-z][a-z_]*` charclass** matches every shipped engine kind (walked all 10): `transport_io`, `transport_closed`, `websocket_invalid_url`, `websocket_connect_failed`, `websocket_handshake_failed`, `websocket_runtime_error`, `session_oplog`, `session_presence`, `session_undo`, `session_replay`. All match.
- **Empty string** `""` — regex fails (no `^\[`), falls to `unknown` branch with `message: ''`. Acceptable.
- **No closing bracket** `"[broken"` — regex fails, falls to `unknown`. Acceptable.
- **TitleCase** `"[Transport_Closed]"` — regex fails (uppercase rejected). Mocha test at `:1548` pins. Acceptable.
- **ReDoS** — linear, no nested quantifiers, no catastrophic backtracking. VERIFIED safe.

Caveat: future engine variants with digits would fall through (LOW-1).

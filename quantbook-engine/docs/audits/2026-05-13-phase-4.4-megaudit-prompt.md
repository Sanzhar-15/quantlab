## Specific concerns to challenge

### CONCERN-A: W5-64 helper migration — silent behavior drift

Four private helpers (`coerce_text`, `coerce_int_arg`, `coerce_numeric` ×2,
`value_to_concat_text`, `format_number_for_text`) were promoted to
`ql-types::coercion` under neutral names. The W5-64 commit message claims
"byte-for-byte" preservation. Verify:

1. **`coerce_text` → `to_text_for_arg`**: identical for Blank / Bool / Text /
   Number-finite / Error? The W5-64 commit added a NaN/Inf branch (returns
   `Err(#NUM!)`). The original `coerce_text` lacked this branch — meaning
   raw `Value::Number(f64::NAN)` would have rendered via `format_number_for_text`
   as `"NaN"`. Is this behavior CHANGE intentional and correctly tested? Is
   there any caller of the old `coerce_text` that relied on getting back
   `"NaN"` / `"inf"` text rather than an error? (Spoiler: probably not, but
   verify with a grep.)
2. **`coerce_int_arg` → `to_int_arg`**: the body `match v { Number, Boolean,
   Blank, Text(s) => to_number_lenient + truncate, Error }` — is it
   identical? Check that the lossy `Err(_) => Err(ErrorValue::Value)` is
   preserved (i.e. we discard the lenient-parse error's specific variant
   and always surface `#VALUE!`).
3. **`coerce_numeric` → `to_number_strict_skip_blank`**: the new central API
   returns `Result<Option<f64>, ErrorValue>`. The `range_aware_fns` cross-
   module shim converts it back to `NumericArg`. Verify the conversion is
   total: every match arm reaches `NumericArg::Number`, `Skip`, or `Error`
   with no missing cases. Also verify that the shim does NOT introduce new
   coercion (it shouldn't — it's literally `Ok(Some(n)) → Number, Ok(None)
   → Skip, Err(e) → Error`).
4. **`value_to_concat_text` deletion**: the W5-64 commit says
   `to_text_for_arg` is byte-for-byte identical. Confirm by inspection.
   Any subtle difference between the deleted function and `to_text_for_arg`
   that would change CONCAT's output?
5. **`format_number_for_text` → `format_number_for_arg`**: now public. Any
   caller outside `to_text_for_arg`? If yes, are they getting the same
   integer-rendering rule?

### CONCERN-B: NaN/Inf policy implementation (W5-64)

The W5-63 Codex review's MEDIUM 1 finding required `to_text_for_display`
and `to_text_for_formula` to handle raw `Value::Number(NaN/±Inf)` by
returning `"#NUM!"` / `Err(#NUM!)`. Verify:

1. **`to_text_for_display`**: the implementation calls
   `n.is_nan() || n.is_infinite()`. Is the check before or after the
   `Display` call? (Should be BEFORE — verify in source.)
2. **`to_text_for_formula`**: similar question.
3. **`to_text_for_arg`**: the function body has the same check. Verify the
   tests in `coercion_matrix.rs` and the unit tests in `coercion.rs::tests`
   actually exercise the NaN/Inf branch — i.e., a test that would FAIL if
   the branch were removed.
4. **Cross-cutting**: a `Value::Number(0.0)` is finite — does the NaN/Inf
   check have any false-positive risk on `0.0` or `-0.0`? Tests should pin
   this.

### CONCERN-H: Performance regression risk

The W5-64 migration added function-call indirection for what used to be
inline match expressions. For tight aggregate loops (SUM over 1M cells),
does this matter?

1. The `coerce_numeric` shim in `range_aware_fns` calls
   `coercion::to_number_strict_skip_blank` which internally calls
   `to_number_strict`. That's now 2 function calls per cell instead of
   the previous 1 match expression. Compiler inlining likely makes this
   free, but it's worth a sanity check on the bench numbers.
2. The `to_text_for_display` NaN/Inf branch adds a check on EVERY display
   call. Negligible for one-off rendering, but if used in a tight loop
   (criteria-key formation in SUMIF over a 1M-row range, for example),
   the additional check accumulates.

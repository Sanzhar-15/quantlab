## § A Summary + Verdict

**Verdict: PASS-WITH-FINDINGS.**

V3.6.0.3 D2 ships the session-wide format-table cache cleanly at the cache-walker level (LWW-by-iteration on the cache; `workbook_snapshot.formats` reads from the authoritative Workbook FormatTable). The new `FormatDefJson` + the `formats: Vec<FormatDefJson>` additive field on `WorkbookSnapshotJson` are positive-Send+Sync compositions; arc terminus stays at 6. The 6-mutation-site discipline for `format_table_cache` is correctly maintained (`new` + `from_snapshot` + `append_op` via `apply_cache_effect` + `rebuild_snapshot_cache` atomic-swap + `merge_bytes` / `discard_pending_ops` / `poll_remote_with_limit` via `rebuild_snapshot_cache` + `force_clear_snapshot_cache` test seam). The findings are concentrated in three areas: (1) the V3.6.0.1 decision-lock body (`.plans/_active.md` § D2) **explicitly REJECTED** LWW-overwrite and **specified "second registration is a no-op"** -- the V3.6.0.3 implementation deviated and uses LWW-by-iteration, contradicting the locked decision; (2) the cache walker accepts **any** `Op::RegisterFormat` payload (Builtin variants, out-of-range Builtins, same-id-different-string) without mirroring the rejection semantics that Workbook::FormatTable::register_at enforces -- producing a cache that, under adversarial / buggy producer input, holds Builtin(0)="MyCustom" or Builtin(200)="OutOfRange" entries (probed); (3) several docstring claims are factually wrong (Builtin count, HashMap iteration "stable for a given workbook state", "ONLY Custom format registrations"). Most findings close in-cycle with small docstring + closure-discipline patches; the decision-lock deviation (HIGH-1) needs either a code patch OR an explicit decision-revisit + lock amendment.

Findings: 1 HIGH (decision-lock deviation), 3 MEDIUM, 4 LOW, 4 INFO. No data-loss bug. No cross-peer convergence bug at the cache level (Loro's iter is deterministic; both peers reach the same LWW winner per the cross-peer probe). The cross-peer-divergence pathology the docstring frets about is **cache-vs-Workbook on the same peer**, not peer-vs-peer.

## § B HIGH findings

### B.1 -- HIGH-1: V3.6.0.1 decision-lock deviation (cache LWW vs locked "no-op" semantic)

**Scope**: `crates/ql-collab/src/session.rs:1211-1213` (`apply_cache_effect` `CacheEffect::RegisterFormat` arm) vs `.plans/_active.md` § D2 line 133.

The V3.6.0.1 decision lock (`.plans/_active.md` § D2, line 133) explicitly decided:

> "**Cross-peer convergence:** concurrent `Op::RegisterFormat { id: SAME, string: DIFFERENT }` on the same id is the cross-peer collision case. Per Loro CRDT semantic + Phase 4.6 D-1 `register_at` impl: the engine rejects same-id-different-string registrations with a `FormatRejected` replay error. V3.6 ADOPTS this contract (engine rejects; **cache walker treats the second registration as a no-op**). **Alternative LWW-overwrite was REJECTED** because the engine already has the rejection semantic from D-1."

The shipped V3.6.0.3 D2 implementation is the **rejected** LWW-overwrite variant:

```rust
// session.rs:1211
CacheEffect::RegisterFormat { id, string } => {
    format_cache.insert(id, string);  // LWW-by-iteration; later overwrites earlier
}
```

The `CacheEffect::RegisterFormat` docstring (session.rs:186-204) ACKNOWLEDGES this:
> "LWW-by-iteration semantic (later same-id RegisterFormat overwrites earlier)."

This is the option the V3.6.0.1 decision lock REJECTED. The implementation went the other way and the docs sweep commit `0c3cbef8cea` did NOT update the decision-lock body to reflect the deviation.

**Reproducible probe** (Opus Lane B inline, removed post-audit):

```rust
#[test]
fn opus_probe_lww_cross_peer_concurrent_register_format() {
    let peer_a = PeerId::new(0xa);
    let peer_b = PeerId::new(0xb);
    let mut a = CollabSession::new(peer_a).unwrap();
    let mut b = CollabSession::new(peer_b).unwrap();
    a.append_op(Op::RegisterFormat { id: Custom { peer: peer_a, counter: 0 }, string: "FromA" });
    b.append_op(Op::RegisterFormat { id: Custom { peer: peer_a, counter: 0 }, string: "FromB" });
    a.merge_bytes(&b.export_bytes().unwrap()).unwrap();
    b.merge_bytes(&a.export_bytes().unwrap()).unwrap();
    // Both peers' caches: [(Custom(peer_a, 0), "FromB")]  -- second-iterated wins
    // (whichever Loro placed second in causal order).  Decision lock said "no-op";
    // implementation does overwrite.
}
```

**Severity**: HIGH because it's a documented decision-lock deviation -- the audit discipline (Rule 4 + V3.5.0.X cycle) requires that implementations match the lock OR the lock be amended in-cycle. Today neither is true. The functional impact at V3.6.0.3 D2 is bounded (the napi reads from Workbook, not the cache, so end-users don't see the wrong string), but the discipline gap will compound at V3.7+ when delta consumers use `format_table_cache_iter` as authoritative (per the docstring's own claim about V3.7+ scope).

**Suggested closure** (pick one, in-cycle):

(a) **Mirror the rejection in the walker** (matches the locked decision): change `apply_cache_effect`'s `CacheEffect::RegisterFormat` arm to use `format_cache.entry(id).or_insert(string)` (first-write-wins). Walks then preserve the SAME semantic as `FormatTable::register_at` for the same-id case (FormatTable rejects with `IdCollision`; entry().or_insert avoids overwriting; semantically equivalent at the cache layer where we don't propagate the error). Add a regression test that demonstrates: peer_a "FromA" + peer_b "FromB" same-id -> cache holds "FromA" (whichever appears first in iteration). Update `CacheEffect::RegisterFormat` docstring + `format_table_cache` field docstring to remove the LWW caveats.

(b) **Amend the decision lock** (`.plans/_active.md` § D2 line 133): document that the implementation chose LWW because the napi reads from Workbook, the cache is internal-only, and LWW-vs-no-op-vs-merge are all "any deterministic single-value-per-id" -- equivalent at the consumer layer. Note that the lock body was overruled in-cycle, why, and that V3.7+ delta consumers must consult Workbook (not the cache) for authoritative format strings.

I lean (a) for two reasons: the locked semantic IS cheaper than LWW (one map lookup, no allocation if the entry already exists, no `Arc<str>` clone), AND it future-proofs the cache against the V3.7+ delta-consumer scenario the docstring itself acknowledges. (a) also closes the parallel concern in B.2 below (since first-write-wins also blocks the Builtin-overwrite + out-of-range-overwrite attacks at the cache walker -- the first registration, whether the preloaded Builtin(0)="General" or a bogus producer op, sticks).

Diff sketch for (a):

```rust
// session.rs:1205-1213 -- BEFORE
CacheEffect::RegisterFormat { id, string } => {
    format_cache.insert(id, string);
}

// AFTER
CacheEffect::RegisterFormat { id, string } => {
    // V3.6.0.1 locked decision § D2: first-write-wins (mirrors
    // FormatTable::register_at's IdCollision rejection at the cache
    // layer; same-id later registrations are no-ops).  HashMap::entry
    // avoids the redundant Arc<str> clone for the no-op case.
    format_cache.entry(id).or_insert(string);
}
```

Plus a regression test pinning the first-write semantic + docstring sweep on `CacheEffect::RegisterFormat` + `format_table_cache` + `format_table_cache_iter` to remove the "LWW caveat" sentences and replace with "first-write-wins mirrors FormatTable::register_at IdCollision rejection".

## § C MEDIUM findings

### C.1 -- MED-1: Cache walker accepts ANY Op::RegisterFormat payload without mirroring FormatTable's validation

**Scope**: `crates/ql-collab/src/session.rs:1091-1100` (`collect_cache_effects`), `1205-1213` (`apply_cache_effect`).

`FormatTable::register_at` (storage side) enforces THREE validations (`crates/ql-storage/src/format.rs:416-514`):

1. `Builtin(n)` requires `n <= FIRST_XLSX_BUILTIN_MAX (= 163)` -> else `BuiltinOutOfRange`.
2. Same `id` already present with different string -> `IdCollision`.
3. Same string already at a different `id` (within its Builtin/Custom string-namespace) -> `StringCollision`.

The cache walker performs **zero** of these. Any `Op::RegisterFormat` that lands in the log via `collect_cache_effects` blindly goes into the cache.

**Reproducible probes** (Opus Lane B, removed post-audit):

```rust
#[test]
fn opus_probe_builtin_register_format_overwrites_cache_silently() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(Op::RegisterFormat {
        id: FormatIdWire::Builtin { id: 0 },     // already preloaded as "General"
        string: "MyCustom".to_string(),
    }).unwrap();
    // Cache: [(Builtin(0), "MyCustom")] -- but Workbook keeps "General"
}

#[test]
fn opus_probe_builtin_out_of_range_register_format_in_cache() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(Op::RegisterFormat {
        id: FormatIdWire::Builtin { id: 200 },   // > FIRST_XLSX_BUILTIN_MAX
        string: "OutOfRange".to_string(),
    }).unwrap();
    // Cache: [(Builtin(200), "OutOfRange")] -- Workbook would Err with BuiltinOutOfRange
}
```

Both pass under V3.6.0.3 D2.

Production impact today: bounded. The IDE napi `workbook_snapshot` reads `Workbook.formats().iter()` (authoritative), and a replay error on the SAME log would surface as `Err(CollabSessionError::Replay(ReplayError::FormatRejected))` from `rebuild_workbook` -- the IDE never observes the cache state in that case (the snapshot call errors). I probed:

```rust
#[test]
fn opus_probe_rebuild_workbook_under_concurrent_same_id_diff_string() {
    // Two peers concurrently register same-id-different-string.
    // After merge_bytes, rebuild_workbook returns:
    // Err(Replay(FormatRejected { index: 1, source: IdCollision { id: Custom(peer_a, 0),
    //   existing: "FromA", attempted: "FromB" } }))
}
```

So the **cross-peer concurrent same-id-different-string scenario produces a SESSION-LEVEL Err on the workbook side**, not silent divergence. The IDE never displays mismatched data; it displays "snapshot failed". That's not great, but it's not silent-data-corruption.

Future impact (V3.7+ scope per the docstring): when incremental snapshot deltas land and `format_table_cache_iter` becomes a consumer, the cache holding `(Builtin(0), "MyCustom")` would surface that string to the IDE. The Workbook would have rejected the registration entirely; the cache silently kept the bogus value.

**Severity MED** because: (a) V3.6.0.3 D2 napi DOESN'T consume the cache, so today's impact is theoretical / V3.7+; (b) the producer side `WorkbookRuntime::recompute_all` + `intern` doesn't currently emit `Op::RegisterFormat { id: Builtin(_), string: _ }` so the cache-walker pathology is reachable only from a malformed wire (corrupt qbook envelope, foreign producer, fuzzer); (c) the V3.5.0.X audit closed similar tombstone-walker gaps proactively (Opus-H1 widened SetCellFormat guard), so this is a consistent finding pattern.

**Suggested closure** (in-cycle):

Adopt the FormatTable's `register_at` validation logic inside the cache walker. Concretely, in `collect_cache_effects`'s `Op::RegisterFormat` arm, reject (drop the effect) if `id` is out of Builtin range OR if `id` is already in the local cache with a different string. Since cache rebuild is downstream of the wire log, and the wire log is the same the Workbook side replays, this keeps cache + Workbook semantically identical for legal inputs and silently drops illegal effects (instead of surfacing as Workbook Err on snapshot calls).

Alternative: the cleaner closure pairs B.1 (first-write-wins) with C.1 (range-check Builtin). Diff sketch:

```rust
// collect_cache_effects, lines 1091-1100 -- BEFORE
Op::RegisterFormat { id, string } => out.push(CacheEffect::RegisterFormat {
    id: id.to_storage(),
    string: Arc::<str>::from(string.as_str()),
}),

// AFTER
Op::RegisterFormat { id, string } => {
    let fid = id.to_storage();
    // Mirror FormatTable::register_at's Builtin-range validation.
    // Out-of-range Builtin in the wire is a malformed producer or a
    // foreign-envelope migration corner; the Workbook side rejects via
    // BuiltinOutOfRange.  Drop at the cache walker to keep semantic parity.
    if let FormatId::Builtin(n) = fid {
        if n > 163 {  // FIRST_XLSX_BUILTIN_MAX
            return;
        }
    }
    out.push(CacheEffect::RegisterFormat {
        id: fid,
        string: Arc::<str>::from(string.as_str()),
    });
}
```

Plus the entry().or_insert change in apply_cache_effect (B.1) which closes the same-id-different-string case automatically. Plus regression tests for both attack vectors.

### C.2 -- MED-2: FormatTable.iter() is HashMap iteration; napi docstring + IDE TS docstring claim "stable for a given workbook state" -- factually WRONG

**Scope**:
- Engine napi docstring `crates/ql-bindings-node/src/lib.rs:621-624` -- "Sort order: iteration order of FormatTable::iter() (stable for a given version + workbook state; not sorted by id)."
- IDE TS docstring `extensions/quantlab/src/quantbook/types.ts:202-205` -- "Iteration order: stable for a given workbook state but NOT sorted by id (engine HashMap iteration)."

`FormatTable::iter()` (`crates/ql-storage/src/format.rs:542-544`) wraps `HashMap.iter()`. Rust's `std::collections::HashMap` does NOT guarantee stable iteration order across HashMaps -- even for the SAME logical content (the random seed is per-HashMap-instance via the default `RandomState`). Critically, `workbook_snapshot` calls `rebuild_workbook` which constructs a **FRESH** Workbook each call (per the V3.5.0.2 design), so EACH `workbook_snapshot` call:

1. Builds a fresh `Workbook::new()` -> fresh `FormatTable::default()` (with the per-instance random hasher state).
2. Replays `Op::RegisterFormat` ops in causal-order into the new FormatTable.
3. Iterates the table for the `formats` array.

Two consecutive `workbook_snapshot` calls on the same session produce TWO FormatTable instances with TWO independent hasher states -> two different orderings of `formats[]` are possible.

The IDE mocha test 3 ("formats field type shape -- FormatDefJson { id, string }") reads `snap.formats[0]` -- order-dependent but it just checks that the entry has `{ id, string }` keys, which is per-entry shape. Test 2 ("Builtin format ids surfacing") sorts before checking -- ordering-independent. Test 4 ("top-level shape includes formats") sorts top-level keys -- ordering-independent. So the IDE tests SURVIVE the non-determinism today, but the docstring is misleading.

**Severity MED** because the false stability claim leads V3.6+ D4 (format-aware rendering) consumers to expect deterministic order. A consumer that builds a presentation list assuming ordering stability across calls will see flicker.

**Suggested closure** (docstring-only):

Replace "stable for a given version + workbook state" with "NOT deterministic across calls; HashMap iteration uses a per-instance random hasher. Callers requiring deterministic order MUST sort client-side (e.g., by `id.kind` then `id.builtin ?? id.customCounter`)." In the IDE typedoc, mirror the warning and link to a recommended `compareFormatDefJson(a, b)` helper that V3.6+ D4 can call.

### C.3 -- MED-3: `format_table_cache_iter` accessor docstring claims cache holds "ONLY Custom format registrations" -- the wire allows Builtin too

**Scope**: `crates/ql-collab/src/session.rs:1337-1357` (`format_table_cache_iter` docstring) + the field docstring on `format_table_cache` (lines 765-771).

Both claim:

> "this cache holds ONLY Custom format registrations (the only ones that come from `Op::RegisterFormat`). Builtin formats (ids 0..=163 per Phase 5.2 D-1) are defined at `FormatTable` construction and never appear in an op log."

The `FormatIdWire` enum (`crates/ql-oplog/src/wire.rs:281-286`) allows `Builtin { id: u32 }`. The `to_storage()` conversion at `collect_cache_effects:1098` is lossless. The cache walker accepts whatever the wire carries. **Production producers** (the `WorkbookRuntime::intern` flow) only emit Custom-variant RegisterFormat ops today, so in practice the cache holds only Custom ids -- but the wire is the authoritative ABI surface, and the docstring's claim is wire-level FALSE.

Probe `opus_probe_builtin_register_format_overwrites_cache_silently` (Opus Lane B inline, removed post-audit) demonstrated the cache holding `(Builtin(0), "MyCustom")` after a hand-crafted `Op::RegisterFormat { id: Builtin(0), string: "MyCustom" }`.

**Severity MED** because this is the cross-cutting docstring drift class -- a future producer-side enhancement (e.g., explicit overlay of Builtins for renderer-tuning purposes) would invalidate the docstring's implicit invariant. C.1's closure (range-check Builtin in walker) tightens this surface to `Builtin(0..=163)` registrations only; without C.1's closure, the cache can hold ANY Builtin u32.

**Suggested closure** (docstring + alignment with C.1's closure):

If C.1 closure adopts (FormatTable validation in walker), the docstring becomes accurate post-closure: "Cache holds Custom format registrations + Builtin overrides (range-checked to 0..=163 per FormatTable::register_at's BuiltinOutOfRange rejection). Production producers only emit Custom registrations; Builtin pass-through exists for wire compatibility."

If C.1 closure is deferred, the docstring should say: "Cache holds ALL Op::RegisterFormat applications regardless of variant or range. Production producers only emit Custom variants today; Builtin-variant entries surface only from foreign producers or malformed envelopes."

## § D LOW findings

### D.1 -- LOW-1: `apply_cache_effect` signature grows linearly with cache fields; bundling into a `CacheState` struct would block forgetfulness

**Scope**: `crates/ql-collab/src/session.rs:1121-1126` (signature) + 3 call sites (1033, 1529, 1632).

`apply_cache_effect` now takes `&mut HashMap<...> snapshot`, `&mut HashSet<u16> tombstones`, `&mut HashMap<FormatId, Arc<str>> format_cache`, `effect: CacheEffect` -- 4 params, 3 mutable refs to disjoint cache buckets. V3.6.0.4 D3 (per-cell op-index) per the V3.6.0.1 plan body will add a 4th cache bucket. V3.7+ incremental deltas may add a 5th.

Current discipline is "every new bucket = signature change at 1 helper + 3 callers". Forgetting one of the callers produces a state-divergence bug that the type system doesn't catch (a freshly-rebuilt cache vs. a missed incremental update).

**Severity LOW** because the V3.6.0.3 D2 implementation correctly threaded all 3 callers + the type system DID catch the forgetfulness during development (`fn apply_cache_effect` won't compile if a caller passes 3 args instead of 4). But the refactor risk grows with each new bucket; V3.6.0.4 D3 will introduce a 4th bucket and that's a natural inflection point.

**Suggested closure** (DEFER to V3.6.0.4 D3 ship as part of that closure, NOT blocking V3.6.0.3 D2):

```rust
struct CacheBuckets<'a> {
    snapshot: &'a mut HashMap<(u16, u32, u32), CellState>,
    tombstones: &'a mut HashSet<u16>,
    format_cache: &'a mut HashMap<FormatId, Arc<str>>,
    // V3.6.0.4 D3: cell_op_index: &'a mut HashMap<(u16, u32, u32), Vec<usize>>,
}
fn apply_cache_effect(buckets: &mut CacheBuckets<'_>, effect: CacheEffect) { ... }
```

V3.6.0.4 D3 ship is the right place to introduce this refactor since it adds a 4th bucket anyway.

### D.2 -- LOW-2: Per-walk `Arc::<str>::from(string.as_str())` allocation in `collect_cache_effects`

**Scope**: `crates/ql-collab/src/session.rs:1097-1100`.

`collect_cache_effects` is called from two paths: `append_op` (O(1) per append) and `rebuild_snapshot_cache` (O(N) per full walk). For each `Op::RegisterFormat` encountered, the walker allocates a fresh `Arc<str>` via `Arc::<str>::from(string.as_str())`. The original `String` in the op is then consumed by `OpLog::append`. Per full rebuild over a 100-format workbook, this is 100 small heap allocations.

**Severity LOW** because: (a) format counts are bounded (production workbooks have < 100 custom formats per the V3.6.0.3 ship docstring); (b) the allocation is necessary if `CacheEffect::RegisterFormat` is to own the string (the alternative `&str` borrow would tangle lifetimes against the OpLog's Loro-backed iter).

**Suggested closure** (DEFER unless profiling justifies):

V3.7+ incremental snapshot deltas may want a string-interned arena: a `StringArena` on CollabSession with `intern_arc` that returns an `Arc<str>` from a `&str`, deduping across all `Op::RegisterFormat` applications in the log. Per-walk cost drops to O(N_unique_format_strings) instead of O(N_ops). Skip until V3.7+ profiling.

### E.2 -- INFO-2: Iteration cost of `formats` in `workbook_snapshot` is O(N_formats); negligible today but compounds with R-V3.5-1

**Scope**: `crates/ql-bindings-node/src/lib.rs:1690-1697`.

Each `workbook_snapshot` call:
1. Constructs fresh `Workbook::new()` (Phase 5.7 V3.5.0.2 design).
2. Replays the full op log via `replay_into` -> FormatTable.register_at for every `Op::RegisterFormat`.
3. Iterates `Workbook.formats().iter()` to build the `formats: Vec<FormatDefJson>`.

Cost: O(N_ops + N_formats). At V3.6-scale (typical < 100 formats), step 3 adds ~few microseconds. R-V3.5-1 already documents the per-call cost issue + says IDE callers MUST batch.

**Severity INFO** because the new field's cost is in the noise. Worth flagging because V3.6.0.5 D4 format-aware rendering will need the format strings on every render, and the same WorkbookSnapshotJson call powers both cells + formats; combining them is correct. But once V3.6.0.7 D6 profiling spike runs (per the V3.6.0.1 plan), the formats iteration cost should be measured.

### E.3 -- INFO-3: `pending_undo_cells` Mutex stale-data leak under `undo()` Err early-return (V3.6.0.2 carry, V3.6.0.3 unaffected but worth re-flagging)

**Scope**: `crates/ql-collab/src/session.rs:2876-2878`.

The V3.6.0.2 D1 audit (Codex Lane A INFO-1) flagged: `undo()` stages `pending_undo_cells = Some(pending_value)` BEFORE calling `self.undo.undo()?`. If Loro's undo errors (returning `Err(LoroError)`), the `?` propagates and the Mutex stays at `Some(stale)`. A subsequent `append_op` would then read the stale stash via the on_push closure. Marked "benign" because Loro's undo only errors on transactional-state issues, not common paths.

V3.6.0.3 doesn't touch this code, BUT the new `format_table_cache` adds a new failure surface: if `rebuild_snapshot_cache` errors mid-walk (op-log decode failure), the cache stays at the pre-call state (atomic-swap pattern), BUT the staged `pending_undo_cells` from the in-progress `undo()` is NOT cleared on the error path. Same shape as the V3.6.0.2 carry.

**Severity INFO** -- pre-existing pattern. Suggest unified hardening at V3.6.0.4 (defensive `pending_undo_cells = None` on any undo/redo `?` early-return).

### E.4 -- INFO-4: `register_format_op_populates_session_format_table_cache` test uses `format_table_cache_iter` directly; doesn't pin Workbook side via `rebuild_workbook` parity

**Scope**: `crates/ql-collab/src/session.rs:3918-3964` (V3.6.0.3 D2 regression tests).

The 2 new regression tests verify:

2. Cache rebuilds via full rebuild path.

Neither test verifies that the cache content MATCHES the workbook content after `rebuild_workbook`. The docstring claims "session cache is downstream mirror of Workbook FormatTable" but no test pins the equality. ## § G Forward-looking design recommendations

### G.1 -- V3.6.0.X audit-of-D2 should converge with this lane's HIGH-1 + MED-1 closures

The V3.6.0.X audit cycle (Codex Lane A + Opus Lane B) is the canonical site for cross-lane convergence + in-cycle closures. The two key candidates from this transcript:

1. **HIGH-1 (decision-lock deviation)**: needs either code patch (recommended) OR lock amendment. The Codex Lane A audit is likely to converge if Codex reads the V3.6.0.1 plan body alongside the shipped code; even if Codex doesn't catch it, this audit's transcript surfaces it explicitly.
2. **MED-1 (cache walker doesn't mirror FormatTable validation)**: complementary to HIGH-1; the entry().or_insert() closure + the Builtin range-check together produce a cache walker that's semantically identical to FormatTable::register_at for legal inputs + silently drops illegal ones. ### G.2 -- V3.6.0.4 D3 (per-cell op-index) should introduce `CacheBuckets<'a>` refactor

D.1's LOW recommendation: V3.6.0.4 D3 adds a 4th cache bucket (`cell_op_index`). Now is the natural inflection to bundle the bucket refs into a struct + change `apply_cache_effect` to take `&mut CacheBuckets<'_>`. Prevents future bucket-forgetfulness.

### G.3 -- V3.6.0.5 D4 (format-aware buildHtml) should NOT use `formats[]` ordering as a key

Per MED-2: `formats[]` order is non-deterministic across calls. V3.6.0.5 D4 cell renderer should build a `Map<string, string>` from `formats[]` indexed by stringified `FormatIdJson` (e.g., `"builtin:0"` / `"custom:peer_hex:counter"`) before rendering, never index by position.

### G.4 -- V3.7+ delta consumer of `format_table_cache_iter` MUST tolerate Builtin entries (or rely on HIGH-1 closure)

If HIGH-1 + MED-1 close in-cycle (cache walker mirrors FormatTable validation), V3.7+ delta consumers can safely treat `format_table_cache_iter` as Workbook-equivalent. If both stay deferred, V3.7+ consumers must filter out-of-range Builtins client-side.

### G.5 -- IDE write-path for Op::RegisterFormat is a V3.6+ gap not closed by V3.6.0.3 D2

V3.6.0.3 D2 ships the READ surface (workbookSnapshot.formats). There's no napi method to APPEND a RegisterFormat op. Per the V3.6.0.1 plan, the format-UI write-path (`appendSetCellFormat` + companion `appendRegisterFormat`) is V3.6+ scope. Worth flagging because today's IDE can DISPLAY format strings registered by foreign (e.g., qbook envelope) sources but can't ADD new ones through the napi. V3.6.0.5 D4 + V3.6.0.6 D5 don't address this; it's a separate sub-step.

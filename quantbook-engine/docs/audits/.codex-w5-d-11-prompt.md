## Microsoft canonical algorithm (port reference)

PERCENTILE.INC(array, k):
- Sort array ascending. n = len.
- Validate `0.0 <= k <= 1.0` else `#NUM!`.
- Single-element array → return that element for any valid k.
- Position = `k * (n - 1)`.
- `lo = floor(pos) as usize`.
- If `lo + 1 >= n` (occurs at k=1.0 or n=1 edge) → return `sorted[n-1]`.
- Otherwise: `frac = pos - lo as f64`, return
  `sorted[lo] + frac * (sorted[lo + 1] - sorted[lo])`.

PERCENTILE.EXC(array, k):
- Sort array ascending. n = len.
- Validate `1/(n+1) <= k <= n/(n+1)` else `#NUM!`. This
  AUTOMATICALLY rejects k=0 and k=1.
- Position = `k * (n + 1) - 1`.
- `lo = floor(pos) as usize`.
- If `lo + 1 >= n` (at upper bound k = n/(n+1) → pos = n - 1) →
  return `sorted[n-1]`.
- Otherwise: linear interpolation.

QUARTILE.INC(array, q):
- Validate `q in {0, 1, 2, 3, 4}` (truncate fractional toward
  zero first) else `#NUM!`.
- Delegate to `percentile_inc_at(sorted, q as f64 / 4.0)`.

QUARTILE.EXC(array, q):
- Validate `q in {1, 2, 3}` (truncate fractional toward zero
  first) else `#NUM!` — Microsoft canon rejects q=0 and q=4 (use
  .INC for min/max).
- Delegate to `percentile_exc_at(sorted, q as f64 / 4.0)`.

## What to look for

### Correctness

1. **Microsoft Position formulas**:
   - INC: `pos = k * (n - 1)` — verify the `(n - 1)` not `(n + 1)`.
   - EXC: `pos = k * (n + 1) - 1` — verify the `- 1` is present.
   - Mistakes here would silently shift percentiles by a quantile.

2. **EXC bound validation `1/(n+1) <= k <= n/(n+1)`**:
   - Lower bound `1/(n+1)`: at this exact k, pos = 0 → return
     sorted[0] (minimum).
   - Upper bound `n/(n+1)`: at this exact k, pos = n - 1 → return
     sorted[n-1] (maximum).
   - k below lower or above upper → `#NUM!`.
   - For n=1 the valid range degenerates to {0.5}.

3. **k = 1.0 edge case in INC**: pos = n - 1 → lo = n - 1 →
   `lo + 1 = n >= n`. The fall-through branch returns
   `sorted[n - 1]`. Verify this path doesn't index out of bounds.

4. **NaN safety on k**: My `extract_percentile_k` accepts
   `Value::Number(n)` and passes it through. Excel doesn't
   produce NaN literals, but our engine COULD theoretically
   produce `Value::Number(NaN)` if a downstream computation
   created one. The contains-range checks use `(0.0..=1.0)`
   which returns false for NaN, so `!(0.0..=1.0).contains(&NaN)`
   is true → `#NUM!`. Verify this short-circuit holds.
   Same analysis for infinite k.

5. **`pos.floor() as usize` overflow**: For valid k in INC range
   `[0, 1]`, pos in `[0, n - 1]`. For valid k in EXC range
   `[1/(n+1), n/(n+1)]`, pos in `[0, n - 1]`. Both fit safely.

6. **Empty after coercion → `#NUM!`** (matches LARGE/SMALL/MEDIAN
   convention). Path: `collect_numbers_strict` may return an
   empty Vec from an all-Blank range (Blank → NumericArg::Skip).
   My check `if arr.is_empty()` comes BEFORE the sort + kernel
   call. Verify the early-return correctness.

7. **Quartile truncation toward zero**: `q.trunc() as i64` for
   `q = 2.9` gives 2 (correct). For `q = -0.5` gives 0 (NOT -1).
   For QUARTILE.INC this means q=-0.5 passes the `(0..=4)`
   check. Is this the right Excel behavior? Per docs, "If quart
   is not an integer, it is truncated" — Excel uses INT() which
   is FLOOR toward -∞, NOT trunc toward zero. For positive q
   they agree; for q in (-1, 0) they DIVERGE:
   - Trunc: -0.5 → 0 → valid.
   - INT: -0.5 → -1 → #NUM!.
   This is a potential divergence — flag it for review.

8. **Engine-wide text → #VALUE! divergence**: My docstring says
   "text in range raises #VALUE! per W5-58 strict convention".
   Microsoft canon for PERCENTILE/QUARTILE skips text in the
   data array. Documented divergence (matrix + coverage); flag
   if you think we should match Microsoft instead.

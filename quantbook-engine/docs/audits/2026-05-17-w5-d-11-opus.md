## Summary

W5-D-11 is **mathematically correct and committable**. The position formulas are right (`k*(n−1)` for INC; `k*(n+1)−1` for EXC), bound checks are correct, no panic risk on NaN/Inf k (both kernels' `(lo..=up).contains(&k)` rejects NaN cleanly), no usize-overflow risk for realistic arrays, the QUARTILE wrappers delegate consistently to PERCENTILE.* via `k = q/4`, the legacy `PERCENTILE` / `QUARTILE` aliases register to the `.INC` variant per Excel 2010+ canon, and the e2e test verifies case-insensitive dotted-name dispatch.

**No HIGH findings.** **1 MEDIUM** (under-pinning of PERCENTILE.EXC test coverage relative to PERCENTILE.INC). **6 LOW** (negative-fractional `quart` boundary not pinned, matrix test-count drift, docstring/test-comment inaccuracies, missing test coverage for the documented Excel-compat boundaries).

Two key Excel-compat points were resolved during the audit by external verification (Codex consultation, citing Microsoft docs):
1. **Truncation direction for fractional `quart` arg**: Excel uses **TRUNC** (toward zero), confirmed via Microsoft's TRUNC function doc (https://support.microsoft.com/en-us/office/trunc-function-8b86a64c-3127-43db-ba14-aa5ceb292721) cross-referenced with the QUARTILE.INC doc (https://support.microsoft.com/en-us/office/quartile-inc-function-1bbacc80-5075-42f1-aed6-47d735c4819d). The implementation's `n.trunc() as i64` is **correct per Microsoft canon**, NOT an engine-consistency-only choice as I initially assumed. The remaining concern is just that the negative-fractional boundary (e.g. `quartile_inc(arr, -0.5) → minimum`, not `#NUM!`) is not pinned by an explicit test.
2. **PERCENTILE.EXC boundary inclusivity at `k = 1/(n+1)` and `k = n/(n+1)`**: Excel **includes** the boundary (e.g. `PERCENTILE.EXC({1,2,3,4}, 0.2) = 1`), confirmed via the Microsoft EXC docs. The implementation's `(lower..=upper).contains(&k)` (inclusive range) is **correct per Microsoft canon**. The unit tests `percentile_exc_k_at_lower_bound_returns_minimum` and `percentile_exc_k_at_upper_bound_returns_maximum` already pin this correctly.
3. **EXC text-handling divergence** — already noted in the matrix as engine-wide W5-58 strict convention. Confirmed consistent with sibling fns (MEDIAN / LARGE / SMALL / MODE / RANK). Microsoft's docs are silent on text handling for PERCENTILE/QUARTILE family; the engine's strict W5-58 convention is a deliberate, documented divergence shared across all sibling fns.

The implementation reuses the well-established `collect_numbers_strict` + `extract_*` + `sort_asc` pattern already shared by `large` / `small` / `median` / `mode`, so the layered semantics are consistent with the engine and audit-debt-free at the helper layer.

## MEDIUM

### MEDIUM-1 — PERCENTILE.EXC text-in-range / boolean / NaN-k semantics: under-pinning

**Where:** `crates/ql-functions/src/range_fns.rs` test block 4701-4825 (PERCENTILE.EXC tests).

**Detail:** Compared against PERCENTILE.INC's 16-test suite, PERCENTILE.EXC has 12 tests. Gaps:

1. **No Boolean-k coercion pin for PERCENTILE.EXC.** PERCENTILE.INC pins `percentile_inc_boolean_k_coerces` (TRUE → 1.0 → max, FALSE → 0.0 → min). The EXC counterpart would be informative — TRUE → 1.0 should hit `!(lower..=upper).contains(&1.0)` → `#NUM!`; FALSE → 0.0 → same → `#NUM!`. This pins the contract that EXC rejects {0, 1} via the engine-strict bound check, not via a separate clamp.

2. **No text-k pin for PERCENTILE.EXC.** PERCENTILE.INC pins `percentile_inc_text_k_is_value_error` (text k → `#VALUE!`). PERCENTILE.EXC routes through the same `extract_percentile_k` helper so behavior is shared, but the test isn't pinned. Same applies to `percentile_inc_error_in_k_propagates` — no EXC counterpart.

3. **No skip-blank-in-range pin for PERCENTILE.EXC.** PERCENTILE.INC has `percentile_inc_skips_blank_in_range`; PERCENTILE.EXC does not.

4. **No NaN-k pin for either.** While my compiled probe confirmed both kernels reject NaN k via `(0..=1).contains(&NaN) == false` and the engine's `to_number_strict_skip_blank` already maps NaN-bypassing `Value::Number(NaN)` to `#NUM!` upstream, **the test suite does not pin the NaN-k behavior**. Pinning it would harden the implementation against a future refactor that bypasses the `(range).contains` rejection (e.g. if someone re-orders the checks).

**Recommendation:** Add 4 small tests for PERCENTILE.EXC (Boolean k, text k, error k, skip-blank) + 1 NaN-k test for each (PERCENTILE.INC and PERCENTILE.EXC). This brings PERCENTILE.EXC's test count up from 12 → 16 (parity with PERCENTILE.INC) and pins the panic-safety contract explicitly. Fix in a `.1` closure commit.

**Severity rationale:** No correctness bug — the behavior is correct under the current code path. But the missing pins mean a future refactor could silently change behavior without test failure. NaN-k in particular: a refactor that moves the bound check below the `pos.floor() as usize` cast (which is `0` for NaN, not a panic in safe-cast Rust) would silently return `sorted[0]` instead of `#NUM!` — a real correctness regression that would slip through.

## LOW

### LOW-1 — Negative-fractional `quart` (the TRUNC boundary) is not pinned by a unit test

**Where:** `crates/ql-functions/src/range_fns.rs` (no test exists).

**Detail:** Per Codex's documentation review (citing Microsoft TRUNC + QUARTILE.INC docs), Excel truncates a fractional `quart` argument toward zero (TRUNC, not FLOOR). The current implementation uses `n.trunc() as i64` — **correct per Microsoft canon**. But the test suite only pins the positive-fractional case (`quartile_inc_q_truncates_toward_zero`: 2.9 → 2). The negative-fractional case (e.g. `quartile_inc(arr, -0.5)` should return the minimum, NOT `#NUM!`) is NOT pinned. A naive future refactor to `n.floor() as i64` (a plausible misreading of "truncated") would silently change behavior on a sliver of input space without test failure.

**Recommendation:** Add `quartile_inc_q_negative_fraction_truncates_toward_zero` covering at minimum:
```rust
// q = -0.5 truncates toward zero (TRUNC, not FLOOR) → q=0 → minimum (Microsoft canon).
let arr = r(vec![n(1.0), n(2.0), n(3.0), n(4.0), n(5.0)]);
approx_scalar(quartile_inc(&[arr.clone(), s(n(-0.5))]), 1.0, 1e-12);
// q = -0.99 still truncates to 0 → minimum.
approx_scalar(quartile_inc(&[arr.clone(), s(n(-0.99))]), 1.0, 1e-12);
// q = -1.01 truncates to -1 → invalid → #NUM!.
assert_eq!(quartile_inc(&[arr, s(n(-1.01))]), Value::Error(ErrorValue::Num));
```

Same for QUARTILE.EXC (where q=-0.5 → q=0 → still #NUM! since EXC requires q in {1,2,3}). Bonus: matrix narrative could explicitly cite "Excel TRUNC (toward zero), per Microsoft TRUNC + QUARTILE.INC docs" for the audit trail.

**Severity rationale:** Pure test-coverage gap. The code is correct per Microsoft canon (verified via Codex consultation of Microsoft TRUNC doc). LOW because no behavioral bug — but worth pinning to defend against a future TRUNC→FLOOR refactor.

### LOW-3 — Comment inaccuracy: `0.3 * 3 = 0.9` (actually 0.8999...)

**Where:** `crates/ql-functions/src/range_fns.rs:4548` (test `percentile_inc_microsoft_example` comment).

**Detail:** The comment says:
```
// pos = 0.3 * 3 = 0.9 → interpolate between sorted[0]=1 and
// sorted[1]=2 with frac=0.9 → 1 + 0.9*(2-1) = 1.9.
```

In IEEE 754 double precision, `0.3 * 3.0 == 0.8999999999999999`, not `0.9`. The test still passes (the algebraic result rounds to 1.9 within the 1e-12 tolerance), but the comment's mathematical setup is fp-naive.

**Recommendation:** Either annotate the fp drift (`pos = 0.3 * 3 ≈ 0.9 (actually 0.8999... in fp; algebraically rounds to 1.9 within 1e-12 tolerance)`) or drop the intermediate computation altogether.

**Severity rationale:** Documentation hygiene; no functional impact.

### LOW-6 — Comment about NaN unreachability is partially defensive theater

**Where:** `crates/ql-functions/src/range_fns.rs:1684-1686` (`sort_asc` doc comment).

**Detail:** The comment says:
```
/// last. NaN can't reach this kernel — `to_number_strict_skip_blank`
/// rejects it upstream — but the `unwrap_or(Equal)` is the defensive
/// convention already used by `large` / `small` / `median`.
```

This is technically correct for **range data** (which flows through `collect_numbers_strict` → `to_number_strict_skip_blank` → `sanitize_f64`). But it's **partially misleading** because the `k` argument flows through `extract_percentile_k` which does **NOT** call `sanitize_f64` and so **can** propagate a `Value::Number(NaN)` to the kernel. The kernel then catches it via `!(0..=1).contains(&NaN) == true` (because `NaN.partial_cmp(anything) == None`), but the "NaN can't reach this kernel" framing applies only to the sorted-array path, not the k path.

**Recommendation:** Tighten the comment to "NaN can't reach the **data array** here — `to_number_strict_skip_blank` rejects it upstream — but the `unwrap_or(Equal)` is the defensive convention already used by `large` / `small` / `median`. (Scalar `k` NaN is caught separately by the `!(0..=1).contains(&k)` bound check.)"

**Severity rationale:** Doc precision; no functional impact. Flagged because future maintainers might rely on the "NaN can't reach here" guarantee in a refactor.

# W5-D-8 Opus Audit: BITAND / BITOR / BITXOR / BITLSHIFT / BITRSHIFT
Date: 2026-05-17

## Summary

Independent post-implementation review of W5-D-8 (Phase 4.10 V1-260 closeout
— BIT* engineering family ported from IronCalc `engineering/bit_operations.rs`).

Scope: 5 modified files (uncommitted on `feat/quantbook-engine` atop
`cfa14ed2055`). 5 new scalar `pub fn`s, 5 registry entries (registry count
bumped `238 → 243`), 5 coverage rows, 53 unit tests, 1 e2e dispatch test,
5 matrix rows replacing a placeholder.

**Verdict: SHIP BLOCKED on two HIGH issues, both in the shift family.**

The HIGHs are *correctness* divergences from Excel canon: the
overflow guard `result_f.abs() > BIT_MAX` is **insufficient** to catch
all in-domain inputs that overflow the i64 representation modulo
`2^64`. Concretely:

- `BITLSHIFT(65_536, 48)` returns `Value::Number(0.0)` instead of `#NUM!`
  (mathematical result is `2^64`; `i64::wrapping_shl` produces `0`;
  `abs(0.0) <= BIT_MAX` so the guard passes through a clearly-wrong value).
- `BITLSHIFT(281_474_976_710_655, 16)` returns `Value::Number(-65_536.0)`
  instead of `#NUM!` (mathematical result is `2^64 - 2^16 ≈ 1.844e19`;
  `i64::wrapping_shl` produces `-65_536`; the guard checks `.abs()`
  which is `65_536 <= BIT_MAX`, so a *negative* result is returned —
  doubly wrong since the function is supposed to produce values in
  `[0, 2^48-1]`).
- `BITRSHIFT(65_536, -48)` and `BITRSHIFT(2^48-1, -16)` are symmetric:
  the negative-shift branch invokes `wrapping_shl` and hits the same
  trap.

These cases are confirmed by direct `rustc` execution against the same
`wrapping_shl` semantics (see HIGH-1 evidence block below). IronCalc's
plain `<<`/`>>` operators panic in debug on `>= 64`-bit shifts but in
release they share the wrap-mod-2^64 semantics, so IronCalc has the same
underlying defect — but neither IronCalc's tests nor ours pin the
pathological inputs. We are not strictly worse than IronCalc, but
Excel canon is what we promise to compatibility users, and Excel canon
says `#NUM!`.

Outside the shift bugs, the batch is in good shape:
- Validate helpers (`validate_bit_pair`, `validate_bit_shift`) correctly
  factor the IronCalc-equivalent integer / non-negative / `[0, BIT_MAX]`
  checks for the three pure-bitwise fns.
- `BIT_MAX = 281_474_976_710_655` is exactly `2^48 - 1` — matches
  IronCalc's `MAX` constant and Microsoft's documented domain.
- `to_number_strict` correctly rejects text with `#VALUE!` and
  propagates `Error(e)` — verified against `crates/ql-types/src/coercion.rs:29-37`.
- Negative-shift inversion (`BITLSHIFT(x, -s) = BITRSHIFT(x, s)`) is
  pinned by tests for the cases that don't wrap.
- Coverage shape is consistent across the batch (closed-form, identity,
  above-max, negative, non-integer, text, error-prop, arity) with two
  cross-fn property tests (round-trip + algebraic identity).
- 5/5 registry entries, 5/5 coverage rows, 5/5 matrix rows, e2e covers
  case-insensitive lookup.

## HIGH

### HIGH-1: BITLSHIFT result-overflow guard fails on mod-2^64 wrap-to-zero

**File**: `crates/ql-functions/src/scalar_fns.rs:3366-3375` (and
symmetric for BITRSHIFT negative branch at `:3400-3408`).

The current guard:

```rust
let result = if s_i >= 0 {
    n_i.wrapping_shl(s_i as u32)
} else {
    n_i.wrapping_shr((-s_i) as u32)
};
let result_f = result as f64;
if result_f.abs() > BIT_MAX {
    return Value::Error(ErrorValue::Num);
}
Value::Number(result_f)
```

is intended to catch "result overflows the Excel canon `[0, 2^48-1]`
domain". It works for results that exceed BIT_MAX in absolute value
within i64 (e.g., `2^47 << 2 = 2^49`, properly caught). It **fails** when
the wrapping shift produces a value whose `.abs()` happens to fall back
inside `[0, BIT_MAX]` — which is reachable in-domain.

**Reproduction** (rustc release, 1.x):

```text
BITLSHIFT(65_536, 48):
  wrapping_shl raw: 0
  as f64: 0.0, abs: 0.0
  passes guard (abs <= BIT_MAX): true
  → returns Value::Number(0.0)
  Excel canon: 65_536 × 2^48 = 2^64 > 2^48-1 → #NUM!
```

Both args are in-domain: `65_536 ≤ BIT_MAX` and `48 ≤ 53`. Multiple
in-domain pairs hit the same trap, including:
- `(65_536, 48)` → wraps to 0
- `(32_768, 49)` → wraps to 0
- `(16_384, 50)` → wraps to 0
- `(8_192, 51)` → wraps to 0
- `(4_096, 52)` → wraps to 0
- `(2_048, 53)` → wraps to 0

The shape is general: any `n = 2^k`, `s = 64 - k` for `0 ≤ k ≤ 16`
(so that `n ≤ BIT_MAX` and `s ≤ 53`) produces this exact zero wrap.

**Fix options** (ordered by clarity):

1. **Compute the result in f64 and compare** before any i64 truncation:
   ```rust
   let result_f = (n_i as f64) * 2f64.powi(s_i as i32);
   if !(0.0..=BIT_MAX).contains(&result_f) {
       return Value::Error(ErrorValue::Num);
   }
   Value::Number(result_f)
   ```
   For `|s| ≤ 53` and `n ≤ 2^48-1`, the maximum *legitimate* result is
   `BIT_MAX` itself; everything above goes to `#NUM!`. f64 has 53-bit
   mantissa precision so all in-domain results are exactly
   representable. This matches Excel's f64-based arithmetic exactly.

2. **Check before-shift** using `i64::leading_zeros`:
   ```rust
   let shifted = if s_i >= 0 {
       if (n_i as u64).leading_zeros() < s_i as u32 + 16 {
           return Value::Error(ErrorValue::Num);
       }
       n_i << s_i
   } else { n_i >> -s_i };
   if shifted > BIT_MAX as i64 { return #NUM; }
   ```
   More complex; the f64 path is preferable.

3. **Use `checked_shl` + domain check**:
   ```rust
   let result = n_i.checked_shl(s_i as u32).ok_or(...)?;
   if result < 0 || result > BIT_MAX as i64 {
       return Value::Error(ErrorValue::Num);
   }
   ```
   Note that `checked_shl` only checks the *shift amount* not the
   result domain, so the `> BIT_MAX` check is still needed; but it
   also doesn't catch the `2^16 << 48` case because the shift amount
   is in-bounds (`48 < 64`). So option 3 is **insufficient on its own**.

Recommendation: **option 1** is the cleanest. Excel's arithmetic is
already f64-based and the bound `(BIT_MAX × 2^53)` is well within f64
range. After the fix, drop `wrapping_shl`/`wrapping_shr` entirely — the
bitwise ops aren't even needed when you can multiply/divide by 2^s.

**Test additions required**:

```rust
#[test]
fn bitlshift_wrapping_mod_2_64_is_num_error() {
    // (2^16) << 48 = 2^64 — wraps to 0 in i64; must be #NUM!.
    assert_eq!(bitlshift(&[n(65_536.0), n(48.0)]), Value::Error(ErrorValue::Num));
    // (2^15) << 49 = 2^64 — same trap.
    assert_eq!(bitlshift(&[n(32_768.0), n(49.0)]), Value::Error(ErrorValue::Num));
    // BIT_MAX << 16 — wraps to a negative i64; abs(-65536) < BIT_MAX
    // so the current guard mis-passes.
    assert_eq!(
        bitlshift(&[n(281_474_976_710_655.0), n(16.0)]),
        Value::Error(ErrorValue::Num)
    );
}

#[test]
fn bitrshift_wrapping_mod_2_64_is_num_error() {
    // Symmetric: negative-shift BITRSHIFT goes through wrapping_shl.
    assert_eq!(bitrshift(&[n(65_536.0), n(-48.0)]), Value::Error(ErrorValue::Num));
    assert_eq!(
        bitrshift(&[n(281_474_976_710_655.0), n(-16.0)]),
        Value::Error(ErrorValue::Num)
    );
}
```

### HIGH-2: Negative result from wrapping-shift escapes the domain guard

Sub-case of HIGH-1 but separable because the fix is independent of the
overflow detection — even after HIGH-1 is fixed via option 1, the
abs-only guard `result_f.abs() > BIT_MAX` would *still* let a negative
`result_f` through if it slipped past detection. The deeper issue is
that **bitwise-AND/OR/XOR/SHIFT outputs in Excel are always in
`[0, 2^48-1]`** — there is no legitimate negative result. The guard
should be a domain check, not a magnitude check:

```rust
if !(0.0..=BIT_MAX).contains(&result_f) {
    return Value::Error(ErrorValue::Num);
}
```

This also covers the BITLSHIFT-of-BIT_MAX-by-16 case (which wraps to
`-65_536` and currently returns `Value::Number(-65_536.0)`).

(For BITAND/BITOR/BITXOR the i64 ops can't produce a negative because
both operands are non-negative after `validate_bit_pair`, and the
results of those ops on non-negative i64s stay non-negative. So this
domain check is shift-specific.)

## MEDIUM

### MEDIUM-1: Coverage shape missing the wrap-to-zero / wrap-to-negative case

Pre-existing tests `bitlshift_result_overflow_is_num_error` (`2^47 << 2`)
and `bitrshift_negative_shift_overflow_is_num_error` (`2^47 >> -2`)
both pin overflow cases **that stay inside i64's positive range** and
correctly hit the `> BIT_MAX` guard. Neither covers the pathological
`(small_n × large_s)` pairs where the i64 wraps to a value back inside
the domain.

This is the proximate cause of HIGH-1 / HIGH-2 not being caught by the
test suite. Even if the implementation is rewritten per HIGH-1 option 1,
these tests should be added to prevent regression — they're a known-trap
class for any future port.

### MEDIUM-2: BITXOR missing `max_value_canon` test (coverage shape gap)

BITAND has `bitand_max_value_canon` (BIT_MAX & BIT_MAX = BIT_MAX).
BITOR has `bitor_max_value_canon` (0 | BIT_MAX = BIT_MAX).
BITXOR has **no** max-value canon test.

The natural fixture would be `BITXOR(BIT_MAX, 0) = BIT_MAX` (showing
that BIT_MAX is accepted at the upper edge for BITXOR too). Currently
BITXOR is 9 tests vs BITAND/BITOR at 10. Asymmetry isn't a bug but the
matrix-doc footprint is uneven, and the coverage-row note ("above-max
#NUM!") implies-but-doesn't-pin "exactly-at-max is accepted".

Minor; add one test for symmetry.

### MEDIUM-3: `validate_bit_shift` re-truncates the already-checked f64

```rust
fn validate_bit_shift(number: f64, shift: f64) -> Result<(i64, i64), ErrorValue> {
    if number.trunc() != number { return Err(ErrorValue::Num); }
    if !(0.0..=BIT_MAX).contains(&number) { return Err(ErrorValue::Num); }
    if shift.abs() > 53.0 { return Err(ErrorValue::Num); }
    Ok((number.trunc() as i64, shift.trunc() as i64))   // <- number.trunc() again
}
```

`number.trunc()` is called twice (once in the integer check, once in
the cast). Equivalent to `number as i64` after the integer check — the
double-trunc is wasteful but not wrong. Same shape in `validate_bit_pair`
(line 3260). Consider:

```rust
Ok((number as i64, shift.trunc() as i64))
```

Minor; cosmetic. Not blocking.

### MEDIUM-4: `bit_de_morgan_xor_identity` docstring claim is too narrow

```rust
// a ^ b = (a | b) - (a & b) — informal but useful.
//
// (a | b) - (a & b) = a ^ b — informal but useful.
// ...
// a ^ b = (a | b) - (a & b) when there's no carry overlap.
```

The comment "when there's no carry overlap" / "bit-disjoint values"
suggests the identity is conditional. It's **not** — `a ^ b = (a | b) - (a & b)`
holds for all non-negative integers (because
`a + b = (a | b) + (a & b)` and `a ^ b = a + b - 2(a & b)`, so
`a ^ b = (a | b) + (a & b) - 2(a & b) = (a | b) - (a & b)`).

The fixture values used (54, 43) have non-zero `a & b` and the test
still passes — confirming the identity is unconditional. Just clean up
the comment.

## Confirmed Non-Issues

- **BIT_MAX value**: `281_474_976_710_655 == 2^48 - 1`. Confirmed by
  rustc: `(1i64 << 48) - 1 = 281_474_976_710_655`. Matches IronCalc
  `MAX = 281474976710655.0` (`engineering/bit_operations.rs:8`) and
  Microsoft documented domain.
- **Integer-rejection asymmetry on shift fns**: IronCalc only enforces
  `number.trunc() == number` on the first arg of the shift fns; the
  shift arg is silently truncated. Our `validate_bit_shift` follows
  the same pattern (line 3274). Faithful parity.
- **`|shift| <= 53` check**: matches IronCalc line 157, 211. Both use
  `>` not `>=` so 53 itself is allowed. Test `bitlshift_shift_above_53_is_num_error`
  pins shift=54 → #NUM!. Implicitly: shift=53 is accepted. Correct.
- **i64 cast safety post-validate**: After `validate_bit_pair` /
  `validate_bit_shift`, all values are in `[0, BIT_MAX]` where
  `BIT_MAX = 2^48 - 1 ≪ i64::MAX = 2^63 - 1`. `f64::trunc() as i64`
  is exact for these values (f64 has 53-bit mantissa, 48 bits fit). Safe.
- **`wrapping_shl`/`wrapping_shr` for in-domain inputs with sane
  shifts**: For `shift ∈ [0, 53]` of a value `n ≤ 2^48-1`, when the
  mathematical result fits in i64 (i.e., total bit width ≤ 63), wrapping
  behavior is identical to non-wrapping. The divergence-from-IronCalc
  flagged in the prompt does **not** apply for those inputs. (The
  divergence that DOES happen — wrap-mod-2^64 to a domain-pass value —
  is the HIGH issue above and is not actually IronCalc parity; IronCalc
  in release exhibits the same wrap-then-pass behavior, just via plain
  `<<`. Both ports diverge from Excel canon.)
- **Negative-shift direction inversion**: `BITLSHIFT(x, -s) = x >> s`,
  `BITRSHIFT(x, -s) = x << s`. Matches IronCalc's `if shift > 0 ...
  else ...` branches (lines 167-171 / 221-225). Pinned by tests
  `bitlshift_negative_shift_is_right_shift` (8 << -2 = 2) and
  `bitrshift_negative_shift_is_left_shift` (2 >> -3 = 16).
- **`(-s_i) as u32` cast for `s_i ∈ [-53, -1]`**: `(-s_i) ∈ [1, 53]`,
  cast to u32 is exact. No edge case at `s_i = i64::MIN` because
  `|shift| ≤ 53` filters it out before the cast. Safe.
- **`shift = -0.0` edge case**: passes integer check
  (`(-0.0).trunc() == -0.0`), abs check (0.0 ≤ 53.0), truncates to
  `0_i64`, then `s_i >= 0` branch fires with `wrapping_shl(0) = n_i`.
  Identity. Correct.
- **Number-arg `-0.0` edge case**: passes integer check, in-domain
  check (`(-0.0..=BIT_MAX).contains(&-0.0)` is true because `-0.0 >= 0.0`
  in Rust), truncates to `0_i64`. Correct.
- **Registry registration**: 5 fresh `r.register(...)` calls, count
  bumped 238 → 243 (verified by `awk` between the `default_registry`
  body braces). No double-registration (verified by sort+uniq -d on
  all `register*` calls in the body). e2e covers case-insensitive
  lookup (`bitand(12, 10)`). Good.
- **Coverage entries**: 5/5 entries match the 5 registered fns;
  descriptions mention the W5-D-8 batch, the canon, and the test
  shape. Good.
- **Matrix rows**: 5 new `✅` rows replace one `❌` placeholder;
  test counts (10/10/9/11/11) match the actual `fn bit*_` count in
  the impl. Good.
- **`coercion::to_number_strict` propagates `ErrorValue` correctly**:
  verified against `crates/ql-types/src/coercion.rs:29-37`.
  `Value::Blank → 0.0`, `Value::Number(n) → n` (NaN/Inf → `#NUM!` via
  `sanitize_f64`), `Value::Boolean → 1.0/0.0`, `Value::Text → #VALUE!`,
  `Value::Error(e) → e`. Tests `bit*_error_arg_propagates` pin the
  error-propagation path (RefError + DivZero used).
- **Out-of-scope code untouched**: `git diff --stat HEAD` confirms
  exactly 5 modified files, no other code edits.

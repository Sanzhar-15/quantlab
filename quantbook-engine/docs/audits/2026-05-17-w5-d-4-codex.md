## HIGH

### CODEX-HIGH-1

Subject: `BINOM.INV` still panics for the zero-trial degenerate distribution

Where: `crates/ql-functions/src/distribution_fns.rs:1056`

Detail: The implementation correctly short-circuits `p == 0.0`, but `trials == 0` is also a constant-CDF binomial distribution. The domain check allows `trials >= 0`, matching IronCalc. For `BINOM.INV(0, 0.5, 0.5)`, `n` becomes `0`, `p != 0.0`, and the code reaches `dist.inverse_cdf(alpha)`. In statrs 0.18.0, `Binomial::cdf(x)` returns `1.0` for every `x >= n`; with `n == 0`, the default `DiscreteCDF::inverse_cdf` calls `integral_bisection_search` over an interval where both endpoints have CDF `1.0`. Because `alpha` is in `(0, 1)`, the search returns `None`, and statrs unwraps it. This is the same panic shape documented for `p == 0`, just through a second degenerate case.

Recommendation: Short-circuit before calling statrs inverse when `n == 0` as well as `p == 0.0`, returning `Value::number(0.0)`. Add unit and dispatcher regressions for `BINOM.INV(0, 0.5, 0.5)`. Consider documenting this together with the `p == 0` IronCalc-divergent panic avoidance.

Severity rationale: HIGH because a valid user formula can panic the engine instead of returning a spreadsheet value. The expected mathematical result is unambiguous: the only possible success count is `0`, so the smallest `k` with `CDF(k) >= alpha` is `0`.

## MEDIUM

### CODEX-MEDIUM-1

Subject: `to_u64_index` accepts the f64 value `2^64` and saturates it to `u64::MAX`

Where: `crates/ql-functions/src/distribution_fns.rs:244`

Detail: The guard uses `v > u64::MAX as f64`. On Rust/f64, `u64::MAX as f64` rounds up to `18446744073709551616` (`2^64`), not the exact integer max. Therefore the f64 value `2^64` passes the guard and `v as u64` saturates to `u64::MAX`. This is memory-safe, but it is not the documented semantic check "exceeds `u64::MAX` -> `#NUM!`" and it affects every W5-D-4 discrete integer argument routed through `to_u64_index`.

Recommendation: Treat the upper bound as exclusive in f64 space: reject `v >= u64::MAX as f64`, or introduce a named constant/comment explaining that `u64::MAX as f64` is `2^64`. Add boundary tests for each discrete public surface or at least for the helper's callers using `Value::Number(u64::MAX as f64)`.

Severity rationale: MEDIUM because the issue is limited to extreme numeric inputs, but it violates the stated overflow contract and can silently feed maximum-size indices/trial counts into statrs instead of returning `#NUM!`.

## LOW

### CODEX-LOW-1

Subject: BINOM.DIST matrix anchor is malformed

Where: `docs/compat/excel-matrix.md:114`

Detail: The matrix says `pmf(0/5/10; n=10, p=0.5) = 1/252/1024-1024`. That is not a valid statement of the three anchors and is easy to misread as an arithmetic expression.

Recommendation: Replace it with the explicit anchors: `pmf(0)=1/1024`, `pmf(5)=252/1024`, `pmf(10)=1/1024`.

Severity rationale: LOW because runtime behavior is unaffected; the compatibility matrix is just misleading on a simple closed-form anchor.

### CODEX-LOW-2

Subject: Coverage text overstates W5-D-4 test counts and one BINOM.DIST anchor

Where: `crates/ql-functions/tests/coverage.rs:822`; `crates/ql-functions/tests/coverage.rs:826`

Detail: The W5-D-4 coverage comment says "Per-fn >=10 tests", but the actual matrix and unit suite have 8 or 9 tests for several functions, which still satisfies the requested >=8 threshold. The `BINOM.DIST` entry also claims `pmf(10)` is covered; the current direct unit tests cover `pmf(0)`, `pmf(5)`, `CDF(0)`, and `CDF(n)`, but not `pmf(10)` specifically.

Recommendation: Reword the summary to "Per-fn >=8 tests" and either remove the `pmf(10)` claim or add the missing `pmf(10; n=10, p=0.5) = 1/1024` test.

Severity rationale: LOW because the implementation has adequate coverage under the requested design threshold. The risk is audit/accounting drift, not a behavior regression.

### CODEX-LOW-3

Subject: `BINOM.INV p == 0` divergence is not listed in the module's IronCalc divergence section

Where: `crates/ql-functions/src/distribution_fns.rs:212`; `crates/ql-functions/src/distribution_fns.rs:1044`

Detail: The inline implementation comment documents the statrs panic and mathematical return value for `p == 0`, but the top-level "IronCalc divergences" section only documents coercion and error-class differences. This batch intentionally diverges from IronCalc by not panicking on `BINOM.INV(..., 0, alpha)`, and the prompt calls out that this should be documented as IronCalc-divergent-but-mathematically-correct.

Recommendation: Add a W5-D-4 bullet to the IronCalc divergences section for `BINOM.INV` degenerate binomials. If CODEX-HIGH-1 is fixed, document both `p == 0` and `trials == 0` as panic-avoidance cases.

Severity rationale: LOW because the code path for `p == 0` is correct. The issue is that the public module documentation under-reports an intentional IronCalc divergence.

## One-paragraph verdict

The W5-77 → W5-83 arc ships a complete Excel number-format pipeline:
lexer → parser → renderer → FormatTable/CellFormatOverlay storage →
op-log ops → .qbook schema v4 → WorkbookRuntime wrappers → TEXT()
formula function. The overall architecture is clean: append-before-mutate
ordering is consistent, schema v3→v4 backwards compatibility is correct,
and the TEXT() function faithfully implements all Excel-canon error
propagation rules. **However two real correctness bugs exist that the
current test suite does not catch.** First (MEDIUM): the `walk_for_anchor`
backward scanner in `parser.rs` does not treat `Token::DateM` as a
stopping point, causing "h:mm m" to produce [Minute, Minute] instead of
the spec-mandated [Minute, Month] — a case explicitly listed in mini-spec
§ 12.2 as a required test that is absent. Second (LOW): the lexer accepts
"PM/AM" and "P/A" as valid AM/PM tokens despite these reversed forms
being absent from mini-spec § 2. Three additional MEDIUM gaps in test
coverage round out the findings: equivalence testing ignores format state,
the full persistence round-trip for format ops has no E2E test, and
MASTER-PLAN.md lacks shipped markers for 4.5.D/4.5.E. All other areas
(storage semantics, op-log replay, schema migration, runtime wrappers,
TEXT() correctness, EvalContext threading) pass cleanly.

## Concern A — Parser correctness

**Verdict: MIXED**

### A.1 — m/mm disambiguation "h:mm m" (MEDIUM / correctness)

**File:** `crates/ql-functions/src/format/parser.rs`, lines 287-303
(`walk_for_anchor`)

Mini-spec § 4.1 states the disambiguation rule:

> "Walk left-to-right. Each m/mm token's role is: Minute if the most
> recent date/time token **before** it (within this section) was h/hh
> or s/ss. Minute if the next date/time token after it is s/ss. Month
> otherwise."

The critical word is "most recent date/time token". In the format
`"h:mm m"` the token stream is `[TimeH, Literal(':'), DateM(2), Literal(' '), DateM(1)]`.
When `classify_one_m` processes the trailing single `m`, it calls
`walk_for_anchor` scanning backward. The match arms in `walk_for_anchor` are:

```rust
Token::TimeH { .. } => return Some(AnchorKind::Hour),
Token::TimeS { .. } => return Some(AnchorKind::Second),
Token::DateY { .. } | Token::DateD { .. } => return Some(AnchorKind::DateYDM),
_ => continue,   // ← DateM falls here
```

`Token::DateM` is NOT in the match — it falls through to `_ => continue`.
The backward scan therefore skips the `mm` token entirely and reaches
`TimeH`, returning `AnchorKind::Hour`. The trailing `m` is classified
Minute. The correct answer per spec is Month: the "most recent date/time
token before" the trailing `m` is the `mm` token (already resolved as
Minute), not the `h`.

**Impact:** Any format string with a date `m`/`mm` token appearing after
an earlier time `m`/`mm` token will silently misclassify the later token.
This is a user-visible rendering bug: "h:mm m" would render noon on July 4
as "12:00 0" (minute 0 for the fractional part) instead of "12:00 7"
(month 7).

**Test gap:** Mini-spec § 12.2 explicitly enumerates `"h:mm m"` as a
required test case. No test for this case exists in
`crates/ql-functions/src/format/parser.rs` or anywhere in the test suite.

**Fix needed:** Add `Token::DateM { .. } => return Some(AnchorKind::DateYDM),`
to the match arms in `walk_for_anchor`. Then add the missing test.

### A.2 — Comma-scaling logic (PASS)

Thousands separators and scaling commas (trailing `,` = divide-by-1000)
are handled in `parser.rs` inside `parse_number_section`. The comma-at-end
detection iterates backward from the last digit/placeholder token. Logic
is correct.

### A.3 — V2-token bracket dispatch (PASS)

Color/conditional brackets surface as `UnsupportedV2(V2Token::Color)` or
`UnsupportedV2(V2Token::Conditional)`. The parser returns `Err(...)` which
`text_ctx` maps to `#VALUE!`. Correct.

### A.4 — Length limits / pathological inputs (PASS)

No panics on empty string input (returns `Err(FormatParseError::Empty)`).
Recursive structure is bounded by section count (≤ 4 sections enforced).
No unbounded allocation paths found.

### A.5 — Error position quality (PASS)

`FormatParseError` variants carry enough context (token, position) for
diagnostic use. `#VALUE!` is the correct surface for all parse errors in
TEXT().

## Concern B — Renderer correctness

**Verdict: MIXED (one minor gap)**

### B.1 — 1-section vs multi-section sign handling (PASS)

`render_number_section` auto-prepends minus for negative values in
1-section formats. 2/3/4-section formats route the raw absolute value to
the matched section. Verified at `render.rs` lines 490-530. Correct.

### B.2 — Time-only rendering (PASS)

`render_date_section` checks whether any Year/Month/Day tokens are present
before calling `serial_to_ymd`. When only time tokens appear, serial
decomposition is skipped and the fractional day is used directly.
No cross-section bleed. Lines 535-551.

### B.3 — AM/PM hour conversion (PASS)

Hour mapping at lines 561-569:
- `h=0` → 12 AM
- `h=1..=11` → h AM
- `h=12` → 12 PM
- `h=13..=23` → h-12 PM

All four branches correct. `text_fn` tests `"h:mm AM/PM"` with noon
(serial 0.5) → "12:00 PM". PASS.

### B.4 — Built-in format id 37 render test gap (LOW)

Built-in id 37 maps to `"#,##0 ;(#,##0)"` (parenthesized-negative
accounting). No render test for this id exists in `format/render.rs` or
`text_fn.rs`. Not a correctness bug — the 2-section dispatch is covered
by other tests (`"0;(0)"` in `text_fn.rs:178`) — but a coverage gap.

### B.5 — AmPm token in number section (LOW)

`SectionKind::Number` classification does not produce a Date section even
when AM/PM tokens appear. If a user writes `"0 AM/PM"` the section is
classified as Number and rendered numerically; the AM/PM token is silently
dropped. No test pins this. Not a spec violation (it's malformed input)
but the behavior is undocumented.

### B.6 — EvalContext threading (PASS)

`read_display` in `workbook_runtime.rs` constructs a fresh `EvalContext`
via `self.workbook.date_system()` on each call. The date system is never
stale-cached. TEXT() receives the live context. Correct.

## Concern D — Op-log replay

**Verdict: MIXED**

### D.1 — RegisterFormat replay (PASS)

`crates/ql-oplog/src/replay.rs`: `Op::RegisterFormat { id, format }` calls
`FormatTable::register_at(id, &format)`. Idempotent for same input. Correct.

### D.2 — SetCellFormat unknown-id guard (PASS)

`Op::SetCellFormat` replay checks that the id is known in FormatTable before
applying to overlay. Returns `ReplayError::FormatNotRegistered` otherwise.
Correct order dependency: RegisterFormat must precede SetCellFormat in the
log. Verified in `replay.rs`.

### D.3 — Equivalence test does not cover format state (MEDIUM)

**File:** `crates/ql-oplog/tests/producer_replay_equivalence.rs`

`assert_workbooks_observationally_equal` compares cell values, formula
strings, and sheet names. It does **not** compare:
- `FormatTable` contents (custom entries)
- `CellFormatOverlay` entries per sheet

A bug in op-log append ordering for format ops (e.g., RegisterFormat
emitted after SetCellFormat, or id predicted incorrectly) would produce
a workbook with wrong display values but the equivalence test would not
catch it, because all *computed values* might still match.

### D.4 — BatchCommit recursive dispatch (PASS)

`BatchCommit` recursively calls `apply_op` for each contained op. Format
ops within a batch are replayed correctly.

## Concern F — WorkbookRuntime wrappers

**Verdict: PASS**

### F.1 — intern_format append-before-mutate (PASS)

`workbook_runtime.rs` lines 780-803: `intern_format` checks `format_table`
for existing string first (return cached id). For new strings it predicts
the next id from `format_table.len()`, appends `Op::RegisterFormat` to the
op-log, then calls `format_table.intern(...)`. Op is emitted before the
in-memory state is mutated. Correct.

### F.2 — intern_format id prediction stability (PASS)

FormatTable grows monotonically. The next id equals `base_custom_id +
current_count`. Since `intern` never removes entries, the prediction is
stable between append and mutate. Correct.

### F.3 — set_cell_format validates before appending (PASS)

`workbook_runtime.rs` lines 814-853: unknown format id triggers error
return before `Op::SetCellFormat` is appended. Prevents replay from
encountering orphaned format references. Correct.

### F.4 — read_display cache and fallback (PASS)

`workbook_runtime.rs` lines 872-903: cache hit → direct return. Cache miss
→ `format_table.get_by_id()` → `parse()` → insert into `format_cache`. If
`get_by_id` returns `None` (unknown id), returns `GeneralFormat` rendered
value. The General fallback is intentional and acceptable: it fires only
when a cell carries a format id that was never registered, which should not
happen in correct usage but is a valid defensive path (not a fallback that
hides bugs).

### F.5 — format_cache stability (PASS)

`format_cache: HashMap<FormatId, FormatString>` is stable because
FormatTable rejects overwriting existing entries. A cached parse result
for a given id is always correct for the lifetime of the workbook.

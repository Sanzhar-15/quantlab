## Findings

Three audits ran in parallel:

2. **Opus correctness agent** — narrower focus on borrow semantics, op-log ordering, and edge cases.

Findings consolidated. Each finding tagged with HIGH / MEDIUM / LOW / DOC and a disposition.

### HIGH (correctness or data-loss risk)

#### H1 — `add_sheet` lacks input validation; bad inputs leak orphan op-log entries

**Source:** Codex (S1.1), Opus correctness (H1)  
**File:** `crates/ql-exec/src/workbook_runtime.rs` `WorkbookRuntime::add_sheet`

Two paths lead to a phantom `Op::AddSheet` followed by a workbook-corrupting panic:

- `chunk_rows == 0`: accepted silently → sheet created with `chunk_rows=0` → first cell write panics in `ColumnStore::with_chunk_rows`. Op log persists the bad `Op::AddSheet`; replay reproduces the same poison on next load.
- `sheet_count >= SheetId::MAX (65,535)`: `Workbook::add_sheet_with_chunk_rows` panics on the assertion. Same phantom-op + panic shape.

**Disposition:** **FIXED** in this audit-closure commit. New `RuntimeError::InvalidChunkRows(u32)` and `RuntimeError::TooManySheets { current, max }` variants. `add_sheet` pre-validates BEFORE the op log append. Tests added: `add_sheet_rejects_zero_chunk_rows`.

#### H2 — `set_name` mutate-first ordering left workbook+log divergent on append failure

**Source:** Codex (S1.2), Opus correctness (H3)  
**File:** `crates/ql-exec/src/workbook_runtime.rs` `WorkbookRuntime::set_name`

The 2B.5 implementation chose mutate-first ordering to avoid orphan log entries on reserved-name rejection. But on an op-log append failure AFTER the workbook mutation, the workbook had the new name and the log didn't — silent divergence that would replay-corrupt on next load.

**Disposition:** **FIXED** in this audit-closure commit. Pre-flight `NameTable::would_accept(name)` check (new pub method on ql-storage) makes the workbook mutation infallible at this layer. Ordering is now validate → append → mutate, matching the rest of the producer surface (set_value, set_formula, clear_formula, add_sheet).

#### H3 — `set_value` / `clear_formula` two-op appends could partially succeed

**Source:** Opus correctness (H2)  
**File:** `crates/ql-exec/src/workbook_runtime.rs`

Both wrappers emitted two sequential `oplog.append` calls (PutValue then ClearFormula) for the formula-replacement case. If the first succeeded and the second failed (Loro internal error), the log would have a stale `PutValue` without its paired `ClearFormula`. Replay would write the value and keep the prior formula text — a real divergence from producer state.

**Disposition:** **FIXED** in this audit-closure commit. When both ops are needed, they're now wrapped in a single `Op::BatchCommit { ops: [PutValue, ClearFormula] }` — a single Loro append, atomic. Replay treats BatchCommit as a sequence (existing semantics), so the inner-op order is preserved.

#### H4 — `transaction::commit` appended `BatchCommit` AFTER workbook mutation passes

**Source:** Opus IDE-shape (H2)  
**File:** `crates/ql-exec/src/transaction.rs` `WorkbookTransaction::commit`

The two-pass commit ran pass 1 (literals + formula text) and pass 2 (eval + write formula values) BEFORE appending the `Op::BatchCommit` to the log. A serialization failure on the append (e.g., NaN/Inf in a `Value::Number`) would leave the workbook fully mutated and the log without the entry. Save/load would lose the changes silently.

**Disposition:** **FIXED** in this audit-closure commit. Commit is now reordered: build `log_ops`, append `BatchCommit` first (with `had_formula` snapshotted from pre-mutation state), THEN run pass 1 and pass 2. Workbook stays unchanged on append failure.

#### H5 — `Workbook` / `OpLog` Send + Sync unproven (Phase 6.3 binding readiness)

**Source:** Opus IDE-shape (H3)

The two engine state types the Node-API / WASM bindings will own (`Workbook` + `OpLog`) had no compile-time proof that they were `Send + Sync`. A future Loro version regressing `LoroDoc`'s `Sync` impl, or a future Workbook field gaining an `Rc`, would only blow up when the binding crate tries to wrap them — exactly the wrong time to find out.

**Disposition:** **FIXED** in this audit-closure commit. New `_assert_engine_state_is_send_sync` compile-time check in `ql-exec/src/lib.rs`. Today's Loro 1.12.0 LoroDoc satisfies both bounds; the check pins the invariant going forward.

### Filed as gaps (deferred with explicit owners)

#### H6 (filed) — `WorkbookRuntime<'a>` borrow shape incompatible with Node-API object lifetimes

**Source:** Opus IDE-shape (H1)

Node-API can't safely stash a struct with lifetime parameters inside a JS-visible object. Phase 6.3 binding work needs a `WorkbookSession` type that owns wb + oplog + registry without lifetimes. This is **Engine Phase 6.1** scope per MASTER-PLAN ("Stable Engine Session API").

**Filed as GAP-PS-09** in `docs/known-gaps.md`. Target: Engine Phase 6.1.

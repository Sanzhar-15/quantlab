## LOW

### CODEX-LOW-1

Subject: Removed F.DIST PDF-at-zero anchor is still documented as covered

Where: `crates/ql-functions/tests/coverage.rs:780`; `docs/compat/excel-matrix.md:110`

Detail: The implementation removed the original `f_dist_pdf_at_zero_df1_two` test, which is correct because `statrs` returns `0` for `df1=2` at `x=0` while the true density is `1`. However, the coverage deferral reason still says F.DIST tests include `df1=2 closed-form pdf(0)=1`, and the compatibility matrix repeats the same anchor while reporting `F.DIST` as 11 tests. The current F.DIST unit tests are 9 tests: zero CDF, equal-df CDF symmetry, finite positive PDF at `x=1`, 95th-percentile CDF anchor, negative x, df domain, text, error propagation, and arity.

Recommendation: Remove the `df1=2 closed-form pdf(0)=1` claim from both files, and change the F.DIST matrix count from 11 to 9 unless new tests are added.

Severity rationale: Low because runtime behavior and the actual tests are correct. The docs are now misleading exactly on a boundary divergence the batch intentionally removed.

### CODEX-LOW-2

Subject: CHISQ.INV.RT `p=0` public behavior is misdescribed and unpinned

Where: `crates/ql-functions/src/distribution_fns.rs:628`; `crates/ql-functions/src/distribution_fns.rs:632`; `crates/ql-functions/tests/coverage.rs:771`; `crates/ql-functions/tests/coverage.rs:807`

Detail: The `CHISQ.INV.RT` range check admits `p=0`, matching IronCalc's initial domain check, but the next line computes `inverse_cdf(1.0 - p)`. At `p=0`, that is `inverse_cdf(1.0)`, which produces a non-finite value and is surfaced as `#NUM!` by the guard. The coverage text says `p=0 ACCEPTED` for CHISQ.INV.RT and describes F.INV.RT as diverging from CHISQ.INV.RT because CHISQ.INV.RT accepts `p=0`; no unit or e2e test pins the actual returned value.

Recommendation: Add an explicit `chisq_inv_rt_at_zero_prob_is_num_error` test if the intended public behavior is IronCalc parity (`#NUM!` after the result guard). Reword coverage/docs to distinguish "domain check admits p=0" from "the function returns a finite value".

Severity rationale: Low because the implementation matches IronCalc's code path and the required `p=1 -> 0` boundary is tested. The risk is future reviewers reading the coverage text as a public behavior guarantee.

### CODEX-LOW-3

Subject: F.INV.RT Microsoft-domain divergence is not documented

Where: `crates/ql-functions/src/distribution_fns.rs:91`; `crates/ql-functions/src/distribution_fns.rs:117`; `crates/ql-functions/src/distribution_fns.rs:779`; `docs/compat/excel-matrix.md:113`

Detail: The implementation intentionally follows IronCalc for F.INV.RT: `p <= 0.0 || p > 1.0` and no explicit df ceiling. Current Microsoft Support text for F.INV.RT says probability outside `< 0` / `> 1` is `#NUM!`, and separately says `deg_freedom2 >= 10^10` is `#NUM!`. The module docs and matrix present the W5-D-3 F.* rules as Excel/Microsoft canon without calling out that F.INV.RT is IronCalc-prioritized here. The module doc also has a confusing sentence saying both CHISQ.* and F.* enforce a `10^10` ceiling before parenthetically saying CHISQ.* only.

Recommendation: Document this as an intentional IronCalc-vs-Microsoft divergence for F.INV.RT, or add the Microsoft guard if Excel doc parity is the stronger contract. Also rewrite the `df <= 10^10` sentence so it cannot be read as applying to F.*.

Severity rationale: Low under the stated W5-D-3 contract because the code matches IronCalc and the prompt explicitly says no F.* upper ceiling. It is still a user-visible compatibility divergence from current Microsoft docs and should not be hidden under "Microsoft canon" wording.

### CODEX-LOW-4

Subject: F.INV.RT has no negative-probability regression test

Where: `crates/ql-functions/src/distribution_fns.rs:779`; `crates/ql-functions/src/distribution_fns.rs:2542`; `crates/ql-exec/tests/distribution_fns_e2e.rs:487`

Detail: `F.INV.RT` correctly rejects `p <= 0.0 || p > 1.0`, and the suite pins the lower-strict boundary with `p=0`. It does not separately test `p < 0`, unlike `CHISQ.INV`, `CHISQ.INV.RT`, and `F.INV`. A future edit that rejects exactly zero but accidentally permits negative probabilities would not be caught by the current F.INV.RT-specific tests.

Recommendation: Add `f_inv_rt_p_negative_is_num_error` at the unit layer. One e2e assertion is optional; the direct unit test is enough to pin the domain branch.

Severity rationale: Low because the implementation is currently correct and the zero-boundary test exercises the same `p <= 0.0` branch. The missing test leaves an explicit domain requirement less well pinned than its sibling inverse functions.

## Confirmed Non-Issues

- `ChiSquared::new(df)` and `FisherSnedecor::new(df1, df2)` are the correct statrs constructors for this batch. The pre-checks plus `to_number_strict` make the `.expect()` paths principled.
- `CHISQ.DIST` uses `cdf` / `pdf` according to `cumulative`, and `CHISQ.DIST.RT` uses `dist.sf(x)` with `ContinuousCDF` in scope.
- `F.DIST` uses `cdf` / `pdf` according to `cumulative`, and `F.DIST.RT` intentionally uses `1.0 - dist.cdf(x)`, not `sf`.
- Domain checks match the local IronCalc sources: CHISQ.* truncates `df` and enforces `[1, 10^10]`; F.* truncates both df args and only checks `>= 1`; F.INV.RT is lower-strict at `p=0`.
- Inverse functions call `inverse_cdf` only after probability range checks that keep statrs from panicking on inputs outside `[0, 1]`.
- All numeric args use `to_number_strict`; cumulative args use `to_logical`; arity mismatches return `#VALUE!`.
- The requested anchors are present and correct: chi-squared df=2 closed forms, `CHISQ.INV(0.95,1)`, F equal-df symmetry at `x=1`, F equal-df median at `p=0.5`, and the statrs-pinned `F.INV(0.95,5,10) = 3.3258345304130046`.
- The statrs F.INV vs true-math divergence is explicitly documented in the unit and e2e test comments.
- The registry count is 217, and the eight W5-D-3 functions are registered.
- The compatibility matrix has eight individual CHISQ/F rows replacing the prior grouped placeholder.
- `EXPLICITLY_DEFERRED` contains entries for all eight W5-D-3 functions.
- No lexer change was required for CHISQ.DIST.RT / CHISQ.INV.RT / F.INV.RT; the existing dotted identifier support handles these letter-only segments.

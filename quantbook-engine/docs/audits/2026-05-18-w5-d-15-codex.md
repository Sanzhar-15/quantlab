# W5-D-15 Audit Findings

Scope: commit `4f5226a9876` on `feat/quantbook-engine`.

Validation note: I could not run `cargo test` in this sandbox. Both the
rustup shim and the direct `/Users/sanzhar/.rustup/.../bin/cargo` binary
route through the host-control socket and fail with
`dial unix /opt/orbstack-guest/run/hcontrol.sock: connect: operation not permitted`.
The direct cargo binary is a macOS Mach-O binary (`cffaedfe` header), so
there is no usable Linux cargo in this sandbox. Empirical checks below are
therefore static source tracing plus Python ZIP/XML scans of actual `.xlsx`
fixture bytes.

## HIGH

### HIGH-1: `styles_xml` drops non-self-closing `<cellXfs><xf>...</xf>` entries, corrupting every later `s="N"` lookup

`crates/ql-io-xlsx/src/read/styles_xml.rs:121-134` only appends a `CellXf`
for `Event::Empty(e)` when `tag == "xf"` under `cellXfs`. `Event::Start(e)`
only pushes the tag name onto `element_stack`; it does not parse the `<xf>`
attributes. Any style like:

```xml
<xf numFmtId="1" ... applyNumberFormat="1"><alignment wrapText="1"/></xf>
```

is omitted from `style_index.cell_xfs` entirely. That is not just a lost
alignment; it changes the positional meaning of all following `s` indices.
`lib.rs:197-211` then resolves `s="N"` against the compressed vector, so it
can silently assign the wrong `FormatId` or skip the style as out of range.

Empirical scan of actual fixture bytes:

- 88 `.xlsx` fixtures contain non-empty `<xf>...</xf>` with alignment or
  protection children.
- 75 fixtures have worksheet cells whose used `s` indices are at or after
  those non-empty XFs.
- Example:
  `.references/ironcalc/xlsx/tests/calc_tests/MOD_QUOTIENT.xlsx` has used
  style indices `[1..15]`; actual `cellXfs[5]` is
  `numFmtId="1" applyNumberFormat="1"` with an `<alignment>` child. The
  current parser skips index 5, so later cells resolve against the wrong
  `cell_xfs` entry.
- Example:
  `.references/ironcalc/xlsx/tests/libreoffice_888_example.xlsx` has all
  seven `cellXfs` entries as non-empty `<xf>...</xf>` records. The parser
  records zero cell XFs, so every worksheet `s` reference is ignored.

Impact: import-side per-cell format application is unreliable for common
Excel/LibreOffice workbooks. The new E2E tests do not catch this because
the Quantbook exporter injects self-closing `<xf .../>` records.

### HIGH-2: Import collapses missing `applyNumberFormat` and explicit false, losing real-world number formats

`parse_xf_attrs` initializes `apply_number_format = false`
(`styles_xml.rs:173-188`) and only sets it true for
`applyNumberFormat="1"` or `"true"`. `import_xlsx_bytes` then skips the
overlay whenever `!xf.apply_number_format` (`lib.rs:202-205`).

OOXML implementation notes say the default for `applyNumberFormat` in
`cellXfs` is false, so this is schema-compatible for strict producers.
However, real workbooks in the repo omit the attribute while still using
the `numFmtId` as the rendered number format.

Empirical scan:

- 18 referenced, nonzero `numFmtId` cell XFs omit `applyNumberFormat`.
- `.references/ironcalc/xlsx/tests/libreoffice_888_example.xlsx` has cells
  referencing `s="4"` and `s="5"` where the XFs are `numFmtId="165"`
  (`[$$-409]0.00`) and `numFmtId="166"` (`0.00`), with no
  `applyNumberFormat`.
- `.references/ironcalc/xlsx/tests/calc_test_no_export/tables.xlsx` has
  cells referencing XFs 6, 7, 13, 16, 17, 18, 23, and 24, all with
  `numFmtId="43"` and no `applyNumberFormat`.

Impact: after HIGH-1 is fixed, these files will still lose per-cell number
formats. If Quantbook wants strict OOXML only, the current behavior is
defensible; if it wants practical Excel/LibreOffice round-trip, the parser
needs a tri-state (`missing`, `false`, `true`) and should likely treat
missing plus nonzero `numFmtId` as applicable while still honoring explicit
`applyNumberFormat="0"`.

### HIGH-3: Export applies per-sheet fixes by vector index, but empty sheets are not pushed into `sheet_fixes`

In `export_new_workbook`, an empty sheet exits at
`umya_export.rs:117-120` before `sheet_fixes.push(fixes)` at line 239.
`post_process_zip` later assumes `sheet_fixes[sheet_idx]` matches
`xl/worksheets/sheet{sheet_idx+1}.xml` (`umya_export.rs:380-384`).

Trigger:

1. Sheet 0 is empty.
2. Sheet 1 has a formula cache fix, error sigil fix, or format overlay.
3. The loop skips pushing an empty fixes vec for sheet 0.
4. Sheet 1's fixes land in `sheet_fixes[0]`.
5. Post-process applies them to `sheet1.xml`; `sheet2.xml` gets no fixes.

Impact: any workbook with an empty sheet before a styled/error/formula sheet
silently loses those post-process patches on the later sheet. For W5-D-15
specifically, a formatted cell on sheet 2 after an empty sheet 1 will not
receive `s="N"`.

### HIGH-4: Export drops format-only blank cells

The value walk skips blank, non-formula cells (`umya_export.rs:193-195`).
The `SetStyle` fixes are scheduled later from `format_overlay.iter()`
(`umya_export.rs:224-237`), but `apply_cell_fixes_to_sheet_xml` only does a
string replacement for an existing `<c r="...">` tag
(`umya_export.rs:461-475`). If the cell is blank, no `<c>` tag exists, so
the replacement is a no-op.

There is a second form of the same bug: if a sheet has only format overlay
entries and no nonblank cells, `bounds.row_extent == 0` causes the early
`continue` at lines 117-120, so the overlay is not even added to the
`cellXfs` roster.

Impact: formatted blank cells are common in templates and input sheets.
They should export as style-only cells, e.g. `<c r="A1" s="1"/>`; the
current code loses them.

## MEDIUM

### MEDIUM-1: XLSX export is byte-nondeterministic because `cellxfs_roster` follows `HashMap` iteration order

`CellFormatOverlay::iter()` documents that it returns `HashMap` iteration
order (`crates/ql-storage/src/format_overlay.rs:72-75`). The exporter uses
that order to assign `xf_index` values and build `cellxfs_roster`
(`umya_export.rs:224-230`). The same workbook can therefore produce
different `<cellXfs>` ordering and different per-cell `s="N"` indices across
processes.

This is semantically OK because each `s` still points at the matching XF in
the same file, but it weakens byte-level replay/golden determinism. The
engine already treats order as important elsewhere: `.qbook` persistence
sorts format overlay entries, and `FormatTable` comments call out replay
determinism. Sorting overlays by `(FormatId, row, col)` or assigning XFs by
sorted `FormatId` would close this.

Related existing issue: `custom_formats` is collected from
`workbook.formats().iter()` (`umya_export.rs:262-270`), which is also a
`HashMap` order. That affects `<numFmts>` byte order, though not semantics.

### MEDIUM-2: Replacing umya's default `<cellXfs>` block clobbers its second default XF

Static trace of umya 2.2.0:

- `new_file_empty_worksheet()` calls `set_stylesheet_defalut_value()`.
- `Stylesheet::set_defalut_value()` inserts two default styles
  (`stylesheet.rs:364-368`).
- `Style::get_default_value_2()` differs only by `Fill::get_default_value_2()`,
  which is `gray125` (`style.rs:331-336`, `fill.rs:71-75`).
- `CellFormats::write_to()` emits every stored cell format as `<cellXfs>`
  (`cell_formats.rs:63-75`).

So umya normally has two cell XFs, not one. The W5-D-15 replacement emits
slot 0 plus the Quantbook roster, discarding umya's slot 1.

Current impact is probably low in this exporter because Quantbook does not
apply styles through umya; umya only writes `s` when `stylesheet.set_style`
returns `> 0` (`cell.rs:474-479`), and Quantbook cells keep
`Style::default()`. But this is a sharp edge: any future row/column/cell
style use through umya would leave existing `s`/`style` references pointing
at the wrong XF after replacement.

### MEDIUM-3: `xfId="0"` is not universally safe unless `cellStyleXfs[0]` exists

The emitted W5-D-15 XFs use `xfId="0"`. OOXML defines `xfId` in `cellXfs`
as a zero-based reference into `<cellStyleXfs>`. The attribute is optional;
if present, it should reference an actual cell-style XF.

Static umya trace suggests fresh umya styles can omit `<cellStyleXfs>`
entirely: `CellStyleFormats::write_to()` only emits the element if its
collection is non-empty (`cell_style_formats.rs:63-75`), while the default
stylesheet setup only populates `cell_formats`, not `cell_style_formats`.
umya also emits `xfId="0"` from `CellFormat::write_to()` for cell XFs
(`cell_format.rs:262-278`), so this is not newly introduced by W5-D-15.

Practical consumers likely tolerate this because umya-generated workbooks
already rely on it, but for strict OOXML validity the exporter should either
omit `xfId` from the injected cell XFs or ensure a matching
`<cellStyleXfs count="1"><xf .../></cellStyleXfs>` exists.

## LOW

### LOW-1: `SetStyle` string patching would double-inject if a cell already has `s=`

The patch replaces `<c r="C5"` with `<c r="C5" s="N"`
(`umya_export.rs:470-475`) without checking for an existing style attribute.
In the current Quantbook path this should not happen: no styles are applied
through umya, and umya writes `s` only for non-default styles. If that
changes, the output can become `<c r="C5" s="N" s="old">`.

### LOW-2: Coverage gaps remain around the failure modes above

The three W5-D-15 E2E tests cover custom, built-in, and dedup for
self-generated, self-closing XFs on sheet 0. They do not cover:

- non-empty `<xf>...</xf>` under `<cellXfs>`;
- omitted vs explicit-false `applyNumberFormat`;
- format overlay on blank cells;
- format overlay on a sheet after an empty sheet;
- multi-sheet style application in general;
- two distinct custom formats applied concurrently;
- exact exported `styles.xml` and worksheet `s="N"` bytes;
- explicit `applyNumberFormat="0"` import skip.

## Non-Findings / Confirmed Behaviors

- `<cellXfs count="...">`: `count` is optional in the schema, but emitting
  it with the actual number of `<xf>` children is correct.
- `applyFont`, `applyFill`, `applyBorder`, `applyAlignment`, and
  `applyProtection` are optional on `xf`; omitting them on the injected
  number-format-only XFs is fine for the modeled surface. Non-default
  number-format XFs correctly include `applyNumberFormat="1"`.
- `applyNumberFormat` default: implementation notes say the default in
  `cellXfs` is false, so the current strict parser default is not a schema
  misunderstanding. The issue is real-world producer compatibility.
- Built-in `numFmtId="0"` / explicit General: skipping this is consistent
  with Quantbook's model, where absent overlay means General. It loses only
  the distinction between implicit and explicit General, which the current
  storage model does not represent.
- Worksheet scanner namespace handling: `cell_styles_xml.rs:41-43` uses
  `e.local_name()`, so `<x:c r="A1" s="3"/>` still matches `tag == "c"`.
  The `r` and `s` attributes are unqualified in normal SpreadsheetML, so
  the direct `key == b"r"` / `key == b"s"` checks are fine.
- `SetStyle` ordering: value/formula/error fixes are pushed during the cell
  walk (`umya_export.rs:145-207`), while `SetStyle` fixes are appended after
  that loop (`umya_export.rs:224-237`). `apply_cell_fixes_to_sheet_xml`
  iterates in vector order, so `SetStyle` runs after `RemoveStrType` and
  `OverrideErrorSigil`.
- `SetStyle` substring safety: the needle includes `<c r="A1"` with the
  closing quote after the reference, so it will not match `<c r="AA1"`.
  Raw `<c r="...">` text inside formulas/shared strings would be escaped,
  so accidental matches outside cell tags are unlikely.
- No format overlays: `post_process_zip` only injects the replacement
  `<cellXfs>` when `!cellxfs_roster.is_empty()`, so an empty workbook with
  no overlays does not get the W5-D-15 replacement block.

## HIGH

### H1 — `Sheet::put` panics on out-of-range row/col; only sheet was guarded in Phase 2A.6 ✅ CLOSED 2A.7
**Files**: `ql-storage/src/sheet.rs:82-91` (panic site); `ql-exec/src/workbook_runtime.rs:144, 162`; `ql-exec/src/transaction.rs:115-117, 153-166`.

Phase 2A.6 audit L4 added `validate_sheet` but missed row/col bounds. `rt.set_formula(0, MAX_ROW+1, 0, "1+1")` runs lex/parse/bind/eval to completion, then panics at `put_at` → `Sheet::put`. In transactions, the panic happens mid-commit leaving a partial-write state. Three agents flagged this independently.

**Fix**: extend `validate_sheet` to `validate_cell(workbook, sheet, row, col)` checking both bounds; add `RuntimeError::InvalidCell { sheet, row, col }`. Wire into all four entry points. ~30 min.

### H2 — `.qbook` save is not actually atomic — `remove_dir_all(path)` before rename leaves a data-loss window ✅ CLOSED 2A.8 (W5-18)
**Files**: `ql-io/src/qbook_format.rs:258-262`.

The Phase 1 W5-8 / audit M4 fix added `write to sibling-tmp + rename`, but the rename path is:
1. Write into `<base>.tmp-save-PID`
2. `fs::remove_dir_all(path)`  ← if crash here, target is gone
3. `fs::rename(<base>.tmp-save-PID, path)`

A crash, OOM, or `kill -9` between (2) and (3) loses the workbook entirely. Two agents flagged this. The fix is well-understood: rename the existing target to `<base>.bak` first, rename temp into target, then best-effort cleanup of the `.bak`. On a crash you always have either the old workbook (via `.bak`) or the new one at `path`.

**Fix**: rewrite the rename sequence; add a recovery path that detects an orphaned `.bak` on next load. ~1 hour including tests for crash-window simulation.

### H3 — Fingerprint uses `DefaultHasher` which Rust does not guarantee is stable across compiler versions ✅ CLOSED 2A.10 (W5-20)
**Files**: `ql-calcgraph/src/fingerprint.rs:28-34, 53-55`.

The module doc claims fingerprints are stable across engine versions. `DefaultHasher`'s contract explicitly says "*The internal algorithm is not specified, and so its instances should not be relied upon over releases.*" Two agents flagged this. Within the pinned `1.95.0` toolchain, fingerprints are deterministic across runs; once the toolchain bumps, every fingerprint value silently shifts. There is also **no golden-fingerprint test** — only relative-equality tests — so a silent shift wouldn't trip CI.

Mitigating: fingerprints aren't persisted yet. The risk lands when Phase 4 calcgraph caching stores them.

**Fix**: switch to FxHash with a fixed seed, or BLAKE3, before Phase 4 persistence. Add a `golden_fingerprints_locked` test pinning a small set of `(Expr, expected_u64)` pairs across the main variants. ~2-3 hours including the hasher swap and the test fixture.

### H4 — `recompute_all` iterates formulas in HashMap-arbitrary order; produces wrong values for cross-cell dependencies
**Files**: `ql-exec/src/workbook_runtime.rs:179-209`.

A loaded workbook with `B1=A1+1, C1=B1+1` may recompute `C1` against the stale saved `B1` value, then `B1` against current `A1`. Result is non-deterministic and incorrect for cross-cell chains. The doc admits "iteration order is HashMap-arbitrary" but understates: re-running `recompute_all` on the same workbook can produce *different* final values across invocations.

**Fix**: integrate with `ql-calcgraph::topo::schedule()` to evaluate in topological order. This is Phase 4 calcgraph integration; it's not a quick fix — needs design work to wire calcgraph dependency graph from formula text. Or: short-term Band-Aid that iterates `recompute_all` to a fixed point with a max-iteration cap (Excel does this). Multi-day item.

### H5 — SIMD division produces `#NUM!` instead of `#DIV/0!` for zero divisors; test pins the buggy behavior ✅ CLOSED 2A.9 (W5-19)
**Files**: `ql-exec/src/lower.rs:176-181`; `ql-exec/src/simd.rs:114-118, 223-231`.

`DivScalar` is lowered to `mul by 1.0/scalar`. So `1/0 → Inf → sanitize_f64(Inf) = #NUM!`. Excel canon: `1/0 = #DIV/0!`. A test at `simd.rs:223-231` pins the wrong-error-class behavior. Per the no-fallbacks rule and Phase 2A.6 audit's emphasis on correct error CLASSES, this is HIGH.

**Fix**: branch-mask zero divisors in the SIMD kernel, OR refuse to classify division into the raw f64 SIMD path until an error-bitmap channel is wired. Replace the buggy-pin test with one asserting `#DIV/0!`. ~2-3 hours.

### H6 — Stale sheet id (saved formula refs deleted sheet) silently reads `Value::Blank` instead of `#REF!` ✅ CLOSED 2A.7
**Files**: `ql-exec/src/plan.rs:117-123`; `ql-exec/src/env.rs:38-47`.

A formula authored against `Sheet3!A1` in a workbook now with 2 sheets binds to `ExprPlan::CellRef { sheet: 2, ... }`, which `WorkbookEnv::read_cell` maps to `Value::Blank`. The env.rs comment admits this is a deferred semantic ("Phase 3+ FormulaRegion binder"). Two agents flagged it. The same agents flagged that `Phase 2A.6` already established the pattern (`NamedTargetIsBlank`, `NamedTargetIsError`) for surfacing previously-silent paths.

**Fix**: at bind time, check `addr.sheet < workbook.sheet_count()` and return `BindError::InvalidSheetRef`; OR change `WorkbookEnv::read_cell` to return `Value::Error(ErrorValue::Ref)` for missing sheets. The second is closer to Excel canon. ~1 hour.

### H7 — Doc rot: `ql-formula-syntax` top-level docs still say "THIS COMMIT SHIPS TYPE DEFINITIONS ONLY" / "PHASE 0 PARTIAL — Pratt parser deferred" ✅ CLOSED 2A.7
**Files**: `ql-formula-syntax/src/ast.rs:1-10`; `ql-formula-syntax/src/lib.rs:3-12`.

The parser shipped on commit `64cd3da0675` (Phase 1 W5-1) and has 80+ tests, dotted identifiers (Phase 2A.5), and NameRef binding (Phase 2A.1). The crate's top-level doc is what every IDE pop-up and docs.rs page shows; it says the parser doesn't exist. Worst rot in the engine.

**Fix**: rewrite both docstrings to reflect Phase 2A current state. Use `ql-exec/src/lib.rs` (which IS phase-current per 2A.6 D4 fix) as the template. ~30 min.

### H8 — `LoadAndRecomputeError::Recompute` partial-workbook M5 fix listed as DEFERRED in the Phase 2 exit packet ✅ CLOSED 2A.7
**Files**: `docs/phase2/exit-packet.md:71-72`.

The exit packet lists "load_workbook_and_recompute partial workbook drop (audit M5)" as backlog. But commit `5ebd8707c41` ALREADY shipped the M5 fix — `LoadAndRecomputeError::Recompute { workbook, error }` struct variant. Self-contradicting exit packet.

**Fix**: delete the M5 bullet from the deferred list; reword the M4 bullet to clarify only `recompute_all` (not loader) still short-circuits. ~2 min.

### H9 — `ql-exec` Phase 2A.1 public API (`bind_with_names`, `NameLookup`, `ResolvedName`) not re-exported from `lib.rs` ✅ CLOSED 2A.7
**Files**: `ql-exec/src/lib.rs:37-46`.

The module doc advertises `bind_with_names`/`NameLookup`/`ResolvedName` as the Phase 2A.1 public surface, but only `bind` and `BindError` are in the `pub use plan::{...}` block. Callers must reach through full module paths.

**Fix**: extend `pub use plan::{...}` to include `bind_with_names, NameLookup, ResolvedName, NamedTargetIsBlank, NamedTargetIsError`. ~1 min.

### H10 — Bench machine reporter silently falls back on `QBOOK_CHUNK_ROWS` parse failure ✅ CLOSED 2A.7
**Files**: `ql-bench/src/machine.rs:84-87`.

```rust
chunk_rows: env::var("QBOOK_CHUNK_ROWS")
    .ok()
    .and_then(|s| s.parse().ok())
    .unwrap_or(16_384),
```

The storage-side version (`ql-storage/src/column.rs:35-52`) panics loudly on parse failure, explicitly *because* "prior behavior silently defaulted on any parse failure, which would let a misconfigured A7 chunk-size sweep benchmark the wrong chunk size while pretending to test another." The bench reporter re-introduces the exact bug for its output column. The two env-var paths disagree on policy.

**Fix**: call `ql_storage::chunk_rows_from_env()` (existing public helper) or capture as `Result<u32, String>` and render the parse error in the report. ~5 min.

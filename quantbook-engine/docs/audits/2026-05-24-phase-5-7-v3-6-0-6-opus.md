## § B  Verdict

Six findings cross the audit-of-D5 closure bar.

The headline claim — "V3.5.0.X A-HIGH-2 IDE-level verification gap CLOSED end-to-end" — is **only true at the napi-call level**. ### C.1  OPUS-V3-6-0-6-HIGH-1 — IDE write-path for formulas does NOT exist; D5 closure framing is misleading

**Severity**: HIGH.
**Files**:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:163` (`parseCellRawInput`)
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:364` (`dispatchIncomingMessage` `'putValue'` arm)
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:411-418` (`endEdit` `vscode.postMessage({type:'putValue',...})`)

**Mechanism**:

1. User clicks a cell → `beginEdit` runs. Post-D5 the `<input>` is populated from `data-raw-formula` if present, else `data-raw-value`, else `data-original-text`.
2. For a formula+value cell, the input shows `=21*2` (the formula). For a pure-literal cell, it shows the raw value (e.g., `42`).
3. User edits → presses Enter → `endEdit(true)` runs.
4. `endEdit` sends `vscode.postMessage({type:'putValue', sheet, row, col, rawInput: input.value})` regardless of whether the input was originally a formula or a value.
5. Host receives `{type:'putValue', rawInput:'=21*2'}` → `dispatchIncomingMessage`'s `'putValue'` arm calls `parseCellRawInput('=21*2')`.
6. `parseCellRawInput` does `Number('=21*2'.trim())` → `NaN`. The `Number.isFinite(n)` check throws `[bad_argument] cell value must be a finite number, got "=21*2"`.
7. The error surfaces as an `errorReply` decoration on the cell.

**Result**: there is NO IDE-driven write-path that reaches `appendPutFormula` or `appendPutFormulaValidated`. The napi method is reachable only from test code that calls it directly.

**Why this matters for the D5 closure framing**:

The plan body says "V3.5.0.X A-HIGH-2 IDE-level verification gap CLOSED end-to-end (engine-side Rust regression already verified the repair; now IDE-driven mocha verifies the rename-chain repair surfaces through napi)". The mocha test `formula text repaired through Phase 5.3 rename chain` DOES drive `appendPutFormula` → `renameSheet` → `workbookSnapshot` and asserts the repair surfaces. So the SURFACE CONTRACT is closed. But the framing "the IDE can drive the end-to-end repaired-formula scenario" is misleading because a USER cannot drive that scenario — only test code that directly calls the napi can.

**Comparison with the V3.5.0.X audit-closure A-HIGH-2 wording** (the gap V3.6.0.6 D5 claims to close):

V3.5.0.X A-HIGH-2 said the repair was "verified only by a Rust ql-collab test today because the IDE has no PutFormula write-path. V3.5.0.X documented this as deferred to V3.6+." The V3.6.0.6 D5 plan promises to close this by adding `appendPutFormula`. But "no PutFormula write-path" meant "no user-facing way to write a formula". V3.6.0.6 adds the napi WITHOUT adding the user-facing path. The gap is only partially closed.

**Closure options**:

(a) **In-cycle**: add a `putFormula` arm to `dispatchIncomingMessage`. Detect formula input via `raw.startsWith('=')` heuristic (Excel convention). Route to `appendPutFormulaValidated`. `endEdit` may stay as-is (server-side detection) OR webview can pre-classify via a new `type:'putFormula'` postMessage and the host trusts the classification (defense-in-depth: re-classify host-side; if mismatch, log + drop).

(b) **Defer + acknowledge**: amend the V3.6.0.6 D5 closure framing to "napi-level verification gap CLOSED; user-driven write-path deferred to V3.6.0.7 IDE wiring". Update plan body, MASTER-PLAN, and ide-consumer-contract.md § 4.1.z6 to reflect the scope split.

**Recommendation**: in-cycle closure (a) is preferable because the napi-level verification gap closure is shallow without the actual user-facing flow. The dispatcher arm is ~30 lines of TS. Alternatively, if (a) is too large for this cycle, the docstring/plan must be amended to honestly state the gap is half-closed; otherwise the audit verdict propagates an inaccurate "closed" status.

**Severity**: HIGH.

### C.3  OPUS-V3-6-0-6-HIGH-3 — engine `appendPutFormula(sheet: u16, ...)` silently coerces NaN/Infinity/fractional/2^32+ JS Numbers to in-range u16

**Severity**: HIGH (binding boundary correctness; identical class to V1 Opus H2 closure but for u16 instead of u32).
**Files**:
- `crates/ql-bindings-node/src/lib.rs:1258` (`pub fn append_put_formula(&self, sheet: u16, ...)`)
- `/Users/sanzhar/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/napi-3.9.0/src/bindgen_runtime/js_values/number.rs:45-58` (napi-rs u16 FromNapiValue impl)
- `crates/ql-bindings-node/src/lib.rs:876-878` (the partially-wrong "u16 is safe" docstring)

**Mechanism**:

napi-rs 3.9.0's `FromNapiValue for u16` reads via `napi_get_value_uint32`, then calls `try_into::<u16>()`:

```rust
// napi-3.9.0/src/bindgen_runtime/js_values/number.rs:46-57
impl FromNapiValue for u16 {
    unsafe fn from_napi_value(env, napi_val) -> Result<Self> {
        let mut ret = 0_u32;
        sys::napi_get_value_uint32(env, napi_val, &mut ret); // ECMAScript ToUint32 applied here
        ret.try_into().map_err(|_| Error::from_reason("Failed to convert u32 to u16"))
    }
}
```

ECMAScript ToUint32 (which `napi_get_value_uint32` uses) does:
- `Number(NaN)` → `0` (silent coercion)
- `Number(Infinity)` → `0` (silent coercion)
- `Number(-Infinity)` → `0` (silent coercion)
- `Number(0.5)` → `0` (truncate-toward-zero)
- `Number(2.7)` → `2` (truncate-toward-zero)
- `Number(65535.9)` → `65535` (truncate to valid u16)
- `Number(-1)` → `0xFFFFFFFF` (silent two's-complement wrap; subsequently rejected by `try_into::<u16>()`)
- `Number(65536)` → `65536` (preserves; rejected by `try_into::<u16>()`)
- `Number(2^32)` → `0` (silent ECMAScript ToUint32 wrap; NOT rejected by `try_into`)
- `Number(2^32 + 1)` → `1` (silent wrap)

**The hazard**:
- `session.appendPutFormula(NaN, 0, 0, '=A1')` → sheet silently becomes 0; op appends to sheet 0.
- `session.appendPutFormula(Infinity, 0, 0, '=A1')` → silently sheet=0.
- `session.appendPutFormula(2.7, 0, 0, '=A1')` → silently sheet=2.
- `session.appendPutFormula(4294967296, 0, 0, '=A1')` → silently sheet=0.

These produce no JS error AND no engine error (the op replays correctly to the wrong sheet OR to sheet=0 which always exists).

**The misleading docstring**:

`crates/ql-bindings-node/src/lib.rs:876-878` says:

> `sheet: u16` stays as-is -- u16's `try_into::<u16>()` correctly rejects out-of-range values from ToUint32, so the asymmetric safety (Opus audit H2 finding) doesn't apply at u16.

This claim is true ONLY for the positive-overflow case (e.g., 65536 → ToUint32 → 65536 → try_into fails). It misses ALL the silent-coercion cases above. The V1 audit H2 finding's actual concern was silent coercion of NaN/Infinity/negative/fractional, NOT just positive overflow — so the "doesn't apply at u16" conclusion is empirically wrong.

**Mitigation today**: the IDE TS wrapper `appendPutFormulaValidated` (`extensions/quantlab/src/quantbook/session.ts:129`) DOES validate `Number.isInteger(sheet) && sheet >= 0 && sheet <= 0xFFFF` before the napi call. So IDE consumers that USE the wrapper are protected. But:

1. The napi method itself remains exposed via `CollabSessionInstance.appendPutFormula(...)` (a direct call path); any consumer that bypasses the wrapper sees the silent coercion.
2. The mocha test suite's `engine rejects fractional row` test pins fractional ROW rejection (which IS rejected by `validate_u32_index`). But there is NO test for `engine rejects fractional sheet` or `engine rejects NaN sheet` or `engine rejects Infinity sheet` — because none WOULD reject. The test suite's coverage gap is itself a finding.
3. The same hazard applies to `appendPutValue` (V3.4.0.2), `exportSnapshot` (V3.2.a), `renameSheet` / `deleteSheet` / `moveSheet` validators — but those have explicit `id > u16::MAX as u32` checks because they take `u32`. `appendPutValue` + `appendPutFormula` are the two that take `u16` directly and propagate the hazard.

**Closure options**:

(a) **In-cycle**: change `sheet: u16` to `sheet: f64` in `append_put_formula` (and ideally `append_put_value` for parity) + add `let sheet_u16 = validate_u16_index("appendPutFormula", "sheet", sheet)?;` mirroring `validate_u32_index`. Add a `validate_u16_index` helper. Add `engine rejects fractional sheet` / `engine rejects NaN sheet` / `engine rejects Infinity sheet` / `engine rejects 2^32 sheet` mocha tests pinning the rejection. Fix the misleading docstring at line 876-878.

(b) **Defer** (V3.6.0.7+ backlog): the IDE-side wrapper catches this for the user-driven path. The napi-direct-call path is a contract violation by the caller. Document the silent coercion as a known limitation in the docstring (replace the "doesn't apply at u16" claim with a precise enumeration of the silent-coercion failure modes). Add a guard mocha test like `napi-direct sheet=NaN documented as silently coerced (V3.7+ tracking)`.

**Recommendation**: in-cycle closure (a). The hazard class is identical to V1's audit H2 finding which was closed via `validate_u32_index`. Symmetry (apply the same closure pattern at the u16 boundary) is the consistent path. The misleading docstring at lines 876-878 has been silently broadcasting a wrong safety claim for ~6 commits — that alone justifies in-cycle correction.

### C.4  OPUS-V3-6-0-6-MED-1 — client-side `renderRowsClient` emits `data-raw-formula` UNCONDITIONALLY (no `editable` guard); divergence from server-side `renderRows` gating

**Severity**: MED (latent; today safe but fragile).
**Files**:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:256` (server, gated: `editable && typeof e.formula === 'string'`)
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:690-692` (client, ungated: `typeof e.formula === 'string'`)

**Server-side (line 256)**:
```typescript
const formulaAttr = (editable && typeof e.formula === 'string')
    ? ` data-raw-formula="${escapeHtml(e.formula)}"`
    : '';
```

**Client-side (line 690-692)**:
```typescript

'        ? \' data-raw-formula="\' + htmlEscape(e.formula) + \'"\'',
'        : \'\';',
```

**Why the divergence is currently safe**: `buildClientScript` is only emitted when `nonce !== undefined` (line 192-194), and `nonce !== undefined` is the same gate that makes `editable = true` for the SERVER renderer (line 95). So at V3.6.0.6 the client script always runs in the editable mode where the attribute is meaningful. The divergence is benign today.

**Why it's fragile**:
1. A future change that introduces a non-editable nonced path (e.g., V3.7+ readonly virtualization for large workbooks with scroll-handler-only nonce) would silently break: the client would emit `data-raw-formula` on non-editable cells, but `beginEdit` would never run (no click handler), so the attribute would be dead weight.
2. More critically, a future change that emits the client script in a non-editable mode would have the client emit attribute strings that the server-rendered initial paint does NOT include — causing a visible "flicker" or shape mismatch on first scroll-triggered repaint.
3. Drift surface: server vs client mirror pattern is documented at `cellGridHtml.ts:344-360` ("V3.3.0.4 + V3.3.0.X drift hazard"); D5 widens the drift surface by introducing an asymmetric guard.

**Closure options**:

(a) **In-cycle**: pass an `editable: boolean` parameter into `renderRowsClient` (currently the function takes only `entries`). Capture editability in a closure-scoped const at the buildClientScript boundary OR inline the `editable === true` test inside `renderRowsClient`.

(b) **Defer + document**: add an inline comment at line 690 explicitly noting "client always runs in editable mode at V3.6.0.6 because buildClientScript only emits when nonce !== undefined". Document the drift hazard for V3.7+.

**Recommendation**: option (b). The drift surface is documented at cellGridHtml.ts:344-360 and the V3.3.0.X audit closure made the same trade-off. Adding the `editable` parameter increases drift surface area without immediate benefit. But the comment is required; the V3.6.0.6 D5 commit added the asymmetry without a comment justifying it.

### C.7  OPUS-V3-6-0-6-LOW-1 — `text` param has no validation at any layer; long-text / NUL-byte / control-char hazards documented as accepted

**Severity**: LOW (intentional design; pin the contract in test + docs).
**Files**:
- `crates/ql-bindings-node/src/lib.rs:1258` (engine napi accepts any String)
- `extensions/quantlab/src/quantbook/session.ts:138-140` (IDE wrapper checks only `typeof text === 'string'`)

The IDE wrapper validates `typeof text === 'string'` but accepts:
- Empty string `''` (intentional; allowed and tested).
- Strings containing NUL `\0` (Rust String tolerates; no engine-side validation).
- Strings containing control chars / RTL overrides / zero-width spaces.
- Strings of arbitrary length (no size cap; a multi-MB formula text would silently store).

The napi accepts the same; the engine's `Op::PutFormula` stores `text: String` verbatim.

**Why LOW**: this is consistent with `Op::PutValue { value: CellWireValue::Text(s) }` which also accepts arbitrary strings. Formula evaluation surfaces parse errors at recompute time, not at append time. So pre-rejecting at the wire would be inconsistent with the existing CellWireValue::Text contract.

**Concerns to acknowledge**:
- A user pasting a 100MB formula text from clipboard would silently bloat the op log. No DoS protection.
- A malicious .qbook file with a 1GB formula text would expand on load.
- A NUL byte mid-formula would survive serde_json round-trip BUT could break some downstream consumers (e.g., a C-FFI that uses null-terminated strings).

**Closure options**:

(a) **Document the contract**: amend the `appendPutFormulaValidated` docstring and the engine napi docstring to enumerate "accepts any string; no size cap; no NUL byte rejection; no control-char rejection; consistent with `Op::PutValue` text variant".

(b) **Add a soft size cap**: e.g., reject `text.length > 32_768` (typical Excel formula max is 8192 chars) at the IDE wrapper. Engine could match. Not a hard correctness requirement; mostly DoS hygiene.

**Recommendation**: (a) docstring update only. Defer (b) to V3.6.1+ if a user-facing DoS scenario surfaces.

### E.4  napi-rs 3.9.0 u16 silent-coercion behavior (HIGH-3)

Verified via `/Users/sanzhar/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/napi-3.9.0/src/bindgen_runtime/js_values/number.rs:46-57`:

```rust
impl FromNapiValue for u16 {
    unsafe fn from_napi_value(env, napi_val) -> Result<Self> {
        let mut ret = 0_u32;
        sys::napi_get_value_uint32(env, napi_val, &mut ret); // ECMAScript ToUint32
        ret.try_into().map_err(|_| Error::from_reason("Failed to convert u32 to u16"))
    }

```

ECMAScript ToUint32 semantics confirmed via spec: NaN → 0, Infinity → 0, -1 → 4294967295, 0.5 → 0, 2.7 → 2, 2^32 → 0, 2^32 + 1 → 1, etc. (https://tc39.es/ecma262/#sec-touint32).

The "try_into rejects out-of-range" only catches the POSITIVE OVERFLOW case (e.g., 65536 survives ToUint32 and is rejected by try_into). It does NOT catch the silent-coercion cases.

The docstring claim at `crates/ql-bindings-node/src/lib.rs:876-878` ("u16's `try_into::<u16>()` correctly rejects out-of-range values from ToUint32") is technically true for the narrow case it addresses but the broader claim ("the asymmetric safety (Opus audit H2 finding) doesn't apply at u16") is wrong — H2's actual concern was silent coercion of NaN/Infinity/negative/fractional, which DOES apply.

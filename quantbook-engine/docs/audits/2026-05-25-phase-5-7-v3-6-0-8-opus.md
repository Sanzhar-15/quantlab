## Executive summary

V3.6.0.8.2's engine foundation (cache fields, accessors, invalidation discipline at 4 callsites, `apply_ops_in_range` helper) is **clean and well-tested**. The +13 ql-collab regression tests pin the right invariants. R-V3.6-14 is closed via TOP-OF-METHOD `force_clear_workbook_cache()` in `undo()` + `redo()` BEFORE Loro's undo/redo. R-V3.6-18 (apply_op private) is closed via the new public helper. Three-field invariant ("all Some / all None") is enforceable.

V3.6.0.8.3's napi surface is **functional but has several silent-correctness bugs + performance regressions invisible at this commit's test surface**. The cell-only fast-path's algorithm is mostly faithful to the V3.6.0.8.1 lock, but at least one HIGH severity correctness issue lands (AddSheet / MoveSheet / SetDateSystem / SetLocale / SetReferenceMode / CreateTable / DropTable are SILENTLY DROPPED from the delta -- the IDE returns `fullRebuildRequired: false` with empty `sheets_changed` while the engine has new sheets/tables) and at least one HIGH protocol gap (IDE consumer protocol step 2 requires a `version` token from `workbookSnapshot()` that does NOT exist on `WorkbookSnapshotJson`). Performance: the `inner.log().iter().skip(N)` pattern in BOTH the napi delta-walk AND the `apply_ops_in_range` helper deserializes ALL N skipped ops -- so a "10-cell-edit delta" at 100k log size pays O(100k) deserialize cost, defeating the spike's purpose. The Workbook clone in step 8 is `(*cached_arc).clone()` (always-clone), not the `Arc::make_mut` claimed by the V3.6.0.8.1 lock (documentation drift); per-call cost at 100k cells is unmeasured.

R-V3.6-15 PARTIAL closure (debug-assert at one site); R-V3.6-17 (clone cost) deferred PER PLAN. Both fine for V3.6.0.8.4 follow-up.

**Verdict**: **PASS-WITH-FINDINGS**. 12 findings (3 HIGH + 5 MED + 3 LOW + 1 INFO). V3.6.0.8.4 audit-of-D6 closure cycle is the natural place to close the in-cycle items.

### 1. Three-field cache invariant ("all Some / all None")

Mutation sites for the three cache fields:

| Site | Action | File:line | Verdict |
|---|---|---|---|

| `set_workbook_cache(arc, vv)` | set all 3 to `Some` atomically | session.rs:1814-1822 | OK |

| `force_clear_snapshot_cache` (test seam) | clear all 3 to `None` | session.rs:1941-1943 | OK |

Production paths that call invalidator: `merge_bytes` (session.rs:1614), `discard_pending_ops` (session.rs:3117), `undo` (session.rs:3663 -- BEFORE Loro), `redo` (session.rs:3757 -- BEFORE Loro). All correct.

Napi `workbook_snapshot` (lib.rs:2271) and `workbook_snapshot_delta` (lib.rs:2609) call `set_workbook_cache`. Both hold `inner.lock()` for the whole function, guaranteeing atomicity (`cache_vv` captured at start cannot drift from `self.log.len()` captured inside `set_workbook_cache` because the lock is held throughout).

**One brittleness**: `set_workbook_cache` takes an externally-supplied VV but internally reads `self.log.len()` for `op_count`. A caller could pass a stale VV with a fresh op_count. In practice the only caller holds the lock + captures both in the same critical section, so safe -- but the API surface invites future misuse. See OPUS-V3-6-0-8-LOW-3 below.

### 2. Algorithm correctness (8-step walk)

Step 1a (empty buffer → fullRebuild): lib.rs:2356-2358. ✓
Step 1b (no cache → fullRebuild): lib.rs:2360-2372. Uses the all-Some destructure -- correct (a "2 Some 1 None" state could fall through, but per (1) above it cannot occur). ✓
Step 2 (decode caller VV): lib.rs:2375-2385. On Err returns fullRebuild (NOT throws). Matches docstring. ✓
Step 3 (staleness check `caller_vv != cached_vv`): lib.rs:2388-2390. Uses Loro's custom `PartialEq` (FxHashMap-set-based equality, `unwrap_or(&0)`-based -- trailing-zero-counter peers compare equal -- see Loro verification below). ✓
Step 4 (same-VV fast-path `current_vv == cached_vv`): lib.rs:2393-2395. ✓
Step 5-6 (op enumeration + classify): lib.rs:2409-2476. Range is `[cached_op_count, current_op_count)` -- half-open, correct off-by-one. Defensive guard `cached_op_count > current_op_count` at line 2402-2408 returns fullRebuild + force-clears cache (handles "shouldn't happen but check anyway").
Step 7 (rename → fullRebuild): lib.rs:2479-2481. ✓
Step 8 (cell-only fast-path): lib.rs:2483-2619. Walks correctly.

**ISSUE found in Step 6's `classify_delta_op`**: silently skips `AddSheet`, `MoveSheet`, `CreateTable`, `DropTable`, `SetDateSystem`, `SetLocale`, `SetReferenceMode`. See OPUS-V3-6-0-8-HIGH-1 below.

**Loro VersionVector verification**:
- The cached `last_snapshot_oplog_vv` docstring (session.rs:983) claims `BTreeMap<PeerID, Counter>`. **WRONG**: actual upstream type is `FxHashMap<PeerID, Counter>` (verified at `~/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/loro-internal-1.12.0/src/version.rs:29`).
- Custom `PartialEq` (loro-internal version.rs:269-277) uses `unwrap_or(&0)` for missing entries in BOTH directions -- so a VV with `{A:5, B:0}` compares EQUAL to `{A:5}`. Trailing-zero counters DON'T cause spurious staleness fallbacks. ✓
- `encode()` uses `postcard::to_allocvec(self).unwrap()` (version.rs:843-845). The `unwrap()` is a panic point but only fires on truly degenerate postcard encoding (insufficient memory or similar); standard FxHashMap<u64, i32> serializes without error. **Acceptable**.
- `decode(bytes)` returns `Err(LoroError::DecodeVersionVectorError)` on malformed input -- caller's `.ok()` -> `fullRebuild` is correct.
- `encode()` does NOT necessarily produce byte-stable output across calls for the same logical VV: `FxHashMap` iteration order is bucketing-deterministic per key set (FxHasher is unseeded, hash:0 init -- see rustc-hash-2.1.1/src/lib.rs:85-87), so for a fixed insertion sequence + key set the order IS deterministic, but two different insertion orderings of the same final key set MIGHT produce different bucketing. The mocha "empty Buffer probe to get version" pattern works ONLY because equality is set-based, not byte-based. The IDE never compares `version` bytes directly; it only roundtrips them.

### 3. Borrow-checker workaround at lib.rs:2425-2432

```rust
let new_ops: Vec<std::result::Result<Op, ql_oplog::OpLogError>> = inner
    .log()
    .iter()
    .enumerate()
    .skip(new_ops_range.start)
    .take(new_ops_range.end - new_ops_range.start)
    .map(|(_idx, op_result)| op_result)
    .collect();
```

Soundness: the `inner.log()` borrow is `&OpLog`, the `.collect()` materializes into an owned `Vec` so the borrow ends at line 2432. Subsequent `inner.force_clear_workbook_cache()` (line 2462) requires `&mut`, which compiles only because the immutable borrow is gone. ✓

**But performance**: `.iter()` is `(0..len).map(|i| { LoroList::get(i) + serde_json::from_str })`. `.skip(N)` on this `Map<Range, Closure>` calls `.next()` N times, **and each `.next()` invokes the closure -- deserializing the skipped op**. So `.skip(cached_op_count)` deserializes `cached_op_count` ops just to throw them away. At 100k log + 10 new ops, this is ~100k unnecessary `serde_json::from_str<Op>` calls (each O(op size)). See OPUS-V3-6-0-8-HIGH-3 below.

### 4. R-V3.6-14 closure verification

`undo()` (session.rs:3663) calls `self.force_clear_workbook_cache()` AT TOP, BEFORE `self.undo.undo()` (line 3664). ✓
`redo()` (session.rs:3757) calls `self.force_clear_workbook_cache()` AT TOP, BEFORE `self.undo.redo()` (line 3758). ✓

**Edge case**: when `consumed=false` (empty undo/redo stack), the cache has been cleared but NOTHING in Loro's state changed. The next `workbook_snapshot_delta` returns `fullRebuildRequired=true`. The docstring at line 3753-3756 explicitly documents this as a tolerated suboptimality. Recommendation: check `can_undo()`/`can_redo()` first and skip the cache clear when no work will happen. See OPUS-V3-6-0-8-LOW-1 below.

### 6. R-V3.6-17 closure (DEFERRED PER PLAN)

V3.6.0.8.1 design lock claimed `Arc::make_mut` for the next-workbook construction (ide-consumer-contract.md:1972, 2011). V3.6.0.8.3 actual code at lib.rs:2491 is:

```rust
let mut next_workbook = (*cached_arc).clone();
```

This is **always-clone** -- it deep-clones `Workbook` every delta call. `Arc::make_mut` would have given fork-on-write semantics: clone only if `Arc` strong count > 1. With `(*cached_arc).clone()`, the deep clone is unconditional.

**Documentation drift**: the lock claim and the implementation disagree. See OPUS-V3-6-0-8-MED-3.

**Performance concern**: At 100k cells, `Workbook::clone()` deep-clones `Vec<Sheet>` (each sheet has `Vec<ColumnStore>` with chunked storage), `formula_cells: HashMap<(SheetId, RowId, ColId), Arc<str>>` (Arc::clone is cheap, HashMap structure is not), `FormatTable`, `SpillAnchorTable`, `TableTable`, etc. The V3.6.0.7 spike measured `rebuild_workbook` (which includes `replay_into` + 3 repair walks) at 251 ms; `Workbook::clone()` at 100k cells likely runs 10-50 ms by itself. V3.6.0.8.4 bench must measure this. See OPUS-V3-6-0-8-MED-4.

Notes: `Arc::make_mut` would NOT be the right replacement because at the moment the napi takes `cached_arc = Arc::clone(arc)`, the strong count is 2 (cache + our local), so `make_mut` would clone anyway. To get true fork-on-write, the cache would need to be replaced with `take()` semantics (cache's Arc moved out, leaving cache empty until we set_workbook_cache back at the end). That's an architectural change.

### 7. BatchCommit recursion in `classify_delta_op`

lib.rs:408-420. Recurses correctly into nested ops. Short-circuits on `has_rename=true` at line 417-419 inside the inner loop. Empty `BatchCommit { ops: [] }` is a no-op (for loop iterates 0 times). Nested `BatchCommit { BatchCommit { ... } }` correctly recurses to arbitrary depth.

**Subtle**: if a BatchCommit's `ops` contains `[PutValue, RenameSheet, PutValue]`, after RenameSheet sets `has_rename=true`, the loop exits via the inner check before processing the trailing PutValue. The outermost caller then short-circuits at lib.rs:2473-2475. The trailing PutValue's `changed_cell_coords` entry is never added -- but since `has_rename=true` triggers a full rebuild anyway, this is irrelevant. ✓

`apply_op` in replay.rs:850-858 also handles `Op::BatchCommit` via recursion. Behavior matches `classify_delta_op` semantically (both walk recursively). ✓

### 10. IDE consumer protocol race window

The two-call IDE protocol (per the docstring at lib.rs:925-933 + ide-consumer-contract.md:1963-1968):
1. First call: empty Buffer → fullRebuild + version.
2. IDE calls `workbookSnapshot()` for the full state, "records the returned `version` token alongside".
3. Subsequent calls: IDE passes the stored `version`.

**HIGH GAP**: `WorkbookSnapshotJson` (types.ts:233-274) has NO `version` field. The docstring at lib.rs:927-929 + types.ts:336-338 + ide-consumer-contract.md:1966 all CLAIM the IDE records a version from `workbookSnapshot()`, but the actual napi `workbook_snapshot()` returns only `{sheets, formats, date_system}`. The IDE has no documented way to obtain the cached VV after a workbookSnapshot call. The mocha tests work around this with an "empty Buffer probe" pattern (test at line 6523), but that workaround:
- Returns the LIVE current VV, not the CACHED VV. If multiple ops appended between `workbookSnapshot()` and the probe, the probe's VV ≠ cached VV, and the next delta call with that token returns `fullRebuildRequired=true` -- which the IDE would interpret as "another full rebuild" even though no real change occurred.
- Adds a second napi call per bootstrap (2× the round-trip).

The V3.6.0.8.1 lock at ide-consumer-contract.md:1966 explicitly TBD'd this: "likely a new `currentVersion(): Buffer` napi method or `version` field on `WorkbookSnapshotJson`". V3.6.0.8.3 shipped without either. See OPUS-V3-6-0-8-HIGH-2.

For a single-threaded IDE without remote peers, the race is hypothetical -- napi calls are serialized on the libuv main thread; nothing can interleave. But the multi-window collab story (V3.5/V3.6 audit chain context) involves merge_bytes via WebSocket which CAN fire on a separate thread (per the V3.5 session WS infrastructure). The probe-then-delta two-call bootstrap leaves a 2-call race window where merge_bytes could land.

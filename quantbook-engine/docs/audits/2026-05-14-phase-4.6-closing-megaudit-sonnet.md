## Per-Concern Verdicts

### A. Sheet-Name Canonicalization

**A.1 — Canonicalizer definition:** PASS  
`Workbook::canonical_sheet_name` at `crates/ql-storage/src/workbook.rs:333–335` uses `name.to_ascii_uppercase()`. ASCII-only, consistent with Excel canon. Unicode normalisation is deliberately out of scope.

**A.2 — `sheet_id_by_name` lookup:** PASS  
`sheet_id_by_name` at `workbook.rs:344–352` compares `canonical_sheet_name(s)` vs stored `canonical_sheet_name(sheet.name())`. O(sheet_count) scan is acceptable for the current scale. Round-trips correctly.

**A.3 — `validate_sheet_name` completeness:** PASS  
`validate_sheet_name` at `workbook.rs:411–426` guards: (1) empty name, (2) Excel-reserved chars `': \ / ? * [ ]'` on ALL chars (not just the first), (3) canonical-duplicate. All three cases confirmed against spec.

**A.4 — `add_sheet` bypasses `validate_sheet_name`:** FAIL — MEDIUM  
`Workbook::add_sheet` (`workbook.rs:463–473`) does NOT call `validate_sheet_name`. The storage-layer `add_sheet` method also lacks a `try_add_sheet` variant with name validation. Duplicate names can be silently created at the raw storage level:

```rust
wb.add_sheet("Sheet1");
wb.add_sheet("sheet1"); // silently creates a second sheet with canonical collision
```

`WorkbookRuntime::add_sheet` (`workbook_runtime.rs:761–798`) also does NOT call `validate_sheet_name` — it only validates `chunk_rows == 0` and sheet count overflow. The `Op::AddSheet` replay path (`replay.rs:298–305`) likewise calls `add_sheet_with_chunk_rows` directly without name validation. This means the op-log CAN legitimately record a duplicate-name `AddSheet` emitted by a runtime caller who bypassed the runtime `add_sheet` method. The design acknowledges this as a known gap (GAP referenced in Phase 2A.6 audit M1). Severity is MEDIUM rather than HIGH because the rename path (`WorkbookRuntime::rename_sheet`) DOES call `validate_sheet_name`, and the most common user-facing add-sheet path goes through the runtime. Raw storage callers are documented as low-level.

### C. Lexer

**C.1 — `try_lex_sheet_name_prefix` ordering:** PASS  
The dispatch at `crates/ql-formula-syntax/src/lexer.rs:168` routes alpha/underscore to `try_lex_sheet_name_prefix` BEFORE `lex_ident_or_ref`. The order is correct; unquoted sheet names starting with `[A-Za-z_]` are correctly caught.

**C.2 — Cheap lookahead via `Chars::clone()`:** PASS  
`lexer.rs:473–531` uses `self.chars.clone()` for the `!` lookahead. No allocation, no state corruption if lookahead fails.

**C.3 — `lex_quoted_sheet_name` `''` escape:** PASS  
`lexer.rs:539–578` handles the `''` → `'` escape inside quoted sheet names, and requires `!` immediately after the closing `'`. Correct Excel canon.

**C.4 — Digit-starting unquoted sheet names:** PASS (by design — documented limitation)  
The lexer only enters `try_lex_sheet_name_prefix` for `[A-Za-z_]`; digit-starting names (e.g., `1Sheet`) route to `lex_number`, leaving `!` as an unexpected token. This means digit-starting names MUST be quoted. No explicit rejection at lex time; the parse will surface an error via the unexpected `!`. The lexer does not silently accept malformed input — it surfaces errors at a different layer. This is consistent with Excel's behavior (digit-starting sheet names must always be quoted). Documenting rather than flagging.

### E. Printer

**E.1/E.4 — `print_sheet_prefix` panics on `SheetRef::Id`:** FAIL — MEDIUM  
`crates/ql-formula-syntax/src/printer.rs:82–85`:

```rust
SheetRef::Id(id) => panic!("SheetRef::Id({id}) cannot be printed without a resolver ..."),
```

Any code that attempts to print a post-bind AST (where `SheetRef::Name` has been resolved to `SheetRef::Id` by the binder) will panic. The rename rewrite round-trip in `workbook_runtime.rs:85–108` correctly uses a pre-bind parse (never binds before printing), so the panic is not triggered in the current happy path. Severity: MEDIUM (no current crash path, but the API is a trap for future contributors).

**E.5 — `SheetRef::Name` emits correct token:** PASS  
`Name(name)` → `print_sheet_name + !`. Correct.

### L. Rename Edge Cases

**L.1 — Case-only rename allowed:** PASS  
`workbook_runtime.rs:839–843`: if `new_canonical == old_canonical` (i.e., case-only change), `validate_sheet_name` is skipped. Correct — a case-only rename cannot produce a duplicate.

**L.2 — `NamedTarget::Formula` entries NOT rewritten on rename:** FAIL — MEDIUM  
`workbook_runtime.rs:855–857`:
```rust
// (Phase 4.6.D / future): walk NamedTarget::Formula entries for
// the same rewrite. Today named formulas are deferred so
// formula_cells is the only text-bearing surface to rewrite.
```
The design doc §3.1 step 4 explicitly says rename should rewrite `NamedTarget::Formula` entries in BOTH workbook `names` AND per-sheet `scoped_names`. The implementation skips this. If a named formula contains a cross-sheet reference (e.g., `Sheet1!A1 + 1`) and the user renames `Sheet1`, the named formula text will contain a stale reference after the rename.

This is currently low-impact because `NamedTarget::Formula` entries are not fully surfaced in the formula-evaluation path (deferred to Phase 3+). However, the formula text is persisted via `.qbook` save/load and op-log replay — a stale text will silently carry incorrect references into future phases when named formulas are evaluated. The comment says "today named formulas are deferred" but does not document this as a known gap or file a follow-up issue. Severity: MEDIUM (latent correctness gap, not a current user-visible crash).

**L.3 — Scoped-names formula entries not rewritten on rename:** FAIL — MEDIUM  
Same as L.2 but specifically for per-sheet `scoped_names` entries. The rename walk (line 848) uses `self.workbook.iter_formulas()` which iterates cell formula texts only — it does not iterate `NamedTarget::Formula` entries in either `workbook.names()` or any sheet's `scoped_names`. The `scoped_names` path was added in W5-92 and was not added to the rename walk. Same severity as L.2: MEDIUM.

**L.4 — Rename with no cross-sheet references is correct:** PASS  
When no formula references the renamed sheet, `rewritten_cells` is empty, the `BatchCommit` contains only `[RenameSheet]`, and the name swap proceeds. Correct.

**L.5 — Excel-reserved-char rejection on rename:** PASS  
`workbook_runtime.rs:842` calls `workbook.validate_sheet_name` which checks all chars via `matches!(c, ':' | '\\' | '/' | '?' | '*' | '[' | ']')`. Correct.

**L.6 — Reserved-name guard fires on sheet-scoped path:** PASS  
`crates/ql-storage/src/sheet.rs:101–107`: `set_scoped_name` calls `self.scoped_names.set(name, target)` → `NameTable::set` → `is_reserved_name` guard. Confirmed by test at `sheet.rs:407–414`.

**L.7 — `NameTable` hash stability:** PASS  
`NameTable` uses `Arc<str>` keys stored in canonical (uppercase) form. Hash is stable across renames because renames don't mutate `NameTable` directly — they rewrite formula texts and clear the plan cache.

## What Is Needed for W5-93 Closure

### HIGH

None. There are no HIGH-severity findings — no crash path in the current happy path, no data loss in the current feature set, no security issue.

### MEDIUM

**MEDIUM-1 — L.2/L.3: `rename_sheet` does not rewrite `NamedTarget::Formula` in workbook `names` or sheet `scoped_names`.**  
Design §3.1 step 4 explicitly requires this. The comment in `workbook_runtime.rs:855–857` acknowledges the gap but does not file a tracking issue. Before W5-93 close, either: (a) implement the rewrite for `NamedTarget::Formula` entries in both `wb.names()` and all per-sheet `scoped_names`, or (b) explicitly document this as a deferred gap with a JIRA/issue reference and a target phase. Doing (b) without (a) is acceptable for W5-93 if named-formula evaluation is not in scope for Phase 4.6.

**MEDIUM-2 — E.1/E.4: `print_sheet_prefix` panics on `SheetRef::Id`.**  
The rename rewrite round-trip does not trigger this because it never binds before printing. However, the footgun is real: any future code that binds a formula (converting `Name` → `Id`) then attempts to print the AST will panic. Options: (a) implement `print_with_resolver` API that takes a `SheetId → &str` resolver, or (b) add a `#[doc(hidden)]` warning and a prominent comment on `print_sheet_prefix` noting the `Id` panic, and file a tracking issue. For W5-93 close, (b) is acceptable.

**MEDIUM-3 — A.4: `WorkbookRuntime::add_sheet` does not validate sheet name for duplicates.**  
`validate_sheet_name` is not called in the runtime `add_sheet` path. A caller can add `"Sheet1"` and then add `"sheet1"` without rejection. The rename path correctly validates, creating an inconsistency. For W5-93 close: add `self.workbook.validate_sheet_name(&name)?` to `WorkbookRuntime::add_sheet` (before the op-log append) for the case where a name is being set. This mirrors the rename validation pattern already in place.

### LOW

**LOW-1 — M.2/M.3: Producer-replay equivalence test does not cover `scope: Some`.**  
The `realistic_op_sequence` in `producer_replay_equivalence.rs` uses only `scope: None`. Add a `scope: Some(0)` `SetName` op to the sequence, and extend `assert_workbooks_observationally_equal` to compare `sheet(id).scoped_names()` for each sheet. This pins the replay correctness for the W5-92 path at the integration level.

**LOW-2 — M.4: No test covers `rename_sheet` with a `NamedTarget::Formula` cross-sheet reference in scoped names.**  
Add a test that: registers a `NamedTarget::Formula("Sheet1!A1 + 1")` on a sheet, renames `Sheet1`, and asserts the formula text is updated (or explicitly asserts it is NOT updated and is therefore a known open gap until L.2/L.3 is fixed).

**LOW-3 — I.3: `NamedEntry` lacks `#[serde(deny_unknown_fields)]`.**  
All other envelope structs have `deny_unknown_fields`. Add `#[serde(deny_unknown_fields)]` to `NamedEntry` for consistency and forward-compat robustness. Lowest-risk change.

**LOW-4 — N.2: XS-4-01 "print" acceptance criterion.**  
The criterion says "cross-sheet cell refs parse, print, bind, and recompute." The `print` direction from a post-bind AST panics. Either scope down the criterion to "pre-bind print" or track the `print_with_resolver` API as a follow-up under XS-4-01. An explicit statement in the MASTER-PLAN that `print` is scoped to pre-bind ASTs would close this interpretive gap.

# Phase 5.7 V2.3 — Opus adversarial audit lane (async Transport surface)

## Scope

V2.3 adds two methods that introduce async surface for the first
time in the V1+V2 binding arc:

- `Transport.websocketConnect(url: String) -> Promise<Transport>` —
  async static factory wrapping `ql_collab_ws::WebSocketTransport::connect`.
- `CollabSession::flushPendingToTransport() -> Promise<void>` — async
  `&mut self` method wrapping the engine's sync `flush_pending_to_transport`
  (Condvar wait inside).

The `async` feature was added to the workspace `napi` dependency (→
`tokio_rt` → static multi-thread tokio runtime). `ql-collab-ws` was
added as a fresh dep on `ql-bindings-node`.

This lane checks: tokio runtime ownership semantics, the `unsafe` /
async `&mut self` pattern's actual safety vs documented safety,
Condvar-blocking-tokio-worker hazards, JS re-entry into `&mut self`
during await, WebSocket error discrimination (V2.2 MEDIUM-3
carry-forward), test fixture (`spawnWsRelay`) race conditions and
fan-out semantics, Promise lifecycle on process exit, Send/Sync claims
(Rule 4 sweep), and the carry-forward of V2.1+V2.2 audit items.

## Verdict

**PASS-WITH-FINDINGS** with two consequential HIGHs that should close
before V2.7 megaudit. Findings cluster around the async-pattern's
informal safety story:

1. **HIGH-1**: the V2.3 binding wraps a sync Condvar-blocking method in
   `#[napi]` async without `spawn_blocking`. A tokio worker thread is
   occupied for the duration of the Condvar wait. With napi-rs's
   single shared multi-thread runtime, N concurrent `flushPending`
   calls can starve the runtime — and since the WebSocket reader+writer
   tokio TASKS share the same runtime, starvation produces a deadlock
   (the writer task can't make progress → the Condvar never gets
   notified → the worker stays blocked). The current docstring
   rationalizes this away inconsistently with its own opening paragraph
   (lines 720-728 claim spawn_blocking IS used; lines 749-768 explain
   why it ISN'T).

2. **HIGH-2**: the `unsafe pub async unsafe fn ... &mut self`
   docstring claims "napi-rs's generated wrapper holds the `Reference<T>`
   exclusively for the duration of the await." This is FALSE per
   napi-derive-backend 5.0.4 source — the generated code does
   `Box::leak(Box::from_raw(this_ptr))` to produce a `&'static mut
   CollabSession` captured by the future, with NO lock or
   exclusive-access mechanism on the JS object. JS can re-enter the
   same instance during the await (e.g., `session.appendPutValue(...)`
   called while `await session.flushPendingToTransport()` is pending).
   The second call's `unwrap_raw` produces a SECOND `&'static mut
   CollabSession` to the same memory. **Two simultaneous Rust `&mut`s
   to the same data is UB.** This is exactly the hazard the `unsafe`
   marker exists to flag — but the binding does not enforce any
   discipline that would prevent it. The Send + !Sync argument (V1
   megaudit Opus-A M1 closure) is about cross-Worker sharing — it does
   NOT prevent same-thread re-entry.

Rule 4 (negative trait claims): no new !Send/!Sync claims in V2.3. The
V2.1 + V2.2 `Send + !Sync` story for CollabSession carries through with
no modification, and the V2 V4 V1 step 3 positive Send+Sync compile
asserts on `WebSocketTransport` cover the new boxed-transport path.
The current V2.3 compile-asserts at lib.rs:1021-1039 are correct.

V2.2 → V2.3 propagation: MEDIUM-3 (lossy Transport error mapping) is
now LOAD-BEARING because WebSocket can actually error. Lifted to
MEDIUM-1 below.

The 7 mocha tests cover the happy path adequately but ALL exercise
single-session, single-flush scenarios. **None of them stress the
HIGH-1 or HIGH-2 hazards** — those require concurrent calls or
multi-session-shared-runtime scenarios that are out-of-scope for the
V2.3 test surface but reachable in real IDE usage.

## HIGH

### HIGH-1: `flushPendingToTransport` async wrapper blocks a tokio worker for the duration of the Condvar wait — N concurrent calls can starve the napi-rs single shared multi-thread runtime, blocking the WebSocket reader+writer tokio tasks themselves and producing a deadlock

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:747-769` (binding) +
`crates/ql-collab/src/session.rs:855-861` (engine method) +
`crates/ql-collab-ws/src/lib.rs:733-760` (`WebSocketTransport::flush_pending`).

**Specific issue**:

The V2.3 binding for `flushPendingToTransport` is:

```rust
#[napi(js_name = "flushPendingToTransport")]
pub async unsafe fn flush_pending_to_transport(&mut self) -> Result<()> {
    self.inner
        .flush_pending_to_transport()
        .map_err(|e| Error::from_reason(format!("{e}")))
}
```

The `async fn` body has NO `.await`. When napi-rs spawns this future
onto its global tokio runtime (via
`execute_tokio_future_with_finalize_callback` — verified by reading
`napi-3.9.0/src/tokio_runtime.rs:256-320`), the future is polled once
and executes the ENTIRE sync body to completion before returning Ready.

The sync body calls `self.inner.flush_pending_to_transport()` →
`t.flush_pending()` → for `WebSocketTransport`,
`std::sync::Condvar::wait_timeout(counter, Duration::from_millis(100))`
in a loop until either the writer task has caught up or the transport
is closed (`ql-collab-ws/src/lib.rs:733-760`).

**`Condvar::wait_timeout` blocks the calling thread.** The calling
thread is a tokio worker thread (per
`napi-3.9.0/src/tokio_runtime.rs:12-43`:
`tokio::runtime::Builder::new_multi_thread().enable_all().build()`).
Default tokio worker count = `num_cpus` (per
`tokio-1.50.0/src/runtime/builder.rs:1780`).

**The runtime is SHARED with the WebSocketTransport's tokio tasks.**
napi-rs's runtime is `static RT: LazyLock<RwLock<Option<Runtime>>>`
(tokio_runtime.rs:46-47) — process-wide singleton. When
`WebSocketTransport::connect` is called from the napi async binding,
its `connect_async` future runs on this same runtime. The two
spawned tasks (`writer_task`, `reader_task`) at
`ql-collab-ws/src/lib.rs:412, 469` are also on this runtime.

**Starvation scenario (N concurrent flushPending)**:

1. IDE attaches WebSocket transports to N=8 sessions (one per
   workspace folder, say).
2. Some external event triggers 8 simultaneous
   `await session.flushPendingToTransport()` calls.
3. Each call's future is spawned onto the napi tokio runtime.
4. Tokio scheduler picks each up; all 8 worker threads (typical
   `num_cpus`) enter Condvar::wait_timeout.
5. **Now no worker thread is available to poll the
   `writer_task`/`reader_task` futures.** The writer task can't
   make progress on `ws_sink.send` → `progress.0` doesn't advance
   → the Condvar isn't notified → the worker threads stay blocked.
6. Deadlock until the 100ms `wait_timeout` ticks fire and the
   workers re-poll the closed flag, find it unchanged, and re-enter
   `wait_timeout`.

The deadlock isn't permanent (`wait_timeout` periodically wakes), but
it's catastrophic for IDE UX — every Condvar wait_timeout cycle is
100ms of writer-task starvation. In the limit (every worker blocked
in `flush_pending`), the system performs 10 writer-task pollings per
SECOND across the whole runtime.

**The current docstring is internally inconsistent**:

- Lines 720-728: "we wrap with `tokio::task::spawn_blocking` to avoid
  blocking a tokio worker. (Without spawn_blocking, the Condvar wait
  would tie up a worker thread; with it, the wait goes to a dedicated
  blocking-task thread.)"
- Lines 749-768: "For V2.3, call directly without spawn_blocking.
  The wait IS blocking from a tokio worker's perspective, but
  napi-rs's async entry-point runs each call on a freshly-allocated
  future that doesn't tie up napi's threadsafe-function queue."

The body at lines 766-768 does NOT use spawn_blocking. The opening
docstring at lines 720-728 LIES about the implementation; the
mid-method comment at lines 749-768 is correct but the rationale
("doesn't tie up napi's threadsafe-function queue") confuses two
issues — yes it doesn't tie up the threadsafe-function queue, but it
DOES tie up a tokio worker. The threadsafe-function queue isn't the
bottleneck; the worker thread pool is.

The V1 megaudit Opus-B M2 (`docs/audits/2026-05-22-phase-5-7-v1-megaudit-opus-b-v2.md`
line 138-141) explicitly flagged this: "The V2 binding MUST be
`#[napi(ts_args_type = "...")]` async + spawn the blocking call onto
a worker thread via napi's `AsyncTask`, OR document that the JS-side
caller is responsible for not calling it from a busy main thread."

V2.3 did neither. The current implementation is "documented as
acceptable in the body comment" but the V1 megaudit prescription was
explicit: use spawn_blocking OR document the contract to JS callers.
The V2.3 binding does neither — the TS-side `flushPendingToTransport`
JSDoc at types.ts:236-254 makes NO mention of this hazard.

**Closure recommendation**: **FIX NOW** before V2.7 megaudit. Wrap
the body in `napi::bindgen_prelude::spawn_blocking`:

```rust
#[napi(js_name = "flushPendingToTransport")]
pub async unsafe fn flush_pending_to_transport(&mut self) -> Result<()> {
    // We can't move &mut self into spawn_blocking safely (no
    // exclusive-access guarantee across the thread boundary).
    // Engine refactor required: either (a) extract the Condvar
    // wait into a clone-able handle (Arc<...>) and call
    // flush_pending on that without &mut self, OR (b) restructure
    // the engine method to take &Transport and use spawn_blocking
    // with the Arc-cloned handle.
    //
    // Until that refactor lands, document the hazard explicitly
    // in the JSDoc:
    //   "Calling this concurrently from many sessions can starve
    //   the napi-rs tokio runtime; serialize calls if your IDE has
    //   N>4 concurrent sessions on WebSocket transports."
    self.inner
        .flush_pending_to_transport()
        .map_err(|e| Error::from_reason(format!("{e}")))
}
```

The right fix is the engine refactor — clone-able Arc-handle to the
transport's progress channel, exposed as a separate
`Transport::flush_pending_handle() -> impl Send + Future<Output=...>`
method that returns an actually-async future (using
`tokio::sync::Notify` instead of `std::sync::Condvar`). Then the
binding can `.await` that future directly without holding a worker
thread blocked. This is also what the docstring at lib.rs:729-732
foreshadows: "V3 may push the Condvar itself behind an async signal
(tokio::sync::Notify)."

If the engine refactor is too large for this cycle, **AT MINIMUM**:
1. Delete the lying opening docstring (lines 720-728) about
   spawn_blocking.
2. Add a `## Tokio runtime starvation hazard` section to the V2.3
   docstring + types.ts JSDoc warning callers about concurrent-call
   semantics.
3. Add a load test to the IDE mocha that proves 4+ concurrent
   `flushPendingToTransport` calls on Loopback transports complete
   in < 5s (Loopback uses the trait default, no Condvar, so this is
   a smoke that the runtime spawning works). The HARD test (WS
   starvation) needs an engine refactor — defer to V2.4.

**Why HIGH**: this is the V1 megaudit Opus-B M2 hazard ESCALATED by
V2.3 actually binding the method without the prescribed mitigation.
The deadlock pattern is reachable in normal IDE usage (multi-workspace,
multi-session), and the docstring lies about the implementation.

**Likely convergent**: Codex protocol lane may catch this from the
tokio runtime starvation analysis, OR may miss it because the V2.3
test suite doesn't exercise concurrency. The internal-inconsistency
docstring lie is opus-territory.

### HIGH-2: `unsafe pub async fn ... &mut self` docstring claim "napi-rs holds the `Reference<T>` exclusively for the duration of the await" is FALSE — napi-rs creates `&'static mut CollabSession` via `Box::leak(Box::from_raw(...))` with NO locking, and JS can re-enter the same instance during the await, producing aliasing `&mut`s (Rule 4 / undefined behavior)

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:734-746` (docstring
claim) + napi-derive-backend 5.0.4
`/Users/sanzhar/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/napi-derive-backend-5.0.4/src/codegen/fn.rs:285-291`
(actual codegen).

**Specific issue**:

The binding's docstring at lines 734-746 says:

> **`unsafe` marker (napi-rs constraint, V2.3 design note)**:
> napi-rs requires `&mut self` async methods to be marked
> `unsafe` because the async pause-point COULD theoretically
> allow a concurrent JS re-entry on the same instance. In
> practice JS is single-threaded per Worker, AND napi-rs's
> generated wrapper holds the `Reference<T>` exclusively for
> the duration of the await. So calling this from JS is safe.
> The `unsafe` is a Rust-side discipline marker, not a hazard
> for the JS caller — they see `session.flushPendingToTransport()`
> the same as any other async method.

**This claim is wrong.** Reading napi-derive-backend 5.0.4 `codegen/fn.rs:285-291`:

```rust
Some(FnSelf::MutRef) => {
    refs.push(make_ref(quote! { cb.this }));
    arg_conversions.push(quote! {
        let this_ptr = cb.unwrap_raw::<#parent>()?;
        let this: &mut #parent = Box::leak(Box::from_raw(this_ptr));
    });
}
```

The generated code:
1. Calls `cb.unwrap_raw::<CollabSession>()` to get a raw `*mut
   CollabSession` from the wrapped JS object's slot. Per
   napi-3.9.0/src/bindgen_runtime/callback_info.rs:277-292,
   `unwrap_raw` just calls `napi_unwrap` and casts the void pointer
   — **NO LOCKING, NO REFERENCE COUNTING**.
2. `Box::leak(Box::from_raw(this_ptr))` produces a `&'static mut
   CollabSession`.
3. This `&'static mut` is captured by the future closure (via the
   `let this: &mut #parent = ...` binding feeding into
   `this.flush_pending_to_transport()`).
4. The future is then handed to
   `execute_tokio_future_with_finalize_callback`, which spawns it
   on the global tokio runtime via `spawn(inner)`.

**Critically**: the `NapiRefContainer` created at lines 92-133 of
codegen/fn.rs is NOT a lock — it's a `napi_create_reference` that just
INCREMENTS the JS object's refcount to prevent GC during the await.
It does NOT make the JS object unreachable from JS code, nor does it
prevent JS from calling other methods on the same instance.

**Re-entry scenario** (concretely):

```js
const session = createSession(1n);
session.attachTransport(/* WebSocket */);
session.appendPutValue(0, 0, 0, 1);

// Re-entry race:
const p = session.flushPendingToTransport(); // returns Promise; future spawned on tokio runtime
session.appendPutValue(0, 0, 1, 2);           // sync call on V8 thread
await p;
```

**What happens at the Rust level**:

1. `flushPendingToTransport` napi callback runs on V8 thread.
   `unwrap_raw` returns `*mut CollabSession` (pointer P).
   `Box::leak(Box::from_raw(P))` creates `&'static mut CollabSession`
   (call it `M1`). M1 is captured by the future. Future is spawned
   onto tokio runtime. V8 thread returns Promise to JS.
2. `appendPutValue(0, 0, 1, 2)` napi callback runs on V8 thread.
   `unwrap_raw` returns the SAME `*mut CollabSession` (pointer P).
   `Box::leak(Box::from_raw(P))` creates a SECOND `&'static mut
   CollabSession` (call it `M2`). M2 is local to the sync call.
3. Concurrently:
   - V8 thread is using M2 to call `self.inner.append_op(...)` which
     mutates `self.inner.log` (LoroDoc).
   - Tokio worker thread is using M1 to call
     `self.inner.flush_pending_to_transport(&mut self)` which
     accesses `self.inner.transport`.

**Two `&mut CollabSession`s are simultaneously live on different
threads, both writing into the same `CoreCollabSession` memory.**
This is undefined behavior per Rust's aliasing rules, even if the
specific fields touched don't overlap. The compiler is licensed to
assume `&mut` is exclusive.

The CURRENT V2.3 binding only writes to `self.inner.transport` from
the flush path and `self.inner.log` from the append path — those are
disjoint memory regions, so the **OBSERVABLE** behavior is benign in
practice. But:
1. UB is UB; future compiler optimizations (e.g., niche optimization
   on Option<Box>, dead-store elimination assuming `&mut` exclusivity)
   could MISCOMPILE.
2. A V2.4+ method that touches both `self.inner.log` and
   `self.inner.transport` would create observable data races.
3. The V2.3 engine method's body already takes a `&mut Transport`
   (`self.transport.as_mut()`) — re-entry with another `&mut self`
   that itself extracts `&mut self.inner.transport` (e.g., via a
   `detachTransport` call) WOULD overlap.

Concretely: **`session.detachTransport()` called during
`await session.flushPendingToTransport()` IS UB today**:
- M1 holds `&mut self.transport` (the Option) via `as_mut()`.
- M2's detach calls `self.inner.detach_transport()` which does
  `self.transport.take()`.
- Both write to `self.transport.Option<...>` simultaneously.

This IS observable. The V2.3 mocha tests don't exercise this combo,
but it's a realistic IDE pattern: "user closed the file → JS detaches
the transport, then awaits the pending flush" — and the JS code that
naturally writes `session.detachTransport(); await
session.flushPendingToTransport();` would be fine, but the inverted
order or the concurrent pattern produces UB.

**The Send + !Sync argument doesn't apply.** The V1 megaudit Opus-A M1
closure argument is about cross-Worker sharing (different V8 isolates,
different threads). It correctly proves you can't `await
otherWorker.session.flushPending()` because `Reference<CollabSession>`
is !Send. But re-entry on the SAME V8 thread doesn't go through
`Reference::send` — it goes through the napi class's stored `*mut T`
on each call.

The `unsafe` keyword is exactly the napi-rs author's acknowledgment of
this hazard. The binding's docstring at lines 734-746 misreads the
`unsafe` as "just a Rust syntax requirement" when it's actually
"YOU MUST GUARANTEE no JS re-entry on this instance during the
await." The current binding does NOT guarantee that.

**Closure recommendation**: **FIX NOW**. Two options:

**Option A (recommended)**: serialize calls per-session via a Rust-side
guard. Add a `flush_pending_in_progress: AtomicBool` field on the
napi `CollabSession` wrapper. The async fn:
```rust
#[napi(js_name = "flushPendingToTransport")]
pub async unsafe fn flush_pending_to_transport(&mut self) -> Result<()> {
    if self.flush_pending_in_progress.swap(true, Ordering::SeqCst) {
        return Err(Error::from_reason(
            "flushPendingToTransport already in progress on this session; \
             concurrent calls are not supported (would cause &mut self aliasing UB)"
                .to_string(),
        ));
    }
    let result = self.inner.flush_pending_to_transport().map_err(...);
    self.flush_pending_in_progress.store(false, Ordering::SeqCst);
    result
}
```
This rejects re-entry loudly. The IDE either serializes the calls
itself, or sees the error and handles. Per CLAUDE.md no-fallback: fail
loudly, don't silently corrupt state. (Note: this still doesn't fully
solve the OTHER `&mut self` methods racing — see Option B.)

**Option B (correct)**: switch the engine method to take `&self` and
hide the mutation behind interior synchronization. The
`flush_pending` on WebSocketTransport is already thread-safe (Condvar
+ Mutex). The engine's `flush_pending_to_transport(&mut self)` only
needs `&mut` because it calls `&mut t.flush_pending()`. But
`WebSocketTransport::flush_pending(&mut self)` could be
`flush_pending(&self)` since its internals are Arc<Mutex>/Arc<Condvar>
— the `&mut` is required by the Transport trait, not by the
implementation. Adding a `flush_pending_shared(&self) -> ...` method
to the trait + binding-side support would eliminate the `unsafe`
need entirely.

**Option C (cheapest)**: REWRITE the docstring at lines 734-746 to
state the actual contract clearly. Approximately:

> **`unsafe` marker (THIS IS LOAD-BEARING)**: napi-rs cannot prevent
> the JS event loop from re-entering this `CollabSession` instance
> during the await. The async fn body holds a `&'static mut
> CollabSession` (via napi-derive-backend's `Box::leak(Box::from_raw(...))`
> pattern). If JS code calls another method on the same session
> while the Promise is pending — e.g., `const p =
> session.flushPendingToTransport(); session.appendPutValue(...); await p;` —
> the second call obtains a SECOND `&'static mut CollabSession` to
> the same memory. Two simultaneous `&mut`s is UB regardless of
> field overlap. **JS callers MUST serialize calls to any method on
> this session for the duration of the Promise.** V2.4+ will add a
> Rust-side guard that rejects concurrent calls loudly (per CLAUDE.md
> no-fallback). Until then, the IDE is responsible.

The Option C path SHIPS the docstring lie corrected NOW, defers the
hard fix to V2.4 with a clear backlog entry. But it does NOT close
the UB hazard — just makes it visible to maintainers.

**Why HIGH**: V1 megaudit memory notes Rule 4: "negative trait
claims need positive compile proof OR per-field walk." The
`Reference<T>: !Send` argument was the positive proof for cross-Worker
isolation. There is NO positive proof for same-V8-thread re-entry
prevention — and the docstring claims one ("napi-rs's generated
wrapper holds the `Reference<T>` exclusively") that doesn't exist in
the source. This is exactly the audit-discipline failure pattern Rule
4 was added to catch.

**Likely convergent**: Codex protocol lane reads napi-derive-backend
source for the V2.3 audit (per its protocol-lane pattern). The codegen
walk should reveal the lack of locking. Opus-lane catches the
docstring lie + the re-entry scenario.

## MEDIUM

### MEDIUM-1: WebSocket error discrimination via substring match — V2.3 is the FIRST step where this carry-forward from V2.1+V2.2 is actually reachable (LoopbackTransport never errors, WebSocketTransport does). The V2.3 binding doesn't add `Error.code` discrimination, so IDE reconnect logic must substring-match Display strings.

**Repo**: engine + IDE.
**File:line**: `crates/ql-bindings-node/src/lib.rs:893-901` (V2.3
binding) + `crates/ql-collab-ws/src/lib.rs:214-239` (WebSocketError
variants).

**Specific issue**:

The V2.3 binding's `Transport.websocketConnect` maps `WebSocketError`
to JS Error via `format!("{e}")`:

```rust
#[napi(js_name = "websocketConnect")]
pub async fn websocket_connect(url: String) -> Result<Transport> {
    let ws = WebSocketTransport::connect(&url)
        .await
        .map_err(|e| Error::from_reason(format!("{e}")))?;
    Ok(Transport { inner: Some(Box::new(ws)) })
}
```

The 4 `WebSocketError` variants produce these Display strings:
- `InvalidUrl(msg)` → `"invalid WebSocket URL: {msg}"`
- `ConnectFailed(msg)` → `"WebSocket connection failed: {msg}"`
- `HandshakeFailed(msg)` → `"WebSocket handshake failed: {msg}"`
- `RuntimeError(msg)` → `"WebSocket runtime error: {msg}"`

The mocha test at line 1043-1049 substring-matches three of these:

```ts
await assert.rejects(
    engine.Transport.websocketConnect('not-a-ws-url'),
    /invalid WebSocket URL|WebSocket connection failed|WebSocket handshake failed/,
);
```

This is FRAGILE:
1. The Display strings are not stable API — they're `#[derive(Error)]`
   `#[error("...")]` strings that a future minor release could change.
2. The catch-all in `WebSocketTransport::connect` at lines 362-371
   routes `tungstenite::Error::Url` to InvalidUrl, `Error::Io` to
   ConnectFailed, `Error::Http`/`HttpFormat` to HandshakeFailed, and
   **everything else** (capacity, ProtocolError, Tls, etc.) ALSO to
   HandshakeFailed. The IDE can't distinguish "TLS not supported" from
   "HTTP 401" — both surface as HandshakeFailed with different inner
   messages.
3. JS callers writing reconnect logic do `error.message.includes(
   "connection failed")` — vulnerable to string reformatting.

V2.1 MEDIUM-3 said: "V2.2 should either: (a) Bind
`transport_last_error()` AND add a `kind()` accessor with stable
string discriminant, OR (b) Switch the IDE binding to throw a
structured error subclass." V2.2 took (a)-without-(a) — bound
`transport_last_error()` but skipped the `kind()` discriminant.

V2.3 is the FIRST step where WebSocketTransport can actually produce
non-trivial errors at the JS surface. The right time to add
`Error.code` was V2.3. Instead V2.3 ships another
`format!("{e}")` site (3 of them: connect failure mapping, transport
operation failure via attachTransport etc., flushPending failure).

**The carry-forward debt is now load-bearing**, not theoretical. The
IDE V2 demo's first WebSocket reconnect handshake will need to
distinguish at least:
- "URL parse failed" (don't retry — user must fix config)
- "Connection refused" (retry with exponential backoff)
- "Handshake failed with HTTP 401" (prompt for re-auth)
- "Handshake failed with TLS" (don't retry — V2.4 missing feature)
- "Connection closed mid-stream" (retry immediately)
- "Capacity exceeded" (retry with backoff)

The current binding flattens these into 3 variant strings + an
inner-message substring. IDE substring-matching code will break on the
first message reformatting.

**Closure recommendation**: V2 BACKLOG ITEM — **uplift to V2.4
required-before-megaudit**. Add a per-variant code string. The napi
Error has a `code` field accessible via `Error::with_code(code,
reason)` per napi-3.9.0 API. Approximately:

```rust
fn websocket_error_to_napi_error(e: WebSocketError) -> Error {
    let code = match &e {
        WebSocketError::InvalidUrl(_) => "WS_INVALID_URL",
        WebSocketError::ConnectFailed(_) => "WS_CONNECT_FAILED",
        WebSocketError::HandshakeFailed(_) => "WS_HANDSHAKE_FAILED",
        WebSocketError::RuntimeError(_) => "WS_RUNTIME_ERROR",
    };
    Error::new(Status::GenericFailure, format!("{e}"))
```

### MEDIUM-3: V2.3 two-peer round-trip test relies on a 50ms `setTimeout` between `flushPending` (level-1 ack) and `pollRemote` (peer drain) — flaky on busy CI; no explicit synchronization for the peer-side receive

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:1075-1108`.

**Specific issue**:

The round-trip test:

```ts
sessionA.appendPutValue(0, 0, 0, 42);
assert.strictEqual(sessionA.flushDeltaToTransport(), true);
await sessionA.flushPendingToTransport();

// Allow the relay to fan out + B's reader to enqueue bytes.
// 50ms is generous for localhost.
await new Promise<void>((res) => setTimeout(res, 50));

const blobsDrained = sessionB.pollRemote();
assert.ok(blobsDrained >= 1, `B drained at least 1 blob, got ${blobsDrained}`);
```

`flushPendingToTransport` only guarantees level-1 ack: bytes left A's
writer task and hit the OS kernel buffer. It does NOT guarantee:
- (a) The bytes have traveled across localhost TCP to the relay.
- (b) The relay's `ws.on('message', ...)` handler has fired.
- (c) The relay's `peer.send(data)` to B's socket has completed.
- (d) The bytes have crossed back across localhost TCP to B's reader
      task.
- (e) B's `reader_task` has dequeued the bytes from `ws_stream.next()`
      and pushed into `inbound_tx`.

All 5 steps happen in 50ms typical on localhost. But under CI load
(GitHub Actions with concurrent jobs, slow VM, OS noise), 50ms may
not be enough. The test comment says "50ms is generous for
localhost" — true on bare metal, but the test will run on CI VMs.

**Worst case observable**: `blobsDrained = 0`, test fails with
`B drained at least 1 blob, got 0`. False positive in CI.

**Closure recommendation**: V2 BACKLOG ITEM. Replace the 50ms wait
with a polling loop:

```ts
// Wait up to 5000ms for B to receive at least 1 blob.
const deadline = Date.now() + 5000;
let blobsDrained = 0;
while (Date.now() < deadline) {
    blobsDrained = sessionB.pollRemote();
    if (blobsDrained >= 1) {
        break;
    }
    await new Promise<void>((res) => setTimeout(res, 10));
}
assert.ok(blobsDrained >= 1, `B drained at least 1 blob within 5s`);
```

This:
- Polls every 10ms instead of waiting a fixed 50ms.
- Has a 5s ceiling that catches genuine failures.
- Logs how long the wait was if the test is debug-noisy.

Same fix applies to ANY test that uses `setTimeout` to wait for
async transport propagation.

**Why MEDIUM not LOW**: test flakiness is a known CI cost. Fix is
mechanical and prevents intermittent red-test noise.

### MEDIUM-4: `spawnWsRelay` test fixture uses fire-and-forget `try { s.terminate(); } catch { /* ignore */ }` — violates CLAUDE.md no-fallback rule (errors swallowed); also doesn't ensure socket cleanup completes before resolving the close()

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:1021-1026`.

**Specific issue**:

```ts
close: () => new Promise<void>((res) => {
    for (const s of sockets) {
        try { s.terminate(); } catch { /* ignore */ }
    }
    wss.close(() => res());
}),
```

Two issues:
1. **`try { ... } catch { /* ignore */ }`** is a CLAUDE.md no-fallback
   rule violation. The comment "ignore" is exactly the "rescue nil /
   except: pass" pattern flagged in CLAUDE.md ("NEVER `value || default`
   patterns ... no `rescue nil`, `except: pass`, `catch {}` ..."). If
   `s.terminate()` throws, the test fixture proceeds as if nothing
   happened — but a throwing `terminate()` means the socket is in an
   abnormal state that future tests will likely hit again.
2. **`wss.close(() => res())`** fires when the server stops listening,
   NOT when all client sockets have fully closed. If a slow socket is
   mid-close when `wss.close` fires, the next test's `spawnWsRelay`
   might race against the old socket's TCP-state cleanup. Localhost
   TIME_WAIT can keep ports alive for ~120s by default — though
   `port: 0` lets the OS pick a fresh port each time, so this isn't
   reachable in practice. But the semantic is wrong.

**Closure recommendation**: V2 BACKLOG ITEM. Remove the swallow:

```ts
close: () => new Promise<void>((res, rej) => {
    for (const s of sockets) {
        s.terminate(); // Let exceptions propagate.
    }
    wss.close((err) => {
        if (err) rej(err);
        else res();
    });
}),
```

The `wss.close` callback's `err` parameter (per `ws` docs) signals
"already closed" — those are non-fatal but should NOT be silently
ignored. The test's `finally` block can wrap in a top-level try/catch
if it really wants to ignore close-during-teardown failures.

**Why MEDIUM**: violates a hard CLAUDE.md rule directly in test code,
which sets the wrong example for V2.4+ test writers. Cheap fix.

### OBS-5: V2.3 tests run on the SAME mocha suite as V2.1+V2.2 — total mocha count grows from 60 → 67 (added 7 V2.3 tests). The V2.3 suite has its own `suiteSetup` that calls `loadQuantbookEngine()` again. Per the V1 loader pattern (`cachedModule` is a module-level singleton), the engine is loaded once per Node process, so the V2.3 suite's load is a cache hit. No new dlopen overhead

**Repo**: IDE.

**Specific observation**:

The `_resetQuantbookEngineCacheForTests()` call in V2.3's
`suiteSetup` looks like it forces a fresh load — but per the V1
loader at `loader.ts:35`, the `cachedModule` is reset and then
`loadQuantbookEngine()` repopulates it. So each suite starts with a
"freshly loaded" cache, but underneath `process.dlopen` would re-dl
the .dylib (which IS expensive — ~50-200ms cold).

Actually checking: `_resetQuantbookEngineCacheForTests()` likely only
resets the cachedModule pointer; the actual `.dylib` stays in memory
because process.dlopen is process-lifetime. So the "reset" is just
the JS-side cache, not the underlying native module. This is the
correct behavior — re-dl would risk thread-state corruption.

V2.3's suiteSetup pattern is consistent with V2.1+V2.2.

# V3.6.0.8 D6 Audit - Codex Lane A

Date: 2026-05-25

Scope: audited the V3.6.0.8 D6 chain:

- Engine `ebe7c946429` docs lock, `dc74d48b97e` engine foundation, `2dbce5ee2a5` napi delta surface.
- IDE `9b7ac290917` type and mocha shape-test surface.
- Current working tree also includes audit-cycle changes for R-V3.6-15 debug assert and R-V3.6-17/delta Criterion benches in `crates/ql-bindings-node/src/lib.rs` and `crates/ql-bindings-node/benches/workbook_snapshot.rs`; those were included in this audit.

## Executive Result

Verdict: FAIL.

The 3-field cache invariant is mostly sound in the direct mutation paths, the core version-vector decode/equality assumptions check out against local napi/loro sources, and the targeted D6 mocha tests pass. However, D6 cannot ship as-is:

- `poll_remote_with_limit` merges remote bytes without invalidating the workbook cache, bypassing the direct `merge_bytes` D6 invalidation.
- The delta classifier silently treats unsupported workbook metadata ops as delta-safe and then advances the cached version, which can make the IDE permanently miss sheet/order/table/workbook-metadata changes.
- The new delta benchmark fails the D6 performance rule: 1 new cell after 100k initial cells measured about 104 ms, and 100 new cells measured about 746 ms versus a full-snapshot baseline of about 248 ms in the same run.

## Cache Invariant

The V3.6.0.8.3 3-field invariant is implemented correctly for the direct setter/clearer:

- `set_workbook_cache` sets `last_snapshot_workbook`, `last_snapshot_oplog_vv`, and `last_snapshot_op_count` under `&mut self` at `crates/ql-collab/src/session.rs:1814`.
- `force_clear_workbook_cache` clears all three at `crates/ql-collab/src/session.rs:1878`.
- `force_clear_snapshot_cache` clears all three test-seam fields at `crates/ql-collab/src/session.rs:1941`.
- The napi delta tuple match at `crates/ql-bindings-node/src/lib.rs:2361` requires `(Some, Some, Some)`; any partial state falls back to full rebuild.
- There is no practical observer of the intermediate sequential writes inside `set_workbook_cache`, because the mutation requires `&mut self` and the napi layer holds the session mutex.

Direct invalidation callsites are mostly correct:

- `merge_bytes` clears at `crates/ql-collab/src/session.rs:1614`.
- `discard_pending_ops` clears after cache rebuild at `crates/ql-collab/src/session.rs:3117`.
- `undo` clears before Loro undo at `crates/ql-collab/src/session.rs:3663`.
- `redo` clears before Loro redo at `crates/ql-collab/src/session.rs:3757`.
- `append_op` intentionally does not clear.

The exception is `poll_remote_with_limit`, covered as HIGH-1 below.

## Algorithm Walk

Step 1, empty Buffer: `last_seen_version.is_empty()` at `crates/ql-bindings-node/src/lib.rs:2356` is sound for `Buffer.alloc(0)`. napi 3.9.0 `Buffer` derefs to `[u8]`; `FromNapiValue` records the Node buffer length and uses a dangling non-null pointer for len 0, so `.is_empty()` is a slice length check.

Step 2, no cache: the tuple match at `crates/ql-bindings-node/src/lib.rs:2361` handles all `None` cases by returning `fullRebuildRequired=true`.

Step 3, malformed VV: Loro 1.12.0 `VersionVector::decode` uses `postcard::from_bytes(bytes).map_err(...)`, so garbage bytes return an error rather than panicking. The napi code correctly returns full rebuild instead of throwing.

Step 4, VV equality: Loro 1.12.0 uses `VersionVector(FxHashMap<PeerID, Counter>)`, not the documented BTreeMap. Its custom `PartialEq` treats missing counters as zero, which is the correct version-vector semantic for the staleness comparison.

Step 5, same-VV: early return at `crates/ql-bindings-node/src/lib.rs:2393` is correct.

Step 6, enumeration: collecting `Vec<Result<Op, OpLogError>>` at `crates/ql-bindings-node/src/lib.rs:2425` releases the immutable `inner.log()` borrow before cache-clear paths. No op payload is lost; `OpLog::iter()` yields owned decoded `Op` values. The audit-cycle debug assert at `crates/ql-bindings-node/src/lib.rs:2446` is in the right place after enumeration and before classification.

Step 7, rename detect: nested `BatchCommit` recursion is present at `crates/ql-bindings-node/src/lib.rs:408` and handles nested/empty batches. `RenameSheet`, `RenameTable`, and `RenameColumn` are detected. `MoveSheet` is not a rename for formula-repair purposes, but it is sheet metadata and must not be silently emitted as an empty cell delta; see HIGH-2.

Step 8, apply: `(*cached_arc).clone()` at `crates/ql-bindings-node/src/lib.rs:2491` creates an owned `Workbook`; the immutable `inner.log()` borrow for `apply_ops_in_range` ends before the later `set_workbook_cache`. Prior cache Arcs are dropped normally when overwritten, except for ordinary temporary clones held by the current call.

## Cache Populate In `workbookSnapshot`

`workbookSnapshot` now locks `&mut inner`, rebuilds the workbook, captures the VV, wraps the workbook in `Arc`, renders through the same workbook data, then populates the cache.

The important ordering is correct:

- `let cache_vv = inner.oplog_vv()` is captured after rebuild and before rendering at `crates/ql-bindings-node/src/lib.rs:2018`.
- The session mutex is held until `inner.set_workbook_cache(...)`, so `self.log.len()` in the setter cannot drift between VV capture and op-count pinning.
- The `Arc` wrap does not introduce meaningful contention; the only steady cost is refcounting around a mutex-protected session.

## Multi-Peer And Polling

Direct `mergeBytes` recovery is sound: merging remote bytes clears the workbook cache, so the next delta call returns `fullRebuildRequired=true`.

Transport polling is not sound. `poll_remote_with_limit` intentionally bypasses public `merge_bytes` by calling `self.log.merge_bytes(&bytes)` directly, then rebuilds the snapshot cache, but it does not call `force_clear_workbook_cache`. This is the same class of remote-merge hazard that D6 correctly handled in direct `merge_bytes`.

## BatchCommit

`classify_delta_op` recurses into `Op::BatchCommit { ops }`, including nested batches. An empty batch is a no-op. A batch containing any rename sets `has_rename=true` and stops the outer classifier. A batch containing `PutValue + PutFormula + SetCellFormat` for one coordinate deduplicates to one `changedCells` entry via the `HashSet<(sheet,row,col)>`.

Undo/redo invalidation is correctly placed before the Loro call:

- `undo`: `force_clear_workbook_cache()` at `crates/ql-collab/src/session.rs:3663`, then `self.undo.undo()?` at `crates/ql-collab/src/session.rs:3664`.
- `redo`: `force_clear_workbook_cache()` at `crates/ql-collab/src/session.rs:3757`, then `self.undo.redo()?` at `crates/ql-collab/src/session.rs:3758`.

The unconditional clear on no-op undo/redo is acceptable. Extra clears are cheap; missed clears are correctness bugs.

It checks that the enumerated new-op count matches `current_op_count - cached_op_count`. This does not fix the missing `poll_remote_with_limit` invalidation, but it can catch future invalidation drift in debug builds.

## R-V3.6-17 And Delta Benchmark

The clone-cost profile does not justify an Arc/COW change by itself. `Workbook::clone()` at 100k cells measured about 0.68 ms, well below the 20 ms threshold.

The cell-only delta implementation still fails the D6 decision rule. The hot path calls `inner.snapshot_cells(sheet)` inside the loop for each changed coordinate at `crates/ql-bindings-node/src/lib.rs:2527`. `snapshot_cells` is documented and implemented as an O(cells-in-cache) filter plus sort at `crates/ql-collab/src/session.rs:1974`. That means even one changed cell scans and sorts the full sheet snapshot, and 100 changed cells can do that 100 times.

This explains the benchmark results:

- 1 new cell: 104 ms, not `< 5 ms`.
- 100 new cells: 746 ms, not `< 50 ms`, and slower than full snapshot.
- Full baseline in the same run: 248 ms.

## IDE Protocol

The current "probe with empty Buffer to read version" pattern is correctness-safe but clumsy:

1. If nothing mutates between `workbookSnapshot()` and the probe, the IDE captures the matching current version.
2. If an edit does happen in that window, the empty-buffer probe returns a newer version while the engine cache still pins the older version; the next delta call returns `fullRebuildRequired=true` via staleness instead of corrupting state.

This can cause an extra full rebuild but not a silent wrong delta. A `currentVersion()` accessor or a `version` field on `WorkbookSnapshotJson` should be V3.7+ cleanup.

## Rule 4

No new negative-trait trigger was found.

Positive walk:

- `last_snapshot_workbook: Option<Arc<Workbook>>`: `Workbook` derives `Clone/Debug/Default` and is Send+Sync by field composition over `Vec<Sheet>`, `NameTable`, `HashMap<..., Arc<str>>`, `DateSystem`, `FormatTable`, `SpillAnchorTable`, `TableTable`, `ReferenceMode`, and `Locale`. `Arc<T>` and `Option<T>` preserve Send+Sync when `T` does.
- `last_snapshot_oplog_vv: Option<loro::VersionVector>`: actual implementation is `FxHashMap<u64, i32>`, not BTreeMap; still positive by composition.
- `last_snapshot_op_count: Option<usize>`: trivial.
- Napi delta structs: `Vec<T>`, primitives, and `Buffer`. napi 3.9.0 marks `Buffer` `Send` and `Sync`; the JS mutability caveat is already internal to napi's unsafe impl.

Rule 4 arc terminus stays at 6.

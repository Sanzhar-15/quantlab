### B. Webview snapshot data block + scroll handler (V3.3.0.4) -- PASS

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:97-176`
(data block + scriptTag wiring) + `:277-488` (buildClientScript).

**Adversarial walks:**

1. **`</script` variant coverage in the JSON escape regex `/<\/(script)/gi`**
   (line 113). Tested mentally against:
   - `</SCRIPT`, `</ScRiPt`: matches (case-insensitive `i` flag). PASS.
   - `</script foo`, `</script\t`, `</script\n`: the regex matches `</script`
     itself (no trailing-char requirement); the `\t`/`\n`/`>`/`space` are
     LEFT OUTSIDE the match. Per HTML5 spec § 13.2.5.4 "Script data state",
     the parser only enters "script data end tag open state" on `</script`
     followed by tab/LF/FF/CR/space/`/`/`>`. By escaping `</script` to
     `<\/script`, the `<` becomes literal-`<` followed by `\/script` (the
     `\/` is JSON's escaped-`/` notation) -- inside `<script type="application/json">`,
     the browser sees this as plain script-data text (the literal `<\` sequence
     does not enter end-tag-open state because the next char isn't `/`). PASS.

2. **`<!--<script>` constructs in cell text:** The HTML5 spec's "script data
   escaped state" / "script data double escaped state" pathway is the
   theoretical concern. Per the spec, only `</script` ends the OUTER
   `<script>` tag. Cells containing `<!--<script>...` would still be
   regex-escaped at the `</script>` boundary (which IS present at the closing
   `</script>` of the data block); but a cell containing `<!--<script>...<!--`
   without closing the script tag would put the parser into a state that
   ignores subsequent `</script>`. HOWEVER: the JSON.stringify of any cell
   text means the cell content is JSON-encoded; the literal `<!--<script>`
   sequence never appears verbatim inside the data block content (it'd be
   inside a JSON string). The outer `<script type="application/json">` tag
   parses by HTML5 script-data rules, and only `</script` exits the tag.
   PASS.

3. **`<\/SCRIPT` (already-backslashed):** regex matches `</[Ss][Cc][Rr][Ii][Pp][Tt]`
   anywhere; a pre-existing `<\/script` would not match (the regex requires
   literal `</`). serde_json::to_string on a `String` containing literal
   `</script` would NOT pre-escape the slash; only `"` and `\` get escaped.
   So the regex IS the primary defense. PASS.

4. **Scroll handler's `renderRowsClient` attribute escape audit** (line
   438-453): Each attribute value is either:
   - `e.row` (Number, unescaped) -- type-guaranteed integer at engine layer,
     LOW-1 finding for defense-in-depth.
   - `e.col` (Number, unescaped) -- same, LOW-1.
   - `htmlEscape(valueStr)` -- valueStr from `formatCellValueClient(e.value)`,
     escapes `& < > " '`. PASS.
   - `htmlEscape(kind)` -- escapes same set. PASS.

5. **`htmlEscape` backtick handling:** does NOT escape `` ` ``. In HTML5,
   backticks are not special inside double-quoted attribute values. IE
   quirks-mode treated backticks as attribute delimiters; the webview runs
   on Electron Chromium (not IE), so this is LOW-4 (theoretical only).

6. **CSP `style-src 'unsafe-inline'` exposure:** cell text never reaches a
   style context. Cells render as `<td>` text or `data-*` attributes; both
   are safe contexts. No cell text is interpolated into a `<style>` block
   or `style=` attribute. PASS.

7. **Snapshot data block size at V3.3 scale:** sub-1MB typical. V3.x
   consideration documented in the data block's own JSDoc; no V3.3.0.X
   blocker.

8. **`<script id="cell-grid-data" type="application/json">` and CSP:**
   the unnonced data block runs without script execution because:
   (a) CSP `script-src 'nonce-${nonce}'` blocks unnonced JS scripts;
   (b) `type="application/json"` is non-executable by HTML5 spec.
   Belt-and-suspenders. PASS.

**B-side conclusion:** the V3.3.0.4 webview surface is XSS-safe at the
engine-typed-data layer. Defense-in-depth gap on row/col integer attribute
interpolation (LOW-1).

### H1 -- target A -- `undo` and `redo` bypass `rebuild_snapshot_cache`; cache becomes stale on undo

**File / line:** `crates/ql-collab/src/session.rs:1822-1835` (undo) +
`:1846-1853` (redo).

**Reproduction (Rust caller, the napi binding does not yet expose undo):**
```rust
let mut s = CollabSession::new(PeerId(1)).unwrap();
s.append_op(Op::PutValue { sheet: 0, row: 0, col: 0,
    value: CellWireValue::Number(42.0) }).unwrap();
assert_eq!(s.snapshot_cells(0).len(), 1);  // cache has the cell
s.undo().unwrap();  // Loro appends inverse op; iter() now reflects undo
assert_eq!(s.op_log().iter().count(), 2);  // log grew (inverse op present)
// BUG: snapshot_cells still shows the cell as if undo never fired,
// because rebuild_snapshot_cache was NOT called on the undo path.
assert_eq!(s.snapshot_cells(0).len(), 0);  // FAILS today -- cell still there
```

**Severity:** HIGH at engine level. Today the napi does not bind undo/redo
so a JS caller cannot hit this; the field docstring at line 424-429
explicitly says "V3.4 undo lands → the undo path MUST call
`rebuild_snapshot_cache()`". The hazard is correctly tracked in
R-V3.3-2 but the implementation contract is silent at the methods
themselves.

The undo/redo methods on `CollabSession` (lines 1822, 1846) currently:
- Call `self.undo.undo()` / `self.undo.redo()` -- Loro's `UndoManager`
  appends an inverse op to the document, mutating `self.log`.
- Call `self.maybe_auto_flush()` only.
- DO NOT call `self.rebuild_snapshot_cache()`.

Anyone consuming `CollabSession::undo` from Rust today (no JS caller
exists yet) gets a stale `snapshot_cells` view.

**Suggested closure:**
Two paths -- pick one:

(a) **Cache invalidation at undo/redo methods.** Add
`self.rebuild_snapshot_cache()?` after the auto-flush block:
```rust
pub fn undo(&mut self) -> Result<bool, CollabSessionError> {
    let consumed = self.undo.undo()?;
    if consumed {
        self.rebuild_snapshot_cache()?;
        self.maybe_auto_flush()?;
    }
    Ok(consumed)
}
// Same for redo.
```
This makes the undo path correct TODAY (defensive against future Rust
callers) and removes the V3.4 documentation contract as a load-bearing
correctness requirement.

(b) **Defer to V3.4 with a compile-time guard.** Add a
`#[deny(...)]`-style sentinel OR an `unimplemented!()` assertion in
both `undo` and `redo` that fires when `last_snapshot.len() > 0` --
i.e., refuse to undo/redo with a populated cache until V3.4 closes the
invalidation gap. This is uglier but unambiguous.

Recommendation: (a). The fix is one line each at both call sites; the
cost is one rebuild per undo/redo invocation (already O(N) in op count
the user would otherwise pay at the next `snapshot_cells` lookup if
the cache were lazily invalidated).

**Why HIGH, not MEDIUM:** the docstring claim at line 399 says "every
op-log mutation site" but two op-log-mutation sites (undo, redo) are
NOT enumerated and NOT updated. The negative-invariant claim
"every op-log mutation site updates the cache" is FALSE today. Per
Rule 4 § negative-trait extension to negative invariants
(audit-discipline § rule 4 applies to "any claim like 'this state
cannot be mutated after X'"), the claim needs compile-time enforcement
OR per-call verification. Neither is in place.

### H2 -- target C -- silent `listSheets()` error swallow at panel title violates CLAUDE.md No-Fallbacks rule

**File / line:** `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:163-166`.

**Reproduction:**
```typescript
let titleSuffix = '';
try {
  const totalSheets = session.listSheets().length;
  titleSuffix = totalSheets > 1 ? ` of ${totalSheets}` : '';
} catch { /* best-effort: silent fall-through to no suffix */ }
```

If `session.listSheets()` throws (e.g., op log iter error -- a corrupted
remote blob triggers a `bad_argument` napi error), the catch block silently
discards the error AND falls back to the default `titleSuffix = ''`.

User impact: a user with a corrupted op log sees a normal "Cell Grid
(Sheet N)" title with no indication the session is broken. The next
`render()` will likely also throw (exportCellSnapshot uses the same op
log surface), surfacing eventually -- but the title computation already
ate the diagnostic that would have led the user to the root cause.

**Severity:** HIGH per CLAUDE.md hard rule:
> "No try/catch that swallows errors or returns a default value."
> "No 'graceful degradation' that silently switches to an alternative path."

The comment "best-effort: silent fall-through to no suffix" is exactly
the pattern the rule prohibits.

**Suggested closure:**
Either:

(a) **Let the error propagate.** Remove the try/catch; let
`CellGridPanel.show()` throw. The caller (registerCommand) already
catches throws and surfaces via `showErrorMessage`. The user gets the
diagnostic immediately.

(b) **Log + surface.** Replace with:
```typescript
let titleSuffix = '';
const totalSheets = session.listSheets().length;
titleSuffix = totalSheets > 1 ? ` of ${totalSheets}` : '';
```
If the project DOES want the panel to open with a sane fallback (and
the user-facing error to come later via render()'s own throw path),
that's a deliberate UX decision that needs explicit justification --
not a silent catch.

Recommendation: (a). The current `show()` callers already wrap in
`try/catch` with showErrorMessage; bubbling listSheets() failure
through their handler is consistent.

**Note:** Three other catch blocks in the same file (lines 485, 558, 568)
predate V3.3.0 and are out of V3.3.0.X audit scope (they were present at
V3.2.c.3 and earlier). Flagging here for V3.x cleanup pass: all three are
also `catch { /* best-effort */ }` silent swallows on
`detachTransport()` / `kill()` -- same anti-pattern.

## MEDIUM findings

### M1 -- target A -- `rebuild_snapshot_cache` leaves partially-cleared state on iterator Err

**File / line:** `crates/ql-collab/src/session.rs:725-734`.

**Reproduction:**
```rust
fn rebuild_snapshot_cache(&mut self) -> Result<(), CollabSessionError> {
    self.last_snapshot.clear();            // <-- cleared FIRST
    for op_result in self.log.iter() {
        let op = op_result.map_err(...)?;  // <-- ? early-returns on Err
        if let Op::PutValue { sheet, row, col, value } = op {
            self.last_snapshot.insert((sheet, row, col), value);
        }
    }
    Ok(())
}
```

If `op_result` returns Err at op index `k`, the function returns Err
with the cache containing entries from ops `[0..k)` only -- a strict
subset of the correct state.

If the caller (e.g., `merge_bytes`) propagates Err upward, the next
`snapshot_cells` call returns this partial state as if it were
complete. The cache stays in this bogus state until the next successful
op-mutation rebuilds it.

**Severity:** MEDIUM. `OpLog::iter()` errors are RARE (schema mismatch or
deserialize failure -- the Loro list would have to be corrupted between
appends). In practice, V3.3.0 sessions on healthy Loro state never hit
this. But per CLAUDE.md "Errors Must Be Visible" -- the failure mode
here is INVISIBLE silent partial-state, not loud propagation.

**Suggested closure:**
Build into a fresh HashMap; swap on success:
```rust
fn rebuild_snapshot_cache(&mut self) -> Result<(), CollabSessionError> {
    let mut fresh: HashMap<(u16, u32, u32), CellWireValue> = HashMap::new();
    for op_result in self.log.iter() {
        let op = op_result.map_err(CollabSessionError::OpLog)?;
        if let Op::PutValue { sheet, row, col, value } = op {
            fresh.insert((sheet, row, col), value);
        }
    }
    self.last_snapshot = fresh;
    Ok(())
}
```
On Err, `fresh` drops; `self.last_snapshot` retains its PRE-call state
(which is consistent with the LAST successful rebuild). Slightly more
memory pressure (transient duplicate) but trades for atomicity.

Alternative (cheaper but ugly): set a `cache_invalid: bool` flag on
Err; `snapshot_cells` returns Err if the flag is set. Requires
threading the flag through `napi::export_snapshot` too.

Recommendation: the swap pattern. Self-documenting + cheap.

### M3 -- target D -- `listSheets` walks op log directly, not the `last_snapshot` cache

**File / line:** `crates/ql-bindings-node/src/lib.rs:587-603`.

The cache-backed `export_snapshot` (V3.3.0.3 closure of V3.2.d Opus M4)
already pays for incremental cache maintenance on every op-mutation
path. `list_sheets` could trivially derive sheets from the cache keys
(`self.last_snapshot.keys().map(|(s, _, _)| s).collect::<BTreeSet<_>>()`).
Current impl walks the entire op log per call (O(N) in op count).

V3.3 scale acceptable (the doc at line 580-586 says <1ms on local
dev). At V3.4+ scale (post-undo, longer-lived sessions, larger ops),
this becomes a hot path because the switch-sheet command fires on
every show() invocation.

**Suggested closure:**
Add a `CollabSession::list_sheets()` engine method that derives from
the cache; have the napi binding delegate. Pseudocode:
```rust
// session.rs
pub fn list_sheets_from_cache(&self) -> Vec<u16> {
    let mut sheets: BTreeSet<u16> = BTreeSet::new();
    for (sheet, _, _) in self.last_snapshot.keys() {
        sheets.insert(*sheet);
    }
    sheets.into_iter().collect()
}
```
Then bindings/lib.rs:`list_sheets` calls `inner.list_sheets_from_cache()`.
Saves the O(N) op-log walk. Tracked as a V3.4 entry candidate (LOW
priority by itself, but conceptually load-bearing for the cache-as-
source-of-truth narrative).

### L1 -- target B -- `data-row` / `data-col` integer attribute interpolation without escape

**File / line:** `cellGridHtml.ts:198` (server-side) + `:445-446` (client-side).

```typescript
` data-row="${e.row}" data-col="${e.col}" data-original-text="..."`
```

Server-side: `e.row` / `e.col` are TypeScript `number` from
`QuantbookCellSnapshot`. The engine guarantees these are u32 integers
(see Target B analysis). Safe at the layer.

Client-side `renderRowsClient`: `e.row` / `e.col` come from JSON.parse
of the `<script id="cell-grid-data" type="application/json">` content.
JSON.parse coerces JSON numbers to JS numbers; a malicious peer would
need to compromise the engine OR the in-memory napi data structure to
inject non-numeric row/col.

**Severity:** LOW (defense-in-depth gap, not exploitable today).

**Suggested closure:**
Wrap with `Number()` coercion at the interpolation site:
```typescript
` data-row="${Number(e.row)}" data-col="${Number(e.col)}"`
```
`Number("malicious-string")` returns NaN, which interpolates as `"NaN"`
-- a valid attribute value with no XSS surface. Matches the defensive
pattern already used in the errorReply selector at line 378.

## V3.4 ENTRY READINESS

V3.4 scope per V3.3.0.1 decision D4 + V3.2.e exit packet + V3.3 plan:
- `.qbook` persistence (save / load with envelope versioning).
- Undo / redo (engine-side already present; needs napi binding +
  cache-invalidation contract).
- Presence integration with the cell-grid.

### Required pre-V3.4 (BLOCK V3.4 entry)

1. **H1 (undo/redo cache bypass) MUST close.** Either fix the engine
   methods to call `rebuild_snapshot_cache` (Path A) OR add the
   `#[unimplemented]`-style guard (Path B). Otherwise V3.4 napi binding
   of undo/redo + the V3.4 IDE wiring will ship with a known-bug
   on the FIRST undo call. Per the field docstring at line 424-429,
   this is already documented as a V3.4 prerequisite.

2. **M5 (clear_snapshot_cache test seam) MUST land** to make undo
   invalidation tests possible. V3.4 cannot ship cache-invalidation
   regression coverage without this seam.

3. **M1 (rebuild atomicity) SHOULD close** before V3.4 to remove the
   partial-clear hazard from the foundation V3.4 builds on. Not a hard
   blocker; V3.4 can ship with M1 open if its iter-error paths are
   audited separately.

### Required pre-V3.4 (design lock items)

4. **Cache shape extension under V3.5 Op enum growth.** V3.3.0
   `last_snapshot` is `Op::PutValue`-only. V3.5+ adds RegisterFormat /
   SetCellFormat / etc. Decision needed at V3.4 entry: (a) separate
   cache map per Op variant; OR (b) unified per-cell state with
   multiple fields (`struct CellState { value: ..., format: ..., ... }`).
   Locking the choice at V3.4 entry avoids a V3.5 migration.

5. **Persistence round-trip preserves cache invariants.** V3.4
   `export_to_qbook(path)` + `from_qbook(path)` napi methods MUST
   call `rebuild_snapshot_cache` after `OpLog::import_bytes` (mirrors
   the existing `from_snapshot` pattern at session.rs:547). The
   round-trip through Tier D3 envelope should be lossless because:
   - Cache is derived state (not persisted).
   - `from_qbook` calls `from_snapshot` after parsing the envelope.
   - `from_snapshot` already rebuilds the cache.
   Document as a V3.4 entry constraint; no engine change required.

6. **Presence integration with grid widget.** V3.4 presence wires
   PresenceState into the cell-grid (cursor color, who-edits-what).
   Current panel structure: singleton render via `panel.webview.html =
   buildHtml(...)`; full-rebuild on update. The V3.3.0.4
   virtualization-via-scroll already moved toward incremental DOM
   updates. Presence would extend the same pattern:
   - Add a `PresenceState` data block (parallel to the existing
     `cell-grid-data` block).
   - Webview script reads the block, decorates `<td>` cells with
     `data-peer-${peerId}` attributes.
   - On presence updates: post a message via `webview.postMessage`
     with a delta; webview script updates the decorations
     incrementally.
   No fundamental architecture change required; the V3.3.0.4 surface
   is friendly to presence integration.

7. **R-V3.3-5 (PeerId reuse under restart)** continues to carry
   forward. V3.2.d HIGH-1 closure handled same-window collab-then-
   collab; cross-restart still uses `BigInt(process.pid)` which can
   collide on PID reuse across system restart. V3.4 entry should
   decide: UUID-derived peerId (defensive) OR carry-forward (accept
   the rare collision case). Tracked in `.plans/_active.md` as V3.x
   backlog.

### Deferred to V3.4 (no V3.3 carry burden)

- M3 (listSheets-from-cache optimization). V3.3 scale doesn't need it.
- M4 (multi-panel switch-sheet UX confusion). User-visible polish;
  V3.4 panel-picker design naturally subsumes.
- L2 (static_assertions !Sync proof). V3.x cleanup; no V3.4 dependency.
- L3 (sample-data pin test). V3.4 will likely replace sample-data
  entirely with real persistence-loaded workbooks.

### V3.4 design decisions to lock at entry

- **Op-enum cache shape** (per item 4 above).
- **Undo/redo cache-invalidation strategy** (full rebuild vs
  partial-invalidate accessor `invalidate_cells(...)`). The docstring
  hints at the partial-invalidate option but no design is fixed.
- **Persistence schema versioning gate** (per R-V3.3-4): V3.4 must
  decide whether `qbook_format_version` lives in the envelope or in
  the engine-emitted snapshot wrapper. D-1 ship established Tier D3
  envelope; V3.4 enters with the envelope as the gate.
- **Presence + virtualization race** (per R-V3.3-6 carry-forward):
  presence-driven repaints while user is mid-scroll OR mid-edit. The
  existing `activeInput !== null` guard handles edit; presence will
  need its own quiescent-state guard.

## § A Summary + Verdict

**Verdict: PASS-WITH-FINDINGS.**

V3.6.0.4 D3 lands cleanly. The CacheBuckets<'a> refactor is well-shaped (5 disjoint &mut references via split-field borrow at construction sites; no aliasing; lifetime soundness via 'a binding the borrow scope to the helper call); `cell_op_index` + `sheet_op_index` are positive Send+Sync HashMap compositions, arc terminus stays at 6. The 6-mutation-site discipline holds across `new` (empty) + `from_snapshot` (rebuild via `rebuild_snapshot_cache`) + `append_op` (apply_cache_effect incremental) + `merge_bytes` (rebuild) + `discard_pending_ops` (rebuild) + `undo`/`redo` (rebuild_op_indices_only then per-cell invalidate). poll_remote_with_limit rebuilds via `rebuild_snapshot_cache` after the drain (probed). The R-V3.6-10 design discovery (positional indices DON'T survive Loro UndoManager retract) is correctly mitigated by `rebuild_op_indices_only()` called BEFORE the per-cell invalidate loop in undo/redo. Side-by-side parity probe confirms incremental `cell_op_index` + `sheet_op_index` populated via `append_op` matches `rebuild_op_indices_only` matches `rebuild_snapshot_cache` exactly.

The findings are concentrated in four areas: (1) **invalidate_cell does NOT remove the target cell's entry from session `cell_op_index` after the rebuild** -- both the snapshot and the index leak entries that persist across calls. The next invalidate_cell call re-uses the (now-stale) index entry, but because indices are append-only and dedup-monotonic, the entry is still valid (it points at ops that DID touch this cell). However this becomes a **memory leak on tombstoned cells** (B-MED-1 below: `cell_op_index` entries for cells on a tombstoned sheet persist indefinitely until the next full rebuild). Probed. (2) **invalidate_cell's throwaway local `CacheBuckets` accepts the per-cell write path correctly, but writes both local_cell_op_index AND local_sheet_op_index that are immediately discarded** -- wasted work but harmless (D-LOW-2). (3) The OpLog::get error-mode handling in invalidate_cell **surfaces an out-of-range index as `Err(OpLogError::SchemaMismatch)` AFTER possibly clearing the target cell** -- the caller sees the cell wiped from `last_snapshot` (because `last_snapshot.remove(&target_key)` happens BEFORE the index walk) but no replacement state inserted (because the walk errored mid-fetch). This produces a torn write across the affected cell + an error to the caller (B-HIGH-1 below). (4) Several doc-drift items in ide-consumer-contract.md (V3.6.0.4 D3 still listed as "planned" at line 1553; R-V3.5-2 still listed as "DOCUMENTED" / "V3.6+ scope" at line 1540; same line 1551 sub-bullet structural anomaly).

Findings: 1 HIGH, 2 MEDIUM, 4 LOW, 3 INFO. No data-loss bug. No cross-peer convergence bug. The HIGH is a torn-write-on-error pattern that needs in-cycle closure or an explicit reasoned defer.

## § B HIGH findings

### B.1 -- HIGH-1: `invalidate_cell` partial-error torn-write on OpLog::get failure mid-walk

**Scope**: `crates/ql-collab/src/session.rs:1960-2071` (`invalidate_cell`), specifically the interaction between:
- Line 1970: `self.last_snapshot.remove(&target_key)` (unconditional pre-walk wipe).
- Lines 2021-2029: `OpLog::get(op_log_index)` error / None handling -> `return Err(...)`.

The current sequence is:

1. Line 1970: `self.last_snapshot.remove(&target_key)` -- target cell wiped from session snapshot.
2. Lines 1980-1995: merged index walk constructed from `cell_op_index` + `sheet_op_index`.
3. Lines 2012-2060: iterate merged_indices, `OpLog::get(idx)` per index. If `get` returns `Some(Err(_))` or `None` (out-of-range), the function does an early `return Err(...)`.
4. Lines 2067-2069: ONLY on the happy path, `if let Some(state) = local_snapshot.remove(&target_key) { self.last_snapshot.insert(target_key, state); }`.

If `OpLog::get(idx)` fails midway through the walk, control returns Err WITHOUT reinstating `self.last_snapshot[target_key]`. The cell is now MISSING from the session snapshot, the index `cell_op_index[(s,r,c)]` is STILL populated (untouched), and the caller sees an Err.

This is a **partial-error / torn-write** pattern that violates the atomic-swap contract used elsewhere (rebuild_snapshot_cache atomic-swaps the whole snapshot on success).

**Reproducibility**: Probed via `opus_probe_invalidate_cell_out_of_range_does_not_panic` (inline, removed post-audit). Manually injected `cell_op_index[(0u16, 99u32, 99u32)] = vec![99usize]` into a session with only 1 op. Then called `s.invalidate_cell(0, 99, 99)`. Returned `Err(OpLogError::SchemaMismatch("cell_op_index / sheet_op_index pointed past end of log"))`. Cell (0,99,99) was not in the session snapshot pre-call (no prior put_value), but the **same pattern applies to cells that ARE in the snapshot**:

```rust
#[test]
fn opus_probe_invalidate_cell_partial_error_torn_write() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(put_value(0, 5, 5, 42.0)).unwrap();
    // Snapshot has (0,5,5) = 42.0.  cell_op_index[(0,5,5)] = [0].
    assert_eq!(s.snapshot_cells(0).len(), 1);

    // Inject corrupted index entry pointing past end of log.
    s.cell_op_index.entry((0, 5, 5)).or_default().push(999);

    // Invalidate.
    let result = s.invalidate_cell(0, 5, 5);
    assert!(result.is_err(), "out-of-range produces Err");
    // BUT: (0,5,5) is now MISSING from the snapshot.
    let snap = s.snapshot_cells(0);
    let found = snap.iter().find(|((r, c), _)| *r == 5 && *c == 5);
    assert!(found.is_none(), "TORN WRITE: cell wiped + no replacement");
}
```

Under the docstring's own claim ("Out-of-range indices surface as `OpLogError::SchemaMismatch` ... invariant violation; unreachable post-undo-fix"), the torn write should never happen in production -- the index discipline at 6 mutation sites guarantees `cell_op_index` indices ALWAYS point within log range. But:

- The docstring claim is invariant-dependent. If the invariant is ever broken (future regression in any of the 6 sites; a future caller of `force_clear_snapshot_cache` followed by a series of appends without rebuild; a corruption-style fault), the torn-write surfaces.
- The existing pre-D3 path (full log walk via `self.log.iter()`) did NOT have this concern -- a `log.iter()` decode failure mid-walk would still leave the snapshot in a known empty state (the cell was wiped at line 1970, and the per-cell rebuild fails to populate -- but the CALLER knew the cell was wiped from the Err signal).
- Post-D3, the caller sees an Err AND a wiped-but-not-rebuilt cell. The cell APPEARS to have been retracted in the snapshot view.

**Severity**: HIGH because the contract documented in invalidate_cell's docstring ("Returns `Err(OpLog(_))` if the indexed op-log lookup fails to deserialize. Same propagation as `rebuild_snapshot_cache`") implies error propagation parity with `rebuild_snapshot_cache` -- but `rebuild_snapshot_cache` is atomic-swap (fresh local map drops on error; session state unchanged) while `invalidate_cell` is NOT atomic-swap (session `last_snapshot` is mutated pre-walk).

**Suggested closure** (in-cycle):

Option (a): Adopt the atomic-swap pattern. Capture the pre-walk state of `self.last_snapshot.get(&target_key)` before the `remove` call; on Err, reinstate. Diff sketch:

```rust
// invalidate_cell BEFORE line 1970 -- capture pre-call state.
let pre_state = self.last_snapshot.get(&target_key).cloned();
self.last_snapshot.remove(&target_key);
// ... walk ...
// On Err path (lines 2023-2029), reinstate:
let result_or_err = self.log.get(op_log_index);
let op = match result_or_err {
    Some(Ok(op)) => op,
    Some(Err(e)) => {
        if let Some(state) = pre_state {
            self.last_snapshot.insert(target_key, state);
        }
        return Err(CollabSessionError::OpLog(e));
    }
    None => {
        if let Some(state) = pre_state {
            self.last_snapshot.insert(target_key, state);
        }
        return Err(CollabSessionError::OpLog(OpLogError::SchemaMismatch(
            "cell_op_index / sheet_op_index pointed past end of log",
        )));
    }
};
```

Option (b): Defer the `self.last_snapshot.remove(&target_key)` until AFTER the walk completes successfully. The walk builds `local_snapshot[target_key]`; on success, mutate `self.last_snapshot`. Cleaner; matches the build-into-fresh pattern of `rebuild_snapshot_cache`.

```rust
// invalidate_cell -- BUILD INTO FRESH then atomic-swap.
// Remove line 1970 entirely.
// ... walk (unchanged) into local_snapshot ...
// At the end (lines 2067-2069 replacement):
match local_snapshot.remove(&target_key) {
    Some(state) => self.last_snapshot.insert(target_key, state),
    None => self.last_snapshot.remove(&target_key),
};
// Errors from the walk leave self.last_snapshot UNCHANGED.
```

I recommend (b) -- it's structurally cleaner (mirrors `rebuild_snapshot_cache`'s pattern), produces no additional clones in the happy path, and surfaces the Err with the session state intact.

Plus a regression test pinning the contract:

```rust
#[test]
fn v3_6_0_4_d3_invalidate_cell_atomic_under_oplog_get_error() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(put_value(0, 5, 5, 42.0)).unwrap();
    let pre = s.snapshot_cells(0);  // (0,5,5) = 42
    s.cell_op_index.entry((0,5,5)).or_default().push(999);  // corrupt
    let result = s.invalidate_cell(0, 5, 5);
    assert!(result.is_err());
    // Atomic-swap: post-Err, the snapshot must equal pre-call.
    let post = s.snapshot_cells(0);
    assert_eq!(post, pre, "invalidate_cell is atomic under OpLog::get error");
}
```

## § C MEDIUM findings

### C.1 -- MED-1: `cell_op_index` entries for cells on tombstoned sheets persist (memory leak; not corrected by RemoveSheet handler)

**Scope**: `crates/ql-collab/src/session.rs:1424-1427` (RemoveSheet handler in `apply_cache_effect`).

The current `CacheEffect::RemoveSheet { id }` arm:

```rust
CacheEffect::RemoveSheet { id } => {
    buckets.tombstones.insert(id);
    buckets.snapshot.retain(|(sheet, _, _), _| *sheet != id);
}
```

Cleans up `snapshot` (removes all cells for the tombstoned sheet) but does NOT touch `cell_op_index`. `cell_op_index` entries for cells `(id, r, c)` remain in place, pointing at op-log indices of the now-tombstoned cells.

**Reproducible probe** (Opus Lane B, removed post-audit):

```rust
#[test]
fn opus_probe_remove_sheet_leaves_stale_cell_op_index_entries() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(Op::AddSheet { name: "S1".into(), chunk_rows: 100 }).unwrap();
    s.append_op(put_value(1, 0, 0, 1.0)).unwrap();
    assert!(s.cell_op_index.contains_key(&(1u16, 0u32, 0u32)));
    s.append_op(Op::RemoveSheet { id: 1 }).unwrap();
    assert!(s.cell_op_index.contains_key(&(1u16, 0u32, 0u32)),
        "leaked entry persists post-RemoveSheet");
}
```

Production impact:
- **Memory**: bounded by op log size (each entry is `(u16,u32,u32) + Vec<usize>`; small). For a 100k-op session that creates+deletes many ad-hoc sheets, the leak compounds.
- **Behavior**: `invalidate_cell` on a tombstoned-sheet cell walks the stale `cell_op_index[(s,r,c)]` entries + `sheet_op_index[s]` (the RemoveSheet ops). The walk correctly processes RemoveSheet first (if it comes first in causal order) OR processes the cell-keyed effects then tombstone-then-clear (correct end state). **Functional correctness is preserved** -- probed via `opus_probe_remove_sheet_leaves_stale_cell_op_index_entries` (invalidate_cell on (1,0,0) post-RemoveSheet returns empty snapshot).
- **Iter accessor consumers**: `cell_op_index_iter` returns ALL entries, including the stale ones. Today no production code consumes this accessor (engine-internal only), but V3.7+ incremental snapshot deltas may. The accessor's docstring doesn't warn about tombstoned-sheet leakage.

**Severity MED** because: (a) memory leak is bounded; (b) functional correctness is preserved (verified by probe); (c) the leak rebuilds-out at next `rebuild_snapshot_cache` (merge_bytes, discard_pending_ops, etc.). But it violates the "6-mutation-site sync invariant" the field docstring claims at lines 883-887.

**Suggested closure** (in-cycle):

Adopt the same `retain` discipline in `cell_op_index` that's already applied to `snapshot`:

```rust
CacheEffect::RemoveSheet { id } => {
    buckets.tombstones.insert(id);
    buckets.snapshot.retain(|(sheet, _, _), _| *sheet != id);
    // V3.6.0.4 D3 audit closure: drop cell_op_index entries
    // for cells on the now-tombstoned sheet so the index doesn't
    // diverge from snapshot (also bounds memory).
    buckets.cell_op_index.retain(|(sheet, _, _), _| *sheet != id);
}
```

Plus a regression test:

```rust
#[test]
fn v3_6_0_4_d3_remove_sheet_cleans_cell_op_index_entries() {
    let mut s = CollabSession::new(PeerId::new(7)).unwrap();
    s.append_op(Op::AddSheet { name: "S1".into(), chunk_rows: 100 }).unwrap();
    s.append_op(put_value(1, 0, 0, 1.0)).unwrap();
    s.append_op(Op::RemoveSheet { id: 1 }).unwrap();
    assert!(!s.cell_op_index.contains_key(&(1u16, 0u32, 0u32)),
        "RemoveSheet cleans cell_op_index entries for cells on tombstoned sheet");
}
```

## § D LOW findings

### D.1 -- LOW-1: `op_log_index` capture via `self.log.len().saturating_sub(1)` post-append; trusts visible-counter semantics

**Scope**: `crates/ql-collab/src/session.rs:1178-1186` (`append_op`).

```rust
self.log.append(op)?;
let op_log_index = self.log.len().saturating_sub(1);
```

The captured `op_log_index` reflects the visible-counter (post-append). For a local append at the local peer's frontier, `op_log_index = log.len() - 1` is correct (Loro's normal-flow append puts the op at the tail of the visible list).

But the `saturating_sub(1)` is defensive -- if `log.len()` returned 0 after a successful `log.append(op)`, the saturating subtraction returns 0 instead of underflowing. This is an impossible state under documented Loro semantics (append cannot reduce list length), but the code chose to guard it anyway.

**Concern**: if `log.len() == 0` after `log.append(op)?` returned Ok, then capturing `op_log_index = 0` would be silently wrong (the just-appended op DOESN'T exist in the visible list per Loro). The downstream `apply_cache_effect` would push 0 into `cell_op_index` entries, but the visible log might have a DIFFERENT op at index 0 (e.g., a pre-existing op from `from_snapshot`).

This is a defense-in-depth concern only -- under documented Loro 1.12.0 semantics it's unreachable. But the silent failure mode (vs panicking on underflow) makes regressions invisible.

**Severity LOW** because: (a) unreachable under current Loro version; (b) the defensive saturating_sub doesn't hide a real bug today.

**Suggested closure** (in-cycle, comment-only):

Add a docstring note on the `saturating_sub` line:

```rust
// V3.6.0.4 D3 audit closure: saturating_sub guards against a
// theoretical post-append len() == 0 (which Loro 1.12.0 cannot
// produce -- append always grows visible list).  If this guard
// ever fires, indices are silently wrong.  Prefer assertion in
// debug builds; saturating_sub in release.
let op_log_index = {
    let len = self.log.len();
    debug_assert!(len > 0, "log.len() == 0 after successful append (Loro invariant violation)");
    len.saturating_sub(1)
};
```

Or accept the current code as-is and just add a comment explaining why saturating_sub is defensive.

### D.2 -- LOW-2: `invalidate_cell` throwaway local CacheBuckets accumulates wasted index entries

**Scope**: `crates/ql-collab/src/session.rs:2007-2010, 2032-2037, 2057`.

```rust
let mut local_format_cache: HashMap<FormatId, Arc<str>> = HashMap::new();
let mut local_cell_op_index: HashMap<(u16, u32, u32), Vec<usize>> = HashMap::new();
let mut local_sheet_op_index: HashMap<u16, Vec<usize>> = HashMap::new();
// ...
let mut local_buckets = CacheBuckets {
    snapshot: &mut local_snapshot,
    tombstones: &mut local_tombstones,
    format_cache: &mut local_format_cache,
    cell_op_index: &mut local_cell_op_index,
    sheet_op_index: &mut local_sheet_op_index,
};
// ...
Self::apply_cache_effect(&mut local_buckets, effect, op_log_index);
```

`apply_cache_effect` writes per-effect index entries to `local_cell_op_index` + `local_sheet_op_index`. These maps are immediately discarded at the end of invalidate_cell. Per-effect cost: 2 HashMap inserts (or contains-checks if already there) + a Vec push.

**Severity LOW** because:
- The merged walk in invalidate_cell is typically 1-4 ops (typical case the optimization was designed for).
- 1-4 HashMap inserts of throwaway entries is microseconds.
- The wasted work doesn't affect correctness.

But the pattern produces avoidable allocation pressure (Vec<usize> heap-allocated for each cell that lands a local effect). For LARGER merged walks (rare; would only happen if a cell has many ops AND its sheet has many RemoveSheets, both unusual), the cost compounds.

**Suggested closure** (DEFER unless profiling justifies):

Option (a): introduce a separate helper `apply_cache_effect_no_indices` that takes only `snapshot/tombstones/format_cache` (3 buckets) for per-cell walks. Avoids the index allocations entirely.

Option (b): make CacheBuckets's index fields `Option<&mut ...>` and have apply_cache_effect skip the index push if None. Backward-compat at the type level; saves the allocation.

Option (c): keep as-is (current state). Profiling at V3.6.0.7 D6 spike should measure whether the cost is observable.

I lean (c) for now; flag for V3.6.0.7 profiling spike.

### D.3 -- LOW-3: `rebuild_op_indices_only` duplicates the index-extraction logic from `apply_cache_effect`

**Scope**: `crates/ql-collab/src/session.rs:1884-1922` (`rebuild_op_indices_only`).

The helper iterates ops + extracts cell + sheet keys with the same `cell_key_for_index` / RemoveSheet branch logic as `apply_cache_effect` (lines 1346-1364). Two implementations of the same classifier diverge if one is updated without the other.

**Severity LOW** because: (a) both implementations are inline + short; (b) the type system catches obvious divergence (CacheEffect enum variants enumerated); (c) the regression test `v3_6_0_4_d3_rebuild_snapshot_cache_repopulates_both_indices` covers the parity at the integration level. But the duplication is a maintenance hazard at V3.7+ if new CacheEffect variants are added.

**Suggested closure** (DEFER; V3.7+ refactor):

Extract a helper `fn extract_index_keys(effect: &CacheEffect) -> (Option<(u16,u32,u32)>, Option<u16>)` that both `apply_cache_effect` and `rebuild_op_indices_only` call. Diff sketch:

```rust
fn extract_index_keys(effect: &CacheEffect) -> (Option<(u16, u32, u32)>, Option<u16>) {
    let cell_key = match effect {
        CacheEffect::PutValue { key, .. } => Some(*key),
        CacheEffect::PutFormula { key, .. } => Some(*key),
        CacheEffect::ClearFormula { key } => Some(*key),
        CacheEffect::SetCellFormat { key, .. } => Some(*key),
        CacheEffect::RemoveSheet { .. } => None,
        CacheEffect::RegisterFormat { .. } => None,

    let sheet_id = if let CacheEffect::RemoveSheet { id } = effect { Some(*id) } else { None };
    (cell_key, sheet_id)
}
```

Defer to V3.7+ unless V3.6.0.X audit-of-D3 closure cycle wants to fold this in.

### D.4 -- LOW-4: `apply_cache_effect` ordering question: index push BEFORE snapshot mutation

**Scope**: `crates/ql-collab/src/session.rs:1354-1365` (index push) vs lines 1366-1448 (snapshot mutation).

The index push happens BEFORE the snapshot mutation. This means:
- A `PutValue { sheet: 0, row: 0, col: 0 }` on a NON-tombstoned sheet: tombstone-check passes, index pushed, then snapshot updated. ✓
- A `PutValue { sheet: 0, row: 0, col: 0 }` on a TOMBSTONED sheet: tombstone-check fires early-return (line 1333), index NOT pushed, snapshot NOT updated. ✓

But subtle: the ORDER between index-push and snapshot-mutation matters when reading `cell_op_index` mid-call. There's no such mid-call read in current code, so this is purely theoretical. Future refactors should preserve "index push before snapshot mutation" to keep the invariant "index entry exists iff effect was applied".

Or, more importantly: should the invariant be reversed -- "snapshot mutation BEFORE index push"? If snapshot mutation fails for any reason (it can't currently, since the variants are all HashMap upserts), the index would have an entry for a non-existent state. Today this can't happen.

**Severity LOW** because:
- No failure path between index push and snapshot mutation in current code.
- The invariant choice doesn't affect correctness; it's a documentation question.

**Suggested closure** (in-cycle, docstring polish):

Add a docstring sentence in `apply_cache_effect`:

```rust
// V3.6.0.4 D3 INVARIANT: index push BEFORE snapshot mutation.
// Since neither operation can fail, the order is semantically
// irrelevant -- but future refactors that introduce failure paths
// MUST decide whether index entries should reflect ATTEMPTED or
// SUCCEEDED effects.  Today: ATTEMPTED (tombstone-passing effects
// land in the index regardless of snapshot mutation outcome).
```

## § E INFO findings

### E.1 -- INFO-1: `OpLog::get` re-reads the LoroList container handle per call

**Scope**: `crates/ql-oplog/src/log.rs:180-213` (`get`).

```rust
pub fn get(&self, index: usize) -> Option<Result<Op, OpLogError>> {
    let list: LoroList = self.doc.get_list(OPS_CONTAINER);
    // ...
}
```

`self.doc.get_list(OPS_CONTAINER)` is called per `get` call. For invalidate_cell walking 1-4 indices, that's 1-4 container-handle lookups + 1-4 `len()` calls. Each lookup is cheap (Loro internal Arc clone), but for a microbench scenario walking 1000 indices in tight loop, the per-call overhead may compound.

**Severity INFO** because: (a) typical invalidate_cell walk is 1-4 ops; (b) the per-call cost is Arc-clone-level (nanoseconds); (c) `OpLog::iter` has the same pattern but amortizes via the outer iterator captures.

**Suggested closure** (DEFER; V3.6.0.7 profiling spike):

If profiling at D6 spike shows the per-`get` overhead is visible, expose a `get_many(indices: &[usize]) -> Vec<Result<Op, OpLogError>>` that lifts the container lookup outside the loop.

### E.2 -- INFO-2: OpLog::get error mode "ops LoroList lost an entry between len() and get()" -- now reachable via OpLog::get vs. only iter() pre-D3

**Scope**: `crates/ql-oplog/src/log.rs:185-191` vs `iter` at lines 116-118.

The `LoroList::get(index)` returning None when `index < len()` was previously only an `iter()` concern (legacy Phase 2A code). V3.6.0.4 D3 surfaces this via the new `get` API. The error message is identical (good docstring parity).

Concurrent mutation of the visible list between `len()` and `get()` is impossible in single-threaded use, but `&self` access to a `LoroDoc` is theoretically safe across multiple readers (Loro's `Doc` is `Send + Sync` with interior mutability). If two threads concurrently read+mutate, the lost-entry race is theoretical.

In production, all CollabSession callers go through `&mut self` methods, so this is unreachable.

**Severity INFO** because the error path is unreachable under documented use.

### E.3 -- INFO-3: V3.6.0.4 D3 forward-compat -- if Loro adds a "stable op-ID" API, migration breaks the wire format only if delta consumers store op-IDs

**Scope**: R-V3.6-10 documentation in `.plans/_active.md` lines 311-318.

The risk register documents a V3.7+ migration path: extend OpLog with stable op-ID lookup + migrate cell_op_index to op-IDs. This avoids the per-undo `rebuild_op_indices_only` O(N) cost.

The migration concern: Loro op-IDs (PeerID + counter) are CRDT-native. Storing them in the wire format would require a schema bump (Phase 2A.8 envelope versioning). Pure in-memory migration (op-IDs only in CollabSession state; wire format unchanged) doesn't require a bump.

The risk register correctly flags the design discovery but doesn't specify the wire-format implications. Future V3.7+ design decisions should evaluate (a) in-memory-only op-ID storage (no schema bump) vs (b) wire-level op-ID encoding (requires schema bump for incremental delta consumers).

**Severity INFO** because the R-V3.6-10 doc currently identifies the right closure direction without specifying scope.

**Suggested closure** (V3.7+ design lock):

When the V3.7+ stable-op-ID migration is locked, add a "wire format impact" sub-bullet to R-V3.6-10:

> If op-IDs land in the wire format (Phase 2A.8 envelope), bump schema version. If op-IDs stay in-memory only, no bump needed.

## § G Forward-looking design recommendations

### G.1 -- V3.6.0.X audit-of-D3 closure should land MED-1 cell_op_index retain + HIGH-1 atomic invalidate_cell + MED-2 doc drift

The 3 in-cycle closures (B.1 HIGH-1 atomic invalidate_cell, C.1 MED-1 RemoveSheet retain, C.2 MED-2 ide-consumer-contract sweep) total ~30 LOC code + ~80 LOC test + ~30 LOC doc. The HIGH-1 in particular tightens the documented "atomic propagation" contract; without it the invalidate_cell contract is fragile.

### G.2 -- V3.6.0.5 D4 (format-aware buildHtml) doesn't depend on V3.6.0.4 D3 -- can proceed in any order

V3.6.0.5 D4 reads `WorkbookSnapshotJson.formats` (V3.6.0.3 D2 surface) + `cell_value` rendered fields. No `cell_op_index` consumer. The V3.6.0.4 D3 invalidate_cell perf win benefits V3.6+ undo/redo workflows on large logs; D4 doesn't touch this path. Sequencing flexibility preserved.

### G.3 -- V3.6.0.7 D6 profiling spike should measure invalidate_cell vs full rebuild on 1k+, 10k+ op sessions

The R-V3.6-10 discovery (rebuild_op_indices_only O(N) per undo) means single-cell undo doesn't win post-D3 vs pre-D3 (both O(N) -- pre-D3 walks log, post-D3 walks log via rebuild_op_indices_only). The win is K * O(k) per multi-cell undo (BatchCommit retract). Profiling should pin the K * O(k) win vs the O(N) rebuild_op_indices_only cost at various log sizes:

| Log size | Pre-D3 cost | Post-D3 cost (K=1) | Post-D3 cost (K=10) |
|----------|-------------|-------------------|---------------------|
| 100 ops  | O(100)      | O(100)            | O(100) + 10*k       |
| 1000 ops | O(1000)     | O(1000)           | O(1000) + 10*k      |
| 10k ops  | O(10000)    | O(10000)          | O(10000) + 10*k     |

For single-cell undo (K=1), there's NO win -- both paths are O(N). For BatchCommit retract (K=10), post-D3 wins iff k < N/10. The V3.6.0.7 spike should validate the win is observable for realistic K.

### G.4 -- V3.7+ stable op-ID migration design lock

R-V3.6-10's documented V3.7+ closure (stable op-IDs) needs design lock:
- In-memory-only (CollabSession state holds op-IDs; OpLog API returns op-IDs from append/iter; wire format unchanged) -- preferred for backward compat.
- Wire-level (op-IDs in envelope; consumers store op-IDs in deltas) -- requires Phase 2A.8 schema bump.

Recommend in-memory-only at V3.7 + revisit wire-level at V3.8 if delta consumers materialize.

### G.5 -- V3.7+ CacheBuckets evolution path

D.1 LOW-1 from V3.6.0.X audit-of-D2 (CacheBuckets refactor) is closed at V3.6.0.4 D3. The current shape (5 disjoint &mut refs) supports up to ~10 buckets before becoming unwieldy. V3.7+ may want a trait-based shape:

```rust
trait CacheBucket {
    fn apply(&mut self, effect: &CacheEffect, op_log_index: usize);
    fn rebuild_from_walk(&mut self, ops: impl Iterator<Item = (usize, &Op)>);
}
```

Defer until the 6th bucket lands (currently V3.7+ delta consumer storage).

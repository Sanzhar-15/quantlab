## Audit angles

### 1. Round-trip fidelity correctness

The crux: import → export → re-import preserves what we say it
preserves. Spot-check the path with adversarial fixtures:
- Cells with int / float / text / bool / error / blank values.
- Formula text round-trip (no leading `=` per Quantbook storage).
- Date system 1904 (does set_date_system survive export? — note:
  export currently emits a fresh umya workbook, so date_system
  defaults to 1900).
- Sheets with names containing special chars.
- Sheet count preservation.
- Multiple sheets with cross-references.

### 2. Calamine ↔ Quantbook coordinate translation

Calamine uses 0-indexed (row, col) range-LOCAL coordinates (relative
to range.start). umya uses 1-indexed (col, row). Quantbook uses
0-indexed (row, col). All three conversions happen at boundaries.

Look for:
- Off-by-one in the calamine→Quantbook translation
  (`read::calamine_grid::iter_sheet` — verify the
  `start_row + local_row` math).
- Off-by-one in the Quantbook→umya translation
  (`write::umya_export::export_new_workbook` — verify
  `umya_col = col + 1; umya_row = row + 1`).
- Bounds-check off-by-one (`row > MAX_ROW` vs `>= MAX_ROW`).

### 3. Error mapping

The `Data → Value` mapping (calamine_grid.rs:`data_to_value`)
handles all 9 Data variants. Sanity-check:
- `GettingData → ErrorValue::NA` — defensible but engine has 16+
  ErrorValue variants; is this the right collapse?
- DateTime / DateTimeIso / DurationIso — DateTime returns the
  serial (`dt.as_f64()`) but DateTimeIso/DurationIso fall back to
  text. Should the ISO forms be parsed too? (W5-D-14b note says
  later; verify the deferral is documented and tracked.)

### 4. umya-spreadsheet edge cases

Look at the umya exporter (`write::umya_export.rs`) for:
- What happens when a sheet name has a character umya rejects?
  (We use `new_sheet(name)` which returns `Result`; verify the
  error path is propagated cleanly.)
- Cells beyond umya's bounds — does umya panic or error?
- Formula text with special characters (`"`, `<`, `&`) — does umya
  escape correctly when serializing OOXML?
- Boolean → set_value_bool → does umya serialize as the
  OOXML `t="b"` form correctly?
- Error values → we call `set_value_string(e.sigil())` — does
  umya treat that as text or error on re-read?

Probe via compiled tests if useful.

### 5. OOXML scanner correctness

The OOXML scanner (`read::package`, `read::workbook_xml`,
`read::feature_inventory`, `read::rels`, `read::tables_xml`,
`read::styles_xml`) parses 6 distinct OOXML parts. Each has
edge cases:
- `workbook.xml`: namespace-prefixed `r:id` attribute — does the
  attribute lookup work when the namespace prefix is something
  other than `r`? (Per OOXML spec, namespace prefix is arbitrary.)
- `styles.xml`: the `xf` element-stack filter for distinguishing
  `cellXfs` from `cellStyleXfs` — does it handle nested elements
  correctly?
- `rels`: the `..`-path resolution — what about `../../`-style
  paths? Mid-path `.`?
- `tables_xml`: ref parsing — does it handle the `XFD1048576`
  upper bound (Excel's max)?

### 6. Feature inventory completeness

`feature_inventory::scan_unsupported_features` has path patterns
for 7 kinds + in-sheet trigger element scanning for 5 kinds.
- Is the path-pattern list exhaustive? (Cross-reference against
  IronCalc's import to see what they parse — Quantbook should at
  minimum DETECT every OOXML feature IronCalc handles.)
- Are there false positives? (E.g., does `xl/comments_*` regex
  accidentally match `xl/commentsHistory.xml` or similar?)
- Strict-mode error reporting: does the error message identify the
  FIRST detected kind in a deterministic way?

### 7. Integration with engine internals

The import pipeline calls:
- `Workbook::add_sheet(name)` — wrapped in `catch_unwind` per the
  trust-boundary convention. Verify the panic-→-error translation
  is right.
- `Workbook::put_at` / `put_formula` — bounds-checked at the
  storage layer; we duplicate bounds checks in the import path
  with warnings. Is the double-check correct, or is one redundant?
- `WorkbookRuntime::recompute_all` — what happens if recompute
  panics? The `BestEffort` mode promises to report failures, but
  a panic would still propagate.
- `TableTable::insert` — table name collision (two tables with
  the same canonical name) — what's the behavior? Are tests
  exercising this?

### 8. Defense-in-depth + no-fallback rule compliance

Per CLAUDE.md: errors must be visible. Look for:
- `unwrap_or_default()` on attribute parses — does this silently
  swallow malformed OOXML? (Acceptable when a default IS the
  spec-defined value, e.g. `headerRowCount` defaults to 1; flag
  if used where the spec says the attribute is required.)
- `parse::<u32>().unwrap_or(0)` patterns — same question.
- Empty matches on Event types — Event::CData / Event::Comment
  etc.; verify the match-all `_ => {}` doesn't drop a load-bearing
  event.

### 9. Test quality

50 tests is a lot but most are unit. Per the Rule-3 lex+bind+eval
audit-discipline criterion:
- Are the integration tests load-bearing? Would a typical refactor
  break them?
- Is the round-trip smoke test STRICT enough? It currently asserts
  sheet count preservation, not full semantic equivalence. Should
  it assert at least cell-value equality post-roundtrip?
- Coverage of edge cases (empty sheet / single-cell formula /
  cell with both value and formula / 1904 date system / table with
  totals row / etc.).

### 10. Documentation accuracy

- Public-API rustdoc accuracy.
- W5-D-14a..e per-commit messages — do they accurately describe
  what shipped?
- The Phase 4.11 plan (`.plans/_active.md`) — is it up to date
  with what was shipped?
- Acceptance criterion XLSX-4-03 — the plan claims tables and
  formats survive round-trip "where supported". Have we ACTUALLY
  tested that tables survive export-then-reimport? (The
  round-trip smoke only tests sheet count. We may have a docs
  overclaim.)

### 11. Anything else adversarial

The user explicitly asked for deep, no-lazy audits in this engine's
audit-discipline rule. Find what's wrong, not what's right.

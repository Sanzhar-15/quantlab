## Microsoft canonical algorithm

`SUBTOTAL(function_num, ref1, [ref2], ...)`:
- `function_num` ∈ {1..=11, 101..=111} else `#VALUE!`.
- 1-11: 1=AVERAGE, 2=COUNT, 3=COUNTA, 4=MAX, 5=MIN, 6=PRODUCT,
  7=STDEV.S, 8=STDEV.P, 9=SUM, 10=VAR.S, 11=VAR.P.
- 101-111: same indices but "ignore hidden rows" (Excel's filter/
  outline integration).
- Skips nested SUBTOTAL calls in arg ranges (the "subtotal of
  subtotals" guard against double-counting).
- Text values in ranges: skipped (per Microsoft canon — but our
  engine inherits the W5-58 strict text-rejection from the
  underlying aggregate).

IronCalc reference: `.references/ironcalc/base/src/functions/
subtotal.rs` — has full row-visibility metadata + AST access so
implements both hidden-row + nested-skip behaviors fully.

## v1 divergences (documented in module block + matrix + coverage)

1. **101-111 normalize to 1-11**: the engine has no hidden-row
   metadata, so the two Excel modes are observationally identical
   in v1. Our impl applies `fn_num - 100` to normalize.
2. **No nested-SUBTOTAL skip**: the engine evaluates args before
   the fn is called, so by the time `subtotal()` receives `FnArg`s,
   the value of a nested SUBTOTAL has already been computed; we
   cannot distinguish it from any other numeric value. This only
   matters with multi-level outline/group views, which are not in
   v1.
3. **Text-in-range coercion**: SUBTOTAL inherits the W5-58 strict
   convention from the underlying aggregates (SUM/AVG/etc.) it
   dispatches to. Microsoft canon for SUBTOTAL specifically would
   skip text; this divergence is already engine-wide for sibling
   fns (LARGE/SMALL/MEDIAN/MODE/PERCENTILE/QUARTILE).

## What to look for

### Correctness

1. **function_num dispatch table parity with IronCalc**:
   1→AVERAGE, 2→COUNT, 3→COUNTA, 4→MAX, 5→MIN, 6→PRODUCT,
   7→STDEV.S, 8→STDEV.P, 9→SUM, 10→VAR.S, 11→VAR.P. Verify each
   numbered route points to the right scalar_fns::* fn.

2. **101-111 normalization correctness**: my impl uses
   `fn_num - 100` for 101..=111. Verify: 101→1 (avg), 109→9 (sum),
   111→11 (var.p). All 11 should be reachable.

3. **NaN function_num panic-safety**: my impl adds an explicit
   `is_nan()` guard (same pattern as W5-D-11.1 closure). Verify
   `subtotal(&[s(n(NaN)), arr])` returns `#NUM!`.

4. **Boundary checks**: function_num ∈ {0, 12, 100, 112, -1, +Inf,
   -Inf} should all return `#VALUE!`. My impl uses `match fn_num
   { 1..=11 => ..., 101..=111 => ..., _ => Err(Value) }`. +Inf
   saturates to `i64::MAX`, -Inf to `i64::MIN` — both fall to the
   `_` arm. Verify.

5. **Fractional function_num truncation**: 9.7 → 9 (SUM), 9.99 →
   9 (SUM), 0.5 → 0 (invalid). My impl uses `n.trunc() as i64` —
   same as quartile_q extraction.

6. **Flattening of multi-arg / scalar+range mix**: my impl iterates
   `args[1..]` and pushes Scalar values + extends from Range
   values. Verify no double-counting or skipped values.

### Dispatched-kernel inheritance

7. **STDEV.S/STDEV.P/VAR.S/VAR.P** use the engine's Welford-based
   `scalar_fns::*` impls (NumAcc-3 certified per A6 spec). IronCalc
   uses naive two-pass. Our results should be more precise; not
   a divergence so much as a quality difference.

8. **PRODUCT empty input** returns 0 (per Excel canon; matches
   `scalar_fns::product` behavior). IronCalc returns 1.0 (technically
   wrong per Excel). Cross-check.

9. **MIN/MAX empty input** returns 0 (per Excel canon; matches
   `scalar_fns::min/max`). Verify.

10. **Error in data range propagates** — both Codex and IronCalc
    treat error in data as propagating. Verify via dispatched fn.

## MEDIUM

### M1. `poll_remote_with_limit` skips `maybe_auto_flush` — undocumented asymmetry

`session.rs:715-740`: `poll_remote_with_limit` merges remote bytes via `self.log.merge_bytes(&bytes)?` directly (the low-level `OpLog` method), NOT `self.merge_bytes(bytes)` (the `CollabSession` wrapper that fires auto-flush). The wrapper at `session.rs:389-392` calls `maybe_auto_flush()`; the poll path bypasses it.

Concretely: peer A with `OnAppend` calls `poll_remote()` → merges N blobs from peer B → A's log grew by potentially many ops → A does NOT auto-flush the merged union back to peer C (a third peer attached via A's transport).

Contrast with the `merge_bytes` caller path which DOES auto-flush specifically "so 3rd-party peers see the merged union" (per the docstring at `session.rs:380-388`). Both code paths land in `OpLog::merge_bytes` and both grow the log identically — the auto-flush asymmetry is purely an artifact of which wrapper the merge passes through.

This may be intentional (prevents auto-flush ping-pong; see M2) but it is **not documented** and **not tested**. If intentional, the docstring on `merge_bytes` over-promises ("3rd-party peer fanout via this session's transport endpoint") because the most natural fanout — drain inbox via `poll_remote`, re-fanout via OnAppend — silently doesn't fire.

Resolution either way is one line:
- (a) **Wire it in.** Change `self.log.merge_bytes(&bytes)?` to `self.merge_bytes(&bytes)?` inside the loop. Then add a test for 3-peer fanout via `poll_remote`. **MUST be paired with M2 idempotency guard or echo loop results.**
- (b) **Document the asymmetry** with a fixed reason: "poll_remote does not auto-flush by design — when a remote feeds you their snapshot, your peer-fanout side is responsible for batching its own flushes via `flush_to_transport` after drain."

Either is fine; the current state is "silently neither."

### M2. Echo loop probe (E1) — two OnAppend peers ping-pong forever (LATENT)

When both peers in a `LoopbackTransport::pair()` enable `OnAppend`, ANY append by either side could trigger an infinite ping-pong at the wire level. Trace:

1. A.append_op(op) → A.maybe_auto_flush → A sends snapshot S1 to B's inbox.
2. B.poll_remote → drains S1 → calls `self.log.merge_bytes(S1)` directly. This **bypasses** B's auto-flush (per M1). **Loop terminates here on the read side.**

So the M1 asymmetry actually PREVENTS the worst case today. If M1 is "fixed" by wiring `poll_remote` to auto-flush, this becomes an immediate infinite loop:

1. A.append_op(op) → A flushes S1 to B's inbox.
2. B.poll_remote drains S1, merges, **auto-flushes** S1' (now containing the same op) back to A's inbox.
3. A.poll_remote drains S1', merges (Loro deduplicates), auto-flushes S1'' back to B.
4. ... forever, with each side processing identical-state snapshots.

Loro's CRDT merge IS idempotent in op-level semantics (the merged op set doesn't grow), but `OpLog::merge_bytes` returns `self.len()` (the unchanging post-merge length) AND `maybe_auto_flush` fires unconditionally — it has no "did anything actually change?" check. So fixing M1 without fixing M2 detonates.

**Recommendation:** when fixing M1, add a "did-the-log-grow" guard to `maybe_auto_flush`. Sketch:

```rust
fn maybe_auto_flush(&mut self) -> Result<(), CollabSessionError> {
    match self.auto_flush_policy {
        AutoFlushPolicy::Disabled => Ok(()),
        AutoFlushPolicy::OnAppend => {
            if self.transport.is_none() { return Ok(()); }
            let cur_len = self.log.len();
            if self.last_flushed_len == cur_len { return Ok(()); }
            let _ = self.flush_to_transport()?;
            self.last_flushed_len = cur_len;
            Ok(())
        }
    }
}
```

Until then, **OnAppend must NOT be enabled on both endpoints of a paired transport** — and this constraint is not documented. The IDE in Phase 5.7 will be the first real consumer; if the user enables OnAppend on a peer and another peer (server) does the same, the wire blows up.

**Recommended action right now (V2 V2):** add a one-line caveat to the `OnAppend` docstring: *"Symmetric OnAppend across two paired peers is unsafe in V2 V2 — the second peer's poll_remote currently does not auto-flush (see M1), but if that asymmetry is resolved without a version-vector guard, an echo loop results. V2 V3 closes both."* This costs nothing and prevents a future contributor from "fixing" M1 in isolation.

### M3. Bandwidth — every mutator sends a full snapshot

`flush_to_transport` calls `export_bytes()` which is `ExportMode::Snapshot` (`log.rs:325-327`). Every keystroke under OnAppend serializes + sends the FULL Loro state. For a 10k-cell workbook with 50k ops in history, this is many megabytes per keystroke.

This is acknowledged at `session.rs:660-663` ("V2 V1 sends the FULL snapshot each call (O(state)). V2 V3 will track per-transport version vectors and send deltas only.") and at the V2 V3 backlog row in `v1-exit-packet.md:250-253`.

Worth flagging because **OnAppend amplifies the bandwidth cost** by a factor of "ticks-per-second × keystrokes-per-tick" relative to V2 V1's explicit-drive (which most IDEs would tick at 100-500ms). V2 V1 + tick-batching naturally coalesces many appends into one snapshot send; OnAppend cannot coalesce. For Phase 5.7 IDE vertical slice using OnAppend over LoopbackTransport in-process, this is fine. Over a WebSocket it would be a usability cliff.

**Action:** keep V2 V2 shipped. Make sure V2 V3 lands **before** any production-scale OnAppend dogfooding. Consider adding a "Threshold(usize)" or "TimeWindow(Duration)" coalescing variant before declaring OnAppend production-ready.

## LOW

### L1. Undo-group + OnAppend semantics undertested (Probe E2)

Walk through:
```
session.start_undo_group()?;             // no flush
session.append_op(op1)?;                  // auto-flush → S1 (op1 visible)
session.append_op(op2)?;                  // auto-flush → S2 (op1+op2 visible)
session.end_undo_group();                 // no flush (infallible)
```

Peers see op1 and op2 land independently mid-group. If the user then undoes the group, **one** undo() returns true and auto-flushes the inverse-bundle snapshot.

But: the group is supposed to be a single LOCAL undo unit. On the wire it's two units. A naive observer that does NOT do its own undo grouping (e.g. a "live spreadsheet view" peer that just re-renders on every snapshot) will paint op1, then op1+op2, then bundle-inverse — fine for final state, but mid-group flicker is visible.

**For V2 V2:** add a test that exercises the mid-group behavior and **assert the current semantics deliberately**, e.g. "2 wire sends during a group, group atomicity is local-only." That pins the contract — if anyone tries to change it later, the test fails loudly.

### L2. Reattach-after-failure semantics (Probe E5) — confirmed correct, undertested

The `on_append_close_mid_session_recovers_via_detach_and_reattach` test attaches `NoopTransport::new()` as the recovered transport — and `NoopTransport::sent` is captured through `Box<dyn Transport>` which can't be downcast, so the test never asserts that op #2 actually appears in the recovered wire stream. The test only asserts `s.op_count() == 3`.

Fix: use `LoopbackTransport::pair()` for the recovery side too and drain the observer to confirm op #2 + op #3 BOTH appear in the new transport's stream after recovery.

### L3. 3-peer fanout caveat undocumented (Probe E6)

The OnAppend policy is per-`CollabSession`. In a 3-peer scenario where A↔B(T1) and B↔C(T2), enabling OnAppend on A propagates A's writes to B via T1 but does NOT propagate them onward to C unless B also has OnAppend (or B explicitly flushes after each `poll_remote`).

Compounds with M1: if B opts in but uses `poll_remote` to drain from A, the auto-flush still won't fire on the merge.

### L4. `flush_to_transport` discards `_sent` boolean from auto-flush — minor dead-code smell

`session.rs:632-642`: the `_sent: bool` return value is always `true` in the OnAppend branch because of the early-return on `transport.is_none()`. Either trust `flush_to_transport`'s no-transport branch and remove the early-return (loses doc-of-intent), or trust the early-return and assert `_sent`. Trivial.

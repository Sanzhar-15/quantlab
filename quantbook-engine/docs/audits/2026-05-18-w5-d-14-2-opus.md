# Separate-Opus audit: W5-D-14.2 (4 HIGH closures)

Auditor: Claude Opus 4.7 (1M ctx) — independent pass, no comms with Codex.
Scope: commit `6ba2ce6ff89` on `feat/quantbook-engine`.
Method: read all 7 modified files end-to-end + build/run 5 external Rust probes via the Mac bridge against the actual artifacts (`/tmp/probe-xlsx/`, see Verification appendix). All findings were checked against the **emitted bytes** of real `xl/*.xml` parts, not inferred from the code shape.

## HIGH findings

### H-1: UpdateOriginal silently overwrites the original theme/docProps with umya defaults
- File: `crates/ql-io-xlsx/src/write/update_original.rs:108-113` (overlay loop) + `194-228` (`classify_part::preserve_prefixes` includes `xl/theme/`, `docProps/`).
- What's wrong: Step 3b skips any original part whose name is already in `shadow_part_names`. Shadow ALWAYS emits `xl/theme/theme1.xml`, `docProps/app.xml`, `docProps/core.xml` (umya hard-emits them). So the membership check at line 111 trips FIRST and the original's theme/docProps are dropped, even though `classify_part` would have returned `PartAction::Preserve` for them. The comment on `docProps/` (line 224-227: "Most authors care about author / company metadata surviving; preserve") flatly contradicts what the code does.
- Why it matters: I ran the existing test fixture (basic_text.xlsx) through `UpdateOriginal` and compared bytes. Original `xl/theme/theme1.xml` = 8390 bytes (Calibri Light + 30+ script-specific Office fonts). Output theme = 6518 bytes (umya default — different font roster, different effectStyleLst, no font script fallbacks). Original `docProps/core.xml` has `<dc:creator>Nicolas Hatcher</dc:creator>` + real `dcterms:modified` date `2023-01-22T01:26:39Z`. Output has empty `<dcterms:created>2006-09-16T00:00:00Z</dcterms:created>` (umya stub). The user-visible "Round-trip preserves Office theme" claim is FALSE; the test `w5_d_14_2_update_original_round_trip_preserves_opaque_theme` passes only because it asserts merely that `xl/theme/*` exists — not that the content matches.
- Suggested fix: invert the precedence for parts in the explicit preserve_prefixes list. The intent (per the comment) is that preserve_allowlisted prefixes wins over shadow, so before writing shadow's version in step 3a, check `classify_part`; if it's `Preserve` and the original has a copy, write the ORIGINAL bytes instead. Easiest: walk shadow first (skipping any name where original also exists AND `classify_part(name) == Preserve`), then walk original normally.

### H-2: Original's sheet/workbook rels are dropped, leaving preserved drawings/comments/connections/printerSettings orphaned
- File: `crates/ql-io-xlsx/src/write/update_original.rs:194-254` (`classify_part`).
- What's wrong: `xl/worksheets/_rels/sheetN.xml.rels` and `xl/_rels/workbook.xml.rels` are NOT in `preserve_prefixes` and don't match any special-case. classify_part falls through to `PartAction::DropSilently`. Shadow's versions ALWAYS win (they're in `shadow_part_names`). Result: when the original has `<drawing r:id="rId4"/>` in its sheet rels (linking `xl/drawings/drawing1.xml`), we preserve `xl/drawings/drawing1.xml` (preserve_prefixes match) but drop the rels entry pointing to it. The drawing part becomes orphaned — Excel will silently strip on next save; LibreOffice may complain about a stale package.
- Why it matters: this defeats most of the "opaque parts round-trip" claim. Every preserved-via-prefix path that's only reachable via a Relationship reference (drawings, charts, comments, printerSettings, externalLinks, connections, pivotCache, pivotTables, queryTables, threadedComments, embeddings) is orphaned in UpdateOriginal mode. The basic_text.xlsx test fixture has none of these, so the test passes; the moment a user opens a real workbook with charts, the charts vanish even though their XML survives.
- Suggested fix: build a "preserved-rel merge" pass. For each `*.rels` file in original that shadow ALSO emits, parse both, take the union (or shadow + original-rels-pointing-to-preserved-parts), and write the merged rels. Or simpler v1: any rels file where `classify_part` returns `Preserve` for at least one of its `Target` references → carry the original rels through (and tolerate the dangling entries; Excel ignores rIds it doesn't recognize).

### H-3: `xl/connections.xml`, `xl/cellMetadata.xml`, `xl/customProperty.xml` are NOT actually preserved (preserve list uses wrong trailing-slash prefix form)
- File: `crates/ql-io-xlsx/src/write/update_original.rs:202-228`.
- What's wrong: `preserve_prefixes` includes `"xl/connections/"`, `"xl/customProperty/"`, `"xl/cellMetadata/"` (trailing slash, directory-form). But the real OOXML paths are single XML files: `xl/connections.xml`, `xl/customProperty.xml`, `xl/cellMetadata.xml`. `"xl/connections.xml".starts_with("xl/connections/")` is **false**. So these three part types match no preserve prefix, fall through to `DropSilently`, and are LOST without a `dropped_features` entry.
- Why it matters: workbooks using Power Query, External Data Connections, or cell-metadata features (e.g. SpilledChartData) lose those features silently in UpdateOriginal. Users get no error, no report entry, and the original-side feature_inventory may have flagged them on import but the export-side silent-drop is invisible.
- Suggested fix: change the three entries to exact-path matches (or use both): `if name == "xl/connections.xml" || name == "xl/cellMetadata.xml" || name == "xl/customProperty.xml" { return Preserve; }`. Audit the rest of the preserve list for the same trailing-slash-vs-file-name confusion (looks like `xl/printerSettings/` is correct as a prefix because parts are `xl/printerSettings/printerSettings1.bin`; same for `xl/persons/` → `xl/persons/person.xml`; `xl/richData/` → `xl/richData/*.xml`).

### H-4: `sibling_tmp_path` AtomicU64 is local to the call → concurrent same-output exports corrupt each other's data
- File: `crates/ql-io-xlsx/src/write/update_original.rs:447-459`.
- What's wrong: `let counter = std::sync::atomic::AtomicU64::new(0);` is allocated INSIDE the function. Every invocation starts with counter=0. So `fetch_add(1)` always returns 0. The shadow path is fully determined by `(stem, pid)`. Two threads in the same process calling `export_xlsx_path` to the SAME `output_path` get the SAME shadow path. They race on `std::fs::write(&shadow_path, ...)` and `std::fs::read(&shadow_path)`. The brief flagged this as needing confirmation — **CONFIRMED via probe**.
- Why it matters: I ran 8 threads exporting to the same `/tmp/probe-corruption.xlsx` (Barrier-synced for max collision). Across 5 runs, **5-6 of 8 threads received WRONG output** every time. Each thread wrote a unique numeric sentinel to a unique column; on re-import, the sentinel was replaced with text/Blank values from a different thread's preservation source (basic_text.xlsx's shared-string content). This is silent data corruption: no error returned, output file looks valid, but cells contain another thread's content. The ScopedFileGuard then races on cleanup — `remove_file` of a nonexistent file is silently ignored.
- Suggested fix: use a process-static counter (`static SHADOW_COUNTER: AtomicU64 = AtomicU64::new(0);` at module scope) and/or add `std::process::id()` plus a thread id plus a random nanosecond suffix. Even better: use `tempfile::Builder::new().tempfile_in(parent)` which handles this correctly (it's already a transitive dep via `umya-spreadsheet`).

### H-5: `xl/_rels/workbook.xml.rels` merge — pivotCache / connections / externalLinks / customXml references from the original are dropped
- File: `crates/ql-io-xlsx/src/write/update_original.rs:194-254` (`classify_part`).
- What's wrong: Same root cause as H-2 at workbook level. The shadow's `xl/_rels/workbook.xml.rels` only contains rels for the parts shadow emits (sheets, styles, theme, sharedStrings). The original's may contain additional rels for `pivotCache`, `connections`, `externalLinks`, `customXml`, `vbaProject`, etc. Original's workbook.rels file is named the same as shadow's → DropSilently. Original's rels are LOST.
- Why it matters: even with H-1 fixed (preserved-prefix parts survive), the workbook-level Relationship entries that BIND them to the document are gone. The merged Content_Types may still have Overrides for the preserved parts, but Excel won't load them because there's no `r:id` linkage from `xl/workbook.xml/<extLst>` or similar. Net effect: pivot tables, external links, and custom XML mappings are silently broken even when the XML parts survive.
- Suggested fix: same merge strategy as H-2 — for any `*.rels` file, take the union of shadow's entries + original's entries that target preserved parts. Or carry original's entire rels through and let it dangle on shadow-emitted parts (Excel tolerates this since shadow's rels Relationships are also schema-valid).

## MEDIUM findings

### M-1: `inject_*` "Case 1" replacement branch checks `/>` BEFORE `</tag>` — broken for non-empty existing elements
- File: `crates/ql-io-xlsx/src/write/umya_export.rs:508-527` (`inject_custom_formats_into_styles_xml`), `725-743` (`inject_defined_names_into_workbook_xml`), `934-952` (`inject_table_parts_into_sheet_xml`).
- What's wrong: All three "Case 1" branches do `if let Some(self_close_rel) = text[after..].find("/>") { ... return ... }` BEFORE `find("</tag>")`. `text[after..]` is the entire remainder of the document. `find("/>")` finds the FIRST `/>` after the opening — which, for non-self-closed elements with self-closing children, will be the CHILD's self-close, not the outer element's. Example: existing `<numFmts count="1"><numFmt numFmtId="164" formatCode="0.00"/></numFmts>` → `text[after..]` starts at ` count="1"><numFmt numFmtId="164" formatCode="0.00"/></numFmts>...`; `find("/>")` finds the inner `<numFmt .../>`'s `/>`. The code then truncates at that point, replacing only the prefix and leaving `</numFmts>...` as orphan tail. Result: malformed XML.
- Why it matters: in v1 NewWorkbook mode, umya never emits any of these three elements pre-injection, so Case 1 never fires — empirically safe. But it's a latent corruption bomb: any future refactor that has umya emit `<numFmts>`/`<definedNames>`/`<tableParts>` (e.g., adopting a newer umya version that handles custom formats natively, or extending to UpdateOriginal with sheet-xml surgery) will silently produce invalid xlsx files.
- Suggested fix: in all three functions, swap the order — try `</tag>` close-form FIRST, then fall back to self-close. Or use a proper XML library (we're already pulling in `quick-xml`). Adding a regression test that injects into pre-populated content would have caught this.

### M-2: Cell-fix needle patterns omit the `s="..."` style attribute that umya emits when a cell has a non-zero style
- File: `crates/ql-io-xlsx/src/write/umya_export.rs:389-419` (`apply_cell_fixes_to_sheet_xml`).
- What's wrong: needles are `<c r="C5" t="str"` and `<c r="C5" t="e"><v>#VALUE!</v>`. umya's cell writer (`umya-spreadsheet/src/structs/cell.rs:464-479`) emits attributes in order `r`, `t`, `s` — and emits `s="N"` for any cell where `stylesheet.set_style(...)` returns a non-zero xfId. For a styled error cell, umya writes `<c r="C5" t="e" s="2"><v>#VALUE!</v></c>`. The patch needle doesn't match; the cell silently keeps the umya hardcoded `#VALUE!` regardless of the actual error variant.
- Why it matters: in v1, Quantbook's `apply_value_to_cell` doesn't apply per-cell styles (all error cells get default style 0), so empirically the patch matches. But the moment per-cell style application lands (W5-D-14 followups + Phase 4.12), styled error cells will silently corrupt to `#VALUE!` on export. Same defect applies to the `t="str"` removal.
- Suggested fix: make the needle more permissive — match `<c r="C5" t="str"` regardless of trailing attrs, e.g. `<c r="C5" t="str"[^>]*>` via regex, or scan attribute-by-attribute. Add a unit test that exports a styled error cell.

### M-3: Sheet-rels file is dropped silently when original has it but shadow has tables (overwriting original's drawing/comment rels)
- File: `crates/ql-io-xlsx/src/write/update_original.rs:194-254` + `crates/ql-io-xlsx/src/write/umya_export.rs:357-371`.
- What's wrong: closely related to H-2 but specific to the table-export interaction. `render_fresh_sheet_rels` emits `xl/worksheets/_rels/sheetN.xml.rels` with ONLY the table rels (rIdT1, rIdT2). If the original had drawings/comments rels for that sheet, they're lost. `shadow_part_names` now contains the rels path → original's version is skipped in UpdateOriginal mode.
- Why it matters: a user importing a workbook with drawings + cells, then adding a Quantbook table to that sheet, and exporting via UpdateOriginal, loses the drawings link entirely.
- Suggested fix: in `render_fresh_sheet_rels`, when called from UpdateOriginal context, merge with the original's sheet rels (preserving non-table rels and only adding the table rIds).

### M-4: `'O''Brien'!$A$1` (single-quote escape in quoted sheet name) is parsed incorrectly on import
- File: `crates/ql-io-xlsx/src/read/names_import.rs:122-133` (`split_sheet_ref`).
- What's wrong: the function comment explicitly acknowledges "support unescaped names only — `''`-escaped single quotes in sheet names is a follow-up edge case (real-world incidence is near zero)". For `'O''Brien'!$A$1`, the code does `after_open.find('\'')` which finds the FIRST `'` (the escape's opening quote), splits at `O` (incorrect), then tries `after = "'Brien'!$A$1"` strip_prefix `!` → fails (the next char is `'`, not `!`). Returns `None`, falls back to `NamedTarget::Formula(raw)`.
- Why it matters: Excel allows `'` in sheet names (escaped as `''`). The fallback path captures the raw text as `Formula(...)`, which the binder MAY resolve later (Phase 3+). But until the binder lands, names targeting `O'Brien!$A$1` are effectively orphaned (no Cell/Range resolution). The export side handles the escape correctly (`quote_sheet_name` does `name.replace('\'', "''")`); only the import side is asymmetric.
- Suggested fix: extend `split_sheet_ref` to handle `''` escape — scan for an UNESCAPED single quote (i.e., `'` not followed by another `'`). Add a unit test mirroring `parse_quoted_sheet_target`.

### M-5: Names that fail to register on import (reserved-name, unknown sheet for sheet-scoped, set_name error) are silently dropped even in Strict policy
- File: `crates/ql-io-xlsx/src/read/names_import.rs:42-66`.
- What's wrong: the function silently discards on `.is_ok()` boolean checks (lines 54, 60) and on the sheet-not-found branch (line 59). Returns only the count of successfully-registered names. The caller (`lib.rs:184`) discards even that count (`let _names_registered = ...`). `UnsupportedPolicy::Strict` (in `lib.rs:189-208`) only fires for `feature_inventory.is_clean()` and doesn't include named-import failures. Strict mode is supposed to be the safety valve for round-trip correctness; this gap means a Strict import can return success while silently losing defined names.
- Why it matters: a Strict-mode user importing a workbook with a name like `Print_Area` (reserved on Quantbook side?) or a sheet-scoped name pointing to a sheet that calamine rejected (e.g. by `add_sheet`'s validation), gets no error and no warning. The exported version differs from the imported version and the user doesn't know.
- Suggested fix: collect failed-to-register names into a typed report field (e.g. `XlsxImportReport.dropped_names: Vec<DroppedName>`). In Strict mode, error if non-empty. In Permissive, surface as warnings.

### M-6: Original's xl/calcChain.xml Override entry could be partially merged into shadow's Content_Types (no defect today; latent)
- File: `crates/ql-io-xlsx/src/write/update_original.rs:301-312` (`merge_content_types`).
- What's wrong: classify_part returns `DropSilently` for `xl/calcChain.xml`, so `preserved_part_paths` doesn't include it. The merge logic at line 303 (`if !preserved_set.contains(normalised.as_str()) { continue; }`) skips it correctly. **No defect today.** Flagging because the design conflates "preserved" with "Content_Types-merged" — future divergence (e.g. someone adds a part that needs DropSilently but its Override should still be carried) requires both lists.
- Why it matters: this is the kind of invisible coupling that breaks the next change.
- Suggested fix: split `preserved_part_paths` from `content_types_merge_paths` — same set today, distinct concepts.

### M-7: `xml_attr_escape` over-escapes `'` (which is valid in `"..."`-delimited attribute values) — but never wrong, just verbose
- File: `crates/ql-io-xlsx/src/write/umya_export.rs:761-767`.
- What's wrong: replaces `'` with `&apos;` even though OOXML attribute values are always wrapped in `"..."` and `'` is legal raw. This makes the output noisier and slightly larger.
- Why it matters: cosmetic; round-trip semantics unchanged (XML parsers all handle `&apos;`). But OOXML produced by Microsoft Excel never uses `&apos;` in attribute values; consumers that compare bytes (rare but exists for diff-based tests) will see needless diff.
- Suggested fix: drop the `'` replacement. Same for the `>` replacement, which is technically also unnecessary inside `"..."` attrs but Excel itself does it so it's defensible.

### M-8: ContentTypes Override parser would mis-attribute `<x:Override>` (namespace-prefixed) elements
- File: `crates/ql-io-xlsx/src/write/update_original.rs:388-418` (`iterate_simple_self_closing`).
- What's wrong: `find("<Override")` matches `<x:Override` too (matches `Override` substring of `x:Override`). The `next` byte check on line 399-406 looks at the byte AFTER `Override`, which for `<x:Override ` is ` ` (space) — passes the check. The `raw` field is then `Override Foo="..."/>` (no `<x:` prefix). When emitted to the merged Content_Types via `to_append.push_str(&over.raw)`, the output has a stray `Override .../>` fragment without proper element opening. Malformed XML on the way out.
- Why it matters: Content_Types.xml is essentially never namespace-prefixed in real-world OOXML (the Types element has the default namespace), so this is a latent bug. If anyone ever feeds an unusual original through UpdateOriginal, the merge could corrupt Content_Types.
- Suggested fix: in the cursor advance, require the byte BEFORE `<Override` to be `<` (i.e., search for `<Override` and verify position-1 is the matching `<`). Or just use quick-xml — we have it as a dep.

### M-9: `iterate_simple_self_closing` finds the wrong `/>` when an attribute value contains `/>` literally
- File: `crates/ql-io-xlsx/src/write/update_original.rs:407-410`.
- What's wrong: `text[start..].find("/>")` finds the first `/>` after the element start. If any attribute value contains `/>` (e.g., `<Override ContentType="vnd.foo/>;v=1" PartName="..."/>`), the close-detection truncates inside the attribute value. Element bounds are wrong; attribute extraction may then fail; the raw fragment is truncated.
- Why it matters: ContentType values are typed MIME identifiers, e.g. `application/vnd.openxmlformats-officedocument...+xml` — these don't contain `/>` in practice. But the parser makes no guarantee, and a hostile or unusual original could trigger malformed Content_Types output.
- Suggested fix: same as M-8 — quick-xml.

### M-10: `format_number_literal` truncates `-0.0` → `"0"` and may produce non-Excel-parseable `inf`/`-inf`/`NaN`
- File: `crates/ql-io-xlsx/src/write/umya_export.rs:658-664`.
- What's wrong: `n == n.trunc() && n.abs() < 1e15` matches for `-0.0` (since `(-0.0).abs() == 0.0`); `n as i64` = `0`. Sign of zero lost on round-trip. For `f64::INFINITY`, `n.is_finite()` is false, falls to `format!("{n}")` → `"inf"`. Excel doesn't accept `inf` as a defined-name target — re-import would treat as Formula and the binder would fail.
- Why it matters: edge cases (NaN/inf constants in defined names) are exotic; -0.0 loss is academic. LOW severity if you only care about realistic workbook content.
- Suggested fix: short of nothing — document the limitation; or filter NaN/Inf out of the export path entirely (skip the name with a warning).

### M-11: `quote_sheet_name` doesn't quote names starting with `R1C1`-pattern that look like cell references
- File: `crates/ql-io-xlsx/src/write/umya_export.rs:669-684`.
- What's wrong: Excel requires sheet names like `A1`, `R1C1`, `XFD1048576` (anything that looks like a cell reference) to be quoted in formula context. The current logic only quotes when first-char-is-digit OR contains non-`[A-Za-z0-9_]`. So `A1` (a legal sheet name in Excel) would NOT be quoted; the export emits `A1!$B$2` which Excel parses as cell `A1` of the current sheet's column `B$2`-nothing-makes-sense. The parser ambiguity is real and Excel's resolution rules differ.
- Why it matters: rare (most users don't name sheets `A1`), but real round-trip bug. Quantbook validates sheet names on `add_sheet`; need to check whether `A1` is rejected there. If it isn't, the export path is wrong.
- Suggested fix: extend the `needs_quote` check to reject names that match the cell-ref regex `^[A-Z]+\d+$`.

## What looked right

- The `xmlns:r` namespace IS declared on umya's emitted `<worksheet>` (probed `xl/worksheets/sheet1.xml`): `xmlns:r="http://schemas.openxmlformats.org/officeDocument/2006/relationships"`. So `<tablePart r:id="rIdT1"/>` resolves the prefix correctly. (Brief raised this; confirmed safe.)
- The `<numFmts>` block is correctly placed as the FIRST child of `<styleSheet>` (before `<fonts>`). Probed `xl/styles.xml`: `<styleSheet ...><numFmts count="1"><numFmt numFmtId="164" formatCode="#,##0.00 &quot;USD&quot;"/></numFmts><fonts ...>`. OOXML schema position is honored.
- `rIdT{i}` does not collide with umya-emitted `rId{i}` in sheet rels — umya doesn't emit any sheet rels file at all for plain sheets (probe confirmed empty rels file path in non-table sheets; `render_fresh_sheet_rels` fires only when needed). For sheets with tables, the rels file is freshly emitted by us with only `rIdT*` entries. No id collision in current emission path.
- VBA / ActiveX rejection ordering in `classify_part` IS correct: the `if name == "xl/vbaProject.bin" || name.starts_with("xl/activeX/")` early-return at line 196-198 fires BEFORE the preserve_prefixes loop at line 229.

#### M5 finding -- iteration-order invariant under-documented

**File / line:** `crates/ql-collab/src/session.rs:921-955`.

The `rebuild_snapshot_cache` walk relies on `self.log.iter()` returning ops in
Loro's causal-merge order. This order is canonical across peers per Phase 5.1
audit Codex V1. However, the LWW correctness of the cache depends on this
order being maintained: if the iterator ever returned ops out of causal order,
`ClearFormula` at iteration index `k` could occur before its causal predecessor
`PutFormula` at iteration index `k+1`, and the cache's `formula` field would
incorrectly remain set.

The docstring at `:889-906` says "iteration order = Loro's causal-merge order
which converges across peers" but does not explicitly pin this as a SOURCE-of-
TRUTH invariant for the cache's LWW semantic. A future Loro dep bump or
iterator-optimization could silently break this.

**Severity:** MEDIUM (doc-drift risk; correctness preserved at HEAD).

**Suggested closure:**

Strengthen the docstring at `:889-906`:

```rust
/// **LWW correctness invariant**: this method relies on
/// `self.log.iter()` returning cell-keyed ops in Loro's causal-merge
/// order. ClearFormula at iteration index k MUST be preceded in the
/// iteration by its causal-predecessor PutFormula (else the cache's
/// formula field would incorrectly persist after the user's clear).
/// Loro 1.12.0 guarantees this via the underlying LoroList's causal
/// iteration; a future Loro bump must re-verify.
```

Also consider adding a regression test: append PutFormula -> ClearFormula ->
merge_bytes from a peer whose ops would, if re-ordered, surface the cleared
formula. Empirically pin the iteration-order invariant.

### C. UUID PeerId derivation correctness (V3.4.0.4b) -- PASS-WITH-FINDINGS

**File:** `extensions/quantlab/src/quantbook/session.ts:193-209`
(generateUuidPeerId) + `crates/ql-bindings-node/src/lib.rs:230-254`
(peer_id_from_bigint engine validator).

#### Adversarial walks

1. **64-bit truncation of 122-bit UUIDv4**:

   ```typescript
   const uuid = crypto.randomUUID();
   const hex16 = uuid.replace(/-/g, '').slice(0, 16);
   const value = BigInt('0x' + hex16);
   ```

   UUIDv4 format: `xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx` (32 hex chars after
   dashes are removed; 122 bits of randomness; the `4` at position 12 and the
   `y` at position 16 are version + variant markers).

   The first 16 hex chars of UUIDv4 = bytes 0-7 (the first 64 bits). This
   covers the first 60 bits of randomness PLUS the version-marker `4` at
   position 12 (= bit 48 from MSB). So the truncated value's bit 48-51 is
   always `0100` (the literal hex digit `4`). Birthday-paradox collision at
   ~2^32 sessions is unchanged because the deterministic `4` at the same
   bit-position cancels in the collision calculation (both colliding values
   have it).

   Concretely: 2^60 effective entropy after extracting the `4` marker -- still
   above the IDE's threat model (a user spawning 2^30 = 1 billion sessions in
   one workbook is not the threat model). **PASS.**

2. **8-attempt cap on all-zero retry**:

   ```typescript
   for (let attempt = 0; attempt < 8; attempt += 1) {
       ...
       if (value !== 0n) return value;
   }
   throw new Error('[bad_argument] generateUuidPeerId: 8 consecutive zero-truncated UUIDs ...');
   ```

   The truncated value is all-zero iff the first 16 hex chars of the UUID are
   all `0`. UUIDv4 has the deterministic `4` at position 12, so the first 16
   hex chars CANNOT be all-zero (the `4` makes char-12 `4`, not `0`). The
   all-zero check is therefore DEAD CODE under a spec-compliant UUIDv4
   generator.

   Wait -- let me re-verify. `crypto.randomUUID` per Node 14.17+ docs returns
   UUIDv4. UUIDv4 byte 6 is `0x40 | (random & 0x0F)` (the `4` is the upper
   nibble, version 4). Byte 6 in hex maps to chars 12-13 of the 32-char
   dashless form. Char 12 = upper nibble = `4` always. Therefore the first
   16 hex chars CANNOT be all-zero.

   **The all-zero retry loop is defensive dead code** for spec-compliant
   UUIDv4. It would only fire if `crypto.randomUUID` returned a non-spec UUID
   (i.e., entropy source is broken). The retry IS the correct No-Fallbacks
   surface: 8 consecutive non-spec UUIDs throws.

   **PASS** -- the cap rationale is correct; the M3 verdict-summary entry
   over-stated this as a concern. Re-classifying as informational. The
   `~2^-512` in the docstring is `(2^-64)^8 = 2^-512` if all 8 truncations
   independently produced all-zero (which they can't under spec). The
   docstring is technically correct but the analysis is hypothetical (the
   precondition is impossible under spec).

3. **No-Fallbacks compliance: throws with `[bad_argument]` prefix**:

   Verified at `:208`. The error message is `[bad_argument] generateUuidPeerId:
   8 consecutive zero-truncated UUIDs from crypto.randomUUID -- entropy source
   broken`. The `[bad_argument]` prefix matches the V2.7 `KNOWN_QUANTBOOK_ERROR_
   CODE_RECORD` at `:586`. `parseQuantbookError` will route this to
   `code: 'bad_argument'`. **PASS.**

4. **Engine `peer_id_from_bigint` validation**:

   Verified at `crates/ql-bindings-node/src/lib.rs:230-254`. Pre-rejects:
   - Negative BigInt (sign_bit) -> `[bad_argument] peerId BigInt must be
     non-negative`.
   - Lossy conversion (> u64) -> `[bad_argument] peerId BigInt does not fit
     in u64`.
   - peer_id == 0 -> `[bad_argument] peerId must be non-zero (PeerId(0) is
     LEGACY_PEER ...)`.
   - peer_id == u64::MAX -> `[bad_argument] peerId must not be u64::MAX
     (Loro reserves PeerID::MAX ...)`.

   The IDE-generated UUID can never produce these:
   - `BigInt('0x' + hex16)` is always non-negative (no sign bit on the parsed
     string).
   - First 16 hex chars of a UUIDv4 always fit in u64 (it IS u64).
   - The non-zero guarantee is enforced by the retry loop.
   - The u64::MAX value requires `0xffffffffffffffff` for the first 16 chars,
     which requires char-12 to be `f`. But char-12 is always `4` (UUIDv4
     version marker). So u64::MAX is ALSO impossible.

   The engine's validation is defense-in-depth -- the IDE generator already
   guarantees the invariants the engine checks. **PASS.**

#### M3 finding -- 8-attempt cap rationale is defensive dead code under spec

**File / line:** `extensions/quantlab/src/quantbook/session.ts:195-209`.

Per the analysis above, the all-zero retry path is unreachable under
spec-compliant UUIDv4 (char-12 of the dashless form is always `4`).

The docstring at `:175-178` says:
> A truncated UUID could theoretically be all-zero (probability ~2^-64); we
> retry in that case.

This is FALSE for spec-compliant UUIDv4 (the probability is 0, not 2^-64).
The retry-loop + 8-attempt cap is defensive against a NON-SPEC UUID source
(Node's `crypto.randomUUID` going off-spec).

**Severity:** MEDIUM (doc-accuracy; defensive code retained is correct).

**Suggested closure:**

Update the docstring to reflect the actual threat model:

```typescript
/**
 * **Non-zero guarantee**: `PeerId(0)` is the engine's `LEGACY_PEER`
 * sentinel + would assert-fail `CollabSession::new`. Spec-compliant
 * UUIDv4 has a deterministic `4` at hex-char position 12 (= bit 48
 * from MSB of the truncated 64-bit value), so the all-zero outcome
 * is IMPOSSIBLE under spec. The retry loop + 8-attempt cap is
 * DEFENSE against a non-spec `crypto.randomUUID` source (entropy
 * broken / unexpected impl). Per CLAUDE.md No-Fallbacks: 8
 * consecutive failures surface loudly via thrown error.
 */
```

Optional secondary improvement: add a mocha test that empirically verifies
char-12 is always `4` across N=1000 invocations:

```typescript

    for (let i = 0; i < 1000; i++) {
        const v = generateUuidPeerId();

        assert.strictEqual(nibble, 0x4n, 'UUIDv4 version marker preserved');

});
```

This pins the spec-compliance assumption that the dead-code defense relies on.

### D. D5 DEVIATION cross-restart safety analysis -- PASS-WITH-FINDINGS

**File:** `.plans/_active.md:144-171` (original D5 lock + deviation note) +
`extensions/quantlab/src/quantbook/session.ts:180-209` (generateUuidPeerId
docstring) + `docs/architecture/ide-consumer-contract.md:1045-1077` (D5
DEVIATION section).

#### Adversarial walks

1. **Two-windows-same-workspace collision claim verification**:

   The deviation rationale: if PeerId were persisted per-workbook (via envelope
   v3 OR `~/.config/quantlab/peer_ids.json` keyed by workbook UUID), then
   opening the same workbook in two vscode windows of the same workspace
   simultaneously would read the SAME persisted PeerId twice.

   Verified by mental trace:
   - Window A opens workbook X -> reads stash entry for workbook X -> gets
     PeerId Y -> creates session with Y.
   - Window B opens workbook X (concurrent) -> reads stash entry for X ->
     gets the same PeerId Y -> creates session with Y.
   - Both sessions have the same PeerId Y. CRDT causality is violated: Loro
     deduplicates operations by `(peer, counter)` pairs; two writers with the
     same peer producing the same counter values produce indistinguishable
     ops -> dedup drops one writer's edits silently.
   - The `assert_ne!(peer_id.as_u64(), 0)` does NOT catch this -- both
     windows pass that gate.
   - Loro's own LoroDoc allows duplicate peer IDs (it doesn't deduplicate
     PeerIds at construction time). Hard to detect at the engine layer.

   **The claim is CORRECT.** The two-windows-same-workspace collision IS
   unsolvable with naive per-workbook stash.

2. **CRDT correctness under fresh-PeerId-per-session**:

   Each session uses a unique 64-bit UUID-truncated PeerId. Loro records each
   session's ops with the session's PeerId; the (peer, counter) namespace
   stays distinct.

   - Session 1: writes (PeerId A, counter 0), (A, 1), (A, 2) ...
   - Session 2 (same workbook, later restart): writes (PeerId B, counter 0),
     (B, 1) ...
   - When session 2 merges session 1's exported state, Loro sees A's ops as
     foreign-peer ops + applies them in causal order.
   - Loro causality is preserved: A's ops have their own VV chain; B's ops
     have a separate VV chain that includes a `(A, 2)` "I've seen A up to
     counter 2" entry once B merges from A.

   **PASS.** Fresh-UUID-per-session is CRDT-correct.

3. **Op-attribution continuity loss**:

   "This peer is User A across sessions" is LOST. Future "show my
   contributions" feature would surface session-3's ops as if they were from a
   different user than session-1's, even though both are "Alice on
   alice's-laptop".

   Trade-off accepted at V3.4 per the deviation note. V3.4.1+ may revisit.

   **What V3.4.1+ would actually need to solve**: not "persist PeerId per
   workbook" (which has the two-windows collision) but rather "persist a
   stable user-identity separately from PeerId, then have presence + ops
   carry both PeerId (for CRDT) + UserIdentity (for attribution)". This is a
   two-layer design that the deviation note correctly identifies as
   V3.4.1+ scope.

#### M1 finding -- D5 DEVIATION rationale understates the cross-WINDOW collision class

Not a V3.4 blocker.

### L3 -- target C -- UUID generation alloc cost

**File / line:** `extensions/quantlab/src/quantbook/session.ts:193-209`.

Each retry attempt allocates:
- `crypto.randomUUID()` -> one String (36 chars).
- `uuid.replace(/-/g, '')` -> another String (32 chars).
- `.slice(0, 16)` -> another String (16 chars).
- `BigInt('0x' + hex16)` -> the BigInt + a temporary string for the `0x` prefix.

8 attempts maximum = up to 32 transient allocations. In practice, 1 attempt
succeeds (the all-zero retry is unreachable per § C). The cost is one BigInt
allocation per `generateUuidPeerId` call. Effectively zero at V3.4 scale
(workbook open is ~1/min user action). **Acceptable.**

### L4 -- target F -- clearPresence on dispose console.warn pattern

Covered above in target F M4. Demoted to LOW because the dispose-time
fire-and-forget IS a legitimate No-Fallbacks "system boundary" exception;
the only fix needed is documentation of the policy.

### L5 -- target B -- cellGridLogic.ts presenceUpdate doesn't validate u16/u32 ranges

**File / line:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:217-263`.

The runtime-validation block at lines 220-229 checks types only:
```typescript
typeof (state as { sheet?: unknown }).sheet !== 'number'
...
typeof (state as { typing?: unknown }).typing !== 'boolean'
```

It does NOT check that `sheet` fits in u16, `row` / `col` / `selectionEnd*`
fit in u32, or that the numeric fields are integers. The engine's napi will
reject out-of-range values via napi-rs's ToUint16/ToUint32 coercion, which
silently wraps for `u16` field but produces a meaningful error for the napi
boundary.

Wait -- verify: PresenceStateJson uses `pub sheet: u16` at lib.rs:385. napi-rs
for `u16` field generates code that calls `napi_get_value_uint32` then casts
to u16. ECMAScript ToUint32 silently wraps `-1` to `0xFFFFFFFF`, then the
u16 cast `0xFFFFFFFF as u16 = 0xFFFF` (silent wrap). So a JS-side `sheet:
-1` becomes `sheet: 0xFFFF = 65535` silently. No error surface.

This is the same class of issue that V1 megaudit Codex H1 + Opus H2 fixed
for the `appendPutValue` numeric params (took as `f64` + validated). The
`PresenceStateJson` napi(object) does NOT have the f64+validate treatment;
it's `u16/u32` direct binding.

**Severity:** LOW (defense-in-depth gap; users typing into webview can't
reach this since `beginEdit`'s presenceUpdate broadcast uses
`Number(cell.getAttribute('data-row'))` which the webview's own DOM bounds
already constrain to valid u32).

**Suggested closure:**

V3.4.1+ could add per-field range checks in `dispatchIncomingMessage`'s
presenceUpdate arm. Not a V3.4 blocker.

### Required pre-V3.5 (design lock items)

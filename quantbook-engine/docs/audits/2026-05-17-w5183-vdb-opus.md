## Summary of method

1. Independently reproduced all 6 Microsoft documented fixtures in Python using the same algorithm body as `compute_vdb`. All 6 match within tolerances.
2. Hand-traced fractional-overlap cases (`start=2.3, end=4.7`; `start=0.5, end=1.5`; `start=0, end=0.875`) — overlap arithmetic is correct.
3. Verified the "locked SLN" crossover semantics against the "recompute SLN each period" alternative — they are **mathematically equivalent** post-switch (locked value equals recomputed value as long as book is depleted by exactly `sln_locked` each period). The locked form is a valid optimisation.
4. Verified `no_switch=TRUE` matches DDB period-by-period exactly (rate=0.2, life=10, salvage cap, all 10 periods match `compute_ddb`).
5. Verified additivity invariant: `VDB(0,k) + VDB(k,n) == VDB(0,n)` holds for several partitions.
6. Verified the "full book depletion (not overlap×period_dep)" semantics — the alternative gives 438.36 instead of 396.31 for `VDB(2400,300,120,6,18)`, so the impl's choice matches Microsoft.

## Algorithm-level findings

I found **no HIGH bugs in the core algorithm itself**. The crossover logic, fractional-overlap math, full-book-depletion model, period indexing, and `no_switch` salvage-cap inheritance are all consistent with Microsoft's documented examples and with the canonical period-iteration form.

I did find one HIGH validation gap (the i32-boundary DoS, inherited from the W5-182.1 DB pattern but with the same off-by-one edge), several MEDIUM documentation/test mismatches, and a number of LOW coverage gaps.

### HIGH-1: i32-overflow DoS guard is off-by-one — exact `i32::MAX` (~2.147e9) bypasses the bound

**File:** `crates/ql-functions/src/financial_fns.rs:837-838`

**Issue:**

```rust
|| life > i32::MAX as f64
|| end_period > i32::MAX as f64
```

`i32::MAX = 2147483647`. As `f64`, this value is exactly representable. The check uses strict `>`, so a user input of exactly `2147483647.0` for `life` and `end_period` **passes validation**, then `end_ceil = end_period.ceil() as i32 = 2147483647`, and the loop iterates 2.15 billion times.

**Why it's wrong:**

- This is the exact pattern W5-182.1 was meant to close. The `db_huge_life_rejected` test uses `i32::MAX as f64 + 1.0` (just over threshold), implicitly acknowledging that exactly `i32::MAX` is allowed — but `i32::MAX` itself triggers a 2-billion-iteration loop on each call, which is DoS-class for a per-cell function.
- DB has the same off-by-one (line 710–711), so the issue is consistent with sister behavior — but VDB shipped without fixing the bug DB introduced. The lesson from W5-182.1 was "soundness > IronCalc fidelity"; this is a soundness gap.
- Python verification: a 2.15-billion iteration loop with ~10 arithmetic ops per iteration is ~20+ seconds on modern hardware. Per-cell. Catastrophic for sheets with VDB in many cells.

**Fix:** Change `>` to `>=` (or equivalently use `>= i32::MAX as f64` since `i32::MAX as f64` is the borderline). Update `vdb_huge_life_rejected` to pin both `1e15` and exactly `i32::MAX as f64`. Apply the same fix to `compute_db`. New test: `vdb(&[n(2400.0), n(300.0), n(i32::MAX as f64), n(0.0), n(i32::MAX as f64)])` should be `#NUM!`.

### MEDIUM-1: Doc-comment omits the `.max(1.0)` floor on `periods_remaining`

**File:** `crates/ql-functions/src/financial_fns.rs:796-797, 871`

**Issue:**

Doc-comment §Algorithm step 2 says:
> SLN-from-here `(book − salvage) / (life − i)`

The impl line 871–872 actually computes:
```rust
let periods_remaining = (life - period_f).max(1.0);
let sln_now = (book - salvage) / periods_remaining;
```

The `.max(1.0)` floor is a behavioural divergence from the documented formula and is not flagged.

**Why it's wrong:**

- The doc-comment is the canonical spec we use to verify against Microsoft. Auditors comparing impl to doc would assume the floor was an unintended omission.
- The floor matters for fractional life (e.g., `life=4.5`, `period_f=4` → `periods_remaining = max(0.5, 1) = 1`, an artificial 2x suppression of `sln_now`). In practice the salvage cap drives book to salvage before the floor matters, so I could not construct a case where the impl returns a different value than the unfloored formula — but the algorithm is **specified differently than implemented**, which is a documentation defect even if currently benign.
- The inline comment (line 868–870) says "Periods remaining including this one. Guarded against div-by-zero (validation ensures end_period <= life so period <= life - 1, hence life - period >= 1)." But `period <= life - 1` only holds for **integer life**. For `life = 4.5`, `period` iterates up to `ceil(4.5) - 1 = 4`, and `life - 4 = 0.5 < 1`. The inline comment's reasoning is wrong for fractional life — the `.max(1.0)` is doing real work the comment denies.

**Fix:** Update doc-comment §Algorithm step 2 to read `(book − salvage) / max(life − i, 1)`. Fix the inline comment to acknowledge fractional-life case: `.max(1.0)` is required for fractional life because `period_f` can equal `life - 0.x` at the last iteration. Add a dedicated test for fractional life with `no_switch=False` to pin the floor's effect (currently `vdb_no_switch_keeps_ddb_throughout` uses `life=10.0` integer only).

### MEDIUM-2: Matrix and registry comment claim `arg_type` is "Boolean-strict"; it is not

**File:** `docs/compat/excel-matrix.md:265` and `crates/ql-functions/src/financial_fns.rs:44-49, 818-820`

**Issue:**

Matrix says:
> **Engine convention**: `no_switch` uses `arg_type` (Boolean-strict); other args use `arg_num` (allows Boolean coercion)

Doc-comment §Engine convention (line 818–820) says:
> all numeric args use `arg_num` which accepts Boolean coercion; `no_switch` uses `arg_type` for explicit Boolean semantics.

Actual `arg_type` implementation (line 44–49):
```rust
fn arg_type(v: &Value) -> Result<bool, ErrorValue> {
    match coerce_numeric(v) {
        NumericArg::Number(n) => Ok(n != 0.0),
        NumericArg::Skip => Ok(false),
        NumericArg::Error(e) => Err(e),
    }
}
```

`arg_type` accepts **any numeric value** (including Booleans, which `coerce_numeric` handles via `to_number_strict_skip_blank → to_number_strict`) and treats non-zero as TRUE. It is NOT "Boolean-strict". `VDB(_, _, _, _, _, _, 0.5)` evaluates `no_switch = TRUE` because `0.5 != 0`.

**Why it's wrong:**

- The matrix/doc tells the reader VDB diverges from the rest of the financial family by being strict about Booleans. It doesn't — it accepts the same Boolean-coercion (via numeric) that the rest of the family does. The only difference is the final `!= 0.0` check that turns the number into a bool, which is identical to what every other function does internally.
- The `arg_type` docstring (line 42–43) still says "Coerce optional `type` arg into the `period_start` bool" — copy/paste from its original use site in PMT/FV — and is **incorrect for the VDB context**. A reader sees "type", not "no_switch", and is confused.

**Fix:**
1. Matrix wording: change "Boolean-strict" to "via the same lenient bool coercion the family uses (non-zero numeric → TRUE)".
2. Update the `arg_type` doc-comment (line 42–43) to acknowledge it is the family-wide `bool` coercion helper, used by PMT/FV's `type` and by VDB's `no_switch`.
3. Update VDB doc-comment §Engine convention to drop the "explicit Boolean semantics" framing — it is misleading.

### MEDIUM-3: `vdb_boolean_no_switch_coerces` does not actually test numeric → bool coercion

**File:** `crates/ql-functions/src/financial_fns.rs:2839-2866`

**Issue:**

The test name and intent ("Confirms `arg_type` coercion") implies it tests the Number → bool path. But the test only passes `Value::Boolean(true)` and `Value::Boolean(false)`. 3. Optionally: `Value::Blank` → FALSE (per the `NumericArg::Skip` branch).

### MEDIUM-4: `vdb_no_switch_diverges_from_default_partial_range` asserts only `>=`, would pass under equality

**File:** `crates/ql-functions/src/financial_fns.rs:2700-2703`

**Issue:**

```rust
assert!(
    switched >= no_switch,
    "switched ({switched}) should be ≥ no_switch ({no_switch})"
);
```

The test docstring says "the no_switch sum will be smaller than the default", implying strict inequality. But `>=` allows equality. If a regression made the switch never trigger, both values would be equal and the test would still pass.

**Why it's wrong:**

- I verified via Python that the actual divergence for these inputs is ~7.4 (227.68 vs 220.30 for `VDB(1000, 100, 10, 5, 10)`). A regression that suppressed the switch would yield 220.30 vs 220.30 — still passes.
- The test was intended as the **strongest** divergence assertion in the VDB suite (the only other "switch happened" coverage is the bound `cost-salvage` constraint, which is salvage-cap-driven and would pass even without switching).

**Fix:** Change `>=` to `> no_switch + tolerance` (e.g., `+ 1.0` since divergence is ~7 on a $1000 asset). Pin the actual values: `switched ≈ 227.68` and `no_switch ≈ 220.31` to two decimal places via `approx`. The combination "divergence asserted + value pinned" makes the test resistant to both the suppress-switch regression and any algorithmic drift.

## Items I checked and did NOT find a bug in

For audit accountability, here is the list of concerns from the audit prompt I explicitly checked and concluded are correct:

1. **All 6 Microsoft fixtures.** Independently reproduced in Python. All match within stated test tolerances.
2. **Crossover semantics (locked vs recomputed SLN).** Mathematically equivalent. Verified by tracing periods 6-10 of `VDB(1000, 100, 10, 5, 7)`: locked sum = recomputed sum = 117.96. Once switched, both forms produce identical per-period amounts because `sln_locked = (book_k - salvage)/(life - k)` and book decrements by `sln_locked` each period, so recomputed `sln = (book_k - sln_locked - salvage)/(life - k - 1) = sln_locked`.
3. **Fractional-overlap math.** Hand-traced `start=2.3, end=4.7`: periods 2 (overlap 0.7), 3 (overlap 1.0), 4 (overlap 0.7) — correct. `start=0.5, end=1.5`: periods 0 (overlap 0.5), 1 (overlap 0.5), totals 240+192=432 — additivity holds.
4. **Book depletion vs overlap accounting.** Verified empirically: replacing `book -= period_dep` with `book -= period_dep * overlap` gives 438.36 instead of 396.31 for `VDB(2400, 300, 120, 6, 18)`. The impl's choice (full depletion) matches Microsoft.
5. **Period 0 vs period 1 convention.** Loop iterates `period = 0` for the first life period, matching Microsoft's `start_period = 0, end_period = 1 = first period` semantics. Verified with `VDB(_, _, _, 0, 0.5) = 240 = 480 × 0.5` (half of period 1 DDB).
6. **`no_switch` salvage-cap inheritance.** Period-by-period traced vs `compute_ddb` for all 10 periods of `VDB(2400, 300, 10, 0, 10, 2, TRUE)` — exact match. The cap correctly stops at the salvage floor at period 10 (22.12 vs 80.53 raw DDB).
7. **`periods_remaining = (life - period_f).max(1.0)`** floor — see MEDIUM-1 for the doc-mismatch finding. The floor itself is **never observably wrong** in my probing because the salvage cap drives book to salvage before the floor matters in the cases I could construct. But it's still doc-divergent.
8. **`sln_per_period = (book - salvage) / (life - k)` vs `(life - k + 1)`.** Mathematically `(life - k)`, with `k = period_f` (0-based index). Verified by checking that book reaches exactly `salvage` after `(life - switch_period)` more iterations once locked.
9. **`start_period == end_period → 0`.** Validation passes first; short-circuit returns 0. Works for `start = end = 0`, `start = end = life`, `start = end = mid`. Correct.
10. **NaN/Inf handling.** Rejected at `to_number_strict_skip_blank` (via `sanitize_f64`) — never reaches `compute_vdb`. No kernel-side guard needed.
11. **Salvage > cost.** Returns 0 (DDB cap clamps to 0, SLN goes negative, no switch). Behaviour is reasonable; not flagged as a bug because Microsoft is silent. Could be tested.
12. **rate > 1 (factor > life).** Not clamped in VDB (unlike DDB). Salvage cap absorbs the divergence (`min(book * rate, book - salvage)` = `book - salvage` when `rate > 1`). Functionally equivalent to DDB's rate-clamp. Correct.
13. **Validation error propagation in all 7 arg slots.** `vdb_error_in_arg_propagates` tests arg 0 and arg 6. Not tested for args 1–5. Minor coverage gap (LOW-level), but the pattern is uniform (each arg goes through `arg_num` which propagates errors identically).
14. **Arity boundaries.** `vdb_wrong_arity` covers 0, 4, and 8 args. Correct.
15. **e2e dispatch.** `e2e_vdb_depreciation` exercises VDB through the parser → AST → bind → eval path. Verified both default (480) and factor=1.5 (315) paths.

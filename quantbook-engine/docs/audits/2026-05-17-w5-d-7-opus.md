## Summary

W5-D-7 ships 2 RangeAwareFns closing the Wave-3-tagged matrix gap: `XNPV` (closed-form date-indexed NPV) and `XIRR` (date-indexed IRR via Newton-Raphson with bisection fallback). The diff is exactly the 5 files in the brief (financial_fns.rs, registry.rs, coverage.rs, region_mul2_e2e.rs, excel-matrix.md). 23 unit tests in the W5-D-7 block (11 XNPV + 12 XIRR) plus 1 e2e smoke pass. All 4 gates green (`cargo test --workspace` → 3767 passing; `cargo clippy --workspace --all-targets -- -D warnings` clean; `cargo fmt --all --check` silent; coverage assertion 238). Registry size assertion bumped 236 → 238 and passes.

I executed the Microsoft canonical anchors externally in Python (3.13) before reading the test assertions:

- **XNPV anchor**: rate=0.09, values=[-10000, 2750, 4250, 3250, 2750], dates=[39448, 39508, 39751, 39859, 39904] → `2086.647602031535`. Test asserts `(got - 2086.6478).abs() < 1.0` (tolerance 1.0 is loose; tighter 1e-3 would still pass). The 5 Excel serial-date values are correct (`(toordinal(date) - toordinal(1900-01-01)) + 2` confirms each).
- **XIRR anchor**: same values + dates → Newton from 0.1 converges in <15 iters to `0.3733625335188315` (Microsoft says 0.373362535 ≈ 37.34%). Test asserts `(got - 0.373362535).abs() < 1e-5`.

Algorithm parity vs IronCalc `compute_xnpv` / `compute_xnpv_prime` / `compute_xirr_newton_raphson` / `compute_xirr` (`base/src/functions/financial_util.rs:139-255`) verified line-by-line:

- `compute_xnpv`: hoists `values[0]` out of loop (algebraically equivalent to summing from i=0 since `(1+r)^0 = 1`), then sums `vᵢ / (1+r)^((dᵢ-d₀)/365)` for i≥1. Identical to IronCalc. **Extra guard added**: `if values.is_empty() { return Err(Num) }` before `values[0]` access — IronCalc has a latent panic on empty (guarded at all callers); ours is defensive in-depth. Good.
- `compute_xnpv_prime`: i=0 term correctly omitted (its derivative wrt r is 0 since `v₀` is unscaled). For i≥1: `deriv -= vᵢ * ratio / (1+r)^(ratio+1)`. Identical formula to IronCalc lines 161-176.
- `xirr_newton`: 100 iter cap, eps=1e-7, exit on `|Δ| < eps`. Identical to IronCalc. **Defensive divergence**: `if f_prime == 0.0 { return Err(Num) }` added (IronCalc lets the divide proceed to ±∞ and waits for finite-check to fire on next iter). Ours is strictly safer; semantically the same (both terminate at Err).
- `compute_xirr`: guess ≤ -1 → `#VALUE!`; single-sign vals → `#NUM!`; try Newton from `guess`; on fail, evaluate `f(-0.9999)` and `f(100.0)`; if same sign, try Newton from 200; else bisect over the bracket for 49 iter (loop is `1..50`). Identical to IronCalc.
- The `?` operator propagates non-finite XNPV evaluations during bisection — same as IronCalc.

**Convergence-bound proof**:
- `xirr_newton`: hard 100-iter loop, no `continue`, no recursive call → bounded.
- Bisection: hard 49-iter loop (`1..50`), no `continue`, no recursive call → bounded.
- Newton-from-200 fallback: same 100-iter cap → bounded.
- Even with adversarial inputs (NaN guess, +∞ guess, 100-year date spread, max-Excel-serial date spread, 1000-year date spread, oscillating cashflows, huge initial outflow with tiny middle flows, all-same-date) the implementation either converges or returns `Err(Num)`. I built a standalone Rust harness (`target/adversarial_test.rs`, `target/adversarial_guess.rs`) replicating the four functions verbatim and ran 8 + 5 = 13 adversarial cases. No hangs, no panics, every case terminates in <100 iter. Cases that fail to converge correctly return `Err(Num)` and would surface as `#NUM!` to the user.

**Concrete adversarial-input outcomes** (from the standalone harness):

| Input | Result |
|---|---|
| 100-yr spread, simple 2-flow | `Err("non-finite")` → `#NUM!` |
| 1000-yr spread | `Err("non-finite")` → `#NUM!` |
| Long-tail with huge final flow | `Ok(0.318)` — converges |
| All-same-date (degenerate) | `Err("bisection no root, newton@200 no converge")` → `#NUM!` |
| All-negative cashflows | `Err("single sign")` → `#NUM!` (early reject) |
| Oscillating 1e15 / -1e15 | `Ok(-3e-15)` — converges |
| Huge initial outflow, tiny middles | `Err(...)` → `#NUM!` |
| Max-Excel-serial date spread | `Err("non-finite")` → `#NUM!` |
| guess = NaN | converges via bisection fallback (Newton fails; bisect succeeds) |
| guess = +∞ | same — converges via bisection |
| guess = -∞ | `Err("guess <= -1")` |
| guess = -1.0 | `Err("guess <= -1")` |
| guess = -0.9999 | converges |

Newton-Raphson never crosses `1 + r ≤ 0` without producing NaN/Inf (since `f64::powf(neg, frac) = NaN` propagates), so the bracketing is implicitly safe.

Findings: **0 HIGH, 2 MEDIUM, 5 LOW**. Both MEDIUMs are IronCalc-parity divergences that the implementing instance flagged in code but the matrix-doc/test fixtures pin as the v1 behavior. Pattern prediction (1-2H for iterative kernel) does NOT hold — the iterative kernel is well-bounded by both 100-iter and 50-iter caps and a finite-check Err short-circuit. This is a tighter implementation than W5-D-4's BINOM.INV / W5-D-5's GAMMA.INV iterative kernels (which produced Codex HIGHs); the XIRR fallback ladder (Newton-from-guess → bisection → Newton-from-200) is more defensive than either.

## HIGH

(none)

The first risk listed in the audit brief — XIRR's iterative kernel possibly hanging under adversarial inputs — is conclusively refuted by the harness runs above. All three numerical loops (Newton×2, bisection) have hard iteration caps and no escape hatches that bypass them. The `compute_xnpv` / `compute_xnpv_prime` `is_finite()` guards short-circuit Newton on overflow/underflow on the very next iteration, so divergent Newton paths exit early and fall through to the bisection ladder; the bisection ladder is itself bounded.

The second pre-flagged risk — `xirr_newton` divide-by-zero — is mitigated by the `if f_prime == 0.0 { return Err(Num) }` guard added in our impl (a strict improvement over IronCalc, which lets the divide proceed to ±∞ and relies on the finite-check on the next iter to terminate). Either way, both paths terminate; ours saves one iteration.

The third pre-flagged risk — `compute_xnpv` overflow on huge date deltas — is caught by the `if !xnpv.is_finite()` guard. Verified concretely: 1000-yr spread → Newton-Raphson aborts at iter 2 with `non-finite`, then `compute_xirr` propagates the Err through bisection (since `f1 = compute_xnpv(-0.9999, ...)` produces overflow too: `(0.0001)^1000` is `inf` denominator → `value / inf = 0` per IEEE, but accumulating could produce inf in the other direction; either way the finite-check fires).

## MEDIUM

### MEDIUM-O-1 — `xnpv` text-in-dates returns `#NUM!`; IronCalc returns `#VALUE!`

**Where**: `crates/ql-functions/src/financial_fns.rs:1572-1583` (`collect_xnpv_range`) + test `xnpv_text_in_dates_is_num_error:3534-3540`.

**What**: IronCalc's `get_array_of_numbers_xpnv` takes an `error: Error` parameter (`base/src/functions/financial.rs:296-321`). For `args[1]` (values), the error code is `Error::NUM`; for `args[2]` (dates), the error code is `Error::VALUE` (`base/src/functions/financial.rs:897-904`). Our `collect_xnpv_range` returns `Err(ErrorValue::Num)` for non-numeric cells regardless of which arg it's called for. So `XNPV(0.05, A1:A2, B1:B2)` where `B2` is text returns `#NUM!` in our impl but `#VALUE!` in IronCalc.

The test pins the divergence (`assert_eq!(... ErrorValue::Num)` for text in dates). The matrix-doc row for XNPV says "Empty/non-numeric → #NUM! (strict; XNPV rejects unlike NPV which skips)" — this is accurate for our v1 but does NOT call out the IronCalc divergence.

**Why MEDIUM**: User-visible error-code change vs Excel canon. Other Excel-parity-strict callers (financial regression tests, golden-fixture replay against `.xlsx` exports) will see the mismatch. The fix is one extra parameter on `collect_xnpv_range` plus splitting the empty-cell error from the non-numeric error.

**Fix sketch** (deferred — flag with the implementing instance):
```rust
fn collect_xnpv_range(arg: &FnArg, non_number_err: ErrorValue) -> Result<Vec<f64>, ErrorValue> {
    // ... Blank → Err(Num); non-numeric → Err(non_number_err); ...
}
// Caller:
let values = collect_xnpv_range(&args[1], ErrorValue::Num)?;  // values: non-number → NUM
let dates  = collect_xnpv_range(&args[2], ErrorValue::Value)?; // dates:  non-number → VALUE
```

Once the caller is fixed, update `xnpv_text_in_dates_is_num_error` → `xnpv_text_in_dates_is_value_error` (rename + flip expected error to `Value`) and update the matrix-doc row to "Empty → #NUM!; non-numeric in values → #NUM!; non-numeric in dates → #VALUE! (IronCalc canon)".

### MEDIUM-O-2 — Off-by-one in `MIN_DATE_SERIAL` (0 vs IronCalc 1)

**Where**: `crates/ql-functions/src/financial_fns.rs:1614` (`const MIN_DATE_SERIAL: f64 = 0.0;`) and matrix-doc row.

**What**: IronCalc's `MINIMUM_DATE_SERIAL_NUMBER` is `1` (`base/src/constants.rs:24`), comment: "We do not support dates before 1899-12-31." Excel itself treats serial=0 as the placeholder "1900-01-00" (a non-date), and serial=1 as 1900-01-01. Our impl sets `MIN_DATE_SERIAL = 0.0`, which allows `d = 0` to pass validation. IronCalc rejects `d < 1.0` with `#NUM!`.

After flooring, `d = 0.5` → `0.0` in both impls. IronCalc rejects with `#NUM!`; ours accepts. The XNPV/XIRR result for `d₀ = 0` then computes `(dᵢ - 0)/365` which is fine — the divergence is purely in the **input-validation** error code path, not in the math (math agrees once inputs validate).

The matrix-doc row says "Excel-serial range `[0, 2_958_465]`" — accurate to our impl, but the IronCalc reference uses `[1, 2_958_465]`.

**Why MEDIUM**: An off-by-one in date validation isn't a numerical bug, but it's a parity divergence the implementing instance did not flag. Users importing `.xlsx` files exported from Excel/IronCalc with `d=0` cells (rare but possible) will see different error semantics. Also: the audit brief explicitly listed "verify these are the correct Excel canon" as a special concern.

**Fix sketch**:
```rust
const MIN_DATE_SERIAL: f64 = 1.0;   // was 0.0
```
Update matrix-doc row from `[0, 2_958_465]` to `[1, 2_958_465]`. No test currently pins `d=0` directly, so no test changes needed. Re-add a new test `xnpv_date_zero_is_num_error` to lock the new convention.

## LOW

### LOW-O-1 — `xnpv` rejects scalar args; IronCalc accepts (1×1 array)

**Where**: `collect_xnpv_range:1572-1583` returns `Err(ErrorValue::Value)` for `FnArg::Scalar(_)`. The test `xnpv_scalar_for_values_is_value_error:3592-3597` pins this.

IronCalc's `get_array_of_numbers_xpnv` passes `true` for the `accept_number_node` parameter (`base/src/functions/financial.rs:305`), meaning a scalar value is treated as a 1-element array. `XNPV(0.05, 100, 40000)` works in Excel/IronCalc → `100` (single-value XNPV). Our impl returns `#VALUE!`.

This is **consistent with the established W5-168 NPV / W5-171 IRR / W5-174 MIRR convention** for the financial range-aware family (all reject scalar where IronCalc accepts). So this is not a new W5-D-7 bug; it's the family-wide v1 convention. Worth surfacing the divergence catalog when the convention is reviewed in a later pass.

### LOW-O-2 — Bisection loop is `1..50` (49 iters), doc says "50 iterations"

**Where**: `compute_xirr:1554-1564` — `for _ in 1..max_iterations { ... }` with `max_iterations = 50` runs 49 iterations, not 50. The pub doc on `xirr` says "Newton-Raphson on `XNPV(r) = 0` from `guess`; bisection fallback on `[-0.9999, 100]`" — doesn't specify count, so no drift there. The inline comment in `compute_xirr` doesn't claim 50 explicitly either. Just an off-by-one that mirrors IronCalc verbatim (`base/src/functions/financial_util.rs:242` uses the same `1..max_iterations`).

**Why LOW**: This is an inherited line-by-line port artifact and has no practical impact — bisection with eps=1e-8 over `[-0.9999, 100]` converges in ~34 iters for any well-conditioned bracket (the dx halves each iteration; `(100 - (-0.9999)) / 2^34 ≈ 5.9e-9 < 1e-8`). 49 iters is more than enough. Flag if the convention is ever revisited.

### LOW-O-3 — `xirr` with `guess = NaN` silently converges via bisection

**Where**: `compute_xirr:1525` — `if guess <= -1.0 { return Err(Value) }`. NaN comparisons evaluate to `false`, so `NaN <= -1.0 == false` and NaN passes the guard. `xirr_newton(values, dates, NaN)` then computes `compute_xnpv(NaN, ...)` which produces NaN, fails the finite-check, returns `Err(Num)`; bisection fallback then runs with the original `values`/`dates` (NOT using guess) and succeeds.

Net effect: `XIRR(values, dates, NaN)` returns a valid result instead of `#NUM!` or `#VALUE!`. Excel would refuse to pass NaN as a scalar in normal flow (any expression producing NaN errors out first), so this is unreachable in practice from formula syntax. But a programmatic caller (Python bridge, registry test, fuzz harness) could feed NaN directly.

IronCalc has the same behavior (its `get_number` would let NaN through too). Inherited from IronCalc. Worth a single defensive test if anyone wants to harden it: `if !guess.is_finite() { return Err(Value) }`.

### LOW-O-4 — XIRR doc doesn't mention the implicit "first date is anchor" rule

**Where**: `xirr` doc string `:1693-1701` and matrix-doc row.

The math `(dᵢ - d₀)/365` makes `d₀ = dates[0]` the anchor for all discounting. The unit tests pin "date precedes first is NUM error" but neither the doc nor the matrix entry explicitly states `d₀ = dates[0]` — a user might assume "earliest date" instead of "first date in array order". For IronCalc canon and Excel, it IS `dates[0]` regardless of sort order — the test `xnpv_date_precedes_first_is_num_error` enforces that subsequent dates must not precede the first.

**Why LOW**: Pure documentation polish. The error message would surface if a user got it wrong.

### LOW-O-5 — Matrix-doc divergence-from-IronCalc claims not surfaced

**Where**: `docs/compat/excel-matrix.md:294-295`.

The XNPV row says "Discount `(1+rate)^((dᵢ-d₀)/365)`. `rate > 0` STRICT." — but doesn't mention:
- The serial-date range `[0, 2_958_465]` differs from IronCalc's `[1, 2_958_465]` (MEDIUM-O-2).
- Non-numeric in dates returns `#NUM!` (ours) vs `#VALUE!` (IronCalc/Excel) (MEDIUM-O-1).
- Scalar args rejected with `#VALUE!`; IronCalc accepts as 1×1 (LOW-O-1).

The XIRR row similarly does not call out:
- The guess `NaN` / `+∞` passing the `≤ -1` guard (LOW-O-3).
- The bisection bracket missing roots in `(-1, -0.9999)` (an IronCalc-documented limitation).

**Why LOW**: Matrix doc is the single source of truth for v1 divergences. The depreciation-batch row for SYD (W5-182.1) explicitly calls out the asymmetric `#NUM!` canon vs SLN's `#DIV/0!` — XNPV/XIRR should follow the same template.

## Confirmed Non-Issues

- **Microsoft canonical anchor**: independently reproduced. Excel serial dates 39448/39508/39751/39859/39904 verified via `(date.toordinal() - date(1900,1,1).toordinal()) + 2`. XNPV(0.09) = 2086.6478. XIRR ≈ 0.37336.
- **Single-value XNPV**: `compute_xnpv` returns `values[0]` for `len == 1` (loop body never executes). Test `xnpv_single_value_returns_value_at_zero_offset` pins. Algebraically correct — `XNPV(r, [v0], [d0]) = v0 / (1+r)^0 = v0`.
- **Date floor**: `dates_raw.iter().map(|d| d.floor()).collect()` — matches IronCalc's `dates.iter().map(|s| s.floor()).collect()` byte-for-byte. The flooring happens BEFORE `validate_xnpv_xirr_dates` runs, so the validation sees integer-valued floats. Correct order.
- **XNPV strict 3-arg requirement**: our `xnpv` rejects 2 args with `#VALUE!`. IronCalc accepts 2-3 args at the arity gate (`if !(2..=3).contains(&arg_count)`) but then crashes accessing `args[2]` on 2-arg inputs (latent panic). Our strict-3 guard avoids inheriting that bug. The audit brief specifically asked to verify this — confirmed.
- **`rate > 0` strict (not `rate >= 0`)**: `if rate <= 0.0 { return Value::Error(Num) }`. Matches IronCalc line 942.
- **`compute_xnpv` empty-values guard**: added defensively (IronCalc has a latent panic; we don't). All production callers go through `validate_xnpv_xirr_dates` which would catch empty first, but defense-in-depth costs nothing.
- **`compute_xnpv_prime` i=0 term omission**: correct — the derivative of `v₀` (unscaled) wrt `r` is 0. The loop `for i in 1..values.len()` correctly skips it.
- **Newton-Raphson `f_prime == 0` short-circuit**: added in our impl, missing from IronCalc. Strict improvement; no behavioral regression vs IronCalc (both paths return `Err(Num)`; ours just saves one iter).
- **Bisection bracket `[-0.9999, 100]`**: identical to IronCalc line 222-223. Inherited limitation (misses roots in `(-1, -0.9999)`) is the canonical IronCalc behavior.
- **Single-sign values rejection**: `values.iter().all(|&x| x >= 0.0) || values.iter().all(|&x| x <= 0.0)` — handles all-zero case (both `all()` return true → Err) and empty case (vacuously true → Err) defensively. IronCalc does the same.
- **Date validation order**: IronCalc flooes then validates; we floor then validate. Same.
- **`finish()` wrapper around `compute_xnpv` / `compute_xirr`**: consistent with sibling NPV / IRR / MIRR pattern.
- **Coverage entries**: both XNPV and XIRR added to `EXPLICITLY_DEFERRED` array with descriptive `W5-D-7` rationale matching established W5-D-* conventions.
- **Count bump 236 → 238**: assertion at `registry.rs:1020` matches; `every_registered_function_has_a_coverage_decision` test passes (3/3 coverage suite green).
- **e2e smoke test pattern**: `e2e_xnpv_xirr_registered` follows W5-D-6 / W5-177 / W5-174 sibling fns pattern (case-insensitive lookup, 4 assertions: XNPV/xnpv/XIRR/xirr).
- **Matrix-doc placeholder replacement**: prior `| XNPV / XIRR | ❌ | 0 | Wave 3 | ...` row replaced with 2 distinct rows. No orphan placeholder remains.
- **Files in scope**: `git diff --stat` shows exactly 5 files matching the brief.
- **No code outside scope touched**: confirmed.
- **All gates pass**: `cargo fmt --all --check` silent; `cargo clippy --workspace --all-targets -- -D warnings` clean (only `Checking` and `Finished` lines); `cargo test --workspace` → 3767 passing.
- **debug_assert_eq slice lengths**: present in both `compute_xnpv` and `compute_xnpv_prime`. Production callers validate first; the asserts are belt-and-braces.

## Recommendation

**Ship after addressing MEDIUM-O-1 and MEDIUM-O-2 (or explicitly accepting both as v1 divergences in the matrix-doc).** Both are pure error-code / off-by-one parity issues with IronCalc — not numerical bugs — and would take ~10 lines of code to fix. If shipping as-is, the matrix-doc rows should explicitly call out the divergences (LOW-O-5).

The iterative kernel is the cleanest of the Wave 3 iterative paths (W5-D-4 BINOM.INV and W5-D-5 GAMMA.INV both produced Codex HIGHs around iteration bounds). XIRR's three-layer fallback ladder (Newton-from-guess → bisection → Newton-from-200) is bounded on every layer, and the `is_finite()` short-circuit makes adversarial paths exit early rather than chase NaN/inf around the function space. The added `f_prime == 0` guard in `xirr_newton` is a strict improvement over IronCalc.

W5-D-7 closes Wave 3.

Phase 5.7 V3.2.d Codex lane audit over V3.2.a + V3.2.b + V3.2.c.

Engine HEAD audited: `9ca8fc88648f`.
IDE HEAD audited: `a165141eb68c`.

Verdict: PASS-WITH-FINDINGS. No HIGH findings. Three MEDIUM findings should be closed before treating V3.2 as fully shippable: transport-closed edit recovery, cell-grid panel registry semantics, and uncaught render failures in the collab poll loop.

Tests were not rerun for this audit doc; source paths and existing test coverage were read directly.

Collab opens always create a new panel but still overwrite `activePanels` (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:145-157`). See MEDIUM-2.

## MEDIUM

### M1. `transport_closed` during a cell edit commits locally but is not reconnected, rendered, or explicitly flushed

Files:
- `crates/ql-collab/src/session.rs:283-291`
- `crates/ql-collab/src/session.rs:714-736`
- `crates/ql-bindings-node/src/lib.rs:908-915`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:177-190`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:238-244`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:322-338`

Problem:
Under `AutoFlushPolicy::OnAppend`, the engine's contract is mutate-then-flush: if the flush fails with `transport_closed`, the local op is already committed and IDE retry logic must not retry the mutation; it must reconnect and explicitly call `flushDeltaToTransport()` to flush the pending op (`crates/ql-bindings-node/src/lib.rs:908-915`). `dispatchIncomingMessage` catches all failures from `appendPutValueValidated`, posts an `errorReply`, and does not signal `CellGridPanel` to reconnect (`extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:177-190`). `CellGridPanel.handleIncoming` only wires `onCommit` and `onError`; it has no transport-closed callback (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:238-244`).

The poll loop may later notice `transport_closed` and reconnect, but `handleTransportClosed` attaches the fresh transport without the explicit post-attach flush recommended by the engine docs (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:329-338`). Because `attachTransport` itself does not flush (`crates/ql-collab/src/session.rs:723-736`), the committed edit can remain pending until the next user mutation or a later poll path happens to auto-flush.

Reproduction:
1. Open `quantlab.quantbookCellGridCollab`.
2. Let the transport close after the user presses Enter but before the OnAppend flush succeeds.
3. `appendPutValueValidated` commits the `PutValue`, then throws `[transport_closed]`.
4. The dispatcher posts `errorReply`; it does not call `onCommit`, so the local committed cell is not rendered.
5. If reconnect later succeeds, the fresh transport is attached but the pending op is not explicitly flushed.

Suggested closure:
Add an explicit transport-error path from `dispatchIncomingMessage` to `CellGridPanel` (for example `onTransportClosed` or a structured dispatcher return). On `transport_closed` / `transport_io` from a mutator, do not retry the append; render the local committed state if appropriate, call the reconnect path, and after successful `attachTransport(fresh)` call `flushDeltaToTransport()` when `hasPendingFlush()` is true. Consider `flushPendingToTransport()` if the UI claims the edit is fully on the wire.

### M2. `activePanels` conflates local and collab panels, breaking refresh and local-open semantics

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:54`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:94-108`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:145-164`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:176-180`
- `extensions/quantlab/src/commands/quantbookCommands.ts:198-213`
- `extensions/quantlab/src/commands/quantbookCommands.ts:232-240`

Problem:
The implementation has one module-level `Map<number, CellGridPanel>` (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:54`). Local opens reuse whatever is in the map when `attachment === undefined` (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:102-108`). Collab opens bypass the lookup, but after creating the panel they still run `activePanels.set(sheet, instance)` unconditionally (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:145-157`).

Actual user-facing behavior:
- P1 local open, cache hit with local panel: reveals and refreshes that local panel.
- P2 local open, cache miss: creates a local panel and stores it in the map.
- P3 collab open, no prior panel: creates a collab panel and stores it in the map.
- P4 collab open while local exists: creates a collab panel, overwrites the map slot, and leaves the local tab open but orphaned from `refreshAll`.
- P5 local open after collab exists: does not create or reveal a local panel. It reveals and renders the collab panel because the collab panel owns the map slot.
- P6 collab open after collab exists: creates another collab panel, overwrites the map slot again, and leaves the prior collab panel alive with its own timer but unreachable from `refreshAll`.

The `onDidDispose` identity guard is correct and prevents stale deletes (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:158-164`), but it also confirms the overwritten panel remains alive until the user closes the tab. `CellGridPanel.refreshAll()` only iterates current map values (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:176-180`), so any overwritten local or collab panel is no longer covered by the Refresh command.

Reproduction:
1. Run `Quantbook: Open Cell Grid` to create a local sheet-0 panel.
2. Run `Quantbook: Open Cell Grid (Collab)` to create a collab sheet-0 panel. The local tab remains open but is evicted from `activePanels`.
3. Run `Quantbook: Refresh Cell Grid`; only the collab panel is refreshed.
4. Run `Quantbook: Open Cell Grid` again; the command reveals the cached collab panel, not the local panel or a new local sample-data panel.

Suggested closure:
Do not use one `Map<number, CellGridPanel>` for both modes. Options:
- Track only local panels in the single-tab cache and keep collab panels out of it.
- Use a mode-aware key such as `{ mode: 'local' | 'collab', sheet }`.
- Keep a `Set<CellGridPanel>` of all live panels for `refreshAll`, plus a separate `Map` for local single-tab reuse.

Whichever behavior is chosen, update the V3.2.c docs and the comment at `cellGridPanel.ts:94-101`, which currently implies collab bypass avoids clobbering but the implementation still overwrites the cache slot.

### M3. `tickPollRemote` does not catch render failures after a successful remote drain

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:58-71`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:226-230`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:292-306`
- `crates/ql-bindings-node/src/lib.rs:509-550`
- `crates/ql-collab/src/session.rs:1535-1548`

Problem:
`classifyPollTick` catches exceptions from `session.pollRemote()` only (`extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:58-71`). In the `merged` branch, `tickPollRemote` logs and calls `this.render()` without a try/catch (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:296-299`). `render()` calls `exportCellSnapshot`, which calls the engine `exportSnapshot` path (`extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:226-230`).

This matters because `pollRemote` can successfully import a Loro blob and return a positive blob count, while a later snapshot export can fail during op-log iteration/deserialization (`crates/ql-bindings-node/src/lib.rs:509-550`). For example, a custom or malicious relay peer could send a Loro document whose `ops` list contains invalid op JSON. `pollRemote` imports the blob at the Loro layer; `exportSnapshot` is where the JSON op decode is forced.

Reproduction:
1. Attach a collab panel to a relay.
2. Have another relay client send a Loro blob that imports successfully but contains an invalid `ops` list entry.
3. The panel's next tick sees `classifyPollTick(...).kind === 'merged'`.
4. `this.render()` throws `[bad_argument] exportSnapshot: op log iter error: ...` outside the classifier's try/catch.

Suggested closure:
Wrap `this.render()` in the `merged` branch. Log the structured error. For `bad_argument` or `session_oplog`, prefer a fatal panel state: stop the poll timer, detach transport, and surface a warning that the local collab session cannot render the merged state. For transient or unknown render errors, at minimum prevent unhandled timer exceptions and avoid repeated log spam.

## LOW

### L1. `dispatchIncomingMessage` accepts malformed `putValue` field shapes after checking only `type`

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:158-179`
- `extensions/quantlab/src/quantbook/session.ts:69-89`
- `extensions/quantlab/test/quantbook-roundtrip.test.ts:2451-2468`

Problem:
The dispatcher correctly drops non-objects, messages without a string `type`, and unknown types (`extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:158-171`). Once `type === 'putValue'`, it casts `raw as PutValueRequest` and reads `sheet`, `row`, `col`, and `rawInput` without runtime validation (`extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:172-179`).

Reproductions:
- `{ type: 'putValue', sheet: 0, row: 0, col: 0, rawInput: 42 }` reaches `parseCellRawInput(42)`, where `raw.trim()` throws a TypeError. The catch block turns it into an `errorReply` with `code: 'unknown'`, not `bad_argument`.
- `{ type: 'putValue', sheet: 0, row: [], col: {}, rawInput: '1' }` reaches `appendPutValueValidated`; the wrapper rejects row/col, but those wrapper errors are not bracket-prefixed, so `parseQuantbookError` again reports `unknown`.

Current tests cover unknown types, missing type, non-object, and null (`extensions/quantlab/test/quantbook-roundtrip.test.ts:2451-2468`), but not wrong field types inside a `putValue` envelope.

Suggested closure:
Add an `isPutValueRequest` runtime guard or explicit checks before parsing:
`typeof req.rawInput === 'string'`, `typeof req.sheet === 'number'`, `Number.isInteger(req.sheet)`, and equivalent row/col checks. Bad envelope shape should produce a bracketed `[bad_argument]` reply or be logged and dropped according to the message contract.

### L2. `exportCellSnapshot` validates only `snapshot_format_version` before trusting the parsed shape

Files:
- `extensions/quantlab/src/quantbook/session.ts:130-145`
- `extensions/quantlab/src/quantbook/types.ts:344-351`

Problem:
`exportCellSnapshot` parses JSON, checks `snapshot_format_version === 1`, and then casts to `QuantbookCellSnapshot` (`extensions/quantlab/src/quantbook/session.ts:134-144`). It does not validate `sheet`, `entries`, `row`, `col`, or the `QuantbookCellValue` variants declared in `types.ts` (`extensions/quantlab/src/quantbook/types.ts:344-351`).

Reproduction:
A mocked or future-skewed native session returning `{"snapshot_format_version":1,"sheet":"x","entries":"not an array"}` passes the helper and surprises callers that rely on `entries` being array-like.

Suggested closure:
For V3.2 this is acceptable only because the engine binding is the trusted producer and tests use the real engine. If this helper becomes a public extension API or consumes persisted JSON, add a small runtime validator for the full snapshot shape and return `[bad_argument]` on drift.

## Out of scope (deferred to V3.x)

### D1. Tighten inline style CSP

Current CSP uses `style-src 'unsafe-inline'` because CSS is emitted in an inline `<style>` tag (`extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:80-111`). This is not strictly inherent to VS Code theme variables; the same CSS could live in an extension resource loaded through `asWebviewUri`, or the style tag could carry a nonce with `style-src 'nonce-...'` if VS Code webviews support the intended shape consistently. Not load-bearing for V3.2 because all dynamic cell content is still escaped, and script execution is nonce-scoped.

### D2. Decide which non-transport poll errors are fatal

`classifyPollTick` groups every non-`transport_closed` throw as `{ kind: 'error' }`, and the panel logs and skips the tick (`extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:65-70`, `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:304-306`). That is acceptable for a one-off malformed transport blob, because `poll_remote_with_limit` drains before attempting merge and returns `Err` on merge failure (`crates/ql-collab/src/session.rs:1535-1548`). V3.x should still define which codes are fatal (`session_oplog`, repeated `bad_argument`, render failures) rather than treating all of them as "skip this tick."

### D3. Preserve the input after Enter if a slow failure arrives after blur

On commit, `endEdit(true)` intentionally leaves the input in place by restoring `activeInput` and `activeCell` after posting the message (`extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:221-238`). A subsequent blur before the host responds still calls `endEdit(false)` because `activeInput === input` remains true (`extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:275-280`). With localhost latency this is hard to notice, but under a slower host a failed commit could return `errorReply` after the input has already been canceled, contrary to the "keep input visible for correction" UX. V3.x can add a `commitInFlight` flag or disable blur-cancel after Enter.

### D4. Keep relay constants configurable in a future production surface

The V3.2 demo port is consistent today (`7117` in both IDE and relay binary), but it is still duplicated (`extensions/quantlab/src/quantbook/multiWindowDemo.ts:49-57`, `crates/ql-collab-ws/examples/relay-server.rs:43-59`). This is acceptable for localhost V3.2. A production grid should move relay URL/port into a shared config or user setting.

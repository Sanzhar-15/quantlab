## LOW

### LOW-1

Subject: IronCalc parity comments overstate behavior and omit the intentional coercion divergence

Where: `crates/ql-functions/src/distribution_fns.rs:6`; `crates/ql-functions/src/registry.rs:814`; `crates/ql-functions/tests/coverage.rs:655`

Detail: The implementation is not a verbatim IronCalc port. IronCalc uses `get_number_no_bools` for numeric distribution arguments, rejecting Boolean `x`/`mean`/`sd`/`probability`; this implementation uses `to_number_strict`, which accepts Booleans as `0/1`. That is the right Excel-canonical behavior per the project convention, but the comments say "port IronCalc's impls verbatim" / "matches IronCalc's behavior exactly" / "statrs backing matching IronCalc." Also, local IronCalc maps parameterized `Normal::new(mean, std_dev)` construction failures in `NORM.DIST` and `NORM.INV` to `#NUM!`, while only the impossible standard-normal constructor failure in `NORM.S.DIST` / `NORM.S.INV` maps to `#ERROR!` (`.references/ironcalc/base/src/functions/statistical/normal.rs:41`, `:92`, `:131`, `:174`). The current docs blur those cases.

Recommendation: Reword the comments to say the numerical backend matches IronCalc through `statrs 0.18.0`, while documenting the engine-level divergences explicitly: Boolean numeric args are Excel-coerced to `0/1`, and impossible standard-normal constructor failures are normalized to `#NUM!` instead of IronCalc's `#ERROR!`.

Severity rationale: Runtime behavior is correct, but the misleading comments are exactly where future distribution ports will look for precedent. This can cause regressions toward IronCalc's stricter Boolean behavior or incorrect error-class assumptions.

### LOW-2

Subject: NORM.INV lacks a text-argument regression test despite being part of the requested coverage shape

Where: `crates/ql-functions/src/distribution_fns.rs:400`

Detail: `NORM.DIST`, `NORM.S.DIST`, and `NORM.S.INV` each have a text-argument `#VALUE!` test. `NORM.INV` has anchor, round-trip, domain, error-propagation, and arity tests, but no `Value::Text(...) -> #VALUE!` test for any of its three numeric arguments. The implementation currently handles this through `to_number_strict`, so this is a test gap rather than a behavior bug.

Recommendation: Add a `norm_inv_text_arg_is_value_error` unit test. A single text probability case is enough to pin the common coercion path; testing text mean or text standard deviation as well would better match Microsoft's "any argument is nonnumeric" rule.

Severity rationale: Low because the current code is correct and the shared coercion helper is well established. It still leaves an explicit Excel error-class requirement unpinned for one of the four new functions.

### LOW-3

Subject: NORM.S.INV error-propagation test uses `#NUM!`, which does not prove propagation

Where: `crates/ql-functions/src/distribution_fns.rs:546`

Detail: `norm_s_inv_error_arg_propagates` passes `Value::Error(ErrorValue::Num)` and expects `#NUM!`. That would also pass if the implementation accidentally converted every invalid/error input into a domain `#NUM!`. The other distribution error-propagation tests use distinguishable errors (`#REF!` / `#DIV/0!`), which actually prove propagation.

Recommendation: Change this test input to a distinguishable error such as `Value::Error(ErrorValue::Ref)` or `Value::Error(ErrorValue::DivZero)`.

Severity rationale: Low because implementation is correct through `to_number_strict`; the issue is only that one regression test is weaker than it appears.

# Codex audit - W5-D-7

## HIGH

### HIGH-001

- **Subject:** XIRR Newton can return a non-root for guesses extremely close to `-1`
- **Where:** `crates/ql-functions/src/financial_fns.rs:1511`
- **Detail:** `xirr_newton` accepts convergence solely when `abs(new_xirr - xirr) < 1e-7`, without checking the XNPV residual. Near the singularity at `rate = -1`, the Newton step can be tiny even while the residual is enormous. Repro at the kernel level: `values=[-100, 1000]`, `dates=[40000, 40365]`, `guess=-0.999999999`. The true one-year root is exactly `9.0` because `-100 + 1000/(1+r) = 0`; the first Newton step returns about `-0.999999998` because the step is only about `1e-9`, and `compute_xnpv` at that returned rate is still about `5e11`, not zero. Since `compute_xirr` immediately trusts `Ok(r)` from Newton, the bisection fallback is bypassed.
- **Recommendation:** Require a residual check before accepting Newton convergence, e.g. compute `compute_xnpv(new_xirr, values, dates)` and only return when the residual is below an absolute or cash-flow-scaled tolerance. Otherwise keep iterating or fall back to bisection. Add a regression test with a near-`-1` guess and a closed-form two-cash-flow schedule.
- **Severity rationale:** High because a user-supplied but valid `guess > -1` can produce a wildly wrong numeric XIRR rather than `#NUM!` or the actual root. The loops are bounded, so this is not a hang, but it is a financial correctness failure.

## MEDIUM

### MEDIUM-001

- **Subject:** Date serial `0` is accepted as valid for XNPV/XIRR
- **Where:** `crates/ql-functions/src/financial_fns.rs:1613`
- **Detail:** `MIN_DATE_SERIAL` is `0.0`, so `validate_xnpv_xirr_dates` accepts serial `0` for both functions. That conflicts with IronCalc's `MINIMUM_DATE_SERIAL_NUMBER = 1` in `.references/ironcalc/base/src/constants.rs:24`, and with the local date-system contract in `crates/ql-types/src/date.rs:19`, which says serials `1..=2_958_465` map to real dates and serial `0` is the `1/0/1900` display oddity, not a real YMD. The XIRR impact is broader because blank date cells are collected as `0.0`; with the current lower bound, a blank first date can be treated as a valid schedule anchor.
- **Recommendation:** Change the lower bound to `1.0` unless the project intentionally wants to diverge from both IronCalc and `ql-types::date`; if so, document that divergence in code and matrix, and add explicit tests for serial `0`. Add XNPV/XIRR tests that serial `0` and blank dates reject with `#NUM!` if adopting the IronCalc/local date contract.
- **Severity rationale:** Medium because invalid dates can flow into numeric financial results rather than being rejected. It is an off-by-one domain bug, not a crash.

### MEDIUM-002

- **Subject:** XNPV date text/bool errors are pinned as `#NUM!` instead of IronCalc's date-arg `#VALUE!`
- **Where:** `crates/ql-functions/src/financial_fns.rs:1574`
- **Detail:** `collect_xnpv_range` hardcodes `ErrorValue::Num` for every blank or non-number range cell, and `xnpv` reuses it for both `values` and `dates`. IronCalc distinguishes the two XNPV array args: values call `get_array_of_numbers_xpnv(..., Error::NUM)`, while dates call `get_array_of_numbers_xpnv(..., Error::VALUE)` at `.references/ironcalc/base/src/functions/financial.rs:897` and `:901`. Empty cells still become `#NUM!` via IronCalc's empty-cell handler, but non-number date cells such as text/bool become `#VALUE!`. The new `xnpv_text_in_dates_is_num_error` test pins the opposite behavior.
- **Recommendation:** Parameterize the XNPV collector's non-number error, or add separate `collect_xnpv_values_range` and `collect_xnpv_dates_range` helpers. Keep empty-cell rejection as `#NUM!`, but return `#VALUE!` for non-number cells in the dates range. Update the unit test, coverage rationale, and compat matrix text accordingly.
- **Severity rationale:** Medium because this is an Excel/IronCalc error-class parity drift in a newly-added compatibility function. It returns an error, but the wrong sigil matters for spreadsheet compatibility and downstream tests.

## LOW

### LOW-001

- **Subject:** XIRR fallback paths are not directly tested
- **Where:** `crates/ql-functions/src/financial_fns.rs:3594`
- **Detail:** The 12 new XIRR tests cover the canonical anchor, round-trip, sign validation, optional guess, empty/text semantics, length/date-order checks, error propagation, and arity. None force Newton to fail and then prove the bisection path on `[-0.9999, 100]` works, and none exercise the final `guess=200` Newton probe for roots above `100`. This is a gap relative to the risk profile of this batch and to the existing IRR test `irr_bisection_fallback_when_newton_diverges`.
- **Recommendation:** Add at least one XIRR bisection regression with an intentionally divergent guess and an irregular-date fixture whose true root is known, plus a separate fixture where the root is above `100` so the `guess=200` branch is exercised. Assert both the returned rate and `compute_xnpv(rate, values, dates) ≈ 0`.
- **Severity rationale:** Low because the implementation paths exist and the loop bounds prevent hangs, but future edits could break fallback behavior while the current suite remains green.

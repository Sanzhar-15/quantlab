## MEDIUM

### MEDIUM-001

Subject: Quartile index coercion can normalize invalid `quart` values to `q = 0`

Where: `crates/ql-functions/src/range_fns.rs:1750`, `crates/ql-functions/src/range_fns.rs:1829`, `crates/ql-functions/src/range_fns.rs:1861`

Detail: `extract_quartile_q` accepts `Value::Number(n)` and immediately returns `n.trunc() as i64`. That bypasses the finite-number guard used by the numeric range path (`collect_numbers_strict` -> `coerce_numeric` -> `to_number_strict_skip_blank` -> `sanitize_f64`) and also differs from the percentile `k` path, where NaN is rejected by the range containment check. In Rust, casting `f64::NAN.trunc()` to `i64` yields `0`, so `QUARTILE.INC(array, NaN)` would pass the `0..=4` check and return the minimum instead of an error. The same extraction also makes `quart` in `(-1, 0)` become `0`, so `QUARTILE.INC(array, -0.5)` returns the minimum; the prompt explicitly called out this truncation-vs-INT/bounds ambiguity as a Microsoft-compatibility risk.

Recommendation: Sanitize the numeric `quart` argument before casting, returning `#NUM!` for non-finite values. Resolve the Excel fixture for negative fractional `quart` values and then pin it explicitly. If the target is "negative raw quart is invalid", reject `n < 0.0` before integer coercion, or use the verified Excel/LibreOffice integer conversion rule consistently.

Severity rationale: Medium because this can silently return a plausible numeric result for invalid input rather than surfacing an error. The NaN case is defensive, but the `-0.5` case is ordinary finite user input and affects QUARTILE.INC's min path.

## LOW

### LOW-001

Subject: E2E alias-parity test only checks presence

Where: `crates/ql-exec/tests/region_mul2_e2e.rs:711`

Detail: The test comment says it verifies that `PERCENTILE` registers to the same function as `PERCENTILE.INC` and `QUARTILE` registers to `QUARTILE.INC`, but the assertions at lines 716-729 only check `lookup_range_aware(...).is_some()`. A future regression that mapped `PERCENTILE` to `percentile_exc` or `QUARTILE` to `quartile_exc` would still pass this e2e test as long as all six names remained registered.

Recommendation: Strengthen the test by comparing returned function pointers with `std::ptr::fn_addr_eq`, or by invoking the alias and `.INC` functions on inputs where `.INC` and `.EXC` produce different results.

Severity rationale: Low because the current registry lines are correct, so runtime behavior is not broken. The risk is that the test does not protect the alias contract it documents.

### LOW-002

Subject: Scalar argument edge coverage is thinner than the stated test contract

Where: `crates/ql-functions/src/range_fns.rs:4814`, `crates/ql-functions/src/range_fns.rs:4939`, `crates/ql-functions/src/range_fns.rs:5085`

Detail: `PERCENTILE.INC` pins `Error` and text handling for the scalar `k` argument, but `PERCENTILE.EXC` only pins range-side error/text behavior and arity. `QUARTILE.INC` and `QUARTILE.EXC` likewise pin range-side text/error behavior, but do not pin scalar `quart` text, scalar `quart` error propagation, non-finite `quart`, or the `quart` in `(-1, 0)` edge called out in the audit prompt. This leaves the riskiest coercion branch in `extract_quartile_q` under-covered.

Recommendation: Add targeted tests for `PERCENTILE.EXC(..., #N/A)`, `PERCENTILE.EXC(..., "text")`, `QUARTILE.INC/EXC(..., #N/A)`, `QUARTILE.INC/EXC(..., "text")`, and the resolved behavior for `QUARTILE.INC(..., -0.5)` and `QUARTILE.INC(..., NaN)` or equivalent internal non-finite construction.

Severity rationale: Low because the common value paths, interpolation formulas, empty handling, range text/error handling, and registration are covered. The missing cases matter because they are exactly where invalid scalar inputs enter helper coercion.

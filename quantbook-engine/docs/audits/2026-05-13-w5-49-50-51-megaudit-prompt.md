### CONCERN-2: Determinism of build_range_supplemental

`schedule_dirty` drains `self.dirty: HashSet<NodeId>` into `dirty_vec` then sorts. Good. But `dirty_addrs` is built from `dirty_vec.iter().filter_map(...)`. Iteration order preserved. The inner `for &(g, ...) in &dirty_addrs` iterates in the same order. So `supplemental[F]` ends up with G's in sorted-by-NodeId order.

BUT: the OUTER `for &(f, fs, _, _) in &dirty_addrs` is also in sorted order. So the HashMap's insertion order is sorted-by-F-NodeId. Determinism downstream of HashMap depends on iteration order (HashMap is randomized). The CONSUMER of `supplemental` is `tarjan_dfs`, which looks up by key (`supplemental.get(&v)`) — so the randomized iteration order doesn't matter. Only the per-entry Vec order matters, and that IS sorted. ✓

But there's a subtle point: in Tarjan, the order of children visited at each frame affects the resulting SCC discovery order. For a deterministic schedule output, the per-frame child order must be deterministic. Real outgoing edges come from `Vec<NodeId>` (insertion order — deterministic). Supplemental edges come from `supplemental[v]` which IS sorted. So combined order = (real edges in insertion order) ++ (supplemental in sorted order). Deterministic.

UNLESS: real edges themselves are NOT in deterministic insertion order across runs (e.g., the extract_and_register_deps walk order depends on a HashMap iteration). The walk_plan_for_deps walker is recursive over ExprPlan AST — fully deterministic. Then `deduplicate` uses `HashSet` + `retain` — retain preserves order. So insertion order is the AST walk order. Deterministic. ✓

But hold on — re-bind: `clear_outgoing` drains and `extract_and_register_deps` re-adds. So if a formula's plan is identical, the new outgoing list should equal the old. Determinism test (`determinism_rebind_same_plan_same_edges` in graph.rs::tests) verifies this. ✓

OK determinism looks correct. **But please double-check this independently — I might be missing a subtle case.**

### CONCERN-3: Self-edge in supplemental

`build_range_supplemental` does NOT exclude `g == f`. This is intentional for `A1 = SUM(A1:A1)` self-range cycles. Test `self_range_cycle_via_supplemental` confirms this works.

But what about `A1 = SUM(A1:A10)` where A1 is the cell that contains the SUM formula and A1 is inside the SUM range? Excel: this is a circular reference. My implementation: supplemental[A1] = [A1] (since A1 is in A1:A10). Tarjan emits A1 as cycled. ✓

What about a case where the range covers F but F shouldn't be self-referencing? E.g., F is at C1 with `=SUM(A1:Z1)` — F is NOT in the range (column C is in A1:Z1 columns). The range covers (row 1, cols A..Z). F is at (row 1, col C) → IS in the range. supplemental[F] = [F] if F is dirty. Tarjan emits F as cycled. **WAIT** — is that wrong? Excel would treat `=SUM(A1:Z1)` at C1 as a self-cycle because C1 is in A1:Z1. ✓ this is correct.

OK self-edge handling looks correct.

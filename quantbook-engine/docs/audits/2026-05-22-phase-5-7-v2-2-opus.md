# Phase 5.7 V2.2 — Opus adversarial audit lane

## Scope

V2.2 adds five new napi methods on `CollabSession` (`flushDeltaToTransport`,
`pollRemoteWithLimit`, `transportLastError`, `setAutoFlushPolicy`,
`autoFlushPolicy`) + two helper fns (`parse_auto_flush_policy`,
`auto_flush_policy_to_string`) + an `isAutoFlushPolicy` strict-camelCase
type guard on the IDE side + a new `'unknown'` forward-compat sentinel
on the JS return type for `autoFlushPolicy()` + 19 new mocha tests.

This lane checks: strict/loose parser asymmetry, `'unknown'` sentinel
forward-compat hazards, the empirically-discovered "first flush after
attach always sends" contract, cross-platform usize behavior in
`pollRemoteWithLimit`, lossy `transportLastError` projection, Rule 4
hygiene on the new code, and the test-as-spec discipline applied in
the V2.2 mocha additions.

## Verdict

**PASS-WITH-FINDINGS.** V2.2 is shippable but carries TWO HIGHs that
should close in-cycle. Findings cluster in three areas: (1) the
TS/engine policy-parser asymmetry is documented and tested but the
documentation underplays the size of the IDE-side footgun; (2) the
`'unknown'` sentinel for forward-compat is a silent fall-through that
violates the no-fallback rule; (3) one V2.2 mocha test pins a
behavioral spec via `as`-cast that uses TS narrowing as a load-bearing
silencer rather than as a contract.

Rule 4: zero new negative-trait claims in V2.2. The pre-existing
`!Sync` claim for `CollabSession` carries over from V1 / V2.1 with no
modification.

The V2.1 findings landscape was H=2, M=4, L=5, O=4. V2.2 is similar
shape, with the new surface introducing two new HIGHs (1 carried-
forward + 1 new from `'unknown'` sentinel) while closing 2 of V2.1's
MEDIUMs in the natural course of V2.2 work (MEDIUM-3 transport error
binding shipped, MEDIUM-4 `loopbackTransportPair` helper unchanged but
contextually safer now that `transportLastError` exists).

## HIGH

### HIGH-1: `autoFlushPolicy()` returning `'unknown'` is a silent fall-through that violates the no-fallback rule — JS code that does `policy === 'onAppend'` falls into the disabled branch when a future engine variant ships ahead of the binding

**Repo**: engine + IDE.
**File:line**: `crates/ql-bindings-node/src/lib.rs:666-677`
(`auto_flush_policy_to_string` catch-all returns `"unknown"`) +
`quantlab/extensions/quantlab/src/quantbook/types.ts:225`
(`autoFlushPolicy(): AutoFlushPolicy | 'unknown'`).

**Specific issue**: per CLAUDE.md no-fallback rule ("NEVER implement
fallbacks. If something fails, it MUST fail loudly and visibly"), the
catch-all arm of `auto_flush_policy_to_string`:

```rust
fn auto_flush_policy_to_string(p: CoreAutoFlushPolicy) -> String {
    match p {
        CoreAutoFlushPolicy::Disabled => "disabled".to_string(),
        CoreAutoFlushPolicy::OnAppend => "onAppend".to_string(),
        _ => "unknown".to_string(),
    }
}
```

returns a sentinel string that JS callers will silently mishandle.
Trace the realistic V2.3+ scenario:
1. Engine adds `CoreAutoFlushPolicy::Threshold(usize)` (already
   foreshadowed in `session.rs:213-216`: "V2 V3 will add a `Threshold`
   variant for byte-budget-based batching").
2. IDE ships V2.2 binding without V2.3 changes — i.e., this catch-all
   fires.
3. IDE config logic that branches on policy reads
   `session.autoFlushPolicy()` and does `if (policy === 'onAppend') {
   ... } else { /* disabled-or-unknown */ }`.
4. The Threshold session SILENTLY falls into the disabled branch.
   Calls that should trigger auto-flush fan-out logic don't. No error
   surfaces.

The docstring comment at lib.rs:670-674 even acknowledges this as
intentional: "better than panicking at the FFI boundary." But that
choice optimizes the wrong axis. The CLAUDE.md rule says: errors must
be visible. A `napi::Error::from_reason(format!("AutoFlushPolicy::{:?}
unknown to this binding -- engine ahead of binding; upgrade
ql-bindings-node"))` IS the right shape — the IDE will see a clean JS
Error, the message is actionable, and there's no silent fall-through.

The Display impl on `CoreAutoFlushPolicy` is available (it derives
`Debug`), so the message can include enough detail to identify which
new variant the engine just shipped. This makes upgrades fail-fast at
the right boundary — load time or first auto-flush-policy read — not
at the unobservable "no flush happened" surface.

This is the *exact* pattern that the V1 megaudit caught: a silently-
recovered boundary that hides upstream skew. V1 fixed the loader's
"missing exports" path (loader throws loudly). V2.2 introduces a new
silently-recovered boundary at the wrong layer.

There's also a TS-side asymmetry: `setAutoFlushPolicy` REJECTS unknown
inputs cleanly, but `autoFlushPolicy()` PRODUCES an unknown output
silently. The reader-writer pair should be symmetric — both should
throw on unknown.

**Closure recommendation**: **FIX NOW** — change the catch-all to
throw, and remove the `'unknown'` member from the TS type union.

Engine side:
```rust
fn auto_flush_policy_to_string(p: CoreAutoFlushPolicy) -> Result<String> {
    match p {
        CoreAutoFlushPolicy::Disabled => Ok("disabled".to_string()),
        CoreAutoFlushPolicy::OnAppend => Ok("onAppend".to_string()),
        // Per CLAUDE.md no-fallback rule: surface engine/binding
        // version skew as a JS Error so consumers see it immediately
        // instead of silently falling into the wrong policy branch.
        other => Err(Error::from_reason(format!(
            "AutoFlushPolicy variant {other:?} not known to this binding; \
             rebuild ql-bindings-node against the current engine"
        ))),
    }
}
```

And both call sites (`auto_flush_policy` getter + `set_auto_flush_policy`
return) propagate the Result. TS side: `autoFlushPolicy(): AutoFlushPolicy`
(no `'unknown'`), drop the JSDoc paragraph about forward-compat
sentinels. Drop the "unknown" arm from `parse_auto_flush_policy`'s
JS-side handling — but note that `parse_auto_flush_policy` never
emitted `'unknown'`; only `auto_flush_policy_to_string` did, so only
the latter needs the Result wrap.

**Why HIGH**: this is a no-fallback rule violation, the closure is
~10 lines + one test rewrite, and the alternative is a silent-skew
bug class that's invisible at integration test time (until you ship
a new engine variant).

### HIGH-2: The `setAutoFlushPolicy accepts aliases (Disabled, OnAppend, on-append)` mocha test uses `as` casts to bypass TS narrowing — this pins the engine's loose-parser contract via TS-type-system-defeat, not via an explicit "API allows engine aliases" type or runtime path

**Repo**: IDE.
**File:line**: `extensions/quantlab/test/quantbook-roundtrip.test.ts:812-824`.

**Specific issue**: the test does:

```ts
test('setAutoFlushPolicy accepts aliases (Disabled, OnAppend, on-append)', () => {
    const session = createSession(1n);
    // `as` casts: TS type narrows to the camelCase union; the engine
    // alias acceptance is engine-side behavior.
    assert.doesNotThrow(() => session.setAutoFlushPolicy('Disabled' as 'disabled'));
    assert.doesNotThrow(() => session.setAutoFlushPolicy('OnAppend' as 'onAppend'));
    assert.doesNotThrow(() => session.setAutoFlushPolicy('on-append' as 'onAppend'));
    ...
});
```

The `as 'disabled'` cast is TS's escape hatch for "trust me, this is
actually the type." Using it as a routine test idiom has two problems:

1. **It pins the wrong contract.** The TS signature is
   `setAutoFlushPolicy(policy: AutoFlushPolicy): AutoFlushPolicy` where
   `AutoFlushPolicy = 'disabled' | 'onAppend'`. The test
   ROUTINE-VIOLATES that signature in 3 calls per run. If the engine
   later TIGHTENS the parser (e.g., rejects `'Disabled'` because some
   misuse was found), the TS-side test STILL TYPE-CHECKS — the `as`
   cast bypasses the check — and the runtime assertion catches the
   regression. But because the type system doesn't see the violation,
   a developer reading the type union assumes camelCase-only is the
   contract. The test is then SECRETLY contradicting the public type.

2. **The cast pattern is contagious.** A new developer who needs to
   call `setAutoFlushPolicy('always' as 'disabled')` in IDE production
   code — say, the IDE accepts user input from a config UI and passes
   it through unsanitized — has a worked example in the test file. The
   `as`-cast escape hatch becomes the "Rust didn't reject it so don't
   ask TS" idiom, defeating the purpose of `isAutoFlushPolicy` (which
   exists exactly to gate this kind of input at the TS boundary).

The correct shape is to widen the engine call's input signature for
this codepath. Two options:

**Option A**: add a separate `setAutoFlushPolicyRaw(policy: string):
AutoFlushPolicy` method that explicitly accepts engine aliases. The
IDE-side validated wrapper uses `setAutoFlushPolicy` (strict-typed);
the raw version is for test scenarios and any future engine-alias
migration. Then the test:

```ts
assert.doesNotThrow(() => session.setAutoFlushPolicyRaw('Disabled'));
assert.doesNotThrow(() => session.setAutoFlushPolicyRaw('on-append'));
```

**Option B**: change the TS signature on `setAutoFlushPolicy` to
`(policy: AutoFlushPolicy | string): AutoFlushPolicy` — explicitly
acknowledging that the parameter is wider than the canonical type.
This is the simpler change but it removes TypeScript's load-bearing
narrowing of `policy` for ALL callers.

Option A is cleaner. The TS surface stays strict; the engine's loose-
parser is reachable via a clearly-named method that doesn't lie about
its acceptance contract.

The "isAutoFlushPolicy strict guard rejects engine aliases" test at
lines 845-857 makes the right contractual statement — the type guard
should be the only path into `setAutoFlushPolicy`. But the aliases
test contradicts this by routine-casting around the guard.

**Closure recommendation**: **FIX NOW** by option A. Add
`setAutoFlushPolicyRaw(policy: string): AutoFlushPolicy` to the napi
class (one-line: `pub fn set_auto_flush_policy_raw(&mut self, policy:
String) -> Result<String> { self.set_auto_flush_policy(policy) }` —
they share the same Rust body). Update types.ts + tests.

Alternatively, ACCEPT the asymmetry in-cycle as documented-and-pinned
behavior (the test does pin runtime correctness; the `as`-cast is
just ugly) and CLOSE the discomfort by adding a one-line ESLint
suppression with a comment, e.g.,
```ts
// eslint-disable-next-line @typescript-eslint/no-explicit-any
// Engine accepts loose aliases; tests pin this runtime behavior
// without polluting the public type signature.
assert.doesNotThrow(() => session.setAutoFlushPolicy('Disabled' as 'disabled'));
```
to flag the pattern as deliberate-special-case rather than routine.

**Why HIGH**: this violates the "test-as-spec" discipline that V1 and
V2.1 closures relied on. Audit Rule "each test pins ONE specific
contract" — this test pins TWO contracts (runtime acceptance + TS-
escape-hatch use) and conflates them. V2.3+ tests will copy this
pattern; an IDE developer will write `session.setAutoFlushPolicy(some
UserInput as 'onAppend')` in production code because the test file
modeled the pattern.

## MEDIUM

### MEDIUM-1: `setAutoFlushPolicy` takes `String` (owned, not `&str`) at the napi boundary — every call allocates and immediately drops a String for a 7-character config value. Not hot-path today but napi-rs natively supports `&str`

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:634`.

```rust
pub fn set_auto_flush_policy(&mut self, policy: String) -> Result<String> {
    let policy_enum = parse_auto_flush_policy(&policy)?;
    ...
}
```

**Specific issue**: napi-rs 3.x supports `&str` parameters via
`napi::JsString` automatic coercion (per napi-rs 3.9.0
`bindgen_runtime/types/string.rs`). Taking `String` here means every
JS-side `session.setAutoFlushPolicy('onAppend')` allocates a fresh
String on the napi heap, calls into Rust, and immediately drops it
after `parse_auto_flush_policy(&policy)` borrows it as `&str` anyway.

For V2.2's expected call frequency (config-change rare, maybe once
per session) this is invisible noise. But it sets a pattern: V2.3+
will likely add more string-parameter methods (Transport URL,
HandshakeFailed reason strings, custom error codes). If those copy
this idiom they ship together as a "every string call allocates"
class. Switching now is one-line cheap.

There's a second, smaller issue: `parse_auto_flush_policy` takes
`&str` and returns owned `Result<CoreAutoFlushPolicy>`, then the
caller drops `policy: String` at function end. If instead we wrote:

```rust
pub fn set_auto_flush_policy(&mut self, policy: &str) -> Result<String> {
    let policy_enum = parse_auto_flush_policy(policy)?;
    ...
}
```

the JS-to-Rust string is borrowed across napi-rs's lifetime — no copy
to Rust-heap, no drop at end. Microoptimization at this call site,
but a forward-compat improvement.

Note: the return is correctly `String` (the converted policy string
that goes back to JS — napi-rs owns it).

**Closure recommendation**: V2 BACKLOG ITEM. One-line change but not
in-cycle critical. Should land in V2.3 cleanup. Calling out as a
quality signal for the larger Transport binding surface.

### MEDIUM-2: `pollRemoteWithLimit` casts validated `u32 → usize` always-safe, but the engine's `DEFAULT_POLL_REMOTE_LIMIT = 64` lives in `usize`-domain; the binding silently caps at `u32::MAX` on 64-bit systems where usize is u64. No test pins the cap, no docstring documents it.

**Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:581-588`.

**Specific issue**: the chain is:
1. JS Number → f64 (napi raw)
2. `validate_u32_index` → u32 (capped at u32::MAX = 4294967295)
3. `as usize` cast → usize (always safe: u32 ⊆ u64-or-u32 usize)
4. `poll_remote_with_limit(limit_u32 as usize)` → engine method

But the REVERSE direction is the audit concern. The engine returns
`Result<usize, _>`. The binding then `u32::try_from(blobs_drained).unwrap_or(u32::MAX)`:

```rust
Ok(u32::try_from(blobs_drained).unwrap_or(u32::MAX))
```

On 64-bit systems usize is u64. If a (future) engine ever returned
`usize > u32::MAX` blobs from a single `poll_remote_with_limit` call,
the binding SILENTLY clamps to u32::MAX. This is a
fallback-pattern that masks the bound. Per CLAUDE.md no-fallback:
"NEVER `value || default` patterns that mask missing config or broken
state."

Two practical realities:
- The engine's current cap is `DEFAULT_POLL_REMOTE_LIMIT = 64`. The
  binding's `validate_u32_index` enforces u32::MAX upper bound on
  user-passed `limit`. So under realistic V2.2 usage, the return
  value cannot exceed `limit_u32` which is `<= u32::MAX`. No clamp
  fires in practice.
- However, the JS caller could in principle pass `limit = u32::MAX`
  (4 billion). The engine's `poll_remote_with_limit(usize::4B)` would
  consume up to 4B inbox blobs from a transport. The return value
  is bounded by the actual blobs-drained, which CAN'T exceed limit,
  which CAN'T exceed u32::MAX. So the unwrap_or(u32::MAX) clamp
  ACTUALLY can't fire — every reachable `blobs_drained` value is
  guaranteed `<= u32::MAX`.

So the clamp is dead code today, BUT (a) it's a `unwrap_or` pattern
that violates the no-fallback rule visually, (b) it could become
load-bearing if a future binding adds `pollRemoteUnlimited()` or
similar without a user-provided cap, and (c) the docstring at lines
570-574 mentions the cross-platform usize concern but doesn't
actually pin which side of the boundary caps.

Specifically the docstring says: "Validated finite + non-negative +
integer + in `usize` range (on 64-bit systems usize = u64; we cap at
u32::MAX for cross-platform safety)." But the code validates u32
range (`validate_u32_index`), not usize range. The doc text is
incorrect — on 32-bit Windows where usize = u32, validating u32
range == validating usize range, but on 64-bit linux/macOS where
usize = u64, the binding caps WELL BELOW usize range. The "cross-
platform safety" framing is misleading: the actual reason for the
u32 cap is "u32 is what JS Number can losslessly represent."

**Closure recommendation**: V2 BACKLOG ITEM. Two small fixes:

1. Replace `u32::try_from(blobs_drained).unwrap_or(u32::MAX)` with
   `u32::try_from(blobs_drained).map_err(|_| Error::from_reason(format!(
   "pollRemoteWithLimit drained {} blobs; result exceeds u32::MAX",
   blobs_drained)))?`. This makes the impossible-today case fail
   loudly if the engine's invariant ever changes.

2. Fix the docstring at lines 569-574 to say: "Validated finite +
   non-negative + integer + in `u32` range. JS Number can represent
   any non-negative integer up to 2^53 losslessly; we further cap at
   u32::MAX (≈4.3 billion) because the engine treats limits in usize
   and the bound matches `pollRemoteUnlimited` semantics. On 64-bit
   targets usize is u64, so passing `u32::MAX` does NOT max out the
   engine — that's intentional, see V2.3+ for unbounded variants."

Same issue applies to `mergeBytes` (`u32::try_from(count).unwrap_or(u32::MAX)`,
line 357) and `opCount` (line 371) and `pendingOpCount` (line 389)
— V1 inherited. V2.1 audit MEDIUM-3 noted the binding's error
mapping is lossy; this is the symmetric issue for numeric returns.

**Why MEDIUM not LOW**: applies to a method that V2.2 explicitly
adds; the right time to close is now while the IDE consumer of
`pollRemoteWithLimit` hasn't ossified around the clamp. Not HIGH
because the clamp is unreachable today.

### MEDIUM-3: `flushDeltaToTransport` first-after-attach behavior was empirically discovered during V2.2 test writing — the contract is documented in the docstring but the discovery path suggests V2.3+ callers will hit the same surprise. There's no `hasPendingFlush()`-paired idiom that makes the "first flush always sends" path observable from JS.

**Repo**: engine + IDE.
**File:line**: `crates/ql-bindings-node/src/lib.rs:529-555` (napi
docstring) + `crates/ql-collab/src/session.rs:1347-1380` (engine
implementation).

**Specific issue**: V2.2's mocha test discovered this:

> "First flushDeltaToTransport after attach ALWAYS sends even on
> empty log. Test assumption that 'no ops appended → no-op' was
> wrong: attach sets last_flushed_vv = None, idempotency guard short-
> circuits only when Some(last_vv) == current_vv. With None it
> always proceeds."

The plan note at `.plans/_active.md:99-101` calls this out. The
napi docstring at lib.rs:541-546 ALSO mentions it ("Per Phase 5.5 V2
V3 step 1 contract: attach_transport resets...").

But neither layer captures the discovery surprise. Specifically:
- `hasPendingFlush()` returns `current_vv != last_flushed_vv.unwrap_or_default()`.
- After `attach_transport`, `last_flushed_vv = None` → `unwrap_or_default()
  = default VV`. So `hasPendingFlush()` returns `current_vv != default
  VV`.
- For an empty log (just `new()`), `current_vv == default VV`, so
  `hasPendingFlush() = false`.
- But `flushDeltaToTransport()` STILL fires the send, because the
  idempotency guard only short-circuits when `Some(last_vv) ==
  current_vv` — None doesn't satisfy that.

So `hasPendingFlush() = false` while `flushDeltaToTransport()` is
NOT a no-op. That's the inversion: the helper that's documented to
predict whether flushing is meaningful is OUT OF SYNC with the
flush method's idempotency guard, in the specific window of
"attached, no mutations yet."

Trace this from an IDE consumer's perspective:
1. Create session A, attach transport, no ops yet.
2. IDE thinks "nothing to flush" because `hasPendingFlush() = false`.
3. IDE skips the flush.
4. Peer B never sees anything.
5. IDE adds the first op → `hasPendingFlush() = true` → flush →
   `flushDeltaToTransport()` SENDS, peer B drains, peer B gets
   the ops.

In this trace, step 5 sends the right thing (the new op). So in
practice the bug is invisible. But consider:
1. Create session A from snapshot with 1000 ops, attach transport.
2. `hasPendingFlush()` returns TRUE (last_flushed_vv = None, current_vv
   = non-trivial). IDE knows it should flush.
3. IDE flushes; this is the "send the baseline" path. Bytes propagate.
4. IDE sets `OnAppend` policy.
5. From here, every append auto-flushes idempotency-correctly.

So fromSnapshot + attach is fine. But contrast:
1. Create session A, attach transport, NO ops.
2. `hasPendingFlush()` returns FALSE. IDE doesn't flush.
3. IDE sets `OnAppend`.
4. IDE creates session B, attaches the OTHER end of pair.
5. Session B looks at `hasPendingFlush()` — also false (no ops).
6. Session B initiates a handshake by appending. Auto-flush sends.
7. Session A polls, drains, merges. `hasPendingFlush()` now true
   (Loro merged B's ops; current_vv != default). Auto-flush fires
   on B's policy IF A is also OnAppend.

The hazard is exactly: IDE consumers using `hasPendingFlush()` as a
proxy for "should I flushDelta?" get inconsistent answers vs the
actual idempotency guard. The discovery of this gap during V2.2
test-writing suggests it'll bite V2.3+ implementers.

A `hasPendingFlush()` mocha test (V1) at line 122-123 documents that
it returns `true` AFTER `appendPutValue`, but no test pins the
post-attach-pre-mutation state.

**Closure recommendation**: V2 BACKLOG ITEM. Two options:

**Option A**: align `hasPendingFlush()` with the actual idempotency
guard. Change to:
```rust
pub fn has_pending_flush(&self) -> bool {
    let current = self.log.oplog_vv();
    match &self.last_flushed_vv {
        Some(last) => current != *last,
        None => true, // No flush yet -> first flush will send
    }
}
```

This changes the contract from "current_vv != default" to "current_vv
!= last_flushed_vv (Some)", treating None as "always pending until
explicit flush." This matches `flushDeltaToTransport()`'s actual
behavior.

But: this changes V1+V2.1 contracts. Mocha test at line 100 asserts
`hasPendingFlush() === false` on fresh `createSession`. Under Option
A that assertion would flip to `true`. V1 fromSnapshot test at line
156-157 would also need re-pinning.

**Option B**: keep current semantics, add a new
`willFlushSend()` accessor that DOES match `flushDeltaToTransport()`'s
idempotency guard. Then docs can recommend: "use `hasPendingFlush()`
for UI 'unsynced' indicator, use `willFlushSend()` to predict whether
the next `flushDelta` is a no-op." Two helpers, two clear contracts.

Option B is safer (no V1 contract change). The minor cost is an
additional method to bind and test. Acceptable for V2.3.

**Why MEDIUM not LOW**: this surfaces consistently in real test code
(V2.2's test rewrite was exactly this) so it'll surface in real IDE
code. Not HIGH because it doesn't BREAK anything — the
"pre-mutation flush sends baseline" path is correct under the documented
semantics; the issue is JS consumers building the wrong mental model.

### MEDIUM-4: `transportLastError` returns `Option<String>` and the docstring at lib.rs:601-607 explicitly documents the V2.2-deferred caveat about lossy Display projection — but V2.2 SHIPS this binding without any consumer-facing structured discriminant. Codex MEDIUM-3 from V2.1 was "ship discrimination by V2.2"; V2.2 ships the binding but defers the discrimination still further.

**Repo**: engine + IDE.
**File:line**: `crates/ql-bindings-node/src/lib.rs:601-607` (docstring
acknowledging the deferral).

**Specific issue**: V2.1's MEDIUM-3 said:

> Closure recommendation: V2.1 ship can stay (V1 baseline). V2.2
> should either:
> - (a) Bind `transport_last_error()` AND add a `kind()` accessor to
>   TransportError that returns a stable string discriminant
>   (`'closed' | 'io'`), OR
> - (b) Switch the IDE binding to throw a structured error subclass
>   (`TransportClosedError extends Error` etc.)

V2.2 took the (a)-without-(a) path: bound `transport_last_error()`
but skipped the `kind()` discriminant. The docstring at lib.rs:601-
607 acknowledges this is deferred to V2.3+. So V2.2 ships the V2.1
debt forward — IDE callers writing reconnect logic on V2.2 will
substring-match `'transport closed'` vs `'transport I/O error'` vs
the underlying transport's last_error() result.

That substring-matching is fragile:
1. The Display impl on `TransportError::Closed` is `"transport
   closed"`. Stable today, but the Display string is not a stable
   API — a future minor version could change to "Transport closed
   gracefully (peer initiated)" without warning.
2. `transport_last_error()` returns the BARE underlying transport's
   message — for WebSocket impls this could be anything from
   `"tungstenite::ConnectionClosed(CloseFrame { code: 4000, reason:
   ... })"` to `"i/o error: connection reset by peer"`. IDE callers
   substring-matching on this will be brittle.

The right shape was (b) — `napi::Error::with_code("TRANSPORT_CLOSED",
msg)` produces a JS Error with `.code = 'TRANSPORT_CLOSED'`. IDE
callers `instanceof`-check or `error.code === 'TRANSPORT_CLOSED'`.

V2.2 had the opportunity to ship (b) as a one-time refactor of all
the V2.1+V2.2 napi error-mapping sites (4-6 sites). The deferral
means V2.3+ needs to refactor those AND maintain backward-compat
with V2.2 substring-matching callers.

**Closure recommendation**: V2 BACKLOG ITEM. Carry forward to V2.3
explicitly. Add to `_active.md`'s V2.3+ list: "structured Error.code
mapping for all Transport-bound JS Errors (closes V2.1+V2.2
inherited MEDIUM)." Update the V2.2 ship notes' "V2.2 audit-deferred
caveat" line in the napi docstring to add a verification date so
future readers know it's been re-confirmed.

**Why MEDIUM not HIGH**: V2.2 ship is internally consistent — the
substring-match contract is pinned at the napi layer, the V2.2
mocha tests don't depend on discrimination, no V2.2 IDE consumer
code branches on error type yet. The debt is real but capped.

### MEDIUM-5: V2.2's "engine accepts aliases" mocha test at line 812-824 does NOT assert that the engine's loose parser is the LOAD-BEARING contract; it only asserts `doesNotThrow`. **Repo**: engine.
**File:line**: `crates/ql-bindings-node/src/lib.rs:651-677`.

**Specific issue**: the two helpers are:


### OBS-4: V2.2's IDE-side `isAutoFlushPolicy` type guard at session.ts:161-163 is intentionally STRICT camelCase (no aliases). Engine accepts loose. The asymmetry is documented + tested explicitly. This is fine BUT the docstring comment "this guard is the STRICT camelCase check for IDE-side validation; the engine is the loose parser" should be re-read by V2.3+ implementers because the engine's looseness is the WRONG side of the boundary.

**Repo**: IDE.
**File:line**: `quantlab/extensions/quantlab/src/quantbook/session.ts:155-163`.

The shape:
- Engine accepts `'Disabled'`, `'OnAppend'`, `'on-append'` (loose).
- IDE TS-guard accepts only `'disabled'`, `'onAppend'` (strict).

The asymmetry is documented in the test comment at line 813-814 ("The
engine-side parser is lenient; the strict camelCase check is in
isAutoFlushPolicy (TS guard)"). 

But the GENERAL principle from CLAUDE.md: errors must be visible
+ no fallbacks. A loose engine-side parser IS a fallback — it's
silently accepting non-canonical input from JS. The right shape is
to have the strict check on BOTH sides:

```rust
fn parse_auto_flush_policy(s: &str) -> Result<CoreAutoFlushPolicy> {
    match s {
        "disabled" => Ok(CoreAutoFlushPolicy::Disabled),
        "onAppend" => Ok(CoreAutoFlushPolicy::OnAppend),
        other => Err(Error::from_reason(format!(
            "AutoFlushPolicy must be 'disabled' or 'onAppend' (case-sensitive), got {other:?}"
        ))),
    }
}
```

Then `isAutoFlushPolicy` is the GATE: JS code that needs to validate
config input calls the guard FIRST, throws if the input is malformed,
and only THEN passes the canonical form to the engine. The engine is
the LAST line of defense (defense-in-depth), not the first.

V2.2's loose-parser design defers validation to the engine. A user
who serializes `'Disabled'` in a config and skips the IDE guard gets
through to the engine, which accepts it. The IDE guard's purpose
(reject malformed input) is then circumventable.

Per OBS not LOW because V2.2 ship is internally consistent — the
mocha test pins the asymmetry, the docstrings document it. V2.3+
should tighten the engine parser to match the TS guard exactly,
making the IDE guard the load-bearing validator and the engine a
strict consumer.

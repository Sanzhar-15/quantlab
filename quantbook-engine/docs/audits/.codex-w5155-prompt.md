# W5-155 audit task

Audit commit `a01b40f5101` in this repo. The change wires the W5-154 `on_table_drop` hook into `WorkbookRuntime::drop_table` in `crates/ql-exec/src/workbook_runtime.rs`. The W5-154 hook + reverse index were added in the prior commit `b83c19c7a7d` to `crates/ql-exec/src/calcgraph_session.rs`.

Tasks:

1. **Validate the W5-155 wiring.** Does the call to `g.on_table_drop(&canonical)` deliver what the docstring promises? The W5-154 hook docstring on `calcgraph_session.rs:947` claims: "After this hook fires, the next recompute will: 1. Find each previously-table-referencing formula in `dirty`. 2. Re-bind it (table is gone → `BindError::UnknownTable` → `Value::Error(#NAME?)`)."

2. **Plan cache interaction.** `PlanCacheKey` is `(text, sheet, name_gen, cell_anchor)` (see `crates/ql-exec/src/plan_cache.rs`). Note `name_gen` is `NameTable` generation, NOT `TableTable` generation. `try_recompute_with_simd_profile` (around `workbook_runtime.rs:3350`) is the recompute path — does it correctly re-bind structured-ref formulas after a `drop_table`, or does it serve a stale cached `ExprPlan::StructuredRef { resolved: <pre-drop range> }`?

3. **Symmetry with peers.** `rename_table`, `rename_column`, `resize_table` all call `self.plan_cache.clear()`. `drop_table` does NOT. Is this an accidental asymmetry or intentional?

4. **Op-log replay.** `crates/ql-oplog/src/replay.rs:523` handles `Op::DropTable` directly via `workbook.tables_mut().remove(...)` — replay has no calcgraph. Is this correct given that post-replay state is rebuilt via `CalcgraphSession::rebuild_from_workbook`?

5. **Hook ordering.** Hook fires AFTER op-log append, BEFORE `tables_mut().remove`. Is the ordering correct or could it interleave badly with another thread/borrow?

6. **Test coverage.** Does the new test `drop_table_fires_on_table_drop_hook_and_dirties_readers` actually prove that B1 = SUM(Sales[Qty]) ends up #NAME? after drop_table + recompute_dirty? Or only that it ends up dirty?

7. **Stale docstrings.** Search for any docstring or comment that claims drop_table relies on `plan_cache.clear()`, or that the hook isn't wired yet (W5-154 said "wiring lands in a follow-up commit"). Are they updated?

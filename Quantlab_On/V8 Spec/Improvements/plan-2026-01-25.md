# Quantlab Improvements Plan (2026-01-25)

## Scope
Plan only (no code changes). Address:
1) X‑axis shows random hours in fullscreen or after tab switch.
2) Entry/Exit levels lag during chart/axis drag.
3) Candlestick jitter at drag start/end.
4) Strategy pane instability + add top‑panel toggle button.
5) Optimize parameters bottom pane UI/behavior.

## Guiding Principles
- Fix root causes, not symptoms.
- Preserve performance and reduce layout thrash.
- Prefer minimal, localized changes with clear ownership.
- Ensure changes are testable and reversible.

## Phase 1 — X‑Axis Random Hours in Fullscreen/Tab Switch
**Hypotheses (ranked):**
1) TickCoordinator cache not invalidated on **size changes** or **visibility restoration** (stale tick values with new width).
2) Render/layout runs while webview is hidden (0 width/height), producing invalid tick labels that persist until zoom.
3) `TimeScale` tick step/format hysteresis not reset on big layout width change.

**Plan:**
- **A. Size/visibility correctness**
  - Ensure the chart gets a **post‑visibility resize** (next animation frame after tab becomes visible).
  - Add a visibility hook to call `chart.resize()` or a light `layoutInvalidate()` on activation.
  - Confirm `ResizeObserver` fires when returning from hidden state; if not, add a manual re‑measure.

- **B. TickCoordinator cache invalidation on width change**
  - Extend tickCoordinator cache key to include `plotRect.width` (or a width bucket).
  - Invalidate ticks when width change exceeds threshold (e.g., >5%).
  - Ensure `tickCoordinator.invalidateAll()` runs on resize and on tab activation.

- **C. TimeScale tick step reset on extreme width change**
  - When width changes > threshold, reset TimeScale’s tick hysteresis state (if needed) so it recomputes labels.

**Acceptance:**
- No random hours at any window size; tab switches keep correct X‑axis labels without needing a zoom.

## Phase 2 — Entry/Exit Levels Track During Drag
**Goal:** Entry/Exit levels move smoothly during pan and axis drag (no “snap on mouseup”).

**Plan:**
- **A. Identify render path**
  - Locate Entry/Exit rendering: series markers vs custom overlay plugin vs DOM overlay.
  - Ensure they render in a pass that updates during interactions (Overlay or Series with pan cache).

- **B. Make drag‑time positions truly live**
  - If drawn in overlay: compute positions from current `xScale` / `yScale` every frame (not cached).
  - Apply pan offset (`panOverscrollPx`) so level lines remain spatially aligned during rubber‑band.
  - Ensure overlay invalidation happens on every pan/axis drag frame (not just mouseup).

- **C. Sync with render snapshot**
  - Use the same render snapshot/range used by series rendering to avoid frame mismatch.

**Acceptance:**
- Entry/Exit markers/lines are visually locked to their data points throughout drag.

## Phase 3 — Candlestick Jitter at Start/End of Drag
**Goal:** Remove flicker/blink when pan starts and ends.

**Likely root causes:**
- Pan cache activation causes frame mismatch (first pan frame renders with one layer, next with another).
- Pan start/end toggles series/pan layers too abruptly.
- Mixed snapping/rounding between cached and live frames.

**Plan:**
- **A. Smooth pan cache activation**
  - Pre‑warm pan cache on pan start before hiding series layer.
  - Only switch to pan layer after the cache is ready (1 frame delay ok).

- **B. Smooth pan cache release**
  - On pan end, render a final live series frame **before** clearing pan layer.
  - Optionally retain pan cache for N frames to prevent immediate flicker.

- **C. Pixel alignment consistency**
  - Ensure both cached and live renders use consistent snapping/transform rules.

**Acceptance:**
- Candlesticks remain stable during pan start/end; no visible blinking.

## Phase 4 — Strategy Pane Stability + Top‑Panel Toggle
**Goal:** Strategy pane doesn’t disappear unexpectedly, and can be explicitly hidden via a top‑panel button.

**Plan:**
- **A. Stabilize pane lifecycle**
  - Ensure strategy pane is created once and preserved even if all indicator series are temporarily hidden.
  - Store last pane height and restore it after re‑activation.
  - Verify pane visibility logic doesn’t drop empty panes unless explicitly requested.

- **B. Add explicit show/hide toggle**
  - Add a new top‑panel button (next to timeframe controls) with:
    - Tooltip: “Hide Strategy Pane” / “Show Strategy Pane”
    - Accessible label + icon state
  - Implement a `toggleStrategyPaneVisibility()` in chart API.
  - If core API lacks pane visibility control, add a minimal `PaneApi.setVisible(boolean)` or `pane.hidden` flag and filter in `resolveVisiblePanes()`.
  - Persist visibility state (e.g., localStorage or extension storage).

**Acceptance:**
- Strategy pane never disappears unless toggled off.
- Toggle reliably hides/shows and restores previous height.

## Phase 5 — Parameters Bottom Pane Optimization
**Goal:** More stable UX, clearer layout, and fewer accidental changes.

**Plan:**
- **A. UX audit**
  - Identify common parameter groups (risk, execution, indicators).
  - Confirm keyboard navigation and focus order.

- **B. Layout improvements**
  - Add grouping headers and collapsible sections.
  - Make “Apply/Reset” controls sticky at bottom.
  - Reduce layout shift when values update (fixed row heights or reserved label widths).

- **C. State/Performance**
  - Debounce heavy re‑renders (e.g., only apply chart updates on “Apply”).
  - Track dirty state to avoid unnecessary redraws.

**Acceptance:**
- Less jitter, clearer grouping, and consistent apply behavior.

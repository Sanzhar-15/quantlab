# Lane O1 — Architecture Coherence + Fusion-Readiness

**Scope:** structural soundness of the as-built FE (FE-0a + FE-0b) vs the v2 fusion-first build
plan; readiness as a foundation for FE-1 / FE-1.5 / FE-2. NOT line bugs (other lanes own those).
Read-only.

**Verdict: SOUND FOUNDATION — SHIP.** The as-built honors the plan's load-bearing locked decisions
(own Canvas2D behind a usable seam; persistent bundled webview; build isolation; reuse the engine
snapshot/delta path; loader cdylib guard; text-cell fix). Deviations (0b-2+0b-3 folded together; the
host-pushes-on-commit postMessage model; the 3-column cell-LIST instead of a 2D sheet) are all
explicitly plan-sanctioned and sound. The architecture has clean seams for both the FE-1.5 reactive
bridge and the FE-2 GPU/2D work. No architectural dead-ends. Counts: **HIGH 0 / MED 3 / LOW 4.**

## MEDIUM (friction / readiness gaps — not defects now)

### MED-1 — Renderer seam works but is informal: no named `GridRenderer` interface; `draw()` signature is Canvas2D-shaped. *(readiness gap for FE-2)*
`index.ts:85` constructs `new CanvasGridRenderer(canvasEl)` against the concrete class, and
`index.ts:100-106 redraw()` reaches into renderer internals in a Canvas2D-specific way:
`canvasEl.style.transform = translate(...)` (CSS-transform blit), `renderer.resize(w,h)`,
`renderer.draw(w, h, scrollTop, scrollLeft, errorCells)`. There is **no declared `interface
GridRenderer`** — the "renderer interface so a v1.1+ GPU backend can swap in" (D1, §FE-2) exists only
as a de-facto method shape. The `draw(scrollTop, scrollLeft, errorCells)` contract is fine for a GPU
backend (it would translate the view matrix internally), but a WebGPU backend does NOT want the
host doing `canvas.style.transform` blit-scroll — that is a Canvas2D damage-redraw technique baked
into `index.ts`, not the renderer.
- **Structural risk:** LOW-MED. FE-2's bakeoff/swap will have to (a) introduce the interface type
  and (b) move the scroll-transform decision behind the renderer (a GPU renderer repaints the visible
  window directly; it does not translate a backing canvas). This is refactor friction, not a rewrite.
- **Recommended shape:** before FE-2, extract `interface GridRenderer { setSnapshot; refreshTheme;
  resize; draw(viewport: {w,h,scrollTop,scrollLeft}, errorCells); }` and make `index.ts` depend on
  it; move the `style.transform` blit into the Canvas2D impl (a `present(scroll)` step) so the GPU
  impl can no-op it. Keep `gridLayout` (already pure) as the shared geometry both backends consume.

### MED-2 — Full-snapshot-on-every-commit render model is correct for v1 but is the wrong granularity for FE-1.5 reactive bursts and FE-2 scale. *(readiness gap for FE-1.5 / FE-2)*
`cellGridPanel.ts:284-335`: every `render()` recomputes the whole sheet snapshot (via the delta
cache, so the *fetch* is incremental) and posts the ENTIRE `snapshot` to the webview; the webview's
`applyRender` (`index.ts:109`) **replaces `fullSnapshot` wholesale, `cancelEdit()`s, and clears all
error state**, then full-redraws. For FE-1.5 a single Python cell re-run can dirty+recalc many
dependents and will fire `refreshAll()` (the reactive trigger seam — see fusion section), which posts
a full snapshot and **cancels any in-flight cell edit**. A reactive recalc storm (the moat demo)
would repeatedly blow away the user's edit and repaint everything.
- **Structural risk:** MED. Not a dead-end — the engine already returns `changedCells` deltas
  (`mergeWorkbookDelta`) — but the **webview wire protocol only carries full snapshots**, so the
  partial-redraw the plan calls for ("snapshotDelta partial-redraws without full re-render", §FE-2
  acceptance) is not yet wired end-to-end, and the edit-cancel-on-render coupling will bite FE-1.5.
- **Recommended shape:** add a `{type:'renderDelta', changedCells, version}` host→webview message
  (the host already has the delta) and have the webview patch its in-memory entries + damage-redraw
  only those rows, and NOT cancel an in-flight edit on a delta that doesn't touch the edited cell.
  Decouple "a commit happened" from "the cell *I* am editing changed." This is FE-2-adjacent but
  FE-1.5 forces it earlier than the plan assumes.

### MED-3 — The 3-column cell-LIST model means FE-2's 2D renderer is an EXTENSION of `gridLayout`'s vocabulary but a REPLACEMENT of its semantics. *(readiness gap for FE-2)*
`gridLayout.ts` geometry (columnX, cellContentRect, hitTestContent, totalContentHeight) is clean and
parameterizable — FE-2 can reuse the *shape* of these functions. BUT the model is fundamentally a
list: a display-row is a snapshot *entry index*, and `entry.row`/`entry.col` are rendered as DATA in
two columns (`canvasGrid.ts:181`), not used as grid coordinates. A true 2D sheet inverts this:
display-row = A1 row, display-col = A1 col, and the cell at (r,c) is looked up, with blanks for
absent entries. So `COLUMNS` (3 fixed) → variable A1 columns; `entryIndex`-addressing → (row,col)
addressing; `totalContentHeight(entryCount)` → `MAX_ROW`-extent; the snapshot's sparse entry-list →
a sparse 2D lookup. The pure-geometry seam SURVIVES (uniform stride, columnX, hit-test, truncate are
all reusable); the addressing/lookup layer is net-new.
- **Structural risk:** MED, and EXPECTED (the plan defers the A1 adapter + sizing to FE-2). Worth
  flagging so FE-2 is scoped as "new addressing layer over the same geometry primitives," not "reuse
  the list renderer." The list renderer's `drawRow(entry, ...)` is throwaway; `gridLayout`'s math is
  not.
- **Recommended shape:** FE-2 keeps `gridLayout` as the geometry kernel, adds a `SheetModel` (A1
  addressing + sparse `(row,col)→cell` over the snapshot) and a `draw2D` that walks visible (row,col)
  cells instead of entry indices. Budget it as new, per the plan's 8-12wk.

## Fusion-readiness (the MOAT) — assessment: READY, no dead-end

- **FE-1 (KernelClient + qb.show one-shot writeback):** the host already owns the `Session` (napi)
  and exposes the fusion primitives typed and LIVE — `publishDataset` / `bindRange` (`types.ts:2097,
  2104`, no longer stubs), `recalcDirty` (`recalcDirtyChecked`, `session.ts:265`), `queryRange`,
  `writeRange`, `pollEvents`. A `KernelClient`/ZMQ layer can sit beside the panel and drive
  `publishDataset → recalcDirty → CellGridPanel.refreshAll()` with NO change to the webview wire
  protocol. The render path (`render()` → `acquireWorkbookSnapshot()`) reads the LIVE session each
  call, so a kernel-driven write is picked up by the next render. **No architectural blocker.**
- **FE-1.5 (reactive bridge):** the critical seam exists — `CellGridPanel.refreshAll()` (static,
  `cellGridPanel.ts:155`) re-renders every live panel from current session state, fully decoupled
  from the webview dispatch path. The reactive chain `kernel post_run_cell → publishDataset →
  engine dirty → recalcDirty → refreshAll()` is wireable today without touching the panel/webview
  contract. The render-on-postMessage model IS compatible with dirty-driven updates (render reads
  fresh state; it is not append-only on webview events). **The one real friction is MED-2** (full
  snapshot + edit-cancel on every reactive render) — a granularity problem, not a dead-end.
- **Snapshot/delta path compatibility:** `acquireWorkbookSnapshotViaDelta` rides the engine's
  per-session delta cache and `fullRebuildRequired` is an explicit protocol signal, not a swallowed
  error — fully compatible with external (kernel) writes advancing the version. Good.

## LOW (polish)

- **LOW-1 — palette/font fallbacks in the renderer** (`canvasGrid.ts:260-277`): `v(name, fallback)`
  returns a hardcoded colour when a `--vscode-*` var is empty, and `readFonts` does `|| 'sans-serif'`.
  These are theme-variable defaults at a rendering boundary, arguably benign, but they are `value ||
  default` masking shapes per the No-Fallbacks rule — a missing theme var paints a plausible-but-wrong
  colour silently. Consider asserting the core vars are present once at construction and logging if
  not. (Other lanes own the No-Fallbacks line call; flagged here as a structural smell, not a blocker.)
- **LOW-2 — duplicated visible-range helpers with divergent arg order**: `computeVisibleRowRange`
  (webview, `cellRender.ts:64`) vs `computeVisibleRange` (host, `cellGridLogic.ts:437`) are the same
  algorithm with deliberately different names/arg orders to prevent a copy/paste transposition. The
  divergence is documented and intentional, but it IS two copies of one algorithm (one clamps a stale
  scrollTop, one doesn't). Once the webview owns its own scroll, retire the host copy (it was for the
  old DOM-table virtualization) to remove the fork.
- **LOW-3 — `cellGridHtml.ts` dead but retained** (788 LOC, ~60 test refs): known/deferred per
  CONTEXT. Structural risk of keeping it: it still references the OLD DOM-table contract
  (`pollEvents`-merged diagnostics, `escapeHtml`) and its tests pin behavior the live path no longer
  uses — a future reader may treat it as live. Low risk while clearly comment-flagged DEAD; retire in
  the B2 cleanup so the cell-grid module has one renderer story.
- **LOW-4 — `entryCount` getter on the renderer is unused by `index.ts`** (`canvasGrid.ts:74`): minor
  dead surface; the renderer also caches the snapshot AND `index.ts` holds `fullSnapshot` — two owners
  of the same data. Harmless now; when MED-2's delta path lands, make the webview the single owner of
  entries and have the renderer read from it (or vice versa) to avoid a desync.

## Module-boundary summary
Boundaries are RIGHT: `gridLayout` (pure geometry) ← `canvasGrid` (paint) ← `index.ts` (DOM/scroll/
editor/wire) on the webview side; `cellGridLogic` (pure dispatch/delta/snapshot) ← `cellGridPanel`
(vscode panel + session binding) ← `quantbookCommands` (command wiring) on the host side; `session.ts`
is the single FFI boundary. The `import type`-only snapshot type + the `no-host-runtime` esbuild guard
keep the napi runtime out of the browser bundle — a correctly-placed seam. The only seam I'd
strengthen before FE-2 is the renderer interface (MED-1) and the render granularity (MED-2).

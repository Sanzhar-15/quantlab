# FE Megaudit — Lane S2: Edit/Dispatch/Snapshot Lifecycle

**Lane:** S2  
**Verdict:** SHIP-WITH-FIXES — 2 HIGHs, 3 MEDs, 3 LOWs. No data-loss in the golden path (single edit → commit → render). The HIGHs are both correctness gaps in non-trivial but reachable flows (formula edit-source display; shared delta-cache invalidation on undo). The MEDs are real UX or reliability concerns. LOWs are minor hygiene.

## HIGH findings

### H1 — Formula edit pre-populates input with the BODY (no `=`); user sees e.g. `A1+1` not `=A1+1`

**File/lines:** `webview/sheets-webview/index.ts:145`

**Concrete failure:**

In `beginEdit`, the edit input is pre-populated with:

```ts
inputEl.value = typeof entry.formula === 'string' ? entry.formula : formatCellValue(entry.value);
```

`entry.formula` is the formula BODY as stored by the engine — no leading `=`. The engine strips it at the FFI boundary: `setFormula` takes the body; `dispatchIncomingMessage` strips the `=` prefix before calling `setFormulaValidated` (`cellGridLogic.ts:385`). So when the user clicks a formula cell to re-edit it, the input shows `A1+1` instead of `=A1+1`.

This is a hard UX bug: the user cannot tell whether they are editing a formula or a text cell, and if they press Enter on the pre-populated value (with no leading `=`) it will be re-submitted as a TEXT input (because `classifyCellInput` will classify `A1+1` as text, not a formula), silently replacing the formula with a text cell.

The host's `classifyCellInput` (`cellGridLogic.ts:197`) only routes inputs with a leading `=` to `setFormula`. So after any re-edit, formula cells will be downgraded to text.

**Root cause:** The engine stores the formula body (no `=`) but the webview needs to present it in the user-facing spreadsheet convention (with `=`).

**Minimal fix:** In `beginEdit`, prepend `=` when using `entry.formula`:

```ts
inputEl.value = typeof entry.formula === 'string'
    ? '=' + entry.formula
    : formatCellValue(entry.value);
```

### H2 — Shared delta cache (`SESSION_DELTA_CACHES`) is NOT invalidated on undo/redo; stale snapshot may render after undo

**File/lines:** `cellGridLogic.ts:1201`; `cellGridPanel.ts:267-268`; dispatch `cellGridLogic.ts:291-295`

**Concrete failure:**

`SESSION_DELTA_CACHES` is a `WeakMap<SessionInstance, DeltaSnapshotCache>` shared across all panels bound to the same session. The cache holds a `{ snapshot, version }` pair. After a commit the cache is updated. After an undo/redo the following happens:

1. `dispatchIncomingMessage` calls `session.undo()` → `result.consumed = true` → calls `deps.onCommit()` → `render()`.
2. `render()` calls `acquireWorkbookSnapshotViaDelta` → `session.snapshotDelta(cachedVersion)`.

The `SessionInstance.undo()` docstring in `types.ts:2163-2165` states:

> "Undo/redo clears the delta cache, so the next `snapshotDelta` against an older token full-rebuilds."

The engine will return `fullRebuildRequired: true` on the first delta call after undo, which triggers the full `session.snapshot()` fallback in `acquireWorkbookSnapshotViaDelta`. So the render path IS correct in isolation.

HOWEVER: the shared cache's `version` and `snapshot` are STILL the pre-undo values at the point `snapshotDelta` is called. `acquireWorkbookSnapshotViaDelta` correctly handles `fullRebuildRequired` by re-fetching:

```ts
if (delta.fullRebuildRequired) {
    const full = session.snapshot();
    cache.snapshot = full;
    cache.version = full.version;
    return full;
}
```

So for the FIRST panel to re-render after undo, this path is taken correctly.

The bug is for a SECOND panel bound to the SAME session (same shared cache):
- Panel A receives `onCommit` first, fetches delta → `fullRebuildRequired`, re-seeds cache with the new full snapshot.
- Panel B's `render()` is called (e.g. via `refreshAll()`). By now the shared cache has been updated with the post-undo snapshot. Panel B calls `snapshotDelta(newVersion)` — which may now return an EMPTY delta (no changes since the reseed) instead of a `fullRebuildRequired` signal.
- Panel B renders correctly — but: if panel B had computed and stored `latestSnapshot` from the pre-undo render, and a `postRenderIfReady` for the buffered pre-handshake message was still in flight, B would show stale data until its own `render()` completes.

The more concrete race is: after undo, `refreshAll()` iterates panels in `Map` insertion order. Panel A re-seeds the cache with the post-undo snapshot and updates `cache.version`. Panel B then calls `snapshotDelta(postUndoVersion)` which returns an empty delta (nothing changed since the reseed): the merged snapshot IS correct, so Panel B renders correctly. BUT if the refresh loop is called from within Panel A's `onCommit` synchronously:

```ts
// dispatchIncomingMessage undo branch:
deps.onCommit();   // → this.render() on Panel A only, not all panels
```

The `onCommit` in `cellGridPanel.ts:383` is `() => this.render()` — only the OWNING panel re-renders. Panel B does NOT re-render on undo unless `refreshAll()` is separately called. This is a **silent stale display** for Panel B on undo.

Separate from the multi-panel case: if the panel is NOT webviewReady (bundle still loading), `render()` correctly stores `latestSnapshot` and defers, so the post-handshake re-send will show correct state. No bug in that path.

The ACTUAL severity-H issue: after undo, only the panel that dispatched the `undo` message re-renders (`onCommit` → `this.render()`). All OTHER open panels for the same workbook silently display stale data until the user manually refreshes or triggers another action. Since `refreshAll` is called only on sheet-management commands (not on undo), a two-panel view of the same workbook will show divergent state after undo.

**Minimal fix:** In `dispatchIncomingMessage` the `onCommit` is panel-local. When undo/redo is consumed, all panels for the session should re-render. The cleanest fix is to have `onCommit` for the undo/redo arm call `CellGridPanel.refreshAll()` instead of `this.render()`. In the dispatch wiring in `cellGridPanel.ts`, the `onCommit` is already a generic callback; the panel can detect undo/redo and broaden to `refreshAll`. Alternatively, expose a session-level refresh hook through `DispatchDeps`.

## MEDIUM findings

### M1 — `errorReply` from sheet-mismatch formula parse/bind decorates cell at the WRONG coord when another sheet is active

**File/lines:** `cellGridLogic.ts:393-402`; `cellGridPanel.ts:393-408`; `webview/sheets-webview/index.ts:272-280`

**Concrete failure:**

When `dispatchIncomingMessage` handles a `putValue` and the engine throws (e.g. `[formula_parse]`), the error reply is posted back with `sheet: req.sheet, row: req.row, col: req.col`. The webview stores this in `errorCells` keyed by `Number(er.row) + ',' + Number(er.col)` with no sheet-filter:

```ts
errorCells.set(Number(er.row) + ',' + Number(er.col), '[' + String(er.code) + '] ' + String(er.message));
```

If the user somehow navigates to a different sheet between sending the `putValue` and receiving the `errorReply` (theoretically possible since a sheet-switch replaces the panel, not the session), the `errorCells` map from the prior render will have been cleared by `applyRender → cancelEdit; errorCells.clear()` — so in practice the stale decoration is auto-cleared on the next render. This is acceptable.

However: the `errorReply` structure carries `sheet`, `row`, `col` but the webview does NOT validate that `er.sheet === fullSnapshot.sheet`. If a stale error reply arrives after a render (render changes the snapshot to a new sheet), the `errorCells` map will be decorated with a key from a different sheet's cell coordinates. Since the coordinates may accidentally collide with valid coordinates of the NEW sheet, a spurious red decoration may appear.

**Timing:** `putValue` is sent → host dispatches (synchronous) → `errorReply` posted back (async `postMessage`). Between the message send and the reply arriving, the user cannot switch sheets (there's no in-webview sheet switch; sheet switch is a host command that calls `CellGridPanel.show()` with a new sheet, which spawns a NEW panel). So in practice this race does not occur for the current single-sheet-per-panel architecture.

**But**: it WOULD occur if the user quickly triggered a host-level `quantbookSheetSwitch` command concurrently (which calls `show()` on a new panel). The new panel would be a fresh instance with an empty `errorCells` map. So the collision does not manifest in practice.

**Assessment downgraded to MEDIUM** because the race is currently structurally blocked (new panel = new instance), but the missing `sheet` guard in the webview's error handler is a latent bug for any future change that allows in-webview sheet navigation.

**Minimal fix:** In `index.ts`, add a sheet guard before decorating:

```ts
if (fullSnapshot !== null && er.sheet === fullSnapshot.sheet) {
    errorCells.set(...);
}
```

### M2 — `pendingCommit` is reset on `errorReply` but the `editState.entry` coords may differ from the error reply coords (wrong-cell re-arm)

**File/lines:** `webview/sheets-webview/index.ts:277-279`

**Concrete failure:**

When an `errorReply` arrives:

```ts
if (editState !== null) {
    editState.pendingCommit = false;
}
```

This unconditionally re-arms blur-cancel for WHATEVER cell is currently in `editState`, regardless of whether the error reply coordinates match the cell currently in `editState`. If (in a theoretical race) a new `beginEdit` had started a different cell between the `putValue` submission and the `errorReply` arrival, the new cell's `editState.pendingCommit` is reset to `false`, meaning a blur-away from the new cell will cancel the new (uncorrelated) edit instead of keeping it alive.

**Timing:** `commitEdit` sends a `putValue` → `editState.pendingCommit = true`. The response is async. `cancelEdit` is called if the user presses Escape or if `applyRender` fires. If a RENDER fires first (because the host processed a concurrent undo), `applyRender → cancelEdit` fires, setting `editState = null`. Then the `errorReply` arrives: `editState` is now `null`, so the `if (editState !== null)` guard skips the reset. No bug there.

BUT: could a `beginEdit` start a NEW cell BETWEEN the `putValue` send and the `errorReply` arriving? Yes, if the canvas `click` event fires before the async `postMessage` callback from the host. `commitEdit` sets `pendingCommit = true` and keeps the input visible. The user CAN click another cell — `beginEdit` calls `cancelEdit()` first (`cellGridLogic index.ts:133`) then starts the new edit. The `cancelEdit` sets `editState = null`. So by the time the `errorReply` arrives, `editState` is a NEW entry for the NEW cell, not null. The `pendingCommit = false` reset now incorrectly re-arms the NEW cell's blur-cancel.

The impact: the new cell's edit (user is typing) will be silently cancelled on blur instead of being preserved until explicitly submitted. This is a subtle "my edit disappeared when I clicked away" bug.

**Minimal fix:** Guard the errorReply `pendingCommit` reset by matching coordinates:

```ts
if (
    editState !== null &&
    fullSnapshot !== null &&
    Number(editState.entry.row) === er.row &&
    Number(editState.entry.col) === er.col
) {
    editState.pendingCommit = false;
}
```

### M3 — `classifyCellInput` preserves un-trimmed `raw` for text cells; a trailing space in a text value is silently carried into the engine

**File/lines:** `cellGridLogic.ts:205-206`

**Concrete failure:**

```ts
export function classifyCellInput(raw: string): SessionCellValueInput {
    const trimmed = raw.trim();
    if (trimmed === '') { return { kind: 'blank' }; }
    const n = Number(trimmed);
    if (Number.isFinite(n)) { return { kind: 'number', number: n }; }
    return { kind: 'text', text: raw };   // ← returns `raw`, NOT `trimmed`
}
```

The `text` branch returns the ORIGINAL `raw` string, not `trimmed`. This means a user typing `"hello "` (trailing space) stores a text cell with a trailing space, not `"hello"`. This diverges from the `number` branch (which trims via `Number(trimmed)`) and from the `blank` branch (which trims). It also diverges from what `parseCellRawInput` used to do (trimmed throughout).

The practical impact: whitespace-only trailing or leading characters in text cells will be silently stored and displayed. This is probably a copy-paste oversight (the comment says "preserving the literal verbatim" only for the formula case). The docstring says `text: raw` preserves the literal "verbatim" — but only for `text` kind; the number branch uses the trimmed form for the number payload. The inconsistency will surprise users.

**Minimal fix:** Use `trimmed` in the text branch:

```ts
return { kind: 'text', text: trimmed };
```

This is consistent with the number branch and with what a user would expect (trim input before storing). If the deliberate-verbatim choice is intentional (e.g. for paste-paths that need to preserve leading spaces), add a comment and a test.

## LOW findings

### L1 — `safeRender` catch swallows the error; it only `console.warn`s, no user-visible surface

**File/lines:** `cellGridPanel.ts:197-205`

**Concrete failure:**

`safeRender` returns `false` on a thrown error, which is counted as `failed` in `refreshAll` and returned to the caller. The contract says "callers can surface it LOUD (No-Fallbacks); a panel whose `render()` throws is NOT counted as refreshed." This is correct for the aggregate — the command layer receives `{ refreshed, failed }` and can surface a failure. But `safeRender` itself only calls `console.warn`, not `vscode.window.showErrorMessage`. If the caller (e.g. a B2 sheet-management command) decides to do nothing with the `failed` count, the error is swallowed.

Looking at the callers: `refreshAll()` is called from `quantbookCommands.ts` (not audited in this lane), and the `refreshAll()` doc says "callers can surface it LOUD". But there is no GUARANTEE the caller will. The No-Fallbacks rule says errors must be VISIBLE. `console.warn` is not visible to the user.

**Assessment:** The responsibility is shared between `safeRender` (which chose to not surface visibly) and the callers (which should surface the `failed` count). This is LOW because the architectural contract is correct (the count is propagated) but the implementation chain may lose it.

**Minimal fix:** Either surface a `showWarningMessage` inside `safeRender` (self-surfacing), or ensure the one caller that can lose the count (`refreshAll` callers in `quantbookCommands.ts`) is audited to surface the count. In `safeRender`, add:

```ts
void vscode.window.showWarningMessage(`Cell Grid sheet ${this.sheet}: render failed: ${detail}`);
```

### L2 — `buildSheetMovePositionItems` iterates `sheets.length` positions (before removing source), but valid target positions post-move are `[0, sheets.length - 1]`

**File/lines:** `cellGridLogic.ts:626`

**Concrete failure:**

```ts
for (let pos = 0; pos < sheets.length; pos += 1) {
```

After removing the source sheet, there are `sheets.length - 1` remaining sheets. Valid target positions for the new order are `[0, sheets.length - 1]` (0-based). The loop iterates `sheets.length` positions (one too many), producing a `"Position N (last)"` item that is actually the out-of-bounds `sheets.length - 1 + 1 = sheets.length` position. When the user picks this item, `moveSheet(sourceId, sheets.length)` is called on the `SessionInstance`, which according to the `types.ts` docstring rejects out-of-range indices with `[bad_argument]`: "an out-of-range index (valid positions are `[0, sheetCount)`) throws `[bad_argument]` (NOT a silent clamp)".

Note: `CollabSessionInstance.moveSheet` says "Out-of-range new_index clamps" — but `SessionInstance.moveSheet` throws for out-of-range. Since the panel now uses `SessionInstance`, the last picker item will always fail with `[bad_argument]` if picked.

**Minimal fix:** Change the loop bound to `sheets.length - 1`:

```ts
for (let pos = 0; pos < sheets.length - 1; pos += 1) {
```

Guard for the edge case where `sheets.length === 1` (only the source sheet; no valid positions — the picker should be empty):

```ts
if (remaining.length === 0) return [];
for (let pos = 0; pos < remaining.length; pos += 1) { ... }
```

Note: `remaining.length === sheets.length - 1`. Adjusting labels accordingly (the loop currently uses `sheets.length` for the `"last"` condition, which should change to `remaining.length - 1`).

### L3 — `render()` tombstone path emits a `console.warn` but produces no user-facing surface; the user sees a blank grid with no explanation

**File/lines:** `cellGridPanel.ts:287-297`

**Concrete failure:**

```ts
if (sheetSnapshot === null) {
    console.warn(`[cellGrid] active sheet ${this.sheet} not found in snapshot ...`);
}
```

The empty snapshot `{ snapshot_format_version: 1, sheet: this.sheet, entries: [] }` is sent to the webview, which renders the "empty — no PutValue ops" placeholder message. A user who has a panel open and then deletes the active sheet will see the grid silently go blank with a message that says "empty — no PutValue ops on this sheet" — they have no indication that the sheet was deleted.

The `console.warn` is not visible. A webview-level "this sheet has been deleted — close the panel" message would be more informative.

**Assessment:** LOW because the user can always trigger the confusion intentionally (they deleted the sheet), but the blank grid message is misleading.

**Minimal fix:** Send a special error message to the webview, or emit `vscode.window.showWarningMessage` pointing the user to close the panel. Alternatively, the webview could render a "Sheet deleted — close this panel" overlay instead of the generic "empty" message. The empty-snapshot path could include a `tombstoned: true` flag in the render message to let the webview render a more accurate placeholder.

## Trace summaries

### Click → edit → putValue → recalc → re-render loop

1. User clicks Value column cell in canvas (`canvasEl click`, `index.ts:201-214`) → `hitTestViewport` finds `colIndex === 2` → `beginEdit(hit.entryIndex)`.
2. `beginEdit` positions the `<input>` over the cell, sets `inputEl.value` from `entry.formula ?? formatCellValue(entry.value)` (H1 bug: formula body has no `=`), shows input, focuses+selects.
3. User types, presses Enter → `commitEdit` → checks `editState.pendingCommit` (guard against duplicate send) → sets `pendingCommit = true` → `vscode.postMessage({type:'putValue', ...})`.
4. Host `handleIncoming` → `dispatchIncomingMessage` → `putValue` branch → `req.sheet === deps.sheet` guard (correct) → classify: if `rawInput.trimStart().startsWith('=')` → `setFormulaValidated` (strips leading `=`; correct for new formula entry) → else `setValueValidated(classifyCellInput(raw))` → `recalcDirtyChecked` → `deps.onCommit()` → `this.render()`.
5. `render()` → `acquireWorkbookSnapshotViaDelta` → delta protocol (full seed if first call; delta merge otherwise) → `extractSheetSnapshot` → `QuantbookCellSnapshot` → stored in `latestSnapshot` → `postRenderIfReady`.
6. `postRenderIfReady` checks `webviewReady && latestSnapshot !== undefined && !_disposed` → `panel.webview.postMessage({type:'render', snapshot})`.
7. Webview `message` handler → `applyRender(snapshot)` → `cancelEdit()` (clears input/editState) → `errorCells.clear()` → `redraw()`.

**The golden path is correct.** The H1 bug only manifests on RE-EDIT of a formula cell.

### webviewReady handshake race

1. `show()` calls `panel.webview.onDidReceiveMessage(instance.handleIncoming)` BEFORE setting `panel.webview.html` (correct; avoids the race where the bundle posts `webviewReady` before the listener is attached).
2. Then `panel.webview.html = buildShellHtml(...)` → bundle script evaluates → last line: `vscode.postMessage({type:'webviewReady'})` (sent AFTER all listeners are wired on the webview side).
3. `handleIncoming` receives `webviewReady` → `this.webviewReady = true` → `clearReadyWatchdog` → `postRenderIfReady`.
4. If `render()` was called before the handshake (which it was — `show()` calls `instance.render()` before `armReadyWatchdog()`), `latestSnapshot` is already set; `postRenderIfReady` delivers it now.
5. If the handshake never arrives (bundle missing/CSP error), the `READY_WATCHDOG_MS = 6000` timer fires → `showErrorMessage` — correctly LOUD.

**The handshake race is handled correctly.** Render before ready is buffered and re-sent.

### Presence/typing drop

`presenceUpdate` and `typing_stroke` envelopes: `dispatchIncomingMessage:316-318` silently drops them (no log, no error). The dormant webview DOES still emit these for the single-writer session? No — the `index.ts` webview does NOT emit `presenceUpdate` or `typing_stroke` (the canvas-based FE-0b-2/3 bundle has no presence code; it only emits `webviewReady`, `putValue`, `undo`, `redo`). The drop guards are vestigial from the old collab webview and are harmless dead code in the current bundle.

### Delta snapshot cache path

`acquireWorkbookSnapshotViaDelta` correctly:
- Seeds on first call (undefined version).
- Calls `snapshotDelta(cachedVersion)` on subsequent calls.
- Checks `assertSupportedSchemaVersion` on the delta DTO.
- On `fullRebuildRequired = true`: re-fetches full snapshot (no swallowed error; explicit designed protocol signal).
- On clean delta: `mergeWorkbookDelta` in place (mutates cache, returns merged).

The H2 issue is NOT within the delta path itself but in the undo → multi-panel re-render wiring above it.

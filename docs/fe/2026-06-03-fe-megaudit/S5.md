# FE Megaudit — Lane S5: Test Quality + Coverage

**Lane:** S5  
**Auditor:** Claude Sonnet 4.6 (read-only)  
**Verdict:** PARTIAL — the test suite is genuinely strong on pure-helper coverage
(gridLayout, cellRender, mergeWorkbookDelta, acquireWorkbookSnapshotViaDelta,
extractSheetSnapshot, dispatchIncomingMessage, classifyPollTick, buildHtml, all
the quickpick builders, undo/redo, .qbook B2 ops, B#1/S2-01 CollabSession regressions)
but has four HIGH-severity holes that guard correctness-critical live paths with
no test, and several medium/low issues.

**Counts: 4 HIGH, 5 MEDIUM, 3 LOW**

## HIGH

### H-1 — `classifyCellInput` has zero direct tests; the dispatch path it guards is tested only via integration

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:197`  
**Test file:** none

`classifyCellInput` is the FE-0a B1 "text-cell fix": it replaces the old
numeric-only `parseCellRawInput` for non-formula inputs. It is exported, pure,
and mocha-importable — but no test ever imports or calls it directly.

The *dispatch* tests (`V3.2.b.5`, line 2424 and the FE-0a B1 suite at line 2442)
cover the number, text, blank and formula paths through `dispatchIncomingMessage`,
which *calls* `classifyCellInput` internally. Those tests establish that the
end-to-end commit works, but they do NOT pin:

- `classifyCellInput('TRUE')` — returns `{ kind: 'text', text: 'TRUE' }` (not a
  boolean, which is intentional per the B1 docstring but undocumented by a test).
- `classifyCellInput('0')` vs `classifyCellInput('-0')` — both parse as `number`
  via `Number()`; `-0` in particular: `Number('-0') === -0`, which is a finite
  number. Is `{ kind: 'number', number: -0 }` the intended output? No test says.
- `classifyCellInput('0x1F')` — hex literal: `Number('0x1F') === 31`, routes to
  number. Intentional? Undocumented by a test.
- `classifyCellInput('  hello world  ')` — the function passes `raw` (not
  `trimmed`) to `{ kind: 'text', text: raw }`. A test that checks the whitespace
  behaviour of the `text` branch is absent.
- `classifyCellInput('')` / `classifyCellInput('   ')` — these route to `blank`
  (the trimmed === '' branch). A test that directly asserts the `{ kind:'blank' }`
  return is absent (the integration test checks the cell is cleared, but
  `classifyCellInput` itself is never called in isolation).

**Why HIGH:** `classifyCellInput` is the ONLY classification path for every
non-formula cell write post-B1. If a refactor accidentally inverted the
`Number.isFinite` check or the trimming logic, the dispatch integration tests
would catch the obvious cases (number → number, string → text) but the edge
cases (boolean literals, hex, -0, whitespace-in-text) would silently regress.
The function is two dozen lines and 100% pure: it is exactly what unit tests
are for.

**Minimal fix:** add a new suite in `quantbook-roundtrip.test.ts` (no cdylib
needed):

```typescript
import { classifyCellInput } from '../src/quantbook/cellGrid/cellGridLogic';

suite('FE-0a B1 -- classifyCellInput (pure, no engine)', () => {
    test('empty / whitespace -> blank',     () => assert.deepStrictEqual(classifyCellInput(''),      { kind: 'blank' }));
    test('whitespace-only -> blank',         () => assert.deepStrictEqual(classifyCellInput('   '),   { kind: 'blank' }));
    test('integer string -> number',         () => assert.deepStrictEqual(classifyCellInput('42'),    { kind: 'number', number: 42 }));
    test('float string -> number',           () => assert.deepStrictEqual(classifyCellInput('3.14'),  { kind: 'number', number: 3.14 }));
    test('hex literal -> number',            () => assert.deepStrictEqual(classifyCellInput('0x1F'),  { kind: 'number', number: 31 }));
    test('Infinity -> text (non-finite)',     () => assert.deepStrictEqual(classifyCellInput('Infinity'), { kind: 'text', text: 'Infinity' }));
    test('NaN -> text (non-finite)',          () => assert.deepStrictEqual(classifyCellInput('NaN'),   { kind: 'text', text: 'NaN' }));
    test('plain text -> text (verbatim raw)',  () => assert.deepStrictEqual(classifyCellInput('hello'), { kind: 'text', text: 'hello' }));
    test('whitespace-padded text -> text (raw preserved)', () =>
        assert.deepStrictEqual(classifyCellInput('  hi  '), { kind: 'text', text: '  hi  ' }));
    test('TRUE -> text (no boolean parsing in B1)', () => assert.deepStrictEqual(classifyCellInput('TRUE'), { kind: 'text', text: 'TRUE' }));
});
```

### H-2 — `dispatchIncomingMessage` formula error path (`formula_parse` / `formula_bind`) is never tested end-to-end; the comment acknowledges it then skips

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:376-402`,
specifically the `catch(err) → onError(errorReply)` arm.  
**Test file:** `quantbook-roundtrip.test.ts:6100` (the OPUS-HIGH-1 suite)

The suite at line 6100 ("dispatcher routes = prefix to appendPutFormula") has
two tests — happy path (`=A2+1`, `=A1+1`) and a control (no `=`). It does NOT
have a test for the *failure* path:

```
// comment at line 6148-6149:
// (a literal RangeRef like SUM(A1:B10) does NOT --
// that is a v1 formula_bind limitation, surfaced as a loud errorReply).
```

The comment calls out that `=SUM(A1:B10)` would surface as a loud `errorReply`
(code `formula_bind`) — but there is no test that actually sends such an input,
calls `dispatchIncomingMessage`, and asserts:

1. `getCommitCount() === 0` (no commit on formula error)
2. `errorReplies.length === 1`
3. `errorReplies[0].code === 'formula_bind'` (or `'formula_parse'`)
4. The engine was not left in a dirty state (recalc not called when the formula
   errors at bind time)

This is a HIGH gap because the `catch` in `dispatchIncomingMessage` at lines
392-402 routes the error through `parseQuantbookError` + `onError`. If that
path were accidentally broken (e.g., a refactor that moved the try/catch
boundary, or an engine change in error code), `dispatchIncomingMessage` would
either silently consume the error or produce an errorReply with the wrong code —
and the test suite would never notice.

Also untested: a formula that parses OK but fails at formula_parse level
(`=!@#` malformed syntax) — produces `formula_parse` code, not `formula_bind`.

**Minimal fix:**

```typescript
test('invalid formula (formula_parse error) routes to errorReply with formula_parse/formula_bind code', () => {
    const session = createWorkbookSession();
    session.addSheet('S', 1000);
    const { deps, errorReplies, getCommitCount } = makeDeps(session, 0);
    // "=SUM(A1:B10)" is formula_bind in v1 (range-aggregate not yet bound);
    // "=!@!" is formula_parse. Either surfaces a structured errorReply.
    dispatchIncomingMessage(
        { type: 'putValue', sheet: 0, row: 0, col: 0, rawInput: '=SUM(A1:B10)' },
        deps,
    );
    assert.strictEqual(getCommitCount(), 0, 'no commit on formula error');
    assert.strictEqual(errorReplies.length, 1, 'exactly one errorReply');
    assert.ok(
        errorReplies[0].code === 'formula_bind' || errorReplies[0].code === 'formula_parse',
        `expected formula_bind or formula_parse, got ${errorReplies[0].code}`,
    );
    assert.strictEqual(errorReplies[0].sheet, 0);
    assert.strictEqual(errorReplies[0].row, 0);
    assert.strictEqual(errorReplies[0].col, 0);
});
```

### H-3 — `formatCellValue` in `cellRender.ts` (webview copy) is not tested for the `'error'` branch; test assertions are numerically imprecise for the `'number'` branch

**File:** `extensions/quantlab/webview/sheets-webview/cellRender.ts:31`  
**Test file:** `quantbook-sheets-webview-render.test.ts:21`

**Issue A (imprecision, not vacuous):** The `'number'` test at line 22 uses
`{ kind: 'number', value: 42 }` and asserts `'42'`. The function calls
`String(value.value)`, which for `42` returns `'42'` — trivially true. But for
`Number.EPSILON`, `String(Number.EPSILON)` = `'2.220446049250313e-16'`; for
`1e20`, `String(1e20)` = `'100000000000000000000'`; for
`Number.MAX_SAFE_INTEGER + 1`, it starts losing precision silently. There is
no test that pins what the webview displays for scientific-notation or
precision-boundary numbers. This is LOW, but noted here because the test
claims to cover `number` but does not exercise the boundary cases where the
display string might surprise users.

**Issue B (HIGH) — `'error'` branch identity:** `formatCellValue` for `error`
returns `value.value` — the verbatim error sigil string. The test at line 30
asserts `formatCellValue({ kind: 'error', value: '#DIV/0!' }) === '#DIV/0!'`.
This assertion is `true` and correct, but it is also trivially vacuous: the
function is `return value.value`, and the test passes the value back as the
expected string. It would pass even if the function was `return 'WRONG_' +
value.value`. The assertion is `return-of-its-own-input`.

More critically: `formatCellValue` is a `switch` that TypeScript marks exhaustive
with `never` on the fallthrough. But the switch has no `default:` case — if
TypeScript's exhaustiveness check ever allowed a new `QuantbookCellValue` union
member to be passed at runtime (e.g., a mismatched bundle), the function returns
`undefined` silently. There is no test that provides an unknown kind and asserts
a throw or a fallback string.

Finally, the webview's `formatCellValue` signature differs from the host's old
`cellGridHtml.formatCellValue` (different module, same name). The test file
directly imports from `../webview/sheets-webview/cellRender` — correct. But
the `buildHtml` tests in `quantbook-udf-worker.test.ts:280` (line 280-293) test
a different, dead-code version of `formatCellValue` imported from
`cellGridHtml.ts`. A reader could conflate the two. Not a runtime bug but
creates audit confusion.

**Minimal fix for B:**
Add a test that pins the `'error'` return is the sigil verbatim AND that a
different value changes the output:
```typescript
test('error branch returns the sigil string verbatim', () => {
    assert.strictEqual(formatCellValue({ kind: 'error', value: '#DIV/0!' }), '#DIV/0!');
    assert.strictEqual(formatCellValue({ kind: 'error', value: '#N/A' }), '#N/A');
    assert.notStrictEqual(formatCellValue({ kind: 'error', value: '#N/A' }), '#DIV/0!');
});
```

### H-4 — `cellGridHtml.ts buildHtml` tests (≈65 references in roundtrip.test.ts + 4 in udf-worker.test.ts) exercise retired dead code; tests would PASS even if the canvas render path silently broke

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts` (retired/DEAD)  
**Test files:** `quantbook-roundtrip.test.ts:2168+`, `quantbook-udf-worker.test.ts:21`

The CONTEXT.md acknowledges that `cellGridHtml.ts` is retired, and that the
~60 test references are a "known deferred cleanup". This audit cannot report
"it is dead code" as a novel finding per the context. However the RISK from
a test-quality standpoint is HIGH and is novel:

**The dead-code tests actively provide FALSE COVERAGE SIGNAL.** If the new
Canvas2D renderer in `canvasGrid.ts` had a critical bug (e.g., wrong font
applied, cells not drawn, blank render on large snapshots), the 65 `buildHtml`
tests would all pass anyway because they test the RETIRED path that the panel
no longer calls. The passing test count in CI is inflated by ~65 tests that
do not guard the production rendering surface.

There is no test that exercises `canvasGrid.CanvasGridRenderer` in any way —
not even a structural test that constructs it with a mock canvas context and
calls `draw()`. The canvas renderer is explicitly described as
"DOM/canvas-touching — not unit-tested (no headless 2D context)" in its header
comment, and the CONTEXT.md concurs. The gap is therefore expected and
acknowledged.

**What IS novel and HIGH:** the test file `quantbook-udf-worker.test.ts` (line 21)
imports `buildHtml` from `cellGridHtml.ts` in the suite
"buildHtml renders the diagnostic as a title= tooltip". This suite tests that
`buildHtml` emits `title="..."` for diagnostic cells AND that
`renderRowsClient` (the virtual scroll client script inside `buildHtml`) references
`e.diagnostic`. Both of these behaviours live in the RETIRED code path. The
NEW Canvas2D renderer's tooltip handling is untested:

- The canvas renderer in `canvasGrid.ts` uses `canvas.title` (the whole canvas
  element's title) for hover tooltips — but this is set to the hovered cell's
  `diagnostic` or `value`. The per-cell tooltip-on-hover logic in
  `webview/sheets-webview/index.ts` is not tested at all.
- `attachCellDiagnostics` IS well-tested (the UDF worker test suite has good
  coverage of the merge logic). But the bridge from `attachCellDiagnostics`
  result → canvas hover title is untested (requires a DOM/canvas stub).

**Concrete risk:** A refactor that moved the diagnostic to a different field
name (e.g. `tooltip` instead of `diagnostic`) would be caught by the
`attachCellDiagnostics` tests but NOT by the canvas rendering path, because all
the renderer-side tests reference dead code.

**Minimal fix:** At minimum, add a comment in `quantbook-udf-worker.test.ts`
at the `buildHtml` suite header and in `quantbook-roundtrip.test.ts` at line 2168
marking these as "dead-code path tests, retained for schema contract only; canvas
rendering is smoke-only". This makes the coverage signal honest. Long-term, the
65 dead-code tests should be replaced with tests that cover the live rendering path
(e.g., testing that `attachCellDiagnostics` produces output that `CanvasGridRenderer`
would consume, or a smoke test using a canvas mock).

## MEDIUM

### M-1 — `dispatchIncomingMessage` undo/redo ENGINE ERROR path is untested

**File:** `quantbook-roundtrip.test.ts:3490` (the undo/redo dispatch suite)

The suite at line 3490 tests the happy path (undo consumed, redo consumed) and
the "empty stack" no-op. It does NOT test the error path: if `session.undo()`
throws (e.g., corrupt session state, or a future engine change), the catch at
`cellGridLogic.ts:297` routes through `onError`. There is no test that injects
a session whose `undo()` throws and verifies that `errorReply.code === 'unknown'`
(or whatever code the engine would emit) and `errorReply.message` has an
`[undo]` prefix.

This matters because the `[undo]/[redo]` prefix in the message is the UX
signal that tells the user WHICH action failed — it is explicitly mentioned in
the docstring ("Message prefixed with [undo]/[redo] so the user sees which action
failed"). The prefix logic has no test.

**Minimal fix:** Add a test using a mock session that throws from `undo()`:
```typescript
test('undo engine throw routes to errorReply with [undo] prefix', () => {
    const boom: SessionInstance = {
        undo: () => { throw new Error('[bad_argument] cannot undo this state'); },
        redo: () => { throw new Error('[bad_argument] cannot redo'); },
    } as unknown as SessionInstance;
    const errors: ErrorReplyMessage[] = [];
    const deps = { session: boom, sheet: 0, onCommit: () => {}, onError: (r: ErrorReplyMessage) => errors.push(r) };
    dispatchIncomingMessage({ type: 'undo' }, deps);
    assert.strictEqual(errors.length, 1);
    assert.match(errors[0].message, /\[undo\]/);
    assert.strictEqual(errors[0].code, 'bad_argument');
});
```

### M-4 — `cellGridPanel.ts` host-side `render()`/`postRenderIfReady()`/`handleIncoming('webviewReady')` are fully untested

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:284,320,374`

The panel class is vscode-dependent and cannot be mocha-imported without a vscode
shim. This is expected and acknowledged in CONTEXT.md. However, the three critical
panel behaviors are also NOT tested at any level (not even via a lightweight
mock-vscode harness):

1. `render()` fallback when `extractSheetSnapshot` returns null (deleted sheet):
   it falls back to an empty snapshot and logs a warning. There is no test that
   verifies the fallback snapshot has `entries: []` and `sheet: <active_sheet>`.

2. `postRenderIfReady()` gate: if `webviewReady === false`, the snapshot is stored
   but NOT posted. If `webviewReady === true`, it is posted. The gate logic is
   untested — a subtle boolean inversion would cause blank grids or premature posts.

3. `handleIncoming({type:'webviewReady'})` sets `this.webviewReady = true` AND
   calls `postRenderIfReady()`. The path "render() ran before handshake → snapshot
   stored → handshake arrives → snapshot sent" is the NORMAL startup sequence and
   is completely untested.

This is a known hard constraint (vscode dependency) but worth flagging at MEDIUM
because these paths contain the FE-0b correctness-critical startup logic.

**Minimal fix:** Extract `postRenderIfReady` and the null-sheet fallback in
`render()` into small, vscode-free pure helpers in `cellGridLogic.ts` that can
be unit-tested. The vscode `postMessage` call can remain in the panel as a
thin wrapper.

### M-5 — `gridLayout.ts::cellContentRect` edge cases: negative `entryIndex` and out-of-range `colIndex` return unstable results with no test

**File:** `extensions/quantlab/webview/sheets-webview/gridLayout.ts:69`  
**Test file:** `quantbook-sheets-grid-layout.test.ts:45`

`cellContentRect` does `COLUMNS[colIndex]?.width ?? 0` — for an out-of-range
`colIndex`, it returns `width: 0` silently. For a negative `entryIndex`, the
`y` coordinate is `HEADER_HEIGHT + negative * ROW_HEIGHT`, which is smaller than
`HEADER_HEIGHT`. Both cases produce geometrically nonsensical rects (zero width,
or y inside the header band) that the overlay editor would use to position the
input. No test covers these; the hitTest functions guard against invalid indices
upstream, but `cellContentRect` is called directly in `index.ts` and is therefore
reachable with an invalid index if `hitTestViewport` is ever bypassed.

**Minimal fix:**
```typescript
test('cellContentRect out-of-range colIndex returns width=0', () => {
    assert.strictEqual(cellContentRect(0, 99).width, 0);
});
test('cellContentRect colIndex=3 (past last col) returns width=0', () => {
    assert.strictEqual(cellContentRect(0, 3).width, 0);
});
```

### L-1 — `computeVisibleRange` (HOST version in `cellGridLogic.ts`) and `computeVisibleRowRange` (WEBVIEW version in `cellRender.ts`) have different parameter order; this is documented but no test cross-checks that both produce the same output for the same geometry

**File:**
- `cellGridLogic.ts:437` — `(scrollTop, rowHeight, viewportHeight, totalRows, overscan?)`
- `cellRender.ts:64` — `(scrollTop, viewportHeight, totalRows, rowHeight, overscan)`

Both are tested independently with similar but NOT identical fixture values. If a
caller accidentally used the host version in the webview (or vice versa), the
arg-order swap would produce wrong results silently. The distinct function names
(`computeVisibleRange` vs `computeVisibleRowRange`) are the stated guard — but no
test explicitly verifies that the two functions produce identical output on the
same geometry, confirming they compute the same thing in different arg orders.

**Minimal fix:** Add a cross-check test (can live in either file):
```typescript
test('webview computeVisibleRowRange and host computeVisibleRange agree on same geometry', () => {
    // same 5 params in the right order for each variant
    const host    = computeVisibleRange(250, 25, 100, 100, 5);
    const webview = computeVisibleRowRange(250, 100, 100, 25, 5);
    assert.deepStrictEqual(host, webview);
});
```

### L-2 — `hitTestViewport` golden tests use hardcoded arithmetic comments; if `HEADER_HEIGHT` or `ROW_HEIGHT` constants change, the comments silently lie and the tests may fail with confusing messages

**File:** `quantbook-sheets-grid-layout.test.ts:87-88`

The test at line 87:
```typescript
// localY = HEADER_HEIGHT + 5 -> contentY = +300 = 333 -> entryIndex = floor((333-28)/25) = 12
assert.deepStrictEqual(hitTestViewport(columnX(2) + 10, HEADER_HEIGHT + 5, 0, 300, 20), { entryIndex: 12, colIndex: 2 });
```
The comment `"333 -> entryIndex = floor((333-28)/25) = 12"` is correct for
`HEADER_HEIGHT=28, ROW_HEIGHT=25` but hard-codes these constants numerically.
If either constant changes (e.g., ROW_HEIGHT bumped to 30 for FE-2), the comment
will lie, the expected value `{ entryIndex: 12 }` will be wrong, and the failure
message won't say why.

**Minimal fix:** Replace with symbolic derivation in the test body:
```typescript
const contentY = HEADER_HEIGHT + 5 + 300;
const expectedEntry = Math.floor((contentY - HEADER_HEIGHT) / ROW_HEIGHT);
assert.deepStrictEqual(hitTestViewport(columnX(2) + 10, HEADER_HEIGHT + 5, 0, 300, 20),
    { entryIndex: expectedEntry, colIndex: 2 });
```

### L-3 — `mergeWorkbookDelta` `removedCells` path is marked "forward-compat only — engine emits []" but the only test uses a synthetic fixture; no test verifies that a REAL engine delta never populates `removedCells` unexpectedly

**File:** `quantbook-roundtrip.test.ts:7047`

The `removedCells` test at line 7047 uses a hand-built delta with
`removedCells: [{ sheet: 0, row: 0, col: 0 }]`. This is a pure-helper test
(no engine). The shape-equivalence test at line 7203 does run against a real
session and exercises deleteSheet, undo, renameSheet — but it never asserts
`delta.removedCells === []` (it only checks that the merged shape matches the
fresh snapshot). If the engine ever started populating `removedCells` on a
real path (e.g. after a future engine upgrade), the shape-equivalence test
would still pass — it does a `deepStrictEqual` on the merged result against
`s.snapshot()`, which is correct if `mergeWorkbookDelta` handles `removedCells`
correctly. So this is LOW: the shape-equivalence test does provide end-to-end
coverage; it just doesn't isolate the `removedCells` branch separately for real-engine ops.

**No fix required;** noting for awareness.

## HIGH severity

### H1 — `tryBuild` swallows esbuild errors in watch mode (esbuild-webview-common.mjs:45–51)

**File:line:** `extensions/esbuild-webview-common.mjs:45-51`

```js
async function tryBuild(options, didBuild) {
    try {
        await build(options, didBuild);
    } catch (err) {
        console.error(err);   // ← only logged, not re-thrown
    }
}
```

**Used at:** `esbuild-webview-common.mjs:84–86` — the `--watch` branch calls `tryBuild` for both the initial build AND every subsequent file-change rebuild triggered by `watcher.subscribe`.

**How it hides failures:** In watch mode, if esbuild fails (syntax error, wrong-platform binary, import resolution failure), `tryBuild` logs to stderr and **returns normally**. The watcher loop continues. The stale/broken bundle sits in `dist/webview/quantbook/` silently. The developer gets no exit code, no process termination, and (outside a terminal) may miss the `console.error` entirely. Contrast with the one-shot path (line 88–95) which was explicitly fixed: `build(...).catch(err => { console.error(err); process.exit(1); })`.

The comment on the one-shot fix (line 89–93) literally calls out the old swallow pattern — but the watch-mode `tryBuild` is the same pattern, never fixed.

**Concrete failure scenario:** Developer runs `npm run watch:webviews:quantbook`, saves `index.ts` with a TypeScript error. esbuild fails. `tryBuild` logs the error to console and returns. The watcher rearms. The webview loads the stale bundle from before the error. The grid appears to work but the edit is not live. Developer may spend hours debugging runtime behavior thinking they are running new code.

**Minimal fix:** In the watcher path, re-throw after logging (or call `process.exit(1)` on watch-mode failures — the watcher will restart it on the next edit):

```js
async function tryBuild(options, didBuild) {
    try {
        await build(options, didBuild);
    } catch (err) {
        console.error(err);
        process.exit(1);  // same discipline as the one-shot path
    }
}
```

Or, simpler: remove `tryBuild` entirely and call `build(...)` directly in the watch path (letting the uncaught rejection surface the process).

**Note:** `esbuild-quantbook-webviews.mjs` delegates entirely to `run()` from the shared common file, so this bug affects the Quantbook webview build and any other extension that uses `esbuild-webview-common.mjs`.

### H2 — `safeRender` swallows render failures for disposed panels (cellGridPanel.ts:194–206)

**File:line:** `src/quantbook/cellGrid/cellGridPanel.ts:194-206`

```ts
private safeRender(): boolean {
    if (this._disposed) {
        return true;   // ← disposed panels counted as SUCCESS
    }
    try {
        this.render();
        return true;
    } catch (err) {
        const detail = err instanceof Error ? err.message : String(err);
        console.warn(`[quantbook] cell-grid safeRender failed: ${detail}`);
        return false;
    }
}
```

**How it hides failures:** A disposed panel returns `true` (success) from `safeRender`. `refreshAll()` therefore counts it in `refreshed` rather than `failed`. The caller in `quantbookCommands.ts` surfaces a warning ONLY when `failed > 0`. So if all live panels have been disposed and a `refreshAll` is called, the command reports "Refreshed N panels" for disposed ones and shows no error.

**Concrete failure scenario:** A sheet-management command (add/rename/delete/move sheet) calls `refreshAll()` after the engine op. If all panels happen to be disposed (race with panel dispose during a command), `refreshAll` returns `{ refreshed: N, failed: 0 }` where N = number of disposed panels, the command logs "Refreshed N panel(s)" and shows no warning. The user sees a success count for panels that were NOT actually refreshed.

**Why this matters beyond mere reporting:** The disposed-panel success path is an intentional design — a disposed panel doesn't need rendering. The bug is that it's counted as a `refreshed` success rather than a neutral no-op. The command-layer message to the user becomes misleading: "Refreshed 2 panel(s)" when 2 panels were disposed and 0 were actually re-rendered.

**Minimal fix:** Return a third outcome:

```ts
private safeRender(): boolean | 'skipped' {
    if (this._disposed) {
        return 'skipped';
    }
    // ...
}
```

Or simpler: exclude disposed panels from the count by filtering them at `refreshAll`:

```ts
static refreshAll(): { refreshed: number; failed: number } {
    let refreshed = 0;
    let failed = 0;
    for (const instance of panels.values()) {
        if (instance._disposed) { continue; }  // not counted either way
        if (instance.safeRender()) { refreshed++; } else { failed++; }
    }
    return { refreshed, failed };
}
```

## MEDIUM severity

### M1 — `readFonts` font-family fallback masks missing VS Code CSS variable (canvasGrid.ts:276)

**File:line:** `webview/sheets-webview/canvasGrid.ts:276`

```ts
private readFonts(): { body: string; header: string } {
    const family = getComputedStyle(document.body)
        .getPropertyValue('--vscode-font-family').trim() || 'sans-serif';
    return { body: '12px ' + family, header: '600 12px ' + family };
}
```

**How it hides failures:** `|| 'sans-serif'` silently substitutes a generic font when `--vscode-font-family` is absent or empty. This is the exact "graceful degradation that hides a failure" pattern called out in the No-Fallbacks rule. If VS Code fails to inject its CSS variables (e.g., CSP misconfiguration, bundle loaded in a non-VS-Code context), the grid silently renders with the wrong font and text-measurement widths (the `measureCache` is based on measured widths which will differ for `sans-serif` vs VS Code's Segoe UI / system font). Column truncation becomes wrong — cells will either truncate too early or overflow.

**Compare with `readPalette`:** The palette uses a `v(name, fallback)` helper that also silently substitutes. However, palette colours are purely cosmetic; wrong font metrics silently corrupt the Value column truncation logic (the `truncateToWidth` binary search uses measured widths).

**Severity distinction from H:** This is a MEDIUM because `--vscode-font-family` is almost always present in VS Code webviews; the scenario where it is absent is unlikely in production. But it is a genuine No-Fallbacks violation.

**Minimal fix:** `console.warn` when the variable is missing, then fall back:

```ts
const raw = getComputedStyle(document.body).getPropertyValue('--vscode-font-family').trim();
if (raw.length === 0) {
    console.warn('[sheets-webview] --vscode-font-family CSS variable not found; using sans-serif');
}
const family = raw.length > 0 ? raw : 'sans-serif';
```

### M2 — `readPalette` silently falls back for all 7 colour variables (canvasGrid.ts:260–272)

**File:line:** `webview/sheets-webview/canvasGrid.ts:258-273`

```ts
private readPalette(): Palette {
    const cs = getComputedStyle(document.body);
    const v = (name: string, fallback: string): string => {
        const raw = cs.getPropertyValue(name).trim();
        return raw.length > 0 ? raw : fallback;
    };
    return {
        foreground:  v('--vscode-foreground', '#cccccc'),
        background:  v('--vscode-editor-background', '#1e1e1e'),
        headerBg:    v('--vscode-toolbar-hoverBackground', 'rgba(90,93,94,0.31)'),
        border:      v('--vscode-panel-border', 'rgba(128,128,128,0.35)'),
        descriptionFg: v('--vscode-descriptionForeground', '#9d9d9d'),
        errorFg:     v('--vscode-errorForeground', '#f48771'),
        errorBg:     v('--vscode-inputValidation-errorBackground', 'rgba(190,40,40,0.25)'),
    };
}
```

**How it hides failures:** Every CSS variable has a silent hardcoded fallback. If VS Code CSS injection fails (CSP issue, early bundle evaluation), all 7 colours silently fall back to dark-theme defaults. A user on a light theme would see dark colours without any indication that the theme variables were missing. No log, no warning.

**Severity:** Lower than M1 because colour fallbacks are cosmetic; they don't corrupt measurement math. Still a No-Fallbacks violation — the rule says no graceful degradation that hides a failure.

**Minimal fix:** Add a single guard — if `--vscode-foreground` is absent, log once:

```ts
const foregroundRaw = cs.getPropertyValue('--vscode-foreground').trim();
if (foregroundRaw.length === 0) {
    console.warn('[sheets-webview] VS Code CSS theme variables not injected; using hardcoded fallbacks');
}
```

### M3 — `commitEdit` early-returns silently when `fullSnapshot` is null or `editState` is null (index.ts:161–170)

**File:line:** `webview/sheets-webview/index.ts:161-170`

```ts
function commitEdit(): void {
    if (editState === null || fullSnapshot === null) {
        return;
    }
    if (editState.pendingCommit) {
        return; // duplicate Enter guard
    }
    // ...
}
```

**How it hides failures:** The `fullSnapshot === null` check is a guard against a state that should be impossible in normal flow: the user cannot be editing (which sets `editState`) without having first received a render (which sets `fullSnapshot`). But if this invariant is violated — e.g., by a bug in message ordering, or by a race between a dispose and a user keypress — `commitEdit` silently drops the commit. The user pressed Enter, nothing happened, no error is surfaced. The user doesn't know whether the commit was sent or not.

The `editState === null` guard is legitimate — it guards against `commitEdit` being called from outside an active edit (e.g., Enter with no cell selected). The `fullSnapshot === null` guard is the questionable one: if we have an `editState`, we should always have a `fullSnapshot`.

**Minimal fix:** Assert the invariant loudly:

```ts
function commitEdit(): void {
    if (editState === null) {
        return; // no active edit -- legitimate early return
    }
    if (fullSnapshot === null) {
        // This should be unreachable: editing requires a prior render.
        console.error('[sheets-webview] commitEdit: editState is set but fullSnapshot is null -- invariant violation');
        cancelEdit();
        return;
    }
    // ...
}
```

### M5 — `classifyPollTick` catch-returns a `PollTickResult` instead of propagating (cellGridLogic.ts:58–72)

**File:line:** `src/quantbook/cellGrid/cellGridLogic.ts:58-72`

```ts
export function classifyPollTick(session: CollabSessionInstance): PollTickResult {
    try {
        const n = session.pollRemote();
        if (n > 0) {
            return { kind: 'merged', count: n };
        }
        return { kind: 'idle' };
    } catch (err) {
        const info = parseQuantbookError(err);
        if (info.code === 'transport_closed') {
            return { kind: 'transportClosed' };
        }
        return { kind: 'error', code: info.code, message: info.message };
    }
}
```

**How it hides failures:** Every throw from `pollRemote` is caught and returned as a typed result. This is the "classify errors as values" pattern. The caller is expected to handle `{ kind: 'error' }` — but if the caller silently ignores a `{ kind: 'error' }` result (which the dormant collab path may do), the error is hidden. The function itself is on the dormant collab path (v1.5), so this is a risk for the re-enable rather than an active bug.

**Severity note:** This is a known architectural pattern for poll-tick classification, not a clear swallow. The function is exported (mocha coverage exists) and the error kind carries the full `code`+`message`. The risk is that callers may not handle `{ kind: 'error' }`. Rated MEDIUM because the pattern is intentional but the dormant path's callers are untested.

**Minimal fix for re-enable:** Ensure any re-enable of `classifyPollTick` has a caller that surfaces `{ kind: 'error' }` via at minimum `console.error` or a VS Code error message.

### M6 — `refreshAll` after sheet-management operations swallows the `refreshAll` failure (quantbookCommands.ts multiple locations)

**File:line:** `src/commands/quantbookCommands.ts:467-479`, `540-550`, `607-618`, `671-682`

Pattern repeated 4 times (addSheet, renameSheet, deleteSheet, moveSheet):

```ts
if (opSucceeded) {
    try {
        const { refreshed, failed } = CellGridPanel.refreshAll();
        log.appendLine(`Refreshed ${refreshed} panel(s)...`);
        if (failed > 0) {
            void vscode.window.showWarningMessage(`...`);
        }
    } catch (err) {
        const detail = err instanceof Error ? err.message : String(err);
        log.appendLine(`refreshAll after addSheet failed (non-fatal): ${detail}`);
        // ← NO showErrorMessage; logged only
    }
}
```

**How it hides failures:** The outer `catch` on `refreshAll` logs to the output channel but does NOT surface a VS Code message to the user. Since the output channel is not shown by default (only the initial FATAL errors call `log.show(true)` or use `showErrorMessage`), a user who does not have the Quantbook output channel open will see the sheet-management operation succeed (the `showInformationMessage` ran in the opSucceeded block) and then silently fail to see the re-render. They look at the panel, it shows stale data, they don't know why.

**Comparison:** This is the No-Fallbacks rule's "errors must be VISIBLE" clause. The error is logged but not visible unless the user opens the output channel. The rule requires at minimum `showWarningMessage`.

**Minimal fix (same for all 4 locations):**

```ts
} catch (err) {
    const detail = err instanceof Error ? err.message : String(err);
    log.appendLine(`refreshAll after addSheet failed: ${detail}`);
    void vscode.window.showWarningMessage(`Quantbook: sheet change succeeded but panel re-render failed -- ${detail}`);
}
```

### L1 — `?? 0` in `cellContentRect` on out-of-bounds `colIndex` (gridLayout.ts:76)

**File:line:** `webview/sheets-webview/gridLayout.ts:72-79`

```ts
export function cellContentRect(...): { x, y, width, height } {
    return {
        x: columnX(colIndex),
        y: HEADER_HEIGHT + entryIndex * ROW_HEIGHT,
        width: COLUMNS[colIndex]?.width ?? 0,   // ← ?? 0 fallback
        height: ROW_HEIGHT,
    };
}
```

**How it hides failures:** `COLUMNS[colIndex]?.width ?? 0` returns `0` if `colIndex` is out of bounds (>= 3). This means a zero-width cell rect would be returned without any indication. The overlay editor `<input>` would be positioned with zero width — invisible but not an error. The only callers pass `VALUE_COL_INDEX = 2`, which is always valid, so this never fires in practice. But if a future caller passes an invalid index, it silently gets a zero-width rect instead of a thrown error.

**Minimal fix:** Throw on out-of-bounds instead of returning `0`:

```ts
const col = COLUMNS[colIndex];
if (col === undefined) {
    throw new Error(`[bad_argument] cellContentRect: colIndex=${colIndex} is out of range (COLUMNS.length=${COLUMNS.length})`);
}
return { x: columnX(colIndex), y: HEADER_HEIGHT + entryIndex * ROW_HEIGHT, width: col.width, height: ROW_HEIGHT };
```

### L2 — `window.devicePixelRatio || 1` fallback in `resolveDpr` (canvasGrid.ts:67)

**File:line:** `webview/sheets-webview/canvasGrid.ts:67`

```ts
private static resolveDpr(): number {
    return Math.min(2, Math.max(1, Math.ceil(window.devicePixelRatio || 1)));
}
```

**How it hides failures:** `window.devicePixelRatio || 1` returns `1` when `devicePixelRatio` is `0` (which the spec allows for non-display contexts) or `undefined`/`null` (which shouldn't happen in a browser webview, but could in headless test environments). In a headless context, the webview should throw or warn rather than silently pretending it's a 1× display. In production (VS Code webview), `devicePixelRatio` is always set; this is LOW risk.

**Minimal fix:** `window.devicePixelRatio ?? 1` would be cleaner (avoids treating `0` as falsy, which is actually the wrong DPR) — but even better would be a `console.warn` when `devicePixelRatio` is `0` or `NaN`.

## MEDIUM findings

### M-1: `parseCellRawInput` exported from `cellGridLogic.ts` is dead in live code but not labelled dormant

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:163`

`parseCellRawInput` was the numeric-only parser for the old CollabSession path
(`appendPutValue` took `f64`, so every cell had to be a number). Since FE-0a
Part B1, `dispatchIncomingMessage` routes through `classifyCellInput` instead
(text / number / blank). `parseCellRawInput` is still exported but has zero
callers in live code (no import outside tests).

The function's docstring (lines 103–112) says "V3.2.b ONLY supports numeric
cells — the V1 napi `appendPutValue` binding takes a `f64`…". This is now
stale — `Session.setValue` accepts text/boolean/blank. If someone looking at
this file copies the `parseCellRawInput` pattern for a future input path,
text cells will silently become `[bad_argument]` rejections.

**Test refs:** imported + exercised at `quantbook-roundtrip.test.ts:2317`.

**Classification:** Intentionally dormant for v1.5? No — `parseCellRawInput`
served the old CollabSession numeric-only path, which is superseded (not
re-enabled at v1.5). It is cleanly dead. Risk: drift-source (stale
numeric-only docstring) rather than a No-Fallbacks violation.

**Recommendation:** Mark it `/** @deprecated — superseded by classifyCellInput
(FE-0a B1); numeric-only. Remove when the old-path tests are migrated. */` and
suppress the export, OR delete it together with its ~60 tests that only exercise
`buildHtml`/`computeVisibleRange` on the deprecated DOM-table path (that cleanup
is in the same scope as cellGridHtml.ts retirement, see M-2).

### M-2: `computeVisibleRange` in `cellGridLogic.ts` is orphaned from live code — its only live use was `buildHtml`, which is dead

**File:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:437`

`computeVisibleRange(scrollTop, rowHeight, viewportHeight, totalRows, overscan)`
was the host-side virtualization helper for `buildHtml`'s DOM-table scroll
logic. The canvas webview uses `computeVisibleRowRange` from
`webview/sheets-webview/cellRender.ts` (different argument order; deliberately
renamed). No live production code calls `computeVisibleRange`.

The docstring at line 418 is accurate about its DOM-table origin but does not
flag it as "retired with the DOM table". A developer reading `cellGridLogic.ts`
might try to call it from the canvas path and inadvertently use the wrong
argument order (scrollTop, **rowHeight**, viewportHeight, totalRows vs the
canvas order scrollTop, **viewportHeight**, totalRows, rowHeight).

**Test refs:** imported + exercised at `quantbook-roundtrip.test.ts:2317` and
directly called ~10 times in that file's virtualization suites.

**Classification:** Dormant / dead in production. The name distinction and the
docstring note at `cellRender.ts:51–53` partially mitigate the confusion, but
the `cellGridLogic.ts` export has no analogous note pointing at the difference.

**Recommendation:** Add a note to the `cellGridLogic.ts:437` docstring: "HOST
COPY — kept for the test suite that exercises the old DOM-table virtualization
path (`buildHtml`). The live canvas path uses `computeVisibleRowRange` in
`cellRender.ts` (different arg order). Remove alongside `cellGridHtml.ts`."

### M-4: `cellGridHtml.ts` inline script emits `presenceUpdate` + `typing_stroke` — the live canvas webview (`index.ts`) does NOT handle those messages, creating a silent drift surface for v1.5

**Files:**
- `extensions/quantlab/src/quantbook/cellGrid/cellGridHtml.ts:401,487,506,518`
- `extensions/quantlab/webview/sheets-webview/index.ts:263–284`

The client script inside `buildClientScript()` (still embedded in
`cellGridHtml.ts`) emits `presenceUpdate` (on `beginEdit` and `endEdit`) and
`typing_stroke` (on each `input` event). The live canvas webview (`index.ts`)
has NO `presenceUpdate` or `typing_stroke` outbound message path — the
redesigned webview was intentionally stripped of those envelopes (it does not
call `acquireVsCodeApi().postMessage({type:'presenceUpdate',...})`).

This is known and expected: `dispatchIncomingMessage` silently drops both
(lines 316–318 of `cellGridLogic.ts` with the explicit B1 comment). The
RISK is not in the current live grid but in re-enable: if v1.5 collab
reactivation adds presence to the canvas webview by diffing against
`cellGridHtml.ts` as the reference, the developer will copy the inline-script's
`presenceUpdate` shape (which round-trips over `acquireVsCodeApi()`) rather than
the correct FE-0b architecture (persistent postMessage to the bundled webview).
The inline script architecture and the persistent-bundle architecture have a
different message-channel lifecycle — the inline script fires `acquireVsCodeApi()`
on every full rebuild of `webview.html`, which no longer happens.

**Classification:** Intentionally dormant (the `cellGridHtml.ts` as a whole is
kept for v1.5 per CONTEXT.md), but the inline script is an architectural drift
hazard for the v1.5 re-enable.

**Recommendation:** Add a block comment at the top of `buildClientScript()` in
`cellGridHtml.ts`: "FE-0b ARCHITECTURAL NOTE: the presence/typing_stroke emit
logic here uses the inline-script / `acquireVsCodeApi()` model (one
`acquireVsCodeApi()` per full `webview.html` rebuild). The live canvas webview
(FE-0b) is a PERSISTENT bundle with a single `acquireVsCodeApi()` call on load
(guarded by `__sheetsVscodeApi`). Any v1.5 presence re-enable MUST use the
persistent postMessage channel (`index.ts`), not this inline-script shape."

## cellGridHtml.ts risk assessment (checklist item 1)

Per CONTEXT.md, `cellGridHtml.ts` is KNOWN DEAD and its ~60 test refs are a
known deferred cleanup. This audit found:

1. **No live import outside tests.** The only src references are:
   - `cellGridPanel.ts:39` — a comment saying `buildHtml` is no longer called.
   - `cellGridLogic.ts:12,467` — documentation references (L-5 above).
   - `types.ts:172` — documentation reference (L-2 above).
   None of these are `import` statements pulling executable code from
   `cellGridHtml.ts`.

2. **~74 test references** (grep count) in `quantbook-roundtrip.test.ts` (72)
   and `quantbook-udf-worker.test.ts` (2). All are test-only; no production
   build step imports the file.

3. **The inline script inside `buildClientScript` emits `presenceUpdate` and
   `typing_stroke`** — these are harmless in isolation (the file is not
   executed in production) but create a v1.5 re-enable drift hazard (M-4).

4. **Retirement scope is clean**: deleting `cellGridHtml.ts` requires:
   - Removing its two test-file import lines and the test suites that use
     `buildHtml`/`formatCellValue` from it (the `formatCellValue` tests should
     migrate to `cellRender.ts` which already exports the same function).
   - Removing the `computeVisibleRange` + `buildVirtualRows` test suites from
     `quantbook-roundtrip.test.ts` (they have no canvas equivalent, or could
     migrate to `computeVisibleRowRange`).
   - Removing the dormant `CellGridHtmlOptions`/`PresencePanelSnapshot` type
     references in `cellGridHtml.ts` (they'll lose their only documentation
     consumer).
   - Updating the doc comments in `types.ts` and `cellGridLogic.ts` (L-2..L-5).
   There are **no runtime risks** to retirement; the risk of KEEPING it is
   the v1.5 re-enable drift surface catalogued in M-4.

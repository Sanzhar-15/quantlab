## HIGH findings

### H1 — Session never closed when panel is disposed (`cellGridPanel.ts:132`, `quantbookCommands.ts:254`)

**Severity**: HIGH  
**File:line**: `cellGridPanel.ts:132` (onDidDispose handler), `quantbookCommands.ts:231-261`

**Scenario**:  
Every invocation of `quantlab.quantbookCellGrid` creates a fresh `Session` via `createWorkbookSession()`, seeds sample data, and hands it to `CellGridPanel.show(context, session, 0)`.  When the user closes the VS Code panel tab, `onDidDispose` fires. The handler (lines 132–141) sets `_disposed`, clears the watchdog, and removes the registry entry. It does **not** call `session.close()`.

`Session.close()` is documented as the deterministic release of the napi handle (types.ts:2124–2128). Without it the engine-side `WorkbookSession` (Rust memory + oplog + any open file handles) is kept alive by the JS reference that lives inside the `CellGridPanel` instance. That instance itself is referenced by the closure captured in `context.subscriptions` via `panel.onDidReceiveMessage(..., context.subscriptions)` (cellGridPanel.ts:118–122) and `context.subscriptions.push(panel)` (line 143).

`context.subscriptions` is the extension-lifetime array; it is only cleared when the extension is deactivated. So the `CellGridPanel` instance (and therefore the `SessionInstance` it holds) is not GC-eligible until extension deactivation, even after the panel tab is closed.

In the `quantbookCellGrid` command there is no path that closes the fresh session unless the user runs `quantbookOpen` (which closes displaced sessions explicitly). Repeated open-and-close cycles grow a list of zombie sessions, each holding a live Rust `WorkbookSession` handle.

**Concrete leak path**:  
1. User runs `Quantbook: Open Cell Grid` → session S1 created.  
2. User closes the tab → `onDidDispose` fires; S1 is NOT closed.  
3. User runs the command again → session S2 created.  
4. S1 is still alive (referenced from context.subscriptions via the disposed panel's subscription entry). The napi handle to the engine's `WorkbookSession` is not released.

**Minimal fix**:  
Add `session.close()` inside `onDidDispose`, guarded by a try/catch that logs but does not swallow:

```ts
panel.onDidDispose(() => {
    instance._disposed = true;
    instance.clearReadyWatchdog();
    if (panels.get(sheet) === instance) {
        panels.delete(sheet);
    }
    try {
        instance.session.close();
    } catch (err) {
        console.warn('[cellGrid] session.close() on dispose:', err instanceof Error ? err.message : String(err));
    }
});
```

The `session` field on `CellGridPanel` is `private readonly`; it would need to be promoted to `private` (not `readonly private`) or the close call needs to be inside the `show()` closure where `session` is in scope — either approach works. The `closeSessionQuietly` helper already exists in `quantbookCommands.ts`; consider moving it to `cellGridPanel.ts` so the dispose handler can use it.

### H2 — `onDidReceiveMessage` subscription outlives the panel (`cellGridPanel.ts:118–122`)

**Severity**: HIGH (use-after-free / stale-closure callback)  
**File:line**: `cellGridPanel.ts:118–122`

**Scenario**:  
The message listener is registered as:

```ts
panel.webview.onDidReceiveMessage(
    (raw: unknown) => instance.handleIncoming(raw),
    undefined,
    context.subscriptions,         // ← lifetime anchor
);
```

Using `context.subscriptions` as the disposable array means the VS Code runtime will keep the listener alive until **extension deactivation**, not until **panel disposal**. The VS Code API contract for `onDidReceiveMessage` is that the listener should be disposed with the panel; the correct idiom is to either:
- pass `undefined` for the array and store the returned `Disposable` yourself, then call `.dispose()` inside `onDidDispose`, or  
- pass a **panel-scoped** disposable array, not `context.subscriptions`.

**Consequence**: After the panel is disposed, any pending message delivery from the webview (buffered in the renderer process before the panel's destroy is acknowledged) calls `instance.handleIncoming(raw)`. `handleIncoming` checks `_disposed` in the `onError` path (line 389) but NOT before calling `dispatchIncomingMessage` — which in turn calls `deps.session.setValue` / `deps.session.setFormula` / `recalcDirtyChecked` on a session that may have been closed (see H1). If H1 is fixed and the session is closed on dispose, a late `dispatchIncomingMessage` call would hit `[invalid_state]` from the closed session, producing an `errorReply` that then tries to `panel.webview.postMessage` a reply to an already-disposed panel — the `_disposed` guard there prevents a crash but the underlying call path still exercises a closed session.

Even without H1, calling `deps.session.setValue` on a session whose owner no longer expects writes is a semantic UAF: the session may be reused by the next `quantbookCellGrid` invocation if the JS GC hasn't collected it (unlikely but not impossible with the context.subscriptions pin).

**Minimal fix**:  
Collect the listener in a panel-scoped array and dispose it in `onDidDispose`:

```ts
const panelDisposables: vscode.Disposable[] = [];
panel.webview.onDidReceiveMessage(
    (raw: unknown) => instance.handleIncoming(raw),
    undefined,
    panelDisposables,
);
// ... later in onDidDispose:
panel.onDidDispose(() => {
    instance._disposed = true;
    instance.clearReadyWatchdog();
    panelDisposables.forEach(d => d.dispose());
    if (panels.get(sheet) === instance) { panels.delete(sheet); }
    // + session.close() (H1 fix)
});
```

Note: using `context.subscriptions` here was likely copy-pasted from the established pattern for registering commands/providers, where extension-lifetime is correct. For per-panel listeners it is wrong.

## MEDIUM findings

### M1 — ResizeObserver never disconnected; persists across hide/show (`index.ts:291–293`)

**Severity**: MEDIUM  
**File:line**: `webview/sheets-webview/index.ts:291–293`

**Scenario**:  
```ts
if (typeof ResizeObserver !== 'undefined') {
    new ResizeObserver(() => redraw()).observe(viewportEl);
}
```

The `ResizeObserver` instance is not stored in any variable. It cannot be disconnected. With `retainContextWhenHidden:true` the webview is never destroyed between panel hide/show cycles; the observer accumulates in the browser context for the lifetime of the extension process. Since there is only ONE observer for the ONE viewport element this is a single-allocation leak (not a repeated one), so the practical impact is bounded to a single dangling observer per panel — but there is no mechanism to clean it up if the renderer ever needs a "reload" path (e.g., a future "reset grid" command that reconstructs the skeleton).

More concretely: the `CanvasGridRenderer.resize()` call inside `redraw()` reads `viewportEl.clientWidth/Height`. If the webview content is hidden (`retainContextWhenHidden:true` suspends layout but does not destroy it), a resize event fired by VS Code while the panel is hidden may drive a resize with zero dimensions, setting `canvas.width = 1, canvas.height = 1` (the `Math.max(1, ...)` floor). The next `show()` will redraw and correct the size, but the intermediate state is a 1×1 backing store.

**Minimal fix**:  
Store the observer and expose a disconnect path. Since the webview has no explicit "destroy" lifecycle hook, a `window.addEventListener('unload', ...)` guard is the closest equivalent in the persistent-webview model:

```ts
let resizeObserver: ResizeObserver | undefined;
if (typeof ResizeObserver !== 'undefined') {
    resizeObserver = new ResizeObserver(() => redraw());
    resizeObserver.observe(viewportEl);
}
window.addEventListener('unload', () => {
    resizeObserver?.disconnect();
    bodyObserver.disconnect();
});
```

### M2 — MutationObserver never disconnected (`index.ts:296–299`)

**Severity**: MEDIUM  
**File:line**: `webview/sheets-webview/index.ts:296–299`

**Scenario**:  
```ts
new MutationObserver(() => {
    renderer.refreshTheme();
    redraw();
}).observe(document.body, { attributes: true, attributeFilter: ['class'] });
```

Same structural issue as M1: the observer instance is unreferenced and cannot be disconnected. In a persistent webview it lives forever. Again, since the body is a singleton and the observer is created once, this is a bounded single-allocation leak — but if VS Code's theme system fires many rapid class changes (e.g., during a theme preview), each fires `renderer.refreshTheme()` + a full `redraw()`. `refreshTheme` clears `measureCache` and re-reads `getComputedStyle`, both of which are synchronous but non-trivial on a large document. No debounce is in place.

**Minimal fix**: store the reference and disconnect on `unload` (same guard as M1).

### M3 — `measureCache` eviction strategy causes thundering-herd on large sheets (`canvasGrid.ts:246–256`)

**Severity**: MEDIUM  
**File:line**: `canvasGrid.ts:246–256`

**Scenario**:  
```ts
private measure(text: string): number {
    let w = this.measureCache.get(text);
    if (w === undefined) {
        w = this.ctx.measureText(text).width;
        this.measureCache.set(text, w);
        if (this.measureCache.size > MEASURE_CACHE_MAX) {
            this.measureCache.clear();     // ← drop the entire cache
        }
    }
    return w;
}
```

When the Map reaches 5001 entries it is cleared wholesale. The next frame that draws the full visible window will `measureText()` for every distinct string again — O(visible_rows × columns_per_row) `measureText()` calls in a single `draw()` call. `measureText()` is synchronous and forces a style + text metrics recalculation in the browser. For a sheet with 1000 rows scrolled to mid-point (overscan 2, ~30 visible rows × 3 columns = 90 strings, but many unique), this is manageable. For the deferred FE-2 true 2D sheet with wide columns, a thundering miss on every scroll frame after the cache eviction would cause visible jank.

The MEASURE_CACHE_MAX=5000 cap prevents unbounded growth, which is correct. The issue is the clear-all strategy; a simple LRU (evict oldest 10% or use a Map-insertion-order delete) would avoid the thundering miss.

This is not a bug for the current 3-column list grid (30–90 distinct strings visible at once is well under 5000), but it will become a real perf problem once FE-2 expands to a full 2D grid.

**Minimal fix** (deferred to FE-2 is acceptable):  
```ts
if (this.measureCache.size > MEASURE_CACHE_MAX) {
    // Evict oldest 20% to avoid thundering-miss on the next frame.
    const toDelete = Math.ceil(MEASURE_CACHE_MAX * 0.2);
    let deleted = 0;
    for (const k of this.measureCache.keys()) {
        if (deleted >= toDelete) break;
        this.measureCache.delete(k);
        deleted++;
    }
}
```

### M4 — `quantbookCellGrid` command leaks `errorCells` across renders when a panel is reused (`index.ts:89`, `index.ts:109–121`)

**Severity**: MEDIUM (stale decoration, not a memory leak)  
**File:line**: `webview/sheets-webview/index.ts:109–121`

**Scenario**:  
`applyRender()` calls `errorCells.clear()` on every `render` push from the host. This is intentional: a committed write is a success, so the decoration should vanish. However, `applyRender` is the ONLY path that clears `errorCells`. If the user triggers a sheet switch (panel is revealed for a different sheet via `CellGridPanel.show(context, session, newSheet)`) the single-tab-per-sheet logic creates a NEW panel for the new sheet — the old panel's webview is not cleared of error decorations, but it is not rendered until revealed again (the host's `render()` clears them on reveal). This path is therefore safe.

The edge case: the `SwitchSheet` command calls `CellGridPanel.show(context, session, selection.sheet)` which for a new sheet creates a fresh panel/webview. But for the SAME sheet it reveals + calls `existing.render()`, which sends a fresh `render` message that clears errors. OK.

**Real gap**: If a `render` message is posted but NOT delivered (the `delivered === false` warning path in `postRenderIfReady`), `errorCells` is NOT cleared because the webview never received the `applyRender` call. The user then sees stale error decorations on a cell that may have been successfully updated. The host logged a warning but the webview state is stale. This is a narrow race (typically the panel is visible and `postMessage` delivers), but it is a correctness gap: a non-delivered render leaves the webview in an inconsistent state with no recovery mechanism.

**Minimal fix**: On the `delivered === false` path, post a follow-up render after a short delay (or instruct the user to refresh). Alternatively, keep the `latestSnapshot` and re-send on the next `render()` call (which already happens via the `webviewReady` handshake path — extend that logic to the non-delivered path too).

### M5 — `retainContextWhenHidden:true` memory implication: `fullSnapshot` + `errorCells` live in renderer process forever (`index.ts:87–89`)

**Severity**: MEDIUM (known architectural cost; no fix without changing the model)  
**File:line**: `webview/sheets-webview/index.ts:87–89`

**Scenario**:  
With `retainContextWhenHidden:true`, the webview's JS context is never destroyed between hide/show cycles. `fullSnapshot` holds the last received `QuantbookCellSnapshot`. For large workbooks with many entries, this is a potentially large in-memory object in the renderer process (Electron renderer = separate process, but still). For FE-2's true 2D sheet at Excel parity scale (1M cells), `fullSnapshot` could become a multi-MB object pinned in the renderer even when the panel is hidden.

This is a **known, deliberate** trade-off (documented in `cellGridPanel.ts:103–107`: "no reload flash; this is the point of the persistent model"). The audit notes it as a MEDIUM because the current 3-column list model makes it safe (entries are sparse; typical workbooks have hundreds to low-thousands of cells). It becomes a HIGH when FE-2 delivers true 2D.

**Recommendation**: At FE-2, reconsider whether `retainContextWhenHidden:true` + a snapshot that holds the entire visible range is the right model, or whether a "compact on hide / reload on show" pattern is acceptable given FE-1's latency kill-gate.

## LOW findings

### L1 — `mousemove` handler performs `hitTestViewport` on every event without throttling (`index.ts:221–236`)

**Severity**: LOW  
**File:line**: `webview/sheets-webview/index.ts:221–236`

**Scenario**:  
The `mousemove` listener fires at raw mouse rate (typically 60–120 Hz on modern hardware, up to 1000 Hz on gaming mice). Each event calls `hitTestViewport()` — a pure O(1) geometry test — and then reads `errorCells.get()` and `entry.diagnostic`. All pure / Map operations; no DOM layout. The `lastHoverTitle` guard short-circuits the `canvas.title =` assignment on no-change, which is good.

The risk: on very large snapshots (FE-2 scale), `fullSnapshot.entries[hit.entryIndex]` lookup via direct index is O(1) and fine. `hitTestViewport` is a pure math function with no allocations. This is currently safe.

However, `hitTestViewport` calls `computeVisibleRowRange` which has a `Math.floor`/`Math.ceil`/`Math.max`/`Math.min` chain, and the mousemove fires while the user is actively dragging, which can overlap with scroll redraws. For the current list grid this is not a problem. For FE-2 the mouse rate should be capped via `requestAnimationFrame` or a 16ms debounce.

**Minimal fix** (defer to FE-2): wrap the mousemove handler body in an `rAF` gate.

### L2 — `acquireVsCodeApi` guard is correct but the comment describes a non-existent risk for the current architecture (`index.ts:57–63`)

**Severity**: LOW (doc clarity)  
**File:line**: `webview/sheets-webview/index.ts:57–63`

**Scenario**:  
The comment says: "the persistent webview could re-evaluate this bundle, e.g. 'Developer: Reload Webviews'". In a bundled persistent webview, "Developer: Reload Webviews" would destroy and re-create the webview context, at which point `acquireVsCodeApi()` is safe to call again (new context = new call is the first call). The guard is therefore not needed for that scenario. It IS needed if VS Code ever re-executes the bundle script within the same context (which it does not currently do), but the comment's stated reason is wrong.

The guard itself is harmless and defensive; the issue is only the incorrect comment. No fix required beyond updating the comment for accuracy.

### L3 — `panels` module-level Map is never explicitly cleared on extension deactivation

**Severity**: LOW  
**File:line**: `cellGridPanel.ts:69`

**Scenario**:  
`const panels: Map<number, CellGridPanel> = new Map()` is module-scope and lives until the process exits. When the extension deactivates, VS Code disposes everything in `context.subscriptions`. Since each panel is pushed to `context.subscriptions` (line 143), VS Code's dispose-on-deactivation fires `panel.dispose()` for each, which triggers `onDidDispose`, which calls `panels.delete(sheet)`. So the Map IS drained, just indirectly.

The risk: if any `panel.dispose()` call throws during extension deactivation, the corresponding `onDidDispose` may not fire and that entry stays in the Map. In practice extension deactivation is best-effort anyway, but the dependency on `onDidDispose` for cleanup is fragile.

**Minimal fix**: add an explicit `disposeAll()` call during extension deactivation (i.e., in the `deactivate()` export), which already exists as `CellGridPanel.disposeAll()`.

### L4 — `scroll` event listener on `viewportEl` is never removed (`index.ts:288`)

**Severity**: LOW  
**File:line**: `webview/sheets-webview/index.ts:288`

**Scenario**:  
```ts
viewportEl.addEventListener('scroll', redraw);
```

Like the ResizeObserver and MutationObserver, this listener is never removed. Since `viewportEl` is a singleton element in the persistent webview that lives forever, this is a bounded single allocation — but it means no cleanup path exists. Combined with M1/M2, the pattern is that zero event listeners in this file are ever removed.

For the current architecture this is acceptable because the webview context is destroyed only on extension deactivation (or explicit "Developer: Reload Webviews" which re-creates the context). The practical impact is zero. Flagged for completeness and as a hygiene signal.

### L5 — `document.addEventListener('keydown', ...)` for undo/redo is on `document`, not scoped to the panel element (`index.ts:240–259`)

**Severity**: LOW  
**File:line**: `webview/sheets-webview/index.ts:240–259`

**Scenario**:  
The undo/redo keydown listener is attached to `document`. This means Cmd-Z/Ctrl-Z fires undo even when focus is outside the grid (e.g., another VS Code panel or an unrelated webview). In the current single-webview-per-panel model this is fine because each webview has its own document. With `retainContextWhenHidden:true`, focus events should correctly prevent stale undo fires (you can't fire a keyboard event into a hidden webview). Not a real bug, flagged as best practice: scope keyboard shortcuts to the grid container, not `document`.

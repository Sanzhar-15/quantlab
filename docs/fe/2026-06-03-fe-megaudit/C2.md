# FE Megaudit - Lane C2 Correctness Deep-Dive

Read-only audit of the current Quantbook FE files. Product code was not modified.

## Verdict

Coordinate mapping is internally consistent after the prior sticky-header fix, and the normal `putValue -> setValue/setFormula -> recalc -> render` path uses sheet coordinates, not display indices. I found two HIGH correctness bugs in formula edit round-tripping and in-flight edit reply correlation, plus delta/tombstone visibility gaps and lower-risk dormant/math edge cases.

Counts: HIGH 2 / MEDIUM 2 / LOW 3.

## HIGH

### HIGH-1 - Formula cells can be converted to text by a no-op edit

Files:
- `extensions/quantlab/webview/sheets-webview/index.ts:145`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:376`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:385`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:388`
- `extensions/quantlab/src/quantbook/types.ts:1777`

`Session.setFormula` takes and snapshots the formula body with no leading `=`. The webview editor copies `entry.formula` directly into the input:

```ts
inputEl.value = typeof entry.formula === 'string' ? entry.formula : formatCellValue(entry.value);
```

But the host only routes a commit to `setFormula` when the submitted raw input starts with `=`. Otherwise it classifies the input as a literal and calls `setValue`.

Concrete failure:

1. A user enters `=A1*2` into entry B1.
2. Host sees `rawInput.trimStart().startsWith('=')`, strips the UI prefix, calls `setFormulaValidated(..., 'A1*2')`, runs `recalcDirtyChecked`, and renders.
3. The next `Session.snapshot()` exposes formula text as a body, for example `A1 * 2`, because the Session contract says formula text has no leading `=`.
4. User clicks the same cell and presses Enter without changing anything.
5. Webview sends `rawInput: 'A1 * 2'`.
6. Host does not see `=`, so `classifyCellInput('A1 * 2')` returns `{ kind: 'text', text: 'A1 * 2' }`.
7. `setValueValidated` replaces the formula cell with a text cell. A no-op edit destroys the formula.

Minimal fix:

Display formula cells in spreadsheet UI form by prefixing the body before edit, for example `inputEl.value = entry.formula.trimStart().startsWith('=') ? entry.formula : '=' + entry.formula`. Alternatively add an explicit `wasFormula`/edit-mode field to the `putValue` envelope and route unchanged formula bodies through `setFormula`. Add a regression test that clicking an existing formula and pressing Enter preserves a formula cell.

### HIGH-2 - In-flight edit replies are not correlated to the edit that produced them

Files:
- `extensions/quantlab/webview/sheets-webview/index.ts:109`
- `extensions/quantlab/webview/sheets-webview/index.ts:133`
- `extensions/quantlab/webview/sheets-webview/index.ts:161`
- `extensions/quantlab/webview/sheets-webview/index.ts:191`
- `extensions/quantlab/webview/sheets-webview/index.ts:272`

The pending-commit state is a single mutable flag on the current `editState`, but replies are not matched to the committed sheet/row/col or to a commit id. `beginEdit` also cancels an existing edit even if that edit has a commit in flight.

Concrete failure:

1. User edits cell A `(row=10,col=2)` and presses Enter. `commitEdit` sets `editState.pendingCommit = true` and posts `putValue`.
2. Before the host render/error returns, user clicks cell B. The input blur does not cancel because `pendingCommit` is true, but the canvas click calls `beginEdit(B)`.
3. `beginEdit` sees an existing `editState` and calls `cancelEdit()`, deleting the pending A editor, then opens B.
4. If A succeeds, `applyRender -> cancelEdit()` clears the B editor and loses any B text the user typed while A was being processed.
5. If A fails, the `errorReply` decorates A but the A input is gone. Worse, `errorReply` blindly runs `editState.pendingCommit = false` on whatever edit is current. If B was already pending, the old A error re-arms B and a repeated Enter can double-send B's commit.

Minimal fix:

Track the committed coordinate and a monotonically increasing commit id in `EditState`. While a commit is pending, either block starting another edit or keep the pending editor until its matching render/error arrives. On `errorReply`, only clear `pendingCommit` when `(sheet,row,col,commitId)` matches the active pending edit; otherwise only decorate the reported cell. Avoid unconditional `applyRender -> cancelEdit()` for an unrelated newer edit, or make pending commits modal so no newer edit can exist.

## MEDIUM

### MEDIUM-1 - Deleted active sheets render as ordinary empty sheets

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:286`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:292`
- `extensions/quantlab/webview/sheets-webview/canvasGrid.ts:120`

`extractSheetSnapshot` correctly returns `null` when the active sheet has been tombstoned. The panel then converts that to a normal empty `QuantbookCellSnapshot` and only logs a console warning. The webview renders the ordinary empty-sheet message:

```text
(empty -- no PutValue ops on this sheet)
```

Concrete failure:

1. Sheet 1 contains cells.
2. User deletes sheet 1 via the sheet-delete command.
3. `refreshAll()` rerenders the still-open sheet-1 panel.
4. `extractSheetSnapshot(wbSnapshot, 1)` returns `null`.
5. The panel sends `{ sheet: 1, entries: [] }`.
6. The user sees a live-looking empty Sheet 1, not "this sheet was deleted".

This violates the No-Fallbacks rule at the UI boundary: a tombstone state is masked as a valid empty sheet.

Minimal fix:

Do not encode tombstones as normal empty snapshots. Send an explicit deleted-sheet render state, show a visible in-webview message, and/or dispose/switch the panel after delete. At minimum, surface a visible warning tied to the affected panel instead of only `console.warn`.

### MEDIUM-2 - Delta merge silently drops cell deltas for unknown sheets and advances the cache version

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:1064`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:1069`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:1077`
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:1110`

`mergeWorkbookDelta` silently skips `changedCells` and `removedCells` when the referenced sheet is absent from the cached snapshot. It then advances `cached.version` to `delta.version`.

Concrete failure:

Cached snapshot has sheets `[0]`. Delta arrives with:

```ts
{
  fullRebuildRequired: false,
  changedCells: [{ sheet: 2, cell: { row: 5, col: 5, value: { kind: 'number', number: 99 } } }],
  removedCells: [],
  sheetsRemoved: [],
  formatsAdded: [],
  sheetsChanged: [],
  version: V2,
}
```

The merge finds no sheet 2, executes `continue`, and still sets `cached.version = V2`. The update is now lost and the next delta starts after V2, so the cache can remain permanently divergent from a fresh `snapshot()`.

The engine should not emit this in the current happy path, but this is exactly a contract violation or stale-cache signal. Skipping it hides the fault.

Minimal fix:

Fail loud or force a full rebuild when a non-fullRebuild delta references an unknown sheet. In this pure helper, throwing `[invalid_state] mergeWorkbookDelta: changed cell for unknown sheet ...` is preferable to advancing the version after an unmerged update. The caller can surface the error or discard the cache and re-seed.

## LOW

### LOW-1 - Host `computeVisibleRange` lacks the shrink clamp present in the webview copy

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:453`
- `extensions/quantlab/webview/sheets-webview/cellRender.ts:82`

The live canvas renderer uses `computeVisibleRowRange`, which clamps a stale large `scrollTop` to the last row after data shrink. The host copy `computeVisibleRange` does not.

Concrete failure:

```ts
computeVisibleRange(2400, 25, 100, 10, 5)
```

Math:

- `firstVisible = floor(2400 / 25) = 96`
- `visibleCount = ceil(100 / 25) = 4`
- `startIdx = 96 - 5 = 91`
- `endIdx = min(10, 96 + 4 + 5) = 10`

Result is `{ startIdx: 91, endIdx: 10 }`, so `startIdx > endIdx`. The webview copy correctly clamps `firstVisible` to `maxFirst = totalRows - 1 = 9`, producing `{ startIdx: 4, endIdx: 10 }`.

I found no current product caller mixing the two helpers: the canvas imports `computeVisibleRowRange`, and `computeVisibleRange` is used by tests/retired DOM-table scaffolding. This is still a stale exported helper and a reactivation hazard.

Minimal fix:

Apply the same `maxFirst` clamp to `computeVisibleRange`, or remove/retire the host virtualization helper with the dead DOM renderer.

### LOW-2 - `truncateToWidth` can split surrogate pairs or grapheme clusters

Files:
- `extensions/quantlab/webview/sheets-webview/gridLayout.ts:149`
- `extensions/quantlab/webview/sheets-webview/gridLayout.ts:160`

The binary search slices by UTF-16 code units. That can return malformed display text for emoji and other multi-code-unit characters.

Concrete failure with the existing fake-measurer style:

```ts
const measure = (s: string) => s.length * 10;
truncateToWidth('🙂x', 25, measure);
```

`'🙂x'.length` is 3. The full string measures 30, so truncation starts. `mid=2` measures `'🙂…'` as 30 and fails. `mid=1` measures a lone high surrogate plus ellipsis as 20 and succeeds. The function returns `'\uD83D…'`, which browsers can render as a replacement glyph plus ellipsis.

Minimal fix:

Search over display units instead of UTF-16 offsets. `Array.from(text)` avoids splitting surrogate pairs; `Intl.Segmenter` with grapheme granularity is better if available. Join the accepted prefix before appending the ellipsis.

### LOW-3 - Sheet-mismatched `putValue` gets no response and can leave the editor pending forever

Files:
- `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:344`
- `extensions/quantlab/webview/sheets-webview/index.ts:165`
- `extensions/quantlab/webview/sheets-webview/index.ts:191`

The normal webview sends `sheet: fullSnapshot.sheet`, so this should not happen in honest current UI. But if the sheet id ever diverges, the dispatcher logs a warning and returns without `onCommit` or `onError`.

Concrete failure:

1. Webview commits with `pendingCommit = true`.
2. Host receives `{ type:'putValue', sheet: 2, row: 0, col: 0, rawInput:'1' }` while `deps.sheet === 1`.
3. Dispatcher returns at the sheet-mismatch branch.
4. No render or `errorReply` reaches the webview.
5. Repeated Enter is ignored because `pendingCommit` stays true, and blur refuses to cancel while pending.

Minimal fix:

Return a structured `errorReply` for sheet mismatch, or otherwise send an explicit cancellation/render response so the webview can clear `pendingCommit`.

## Verified Contracts / No Finding

### Coordinate mapping at non-zero scroll

Constants:

- Columns: Row `[0,72)`, Col `[72,144)`, Value `[144,664)`.
- `HEADER_HEIGHT = 28`, `ROW_HEIGHT = 25`.

Worked example: `scrollLeft = 100`, `scrollTop = 300`, entry index `12`, Value column.

Canvas body draw:

- Content rect for entry 12 Value is `x = 144`, `y = 28 + 12*25 = 328`, `w = 520`, `h = 25`.
- `drawRow` local top is `28 + 12*25 - 300 = 28`.
- Value-cell local left is `144 - 100 = 44`.
- The canvas paints that cell at viewport-local `(44,28)`.

Overlay input placement:

- `cellContentRect(12, 2)` returns `{ x:144, y:328, width:520, height:25 }`.
- The input is an absolute scroller child in content coordinates, so its visual position is `(144 - 100, 328 - 300) = (44,28)`.
- This agrees with the canvas.

Hit testing:

- Click inside that cell at local `(54,33)`.
- `hitTestViewport` first checks sticky header: `33 >= 28`, so continue.
- Content point is `(54 + 100, 33 + 300) = (154,333)`.
- `hitTestContent`: `entryIndex = floor((333 - 28) / 25) = floor(305/25) = 12`; `contentX=154` is in Value `[144,664)`.
- This agrees with canvas and input.

Sticky header rejection:

- Header click at local `(54,10)` with the same scrolls.
- `10 < 28`, so `hitTestViewport` returns `null` before adding scroll.
- Without this local check, contentY would be `310`, yielding `floor((310 - 28) / 25) = 11`, incorrectly editing row 11 under the sticky header.
- The current implementation is correct.

HiDPI:

- `resize` sizes the backing store to CSS size times resolved DPR.
- `draw` calls `ctx.setTransform(this.dpr, 0, 0, this.dpr, 0, 0)` every frame, so scale is not cumulative.
- All geometry passed to canvas is in CSS pixels. I found no DPR coordinate mis-scale. The DPR is rounded/clamped for quality/cost, but the coordinate system remains consistent.

### `putValue` sheet coordinates and recalc order

Click-to-edit stores the actual snapshot entry, not just the display index. `commitEdit` sends `row: Number(entry.row)` and `col: Number(entry.col)`, so it writes the sheet coordinate even when entry index differs from sheet row.

Normal formula entry is correctly stripped once:

1. Webview sends raw `'=A1*2'`.
2. Host detects leading `=`.
3. Host computes formula body `'A1*2'`.
4. Host calls `setFormulaValidated`.
5. Host calls `recalcDirtyChecked` before `onCommit`.
6. `onCommit` renders from a fresh/delta snapshot after recalc.

The HIGH-1 finding is specifically the reverse direction: editing an existing formula whose snapshot text is already body-only.

### Delta/snapshot ordinary path

The ordinary delta merge paths are correct for the current tested engine contract:

- `changedCells` upsert by `(sheet,row,col)` and preserve sorted cell order.
- `removedCells` remove the targeted cell.
- `sheetsRemoved` are applied last, so same-delta cell changes cannot resurrect a removed sheet.
- `formatsAdded` merge by full format id.
- `fullRebuildRequired` is handled by `acquireWorkbookSnapshotViaDelta` before merge.
- `extractSheetSnapshot` returns `null` for a tombstoned/missing active sheet.

The MEDIUM findings are the unknown-sheet silent skip and the render-layer masking of that `null` tombstone as an ordinary empty sheet.

### Header/body text measurement

The measure cache is keyed only by text, but current code only calls `measure()` while `ctx.font` is the body font. `drawHeader` uses the header font for direct `fillText` only and restores the body font before returning. I found no current header/body font measurement poisoning.

# FE Megaudit - Lane C1 SECURITY

Scope: landed Quantbook FE cell-grid webview, host dispatcher, `.qbook` open/save command path, browser bundle isolation, and the Session/napi boundary. I read the current source and the runtime built webview artifact where relevant.

## HIGH

No HIGH findings.

I independently traced the main candidate HIGH paths:

- CSP/shell injection: `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:428-445` builds a static shell. Snapshot/cell/formula/diagnostic data is not interpolated into this HTML; it is sent later via `webview.postMessage` at `cellGridPanel.ts:327`.
- Malformed edit envelopes: `dispatchIncomingMessage` reaches `setValueValidated` / `setFormulaValidated` at `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:376-389`; those wrappers validate u16/u32 coordinate domains before the napi call at `extensions/quantlab/src/quantbook/session.ts:193-223` and `session.ts:240-252`. The Rust napi layer also validates raw `f64` coordinates before integer conversion at `../quantlab-quantbook/quantbook-engine/crates/ql-bindings-node/src/lib.rs:4355-4367`, with `setValue`/`setFormula` using that converter at `lib.rs:5718-5724` and `lib.rs:5744-5749`.
- Canvas XSS: the live webview source uses a static `root.innerHTML` skeleton only at `extensions/quantlab/webview/sheets-webview/index.ts:69-76`, then `textContent`, `input.value`, canvas `fillText`, and `canvas.title` for data. The built artifact in `extensions/quantlab/dist/webview/quantbook/sheets-webview.js` matches this pattern.
- `.qbook` open: FE opens the selected folder into a fresh session before replacing current panels at `extensions/quantlab/src/commands/quantbookCommands.ts:367-433`. Rust loading uses fixed child paths (`workbook.toml`, `sheets/{id}.jsonl`) and validates schema/sheet ids/bounds at `../quantlab-quantbook/quantbook-engine/crates/ql-io/src/qbook_format.rs:1578-1845`.

## MEDIUM

### M1 - Host accepts unbounded `rawInput` strings from the webview before formula/text parsing

**Files:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:333-389`, `extensions/quantlab/src/quantbook/session.ts:213-216`, `extensions/quantlab/src/quantbook/session.ts:249-252`, `../quantlab-quantbook/quantbook-engine/crates/ql-bindings-node/src/lib.rs:5736-5749`

**Attack/failure:** A hostile webview script or tampered local bundle can post `{ type: 'putValue', sheet, row, col, rawInput }` with an extremely large string. The dispatcher checks only that `rawInput` is a string (`cellGridLogic.ts:333-343`), then either passes a formula body to `setFormulaValidated` (`cellGridLogic.ts:385-386`) or classifies/stores it as text (`cellGridLogic.ts:388`). The TS wrappers validate type and coordinate domains, but they do not cap formula/text length (`session.ts:213-216`, `session.ts:249-252`). The napi method receives the whole `String` and parses/binds formula text synchronously (`lib.rs:5736-5749`). This does not create an out-of-range write, but it is a concrete extension-host/Rust-engine DoS path via memory pressure or expensive formula parsing.

**Minimal fix:** Define a maximum cell input length at the host boundary, apply it before `trimStart()` / `classifyCellInput`, reject over-limit input with `[bad_argument]`, and mirror the cap in the napi/engine boundary for direct callers. Add tests for oversized text and formula bodies.

## LOW

### L1 - CSP nonce is generated with `Math.random`, not a CSPRNG

**Files:** `extensions/quantlab/src/utils/webview.ts:21-27`, `extensions/quantlab/src/quantbook/cellGrid/cellGridPanel.ts:429-443`

**Attack/failure:** The CSP itself is well shaped for this shell (`default-src 'none'`; nonce-scoped script; extension-resource styles/images), and the same nonce is used in the CSP and `<script>` tag. However `getNonce()` uses `Math.random()` to build the nonce. There is no current cell-data-to-shell-HTML injection path, so I do not see an exploitable XSS today, but CSP nonces should be unpredictable even if a future markup injection bug appears.

**Minimal fix:** Generate nonces with Node crypto, e.g. `crypto.randomBytes(16).toString('base64url')` or `crypto.getRandomValues`, and keep the existing per-shell fresh nonce behavior.

### L2 - Dispatcher rejects malformed coordinates before napi, but echoes unsanitized coordinates in error replies

**Files:** `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:333-347`, `extensions/quantlab/src/quantbook/cellGrid/cellGridLogic.ts:392-401`, `extensions/quantlab/webview/sheets-webview/index.ts:272-280`

**Attack/failure:** Bad `row`/`col` values do not reach Rust mutation unchecked: the TS wrappers and Rust converters reject fractions, `NaN`, `Infinity`, negatives, and out-of-range values before state mutation. But the dispatcher does not normalize the envelope first. On failure it sends `sheet: req.sheet, row: req.row, col: req.col` back to the webview (`cellGridLogic.ts:394-400`), and the webview coerces those fields with `Number(...)` for its error map (`index.ts:272-280`). A hostile message can therefore produce nonsensical reply coordinates such as `NaN,0`, failed decoration, or serialization edge cases. This is not an out-of-range write, but it weakens the trust-boundary contract.

**Minimal fix:** Add a single `validatePutValueEnvelope` step before the write branch that checks `sheet`, `row`, and `col` are finite integers in `[0, 65535]` / `[0, 4294967295]`, checks `sheet === deps.sheet`, and uses sanitized numeric coordinates in every `errorReply`. Add explicit `NaN`/`Infinity`/fractional/string-coordinate tests.

### L3 - The no-host-runtime esbuild guard is narrow; current bundle is safe, but the policy is not comprehensive

**Files:** `extensions/quantlab/esbuild-quantbook-webviews.mjs:45-67`, `extensions/quantlab/webview/sheets-webview/index.ts:27-30`, `extensions/quantlab/webview/sheets-webview/cellRender.ts:20`, `extensions/quantlab/src/quantbook/loader.ts:219-239`

**Attack/failure:** The current source imports only type mirrors from `src/quantbook/types` plus pure webview modules, and direct/indirect value imports of `session.ts` are blocked by the guard. But the guard only rejects specifiers matching `session` or `.node` (`esbuild-quantbook-webviews.mjs:48`). The native loader path is `process.dlopen` of `.dylib`/`.so`/`.dll` (`loader.ts:219-239`), not a `.node` import, and other host modules are not rejected by resolved path. Today esbuild's browser platform would also object to Node builtins for many host imports, but that is an incidental build failure, not a complete security policy.

**Minimal fix:** Replace the narrow denylist with an allowlist/metafile assertion: webview entries may import from `webview/sheets-webview/**` and type-erased mirrors only; any value import resolving under `src/quantbook` host runtime (`session`, `loader`, commands, panel/logic modules) or any native extension suffix (`.node`, `.dylib`, `.so`, `.dll`) should fail the build. Add a small regression fixture that proves a value import from host runtime fails while `import type` is erased.

## Verified Non-Findings

- CSP/local resources: `cellGridPanel.ts:101-112` enables scripts but narrows `localResourceRoots` to `dist/webview/quantbook`; `buildShellHtml` at `cellGridPanel.ts:428-445` contains no snapshot data. `style-src 'unsafe-inline'` is broader than ideal, but without a style injection path it is not a script execution vector under this CSP.
- Canvas/title XSS: cell/rendered/formula/error/diagnostic strings flow through `input.value` (`index.ts:145`), `textContent` (`index.ts:116-117`), canvas drawing (`canvasGrid.ts:166-178`), and `canvas.title` (`index.ts:229-234`). `title` is assigned as a DOM string property, not parsed as markup.
- QuickPick labels/panel titles: sheet names reach VS Code UI strings at `cellGridPanel.ts:300-306` and `cellGridLogic.ts:586-590`; these are not HTML sinks. They may render as UI text/codicon-like label syntax, but I did not find a DOM/script injection path.
- `.qbook` path traversal/arbitrary file: FE uses VS Code picker-returned `uri.fsPath` for save/open (`quantbookCommands.ts:341-352`, `quantbookCommands.ts:367-385`). The engine treats `.qbook` as a directory with fixed children and validates corrupt/missing content loudly before FE replaces the current session (`quantbookCommands.ts:381-412`). I did not find an attacker-controlled path component from workbook content.
- napi panic/coercion boundary: Session coordinate paths validate finite/integer/u16/u32 before mutation in both TS and Rust (`session.ts:193-223`, `session.ts:240-252`, `lib.rs:175-247`, `lib.rs:4355-4367`), and the bound Session methods are `catch_unwind` guarded (`lib.rs:5710-5750`, `lib.rs:6137-6179`).

Verdict: no current XSS, arbitrary file access, out-of-range write, or napi panic path found in the landed FE; harden oversized webview input and nonce/build-guard defense-in-depth. Counts: HIGH 0 / MEDIUM 1 / LOW 3.

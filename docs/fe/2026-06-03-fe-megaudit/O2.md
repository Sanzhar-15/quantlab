# FE Megaudit — Lane O2: End-to-End Integration + Single-Writer Invariant

**Scope:** the FE as a whole system. Full click→edit→commit→recalc→render→repaint loop;
the single-writer `Session` invariant across the dispatch path AND the command path AND
`refreshAll`; error-surfacing coherence napi→user; multi-panel/multi-sheet/Open-replaces
coherence; host↔webview protocol symmetry.

**Verdict:** SHIP-WITH-FIXES. The core single-panel loop is coherent and the No-Fallbacks
discipline is unusually well kept on the per-command error paths. But the **panel registry is
keyed by sheet number alone, ignoring which `Session` owns the panel** — this breaks the
single-writer model the moment a second workbook session exists (and "Open Cell Grid" mints a
new session on every invocation). Separately, the **engine cell-diagnostic tooltip path is
entirely dead** in the Session-backed panel, so UDF `#CALC!`/`#TIMEOUT!` explanations never
reach the user.

Counts: **HIGH 3, MEDIUM 5, LOW 4.**

---

## HIGH

### H1 — Panel registry keyed by sheet-id only: a second `Session` is silently discarded + leaked; cross-session writes collide
`cellGridPanel.ts:69` (`const panels: Map<number, CellGridPanel>`), `:84-89` (`show`),
`:155-166` (`refreshAll`), `:213-219` (`activeLocalPanels`); `quantbookCommands.ts:231-262`
(`quantbookCellGrid` mints a NEW `createWorkbookSession()` every call).

The registry maps `sheet → panel`, with NO session identity in the key. `show()` only checks
`panels.get(sheet)` and, if present, `reveal()`s + `render()`s the EXISTING panel — regardless
of whether `existing.session === session`. Concrete failure:

1. Run "Quantbook: Open Cell Grid" → session **A**, panel for sheet 0 registered at `panels[0]`.
2. Run "Quantbook: Open Cell Grid" **again** → `createWorkbookSession()` builds a fresh session
   **B** (seeded 0/1/2), then `CellGridPanel.show(context, B, 0)`. `panels.get(0)` returns the
   **A** panel; it is revealed + re-rendered against **A**. **Session B is never shown, never
   registered, and never `.close()`d — a silent native-handle leak**, and the user sees A's data
   under the impression they opened a fresh book.

This is not theoretical: the primary command's documented behavior is "opens a Session-backed
grid seeded with sample data," with no single-instance guard at the command layer.

The same key collision corrupts the command path's single-writer assumption. `activeLocalPanels()`
returns `panels.values()` and every sheet-management / Save-As command operates on `localPanels[0]`
= "the oldest open panel" (`quantbookCommands.ts:291, 340, 445, 490, 563, 630`). With two sessions
open across two sheets (e.g. A@sheet0, B@sheet1 — these DON'T collide on the key so both register),
"Add Sheet" / "Save As" / "Rename" all target whichever panel happens to be `values()[0]` —
**not the panel the user is looking at**. The user renames a sheet in session B while viewing
session A, or saves the wrong workbook. There is no "active panel" tracking (no
`onDidChangeViewState` wiring), so `[0]` is an arbitrary insertion-order pick.

**Minimal fix:** key the registry by `(session, sheet)` (e.g. a `WeakMap<SessionInstance,
Map<number, CellGridPanel>>`, or a composite key), and have `show()` only reveal-existing when
`existing.session === session` — otherwise create a new panel. For the command path, track the
last-focused panel via `panel.onDidChangeViewState` and operate on THAT, not `values()[0]`.
At minimum, `quantbookCellGrid` should refuse-or-replace a prior session (and `close()` it)
rather than leak.

### H2 — Engine cell-diagnostic tooltips are dead end-to-end: UDF `#CALC!`/`#TIMEOUT!` reasons never surface
`cellGridPanel.ts:284-312` (`render()`), `cellGridLogic.ts:879-946`
(`buildCellDiagnosticMessages` / `attachCellDiagnostics`), webview `index.ts:217-236`
(hover reads `entry.diagnostic`).

The webview faithfully surfaces `entry.diagnostic` as a hover `title` (index.ts:229), and the
pure helpers `buildCellDiagnosticMessages` + `attachCellDiagnostics` exist to fold
`SessionInstance.pollEvents()` `cell_diagnostic` events onto error cells. **But `render()` never
calls them** — it does `acquireWorkbookSnapshot` → `extractSheetSnapshot` → push, and
`extractSheetSnapshot` never sets `diagnostic` (the snapshot carries values, not events). Grep
confirms the ONLY callers of `attachCellDiagnostics`/`buildCellDiagnosticMessages` are the DEAD
`cellGridHtml.ts` and the test suite. Result: when a UDF cell computes to `#CALC!`/`#TIMEOUT!`/
`#CALC!(no worker)`, the cell shows the bare error string with **no explanation**, even though
the engine emitted a structured diagnostic for it and the whole tooltip apparatus is wired on the
webview side. This is a lost-error integration seam (No-Fallbacks spirit: the failure reason is
produced but silently dropped before the user).

**Minimal fix:** in `render()`, after `extractSheetSnapshot`, drain `session.pollEvents(cursor)`
(threading a per-panel cursor), `buildCellDiagnosticMessages(events, sheet)`, then
`attachCellDiagnostics(snapshot, messages)` before storing `latestSnapshot`. (If UDF eval is
out of v1 scope for the grid, the dead helpers + the webview hover branch should be removed so the
dead-path isn't mistaken for working — but the functions are clearly intended to be live.)

### H3 — `errorReply` to a hidden (not-disposed) panel is silently dropped despite `retainContextWhenHidden`
`cellGridPanel.ts:384-408` (`onError`), `:109-112` (panel options).

The `onError` callback only falls back to `showWarningMessage` when `this._disposed`. For a
panel that is HIDDEN (tab in background) but not disposed, `webview.postMessage(reply)` returns a
promise resolving `delivered === false` (VS Code does not deliver to a hidden webview unless it is
visible OR queues — and queuing is not guaranteed for background tabs). The code DOES handle
`!delivered` with a `showWarningMessage` fallback (good), BUT the panel here uses
`retainContextWhenHidden: true`, under which VS Code **does** keep the message channel and the
webview re-applies on reveal — so in the common case delivery is fine. The real seam is the
COMMENT at `:386-388` claiming the disposed-OR-`retainContextWhenHidden:false` case, which is
stale: this panel is always `retain:true`. More importantly, the success path
(`postRenderIfReady`, `:320-335`) has the SAME `!delivered` branch but only `console.warn`s — a
dropped *render* (vs errorReply) is downgraded to a log, so a cell edit that committed in the
engine but whose repaint was dropped leaves the grid showing **stale values with no user-visible
signal**. That is an asymmetry: errorReply non-delivery escalates to a warning toast, render
non-delivery does not. Given `retainContextWhenHidden:true` this is low-probability, but it is a
real No-Fallbacks gap on the most important message (the post-commit repaint).

**Minimal fix:** treat a dropped `render` the same as a dropped `errorReply` — on
`delivered === false` surface a visible warning ("the grid may be showing stale values; run
Refresh Cell Grid"), not just a `console.warn`. And correct the `:386-388` comment.

## MEDIUM

### M1 — `refreshAll` after a sheet op refreshes EVERY panel of EVERY session, including unrelated workbooks
`cellGridPanel.ts:155-166`, `quantbookCommands.ts:469, 542, 609, 672`.

`refreshAll()` iterates the global `panels` map. After "Add Sheet" on session A, it re-renders
panels bound to session B too. Each B panel re-acquires via its shared delta cache — harmless for
correctness (B's snapshot is unchanged) but it (a) wastes a full delta round-trip per unrelated
panel and (b) muddies the `refreshed N panel(s)` log/warning so a B-panel render failure is
attributed to the A sheet op ("the sheet change succeeded but 1 panel failed to re-render" — the
failing panel is on a different workbook). Couple with H1: with the session-keyed fix, scope
`refreshAll` to the mutated session.

### M2 — Switch-sheet uses `listSheets()` id order, but the grid renders snapshot display order — pickers can disagree with reality
`quantbookCommands.ts:313` (`buildSheetQuickPickItems(sheetInfos.map(s => s.id), ...)`),
`:505, 578, 645` (`buildSheetManagementQuickPickItems(sheetInfos, ...)`).

The switch/rename/delete/move pickers are built from `session.listSheets()`. After a
`moveSheet`, the engine's `workbookSnapshot` iterates `sheet_display_order` (types.ts:626), so the
GRID title/order reflects display order — but it is not verified that `listSheets()` returns the
SAME display order (the `SheetInfoJson` doc at types.ts:1844 says "live (non-tombstoned) sheets"
with no ordering guarantee). If `listSheets()` is id-sorted while the snapshot is display-ordered,
the move-position picker's "(between Sheet X and Sheet Y)" adjacency labels (cellGridLogic.ts:626-
637) describe a DIFFERENT order than the user sees, producing wrong moves. Verify `listSheets()`
order == snapshot display order; if not, build the management pickers from `snapshot.sheets`
(as `buildSheetManagementQuickPickItems`'s own docstring at cellGridLogic.ts:556-571 prescribes —
"Reads sheets from a WorkbookSnapshotJson so we get display-order"), not from `listSheets()`.

### M3 — Switch-sheet to a deleted/never-rendered sheet shows an empty grid with only a console warning
`cellGridPanel.ts:284-297` (tombstone branch), `quantbookCommands.ts:322` (`show` after pick).

If the user deletes the current sheet (panel still open, now showing empty grid +
`console.warn`), then runs Switch-Sheet, the deleted sheet is filtered from the picker (good). But
the still-open panel for the deleted sheet remains registered at `panels[deletedId]` and renders
an empty grid forever with only a `console.warn` (`:293-297`) — no user-visible "this sheet was
deleted; close the panel" surface. No-Fallbacks-adjacent: the state is anomalous but the only
signal is a dev-console line the user never sees.

**Fix:** when `extractSheetSnapshot` returns null on a sheet that USED to exist, post a one-time
visible notice (status-bar item or a webview banner), or auto-close the panel.

### M4 — `webviewReady` re-handshake on webview reload is handled, but the readyWatchdog is one-shot
`cellGridPanel.ts:130, 342-352, 374-379`.

`armReadyWatchdog()` runs ONCE from `show()`. The webview entry guards
`acquireVsCodeApi` against re-eval (index.ts:60-62) and re-posts `webviewReady` on every load,
and the host re-marks ready + re-sends on each handshake (`:374-379`) — good. But if a
"Developer: Reload Webviews" tears down and rebuilds the bundle and the SECOND load fails (e.g.
bundle deleted between loads), there is no re-armed watchdog: the first handshake already cleared
it (`:355-360`), and `webviewReady` stays `true`, so a post-reload blank grid would NOT surface
the loud error. Low-probability (bundle is a local file) but a real gap in the "fail loud if the
bundle never loads" guarantee across reloads.

### M5 — `closeSessionQuietly` swallows a close error to a log-only line on the Open path
`quantbookCommands.ts:60-67`, used at `:399, 408, 424, 430`.

Per CONTEXT's No-Fallbacks rule, a swallowed error is flagged. `closeSessionQuietly` catches
`session.close()` failures and only `log.appendLine`s them (no toast). This is the documented
"underlying error logged at a system boundary" exception (the session is being discarded), so it
is borderline-acceptable — but the user gets NO visible signal that a displaced workbook failed to
release its native handle (a resource leak they can't see). At minimum it is worth a
`showWarningMessage` when close fails, since a leaked engine session is a real (if rare) problem.
Flagging per the audit mandate; severity MED because it's at a genuine boundary.

## LOW

### L1 — Protocol: webview→host `webviewReady` is intercepted in the panel, but the host's unknown-type log lives in the dispatcher
`cellGridPanel.ts:374` vs `cellGridLogic.ts:319-321`. Symmetric and correct (both ends
`console.warn` unknown types: webview index.ts:283, host cellGridLogic.ts:320). One asymmetry: the
host drops `presenceUpdate`/`typing_stroke` SILENTLY (no log, cellGridLogic.ts:316-318) — dormant
collab, documented — but the webview never emits them anymore, so this is pure dead defense. Fine
to keep; noting for completeness.

### L2 — `putValue` sheet-mismatch is dropped with only a `console.warn`, no errorReply
`cellGridLogic.ts:344-347`. If a future multi-sheet panel multiplexes and sends a wrong sheet,
the edit vanishes with no user-visible signal (the webview leaves the input open pending a
render/errorReply that never comes → the cell looks stuck). Single-sheet panels can't hit it
today (the webview bakes `fullSnapshot.sheet`), so LOW. Consider an errorReply instead of a silent
drop so the webview can re-arm.

### L3 — `commitEdit` captures `editState.entry` at beginEdit; a render between begin and commit doesn't refresh it
webview `index.ts:147, 168-179`. `applyRender` calls `cancelEdit()` (index.ts:113) so an
in-flight edit is dropped on any inbound render — meaning a render arriving mid-edit silently
discards the user's typing with no notice. Coordinates are absolute so no corruption, but the lost
keystrokes are invisible. Acceptable for v1 (render == committed state) but worth a UX note.

### L4 — `errorCells` keyed by `"row,col"` is sheet-implicit; correct only because the webview is single-sheet
webview `index.ts:90, 274`. The error map has no sheet component; safe today (one sheet per
webview) but a latent hazard if the panel ever multiplexes sheets — an error on (r,c) of sheet 1
would decorate (r,c) of sheet 2. Mirror of L2's single-sheet assumption.

## Cross-cutting notes (not separate findings)

- **The happy-path single-panel loop is sound.** click → `hitTestViewport` (sticky-header reject
  in local coords first, correct) → `beginEdit` overlay → Enter → `putValue` → dispatcher classify
  (`=`→`setFormula` with leading-`=` stripped; else `classifyCellInput`) → `recalcDirtyChecked`
  (surfaces non-`completed` op state loud) → `onCommit` → `render` → `acquireWorkbookSnapshotViaDelta`
  (full-seed vs delta, `fullRebuildRequired` re-fetch, schema-version asserted on BOTH paths) →
  `postRenderIfReady` → `applyRender` → canvas redraw. No ordering race within one panel (extension
  host JS is single-threaded; renders that share a per-session cache are sequential).
- **Shared per-session delta cache (`SESSION_DELTA_CACHES` WeakMap, cellGridLogic.ts:1201) is
  correct** for multiple panels on ONE session and matches the engine's per-session snapshot model.
  It is keyed by `SessionInstance`, so distinct sessions get distinct caches — fine. (The H1 bug is
  about the PANEL registry, not this cache.)
- **Open-replaces-workbook** (`quantbookCommands.ts:366-435`) is carefully ordered: open new FIRST,
  validate it has a live sheet, THEN `disposeAll()` + close displaced sessions, THEN `show`. The
  `displaced` set excludes the new session before closing (`:422-423`). This is the one place
  multi-session is handled correctly — which makes H1's omission elsewhere more glaring.

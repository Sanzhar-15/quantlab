## Why this existed

The FE-1 shootout cleared the **edit** round-trip (`set_value`/`write_range` → recalc → delta) by ~1000×, but it
**explicitly did not measure the reactive moat path** — the one FE-1.5 acid #1 actually depends on:

> a Python var/frame is **published** into the sheet → the engine **dirties the dependent formula cells** → those
> dependents **recompute** → they surface in the next delta.

That `publish_dataset → dirty dependents → recalc → snapshot_delta` round-trip is the intrinsic cost of *reactive
invalidation*. FE-1.5-0 measures it headless — **before** the multi-week kernel-reactivity glue (Marimo AST +
`post_run_cell`, FE-1.5-1) is built on top of it — so the substrate is proven end-to-end and the number is known first.
**No kernel/reactivity glue is in scope here**: this drives `publish_dataset` directly from a client, exactly as the
FE-1 shootout drove `set_value`.

## Method

Same two-workload contract + per-stage breakdown as FE-1, with `publish_dataset` substituted for the direct write:

- **Workload A — reactive single-publish** (gate A.p50 < 100ms): a dependent formula `C1 = B1*2` is set once; then
  1000× `{ publish_dataset("a", {"values":[[v]]}, B1) → recalc_dirty → snapshot_delta(version) }`. `publish_dataset`
  writes B1 and dirties C1; recalc recomputes C1.
- **Workload B — reactive 1000-cell frame publish** (gate B.p50 < 200ms): a **100×10 = 1000-cell** frame is published
  (rows 10–109, cols A–J), with **100 dependent formulas** in col K — one per row, each an explicit 10-term cell-ref sum
  `A{n}+…+J{n}`. 50× `{ publish 1000-cell matrix → recalc_dirty → snapshot_delta }`. 100 dependents recompute per publish.

**The reactive PROOF (not a write echo):** every timed iteration asserts the **dependent** cell(s) — which `publish_dataset`
never wrote — are present in the delta's `changedCells`. They can only be there because recalc recomputed them after publish
dirtied them. For A that's `C1`; for B it's the **entire K column — all 100 row-sum dependents** (the delta's set of K-column
rows must equal the full published range, not just the first, so a bug recomputing only one row fails the guard). The harness
fails loud (No-Fallbacks) if any iteration falls short (all 1000 A-deltas and all 50 B-deltas passed). End-to-end value is
also read back (`C1 == 2·v`; the first row-sum `== 10·base + 45`).

> Implementation note: a literal range `SUM(A{n}:J{n})` is a **documented v1 binder defer** (AggregateArg-side literal
> RangeRef), and the bindings expose no named-range API — so the row dependents use individual cell refs, the proven
> form (cf. core test `publish_dataset_dirties_dependents`, `B1*2`). Same arithmetic, supported binder path.

Host: **Apple M4 Max**, macOS 26.5 arm64, Node v22.21.1, Python 3.12.13.

## Results

**Two legs measured** — `reactive-pyo3` (in-process lower bound) and `reactive-nodehost`, the **actual shipped topology**
(Python client → Node extension host owning the napi Session → engine), so the verdict is not an extrapolation.

```
WORKLOAD A — reactive single-publish ×1000 (ms)               gate: p50 < 100
leg                topology                              p50      p95      p99      stages pub/recalc/delta (ms)
reactive-pyo3      engine-in-python (publish→recalc)     0.0125   0.0143   0.0175   0.0080 / 0.0015 / 0.0030   PASS
reactive-nodehost  python→node-napi (publish→recalc)     0.0490   0.0738   0.1052   0.0183 / 0.0132 / 0.0182   PASS  ← shipped path

WORKLOAD B — reactive 1000-cell frame publish ×50 (ms)        gate: p50 < 200
leg                topology                              p50      p95      p99      stages pub/recalc/delta (ms)
reactive-pyo3      engine-in-python (publish→recalc)     1.0882   1.3555   1.6802   0.4363 / 0.0700 / 0.5770   PASS
reactive-nodehost  python→node-napi (publish→recalc)     2.1169   2.3185   2.3903   0.4151 / 0.0842 / 1.6012   PASS  ← shipped path
```

For reference, the EDIT-path equivalents (same host): pyo3 A 0.0105ms / B 0.945ms; nodehost A 0.065ms / B 2.30ms.

## Verdict

**The reactive path clears both gates by ~1000×, and the reactive overhead over a plain edit is negligible.**
- Reactive single-publish (A) costs essentially the same as a plain edit: the dependent recompute adds **~0.002ms**
  in-process (pyo3 0.0125 vs edit 0.0105) and the shipped path is **0.049ms** (p99 0.105ms).
- For the 1000-cell frame (B), the **100-dependent recompute** shows up as the `recalc` stage — **0.07ms** in-process
  (vs ~0.0004ms for the edit path with no real dependents) — i.e. the reactive recompute of 100 formula cells over a
  1000-cell published frame is **sub-0.1ms**. Total B stays ~1–2ms, far under the 200ms gate.

**Consequence:** the FE-1.5 reactive **engine substrate is proven end-to-end and is not a latency risk.** What remains
for FE-1.5 is the *kernel-side reactivity glue* (turning a Python cell re-execution into a `publish_dataset`) and the
*engine→grid dirty-notify channel* — neither of which is engine-recompute-bound. The moat's remaining risk is
integration/correctness, not speed.

## Caveats (stated honestly)

1. **Hardware:** M4 Max is fast; even 5× slower the reactive frame B is ~5–10ms, still ~20–40× under budget.
2. **Light formula compute:** the dependents are cheap (`*2`, 10-term sums). A real model with thousands of heavy
   dependent formulas adds **engine recalc compute** — that is engine recalc performance (separately benchmarked),
   orthogonal to the publish→dirty→delta *mechanics* this measures. The `recalc` stage column isolates it (and it's tiny here).
3. **Publish→recalc is measured; the kernel-publish leg is NOT.** This drives `publish_dataset` directly. The cost of a
   Python cell re-execution *deciding what to publish* (Marimo AST scope + `post_run_cell` fingerprint) is FE-1.5-1 glue,
   not measured here. What's proven: once the kernel calls `publish_dataset`, the reactive recompute round-trip is free.
4. **Engine→grid dirty-notify channel not exercised.** The harness reads dependents back via `snapshot_delta` (the grid's
   render path). Whether the kernel-owned Session *pushes* a dirty-notify to the grid host, or the grid polls
   `snapshot_delta`/`pollEvents`, is an FE-1.5 wiring decision — not a latency one (delta read is already in these numbers).
5. **Re-publish under a stable `name`** reuses provenance (intended). The loop publishes under one `name` per workload —
   the steady-state reactive case.
